### Шаг, а не вызов инструмента {#step-not-tool-call}

Маршрутизатор опрашивается **один раз на вызов чат-модели**, перед
`provider.chat` (AT-235). Шаг может нести несколько вызовов инструментов —
десять `emit_artifact` в ответе Criativo, `terminal` + `read_file` в ответе
dev, — поэтому опрос Jev по разу на `tool.call` задавал бы вопросы, которых
продукт никогда не задаёт, с `state`, уже содержащим соседние вызовы того же
шага.

У event log нет маркера шага (AT-235, пробел 1), поэтому граница берётся из
`token_usage`: api записывает строку на вызов LLM **до** того, как engine
запишет `tool.call` этого ответа. Каждый `tool.call` той же сессии и того же
актора между двумя последовательными строками — один и тот же шаг. Отсюда
три метки:

- шаг с **одним** инструментом (один или несколько его вызовов): метка = этот
  инструмент;
- **разнородный** шаг (два разных инструмента): попадание = выбор Jev — один
  из них, — но ограничение меню одним инструментом отрезало бы остальное;
- шаг **без** `tool.call` после своей строки: модель ответила текстом (или
  упала). Это единственная метка, которую `responder_sem_ferramenta` может
  получить этим методом, — бриф не ожидал ни одной; граница шага даёт семь.

Моменты сравниваются как **текст** UTC фиксированной ширины с
микросекундами: строка расхода и первый `tool.call` шага иногда попадают в
одну и ту же миллисекунду.

### Отправляемый `state` {#the-state-sent}

Формат AT-235, вырезанный из того, что существовало **до** шага: `agente`;
`pedido` — для разговорных агентов последнее `chat.message`, написанное
**пользователем**; для dev agents и gates задач — заголовок задачи из
`dev.working`; `contexto` — идентичность агента плюс строка
`agent_instructions` проекта, когда она есть (два слоя системного промпта, а
не весь собранный промпт); `passos_recentes` — последние 6 вызовов этого
актора в этой сессии, с аргументами и результатом, обрезанными до 500
символов. Вопрос — `choice`, чьи `criteria` — это `{name: description}`
каталога плюс зарезервированный `responder_sem_ferramenta`.

Запрос идёт в `POST https://openrouter.ai/api/alpha/decisions` с моделью
`typesafe/jev-1.13`. Исправление к AT-235, измеренное: **`questions` — объект,
индексированный по id вопроса**, а не список — списочная форма получает
`400 expected record, received array`. Ответ —
`answers.<id>.{choice, probabilities, confidence}`, `usage.{input_tokens,
output_tokens, cost}`, `id` (`gen-dec-…`) и датированный снимок в `model`
(`typesafe/jev-1.13-20260917` в каждом ответе этого исполнения).

## Кривая уверенности по принятому правилу {#the-confidence-curve-under-the-decided-rule}

AT-236 решила (ответы 7 и 12), что маршрутизатор **только ограничивает**
меню и что `responder_sem_ferramenta` — с любой уверенностью — отправляет
**весь** каталог в v1. Поэтому шаг *ограничивается*, только когда уверенность
на пороге или выше **и** выбор — инструмент; всё остальное ведёт себя как
сегодня. Дорого стоит ошибка ограничения **не тем** инструментом.

**Порог.** Ни у одного порога сетки нижняя граница интервала не достигает 90%
или выше — ни в целом, ни в какой-либо группе. Единственная точка без

шагов (2%) — с нижней границей 65%. Эта выборка не поддерживает порог; если он
будет зафиксирован по ней, 0.80 — значение, на которое она указывает, с таким
покрытием. Ответ 4 AT-236 просит стоимость каждого типа ошибки, которую этот
повтор оценить не может.

## Чего повтор не видит {#what-the-replay-cannot-see}

- **Первое сообщение цикла.** Агент `ToolLoop` (dev agents, gates, Anamnese,
  Infra-Workflows) начинает с пользовательского сообщения, собранного в коде, —
  задача, история, карта модулей, — которое никогда не доходит до event log. У
  повтора есть лишь заголовок задачи для dev agents и gates задач и ничего
  для `qa-estrategia`, `appsec`, `anamnese` и `infra-workflows`. `state`
  продукта нёс бы это сообщение. 0/16 у `qa-estrategia` (Jev каждый раз
  отвечал `responder_sem_ferramenta`) измеряет слепоту повтора так же, как и
  Jev; эти строки — нижняя граница и ничего не должны решать.
- **Остальной системный промпт.** `contexto` — это идентичность и строка
  инструкции проекта, а не собранный промпт (бизнес-правила, состояние задачи,
  файлы).
- **Верна ли метка.** Модель, выбравшая инструмент, — не эталон; 157 шагов
  помечены как подозрительные и сообщаются отдельно («без подозрения»).
  Согласие ниже на чистых шагах (31%), чем в целом (47%): подозрительные шаги
  — в основном падающие вызовы `terminal` от dev agents, которые Jev тоже
  склонен выбирать, — поэтому плохо размеченные шаги не объясняют
  несогласия.
- **Эффект.** Ограниченное меню меняет то, что модель делает дальше; повтор
  лишь сравнивает выбор с записанным. Становятся ли ходы короче, быстрее или
  дешевле — это AT-239.

### Протокол (записан до любого исполнения) {#protocol-written-before-any-run}

- **Только то, что продукт может произвести во время выполнения, до шага.**
  Ничто от целевого шага не попадает в `state`: ни инструмент, который он
  вызвал, ни аргументы, ни результат, ни текст, который модель написала на
  том же шаге (`Passo.texto` читается только из *предыдущих* шагов;
  `variantes.spec.ts` утверждает для каждого варианта, что вызов, аргумент,
  результат и текст целевого шага отсутствуют). Каждое новое поле имеет
  источник в engine, процитированный в заголовке `scripts/jev/variantes.ts`.
- **Классы эквивалентности зафиксированы в `scripts/jev/equivalencia.ts` до
  запуска**, исходя из семантики инструментов, и сообщаются рядом со строгим
  правилом (правилом первого раунда, чтобы 47% оставались сопоставимыми). Три
  накопительных слоя: **E1** `terminal`, чья команда лишь
  читает/перечисляет/ищет (`ls`, `find`, `cat`, `pwd`, `grep`, `head`,
  `git status/log/diff`… — составная команда считается по самому сильному
  сегменту, исполнение > запись > чтение) ≡ `read_file`/`search_workspace`;
  **E2** `read_file` ≡ `search_workspace`; **E3** `terminal`, пишущий файл
  (перенаправление, heredoc, `tee`, `sed -i`, `cp`, `mv`, `touch`) ≡
  `write_file`. Асимметричны намеренно: выбор Jev `terminal` подходит только к
  вызову `terminal`, а команда, которая *исполняет* (`npm`, `node`, `rm`,
  `mkdir`, `git commit`…), не эквивалентна ничему, кроме `terminal`.
  **Заголовок — полное правило (E1+E2+E3), строгое правило рядом.** Ничего не
  переклассифицировалось после просмотра результата; 3 ошибки, которые классы
  всё ещё допускают, посчитаны как таковые ниже.
- **Настройка × проверка по исполнению, а не по шагу.** Группа — это
  исполнение `ToolLoop` (задача dev agent, раунд gate) или, для разговорных
  агентов, вся сессия агента. Группы упорядочиваются по хешу имени, и каждая
  идёт в ту половину, где к этому моменту меньше шагов, — детерминированно и
  слепо к любому результату. 328 пригодных шагов: **167 настройки, 161

43 ошибки, оставшиеся после последней восстановленной детали, прочитаны по
одной (не выборка): отправленный state, вызванные инструменты, собственный

уверенность Jev. Результат:

- **Мерка, 3.** `dev-board-engine` `terminal`→`search_workspace`: команда агента
  была `find … | sort; ls; for f in docs/*; do …cat` — только чтение, но цикла
  `for` нет в списке «только чтение», поэтому он оценивается как исполнение.
  Плюс два `read_file`→`terminal`, где агент всё время читал через
  `terminal`: эквивалентны при любом прочтении, но классы асимметричны
  намеренно, и это не переоценивалось.
- **Вход, 7.** Все ошибки `infra` (2 шага), `infra-workflows` (2) и `dev-lead`
  (1) — пять шагов, первое сообщение которых перенос не восстанавливает, —
  плюс два `report_done`→`terminal`, где результата последней команды
  («exit 0, a suíte passou») нет в логе. Вариант `acoes` восстанавливает эти
  результаты и в целом сделал Jev *хуже* (61%): перед падающей песочницей он
  говорит `report_blocked` там, где агент продолжал пытаться.
- **Темп агента, 29.** Jev называет *следующий этап* потока, а агент остаётся
  ещё на шаг в текущем:
  14 × `write_file`→`terminal` (Jev: «тесты написаны, запустите их», 8 из них с

  12 × `qa-estrategia` `read/search`→`emit_plano_de_teste` (Jev перескакивает к
  финальному инструменту kickoff с уверенностью 0,25–0,56; агент исследовал
  ~15 шагов, прежде чем выпустить), 2 × `appsec` то же самое, 1 ×
  `terminal`→`report_blocked` после отклонённого действия. Во всех них выбор
  Jev — то, что читатель лога назвал бы естественным следующим шагом. То, что
  решает «сколько ещё файлов, сколько ещё чтений», — это план модели, которого
  нет ни в одном поле, которое продукт мог бы передать маршрутизатору, — он
  существует, один раз, в самом тексте предсказываемого шага.
- **Jev расходится, 4.** `write_file`→`search_workspace` дважды с уверенностью
  0,25–0,26, `rag_search`→`terminal` дважды (0,24, 0,59). Это единственные шаги,
  где state не объясняет выбор: 2,5% шагов.

**пятая часть была меркой, около двух пятых — входом, которого не хватало
повтору** (а восстановимая его часть восстановлена), **и две пятых — темп
агента**, причём **5% шагов — чистая ошибка Jev**. От входа остаётся максимум
4 пункта, и это не то, что отделяет 73% от 90%.

### Чего этот раунд всё ещё не видит {#what-this-round-still-cannot-see}

- **Историю** двух gates, которые работают до любого кода (`qa-estrategia`,
  `appsec`): запрос, запускающий их, внутренний и не идёт в лог.

  системный промпт за `contexto`.
- **Эталон.** Метка по-прежнему — инструмент, который вызвала чат-модель, и
  большинство из 29 ошибок темпа — выборы, которые человек-читатель назвал
  бы разумными, и именно поэтому top-2 и объединение говорят больше, чем top-1.
- **Эффект.** Ограниченное меню меняет то, что модель делает дальше; AT-239.

### Политики (записаны до запуска, в `scripts/jev/menu.ts`) {#policies-written-before-running-in-scriptsjevmenuts}

Политика превращает ответ Jev в ограниченное меню. Решения владельца
действуют везде: Jev только **ограничивает** меню, а когда он отвечает
`responder_sem_ferramenta`, остаётся **весь** каталог (AT-236); потолок
2 000 мс (во втором раунде его не превысил ни один из 328 запросов). Ничего
не переклассифицировалось после просмотра результата; `menu.spec.ts`
фиксирует, что возвращает каждая политика.

| политика | меню |
|---|---|
| P0 | весь каталог (якорь: 100% покрытия, ничего не ограничивает) |
| P1 | два самых вероятных инструмента Jev |
| P2 | {выбор Jev, предыдущий инструмент того же исполнения} |
| P3 | P2, но если Jev говорит `responder_sem_ferramenta` (или предыдущего инструмента нет), меню — весь каталог |
| P4 | {выбор, предыдущий инструмент, второй вариант Jev} (до 3; только для справки) |

Правила, общие для всех: упавший ответ (таймаут, ошибка, выбор вне вариантов)
оставляет весь каталог; предыдущий инструмент, которого нет в каталоге
агента, игнорируется; меню, которое вышло бы пустым, — весь каталог.

**Покрытие** = доля шагов с инструментом, на которых инструмент, который агент
действительно вызвал, находится *внутри* меню, — строго (то же имя) и по
эквивалентности (классы E1–E3 второго раунда, так что меню с `read_file`
покрывает `terminal`, который лишь читает). **Доля ограничения** = доля
шагов, на которых меню меньше каталога агента: политика, которая почти
никогда не ограничивает, тривиально «100%» и бесполезна, поэтому покрытие
даётся также *среди ограниченных шагов*. Вариант `escopo` (победитель второго
раунда), половина проверки, 160 шагов с инструментом (плюс 1 без).

  заработано 160 шагами.

### Потолок: чего не говорит покрытие {#the-ceiling-what-coverage-does-not-say}

**Покрытие — это потолок сквозной точности, а не точность.** Меню содержит
правильный инструмент; модели агента ещё нужно выбрать его среди вариантов.
Метка («инструмент, который вызвала чат-модель») — выбор, сделанный агентом
*из всего каталога*, поэтому полное меню — 100% по построению, а ограниченное
может только терять. Что можно сказать без продукта, для P3 на проверке,
разделив 160 шагов:

- **99 (62%, 54–69%)**: каждый инструмент меню верен, поэтому любой выбор
  агента верен — пол.
- **46 «спорных»**: ровно один из вариантов верен, и агент решает сам — 28
  только предыдущий инструмент, 18 только выбор Jev. Агент, всегда берущий
  предыдущий инструмент, заканчивает на 127/160 = 79%; всегда берущий выбор
  Jev — на 117/160 = 73% (снова базовые линии второго раунда); бросающий
  монетку — на 76%. Агент, выбирающий лучше обоих, а на этом и строится вся
  ставка, попадает между 79% и потолком 91%.
- Остальные 15 вне меню: потеряны, что бы ни делал агент.

Итак, сквозной диапазон — от 62% до 91%, и где он окажется, зависит от того,
насколько хорошо модель агента читает *ситуацию*, которую повтор не видит.
**Ответить на это может только живой тест (AT-239).**

### Экономия на определениях инструментов {#savings-in-tool-definitions}

Каталог содержал *описание* каждого инструмента (`catalogo.json`), а теперь
ещё и `definicoes`: размер в байтах полного `spec/0` каждого инструмента (имя,
описание и схема параметров), сериализованного engine (`catalogo.exs`,
запущен заново; остальная часть файла не изменилась). Токены — это байты,
делённые на 4, приближение, которое использует весь повтор. На проверке P3
уходит с **746 до 138 токенов определений на вызов — 608 токенов, на 81%
меньше**: восемь инструментов dev agent весят 3 068 байт, а меню из двух —
около 500. P1 экономит 596, P2 — 644 (средние по шагам половины; половина
настройки экономит меньше, потому что Anamnese сохраняет весь каталог).

Сколько это стоит — другой вопрос. Сам вызов Jev читает ~1 870 токенов
(US$ 0,0000769) на модели гораздо дешевле модели агента; экономия на
определениях — 608 токенов модели агента на вызов. Точка безубыточности —
входная цена US$ 0,126 за миллион токенов (0,0000769 / 608): выше неё экономия
окупает вызов Jev, без учёта кеша. **Кеш — подвох**: провайдеры кешируют
префикс запроса, определения инструментов идут первыми, а меню, меняющееся от
шага к шагу, меняет префикс — экономия может быть возвращена промахами кеша.
Это живое измерение, и причина, по которой тест ниже записывает долю
кешированных токенов.

### Живой тест (не выполнен): схема {#the-live-test-not-run-design}

- **Вопрос.** С P3 перед агентом ухудшается ли работа агента, и насколько она
  дешевеет? Не «есть ли инструмент в меню» (это этот раздел).
- **Этап 1, тень (дёшево, до того как пользователь увидит меню).** Для каждого
  шага зарезервированной выборки спросить *саму модель агента* дважды об одном
  state, с полным каталогом и с меню P3, и сравнить инструмент, который она
  выбирает, по правилу эквивалентности. Метрика: согласие между двумя, с
  нижней границей 95% интервала. Чтобы показать истинное согласие 94% с нижней
  границей 90% (мощность 80%): около **390 шагов**, взятых из **не менее чем 40
  разных исполнений** и **более чем одного проекта** (в этой выборке 21
  исполнение в одном проекте), интервал по кластеру (исполнению), а не по шагу.
- **Этап 2, живой A/B, только если этап 1 пройден.** Ветви: контроль (полный
  каталог) и P3, разыгрываемые **по исполнению**, никогда по шагу (меню одного
  шага формирует следующий). Основная метрика: исполнение доходит до gate без
  переделки, допуск не меньшей эффективности 5 пунктов; при 80% завершения,
  5% одностороннем и мощности 80% — около **790 исполнений на ветвь** (допуску
  10 пунктов нужно около 200). При объёме этого проекта (7 исполнений dev во
  всей выборке) это требует многих проектов или недель. Вторичные: шаги на
  исполнение, входные токены *включая долю кешированных токенов*, стоимость
  исполнения, задержка, добавленная Jev (p50/p95, потолок 2 000 мс), и доля
  шагов, на которых Jev оставляет весь каталог.
- **Стражи.** Флаг отключения на проект; откат на весь каталог при любом сбое
  Jev или выше потолка задержки (уже в каждой политике); способ для агента
  запросить полный каталог, когда в меню нет нужного (меню из одного вынуждает
  инструмент, 61% шагов здесь); промежуточный просмотр каждые 100 исполнений с
  остановкой, если основная метрика падает больше допуска; Anamnese вне выборки
  (приостановлена); меню и выбор записываются на каждом шаге, чтобы анализ был
  запросом, а не воспоминанием.

### Чего этот раздел всё ещё не видит {#what-this-section-still-cannot-see}

- **Выбор агента внутри меню**: причина, по которой это потолок.
- **Зависимость между шагами**: 10 кластеров в проверке; интервалы — по
  шагам.
- **Кеш промпта** и **задержка в цикле агента**: не измерены (вызов Jev
  измерен, p50 317 мс; его эффект в цикле — нет).
- **Метка**: по-прежнему инструмент, который вызвала чат-модель, а
  ограниченное меню меняет то, что она делает дальше.

### Что запускает инструмент и что является переносом {#what-the-instrument-runs-and-what-is-a-port}

`pnpm --filter @brabo/scripts jev:vivo` (файлы в `scripts/jev/vivo/`) запускает
цикл dev agent на пяти маленьких задачах, один раз с включённым
маршрутизатором и один раз с выключенным, и вызывает OpenRouter напрямую —
api, engine и база не участвуют, как в платной проверке языка AT-167.

| файл | роль | продукт или перенос |
|---|---|---|
| `roteador.ts` | `recortarEstado`, `montarPedidoAoJev`, `lerRespostaDoJev`, `menuP3`, потолок `state` | **код продукта**, реэкспортированный из `apps/api/src/domain/llm/tool-router.ts` |
| `laco.ts` | цикл: потолок итераций, восстановление вызовов инструментов, написанных текстом, остановка на принятом `report_done`/`report_blocked`, единственная повторная попытка с полным каталогом, когда ограниченное меню получило ответ без инструмента | перенос `ToolLoop`, `EngineApiClient.llm_turn/5` и `DecidirFerramentaDoPassoUseCase` |
| `recuperacao.ts` | какие шаги прошли через `tool_call_recovery.ex` | перенос; его spec прогоняет случаи `tool_call_recovery_test.exs` и фиксирует строки-якоря `.ex` |
| `rede.ts` | вызов чата (сообщения на проводе, как их пишет api) и вызов Jev (потолок 2 000 мс, те же именованные падения) | перенос `toWireMessage`/`toWireTool` и `JevToolRouter`; строки-якоря зафиксированы |
| `ferramentas-dev.exs` → `ferramentas-dev.json` | **полный** `spec/0` девяти инструментов `Engine.Dev.Tools.registry/0` (имя, описание, схема параметров) | прочитан из исходников engine чистым `elixir`, без скомпилированного engine; spec падает, когда реестр или описание дрейфует |
| `tarefas.ts` | пять задач над проектом Node без зависимостей, у каждой проверка, запускаемая **после** цикла (исходные тесты восстановлены, скрытые тесты добавлены): «задача вышла» | собственный инструмента |
| `executor.ts` | инструменты в временной песочнице, возвращающие тексты engine там, где они зашиты в код | собственный инструмента |
| `resumo.ts`, `vivo.ts` | таблица, правило решения, оценка стоимости, CLI | собственный инструмента |

Вне инструмента, одинаково в обеих ветвях и заявлено: конвейер одобрения
(`terminal` и `write_file` выполняются напрямую, как в автоматическом
режиме), сжатие контекста, языковая ориентация и профиль автора, добавляемые
в конце каждого вызова, RAG (пустой индекс), контракты модулей (ни одного не
объявлено) и остальная часть настоящего системного промпта (файлы
инструкций, бизнес-правила, состояние задачи). Системный промпт — это
идентичность dev из engine плюс две строки контекста проекта; первое
пользовательское сообщение — собственный kickoff engine
(`scripts/jev/kickoff.ts`). Стоимость каждого вызова — `usage.cost` ответа,
число, которое RN-665 ([ADR 0188](../adr/0188-o-custo-real-do-provider-vira-o-numero-do-metering.md))
кладёт в metering; `token_usage` продукта не участвует.

### Протокол (записан до любого исполнения) {#protocol-written-before-any-run-1}

- **Модели**: `deepseek/deepseek-v4.1-flash` (медленнее, рассуждающая) и
  `anthropic/claude-haiku-4.5` (быстрее), две, до которых проверка AT-167 уже
  дотягивалась с определениями инструментов на этом ключе.
- **Задачи**: `T1-media` (реализовать функцию), `T2-moeda` (исправить баг
  форматирования), `T3-limite` (причина в другом файле: `config/`),
  `T4-slug` (создать модуль и его тесты; скрытые тесты его проверяют),
  `T5-renomear` (переименовать в двух файлах; в `src/` не должно остаться
  следа старого имени). Начальное состояние каждой задачи проваливает
  проверку, а эталонное решение её проходит (spec).
- **Выборка**: 2 раунда → 10 исполнений на ветвь на модель, всего 40. Порядок
  ветвей чередуется по задаче и раунду, чтобы ни одна ветвь не получала
  всегда самую медленную минуту провайдера. Потолок итераций 30 (потолок dev в
  продукте — 60; здесь он ограничивает расход).
- **На исполнение**: шаги; шаги, чьи вызовы пришли **текстом** и прошли через
  восстановление; шаги, на которых маршрутизатор был опрошен, применил меньшее
  меню, оставил весь каталог без падения (нет предыдущего инструмента, или Jev
  сказал `responder_sem_ferramenta`) или **упал** (с причиной и источником
  RN-059); повторные попытки с полным каталогом; вызовы вне меню шага;
  настенная задержка всего исполнения (Jev + чат + инструменты) и части LLM;
  стоимость чата и Jev; как закончилось; вышла ли задача.
- **Правило решения** (`comparar` в `resumo.ts`), по модели, включено против
  выключено: качество — доля «задача вышла» у *включённого* не более чем на
  **10 пунктов** ниже *выключенного*; стоимость — средняя стоимость на вышедшую
  задачу (чат + Jev) у *включённого* не выше *выключенного*; задержка —
  медианное исполнение *включённого* не выше **1,2×** *выключенного*.
  **Оставить включённым по умолчанию**, если все три выполняются на каждой
  модели; **выключить**, если качество проваливается на каждой модели или ни
  одна модель не проходит все три; **ограничить** моделями, которые проходят, —
  в противном случае. Меньше 10 исполнений на ветвь — это
  `amostra_insuficiente`, но никогда не вердикт.

### Рекомендация (измерено — решает владелец) {#recommendation-measured--the-owner-decides}

**Ограничить**, по правилу, записанному до исполнения: оставлять маршрутизатор
включённым там, где у чат-модели нет действующего кеша промпта и она
достаточно медленна, чтобы дополнительный последовательный вызов был мал
(класс Haiku, US$ 1,00/5,00 за миллион), и выключенным там, где провайдер
отдаёт большую часть входа из кеша, а чат быстр (класс DeepSeek). Числа,
которые это оправдывают, — строки правила выше: Haiku ×0,62 по стоимости и
×0,95 по задержке без потери качества; DeepSeek ×2,21 по стоимости и ×1,45 по
задержке без выигрыша в качестве.

Чего это **не** покрывает и чего потребовало бы ограничение:

- **Измерены только dev agents (`ToolLoop`).** Прежнее прочтение — никаких
  свидетельств для семи разговорных агентов — остаётся в силе; ничто здесь на
  них не распространяется.
- **Разделение — по модели, а переключатель продукта — по workspace**
  (`PUT workspaces/:workspaceId/tool-router`). Ограничения по модели (или по
  «действующему кешу») не существует; его создание — новое решение и новое
  изменение, здесь не сделанное. До тех пор измеренный выбор по workspace
  таков: включено, если его агенты работают на модели класса Haiku без кеша,
  выключено, если на модели класса DeepSeek с кешем.
- **Выборка и задачи малы** (10 исполнений на ветвь, пять задач от 4 до 16
  шагов). Отношения стоимости и задержки достаточно широки, чтобы их читать;
  разница качества в одно исполнение — нет.
- **Эффект кеша зависит от кеша провайдера**, а не только от скорости:
  workspace на Haiku с включённым кешем промпта, вероятно, сдвинулся бы к
  линии DeepSeek. Не измерено.

Предварительная рекомендация, которая была здесь до исполнения
(ограничить: включено для dev agents, выключено для разговорных агентов),
заменена вердиктом правила выше, как и говорил тот абзац.

## Как воспроизвести {#reproducing}

```bash
# the catalog, when a tool or an identity changed (inside the dev engine container)
docker cp scripts/jev/catalogo.exs brabo-dev-engine-1:/tmp/catalogo.exs
docker exec brabo-dev-engine-1 mix run --no-start --no-compile --no-deps-check /tmp/catalogo.exs \
  > scripts/jev/catalogo.json

# count the steps and estimate the cost, without calling the network
pnpm --filter @brabo/scripts jev:replay -- --container brabo-dev-postgres-1 --estimar

# the run (resumes: a step already answered in the output is not asked again)
pnpm --filter @brabo/scripts jev:replay -- --container brabo-dev-postgres-1 \
  --arquivo-de-chave ~/.config/brabo/openrouter-test.env --teto-usd 2

# the report again, and the billed cost per generation
pnpm --filter @brabo/scripts jev:replay -- --so-relatorio
pnpm --filter @brabo/scripts jev:replay -- --conferir-custo --arquivo-de-chave ~/.config/brabo/openrouter-test.env
```

Вывод (`$XDG_CACHE_HOME/brabo/replay-jev/respostas.jsonl`, иначе
`~/.cache/…`, права 600) несёт id сессий и остаётся вне checkout — скрипт
отвергает назначение внутри него. Печатаемый отчёт содержит лишь счётчики и
id агентов. Ключ читается из окружения (`OPENROUTER_TEST_KEY`) или из
указанного файла и никогда не печатается и не записывается.

У второго раунда собственная команда, которая читает замороженный снимок базы
(`--dados-cache`, вне checkout) и пишет файл на вариант:

