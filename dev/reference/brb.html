    Registro BRB

    Os achados BRB-NNN são levantados e priorizados no vault do mantenedor (07-backlog/Backlog de Melhorias (Brabo)), que guarda os 33 com prioridade, esforço, origem, proposta e um "pronto quando". Aquele registro é a fonte do que um achado é e de se ele está fechado.

    Este arquivo é a parte que o repositório consegue verificar. Criado pela FASE 29, sessão 1 (fase-29-instalacao-de-uma-linha.md).

    Critério de cobertura

    Todo id de BRB-001 a BRB-033 tem exatamente uma linha, em ordem numérica. Até 2026-09-27 a página listava só os achados que o código podia provar ou refutar — 11 de 33 — e o resto era invisível aqui, inclusive seis que o vault já tinha medido como corrigidos (AT-186). Uma linha por id não custa nada e torna a ausência de evidência visível em vez de silenciosa. Cada linha traz:

    • estado no vault — copiado do registro do vault em 2026-09-27. É decisão do mantenedor e nunca é decidido aqui.
    • medido aqui — o que o repositório mostra, medido contra a dev em 34c1c83bdc em 2026-09-27, salvo quando a evidência data de outro modo.
    • evidência — o arquivo:linha, PR ou execução por trás dessa medição.

    Um achado cujo assunto mora fora deste repositório (as próprias notas do vault, uma decisão de produto, uma credencial paga) ainda ganha linha, marcada não verificável aqui, com o motivo. Um id sem informação nenhuma levaria um TODO(humano) — nenhum leva hoje. Um BRB-NNN novo no vault ganha a linha dele aqui na mesma mudança que o mencionar pela primeira vez.

    Por que este arquivo existe

    BRB-018 é a cara da segunda regra abaixo na prática. Quando este arquivo nasceu nada nele tinha mudado no código — nenhuma reprojeção tinha sido escrita —, mas o repositório ganhou a capacidade de dizer por que ele seguia aberto e quanto custava enquanto seguia, então a linha existiu antes da correção. O comando agora existe (RN-569); a linha fica porque a prova no cluster não existe.

    Dois ids — BRB-005 e BRB-031 — eram citados em cinco documentos daqui, em prosa, sem estado que alguém pudesse conferir. Os outros ids eram completamente invisíveis a este repositório: uma busca no disco inteiro devolveu só esses dois.

    O custo foi medido, não imaginado. O planejamento da FASE 29 listou seis itens BRB como pré-requisitos ou riscos; conferir cada um contra a dev mostrou que dois descrevem defeitos já corrigidos aqui, e que um terceiro tinha sido mal lido só pelo id — ver BRB-004 abaixo, que não é sobre a tag que todo mundo supõe.

    Daí duas regras:

    • Estado se sustenta em arquivo:linha, medido, nunca lembrado.
    • O vault é dono do achado; o repositório é dono da evidência. Onde os dois discordam sobre se algo ainda acontece, o repositório vence — ele é a coisa descrita. Se um item está formalmente fechado continua sendo decisão do mantenedor, no vault.

    O que as palavras de "medido aqui" querem dizer

    São palavras diferentes de propósito. Corrigido seria o juízo do mantenedor, registrado no vault. Defeito não reproduz mais é tudo o que este repositório pode afirmar com honestidade: o comportamento que o achado descreve não é o que o código faz hoje, medido na data da linha. Implementado, ainda não exercitado é mais fraco: o código existe e os testes que podem rodar passam, mas o caminho só executa num lugar que este repositório não alcança — uma tag de release de verdade, na CI. Chamar isso de "corrigido" seria alegar uma prova que ninguém tem. Ainda reproduz e reproduz em parte dizem que o comportamento do achado ainda está lá, no todo ou em parte. Não verificável aqui diz que o achado é sobre algo que este repositório não guarda. Fechar o item — e decidir se a correção cobre tudo o que o achado pediu — fica onde o achado foi levantado.

    BRB-004 é o motivo de a distinção valer o que custa. Lido pelo id, ele parecia o pin de ollama:latest que fechou na #419. Lido no vault, ele pedia digests, que nenhuma imagem tinha. Um id não é uma descrição — e a leitura errada foi o que o manteve aberto enquanto uma regra irmã para uses: já tinha mecanismo desde a #419.

    Mudando uma linha

    O id, o título e a prioridade são copiados do vault ao pé da letra, e o estado no vault também; o estado "medido aqui" e a evidência são medidos aqui. Uma linha muda quando o vault muda o estado dela ou quando uma mudança neste repositório muda o que pode ser provado — nunca para inventar um achado.
