POST-FASE 15 — COMPLETED on 2026-08-08 (v2.5.0 and v2.5.1)​

Not a planned phase: it is what USE found after 15, and it is here because the origin of each item matters. None of this came from a script — it came from browsing the app in Chrome and reading the security panel.

UI defects, found while browsing (RN-088..091):

  • 429 turned into a WHITE SCREEN and the app answered with more traffic. The rule became general: every screen distinguishes THREE states — loading, error (with trace_id and a button) and empty. if (!dado) return null collapses all three.
  • The dashboard made one request per project: 3,824 → 12 req/min, with GET /workspaces/:id/projects-summary. The bell was the missing half: 289 → one request per cycle (RN-090/091).

Security hardening, with both panels at ZERO:

  • ADR 0058 — CSP closed in the api (default-src 'none'), revising item 7 of ADR 0027; and the projectId contained in the root (RN-092), which hit not only permissions.json but the scope that AUTHORIZES the terminal.
  • ADR 0059 — GIT_OAUTH_STATE_SECRET without a default in production (RN-093). The default was PUBLIC (.env.example) and the production compose supplied it as a fallback: requiring "not empty" would have caught nothing, because on the real error path the variable was DEFINED.
  • An alert that didn't hold up was DISMISSED with a written justification, never silenced — and dismissing is the user's decision, not the agent's.

Three operational lessons that cost a CI cycle, and hold as a rule:

  1. Green CodeQL on a PR doesn't prove an old alert closed — the PR check reports a NEW alert. An alert closes on the scan of the DEFAULT branch, that is, only after the fix reaches main.
  2. Gitleaks scans commits reachable from refs/heads/*, not the tree. A high-entropy value committed once fails CI forever on that branch; fixing on top does NOT clean it. The way out is for the commit to stop being reachable (rebuild from dev and DELETE the old branch BEFORE opening the new PR) — never an allowlist, which blinds the scanner on that path for every commit. PR refs are out of scope. A fixture that represents a secret is born WITHOUT entropy.
  3. A barrier that lives in another function CodeQL doesn't see — hence the three js/path-injection surviving the fix. The centralized check was kept (RN-092) and the price was paid on the panel: duplicating it in each caller would be a check that one day diverges.

FASE 29 (sessions 8-10) — the protocol, the picker and the E2E (RN-532..534, ADR 0149/0150/0151)​

FASE 29 (session 8) — the local agent's base gets a consumer (RN-532, ADR 0151 points 3–6)​

In comes the workspace_create/workspace_create_result pair, in the REQUEST WITH REPLY mold of exec/exec_result — and NEVER in that of workspace_confirm, which is ONE-WAY ({:noreply, socket}, pushes nothing back), a precision that the phase had already recorded along with "workspace.verified does NOT exist". FASE 29 (session 5) — the backup starts covering what hurts to lose (ADR 0152, RN-528)​

The backup covered ONE database and ran in ONE place: make test-restore is a Kubernetes path (it requires kubectl, a cluster and the CronJob) and docker-compose.prod.yml had NO backup service at all — migrating a compose installation had no proven path. The decision starts by REFUSING the easy move ("back up all the volumes") and CLASSIFYING the seven: neo4j_data and project_workspaces are derived, ollama_data can be re-obtained, brabo_projects_base is the user's — copying them gives an impression of coverage without adding recovery. The sources of truth are TWO, and the finding is the second: git_local_repos wasn't in any backup, and a project with the local provider keeps its bare repo there — it isn't rebuildable from Postgres (the event log keeps the NARRATIVE, not the git objects), so losing the volume is losing the agents' code. The runbook's prose asserted the opposite ("the real repositories live in GitHub/GitLab") and it is what explains the years without coverage: it holds for github/gitlab, and for local there's no upstream. The file's guarantee is DECLARED and smaller than a "snapshot" — consistency by REFERENCE (git writes objects before moving the ref, and swaps the ref by atomic rename), without a global instant and without git fsck (the image has no git, on purpose); a concurrent gc becomes a FAILURE and not a partial file, with the tar status captured in a FILE because in POSIX sh a pipe's status is that of the last command. The five S3 variables stop being mandatory and become the configuration of ONE destination (BACKUP_DIR chooses disk; absent, S3 — the inference is what keeps the CronJob INTACT). make test-restore-compose triggers a REAL backup and calls the SAME brabo-restore with the SAME three validations: the WRAPPER changes, never the judgment, and deploy/k8s/test-restore.sh stays INTACT (unifying would make the compose one depend on kubectl); restore.sh still doesn't touch the ORIGIN database. Restoring the repos is a SIBLING command (brabo-restore-git, verifies by default, writes only with --restaurar) and not a phase of the other — two artifacts, two judgments, and joining them would make a git failure fail the event log validation. A finding while RUNNING, which reading wouldn't give: the volume is shared by three images with different uids and carries the owner of whoever mounted it first (measured 1000:1000, mode 0755), while the image runs as uid 70 — the extraction died halfway leaving the volume half done; now it refuses BEFORE the tar naming --user 0:0, and what's extracted as root goes back to the DIRECTORY's owner, otherwise the volume would come back intact and USELESS (api and engine, non-root, unable to write to what was just restored). Neo4j gets REPROJECTION and not backup — not built here (BRB-018): a migrated installation is born with the graph EMPTY, a named degradation and not data loss (the RAG lives in pgvector, inside the dump)

FASE 29 delivered installing in one line and STOPPED at two points the product itself already declared in writing: the local agent was still paired per PROJECT (whoever wanted to use the installed binary went back to the browser to paste a command into the terminal), and nobody could get in — the generated .env has no email variable, MAIL_TRANSPORT falls to log and registration requires verifying the email, so the way out was fishing the link from docker compose logs api. Nothing in the engine changed in the whole phase, and that's what kept RunnerReadiness, the mirror and workspace_create intact. Measured: Restart=on-abnormal doesn't look at the exit code, so no unit changed and the effect is that the machine one is genuinely active (running). The other piece (RN-551) closes "nobody CREATES a machine key" from the agent's side, and the decision there is the CUT: the CLI does not talk to the api, because whoever registers is the installer with the BRABO_SERVICE_TOKEN — each side keeps a secret and neither sees the other's.
