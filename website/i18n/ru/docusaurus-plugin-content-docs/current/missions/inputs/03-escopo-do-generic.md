# Входные данные 3 — GenericGitProvider: минимальные capabilities и деградация

Входной материал для PO к Фазе 10.

`GenericGitProvider` — это provider для «любого git-сервера, без API
платформы»: самостоятельно размещённый Gitea, bare repo за SSH, Forgejo,
сервер, говорящий только на протоколе git. Как проблема он противоположен Bitbucket —
там задача в переводе богатого API; здесь — **честно объявить,
чего сделать нельзя**, и гарантировать, что остальная система деградирует, а не
ломается.

Контракт, который нужно выполнить, находится в `inputs/01-contrato-gitprovider.md`.

---

## Прецедент уже существует: `LocalGitProvider` {#o-precedente-já-existe-localgitprovider}

Это не новый provider по духу — это `LocalGitProvider` с удалённым репозиторием в
другом месте. У всего, что нужно решить эпику, там уже есть ответ, и самый
дешёвый путь — прочитать этот файл, прежде чем что-либо проектировать
(`apps/api/src/infrastructure/git/local-git-provider.ts`, 467 строк).

Что он устанавливает:

- **Объявляет `protectBranch: false`** и `pullRequests: true`
  (`apps/api/src/infrastructure/git/local-git-provider.ts:55-58`).
- **Отклоняет неподдерживаемую операцию с `GitNotSupportedError`**, никогда молча
  (`:137`, а также в `:290` и `:323` для путей merge без настоящего
  PR).
- **Реализует настоящий PR без платформы**: лёгкое хранилище PR в sidecar
  bare repo, сделанное для dev agents Фазы 4a (`:51-54`). То есть
  `pullRequests: true` без сервера PR **возможен** — вопрос в том, где живёт
  состояние.
- **Говорит на настоящем git**, через `execFile` бинарника, а не через повторную реализацию.

## Центральный вопрос: где живёт состояние, которое сервер не хранит {#a-pergunta-central-onde-mora-o-estado-que-o-servidor-não-guarda}

Чистый git-сервер знает о refs, объектах и ни о чём больше. У него нет PR, нет
комментариев, нет защиты веток. Десяти операциям контракта нужен
ответ на каждое из этих отсутствий.

| операция | знает ли чистый git-сервер? | ожидаемый ответ |
|---|---|---|
| `createRepo` | зависит — создание удалённого репозитория требует API или доступа к диску | исследовать; это может быть недостающая capability |
| `getRepo` | частично — `defaultBranch` можно узнать через `ls-remote` | вероятно, да |
| `createBranch` | **да** — это push ref | да |
| `protectBranch` | **нет** | `false` + `GitNotSupportedError` |
| `commitFiles` | **да** | да |
| `listBranches` | **да** — `ls-remote --heads` | да, с `protected: false` всегда |
| `openPullRequest` | **нет** нативно | решение: собственное хранилище (как у Local) или `false` |
| `mergePullRequest` | **нет** нативно | то же |
| `commentOnPullRequest` | **нет** | то же — и это то, что используют gates |
| `getFileContent` | **да** — `git show ref:path` | да, с `null` в обоих случаях отсутствия |

**Архитектурное решение только одно:** Generic повторно использует механизм PR
`LocalGitProvider` (и тогда объявляет `pullRequests: true`) или объявляет `false` и
принимает каскадную деградацию? Оба варианта защитимы. Что не защитимо — это
объявить `true` и бросать `GitNotSupportedError`: набор контрактных тестов отклоняет
это, намеренно.

## Чего стоит «объявить `false`», каскадом {#o-que-declarar-false-custa-em-cascata}

Прежде чем выбрать, нужно знать, что теряется. Объявление `pullRequests: false`
— не деталь provider: оно отключает часть продукта.

- **Gates QA и SecOps** публикуют заключение в PR
  (`commentOnPullRequest`, десятая операция, родилась для этого в Фазе 4a).
  Без PR заключение существует как артефакт в event log, но не появляется в
  репозитории.
- **Поток dev agents** открывает PR по завершении task.
- **Блокировка защищённого merge** (`decide.ts:149-160`) продолжает действовать — она
  принадлежит домену, а не платформе. Это важно: **отсутствие защиты на
  сервере ничего не ослабляет**, потому что ненадлежащий merge предотвращает потолок
  в домене.

Эпик должен явно сказать, что происходит с каждым из них в
Generic. «Деградирует» — не ответ; ответ — деградирует **во что**.

## Деградация в bootstrap: механизм уже готов {#degradação-no-bootstrap-o-mecanismo-já-está-pronto}

**RN-029** — bootstrap Gitflow идемпотентен и возобновляем; это шесть шагов,
каждый проверяет перед действием, и `skip` **является успехом**
(`apps/api/src/application/use-cases/git/bootstrap-steps.ts`).

Для provider без `protectBranch` шаг `protect_branches` не проваливается:
он выходит **`degraded`**, что тоже является успехом. Событие
`bootstrap.step_degraded` существует ровно для «завершилось без capability
provider» — см. `docs/reference/events.md`, раздел «Git e bootstrap». С
provider Local это уже происходит сегодня, при каждом запуске.

То есть: **деградацию не нужно строить, её нужно объявить.**
Система уже умеет обращаться с отсутствующей capability; чего она не прощает — так это
лживой capability.

## Что конкретно означает «минимальный» {#o-que-mínimo-significa-concretamente}

Provider принимается, когда:

1. Все десять операций существуют — даже если некоторые лишь бросают
   `GitNotSupportedError` (`apps/api/src/domain/git/git-errors.ts:51`).
2. Две capabilities отражают реальность
   (`packages/shared/src/index.ts:182-185`).
3. **19 сценариев** единого набора тестов проходят, без собственного написанного сценария
   (`apps/api/test/contract/git-provider.contract.ts`). Сценарии
   `protectBranch`, `openPullRequest`, `mergePullRequest` и
   `commentOnPullRequest` проверяют именно согласованность между объявленным
   флагом и поведением — работать при `true`, отказывать при
   `false`.

**RN-028** замыкает правило: решает capability, а не имя provider. Ни один
потребитель не может получить `if (provider.name === 'generic')`. Если кому-то это понадобится,
проблема в моделировании capabilities, а не в потребителе — и тогда это ADR.

## Открытые вопросы для Arquiteto {#perguntas-em-aberto-para-o-arquiteto}

- **Конфигурация.** Generic нужен URL удалённого репозитория и, вероятно,
  учётные данные. Как это входит? У `CreateRepoInput` есть `name`, `visibility`,
  `namespace` и `accessToken` — ни одно из них не является «URL сервера». Где живёт
  URL: в `externalId`, в новом столбце `provisioned_repositories` или в
  конфигурации проекта?
- **Аутентификация.** Токен по HTTPS, ключ SSH или оба? Ключ SSH не помещается в
  `accessToken?: string` так же, как помещается токен, и
  `credentialProviderEnum` (`apps/api/src/db/schema.ts:198-203`) в любом случае
  потребовал бы новой записи.
- **`visibility`.** `GitRepo` требует `"public" | "private"`
  (`packages/shared/src/index.ts:187-193`). У чистого git-сервера может не быть этого
  понятия. Что возвращается — объявленное значение по умолчанию или это становится
  опциональным полем в контракте?
- **`createRepo`.** Если Generic не умеет создавать удалённый репозиторий, он
  бесполезен для текущего мастера, который всегда вызывает `createRepo`
  (`provision-repository.use-case.ts:144`). Это связано с находкой P1
  миссии: продукт не умеет усыновлять существующий репозиторий. **Generic может быть
  именно тем provider, который делает эту находку срочной** — Arquiteto стоит
  оценить, решаются ли они вместе.
- **Безопасность.** URL произвольного сервера, предоставленный пользователем, — это поверхность
  для SSRF. Стоит проверить, как `docs/security-surface.md` обращается с исходящей сетью,
  прежде чем решать.

---

## Чего НЕ делать {#o-que-não-fazer}

- Не реализовывать десять операций «как попало», чтобы можно было объявить всё
  `true`. Честность в capability — требование; полнота — нет.
- Не копировать `LocalGitProvider` буквально. Повторно используется
  **решение** (где живёт состояние PR), а не обязательно код.
- Не создавать `if` по имени provider ни в одном потребителе.
