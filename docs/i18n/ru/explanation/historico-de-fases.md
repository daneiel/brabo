# История фаз

> Неизменяемая запись завершённых фаз Brabo, перенесённая из CLAUDE.md
> 2026-08-23 без переписывания. ДЕЙСТВУЮЩЕЕ состояние продукта живёт в CLAUDE.md,
> в RN (docs/business-rules.md) и в ADR — этот файл отвечает на вопрос «как
> мы сюда пришли», а никогда не «что действует сегодня». Принятый ADR никогда не редактируется;
> исправления ADR, записанные в этом тексте, остаются действительными там, где они есть.

## ФАЗА 14 — ЗАВЕРШЕНА 2026-08-07 (что потребовало реальное выполнение) {#fase-14--concluída-em-2026-08-07-o-que-a-execução-real-exigiu}
Выполнение hello world не прошло дальше первого хода и выявило дефекты, которые
не ловил ни один набор тестов, потому что всё до этого работало с ЛОКАЛЬНОЙ моделью. Исправления

### 14a — Операбельность агентов (ЗАВЕРШЕНА) {#14a--operabilidade-dos-agentes-concluída}
- Сбой хода стал ДОЛГОВЕЧНЫМ `agent.error` с источником, и агент ГОВОРИТ в
  нити; четыре разговорных агента перестали записывать пустой `agent.response`
  (RN-059). Путь ошибки, рассказанной в финальном frame-е, который не выдавал ни одного
  события, тоже закрыт.
- Чат Criativo открывается приглашением, а не пустотой: он активируется и ждёт,
  пока пользователь заговорит первым, и экран теперь говорит об этом — в том числе что технология
  и код — НЕ его дело.
- Ключ, который тратит агент, — ключ OWNER-а workspace (RN-058). Раньше ход
  искал учётные данные по SLUG агента в столбце UUID: ни один агент
  никогда не использовал provider с учётными данными, и работал только `ollama`.
- Отчёт о расходах по ключам, только для владельца, с агентом, отделённым от
  человека (RN-060).
- Bootstrap Gitflow в GitHub: только что созданный репозиторий отвечает 409 во всём Git
  Data API, и первый commit проходит через Contents API. Поддельный backend
  тестов лгал (404 там, где GitHub отвечает 409) — исправлено заодно, именно это
  держало набор тестов зелёным при сломанном продукте.

### 14b — Древовидная временная шкала (ЗАВЕРШЕНА) {#14b--linha-do-tempo-em-árvore-concluída}
Одна ветвь на агента, от первой вехи до того, что он делает СЕЙЧАС, выведенная
на 100% из event log, который экран уже получает. Хронологическая лента остаётся в столбце
активности: она отвечает «что произошло», дерево отвечает «кто что
делает».

Пересмотрено после ФАЗЫ 26 (без новой фазы, в том же духе точечного
исправления, что 12d/ПОСЛЕ-ФАЗЫ 15): критерий открытия по умолчанию сменился с одного лишь
«активен/стоит» на 5 агентов с самой СВЕЖЕЙ активностью — активный по-прежнему
в приоритете (RN-118); каждая свёрнутая ветвь получила собственный счётчик НОВИЗНЫ,
с «последним просмотренным» по агенту в `read-state.ts` (тот же механизм,
что у колокольчика, теперь гранулярный); а `tool.call`/`tool.result`/`agent.response`
стали раскрываться ПО ОТДЕЛЬНОСТИ (аргументы, результат, итерация), сгруппированные
по границе итерации ToolLoop.

1. **Области стали данными**: `agent_areas`/`agent_area_members` по
   проекту, с `max_parallel` по умолчанию 2. Заставила это область
   **dev** — первая ДИНАМИЧЕСКАЯ, чьи участники — по одному на модуль
   module_map. То, что не перечислимо в коде, должно быть данными.
2. **Предел принадлежит СЕССИИ, а не модулю** (RN-083). Счёт по модулю
   позволил бы N модулей × 2 без какого-либо разрешения — прежняя дыра
   под другим именем. Выше предела становится `proposed_action`.
3. **Настраивается по области** в Настройках, требуя `maintainer`
   по той же причине, что и активация выполнения: изменить предел — значит решить, сколько
   продукт тратит, не спрашивая.
4. **Anamnese предлагает повысить**, когда разрешение стало рутиной, — три
   одобрения и НИ ОДНОГО отказа (RN-086). Один отказ гасит сигнал:
   если вы хоть раз отказали, предел делает свою работу.
5. **Dev Lead существует** (RN-087), разговорный, получающий handoff
   от Arquiteto в том же подтверждении, которое уже передаёт Infra, и
   предлагающий план: сколько агентов на модуль и почему.
   `dev-<modulo>` перестали быть адресуемыми через handoff — правило
   ADR 0038 стало действовать для dev так же, как уже действовало для QA и Infra.

**Находка X** закрыта здесь (RN-085): `TOOL_LOOP_MAX_ITERATIONS`
стал пределом ПО ТИПУ — 8 для разговорного, 60 для выполнения и gate. Критерий
того, кто поднимается, — НЕ «кто много работает»: это тот, у кого
под ним есть `token_budget_micros`, удерживающий расходы. `infra-workflows`
использует тяжёлый инструмент и остаётся на 8, потому что работает без бюджета.

**Три пробела самой фазы, найденные мной при написании следующего
среза, и все — один и тот же сбой**: правило предела вошло с зелёными
тестами, а продукт его не задействовал — ни один маршрут не вызывал вариант
использования, одобрение действия ничего не выполняло, а тип мог быть
автоматически одобрен через permissions.json (закрыто RN-086). Тестировать деталь —
не значит тестировать путь к ней.

**Вне объёма, по объявленному решению** (ADR 0053, пункт 5): смена владельца кнопки
«Ativar execução». Делегирование Dev Lead → `dev-<modulo>`
через таблицу `delegations` с `area = "dev"`, которое этот же пункт тоже
объявлял, ПЕРЕСТАЛО быть вне объёма — закрыто ADR 0094
(Аудит fluxo.yml × код, Волна 2, RN-405). Кнопка остаётся
обратимой; выполнение остаётся на текущем пути, а исправление после gate

## ПОСЛЕ ФАЗЫ 15 — ЗАВЕРШЕНО 2026-08-08 (v2.5.0 и v2.5.1) {#pós-fase-15--concluído-em-2026-08-08-v250-e-v251}
Это не запланированная фаза: это то, что ИСПОЛЬЗОВАНИЕ нашло после 15, и оно здесь,
потому что происхождение каждого пункта важно. Ничего из этого не пришло из сценария — пришло
из навигации по приложению в Chrome и чтения панели безопасности.

**Дефекты UI, найденные при навигации** (RN-088..091):
- `429` превращался в БЕЛЫЙ ЭКРАН, а приложение отвечало ещё большим трафиком. Правило
  стало общим: каждый экран различает ТРИ состояния — загрузка, ошибка (с
  `trace_id` и кнопкой) и пусто. `if (!dado) return null` схлопывает все три.
- Dashboard делал по запросу на проект: **3.824 → 12 req/min**, с
  `GET /workspaces/:id/projects-summary`. Колокольчик был недостающей
  половиной: **289 → один** запрос за цикл (RN-090/091).

**Ужесточение безопасности, с обеими панелями на НУЛЕ**:
- ADR 0058 — закрытый CSP в api (`default-src 'none'`), пересматривающий пункт
  7 ADR 0027; и `projectId`, ограниченный корнем (RN-092), что затрагивало
  не только `permissions.json`, но и область, которая РАЗРЕШАЕТ терминал.
- ADR 0059 — `GIT_OAUTH_STATE_SECRET` без значения по умолчанию в production (RN-093).
  Значение по умолчанию было ПУБЛИЧНЫМ (`.env.example`), и compose production подставлял его
  как fallback: требование «не пустая» ничего бы не поймало, потому что на
  реальном пути ошибки переменная была ЗАДАНА.
- Алерт, который не выдерживал проверки, был ОТКЛОНЁН с письменным обоснованием,
  никогда не заглушён — и отклонение — решение пользователя, а не агента.

**Три операционных урока, стоившие цикла CI, и они действуют как правило:**
1. **Зелёный CodeQL в PR не доказывает, что старый алерт закрыт** — проверка
   PR сообщает о НОВОМ алерте. Алерт закрывается при сканировании ветки ПО УМОЛЧАНИЮ,
   то есть только после того, как исправление дойдёт до `main`.
2. **Gitleaks сканирует commit-ы, достижимые из `refs/heads/*`, а не дерево.**
   Значение с высокой энтропией, закоммиченное однажды, навсегда проваливает CI
   на этой ветке; исправление поверх НЕ очищает. Выход — сделать commit
   недостижимым (пересобрать из `dev` и УДАЛИТЬ старую ветку
   ДО открытия нового PR) — никогда allowlist, который ослепляет сканер
   на этом пути для всех commit-ов. Refs PR в область не входят.
   Fixture, представляющий секрет, рождается БЕЗ энтропии.
3. **Барьер, живущий в другой функции, CodeQL не видит** — отсюда
   три `js/path-injection`, пережившие исправление. Проверка осталась
   централизованной (RN-092), и цена была уплачена на панели: дублирование её в каждом
   вызывающем было бы проверкой, которая однажды разойдётся.

### ФАЗА 21 — ЗАВЕРШЕНА: объём событий (RN-099/100) {#fase-21--concluída-o-volume-de-eventos-rn-099100}

    `useSessionEventHistory`, только для Активности, с `afterSeq`, который
    endpoint уже возвращал. Ни нового маршрута, ни нового параметра.

    вперёд, и `beforeSeq` не существует, но открыть ленту на событии № 1

    она помечает. Недостающее число получается ВЫЧИТАНИЕМ (`latestSeq` минус отсечка),

21. Экономия RN-090/091 не регрессировала: один запрос на цикл, а
    первое «загрузить более старые» стоит НОЛЬ — чтение `latest` приносит 200,
    а окно показывает 100. У старой страницы `staleTime: Infinity` и нет
    `refetchInterval`: закрытое окно `seq` над неизменяемым событием не меняется.

24. Коллизия решена разделением ВОПРОСОВ, а не фильтров.
    Отчёт по УЧЁТНЫМ ДАННЫМ остаётся исключительным для владельца (RN-060) и получил
    рядом разбивку workspace по модели/проекту/актору/дню, тоже
    `owner`. Представление участника — по АКТОРУ, в токенах и оценочной стоимости,
    без provider-а и без учётных данных — и актор берётся из аутентифицированного ТОКЕНА,
    без параметра, куда можно вписать id другого человека. Агент не входит в
    счёт участника: `token_usage` записывает, кто потратил, а не кто велел
    тратить.

Без миграции, но С измерением: на 525 тысячах строк запросы выполняются за
55 ms и 38 ms seq scan-ом, а индекс по `token_usage(created_at)`
довёл бы их до 32 ms и 19 ms. Число — в ADR; индекс войдёт в волну, у которой
будет слот.

## ПОСЛЕ ПРОГРАММЫ 16–26 — что использование попросило потом (RN-148) {#pós-programa-1626--o-que-o-uso-pediu-depois-rn-148}
Тот же дух, что ПОСЛЕ ФАЗЫ 15: это не запланированная фаза, это то, что попросило ИСПОЛЬЗОВАНИЕ.
Истории с одновременно ожидающим продвижением (RN-048/RN-126) превращались в N
отдельных карточек на временной шкале сессии PO, когда он производил несколько за одну
партию. `Carousel` (`apps/web/src/components/ui/Carousel.tsx`) — первый
компонент поэлементной навигации в дизайн-системе: 2+ ожидающих
становятся ОДНОЙ навигируемой каруселью (стрелки, точки, клавиатура), где «Aprovar todas»
продвигает всю партию одним вызовом (`promoteStories` уже был пакетным,
без изменения контракта); 1 ожидающая остаётся привычной простой карточкой.
Решение о том, когда формируется «партия», пересматривается при каждом render — это
множество ЕЩЁ ОЖИДАЮЩИХ продвижений в сессии, а не «созданных подряд
без перерыва», — чтобы разрешение истории посреди карусели
само пересчитывало партию, без собственного состояния для синхронизации.

**Проект Local или Container (RN-169/RN-170, ADR 0072).** Запрос владельца
продукта: «перейти границу записи кода только в контейнере и иметь возможность
писать код из папки пользователя», с вариантом **свободно набираемого
пути**, выбранным им, с пониманием, что это работает, только будучи смонтированным в
контейнер. `projects` получает (`workspace_mode`, `workspace_path`) в миграции
`0043`, с `container` по умолчанию — для того, кто не выбирает, ничего не меняется. ADR
0072 ПЕРЕСМАТРИВАЕТ часть 0065 и затрагивает территорию 0055, которые решили обратное
направление (стену контейнера), и поэтому следствие записано без
смягчения: СТРУКТУРНОЕ сдерживание `join(env, coluna)` — ни один
повреждённый столбец не выходит из управляемого корня — перестаёт существовать для проекта Local, и
остаётся защита при создании плюс лексическая повторная проверка при чтении.
ФАЗА 25b остаётся отсечённой: проект Local работает в ТОМ ЖЕ контейнере, что и сегодня, изменилась
только папка.

**Диаграмма C4 Arquiteto (RN-149, ADR 0068).** Новый результат:
`create_c4_diagram` генерирует Context + Container (Simon Brown) в Mermaid,
отображаемые в Обзоре. Уровень Container ВЫВОДИТСЯ из действующего `module_map`
вариантом использования — никогда не перепечатывается моделью, — чтобы не открывать
второй источник, расходящийся с первым; только Context (имя системы и
внешние акторы) приходит из tool call. `artifact.c4_diagram` — артефакт без
таблицы, версионируемый в event log, тот же замысел, что у `artifact.project_image`
(ADR 0065). `mermaid` вошёл как новая RUNTIME-зависимость
`apps/web` — первая такого рода (сайт документации уже использует Mermaid, но на
этапе build) — изолированная за `apps/web/src/lib/mermaid-render.ts` с
динамическим `import()`; `vite build` подтвердил, что только entrypoint загружается
сразу, а тяжёлые chunk-и Mermaid остаются по требованию, и ни один из них не использует
`eval`/`new Function` — закрытый CSP из ADR 0058 остался нетронутым, без
изменения конфигурации.

## РАУНД exp003 — ЗАВЕРШЁН (RN-150..162, PR #278–#293) {#rodada-exp003--concluída-rn-150162-prs-278293}
Это не фаза: это 17 пунктов, которые ИСПОЛЬЗОВАНИЕ нашло в живой тестовой сессии
над проектом `exp003`, исправленные пятью последовательными волнами по
ОСПАРИВАЕМОМУ ФАЙЛУ — четыре из них сходились в `SessionPage.tsx`, что
вынудило сериализовать. Важно происхождение: ни один из них не был найден тестом.

**Чему научил раунд, и это стоит больше списка**: самое большое исправление
(RN-155) было невидимо для любого набора тестов, потому что дефект был в сравнении
двух РАЗНЫХ числовых пространств, которые случайно оба `number`, —
`event.seq` (без пропусков, по СЕССИИ) против `action.seq`
(`proposed_actions.seq`, глобальный `bigserial` ВСЕЙ таблицы, общий
для всех проектов и всех сессий системы и задокументированный в схеме как
намеренный контраст). Порядок казался правильным, лишь пока таблица была
маленькой. Исправление не выдумало поле: оно использовало событие
`proposed_action.created`, которое `ProposeActionUseCase` уже записывает в ТОЙ ЖЕ
транзакции, с `payload.actionId`, указывающим обратно.

**Engine и сдержанное чтение (RN-150)** — `search_workspace` возвращал ВСЕ
совпадения, без предела: вторая настоящая причина `413` при ревью PR, после
исправления `read_file`. Два НЕЗАВИСИМЫХ предела, потому что поиск
переполняется двумя способами — количеством совпадений (`SEARCH_WORKSPACE_MAX_HITS`,
500, над `Stream`, который ПРЕКРАЩАЕТ сканировать на `max_hits + 1`) и байтами
итогового текста (`SEARCH_WORKSPACE_MAX_BYTES`, 32.768). Собственные переменные, не
переиспользованные из двух других: тот же класс переполнения, но расхождение одной не
должно требовать трогать другие. Метка усечения адресована МОДЕЛИ
(велит уточнить термин) и никогда не выдумывает итог, потому что подсчёт итога
снова оплатил бы I/O, ради экономии которого существует предел.

**Числа, которые лгут (RN-151)** — бейдж проекта в боковой панели считал
ЛЮБОЕ непрочитанное событие: `exp003` показывал 392, тогда как вкладка Одобрения
того же проекта показывала 8. Число, которое не соответствует ничему исполнимому
при клике, хуже, чем никакое. Стало `pendingApprovalsCount` в уже
существовавшей read model (RN-090), одной агрегацией больше в `Promise.all` — никогда
N+1.

**Прослеживаемость того, что произвёл агент (RN-152)** — ветка
`feature/task-XXXXXXXX` в dropdown вкладки Code теперь говорит, какому dev
agent и модулю она принадлежит. Модуль берётся из действующего `module_map` ТЕМИ ЖЕ
функциями, что его сгенерировали, никогда обратным regex по имени; без связи
деградирует до `null`, а не угадывает.

**Auto mode (RN-153/154, см. Соглашения)** — подстановка `actionType: "*"`.
Важно, где она живёт: разрешение принадлежит РЕПОЗИТОРИЮ (`findMode`),
а `decide.ts` не получил ни строки — именно это делает три абсолютных
предела истинными по ПОСТРОЕНИЮ, а не ещё одним `if`, который однажды
кто-то забудет.

**Нить сессии, которая читается (RN-155..159)** — упорядочивание (выше);
индикатор 5s с фиксированным текстом «Reunindo informações...» вместо
подстановки агента, который уже появляется в заголовке (RN-156); создание
эпика/истории PO, превращающееся в компактное уведомление, а не в пузырь с тем же
визуальным весом, что у настоящего ответа (RN-157); лёгкий Markdown с подсветкой
в чате собственным парсером на регулярных выражениях, ноль новых зависимостей и ни одного
`dangerouslySetInnerHTML`, причём отображается только ВЫВОД агента — то, что
набирает человек, остаётся буквальным (RN-158); и «Artefatos gerados», сгруппированные по
агенту с `Disclosure` из RN-138, каждый артефакт ведёт туда, где он
живёт (RN-159). module_map/C4 остались ВНЕ по зафиксированному решению: это ДЕЙСТВУЮЩЕЕ
состояние проекта, а не артефакт, датированный сессией.

**Порядок полномочий (RN-160/161, ADR 0069)** — «Confirmar arquitetura
pronta» включается только при хотя бы 1 ПРОДВИНУТОЙ истории (недостаточно иметь
захваченное правило); а принятие handoff для Dev Lead цепляет активацию
выполнения, когда эффективная роль принимающего уже это разрешает. Слияние — только на
клиенте: backend по-прежнему требует `maintainer` (RN-137), поэтому оно избавляет
от лишнего клика, не сдвигая границу авторизации.

**Структурированный ввод (RN-162)** — `ask_structured_questions` у Criativo:
модель объявляет вопросы в схеме, форма отображается
`StructuredQuestionCard`, а ответ ПЕРЕИСПОЛЬЗУЕТ `SendAgentMessageUseCase`,
а не открывает второй путь сообщения. Ответ — однократный акт:
повторная отправка — 409, а не перезапись.

## РАУНД exp001 — Criativo выполняет обещание (RN-163) {#rodada-exp001--o-criativo-cumpre-a-promessa-rn-163}
Тот же дух, что у других раундов: пришло из ИСПОЛЬЗОВАНИЯ, а не из сценария. Жалоба была:
«Criativo не ответил после того, как сказал, что исправит и попробует снова»,
и фраза буквально была в коде — `run_turn_capturing/1` вызывал модель ОДИН
раз, отправлял инструменты и возвращался. Результат инструмента попадал в
историю в памяти, и никто его больше не читал, поэтому обещанное исправление
происходило, только если пользователь присылал другое сообщение.

Criativo был единственным разговорным агентом без цикла tool use; он получил такой же, как у
PO, с собственным пределом 12. Что важно сверх исправления: **решать, что
объявляется, стал предел**, а не фиксированный текст — обещание повторной попытки
входит во фразу, только когда ещё есть ход, чтобы его выполнить. Исчерпанный предел стал
рассказанным `agent.error` (`po_server` в этом случае заканчивал молча, и это был
следующий очевидный долг — закрытый чуть ниже RN-166), а сбой
инструмента перестал быть `agent.response`
— в event log он был неотличим от обычного ответа и не называл
никакого источника, ровно то, что RN-059 закрыла для сбоя хода.

## РАУНД exp001 — PO читает уже существующее, и с него спрашивают (RN-164..166) {#rodada-exp001--o-po-lê-o-que-já-existe-e-é-cobrado-rn-164166}
Это не фаза: это дефект, найденный реальным ИСПОЛЬЗОВАНИЕМ, и происхождение важно, потому что
ни один набор тестов его бы не поймал. Backlog вышел с эпиком и **ни одной историей** — значит,
без задачи, значит, выполнение застряло **без какой-либо ошибки**. Расследование нашло
четыре наложенные причины, и первые три — одна и та же: PO не мог
знать и не мог предупредить.

1. **У PO было четыре инструмента, и все — ЗАПИСИ.** Контекст
   собирался ОДИН раз, на kickoff, из 200 последних событий СЕССИИ —
   с этого момента он больше ничего не перечитывал: не знал, какие правила существуют,
   какие он уже покрыл и что сам уже создал. Вошли
   `listar_regras_de_negocio` и `listar_backlog` (RN-164), обслуживаемые двумя
   внутренними маршрутами с областью ПРОЕКТА — и область здесь ключевая: чтение по
   сессии было ровно тем, что скрывало ранее захваченное правило. Они переиспользуют
   уже существовавшую трубопроводку (`listByTypeForProject`, `ListBacklogUseCase`,
   `computeCoverage`); не хватало маршрута, метода в клиенте и инструмента.
2. **Ничто не требовало историю после эпика**, и **цикл заканчивался молча**.
   Эпик без истории стал ЯВНЫМ исходом — `backlog.epic_without_story`,
   долговечным, по образцу RN-059 (RN-165), — а предел итераций `PoServer`
   начал выдавать `toolloop.limit_reached`, ТОТ ЖЕ тип, что у `ToolLoop`, который
   разговорные агенты никогда не выдавали, имея собственный цикл (RN-166).
3. **Инструкция kickoff не говорила ни слова о том, что делать, когда
   не хватает информации**, — а перед пробелом без инструкции модель выбирает
   между выдумыванием и остановкой. Остановка — то, что она сделала. Третий выход стал
   записан, с инструментом для его применения: `ask_structured_questions`,
   ТОТ ЖЕ, что у Criativo (RN-162), теперь объявленный и PO.

Два решения замысла, важные за пределами этого случая: только `create_story`, который
**удался**, гасит обязательство эпика (история, отклонённая api, ничего
не покрыла, и обращение с ней так, будто покрыла, — это замена одного молчания другим); а
требование — по СЛУЧАЮ, сообщается один раз, никогда не тревога, повторяющаяся каждый
ход, пока кто-нибудь не научится её игнорировать.

## РАУНД exp001 — нить читается так, как происходит ход (RN-172/173) {#rodada-exp001--o-fio-se-lê-como-o-turno-acontece-rn-172173}
То же происхождение, что у других: ИСПОЛЬЗОВАНИЕ, а не сценарий. Четыре жалобы на экран
Сессии — handoff PO появлялся НАД его последней репликой, одобрение
поднималось в середину ответа Arquiteto и опускалось только когда он
заканчивал, карточка одобрения «плохо свёрстана», и прокрутка не следовала за
разговором.

**Расследование выяснило, что упорядочивание было ВЕРНЫМ**, и в этом урок
раунда. RN-155 верна event log; а лог говорит, что
`po_server.ex#run_turn/2` выдаёт в ТОЙ ЖЕ итерации `agent.response`, ЗАТЕМ
`tool.call` для `offer_handoff` и ТОЛЬКО ПОТОМ рекурсирует к заключительной реплике
— значит, `seq` handoff честно МЕНЬШЕ, чем у последней реплики. То же
для `proposed_action.created`. Исправление, следовательно, не в упорядочивании: это
объявленное правило ПРЕДСТАВЛЕНИЯ (RN-172), в отдельном проходе
(`afundarDesfechos`) ПОСЛЕ `sort` по `seq` — а не компаратор из трёх
членов, который никто не смог бы обосновать через год.

То, что не даёт ходам смешиваться, — три барьера, и каждый существует
из-за реального случая: **ход** (у границы между двумя ходами может не быть
ВИДИМОГО элемента — `agent.activated` открывает ход и не становится элементом нити),
**автор** (в сессии выполнения несколько агентов пишут, ни разу не дав пользователю
сказать, и все остаются в одном ходе) и **не-исход** (два исхода
подряд сохраняют порядок между собой — Infra перед Dev Lead).

RN-173 закрывает две другие жалобы, и они были одной и той же: эффект
прокрутки зависел только от `[events.length, streamingText]`, а `actions` —
ОТДЕЛЬНЫЙ запрос — пришедшая карточка выталкивала разговор с экрана, ничего не
прокручивая. Зависимость исправлена, плюс `ResizeObserver` над содержимым
для того, до чего НИ ОДИН список зависимостей не дотягивается (сворачивание `Disclosure`,
перекомпоновка Markdown). Защита в 120px от конца остаётся нетронутой,
намеренно: нить следует за разговором, а не захватывает чтение того, кто прокрутил вверх.

## РАУНД exp001 — нить говорит, кто говорит, с какой моделью и что спрашивает (RN-171/174/175/176) {#rodada-exp001--o-fio-diz-quem-fala-com-qual-modelo-e-o-que-pergunta-rn-171174175176}
То же происхождение: ИСПОЛЬЗОВАНИЕ. Четыре жалобы на экран Сессии, и три из них
разделяют один урок — **продукт знал информацию и не
показывал её**.

**Вопрос по центру, и с выходом (RN-171).** Жалоба была буквальной: «sempre
dê a opção de input do usuário quando ele seleciona Escreva». Модель
предлагала вариант вроде «Напишите сами», а в форме негде было
писать — схема `ask_structured_questions` не умела выразить «помимо
этих, что угодно». `allowOther` вошёл в `select` со **значением по умолчанию
`true`**, и асимметрия — аргумент: список, закрытый по ЗАБЫВЧИВОСТИ, стопорит
разговор, и пользователь не может разблокировать его извне; список, открытый по ошибке, предлагает
лишнее поле. Интерфейсный sentinel никогда не попадает в backend, а кнопка
отправки по-прежнему требует всего заполненного (backend в любом случае отклоняет с 400).
Блок также стал центрированным с пределом 560px от
`ApprovalCard` и получил аватар: это был единственный элемент нити, ни к чему не выровненный.

**Действие, запускающее ход, взводит индикатор (RN-174).** Анимация «думает»
уже существовала — не хватало ПОКРЫТИЯ. Два действия экрана запускают
синхронный ход в engine и ничего не включали: ответ на форму
(`AnswerStructuredQuestionUseCase` переиспользует `SendAgentMessageUseCase`) и возврат
истории PO (`ReturnStoryUseCase` вызывает `reviseStory`, то есть
`handle_call({:revise, …})`). Канал Phoenix не закрывает эту дыру: пока join
ещё идёт (RN-108), у `agent.status` «working» нет слушателя, и он теряется.

**Модель — для ВСЕХ (RN-175).** Предпосылка, что дефект был у PO, не
подтвердилась: четыре разговорных агента записывают `modelName` начиная с RN-146, с
зелёным тестом. Никогда не записывал **`ToolLoop`** — путь каждого агента
выполнения и gate — и чат без активного агента в api. Ни одного нового
вызова: `RunLlmTurnUseCase` уже возвращал поле в теле. Экран перестал
писать одинокое слово «modelo» (которое читается так, будто модель так и называется)
и стал читаемым chip-ом; без данных он ГОВОРИТ, что они не были записаны, —
угадывание по текущему binding приписало бы старому ответу модель, которой,
возможно, даже не существовало, — та же ошибка, которую предотвращает замороженная цена из RN-044.

**Таблица в Markdown становится таблицей (RN-176).** Было возможно два выхода, и
выбран поддерживать таблицу в Markdown чата, с `Table` дизайн-системы.
Отображение `artifact.module_map` в нити было ОТКЛОНЕНО по уже
зафиксированному решению: это ДЕЙСТВУЮЩЕЕ состояние проекта, а не артефакт, датированный
сессией (RN-159), и он живёт в Обзоре. Кроме того, запрос касался
таблицы **внутри сообщения** — и исправление служит любому агенту, который
её напишет, а не только Карте модулей. Разделительная строка остаётся
обязательной (GFM), поэтому проза с `|` никогда не становится таблицей по ошибке.

## РАУНД exp001 — панель группирует, упорядочивает и говорит, чего не показывает (RN-177..181) {#rodada-exp001--o-painel-agrupa-ordena-e-diz-o-que-não-mostra-rn-177181}
То же происхождение, что у других: ИСПОЛЬЗОВАНИЕ, а не сценарий. Пять жалоб на панель
контекста и лог Сессии, и урок раунда один — **панель показывала
срез так, будто это целое, в трёх разных измерениях одновременно**:
скрывала шесть типов событий, не предлагая альтернативы, читала от самого старого к
самому новому и обрезала сессию на 200 событиях, не говоря об этом.

**Источник как новая классификация (RN-177).** `ActivityKind` отвечает «о каком
ПРЕДМЕТЕ говорит событие» и определяет иконку и цвет; `origem` отвечает «из какого СЛОЯ
оно пришло», и именно он делает историю читаемой — `eventos`, `sistema`, `llm`,
`harness`, `agente`, `usuario`, выводимые из СУЩЕСТВУЮЩИХ данных (`actor.kind` и
префикс `type`). Приоритет — то, что делает её предсказуемой, и он задан порядком
`if`: механизм побеждает актора (`tool.call` принадлежит harness, кто бы ни был), а
актор побеждает префикс агента (`chat.message` существует с обеих сторон). 5 самых
свежих остаются открытыми, а остальное сворачивается по источнику, **в обоих местах** —
в панели лога и в нити, где ось инвертирована (нить идёт по возрастанию, поэтому
история оказывается ВВЕРХУ). Фильтр машинного шума **по-прежнему включён по
умолчанию**: его причина не изменилась (116 из 193 реальных событий), изменилось то, что он
стал ВЫБОРОМ, а не свершившимся фактом.

**Порядок и пагинация (RN-178).** Четыре раздела стали убывающими, и
кнопка «Carregar mais antigos» как следствие сменила сторону — прежний
аргумент с обратным знаком. Бизнес-правила свыше 5 пагинируются, причём страница
разрешается через *clamp*, а не эффектом синхронизации.

**Дерево PO (RN-179).** `backlog.task_created` никогда не попадал в панель;
теперь эпик → история → задача образуют дерево по СВЯЗИ, которую событие уже
несёт (`epicId`/`storyId`), никогда по соседству в логе — узел без загруженного родителя
поднимается в корень, а не подвешивается наугад.

**Предел, который стал видимым (RN-180), — самый ценный пункт.** Панель
читала 200 событий через prop и не могла сказать, что их больше. Она стала читать
пагинированную историю RN-099 (тот же `queryKey`, что у хвоста, НОЛЬ лишних запросов
— RN-090/091), получила pager, который у `ActivityFeed` был всегда, но ни одно место
вызова не передавало, а заметка считает, сколько не хватает, ВЫЧИТАНИЕМ по `seq`, как
колокольчик из RN-100. Производные разделы читают `baixados` (всё уже пришедшее), а не
окно ленты, иначе стали бы показывать МЕНЬШЕ, чем раньше.

**Делегирование в нити (RN-181).** `delegation.completed|failed|dispensed`
существовали только в панели лога: gate открывался и закрывался без какого-либо знака того, что
снизу была вторая попытка. Они стали компактным уведомлением в формате RN-157,
с фразой из `classifyEvent` — той же, что в панели. Внешний контракт
области не меняется (ADR 0038): нить рассказывает то, что записал lead, и не начинает
адресовать субагента.

## ПРОГРАММА 28 — Волна 1, фронт A: тема перестаёт быть недостижимой (RN-182..185) {#programa-28--onda-1-frente-a-o-tema-deixa-de-ser-inalcançável-rn-182185}
Светлая тема существовала в `design/tokens.css`, имела тест паритета и была
описана в `design/README.md` так, будто это экран, — и **ничто в `apps/web`
не писало `data-theme`**. Единственный способ её увидеть — вписать атрибут в
DevTools. Оба теста контраста знали и говорили об этом: один утверждал через `expect`,
что ТРИ пары светлой темы проваливаются, — «запись того, что наследуется, а не гарантия того, что
отображается». Пока это длилось, аргумент был честным — измерять экран, который
никто не может открыть, значит измерять намерение. С приходом кнопки темы он
меняет знак.

**Boot — это ФАЙЛ** (`apps/web/public/theme-boot.js`), синхронный в `<head>`,
до бандла. Handoff велит использовать INLINE-скрипт; образ раздаётся под
`script-src 'self'` (ADR 0058), поэтому inline работал бы в `pnpm dev:web` и
блокировался бы в production — сбой ADR 0036 с другим подлежащим. `tema.ts`

требовательный фон светлой темы — бумажный `--code-bg`: accent 3,56 → 4,81, warning

остаётся закреплённым на тех же пяти числах. Два зафиксированных побочных эффекта:
пять пар, являющихся долгом в тёмной, ПРОХОДЯТ в светлой, а «известное исключение
дизайн-системы» (`--on-accent` поверх `--accent`, 3,20:1) исчезает в светлой —
исправление, которое описывал комментарий теста, затемнение до `--terracota-500`,
— как раз то, что стала делать светлая.

**Пять из восьми значений `--syn-*` из handoff были ОТКЛОНЕНЫ измерением** (
худшее, `--syn-cm`, даёт 2,32:1 в светлой). Где handoff проваливается, действует измеренное
число: это та же линейка, что и для шрифтов. Восемь ролей начинают существовать с префиксом
`--syntax-*`; пять семантических, которые ещё раскрашивают, измеряются рядом с ними.

## ПРОГРАММА 28 — Волна 5, фронт I: социальный вход отменяет запрет из backlog ADR 0031 (RN-272..283, ADR 0084) {#programa-28--onda-5-frente-i-login-social-revoga-a-proibição-do-backlog-do-adr-0031-rn-272283-adr-0084}

`docs/fluxo.yml` × код (находка A2,
`docs/explanation/auditoria-fluxo-vs-codigo.md`) — поток уже объявлял
выход `plano-de-paralelismo` у `dev-lead` как `via: proposed_action`
начиная с ADR 0085, а код так и не был приведён в соответствие. Владелец
продукта решил, что ошибался код.

`propose_execution_plan` вошёл в `decide.ts` (минимальная роль
`maintainer`), НАМЕРЕННО вне блока абсолютных пределов — его можно
настроить на автоодобрение, в отличие от
`parallelize`/`raise_max_parallel`. Dev Lead — ПЕРВЫЙ разговорный
агент (все выполняют синхронный ход через `GenServer.call` до
180s), который приостанавливается в ожидании человеческого решения — шаблон уже существовал для
dev agent (ADR 0052) и gate-ов QA/Infra (ADR 0057), но оба
запускаются через `cast` и никогда не имели дела с ожидающим синхронным `from`.
`TurnoAssincrono.tratar_resultado/2` получил ветку: при наличии
ключа `:aguardando_aprovacao` (проверяемого по ЗНАЧЕНИЮ, а не по наличию —
Dev Lead несёт его `nil` начиная с `init/1`) отвечает на `from` так же
и в то же время, что всегда, но выдаёт только `agent.status:
awaiting_approval` вместо `agent.done` — ход не закончился.
`LiveBroadcast.agent_status/4` получил новый статус в guard. Возобновление
использует ТОТ ЖЕ `Engine.Dev.Wake`, который `QaLeadServer` уже переиспользует для
субагентов QA (доставка — по АГЕНТУ, а не по типу).

**Принятый, объявленный пробел**: без собственной таблицы состояния перезапуск
engine, пока Dev Lead приостановлен, теряет подписку — решение
остаётся записанным и видимым в Одобрениях, но он не рассказывает исход
сам. Закрытие этого потребовало бы того же механизма сохранения, что у ADR
0052; вне объёма этого исправления, которое лишь приводит поведение к тому, что
`docs/fluxo.yml` уже объявлял.

## UX Designer — пятый разговорный агент, досрочно (RN-285..287, ADR 0087) {#ux-designer--o-quinto-agente-conversacional-antecipado-rn-285287-adr-0087}
Это не сработавший триггер разделения — `docs/fluxo.yml` всегда объявлял
«когда у УПРАВЛЯЕМОГО проекта будет собственный интерфейс для проектирования»
критерием, и он не сработал: дизайн-система остаётся статичным входом.
ОСОЗНАННОЕ решение владельца продукта всё равно ввести роль досрочно.

`Engine.Agents.UxDesignerServer` отражает `DevLeadServer` — GenServer на
сессию, предел 14 итераций, активируется handoff-ом `accepted`, адресованным
«ux-designer», через уже существующий ОБЩИЙ механизм (ни одна строка не изменилась в
`ActivateAgentUseCase`). SOLO: без области, без субагентов. Kickoff читает
самый свежий `artifact.product_brief` — ту же «бизнес-потребность»,
которую производит Criativo, без нового артефакта, — а дизайн-система
(`design/tokens.css`, `design/COMPONENTS.md`) ОПИСАНА в идентичности
агента (`Engine.Harness.Agents`), статичный текст: у разговорных агентов
нет инструмента чтения файлов репозитория.

`propose_prototype` — ЕДИНСТВЕННЫЙ инструмент (`personas`, `jornadas`,
`prototipo` с `telas`/`anotacoes`, `resumo`). Записывает
`artifact.prototipo_navegavel` **без выделенного варианта использования в api** —
в отличие от `choose_project_image`/`create_c4_diagram`, которым он нужен,
потому что у них есть содержимое, ВЫВОДИМОЕ из другого артефакта, или общий доменный
отказ; ни одна из этих причин здесь не действует, поэтому проверка формы
живёт в engine (`ArtifactSchemas`), а запись использует общий
`append_event_returning`, который api уже открывает, — тот же путь, что `artifact.product_brief`.
Один артефакт, два handoff-а по нему — для «po» и для «dev-lead», — никогда
второй артефакт для «spec-visual»: прототип (экраны + аннотации) И ЕСТЬ
визуальная спецификация, а его дублирование рисковало бы расхождением двух копий потом. Переиспользует
половину замысла ADR 0086, которая выживает без его приостановки:
успешный `propose_prototype` завершает ход, чтобы модель не предлагала
снова и не дублировала артефакт, — без «aguardando_aprovacao», потому что предложение
прототипа не имеет внешнего эффекта.

`apps/web/src/lib/agents.ts` получил запись (`color: var(--accent)`,
наименее переиспользуемый семантический токен roster; `icon: PencilIcon`).
`uxDesignerActive` вошёл в roster в ОБОИХ источниках, которые RN-090 требует
синхронизировать, — панели команды (`agent-status.ts`) и карточке dashboard
(`projects-summary.repository.ts`, тот же запрос, что `infraActive`,
расширенный, без нового query).

**Вне досягаемости, объявлено**: `teste-de-usabilidade` требует настоящего
пользователя-человека — ни один агент это не заменит. `metricas-de-uso` остаётся пробелом даже
при `analytics` `active` (ADR 0089): отчёт о воронке измеряет
сессия→commit→PR→merge, а не принятие функций КОНЕЧНЫМИ пользователями
проекта, который строит Brabo, — «улики принятия по функции»
ОБЪЯВЛЕНЫ метрикой без пути к существованию сегодня, а не незакрытым пунктом,
который закроют в следующем раунде.

## Staff — код готов, спит для автоматического запуска (RN-305/306, ADR 0088) {#staff--código-pronto-dormente-para-disparo-automático-rn-305306-adr-0088}
Это не запланированная фаза: `docs/fluxo.yml` объявляет Staff/Principal Engineer
как `status: planned` начиная с ADR 0085 («контракт готов, активация
решена, ждёт триггера»). ОСОЗНАННОЕ решение владельца продукта:
написать КОД заранее, зная, что АВТОМАТИЧЕСКИЙ триггер (Anamnese,
замечающая ПОВТОРЯЮЩУЮСЯ системную проблему) не сработает — Anamnese
на паузе (`ANAMNESE_ENABLED=false`, решение от 2026-08-10). Спит
для автоматического запуска, но не для РУЧНОГО вызова.

Шестой solo-разговорный агент (`Engine.Agents.StaffServer`), рядом с
Criativo/PO/Arquiteto/Dev Lead/UX Designer, отражающий Arquiteto (ограниченный цикл
с пределом 14) с двумя отличиями: БЕЗ `kickoff/1` (нет артефакта
сессии для резюмирования — поднимается и простаивает до первого `user_message`,

никаких доменных изменений в api не требовалось, потому что
`assertHandoffTargetAllowed` отклоняет только субагента области, а у Staff нет
области. Единственный инструмент, `propose_rfc` (проблема, варианты с компромиссами,
рекомендация, одноразовый PoC), записывает `artifact.rfc_staff` НАПРЯМУЮ через
`append_event_returning` — тот же бестабличный шаблон, что у `emit_insight`, а
не у `artifact.c4_diagram` (который выводит уровень Container из
module_map в api), — и возвращает handoff Arquiteto в ТОМ ЖЕ tool call,
без `proposed_action` (регистрация документа — не внешний эффект).

`staffActive` вошёл в roster панели команды и в карточку dashboard
(`ProjectCardSummary.roster`), по тому же критерию, что `infraActive`, чтобы не
открыть расхождение, о котором уже предупреждал комментарий `RosterFacts`.
**Объявлено, не скрыто**: `SessionPage.tsx`/`AGENTES_DE_CHAT` не
тронуты — тот же уже принятый шаблон, что и для `infra` (НАСТОЯЩИЙ и АКТИВНЫЙ lead
тоже вне этого списка). Сквозной путь использования сегодня — внутренний
маршрут (`POST .../agent/message`, `agent: "staff"`), а не экран
Сессии; общий UI «ручного handoff выбранному агенту» остаётся в
backlog.

## Активный gate `implementavel` — QA-стратегия как второй момент qa-lead (ADR 0090) {#o-gate-implementavel-ativo--qa-estratégia-como-segundo-momento-do-qa-lead-adr-0090}
Осознанное решение владельца продукта досрочно ввести триггер, который
`docs/fluxo.yml` уже предусматривал («когда gate implementavel активируется»), —
триггер ЗДЕСЬ — сама работа по построению механизма, а не симптом
использования, ждущий своего часа. `docs/gates.yml`, `implementavel`:
`status: planned` → `active` (владелец `dev-lead`, `severidade: warn`
не тронута — реестр уже говорил «рождается warn, даже когда активируется»).

**QA-стратегия перестаёт быть ролью `proposto`**: это САМ `qa-lead` во
втором МОМЕНТЕ — тот же процесс, результат отдельный от вердикта PR,
ровно как `docs/fluxo.yml` уже объявлял («может быть сам qa-lead
во втором МОМЕНТЕ, не обязательно новый агент: разделение — по
результату»). `Engine.Gates.QaLeadServer.run_design/3` — НОВАЯ и ДОБАВОЧНАЯ точка
входа (без касания `run/2`, привычного пути, привязанного к
`DevAgentState.find_by_task_id`), вызываемая через
`Engine.Gates.Dispatcher.run_qa_estrategia/3` (та же заменяемая в
тесте косвенность, что уже используют `run_qa/2`/`run_secops/2`).

`Engine.Gates.QaEstrategiaAgent` — модуль БЕЗ СОСТОЯНИЯ (не `GenServer`),
той же формы, что `QaPerformanceSegurancaAgent`, — реестр без `Terminal`
(`ReadFile`, `SearchWorkspace`, `EmitPlanoDeTeste`), — но КОНТЕКСТ
другой: `Engine.Gates.QaEstrategiaContext.fetch/3` получает ТОЛЬКО story (из
`list_backlog`) и действующий `module_map` (из `get_infra_context`, переиспользуемого только
ради поля `moduleMap` — ноль новых маршрутов), без `dev_state` и
`worktree_path`, потому что gate работает PRE-DEV: ещё нет ни dev agent, ни worktree,
ни `task_id`. Ни один из трёх инструментов не проходит через
`ActionPipeline` (проходят только `terminal`/`write_file`), поэтому этот агент
НИКОГДА не приостанавливается — `run_design/3` выполняется синхронно внутри собственного
`handle_cast`. Предел итераций остаётся 8 (разговорный), а не 60
(gate) — НАМЕРЕННО: без `token_budget_micros` под ним (нет task,
PRE-DEV) — та же причина, по которой `infra-workflows` остаётся на 8, даже используя
инструмент (RN-085). Результат (`emit_plano_de_teste`: синтез,
исполнимые критерии, ОБЩАЯ стратегия автоматизации без фреймворка)
становится `artifact.plano_de_teste` в event log вызвавшей сессии.

`assess_implementability`, новый инструмент Dev Lead, читает
самый свежий `artifact.plano_de_teste` story в истории СОБСТВЕННОЙ
сессии: если плана ещё нет, запускает оценку и возвращает ошибку с просьбой
повторить (ошибка инструмента — ВХОД цикла, а не конец пути —
RN-163); при наличии плана предлагает заключение (`implementavel`/`inviavel` +
обоснование, план встроен в payload) как `proposed_action`, по ТОМУ ЖЕ
шаблону трёх исходов, что `propose_execution_plan` (ADR 0086) —
`maintainer`, НАМЕРЕННО вне блока абсолютных пределов
`decide.ts`.

**`appsec` перестаёт быть `proposto`** — второй момент SecOps входит в
следующем разделе.

## `analytics`/`delivery-metricas` становятся отчётом (RN-320..322, ADR 0089) {#analyticsdelivery-metricas-viram-relatório-rn-320322-adr-0089}
Осознанное решение владельца продукта ДОСРОЧНО ввести две роли
целевой модели (`docs/fluxo.yml`, `status: proposto`), не дожидаясь
органического триггера, который каждая уже объявляла. Форма — та, которую сам поток
предписывал: `analytics` «поглощён `medicao`», пока метрика ПРОДУКТА не
станет обязательным входом PO, `delivery-metricas` «никогда не становится агентом —
становится ОТЧЁТОМ `medicao`». Обе становятся одним СКРИПТОМ —
`apps/api/scripts/analise-funil.ts` (`pnpm --filter api analise:funil --
--projeto <uuid> [--json]`), в ТОМ ЖЕ формате, что `medir-execucao.ts`
(Фаза 13b): чистое чтение через Drizzle, ноль записи, без GenServer, без
агента LLM.

Измеряет ПО-НАСТОЯЩЕМУ, по `proposed_actions.execution_result` трёх git-действий
dev agent (`git_commit`/`pr_open`/`git_merge`, только `status:
'executed'`): настоящую воронку (сколько сессий дали commit / открытый PR /
смерженный PR, и конверсию между этапами — считает СЕССИИ, а не действия), настоящий lead
time (от первого commit до первого merge сессии, по `updated_at`
ВЫПОЛНЕНИЯ, а не предложения) и настоящий deployment frequency (merge в
ветку `PROTECTED_BRANCHES`, по дням, со ссылочной сверкой с gate
`backmerge` из `docs/gates.yml` — чья улика — CI, вне досягаемости
скрипта, который только читает базу).

Три метрики остаются в разделе «Não medido, de propósito» — ПОСТОЯННОЕ
объявление, а не пробел, закрываемый в следующем раунде: **полная продуктовая воронка
идеация → commit** (`sessions` без `storyId`, RN-230, потребовала бы
новой схемы — ни одной миграции в этом фронте); **улики принятия по
функции** (это не недостающие данные для сбора — Brabo не инструментирует
проекты, которые он СТРОИТ, и нет никакого пути к существованию этой телеметрии
сегодня); **MTTR и change failure rate** (требуют сигнала настоящего ИНЦИДЕНТА
production, та же зависимость, что у `secops-runtime`/`platform` —
другой фронт).

## `secops-runtime` как скрипт-отчёт (RN-375..377, ADR 0091) {#secops-runtime-como-script-de-relatório-rn-375377-adr-0091}
Решённое владельцем продукта досрочное введение роли `secops-runtime`
(`docs/fluxo.yml`, `camada_seguranca`, ранее `proposto`), не дожидаясь
объявленного триггера («production с реальным трафиком, после `DEPLOY_ENABLED` +
активного `platform`»). Входит только то, чего триггер НЕ требует: `pnpm --filter api
relatorio:seguranca-runtime` читает `rate_limit_hits` — данные, которые
`RateLimitGuard` из ADR 0027 уже записывает, в том числе при трафике dev/CI, — и
производит рейтинг корзин (`user:<uuid>`/`ip:<endereço>`, два единственных
записываемых формата; без маршрута и причины, которых таблица никогда не хранила) и
временное распределение по фиксированным срезам. Это СКРИПТ, а не агент LLM и не
`GenServer`: по данным нечего решать, только агрегировать.

Автоматическое обнаружение инцидентов, реагирование на инцидент и постмортем
безопасности остаются ВНЕ — они зависят от того же несработавшего триггера, — и
отчёт перечисляет их в ПОСТОЯННОМ разделе «não medido», не симулируя
примерный инцидент и не выдумывая числа (тот же принцип, что у ADR
0041/0042/0077). Хранимое окно коротко по замыслу
(`DomainGaugesCollector.pruneRateLimit` удаляет hits старше
`2 × RATE_LIMIT_WINDOW_MS`, 240s по умолчанию), и отчёт объявляет оба
окна — НАСТРОЕННОЕ и НАБЛЮДАЕМОЕ, — никогда не давая второму выдать себя за
историю длиннее, чем она есть.

## `platform` получает первую сдачу: отчёт телеметрии по требованию (RN-385/386, ADR 0092) {#platform-ganha-uma-primeira-entrega-relatório-de-telemetria-sob-demanda-rn-385386-adr-0092}
Осознанное решение владельца продукта досрочно ввести часть роли `platform`
(`docs/fluxo.yml`, `camada_plataforma`) — чей `status` остаётся `planned` и
чья `ativacao` остаётся синхронизированной с `DEPLOY_ENABLED`, которого не существует.
`pnpm --filter api relatorio:telemetria [--projeto <uuid>] [--json]` — это
СКРИПТ (не агент LLM, не `GenServer`), который читает по требованию ТЕ ЖЕ
вопросы, которые `DomainGaugesCollector` уже собирает для scrape
Prometheus, — активные/closing сессии по проекту, заблокированные tasks по
проекту, состояние последнего бэкапа (всегда ГЛОБАЛЬНОЕ, никогда по проекту, потому что
продукт делает бэкап всей базы), — и завершается после печати.
SQL-запросы ПОВТОРЕНЫ, а не импортированы из коллектора: его методы
приватны и заканчиваются записью в gauge Prometheus, без чистой половины «только
запрос», которую можно было бы переиспользовать, не привязывая CLI-скрипт к жизненному циклу
`@Injectable`.

Вывод всегда содержит «где посмотреть больше» (версионируемые dashboards в
`deploy/k8s/observability/dashboards/*.json`, алерты в
`deploy/k8s/observability/alerts/brabo-alerts.yaml`, `docs/runbook.md
#observabilidade`, `pnpm dev:obs` для локальной наблюдаемости) — ссылка, никогда
дублирование — и раздел «não medido», который ОБЪЯВЛЯЕТ, не выдумывая: ни один числовой
SLO в продукте не определён, постмортем зависит от реального инцидента, которого
не было, а телеметрия, возвращающаяся в продукт по замкнутому циклу, — то, что
сделало бы `platform` `active`, — триггер (`DEPLOY_ENABLED`) по-прежнему отсутствует.
`gate_saida: { id: operavel, status: planned }` роли не меняется;
`docs/fluxo.yml` лишь получает `nota` в выходе `telemetria-consolidada`,
говорящую, что ручная/по требованию версия уже реальна.

## dbre становится двумя механическими скриптами (RN-400..403, ADR 0093) {#dbre-vira-dois-scripts-mecânicos-rn-400403-adr-0093}

реального объёма данных (`plano-de-capacidade`, `tuning` — остаются пробелом,
без срока). Двум другим реальная нагрузка не нужна: `parecer-de-
migracao` — распознавание шаблонов в SQL-тексте
(`apps/api/scripts/lint-migracao.ts`, обходит `apps/api/src/db/migrations/
*.sql`, сигнализирует `DROP TABLE`/`TRUNCATE`/`DROP COLUMN`/`ALTER COLUMN ...
TYPE`/`ADD COLUMN ... NOT NULL` без `DEFAULT`, `!= 0`, если что-то найдено, — сегодня
находит 3 вхождения в уже смерженных и принятых миграциях, информативно, не
исправлены попутно); `backup-restore-testado` уже был реальным с

~40s) — не хватало лишь отчёта по требованию (`relatorio:backup`, то же
чтение, что у `DomainGaugesCollector.collectBackup()`). Ни один из двух
пока не входит в CI: линтер обходит весь репозиторий, а не diff
PR, и стал бы gate-ом, проваливающим PR из-за находки, которая ему не принадлежит, — см.
ADR 0093 о технике области (`pr-police.ts`), когда это изменится.
Правило «одна миграция на волну» (`meta/_journal.json`) перестало
называться «механизированной версией» этой роли: оно предотвращает конфликт
снимков между параллельными агентами — забота, ортогональная «в этом SQL
есть рискованный шаблон».

## Аудит fluxo.yml × код — Волна 2: RN-160 в backend и делегирование Dev Lead → dev (RN-404/405, ADR 0094) {#auditoria-fluxoyml--código--onda-2-rn-160-no-backend-e-delegação-dev-lead--dev-rn-404405-adr-0094}

наибольшего объёма после Волны 1 — остальные четыре (3, 4, 5 введены досрочно вне

потребовалось.

**B6 — RN-160 повторно проверяется в backend.** Правило («Confirmar arquitetura
pronta» требует хотя бы 1 продвинутой истории) гарантировалось только на КЛИЕНТЕ
(`SessionPage.tsx`, `hasPromotedStory`) — прямой HTTP-вызов
`POST /agents/arquiteto/handoff-infra` полностью игнорировал правило.
`OfferInfraHandoffUseCase.execute` теперь запрашивает
`StoryRepository.findByProject` и отказывает с `BadRequestException` ДО
записи события или вызова engine, когда ни у одной истории нет

предусматривал это и объявил вне объёма в то время — CLAUDE.md перечислял это как
обратимое отсечение. Закрыто здесь: `AcceptParallelizationUseCase.execute`
(сторона API, даром покрывает прямой И одобренный пути, потому что оба уже
сходятся в нём) записывает `delegations` с `area: 'dev'`, `leadAgent:

заключение), `status: 'completed'` был ПЕРЕОПРЕДЕЛЁН для этой области: он означает
«делегирование ОСУЩЕСТВЛЕНО» (агент поднялся), а не «заключение выдано», — а
`parecerArtifactId` указывает на самый свежий `artifact.module_map`
проекта (через `SessionEventRepository.listByTypeForProject`, уже
существующий метод, без нового запроса). Без module_map в проекте — чего не должно
случаться — делегирование не записывается с фальшивым id: лишь логирует
неожиданное состояние и продолжает, потому что активация dev agent уже успешна, когда эта
запись предпринимается; сбой в `RecordDelegationUseCase` тоже не роняет
активацию, по той же причине. Решение зафиксировано в ADR 0094, который также
отменяет отсечение пункта 5 ADR 0053.

`docs/fluxo.yml` (`dev-lead`, выход `delegacao`): `status: lacuna` →
`status: ativo, regra: RN-405`.

## Аудит fluxo.yml × код — Волна 6 (последняя): gate `necessidade-validada` (RN-406, ADR 0095) {#auditoria-fluxoyml--código--onda-6-última-o-gate-necessidade-validada-rn-406-adr-0095}
Закрывает ПОСЛЕДНЮЮ из шести волн плана аудита (раздел D,
`docs/explanation/auditoria-fluxo-vs-codigo.md`) — закрылись все шесть: 3,
4 и 5 были введены досрочно вне порядка (analytics/DORA, gate

закрылись в предыдущих PR (fluxo.yml/gates.yml в актуальном состоянии; RN-160 в

`modelo-de-time.md` уже фиксировал, почему он стоял: Criativo (
модель), в одиночку решающий, что потребность, которую он сам произвёл,

`docs/gates.yml` получает gate `necessidade-validada`: `active`,

не СПРАШИВАЕТ о прохождении этого gate, прежде чем позволить PO продолжить, в отличие от

## Настоящий SMTP в MailSender (RN-408, ADR 0096) {#smtp-real-no-mailsender-rn-408-adr-0096}
Закрывает пункт backlog, открытый с отказа от Keycloak (ADR 0032, «настоящий SMTP
остаётся будущей конфигурацией»). `nodemailer` поверх чистого SMTP-транспорта
(СТРОЧНЫЙ протокол с состоянием/MIME/STARTTLS/AUTH, в отличие от JSON HTTP API,
с которыми интегрируется остальной продукт), за `MAIL_TRANSPORT` — `log`
(по умолчанию, В ТОМ ЧИСЛЕ в production: отправка настоящей почты — opt-in
оператора) или `smtp`, выбираемый через `useFactory` в `AuthUseCasesModule`,
не трогая ни одного варианта использования (`RegisterUseCase`,
`RequestPasswordResetUseCase`, `LoginUseCase`, скрипт
`migrate-keycloak-users.ts` по-прежнему лишь внедряют `MailSender`).
`SMTP_HOST`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_FROM` следуют шаблону RN-114
в production, когда режим `smtp`, — но БЕЗ публичного значения по умолчанию, которое есть у
четырёх исходных RN-114, поэтому линейка вступает в действие, только когда оператор выбрал
`smtp`; проверка выполняется в конструкторе `SmtpMailSender`, задействованном
через `useFactory` при сборке графа provider-ов (тот же замысел, что у
`CREDENTIALS_MASTER_KEY`), а не немедленным вызовом в `main.ts`. Тело —
ЧИСТЫЙ ТЕКСТ, никогда HTML: порт не несёт структуры для богатого тела, а
шаблонизатор был бы поверхностью инъекции без какого-либо выигрыша.

Расследование нашло настоящий пробел до написания кода: у `email_verification` не было
никакого web-маршрута — `verificarEmail` существовал в
`apps/web/src/lib/auth.ts` с Фазы 7a без ЕДИНОГО вызывающего, так что
ссылка из письма подтверждения вела бы в никуда, как только SMTP
начал бы отправлять настоящую почту. `/verificar-email`
(`VerifyEmailPage.tsx`) закрывает это, отражая `SetPasswordPage.tsx` — тот же
шаблон `validateSearch` в `router.tsx`, тот же единый ответ для несуществующей/
истёкшей/уже использованной ссылки — с одним отличием: без формы
подтверждение срабатывает само при монтировании, поэтому экрану нужны три
состояния RN-088 (загрузка/ошибка/успех), а не только два.

пакетная агрегация в engine) и разговорных агентов (последний `agent.status`
самой свежей сессии с `status !== 'idle'`, `payload`, принимающий только
`working`/`idle`/`awaiting_approval`). QA/SecOps никогда не считаются — они не выдают
`agent.status`, единственный вердикт на вызов, без понятия «простоя» между
вызовами.

Архитектурное решение, которое стоит записать: запрос читает
`engine.dev_agent_states` НАПРЯМУЮ, сырым SQL, пакетированным по workspace, внутри
ТОГО ЖЕ `Promise.all`, который уже суммирует одиннадцать запросов read model RN-090
(ДВЕНАДЦАТЬ → ЧЕТЫРНАДЦАТЬ, по-прежнему КОНСТАНТА), — вместо того чтобы открывать новый внутренний
HTTP-маршрут в engine. `api` и `engine` разделяют ОДНУ физическую базу,
разделённые лишь схемой Postgres, и прецедент уже был
(`apps/api/scripts/medir-execucao.ts` уже читает `engine.oban_peers`); это
решение поднимает шаблон с ручного скрипта до ПРОТЕСТИРОВАННОГО production-кода
(минимальный и объявленный fixture таблицы engine в
`test/support/global-setup.ts`). Принятое и объявленное в ADR
0097 следствие: запрос предполагает, что тот, кто эксплуатирует продукт, мигрирует обе стороны
вместе (`db:migrate` И `engine:migrate`), и падает громко/видимо, если мигрировала только api
— без try/catch, скрывающего ошибку.

## Сессия выполнения больше не закрывается при ожидающем dev agent (RN-411) {#sessão-de-execução-não-fecha-mais-com-dev-agent-pendente-rn-411}
Исправление дефекта, найденного в РЕАЛЬНОЙ сессии выполнения, а не пункт
сценария: пять dev agents поднялись, стали `idle_tripped` (RN-047,
circuit breaker), застряв в ожидании, пока пользователь разблокирует задачу за
задачей, а 30-секундный heartbeat сессии (`Engine.Sessions.SessionServer`)
закрыл сессию из-под них, пока ручная разблокировка продолжалась.
Третий сигнал `GetSessionPendingWorkUseCase` (RN-064) читает только
`agent.status`, словарь разговорных агентов, — dev agents
говорят `dev.*` (`Engine.Dev.AgentIo`) и никогда не выдают `agent.status`, поэтому
ни один dev agent никогда не удерживал сессию этим сигналом. Четвёртый сигнал
читает последнее событие `dev.*` каждого `dev-<modulo>`/`dev-<modulo>-2` в
сессии: `dev.working`/`dev.blocked`/`dev.idle_tripped` удерживают сессию
(застрявший в ожидании человеческого решения — ЭТО незакрытая работа); только `dev.idle`
(по-настоящему дренированный) не удерживает. `dev.awaiting_gate`/`dev.awaiting_approval`
ВОШЛИ в линейку через RN-412 — см. ниже; остаточный пробел, который описывал этот
абзац, закрыт.
## Автоматический личный workspace при регистрации (RN-410) {#workspace-pessoal-automático-no-cadastro-rn-410}
Найдено при навигации: кнопка «Novo projeto» в dashboard ничего не делала, без
ошибки. Корневая причина: `RegisterUseCase` и `SocialLoginCallbackUseCase` (в ветке,
которая создаёт новую учётную запись) создавали пользователя и учётные данные, но НИКОГДА
workspace — КАЖДАЯ новая регистрация упиралась в эту стену, и это не проявлялось раньше
только потому, что `seed.ts` всегда создаёт workspace вместе с демонстрационными данными.
Обе точки теперь создают workspace и добавляют пользователя как `owner`
в ТОЙ ЖЕ транзакции, которая уже создаёт учётную запись. Имя/slug получаются из единственной
чистой функции `nomeESlugDoWorkspacePessoal` (`domain/auth/personal-workspace.ts`),
чтобы правило не расходилось в двух файлах; slug всегда получает суффикс
`userId.slice(0, 8)` (тот же шаблон, что `extraDevAgentId`), чтобы быть уникальным
без обращения к базе (RN-410).

## 413 в PR и Executores «без выполнения» — оба конца и цепочка (RN-412, ADR 0098) {#413-nas-prs-e-executores-sem-execução--as-duas-pontas-e-o-encadeamento-rn-412-adr-0098}
Это не запланированная фаза: исправление, запрошенное реальным ИСПОЛЬЗОВАНИЕМ («nas PRs sempre está
estourando entity too large»), плюс родственный дефект вкладки Executores,
появляющейся пустой при реально идущей работе. Расследование нашло их
сцепленными: gate умирает с `413` → dev-ы застревают в
`dev.awaiting_gate` → это состояние не удерживало сессию (пробел
RN-411) → 30-секундный heartbeat закрывает сессию из-под них → вкладка требует
активной сессии и исчезает со всем roster.

**Причина 413 была в API Brabo, а не в provider-е LLM** —
комментарии, приписывавшие ошибку provider-у (`runtime.exs`,
`terminal_executor.ex`, `docker-compose.yml`), были неверны;
`FalhaDeTurno.origem({413, _})` уже классифицировал её как `"codigo"`, и
был прав. `apps/api/src/main.ts` никогда не настраивал предел тела
Express — действовало значение по умолчанию 100 KB, намного ниже 8 MB, которые
принимает Phoenix, в самом тяжёлом направлении транспорта (engine → api,
`POST /internal/sessions/:sessionId/llm-turn`, который пересылает ВСЮ
историю на каждой итерации ToolLoop). `API_JSON_BODY_LIMIT` (по умолчанию
10 MB) закрывает транспортный конец.

Второй конец, без которого поднятие лимита лишь отложило бы переполнение:
`ContextManager` engine (ADR 0098) имел ДВА дефекта, которые
делали компактизацию недостижимой до переполнения тела —
`estimate/1` считал только `content`, поэтому сообщения `assistant`,
полные `toolCalls`, стоили в оценке ~ноль токенов; а окно
компактизации использовало только `context_window` (128.000 токенов у агентов
gate), что давало ~350 KB до компактизации — далеко после
любого разумного транспортного предела. ЭФФЕКТИВНОЕ окно теперь
`min(context_window, teto_de_transporte)`, с обрезкой всегда на
ГРАНИЦЕ ИТЕРАЦИИ ToolLoop (никогда не отделяя `assistant` с
`toolCalls` от `role: "tool"`, которые на него отвечают, — это сломало бы протокол
tool-use provider-а).

**RN-412** расширяет RN-411: `DEV_PENDING_TYPES` получил
`dev.awaiting_gate` (исходный аргумент — gate может умереть и бессрочно
держать dev agent в этом состоянии), а также
`dev.awaiting_approval`, по новому аргументу, найденному в расследовании:
решение об одобрении записывает `proposed_actions.status`
СИНХРОННО, а возобновление dev agent через outbox/Oban — АСИНХРОННО;
в окне между ними ничто не удерживало сессию — тот же дефект
RN-411 уровнем глубже.

**Вкладка Executores/Обзор** имели родственный дефект на стороне web:
`executionActivated` выводился из `events.some(...)` по окну
всего из 200 событий `useSessionEvents` — `execution.activated` — одно из
ПЕРВЫХ событий сессии и выпадало из окна в любом реальном
выполнении, стирая весь roster. Правильное значение уже существовало, агрегированное
по ВСЕМ событиям, в сводке workspace (RN-090,
`projects-summary.repository.ts`) — оба экрана стали потреблять
это значение. Бонусная находка по пути: `ExecutionSection` (Обзор)
пересчитывал `activated` снова, независимо, по тому же
окну — длительное выполнение снова предлагало «Ativar execução»,
будто никогда не начиналось; исправлено заодно. `gatesEverOpened`
страдает от ТОГО ЖЕ класса дефекта и остался ОБЪЯВЛЕННЫМ известным
ограничением, не исправленным здесь — его исправление потребовало бы изменить сигнатуру
`deriveAgentRoster`/`rosterFactsFromEvents`, вне объёма этого
точечного исправления.

## Neo4j как граф знаний — фундамент (RN-413/414/415, ADR 0099/0100) {#neo4j-como-grafo-de-conhecimento--a-fundação-rn-413414415-adr-00990100}
Запрос владельца продукта: Neo4j + `ollama-model-loader` (gemma:1b,
yi-coder:1.5b, nomic-embed-text), явно вдохновлённый репозиторием
[ErickWendel/neo4j-ai-experiments](https://github.com/ErickWendel/neo4j-ai-experiments)
— благодарность зафиксирована в ADR 0099 и в `prompts/README.md`, за
конкретное вдохновение шаблоном «промпт как версионируемый файл, а не строка,
зашитая в код» и графом как памятью агентов.

Две ответственности, один фундамент: **версионируемые шаблоны промптов**
(`PromptTemplate`/`PromptVersion`, идемпотентно по хешу — RN-413) и
**реляционная память** (взаимодействия, гипотезы Psicólogo с уликами,
профили Anamnese, handoffs — реальное потребление — будущая волна, эта сдача
лишь строит механизм). Граф — ПРОИЗВОДНАЯ память, никогда не источник
истины; pgvector остаётся векторным индексом чанков, без
дублирования embedding в двух базах. Драйвер `neo4j-driver` в api (не в
engine) — api уже владеет всей персистентностью и RAG, engine
потребляет по внутреннему HTTP с service token, как всегда.

`rag_search` (RN-414) закрывает самую большую дыру существующего RAG: ни один агент его не
запрашивал, только web-вкладка «Chat RAG». Новый инструмент в engine, собственные пределы
(RN-150), деградация всегда видна в начале текста для модели.
`ollama-model-loader` (RN-415) закрывает отдельный настоящий баг: `nomic-embed-text`
никогда не скачивался автоматически, и RAG молча деградировал до чисто лексического
в любой чистой среде.

Первая партия шаблонов вынесена в `prompts/*.md` (ux-designer,
Psicólogo, Anamnese, суммаризация `ContextManager`).

## Потребление графа — шаблоны без касания GenServers, релевантность без замены свежести (RN-416/417, ADR 0101) {#consumo-do-grafo--templates-sem-tocar-genservers-relevância-sem-substituir-recência-rn-416417-adr-0101}
`InstructionFiles` получил источник `:graph` (`db > graph > dir > root` —
`instruction_patch` пользователя по-прежнему побеждает всё), и ТРИ агента
стали ПЫТАТЬСЯ разрешить шаблон из графа перед inline-текстом, который
стал обязательным fallback-ом: ux-designer (`graph_instruction_templates_enabled?`),
Psicólogo и Anamnese (`graph_templates_enabled?`, один ключ на
обоих). Два флага, а не один — они столкнулись бы ПРОТИВОПОЛОЖНЫМИ значениями по умолчанию между
параллельными фронтами, если бы делили ключ; оба значения по умолчанию — `false`.
Только `context-manager-summarize` (из четырёх шаблонов партии) остался без
потребителя в то время — пробел, который ADR 0101 объявил открытым и который закрылся
позже, через ЧЕТВЁРТОГО потребителя ТОГО ЖЕ `graph_templates_enabled?`:
промпт суммаризации `ContextManager` (`prompt/1`, см. RN-417).

`Psychologist.ContextBuilder`/`Anamnese.ContextBuilder` получили
ВТОРОЙ источник контекста — `rag_search`, с запросом, выведенным из триггера
анализа, — в КОМПОЗИЦИИ с привычным чтением свежих/временного окна,
никогда не в замену: без совпадения поведение идентично прежнему.
Фрагменты входят в СУЩЕСТВУЮЩИЙ бюджет `Triage`, и
`degraded: true` от RAG всегда видим в контексте, никогда не скрыт.

Граф пишет себя сам: `GraphProjector` (api) дренирует ВТОРУЮ
строку outbox (`aggregateType: 'graph_projection'`, та же транзакция,
значение, которое фильтр engine — `IN ('session', 'task')` — никогда не совпадает,
избегая гонки с `Engine.Outbox.Drain`, который уже дренирует `'session'`
за ~2s), и вызывает уже существующие варианты использования записи. Engine
НИКОГДА не пишет в граф напрямую — это сохраняет event log единственным источником
истины; граф восстанавливается воспроизведением.

**Настоящая находка во время проверки, записанная, потому что учит**: тест
предела тела RN-412 (`apps/api/test/main.spec.ts`) имел СКРЫТЫЙ
баг — `AppModule`, импортированный СТАТИЧЕСКИ в начале файла, вычисляет
`DrizzleModule` (который создаёт свой пул подключений в области МОДУЛЯ, а не
в фабрике Nest) ДО того, как `beforeAll` успевает направить
`DATABASE_URL` на тестовую базу. Это маскировалось, пока локальная база dev
тоже была мигрирована (та же таблица, поэтому запрос «находил», даже
указывая не туда); вскрылось, как только база dev была
пересоздана пустой (настоящим smoke-тестом этой же волны против
Neo4j+Postgres). Исправлено ДИНАМИЧЕСКИМ `await import(...)` внутри
`beforeAll`, после того как `DATABASE_URL` уже задан, — это шаблон, которому следовать
всегда, когда тесту нужно перенаправить `DATABASE_URL` для настоящего
`AppModule`.

## Локальный runner — выполнение на машине пользователя (RN-418/419/420, ADR 0102/0103) {#runner-local--execução-na-máquina-do-usuário-rn-418419420-adr-01020103}
Запрос владельца продукта: агент, работающий на МАШИНЕ ПОЛЬЗОВАТЕЛЯ, в локальной
папке проекта, через стандартный терминал пользователя, — плюс настоящий
интерактивный терминал во вкладке Code. Два изменения, одно зависит от другого.

**Политика (ADR 0102 — ГЛОБАЛЬНОЕ решение, явно подтверждённое владельцем
продукта после автоматического предупреждения безопасности об изменении)**:
`git push`/PR/deploy (RN-106) и `sudo`/`doas` (новые) выходят из безусловного
`deny` и становятся АБСОЛЮТНЫМ ПРЕДЕЛОМ — безусловным `require_approval`,
в ТОМ ЖЕ блоке и по ТОМУ ЖЕ шаблону, что соседние пределы (`current.policy ===
'auto_approve'`), никогда не автоодобряемым ни через `agent_autonomy` (подстановка `"*"`),
ни через `permissions.json`. Щель, которую исходный `deny` затыкал силой,
закрыта в ИСТОЧНИКЕ: `ApproveAlwaysActionUseCase`/`patternForAction`
отказываются записывать шаблон в `allow` для действия с внешним git-эффектом или
привилегированной командой — «sempre permitir» одобряет только экземпляр, никогда
шаблон, для этих двух случаев. Без этой второй половины предел был бы
декоративным. `sudo`/`doas` совпадают по ГЛАГОЛУ в `comandoPrivilegiadoNoComando`
(`external-effect.ts`), обходя все сегменты команды, — тот же
принцип, что у `efeitoExternoNoComando`.

**Runner (`apps/runner`, новый workspace Node/TS, ADR 0103)**: CLI
(`brabo-runner --project <id> --dir <pasta> --token brb_...`), который
пользователь запускает на своей машине, подключается к ENGINE через НОВЫЙ канал Phoenix
(`/runner`,
топик `terminal:<projectId>`), аутентифицированный ОДНОРАЗОВЫМ тикетом (тот же
шаблон RN-108, но тикет ВЫПУСКАЕТСЯ ENGINE — схема `"engine"`,
собственная миграция — и запрашивается api через внутренний HTTP-маршрут, инвертируя
поток тикета сессии). Выполняет `exec` (УЖЕ ОДОБРЕННУЮ команду агента
— маршрутизация в `TerminalExecutor` происходит только ПОСЛЕ привычного конвейера
`decide()`/`proposed_action`, никогда до) в `$SHELL`
пользователя, и интерактивный режим PTY для вкладки Terminal (`pty_open`/`pty_data`/
`pty_input`/`pty_resize`/`pty_close` — engine делает чистый RELAY, никогда
не интерпретируя байты). Только ОДИН runner на проект (`Engine.Runners.Registry`,
`:global`, исключительность `:global.register_name/3`); режим `runner` БЕЗ
проверенного workspace или БЕЗ подключённого runner-а явно ОТКАЗЫВАЕТ — никогда
не падает в `System.cmd`/bind-mount, которых для проекта `runner` не существует
(пересмотрено ADR 0104/RN-423, см. выше; откат на привычный
путь по-прежнему действует, но только для `container`/`mounted`). PTY — действие
аутентифицированного ПОЛЬЗОВАТЕЛЯ, не проходит через `proposed_action`, но аудируется
(`terminal.session.started`/`ended` в event log, в том числе когда вкладка
падает без явного `pty_close`).

Граница безопасности runner-а — НЕ sandboxing, это аутентификация
(CLI предъявляет Personal Access Token УЧЁТНОЙ ЗАПИСИ пользователя) + привычный
конвейер одобрения + согласие пользователя запускать
CLI на собственной машине, с его привилегиями. `apps/runner/src/guard.ts`
проверяет `cwd` внутри корня лексическим разрешением, но объявлен
BEST-EFFORT, а не настоящей гарантией.

**PAT закрыл пробел токена автоматизации (ADR 0105/RN-424..426).**
Настоящая находка Волны 1 — «у продукта нет механизма ДОЛГОЖИВУЩЕГО токена учётной записи
для автоматизации, поэтому runner повторяет вход браузера
(cookie/CSRF, сохранённые в `~/.brabo/runner-credentials.json`)» — была
закрыта в Волне 2: `personal_access_tokens` (`brb_…`, хеш HMAC-SHA256+
pepper через `hashDeToken()`, никогда argon2 — неверно для секрета ВЫСОКОЙ
энтропии) выпускается в Настройках проекта, с областью ОДНОГО проекта,
отзываемый, с опциональным истечением. `apps/runner/src/auth.ts` полностью потерял
интерактивный вход, cookies и файл учётных данных — он лишь
проверяет формат и передаёт `--token`/`BRABO_ACCOUNT_TOKEN`, НИКОГДА не записываемый
CLI на диск. PAT никогда не аутентифицирует вне
`POST .../runner-ticket`, по ПОСТРОЕНИЮ (`IS_PAT_ROUTE_KEY`/
`@RequirePatAuth()` + `PatAuthGuard`) — никогда ветка в глобальном `JwtAuthGuard`,
которая позволила бы `RolesGuard` авторизовать PAT для любого маршрута
роли пользователя.

**`maintainer` отзывает PAT другого пользователя (RN-427)**, закрывая пункт,
который ADR 0105 пока объявил вне объёма (реагирование на
инцидент — уволенный dev с утекающим токеном). Расширение той же модели,
без нового ADR: ОТДЕЛЬНЫЕ маршруты (`GET .../personal-access-tokens/all`,
`DELETE .../personal-access-tokens/:tokenId/admin`), область по
`projectId` вместо `userId` — самоотзыв каждого пользователя
(RN-426) не меняется.

`@xterm/xterm`/`@xterm/addon-fit` (web) и `phoenix`/`node-pty` (runner) —
четыре новые зависимости — та же линейка исключения, что у `mermaid`
(ADR 0068): динамический `import()`, отсутствие `eval`/`new Function` подтверждено
grep-ом по установленному пакету (это не формальная гарантия против обфускации, только
сильная улика — объявлено как неопределённость, а не утверждено как уверенность).

**ADR 0104 — Волна 1 ЗАВЕРШЕНА (RN-421/422/423):** ADR 0072 и 0103
никогда не разговаривали друг с другом — RN-170 требовал bind-mount при создании, а маршрутизация в
runner (RN-420) переиспользовала тот же флаг `workspace_mode == 'local'` без
какого-либо bind-mount, поэтому настоящее использование runner-а по-прежнему было обязано
проходить проверку смонтированной папки. `workspace_mode` (2 значения) стал
`execution_mode` (`container`/`mounted`/`runner`, миграция `0048`) —
RN-170 (теперь RN-422) начинает действовать только для `mounted`; `runner` рождается с
путём, проверенным только ЛЕКСИЧЕСКИ (без I/O), и `workspaceVerifiedAt: null`,
продвигаемым в проверенный, когда runner подключается и подтверждает путь на
ХОСТЕ (`POST /internal/projects/:projectId/workspace-verification`, RN-423)
— runner — ИСТОЧНИК ИСТИНЫ пути, перезаписывающий то, что было
набрано в мастере. `Engine.Actions.TerminalExecutor.decisao_de_execucao/1`
получил ЧЕТЫРЕ выхода: маршрутизирует только при проверенном workspace И подключённом
runner-е; без любого из двух явно ОТКАЗЫВАЕТ — никогда не падает в
`System.cmd`/bind-mount от `mounted`, которых для проекта
`runner` не существует.

**Находка реализации, исправляющая ADR (который не редактируется —
исправление живёт здесь и в
[backlog.md](backlog.md#backlog-of-the-runnerexecution_mode-adr-0104)):**
фраза ADR 0104 о том, что конвертация между тремя режимами существующего
проекта «становится разрешённой без пересоздания проекта», НЕВЕРНА.
`UpdateProjectDto` по-прежнему намеренно исключает `executionMode`/`workspacePath`
— это не тривиальный PATCH (worktree, permissions.json и кеш
engine указывают на старую область). Волна 1 сдала лишь поле из трёх
значений при СОЗДАНИИ; конвертация существующего проекта — будущая волна, с

Волна 3 (ADR 0106) сдала само распространение — `tsup` упаковывает

## ИНСТРУМЕНТ РАЗРАБОТКИ — `pnpm bootstrap` {#ferramenta-de-desenvolvimento--pnpm-bootstrap}
Терминальное меню в `scripts/dev/bootstrap.sh`, группирующее то, что делается
изо дня в день: Docker, K8s, Database и Test. Существует, потому что эти команды живут
в ТРЁХ местах, которые не разговаривают, — `package.json`, `Makefile` и скрипты в
`deploy/k8s/`/`docker/` — а заученное знание гниёт.

Оно **ничего не переизобретает**: каждый лист вызывает уже существующую команду.
Режим `--print-commands` разрешает всё дерево без TTY и без выполнения, и именно
на нём работает тест (`scripts/dev/bootstrap.spec.ts`) — TUI не тестируется
модульно, но отображение меню→команда — да, и ошибается именно оно.
Ноль новых зависимостей; цвета берутся из `design/tokens.css` в 24-битном ANSI
с деградацией до 256 цветов и до отсутствия цвета.

Вывод выполняющейся команды ПРОКРУЧИВАЕТСЯ (колесо мыши в SGR, `j`/`k`,
PageUp/PageDown, `G` для возврата в конец). Не хватало не чтения колеса: не хватало
СМЕЩЕНИЯ — `tail -n` умеет показывать только конец, — поэтому окно стало срезом
через `sed -n 'a,bp'`, тестируемым без TTY через `--print-window`. Два следствия,
которые объявляет подвал: прокрутка назад ЗАМОРАЖИВАЕТ окно (как `less +F`, иначе
перерисовка с частотой 5 Hz отменяет прокрутку), а отслеживание мыши, включаемое только на экране
выполнения, выключается при ЛЮБОМ выходе — `\e[?1006l\e[?1000l` в
`restaurar_terminal`, который покрывает trap на EXIT. Парсер escape — общий CSI
(читает до финального байта): чтение двух фиксированных байтов оставляло остаток последовательности
в буфере, а поскольку меню трактует `[1-9]` как выбор, поворот колеса запускал
пункты меню.

Три зафиксированных решения: `Create` готовит с нуля, а `Deploy` публикует
в уже существующую среду (поэтому выбор по сервису есть только у `Deploy`);
в K8s работает только `All`, а Api/Engine/Web появляются ВЫКЛЮЧЕННЫМИ, а не
исчезают, потому что меню должно говорить, чего продукт не делает; и
`Database › Delete` пересоздаёт расширение pgvector, поскольку
`docker/postgres/init.sql` выполняется только при первой инициализации тома —
чистый `DROP SCHEMA` заставил бы следующую миграцию упасть, а поскольку engine
делит ту же базу, восстановление требует `db:migrate` И `engine:migrate`.

**`Docker › Reset total`** (`scripts/dev/reset-total.sh`) объединяет всю эту
последовательность в один лист — preflight, `up --build --wait` (
`--wait` из Compose v2.17+ — это «пока всё не станет здоровым», без цикла здоровья,
написанного вручную), тот же `DROP SCHEMA`, что у Delete, `db:migrate` +
`engine:migrate` и seed — с СОБСТВЕННЫМ экраном подтверждения
(`confirmar_reset`, требует набрать `RESET`), отличным от экрана Delete (который
требует ИМЯ базы), и без предусловия Delete «postgres уже запущен»,
потому что именно эта команда поднимает compose с нуля. Seed
(`apps/api/src/db/seed.ts`) получил шаг, активирующий учётные данные
provider-а из `.env`, переиспользуя ТЕ ЖЕ переменные
`<PROVIDER>_TEST_KEY`, которые уже используют smoke-тесты LLM
(`apps/api/test/infrastructure/llm/*.smoke.spec.ts`), — одно соглашение
об именах, два потребителя; provider без заданной переменной не входит, без
ошибки, и учётные данные остаются у OWNER-а (RN-058).

Две находки при первом запуске сброса, а не из-за самого пункта —
ни одна не гипотетична, обе сломали реальное выполнение:

1. `gemma:1b` не существует в registry Ollama (`manifest unknown` — существует только
   `gemma3:1b`), поэтому `ollama-model-loader` всегда падал, и
   `--wait` никогда не закрывался зелёным. Исправлено в шести местах, нёсших
   неверное значение как КОД — `docker-compose.yml`/`.prod.yml`,
   `.env.example`, `docker/ollama/pull-models.sh`,
   `scripts/dev/verificar-modelos-ollama.sh`,
   `deploy/k8s/base/ollama/job-model-loader.yaml` и RN-415 в
   `docs/business-rules.md` — без касания ADR 0099/0100 (принятых) и
   исторического повествования этого же раздела CLAUDE.md, которые описывают то, что
   было запрошено/решено тогда, а не текущее операционное значение.
2. Серьёзнее и старше — `Database › Delete` (пункт 3.4, существующий
   с создания меню) никогда не удалял по-настоящему: `DROP SCHEMA public
   CASCADE` не достаёт до `engine.*` (Ecto/Oban живёт в СОБСТВЕННОЙ схеме,
   `engine`) и до `drizzle.__drizzle_migrations` (управление drizzle-kit
   живёт в СОБСТВЕННОЙ схеме, `drizzle`). Результат: `mix ecto.migrate` упирался
   в `duplicate_table` на выживших таблицах engine, а
   `pnpm db:migrate` — хуже, БЕЗ какой-либо ошибки — видел нетронутое управление
   drizzle-kit, заключал, что уже всё выполнил, и не пересоздавал
   НИ ОДНОЙ таблицы api. `Delete`/`Reset total` теперь удаляют также `engine` и
   `drizzle`, в этом порядке, до `public`.

## Ручной handoff выбранному агенту (RN-440/441, ADR 0109) {#handoff-manual-a-agente-à-escolha-rn-440441-adr-0109}
Закрывает пункт backlog, открытый с ФАЗЫ 13c. `CreateHandoffUseCase`
остаётся ЕДИНСТВЕННЫМ местом, которое записывает `toAgent` (ADR 0038), — он получил лишь
опциональный `actor?: Actor`, по умолчанию привычный `{kind:'agent', id: fromAgent}`.
`RequestManualHandoffUseCase` (новый маршрут, `POST
.../sessions/:sessionId/handoffs`, роль `developer`) проверяет `toAgent`
против `addressableAgents()` — ЗАКРЫТОГО каталога (lead-ы областей ∪
`SOLO_CONVERSATIONAL_AGENTS`), строже, чем `assertHandoffTargetAllowed`
(который отклоняет только субагента), — разрешает `fromAgent` по самому свежему
`agent.activated` сессии (sentinel `"usuario"`, если ни одного), и записывает
`actor: {kind:'user'}`. Handoff рождается `offered`, как и автоматический:
уже существующая карточка принятия (`SessionPage.tsx`) подхватывает его сама, ноль
изменений на пути принятия.

Расследование ДО написания кода нашло `ux-designer` (ADR 0087) в ТОЙ ЖЕ
ситуации, что и Staff (ADR 0088), которая мотивировала пункт: клауза `message/2`
готова в `agent_command_controller.ex`, никакого человеческого пути к ней.
Оба вошли в `AGENTES_DE_CHAT` в одном изменении — `infra`/`qa`
остаются вне, по тому же уже задокументированному там шаблону (lead-ы без `kickoff/1`
и без клаузы `message`). Объявлено, не скрыто: зеркало
`SOLO_CONVERSATIONAL_AGENTS` на стороне web (`apps/web/src/lib/agents.ts`)
НЕ сверяется тестом с зеркалом api — расхождение даёт в худшем случае
устаревший вариант в селекторе, который backend всё равно отклоняет с 400.

## Бюджет по области — закрывает отсечение ADR 0038 (RN-443, ADR 0110) {#budget-por-área--fecha-o-corte-do-adr-0038-rn-443-adr-0110}
Одобренный пункт backlog («Older backlog», `docs/explanation/backlog.md`).
`agent_areas` получает `budget_micros`/`spent_micros`, в точности отражая
`max_parallel` — та же строка, тот же владелец решения (`maintainer`), без
новой таблицы. Это ТРЕТИЙ ДОБАВОЧНЫЙ предел рядом с проектом и сессией
(`CheckBudgetGateUseCase` проверяет все три параллельно, любой заблокированный
уже отказывает), **а не** каскад binding модели из ADR 0064 (`sessão >
agente > área > projeto > workspace`, «побеждает наиболее конкретный») — два
механизма разделяют слово «область» и больше ничего; не путать их —
центральная мысль ADR 0110, так же как RN-101/ADR 0063 уже
отделяет представление владельца от представления участника в отчёте о расходах.
`spent_micros` суммирует ВСЕГДА, когда актор принадлежит области (lead или
участник, через `areaDo` — чистая функция, без обращения к базе для актора без области),
с настроенным `budget_micros` или без (`null` — значение по умолчанию, без предела).

## Автономный бинарник runner-а (2026-08-23, RN-451/452, ADR 0112) {#binário-standalone-do-runner-2026-08-23-rn-451452-adr-0112}
Пункт backlog ADR 0104 («standalone binary, `pkg`/`bun build
--compile`»), спутник ADR 0106 (распространение через npm). Явное решение
владельца продукта: по-настоящему ЕДИНЫЙ бинарник, полная матрица
с Windows с v1 — более дешёвая альтернатива («бинарник + папка
`node-pty-native/` рядом») была предложена и отклонена.

`bun build --compile` встраивает нативный `.node` из `node-pty` через
`with { type: 'file' }` и извлекает его в НАСТОЯЩИЙ ВРЕМЕННЫЙ каталог в
runtime (`native-pty-loader.ts`) — необходимо, потому что `node-pty` разрешает
собственный addon через `require()` по ВЫЧИСЛЯЕМОМУ пути
(`lib/utils.js#loadNativeModule`), который Bun не умеет встроить сам
(build проходит, runtime выбрасывает `Cannot find module`, протестировано до
проектирования исправления). Пять платформ
(`linux-x64`/`linux-arm64`/`darwin-x64`/`darwin-arm64`/`win32-x64`), каждая
собрана на своём НАТИВНОМ runner-е
(`.github/workflows/build-runner-binaries.yml`, триггер финального тега,
тот же шаблон, что `publish-runner.yml`), бинарник прикреплён к уже
существующему Release.

**Честная проверка, по платформам**: только `linux-x64` был действительно
выполнен в этой среде (`build:bin`+`smoke:bin` зелёные, многократно —
именно при запуске настоящего бинарника проявились два бага ниже). Остальные
четыре — особенно Windows, с ТРЕМЯ нативными файлами вместо одного —
были продуманы чтением исходного кода `node-pty`, ни разу не выполненные
на реальной машине той ОС; их первое настоящее выполнение — СЛЕДУЮЩИЙ
тег версии, а не этот PR. Ни один платформенный fallback не был применён
превентивно — ничто в этом расследовании не ДОКАЗАЛО, что какая-либо из пяти не
работает так; если настоящий тег покажет, что да, это станет новым пунктом, а не
сегодняшним предположением.

Два дефекта, найденные только запуском скомпилированного бинарника, а не чтением API:
`--external node-pty` должен быть в команде `bun build`, даже при отсутствии
какого-либо статического `import` `node-pty` в коде — fallback `await import(...)`
(используемый только вне бинарника) всё равно обнаруживается и встраивается Bun
и падает в runtime с обманчивой ошибкой; и защите
автозапуска (ADR 0106) понадобилась вторая ветка — `process.argv[1]` внутри
бинарника — ВИРТУАЛЬНЫЙ путь (`/$bunfs/root/...`), до которого `realpathSync`
не дотягивается, выбрасывая `ENOENT` вне любого `try/catch` до того, как
`main()` будет вызван.

## Конвертация execution_mode существующего проекта (RN-447..450, ADR 0111) {#converter-execution_mode-de-projeto-existente-rn-447450-adr-0111}
Закрывает исправление, которое Волна 1 runner-а (ADR 0104) зафиксировала в
`docs/explanation/backlog.md`: пункт 4 того ADR говорил, что конвертация
`execution_mode` между `container`/`mounted`/`runner` в уже существующем проекте
«становится разрешённой без пересоздания проекта», и до сих пор это было ложью —
`UpdateProjectDto` по-прежнему намеренно исключает оба поля.
`PUT projects/:projectId/execution-mode` (`maintainer`,
`ConvertProjectExecutionModeUseCase`) — ВЫДЕЛЕННЫЙ маршрут, а не ослабленный
`PATCH`: он оркестрирует миграцию, а не просто меняет столбец.

Отказывает с 409, пока любой dev agent проекта (в ЛЮБОЙ сессии,
прочитанный напрямую из `engine.dev_agent_states` по `project_id`, тот же путь, что у
RN-409) не находится в `idle` — `idle_tripped` здесь СЧИТАЕТСЯ активным, в
отличие от критерия «онлайн» RN-409, потому что у агента ещё есть
`workspace_root`, захваченный в памяти в ожидании человеческой разблокировки
(RN-447). `PermissionsFileStore` получил `move(from, to)`: содержимое
permissions.json никогда не меняется, меняется только физический путь, потому что `projectScopeRoot`
выводится из пары (режим, путь) (RN-448). При выходе из `container` с
подготовленным контейнером жизненный цикл (ADR 0081) доводится до `removed` — через
`stopped` сначала, если был `running`, — ДО изменения столбца, потому что
`RegistrarTransicaoDeContainerUseCase` отклоняет переход вне режима
`container`; вход В `container` никогда не готовит автоматически (RN-449).
`workspaceVerifiedAt` обнуляется при каждой настоящей конвертации, в том числе при возврате в
`runner` с внешне одинаковым путём (RN-450). Та же (режим, путь), что и
сегодня, — no-op, даже не проверяет активного dev agent.

**Объявленное, не скрытое следствие**: конвертация НИКОГДА не копирует
уже написанный код между старым и новым корнем. Это безопасно для того, что уже
ЗАКОММИЧЕНО — engine выводит worktree из bare-репозитория с нуля
(`Engine.Actions.Workspace.ensure!/4`) всякий раз, когда папка назначения ещё
не помечена готовой, поэтому следующий агент перестраивает рабочее
дерево в новом корне из настоящего git. Что НЕ выживает — это
НЕзакоммиченный diff в брошенном worktree: он остаётся сиротой на старом диске,
никогда не мигрируемый и не удаляемый. Предел активного dev agent (RN-447) снижает
риск (никогда не конвертирует при агенте `working`), но не устраняет: агент
`idle` между tasks может сидеть на грязном diff, и ничто здесь
не проверяет чистоту рабочего дерева перед конвертацией.

## Локальная папка, прикреплённая как справочник Chat RAG (2026-08-23, RN-455..457, ADR 0113) {#pasta-local-anexada-como-referência-do-chat-rag-2026-08-23-rn-455457-adr-0113}
Запрос владельца продукта: прикрепить папку СОБСТВЕННОЙ машины пользователя к
проекту как справочник ДЛЯ ЧТЕНИЯ агентами — без CLI
`brabo-runner` (ADR 0103). Явно НЕ является выполнением/workspace
проекта: `execution_mode: runner` (ADR 0104) нужен CLI, потому что нужен
настоящий путь ХОСТА, чтобы контейнер маршрутизировал команду; это больше
похоже на «прикрепить файлы к разговору». Браузер читает СОДЕРЖИМОЕ
(`File.text()`) и ОТНОСИТЕЛЬНЫЙ путь (`File.webkitRelativePath`)
выбранных файлов — никогда абсолютный путь хоста (API `File`
не открывает его ни одному сайту), и поэтому ADR 0113 прямо говорит, что это НЕ
пересмотр того, что отклонили ADR 0072/0107: те отклоняли
РАЗРЕШЕНИЕ пути хоста из браузера; здесь не существует никакого пути
для разрешения, только байты, которые браузер уже имел право читать.

`chunks.scope` (ADR 0079/0080) получает ЧЕТВЁРТОЕ значение, `'local'` (миграция
`0052`, `ALTER TYPE ... ADD VALUE`, добавочное — оба CHECK миграции
`0045` уже записаны как «это `session` или нет», поэтому `local` попадает на
ту же сторону, что `docs`/`adr`, без нового CHECK). `IndexLocalFolderUseCase`
близко отражает `IndexProjectDocsUseCase` — Markdown-aware чанкинг для
`.md`/`.mdx`, `RagEmbeddingService`, чанк без вектора вместо падения,
когда embedding отваливается (RN-233), — но ОТКЛОНЯЕТ (400) всю загрузку,
когда АГРЕГИРОВАННЫЕ пределы превышены (количество файлов, суммарные
байты), никогда не обрезает молча: это ЕДИНИЧНЫЙ жест пользователя с
селектором папки на экране, а не фоновое сканирование. Отдельный слишком большой файл
или файл с нераспознанным расширением лишь ПРОПУСКАЕТСЯ
(`filesSkipped`), никогда не роняет партию (RN-456). `origemDoChunk` не
понадобилась никакая новая ветка: `local` несёт `sourcePath`, как
`docs`/`adr`, и попадает в `kind: 'file'`, который цитирование уже умело отображать.

**Никогда не входит в общее «Reindexar agora» (RN-457)**: `ReindexProjectUseCase`
переиндексирует, читая из источника, который СЕРВЕР может снова посетить (репозиторий
проекта, event log); у `local` нет никакого источника для повторного посещения —
текст существует только в браузере того, кто прикрепил. Повторное прикрепление папки (новая
загрузка в `POST .../rag/local`, `maintainer`) И ЕСТЬ механизм
повторной синхронизации, намеренно отдельная кнопка, с перекрёстным комментарием
в обоих вариантах использования, указывающим друг на друга и на ADR 0113, чтобы будущее
«исправление» не связало их снова и не стёрло материал пользователя.
Покрытие (`RagCoverage.local`) — СОБСТВЕННОЙ формы — нет «итога в
репозитории» для сравнения — и `lastAttachedAt` — ЕДИНСТВЕННОЕ настоящее исключение из
правила «никогда X мин» (RN-237): настоящий `MAX(chunks.created_at)`, а не
угаданный (RN-458).

## Полоса активности хода — нить получает ответ только в конце (RN-459/460) {#faixa-de-atividade-do-turno--o-fio-só-recebe-a-resposta-no-fim-rn-459460}

Запрос владельца продукта: экран Сессии теперь показывает НАД
composer полосу, которая человеческим языком рассказывает, что разговорный агент
(Criativo, PO, Arquiteto, Dev Lead, UX Designer, Staff)
делает ВО ВРЕМЯ хода — визуальный эталон: строка статуса
Claude Code. Нить получает пузырь ответа только ПОСЛЕ того, как ход
заканчивается; правило относится к ЧАТУ (канал Phoenix) и действует только для шести
разговорных агентов — консультативный чат без активного агента (SSE,
`streamChatMessage`) остаётся с привычным потоковым пузырём,
нетронутым.

**Механизм**: шесть серверов уже выдавали ДОЛГОВЕЧНЫЙ `tool.call`; теперь они
также делают `broadcast(state, "tool.call", %{tool: name, agent: @agent})` —
ЭФЕМЕРНЫЙ, без `args` (RN-096/RN-412), — чтобы канал доставлял в реальном времени.
Нет общего behaviour/макроса между шестью `dispatch_tool`
(четыре разные структурные формы, подтверждено полным чтением) —
изменение — шесть правок, приспособленных к локальной форме каждого, а не
рефакторинг. На стороне web ЧИСТЫЙ reducer
(`reduzirAtividadeDoTurno`/`lib/atividade-do-turno.ts`) накапливает
`agent.delta` как текущий текст; при приходе `tool.call` архивирует
непустой текущий как строку повествования, обнуляет и всегда добавляет
строку инструмента с `fraseDaFerramenta(tool)` (словарь 19
инструментов, `lib/narracao-de-ferramentas.ts`, без собственной RN). СОБСТВЕННЫЙ
флаг (`turnoViaCanal`, никогда не выводимый из `statusAgent`/`streamingAgent`,
которые законно проходят через окна `null` посреди хода) решает, появляется ли
полоса или старый пузырь — никогда оба.

**Правило представления (история)**: `agruparNarracoesDoTurno`, новый
чистый проход после `afundarDesfechos` (RN-172) в том же `useMemo` —
последовательные `agent.response` одного `turno`+`autor` становятся компактным
`Disclosure` («Passos do turno · N»), только последний остаётся нетронутым
вне его. `turno === 0` (сторожевой пролог `turnoDoSeq`) остаётся
ВНЕ группировки — старые fixtures складывают `agent.response` без
границы хода, чтобы тестировать другой механизм (RN-138/RN-177), и без
исключения новая группировка дала бы там `Disclosure` внутри
`Disclosure`. Сам `afundarDesfechos` не изменился.

**Находка по пути, объём расширен по решению владельца продукта**:
расследование выяснило, что ЧЕТЫРЕ из шести серверов (Arquiteto, Dev Lead, UX
Designer, Staff) заканчивали МОЛЧА на пределе итераций —
`defp run_turn(state, remaining) when remaining <= 0, do: state`, без
какого-либо события, вопреки постоянному правилу, что цикл агента не
заканчивается молча. Только PO уже выдавал `toolloop.limit_reached` (RN-166);
Criativo намеренно расходится с `agent.error` (решение задокументировано
в самом коде). Четыре исправленных теперь выдают
`toolloop.limit_reached`, то же событие, что и PO (RN-459).

### Handoff Infra нельзя было принять ни на одном экране (D0) (RN-499) {#o-handoff-da-infra-podia-ser-aceito-por-tela-nenhuma-d0-rn-499}

Infra Lead; его расширение заставило бы экран предлагать несуществующую нить, а composer

### Единая база смонтированных проектов (PR 1, BREAKING) (ADR 0141, RN-500) {#a-base-única-dos-projetos-montados-pr-1-breaking-adr-0141-rn-500}
Создание проекта `mounted` требовало строки bind-mount, написанной ВРУЧНУЮ в `api`
И `engine`, плюс перезапуска обоих — что убивает каждый ход агента, сокет
терминала и вызов LLM в полёте во всей установке, ради подключения ОДНОГО проекта.
Рождается `BRABO_PROJECTS_BASE`: ОДНА база, настраиваемая оператором один раз,
монтируемая по ИДЕНТИЧНОСТИ (`$X:$X`) в обоих сервисах, со всеми смонтированными
проектами внутри неё и НИЧЕГО не редактируется по проекту. Идентичность, а не фиксированная
точка монтирования, потому что `workspace_path` набирается пользователем и показывается ему обратно
— и это то, что позволяет `projectScopeRoot`/`workspace_dir/2` оставаться верными без
нового кода. СОБСТВЕННАЯ переменная (коллизия пространства имён с UNIQUE `workspace_dir_name`
привела бы к `git init` в папке другого проекта; противоположный владелец; база
навигируема, а управляемый корень не должен быть таковым). ОТСУТСТВИЕ — норма: `projectsBase:
null` (`GET workspaces/:id/projects-base`, `maintainer`), и режим не
предлагается. И `pnpm dev` ОТКАЗЫВАЕТСЯ стартовать при базе, пересекающейся с checkout-ом, —
единственная возможная проверка, потому что api сравнивает с `/workspace`. Две объявленные
цены: symlink под базой и только одна база

### Контейнер смонтированного проекта (PR 3) (ADR 0144, RN-503) {#container-de-projeto-montado-pr-3-adr-0144-rn-503}
Проект `mounted` не мог получить НИКАКОГО контейнера из-за двух независимых
блокировок — api отправляла каждый не-`container` режим в RUNNER (который требует
подключённого `brabo-runner`), а broker отклонял не-`container` в источнике. Обе
касались ГЕОМЕТРИИ, а не имени режима, и единая база ADR
0141 изменила геометрию. Ветвление становится по НАЗНАЧЕНИЮ: `container` И
`mounted` → broker, только `runner` → runner (и `container_stop`/`_remove` меняются
ВМЕСТЕ с `_start`, иначе поднимется на сервере и остановится на машине пользователя).
Инвариант ADR 0130 не сдвигается — ни один абсолютный путь не пересекает сеть:
broker получает ВТОРОЙ корень (`BRABO_PROJECTS_HOST_BASE`), а api отправляет
РАЗЛИЧЁННЫЙ локатор (`gerenciada` \|`montada` \|`indisponivel`), говорящий,
относительно какого корня действует относительный сегмент. ТРИ варианта, потому что
у `indisponivel` два разных исправления (`runner` × устаревший `mounted` вне
базы), и недостающий корень НИКОГДА не подменяется другим. `mounted` ВЫБИРАЕТ
образ, как `container`, — broker составляет из `artifact.project_image`, поэтому
незаписанный выбор — инертный выбор (ADR 0133 во втором режиме)

### Dev-агенты только после контейнера (PR 7) (ADR 0143, RN-502) {#agentes-de-dev-só-depois-do-container-pr-7-adr-0143-rn-502}
В реальном выполнении `exp001` ДЕСЯТЬ dev-tasks застряли разом — и
находкой была не упавшая папка, а то, что **ничто не упорядочивало контейнер до
dev agent**. `Engine.Dev.AgentIo.try_claim/2` — ЕДИНСТВЕННАЯ точка claim — начинает
запрашивать `ProjectContainerLifecycle.running?/1` (предикат, который ADR 0134
уже имел) ДО вызова api: без ЗАРЕГИСТРИРОВАННОЙ строки `running` агент падает
в `:idle`, сохраняется и выдаёт `dev.blocked_by_container`. В ENGINE, а не только в
`activate-execution` api, потому что РЕГИДРАТАЦИЯ доходит до `try_claim/2`, не
проходя ни через какой маршрут (`init/1` → `finish_restart_recovery/1`). `:idle`, а
НЕ новый статус, по причине, которую сам docblock `try_claim/2` уже
записывал с Фазы 12b, — это единственное состояние, из которого wake ещё спасает,
и все guard-ы `handle_info/2` на это опираются; «пустую
очередь» от «нет контейнера» отличает СОБЫТИЕ, никогда статус. Wake приходит через outbox:
`RegistrarTransicaoDeContainerUseCase` публикует `container.running` в ТОЙ ЖЕ
транзакции, которая записывает приход в `running`, в НОВОМ `aggregate_type`
(`container`, третий, который читает `Engine.Outbox.Drain`), вместо того чтобы одалживать `task`,
с ПРОЕКТОМ как `aggregateId`; доставляемое сообщение — уже существовавшее `{:wake,
:became_claimable}`. Вторая половина: `TerminalExecutor` перестаёт
молча деградировать — `container` без `running` падал в `System.cmd` ВНУТРИ
процесса engine, а теперь ОТКАЗЫВАЕТ, с `mounted` в той же ветке

### Тревога merge конвейера с получателем (ADR 0139) {#alarme-de-merge-de-esteira-com-destinatário-adr-0139}
Правило «продвижение — это `--no-ff`» было нарушено ТРИЖДЫ (#367, #394, #464 —
третий был PR, исправлявшим первые два). Находка: обнаружение УЖЕ
существовало и УЖЕ сработало (`tag-release` провалил первые два с
правильным сообщением) — не хватало КОМУ звонить, потому что workflow `push`, падающий
на постоянной ветке, не имеет PR, где стать красным, а в репозитории было ноль issues.
`tag-release` получает job `avisar`, который открывает issue (и комментирует в уже открытом,
никогда не дублирует) с `github.token` и никогда с PAT — недействительный PAT — один из
сбоев, о которых он сообщает, — и это перестало быть гипотетическим: `BRABO_BOT_TOKEN`
истёк вечером 2026-09-03, провалил два запуска `tag-release` и был
ротирован 2026-09-04; v4.0.0 проштамповала и ЗАПУСТИЛА Release, что происходит
только с действительным PAT (тег, созданный с `GITHUB_TOKEN`, не запускает workflow).
Правило начинает покрывать `dev` УЗКО: дефектом является только PR, принёсший
НОВОЕ РЕБРО (head был merge, чей второй родитель не был в базе), никогда
squash рабочего PR, что является соглашением. Отключение squash в репозитории было

### ФАЗА 28 (сессия 5) — `join` локального агента перестаёт быть немым (RN-514, ADR 0147, пункт 1) {#fase-28-sessão-5--o-join-do-agente-local-deixa-de-ser-mudo-rn-514-adr-0147-ponto-1}
`join` канала `terminal:<projectId>` был немым с ОБЕИХ сторон — runner
отправлял `{}`, а сервер делал `_params`, — поэтому у сервера не было способа
узнать, понимает ли бинарник на другой стороне новое сообщение, и дефект был
наихудшим из возможных: сообщение приходит, обработчика нет, и НИЧЕГО не происходит, без
ошибки и без лога. Теперь runner ОБЪЯВЛЯЕТ в params
(`Engine.Runners.Capacidades`, словарь `exec`/`pty`/`espelho`), а
сервер ПРЕДОСТАВЛЯЕТ пересечение с тем, что ЗНАЕТ, в `socket.assigns` и НИКОГДА
в таблице (способность — свойство этого ПОДКЛЮЧЕНИЯ). Runner объявляет только
`exec` и `pty` — объявить `espelho`, не реализовав его, — ровно тот дефект,
который предотвращает согласование; он входит как ИМЯ словаря и не более, а
сессия 6 его реализует. Отсутствующие/пустые params — это УСТАРЕВШИЙ бинарник, и они предоставляют
`{exec, pty}` — ФАКТ, а не благосклонность: это две функции, с которыми runner
родился, а отклонение устаревшего было бы `breaking/` и MAJOR. Неизвестное ИГНОРИРУЕТСЯ
(runner НОВЕЕ engine подключается); требуемое-но-не-объявленное отклоняет join,
НАЗЫВАЯ недостающее, ДО `Registry` — механизм реализован и протестирован,
но сегодня НЕ срабатывает (`runner` требует `exec`, который есть у каждого бинарника; ничто пока не требует
`espelho`), и таков замысел. Половина, приносящая пользу СЕГОДНЯ:
сообщение без способности ОТКЛОНЯЕТСЯ с именованным ответом — `exec` отвечает в
формате `exec_result` (126 + причина), вместо того чтобы `RunnerRouter` ждал
timeout, а `pty_*` становится `pty_error` во вкладке вместо исчезновения. `RunnerReadiness`
байт в байт как есть

### ФАЗА 28 (сессия 6, половина B) — зеркало начинает существовать (RN-516, ADR 0147, пункты 2/3/4/8) {#fase-28-sessão-6-metade-b--o-espelho-passa-a-existir-rn-516-adr-0147-pontos-2348}

### Broker, который никогда не поднимался (исправление RN-512) (RN-512, ADR 0130/0146) {#o-broker-que-nunca-subiu-correção-da-rn-512-rn-512-adr-01300146}
RN-512 убрала broker из `profiles`, чтобы он был запущен в dev, и он НИКОГДА не
поднимался: `corepack prepare` выполнялся от ROOT при build (кеш в `/root/.cache`),
контейнер работает как uid 1000, а без кеша corepack пытается СКАЧАТЬ pnpm в
сервисе, чья единственная сеть — `internal: true`, — `EAI_AGAIN registry.npmjs.org`,
`Exited (1)` через пять секунд. Без healthcheck `up --wait` говорил
`Healthy`, а полный сброс объявлял «reset completo» с мёртвым процессом;
пока существовал profile, broker поднимал тот, кто уже на него смотрел.
Исправление убирает registry из RUNTIME и НЕ открывает сеть (первый из пяти
слоёв ADR 0130): `COREPACK_HOME`, подготовленный при build с владельцем uid
runtime, `pnpm install` как шаг BUILD, и — поскольку три тома
`node_modules` перекрывают то, что установил образ, а Docker заполняет только ПУСТОЙ
том, — entrypoint, сверяющий их с копией вне `/workspace`,
помеченной sha256 lockfile из build (та же метка ПРЕДУПРЕЖДАЕТ, что образ
отстал, не отказываясь стартовать). Healthcheck в сервисе, изнутри
контейнера. Production от этого не страдал и не меняется


### ФАЗА 28 (сессия 7) — локальный агент становится пользовательской службой (RN-518, ADR 0147, пункт 5) {#fase-28-sessão-7--o-agente-local-vira-serviço-de-usuário-rn-518-adr-0147-ponto-5}

фатальный отказ join (RN-514) или исчерпанный предел попыток, и перезапуск

CLI никогда не записывал учётные данные на диск. `uninstall` удаляет ВСЕ ТРИ, читая папку
из UNIT-а и никогда из `cwd` (без unit — только с `--dir`; угадывание стёрло бы

сервере. `status` отвечает ЧЕТЫРЬМЯ состояниями с собственной фразой и кодом
(0/3/4/5), и первый ответ приходит с ДИСКА — поэтому он остаётся верным на
машине без менеджера; неудавшийся `spawn` никогда не становится «менеджер сказал
нет». BRB-031 здесь НЕ закрывается

### ФАЗА 29 (сессия 2) — конвейер подписывает то, что публикует (RN-524, ADR 0149) {#fase-29-sessão-2--a-esteira-assina-o-que-publica-rn-524-adr-0149}
Продукт не подписывал **ничего**: `cosign`/`sigstore`/`attestation` не существовали в
`.github/`, `scripts/` или `docker/`, а единственным происхождением был
`--provenance` **npm**-пакета runner-а. `release.yml` публиковал четыре
образа **без** `id-token: write`; `build-runner-binaries.yml` загружал пять
бинарников через `gh release upload` и ничего больше — тогда как уже существовавшие
`sha256sum -c` проверяют **сторонние** бинарники, шаблон, который репозиторий
умел применять и никогда не применял к самому себе. Теперь образы подписываются по
**DIGEST** (никогда по тегу, подвижному указателю), а бинарники получают **ОДИН**
подписанный `checksums.txt`, в job-е `checksums`, который ждёт матрицу, — а не пять
подписей, потому что тот, кто проверяет четыре и забывает пятую, не знает, что
забыл. Job намеренно `if: always()` (`fail-fast: false` в матрице) и
**называет то, что манифест не покрывает**. Оба workflow **проверяют перед
публикацией**. Keyless по истории дома: приватный ключ был бы ещё одним
секретом CI, а PAT уже однажды молча истёк (ADR 0139). Процедура
проверки — в runbook, с двумя **обязательными** флагами `--certificate-*` —
без них `cosign` принимает действительную подпись ОТ КОГО УГОДНО. Закрывает BRB-005
для образов и бинарников; вне остаются, объявлено, code-signing ОС и
прокси загрузки

### ФАЗА 29 (сессия 3) — установщик, который ещё не устанавливает (RN-526, ADR 0150) {#fase-29-sessão-3--o-instalador-que-ainda-não-instala-rn-526-adr-0150}
Рождается `install.sh` в КОРНЕ, версионируемый и раздаваемый через Release. Форма — `sh -c "$(curl …)"` и **никогда** `curl|sh`, по МЕХАНИЧЕСКОЙ причине: с pipe
`stdin` процесса ЯВЛЯЕТСЯ загрузкой, и каждый `read` читает байты самого скрипта или
находит EOF — установщик, который не спрашивает, сам выбирал бы, где создавать папку
на чьей-то машине. Он ПРОВЕРЯЕТ СОБСТВЕННОЕ ПРОИСХОЖДЕНИЕ (подпись
`checksums.txt` из RN-524 и свой хеш ВНУТРИ проверенного манифеста), с
закреплённым `cosign`, сверяемым через `sha256sum` с хешем, записанным в скрипте;
ОБНАРУЖЕНИЕ называет найденное, прежде чем спрашивать; без TTY сообщает и выходит с 0; и
**никогда не удаляет папку пользователя** — база проектов и папка зеркала остаются
вне любого подтверждения, по линейке зеркала (RN-516). Маркер в
`$XDG_STATE_HOME/brabo/`, никогда в `~/.brabo/`, который ПО ПРОЕКТУ. **В этой версии
ничего не устанавливает, и ГОВОРИТ об этом**, вместо того чтобы молча закончить.
`--print-plan`/`--print-state` раскрывают решение без TTY, без сети и без эффекта
— по образцу `--print-commands` из `bootstrap.sh`, тестируемые так же. Два бага
bash, найденные при запуске, оба одного рода: под `set -e`+`pipefail`, `[
cond ] && atribuição`, дающее ложь, УБИВАЕТ скрипт, а несовпавший `ls`
роняет всю подстановку — в функции, чей нормальный случай — «ничего
не нашёл». КОРЕНЬ репозитория не покрывался ни одним docmap (glob-ы
корня — буквальные имена); рождается правило `instalador`

### ФАЗА 29 (сессия 8) — база локального агента получает потребителя (RN-532, ADR 0151, пункты 3–6) {#fase-29-sessão-8--a-base-do-agente-local-ganha-um-consumidor-rn-532-adr-0151-pontos-36}
RN-529 построила БАЗУ и письменно объявила, что её ничто не потребляет. Входит
пара `workspace_create`/`workspace_create_result`, по образцу ЗАПРОСА С
ОТВЕТОМ `exec`/`exec_result` — и НИКОГДА по образцу `workspace_confirm`, который
ОДНОНАПРАВЛЕННЫЙ (`{:noreply, socket}`, ничего не отправляет обратно), уточнение, которое

пишет таблицу, а единственный путь, штампующий `workspace_verified_at`,

потому что оба приходят в один процесс канала по порядку, а обработчик
confirm синхронный). Способность `workspace` входит в словарь В ТОЙ СЕССИИ,
В КОТОРОЙ ВХОДИТ КОД, с обеих сторон — RN-514 сделала противоположную ставку с
`espelho`, и она окупилась лишь потому, что кто-то её востребовал, — и это ЕДИНСТВЕННАЯ из
четырёх, чьё объявление зависит от СОСТОЯНИЯ данного выполнения: runner
объявляет её только при согласованной базе, и именно по этой строке и ни по какой другой
сервер ЗНАЕТ, что база существует (engine не читает диск пользователя). НИКТО её
не требует в join, намеренно: требование её в `runner` было бы `breaking/` и MAJOR

проект `runner` доходит до контейнера `running` только после того, как runner его

отказывает ДО отправки, с `motivo: "sem-base"` по тому же `ref`, в
формате, которого ожидает модуль, — никогда timeout. Пять именованных причин, которые не

### ФАЗА 29 (сессия 5) — бэкап начинает покрывать то, что больно терять (ADR 0152, RN-528) {#fase-29-sessão-5--o-backup-passa-a-cobrir-o-que-perder-dói-adr-0152-rn-528}
Бэкап покрывал ОДНУ базу и работал в ОДНОМ месте: `make test-restore` — путь
Kubernetes (требует `kubectl`, кластер и CronJob), а в `docker-compose.prod.yml`
не было НИКАКОГО сервиса `backup` — у миграции установки через compose не было
доказанного пути. Решение начинается с ОТКАЗА от лёгкого хода («бэкап
всех томов») и с КЛАССИФИКАЦИИ семи: `neo4j_data` и
`project_workspaces` — производные, `ollama_data` — получаемый заново,
`brabo_projects_base` — пользовательский: их копирование создаёт впечатление покрытия, не
добавляя восстановления. Источников истины ДВА, и находка — второй:
**`git_local_repos` не входил ни в один бэкап**, а проект с provider-ом
`local` хранит там *bare* — он не восстанавливается из Postgres (event log
хранит ПОВЕСТВОВАНИЕ, а не объекты git), так что потерять том — значит потерять
код агентов. Проза runbook утверждала обратное («the real
repositories live in GitHub/GitLab»), и именно она объясняет годы без
покрытия: это верно для `github`/`gitlab`, а для `local` upstream нет.
Гарантия архива ОБЪЯВЛЕНА и меньше, чем «снимок», — согласованность по
ССЫЛКЕ (git пишет объекты до сдвига ref и меняет ref атомарным
rename), без глобального момента и без `git fsck` (в образе намеренно нет
git); конкурентный `gc` становится СБОЕМ, а не частичным архивом, со статусом
`tar`, захваченным в ФАЙЛ, потому что в POSIX `sh` статус конвейера — статус
последней команды. Пять переменных S3 перестают быть обязательными и становятся
конфигурацией ОДНОГО назначения (`BACKUP_DIR` выбирает диск; без неё — S3,
этот вывод и сохраняет CronJob НЕТРОНУТЫМ). `make test-restore-compose`
запускает НАСТОЯЩИЙ бэкап и вызывает ТОТ ЖЕ `brabo-restore` с ТЕМИ ЖЕ тремя
проверками: меняется ОБЁРТКА, никогда суждение, и
`deploy/k8s/test-restore.sh` остаётся НЕТРОНУТЫМ (объединение сделало бы вариант compose
зависимым от `kubectl`); `restore.sh` по-прежнему не трогает ИСХОДНУЮ базу.
Восстановление репозиториев — РОДСТВЕННАЯ команда (`brabo-restore-git`, по умолчанию проверяет,
пишет только с `--restaurar`), а не фаза другой — два артефакта, два
суждения, и их объединение заставило бы сбой git проваливать проверку event log.
Находка ПРИ ЗАПУСКЕ, которую чтение бы не дало: том разделяется тремя
образами с разными uid и несёт владельца того, кто смонтировал его первым (измерено
`1000:1000`, режим 0755), тогда как образ работает как uid 70 — извлечение
умирало посередине, оставляя том наполовину; теперь отказывает ДО `tar`,
называя `--user 0:0`, а извлечённое от root возвращается владельцу КАТАЛОГА,
иначе том вернулся бы целым и БЕСПОЛЕЗНЫМ (api и engine, non-root, не
могли бы писать в только что восстановленное). Neo4j получает ПЕРЕПРОЕКЦИЮ, а
не бэкап — здесь не построена (BRB-018): мигрированная установка рождается с
ПУСТЫМ графом, названная деградация, а не потеря данных (RAG живёт в pgvector,
внутри дампа)

### ФАЗА 30 — локальный агент машины (ADR 0154/0155, RN-543..552, закрывается в сессии 8 с RN-549) {#fase-30--o-agente-local-da-máquina-adrs-01540155-rn-543552-fecha-na-sessão-8-com-a-rn-549}
ФАЗА 29 сдала установку одной строкой и ОСТАНОВИЛАСЬ в двух пунктах, которые сам
продукт уже письменно объявлял: локальный агент оставался сопряжённым по
ПРОЕКТУ (кто хотел использовать установленный бинарник, возвращался в браузер, чтобы вставить
команду в терминал), и **никто не мог войти** — сгенерированный `.env` не
содержит переменной e-mail, `MAIL_TRANSPORT` падает в `log`, а регистрация требует
подтвердить e-mail, так что выходом было выуживать ссылку в `docker compose logs api`.
Оба решались в одном месте, и именно это сделало из них одну фазу. Находка, которая
определила её РАЗМЕР, пришла из повторного измерения с `arquivo:linha` утверждения ФАЗЫ
29 о том, что «один runner на проект навязан в пяти местах»: **три из
пяти не нужно было менять**, потому что топик, socket id и тикет описывают
ПОДКЛЮЧЕНИЕ, а процесс, открывающий N подключений — по одному на проект, — удовлетворяет им байт
в байт, сохраняя отказ второму runner-у в том же проекте, что является настоящей
гарантией, а не случайностью. **Ничто в engine не изменилось за всю фазу**, и это
сохранило `RunnerReadiness`, зеркало и `workspace_create` нетронутыми. Осталось
то, что принадлежит ПРОЦЕССУ: учётные данные (`runner_device_keys.project_id` становится
nullable, RN-543 — и список начинает возвращать ОБА помеченных вида,
иначе ключ машины был бы невидимым и постоянным — дефект, который закрыла RN-519,
возродившийся) и unit (RN-545, `service install --machine`, один на
машину, СОСУЩЕСТВУЮЩИЙ с unit-ами по проекту). Два решения противоречили букве
ADR, и оба были ИЗМЕРЕНЫ: дискриминатор unit — флаг `--machine`, а не
отсутствие `--project` (`resolverProjeto` имеет два источника, и обычный путь —
запуск `install` без флага изнутри папки, которую настроил браузер, — буквально
ADR молча сконвертировал бы установку того, кто уже пользуется продуктом), и
`install` ОТКАЗЫВАЕТ, когда другой вид уже установлен, без `--force`, потому что
оба вместе были бы двумя процессами, оспаривающими один проект. Сессия 6
затронула бы три workspace разом и была РАЗДЕЛЕНА на три, причём две
непересекающиеся части вышли раньше, а `install.sh` — после них, как оркестратор и ничего
больше. Из этого разделения вышел самый интересный пересмотр фазы: при НУЛЕ подключений
агент перестал ЗАВЕРШАТЬСЯ и начал ЖДАТЬ, повторно опрашивая через 15s/30s/60s
(RN-550) — аргумент RN-544 против повторного опроса остаётся целым там, где он
действует (список, вернувшийся МЕНЬШИМ, неоднозначен, а обрыв ЖИВОГО подключения из-за неоднозначности
меняет верное состояние на догадку), а при нуле подключений обрывать нечего;
пал аргумент про `exit 0` («активная служба, которая ничего не делает»),
потому что процесс начал что-то делать и ГОВОРИТЬ, что делает. Измерено: `Restart=on-abnormal`
**не смотрит на код выхода**, поэтому ни один unit не изменился, а эффект в том, что unit машины
становится действительно `active (running)`. Другая часть (RN-551) закрывает «никто не СОЗДАЁТ
ключ машины» со стороны агента, и решение там — ОТСЕЧЕНИЕ: CLI **не**
говорит с api, потому что регистрирует установщик с `BRABO_SERVICE_TOKEN`
— каждая сторона хранит секрет, и ни одна не видит секрета другой. Отсюда вытекает замысел
из двух шагов, а из него — инвариант: `kid` ЯВЛЯЕТСЯ id записи и существует только
после неё, поэтому `create` записывает `.parcial`, который читатель игнорирует, а
`finish` записывает настоящее имя — **файл, который читает runner, никогда не существует без
`kid`**, дефект RN-475, ставший невозможным по построению. Половина api
(RN-552) объявила цену, вместо того чтобы её скрыть: учётные данные — service token,
и утёкший токен начинает мочь ФАБРИКОВАТЬ долговременные учётные данные — поэтому три
сдерживания живут в МАРШРУТЕ, а не в тексте (в теле нет `userId`; регистрация
ЗАМЕНЯЕТ активные ключи машины владельца в той же транзакции, так что
переустановленная машина проходит, а тысяча ключей невозможна по клаузе, без числа, которое
устаревает; и JWK с `d` отклоняется по имени). Сессия 6 (RN-547) связала
пять команд цепочкой и закрепила три правила: упавшее среднее звено ничего не откатывает, становится
именованной строкой в финальном блоке, и скрипт ВСЕГДА завершается с 0 (откат потребовал бы удалить
учётную запись и отозвать ключ, а маршрута для этого нет, и не должно быть такого, который
установщик вызывает сам); идемпотентность — это HTTP-КОД, и `409` — ОЖИДАЕМЫЙ
исход, а не сбой, с `000`, обрабатываемым отдельно, чтобы «api не поднялась» не
читалось как «api отказала»; а пароль передаётся через STDIN `curl`, никогда через
`argv`, потому что `/proc/<pid>/cmdline` читаем любым пользователем машины.
Находка этой сессии: `--help` ЛГАЛ месяцами (*«ESTA VERSÃO NÃO INSTALA
NADA»*), потому что печатает заголовок, являющийся комментарием, а правило, запрещающее
говорить о «сессиях фазы», читало только строки кода. Сессия 7 (RN-548) дала
потребителя метке вида, и решение было о ЧЕСТНОСТИ: с ключом и без
живого подключения — самый частый случай — экран говорит две вещи, которые знает, и называет
две, которых не знает (*зарегистрированный ключ — не работающий агент*, *список — от вашей
УЧЁТНОЙ ЗАПИСИ, а не этого браузера*), тон `accent` и никогда `success`. Сессия 8
(RN-549) — единственная, которая могла доказать всё вместе, и она РАСШИРИЛА workflow, который
ФАЗА 29 уже имела, вместо создания второго. Её центральное решение — СИГНАЛ:
`perguntarEstado` отображает `activating` в `rodando` — обоснованно, — поэтому
`systemctl is-active` и `service status --machine` дали бы зелёный процессу,
который умрёт через две секунды; выбранный сигнал — СТРОКА, которую агент
пишет при входе в ожидание, которая существует только после того, как он прочитал ключ,
взял тикет, поговорил с api и получил ПУСТОЙ список, и которая — ЗАПИСАННЫЙ ФАКТ,
а не выборка состояния. Исход доказывается через API, а не через
браузер, потому что субъект утверждения — АГЕНТ, а то, что он наблюдает, —
`GET /runner/projects`; браузер создал бы проект через тот же маршрут с лишним
слоем, падающим по посторонним причинам, а утверждение по-прежнему было бы
строкой журнала. И E2E остаётся ВНЕ `pull_request`, со следствием,
объявленным, а не скрытым (**PR, который его написал, его не выполнил**): открыть
эту дверь — значит дать установщику способ пропустить проверку происхождения, что
отвергает ADR 0150, — отсюда половина, работающая в PR, — это ТЕСТ
(`scripts/dev/install-e2e.spec.ts`), охраняющий два способа, которыми workflow может
молча сгнить: ослабленный gate и переписанная фраза `install.sh` (из-за которой
утверждения не падают, а ИСЧЕЗАЮТ). Проявились два дефекта, оба
невидимые, потому что workflow никогда не запускался: ответы TTY начинались с
`nao-migrar`, что на чистой машине попадает на вопрос МАРКЕРА и заставляло
скрипт выходить с 0, говоря «Nada foi gravado»; и НАХОДКА, оставшаяся находкой, —
опубликованный `install.sh` **ничего сам не поднимает на чистой машине**, потому что
`docker/docker-compose.install.yml` (вместе с `./postgres/init.sql`) не является
asset-ом Release, не входит в подписанный `checksums.txt`, и он его нигде
не скачивает, так что тот, кто следует `curl … install.sh` из runbook, умирает на «no
such file or directory» ПОСЛЕ того, как уже проверил подпись и записал
`.env`. Исправление — решение между подписанным asset-ом и clone, и это отдельная сдача.
Что фаза оставила ОБЪЯВЛЕННЫМ и не сделанным: отзыв по-прежнему достигает
`{projeto, usuário}` и никогда `{chave}`, и теперь это стоит дороже (роняет агента во
ВСЕХ проектах этой машины); нет экрана, где перечислить и отозвать ключ
устройства, а фаза добавила вид для перечисления, не построив экран, —
пробел стал БОЛЬШЕ, намеренно; один процесс на машину — единая точка
отказа, цена замысла; и `install --machine` по-прежнему не знает, является ли ключ
этой папки действительно ключом машины, потому что на диске оба вида — один и тот же
файл, а знает это сервер

### Golden-set QA снова измеряет и запускается по расписанию, еженедельно (AT-076/AT-149, ADR 0168) {#o-golden-set-do-qa-volta-a-medir-e-roda-agendado-semanal-at-076at-149-adr-0168}

Две сдачи, одно человеческое решение между ними. AT-067 измерила, что
время укладывается в `ubuntu-latest` без GPU и что инструмент не измерял: начиная с
RN-502 `npm test` проекта `container` без контейнера `running`
отклоняется, а seed никогда его не поднимал — 0/6 по построению. Мейнтейнер выбрал
«путь 1», и AT-076 его сдала: seed поднимает контейнер каждого случая
путём PRODUCTION (`module_map` → маршрутизация → `container_start`, предложенный
Infra и одобренный владельцем → `ExecuteContainerStartUseCase` → broker → `running`
через машину состояний), с `node:24.11.1-bookworm-slim`, закреплённым по digest,
нетронутой RN-502 и контейнером, который не поднимается, становящимся ИМЕНОВАННОЙ ошибкой, проваливающей
ExUnit (раньше `{:skip, _}` из тела молча проходил зелёным). Два раунда в CI
дали 3/6 и 3/6 против пола 1/6, с разными случаями, за 52 и 86 min
job-а. AT-149 закрыла периодичность: ЕЖЕНЕДЕЛЬНО (суббота 01:17 UTC, плюс
`workflow_dispatch`, никогда `pull_request`), в `golden-set-qa.yml`, по образцу
`golden-set-rag.yml`. Еженедельно, а не еженощно, потому что раунд стоит до 86 min и
МЕНЯЕТСЯ — тот же итог по разным случаям, — и одного в неделю достаточно, чтобы пол
обнаружил падение. `timeout-minutes: 150` по худшему измеренному случаю. Вердикт —
вердикт самого теста; workflow добавляет лишь две защиты ИНСТРУМЕНТА (строка
счёта должна существовать, а в event log не может быть отказа RN-502) и, при
сбое, печатает логи, как у RAG, — без issue. Образ для pull до seed
ЧИТАЕТСЯ из константы seed, никогда из второго литерала, потому что `docker run`
broker-а работает под управляющим пределом 30 s (RN-604). Раунд доказательства, с
временным триггером `push`, удалённым до PR, был 36327281774: снова 3/6,
ноль отказов RN-502, 10 min `mix golden_set.qa` и 13 min 41 s
job-а. Объявлено: у broker-а CI нет пяти слоёв compose, heartbeat
закрывает сессии seed, пока QA ещё в них работает (без видимого
эффекта), а PR, затрагивающий workflow, его не выполняет.

### Infra Lead разговаривает через composer (AT-141, ADR 0175, RN-617) {#o-infra-lead-conversa-pelo-composer-at-141-adr-0175-rn-617}

RN-584 (AT-098) убрала получателя по умолчанию из чата и оставила продуктовый вопрос
письменно: разговаривает ли Infra Lead? Мейнтейнер ответил да
2026-09-27, с условием, которое поставила сама RN-584, — сначала ход.
Ход Infra Lead выполнялся ЦЕЛИКОМ внутри `handle_call`/`handle_cast`: без

(RN-605). Kickoff, будучи `cast`, не держал клик, но держал процесс —
8,4 min измерено в AT-089, — и сообщение в это время ждало бы в очереди.

gate, пришедшее при идущем ходе, получило очередь, потому что `TurnoAssincrono`

(ушёл отказ `agente_sem_conversa`), `via_for` для «Parar» и место в
`AGENTES_DE_CHAT`; принятие его handoff осталось в собственной карточке RN-499, а
карточка нити исключает его по имени. `SOLO_CONVERSATIONAL_AGENTS` не изменился: Infra
Lead — lead области. Объявлено: он не получил ни структурированных вопросов, ни
чтения backlog.

### Аутентифицированный git выполняется на хосте runner-а, код — в контейнере (AT-116, ADR 0193, RN-676) {#o-git-credenciado-roda-no-host-do-runner-o-código-no-container-at-116-adr-0193-rn-676}

2026-10-01, раунд 36. RN-558 закрыла половину МОЛЧАНИЯ — аутентифицированный `git
fetch` в режиме `runner`, при запущенном контейнере, перестал выполняться с
пустыми переменными и стал отклоняться с меткой
`credencial-nao-atravessa-o-container`, — и объявила другую половину незакрытым
ADR, потому что каждый известный вариант затрагивал порт сдерживания ADR 0130.
Решение владельца (01.10) выбрало тот, что не затрагивает: git-операция с учётными данными
на ХОСТЕ, код в контейнере. Измерено заранее: единственный `exec` engine с `env`
был fetch из `RunnerGit.fetch!/3`; не было ни `push`, ни аутентифицированного `clone`
через `exec` (clone при создании папки уже выполнялся на хосте, RN-532); и папка —
одна и та же с обеих сторон (`estado.dir`, смонтированная в `/work`). Выбранный
дискриминатор — явная МЕТКА engine (`gitCredenciado: true`, ставится только
через `RunnerRouter.exec_git_credenciado/5`), а не уже существовавший `env` —
с `env` в роли ключа любая команда с `env` ускользнула бы из контейнера. Отказ
RN-558 выжил в уменьшенном виде, для `env` без метки, и на практике
стал означать «runner старше ADR 0193». Доказательство — AT-111, с обеих
сторон: в runner-е настоящие `git credential fill` и `git fetch origin` с
helper-ом `GitAuth` проходят на хосте при активном контейнере; в engine цепочка
через настоящий `TerminalChannel` заканчивается `{:ok, _}`. ExUnit не запускались в
среде сдачи (`repo.hex.pm` 403) и остались для CI.

### Консультативная сессия без агента просит агента (AT-254, RN-682) {#a-consultiva-sem-agente-pede-um-agente-at-254-rn-682}

2026-10-01, раунд 36. В реальном использовании 29.09 консультативная сессия без агента
ответила «у меня нет доступа к предыдущим разговорам»: сообщение без
получателя шло в SSE `POST .../chat`, который отправляет привязанной модели только
текущий текст — без истории, без системного промпта — и записывает ответ с
именем модели в качестве актора. Решение владельца (01.10) — просить агента, а не
давать историю свободному чату. Измерено заранее: экран был единственным клиентом
маршрута (`curl`, печатаемый seed-ом, — подсказка для разработки, в креативной
сессии), а у варианта использования `SendChatMessageUseCase` был второй
законный потребитель, smoke-тесты provider-ов, которые используют его как сквозной инструмент
в сессии без агента. Поэтому отказ api живёт в МАРШРУТЕ, в собственной
защите, а вариант использования остался нетронутым. На экране строка получателя стала
нести собственный селектор ручного handoff, когда агента нет, — тот же
привычный жест, теперь в том месте, где он — единственный способ дать сообщению
назначение, — а Criativo остался вне списка, потому что консультативная сессия обещает, что он
не войдёт.

### Отзыв нацелен на ключ, а не на пару `{projeto, usuário}` (AT-013, ADR 0201, RN-685) {#a-revogação-mira-a-chave-e-não-o-par-projeto-usuário-at-013-adr-0201-rn-685}

2026-10-01, раунд 36. RN-520 заставила отзыв достигать живого
подключения, с целью `{projeto, usuário}`, потому что идентичность учётных данных умирала
в `PatAuthGuard`; ADR 0154 поставил *«отзыв по ключу»* в список того, чего он не
делал, а PR #534 дал ключу машины ту же пару, применяемую проект за
проектом. AT-013 была заблокирована по объёму и по решению, пока владелец не
выбрал (01.10): по КЛЮЧУ, с ADR, затрагивая engine. Измерено заранее:
тикет рождался из `{userId, kind}`, сокет хранил только проект/пользователь/kind,
а канал сравнивал пользователя — runner того же пользователя с PAT или другим
ключом падал вместе с ним; подключение ключа машины в проекте вне списка
api оставалось запущенным; тикет, выпущенный до отзыва, входил после него; а
отзыв PAT ничего не ронял. Сдано: два nullable-столбца в тикете
(миграция Ecto, таблица принадлежит engine, — журнал Drizzle остался на `0068`),
guard, аннотирующий учётные данные после авторизации, id сокета, получающий
вид и id учётных данных, и маршрут `runner/disconnect-credential`, который аннулирует
ожидающие тикеты и спрашивает каждый runner кластера, родился ли он из них.
Запрет AT-013 (не перестать ронять то, что падало) стал двумя переходными
