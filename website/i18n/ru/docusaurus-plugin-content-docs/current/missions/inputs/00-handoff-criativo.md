# Вход 0 — входной текст сессии 0 (Criativo)

Операционный материал Фазы 10b. В этом файле — **дословный текст** для вставки
в чат первой сессии и prompts уточнения для следующей сессии.

## Почему Criativo, а не PO {#por-que-o-criativo-e-não-o-po}

Исходный план предписывал прямой handoff к PO с входными материалами. Это
невозможно, и причина важна, потому что она также объясняет формат текста ниже.

Единственный путь к PO — кнопка "Estou pronto para produzir", которая появляется только
при активном Criativo, — не существует ручного handoff к агенту по выбору. И
даже если бы он существовал, одного PO было бы недостаточно: story доходит до `ready` только
при **хотя бы одном привязанном бизнес-правиле**, каждый `business_rule_id`
проверяется по реальному событию `artifact.business_rule`, а у PO **нет
инструмента**, выдающего этот артефакт, — он есть только у Criativo.

Без бизнес-правила в журнале ни одна story не становится `ready`; без story `ready`
ни один dev не берёт task. Поэтому текст ниже так настаивает на правилах: **именно они
разблокируют всё выполнение**, а не украшают документацию.

Деталь механики: в продукте нет ни загрузки, ни вложений. Единственный способ
доставить содержимое входных материалов агенту — **вставить текст** в поле
сообщения.

## Текст для вставки {#o-texto-para-colar}

Вставьте это в первое сообщение сессии 0. Он длинный намеренно — у Criativo
нет доступа к репозиторию, поэтому контекст должен прийти вместе с ним.

---

> Определим объём поставки платформы. Продукт — **Brabo**, и
> на этот раз клиент — сама команда: мы добавим в систему два **git-
> providers**.
>
> **Что уже существует.** У Brabo единый контракт git provider с десятью
> операциями (`createRepo`, `getRepo`, `createBranch`, `protectBranch`,
> `commitFiles`, `listBranches`, `openPullRequest`, `mergePullRequest`,
> `getFileContent`, `commentOnPullRequest`), двумя capabilities, объявляемыми каждым
> provider (`protectBranch` и `pullRequests`), семью классами нормализованных ошибок
> и единой контрактной suite из 19 сценариев, которая одинаково работает против любой
> реализации. Сегодня существуют три providers: Local, GitHub и GitLab.
>
> **Чего не хватает.** Двух новых providers:
>
> 1. **Bitbucket Cloud** — полноценная платформа, как GitHub и GitLab. Задача —
>    перевести её API в контракт: аутентификация, идентичность
>    репозитория, ограничение ветки, стратегии merge и карта ошибок по
>    статусу. Ничего из этого не должно угадываться: каждая семантика должна быть сверена
>    с официальной документацией, прежде чем стать кодом.
> 2. **Generic** — любой git-сервер без API платформы (Gitea,
>    bare repo за SSH, Forgejo). Здесь задача обратная: **честно**
>    объявить, что сделать нельзя, и гарантировать, что система деградирует,
>    а не ломается. Provider Local — уже прецедент этого.
>
> **Что мне нужно от вас в этой сессии.** Выдайте **бизнес-правило** для
> каждого утверждения ниже, которое должно действовать в продукте. Они — контракт, на который
> будет ссылаться весь backlog, поэтому предпочитайте несколько конкретных правил одному
> общему:
>
> - объявленная capability должна совпадать с поведением: неподдерживаемая
>   операция отклоняется явно и никогда не падает молча;
> - новый provider проходит существующую контрактную suite без написания собственного
>   сценария;
> - семантика платформы, не проверенная по официальной документации, не становится
>   кодом — она становится объявленным ограничением;
> - ошибка вендора переводится в нормализованную таксономию по статусу и
>   маркеру, никогда по свободному тексту сообщения;
> - bootstrap Gitflow деградирует (а не падает), когда provider не поддерживает
>   capability;
> - интерфейс должен позволять пользователю выбрать новые providers, иначе они
>   существуют, а никто до них не доходит.
>
> Добавьте те, которых, по-вашему, не хватает, — вы знаете продукт.
>
> **Одно обязательное нефункциональное требование:** по крайней мере у одной части этого объёма
> есть требование **производительности (performance)**. Контрактная suite работает против пяти
> providers в каждом PR, и её время — критический путь CI. Зафиксируйте это
> именно этим словом, "performance", явно.
>
> **Гранулярность.** Когда это станет backlog, работа будет нарезана на
> **много модулей с небольшим числом задач в каждом**, а не на несколько модулей с длинной
> очередью. Помните об этом, разделяя темы.
>
> **Что НЕ решать сейчас.** Не выбирайте endpoint, формат payload или
> стратегию аутентификации Bitbucket. Это архитектурное решение, принимаемое
> позже, по официальной документации. Здесь мы определяем **что** и **почему**,
> а не **как**.

## Прежде чем нажать "Estou pronto para produzir" {#antes-de-clicar-em-estou-pronto-para-produzir}

Проверьте в ленте сессии, что бизнес-правила были **выданы**, а не только
упомянуты в разговоре. Они появляются как артефакты.

Если продвинуться без них, PO сгенерирует весь backlog, и все stories останутся в
`draft`. Вы узнаете об этом только в сессиях выполнения, когда ни один dev не сможет
взять task, и тогда будут потрачены две сессии на возврат к началу.

Ожидаемое количество: **одно правило на каждое утверждение списка** плюс те, что
добавит Criativo. Меньше — продолжайте разговор.

## Prompts уточнения для сессии 1 (PO) {#prompts-de-refino-para-a-sessão-1-po}

PO генерирует весь backlog сам, как только handoff принят, — не ждёт
инструкции. Эти prompts — для **последующего**, глядя на то, что он произвёл во вкладке
Backlog.

**Если в backlog мало модулей и много задач:**

> Переработайте backlog, чтобы было больше модулей с меньшим числом задач в каждом. Выполнение
> обрабатывает одну задачу на модуль за раз, поэтому длинная очередь внутри одного
> модуля ничего не ускоряет — а разделение тем на разные модули ускоряет.

**Если ни у одной story нет НФТ производительности:**

> Ни у одной истории нет нефункционального требования производительности. Добавьте его
> явно, используя слово "performance", в историю, которая касается контрактной
> suite, — её время является критическим путём CI.

**Если какая-то story осталась без привязанного правила:**

> История "X" не ссылается ни на одно бизнес-правило. Привяжите правила, из которых она
> возникла, — без этого она не станет готовой к выполнению.

**Для проверки покрытия:**

> Перечислите, какие бизнес-правила ещё не покрыты ни одной историей.

- Сколько сообщений пришлось обменять с Criativo, пока не появились правила.
- Выдал ли он правил слишком много, слишком мало или вне объёма.
