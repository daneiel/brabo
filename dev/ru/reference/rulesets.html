    Rulesets репозитория

    Эта страница — версионируемый источник защиты. Применение её в GitHub — ручной шаг: репозиторий не может защитить сам себя, и эта асимметрия намеренная — ослабляющий защиту должен быть человеком, с записью.

    Политика, которую применяют эти правила, описана в Política de branches.

    Текущее состояние: gh api repos/daneiel/brabo/rulesets возвращает 0. Ничего ещё не применено. До тех пор всё здесь — объявленное намерение, а не реальная защита.

    Предусловие: все три ветки должны существовать

    У лестницы три ступени, и ruleset не нацеливается на то, чего нет.

    git fetch origin
git push origin origin/dev:refs/heads/qa

    dev и main уже существуют. qa рождается от dev — лестница начинается пустой и заполняется продвижениями.

    Ветка rc была удалена из лестницы. Если она ещё существует в remote старого клона, удалите её: git push origin --delete rc. Постоянная ветка, которой нет в лестнице, — приглашение для PR нацелиться на ступень, которой больше нет.

    Ruleset 1 — три постоянные ветки

    Имя: permanentes Enforcement: Active Цель: Branch → Include by pattern, три записи: dev, qa, main

    Один ruleset на три, а не три ruleset: требование во всех идентично. Между ступенями различается кто одобряет, и это решает approval-ladder по назначению, а не защита.

    Правила, которые нужно отметить

    правило значение почему
    Restrict deletions ✅ случайно удалить main через интерфейс необратимо
    Block force pushes ✅ force-push в постоянную ветку переписывает уже продвинутое; тег ступени в итоге указывал бы на несуществующий коммит
    Require a pull request before merging ✅ это центральное правило: никакое изменение не входит без PR
    ↳ Required approvals 0 считает approval-ladder, который знает режим и назначение. Нативное число GitHub не отличает dev от main
    ↳ Dismiss stale approvals on push ✅ одобрение старого коммита не считается — одобренное не то, что будет смёржено
    ↳ Require review from Code Owners ✅ CODEOWNERS ставит владельца ревьюером всего
    Require status checks to pass ✅ см. список ниже
    ↳ Require branches to be up to date ❌ заставило бы делать rebase при каждом merge в dev; CI уже запускается на merge-коммите
    Block merge queue — не используется

    Required approvals = 0 — это не ослабление. GitHub умеет только считать; он не знает, что main требует PO + управление, а dev — одного разработчика, и что в режиме solo PR самого владельца проходит без ревью. Поставить здесь 1 сломало бы режим solo: владелец не может одобрить собственный PR через интерфейс, и PR застрял бы навсегда. Настоящее требование живёт в approval-ladder, который является обязательной проверкой, — а обязательную проверку не обойти.

    pull_request_target требует, чтобы workflow был в ветке ПО УМОЛЧАНИЮ. Быть в базовой ветке PR недостаточно.     Откуда GitHub читает каждый workflow — три семейства, три ответа. Это стоило трёх отдельных открытий за эту фазу и нигде не очевидно:

    триггер читает workflow из следствие здесь
    pull_request, push ветки события работает с первого PR
    pull_request_target ветки по умолчанию не запускался: main отстаёт
    workflow_dispatch ветки по умолчанию даже не появляется в списке workflows

    Последние два создают проблему курицы и яйца, когда ветка по умолчанию устарела: workflow, который двигает конвейер, уже должен быть в main, чтобы его можно было запустить. Обходом было вручную запустить скрипт promote при первом продвижении — тот же скрипт, только ручной триггер. После того как main получает workflows, dispatch работает навсегда.

    Обязательная проверка, которая никогда не запускается, блокирует PR навсегда. Поэтому триггер ci.yml покрывает все три постоянные ветки — до FASE 6 он срабатывал только на PR в dev, и требование этих проверок при продвижении dev→qa дало бы вечно ожидающий PR. Триггер push был удалён: при pull_request, покрывающем всё, он лишь дублировал запуски. Добавляя новый job в CI, либо внесите его в этот список, либо оставьте вне его намеренно и пусть кто-то напишет почему.

    А обязательная проверка, которая не ПЕРЕЗАПУСКАЕТСЯ, приклеивается к старому вердикту. Это другая сторона урока выше, и она стоила одному PR ошибочного провала.

    Типы pull_request по умолчанию — opened, reopened и synchronize, — ни один не покрывает смену базы. А смена базы — рутина: GitHub открывает PR против ветки по умолчанию, а автор затем исправляет её на dev. В PR #71 Drift, gerados e build запустился в первые полдюжины секунд, против origin/main...HEAD, и упал на семи файлах, которые уже были отревьюены и смёржены в #70. Перенаправление его не перезапустило; красное осталось.

    только от HEAD нет ci.yml — тестирует коммит, и база не меняет результат (кроме решения о пропуске в job образов с AT-303 — см. «Следствие для критерия edited» выше)
    от БАЗЫ или от ТЕЛА PR да pr-police, approval-ladder, promotion-check, backmerge-gate, docs-check

    В docs-check — и то и другое: drift сравнивает интервал, начинающийся с базы, и читает тело в поисках строки docs-not-needed:. Без edited предохранительный клапан, документированный чуть ниже, был недостижим — запись обоснования в тело ничего не переоценивала, и только фиктивный коммит разблокировал бы PR.

    claude-review намеренно не входит в этот список, и это и есть «пусть кто-то напишет почему»: ревью через LLM субъективно и стоит токенов, поэтому оно информирует PR, не имея права её блокировать. Поскольку проверка не обязательна, job можно пропустить, не оставив PR ожидающим, — и он пропускается в каждом PR, открытом ботом. Action отказывается работать с нечеловеческим актором ("Workflow initiated by non-human actor: <name> (type: Bot)"), так что без этого if проверка падает каждый раз. Это случилось дважды: в PR #64 и #65 цикла v0.3.1 (продвижение, открытые github-actions[bot]) и снова в PR #526 (Dependabot).

Оно перечисляло логин — github-actions[bot], — что верно, пока множество не изменится, и молча неверно в день, когда появляется новый бот; dependabot.yml пришёл в PR #520, и следующий PR Dependabot воспроизвёл провал, урок которого уже был записан. Условие теперь проверяет type автора, повторяя ehAutorBot (scripts/ci/pr-police.ts), с суффиксом [bot] в логине как страховкой — GitHub не допускает [ в логине человека, так что его не подделать.

    Для PR продвижения есть вторая, независимая причина: это был бы тот же diff, отревьюенный повторно, поскольку продвижение несёт только коммиты, уже отревьюенные в PR в dev. А для Dependabot есть третья, которая закрывает дверь сама по себе, — его PR запускаются с хранилищем секретов Dependabot, отдельным от хранилища Actions, так что CLAUDE_CODE_OAUTH_TOKEN приходит пустым. Даже если разрешить актора, у ревью не было бы учётных данных, а проверка, падающая из-за отсутствия секрета, хуже пропущенной: она читается как дефект кода.

    Чего не может выполнить PR между постоянными ветками

    Drift, gerados e build является обязательной, поэтому запускается в каждом PR — но шаг drift объявляет себя неприменимым, когда head — постоянная ветка самого репозитория (продвижение dev→qa, qa→main; back-merge main→qa, qa→dev). Остальные шаги job — docmap, сгенерированное и сборка сайта — продолжают выполняться: они зависят только от HEAD и действуют на любой ступени.

    Причина та же, что и у claude-review, с отягчающим обстоятельством. Избыточность, во-первых: PR между постоянными ветками не имеет авторства, он упаковывает коммиты, drift которых уже был взыскан в PR в dev, файл за файлом. Взыскивать снова — значит взыскивать тот же долг на каждой ступени. Но, в отличие от ревью через LLM, здесь требование было невыполнимым — и именно это провалило #72, продвижение цикла v1.0.1, из-за файлов docker/**, пришедших из #70:

    кажущийся выход почему его нет
    обновить документацию в PR продвижения promotion-check требует чистого интервала — head должен быть верхушкой источника. Коммит там проваливает другую обязательную проверку
    повторить docs-not-needed: из исходного PR тело PR продвижения генерируется promote; обоснование из #70 не пересекает ступень
    ставить метку на каждое продвижение это учит пользоваться предохранительным клапаном рефлекторно, пока он ничего не будет значить, — противоположность тому, чего просит .docmap.yml

    Фильтр живёт внутри шага, а не в if: на job, следуя тому же принципу, который записывает promotion-check: обязательная проверка, индексированная по sha, которая не запускается, оставляет PR ожидающим навсегда. Шаг запускается, решает, что не применим, и пишет это в сводку — вместо того чтобы исчезнуть.

    Head с именем main из форка — не продвижение. Это рабочая ветка третьего лица, и она проходит drift, как любая другая. Поэтому условие сопоставляет имя и требует того же репозитория — та же оговорка, которую pr-police применяет при классификации семейства PR.

    Bypass

    кто режим зачем
    актор BRABO_BOT_TOKEN Always писать .release/gate.json в main

    Ни у одного человека нет bypass — даже у владельца. Этот принадлежит боту и существует по причине без обхода: gate блокирует ветки, и PR для снятия блокировки был бы заблокирован самим gate. Коммит остаётся в git log, с датой и содержимым, и tag-release распознаёт его по тому, что он затрагивает (.release/ и ничего больше), а не по тому, кем он себя называет.

    Предупреждение об охвате bypass. Rulesets GitHub дают bypass актору, а не пути: тот, кто может писать .release/gate.json в main, технически может писать что угодно. Ограничить по пути в интерфейсе нельзя. Реально ограничивает workflow — он пишет только этот файл — и история, где любой другой прямой коммит сразу бросается в глаза. Записано как есть: ограничение инструмента, а не решение.

    Секрет BRABO_BOT_TOKEN

    Классический PAT со scopes repo + workflow, в Settings → Secrets and variables → Actions:

    gh secret set BRABO_BOT_TOKEN --body '<token>'

    Это не удобство. От него зависят две вещи, и обе молча ломаются без него:

    что почему
    тег запускает Release тег, созданный с GITHUB_TOKEN, не запускает workflow
    PR back-merge рождаются с проверками PR, открытый с GITHUB_TOKEN, не запускает workflow

    Это правило GitHub против рекурсии, и оно уже взяло свою цену: Release v0.2.0 так и не была опубликована из-за него. Второй случай хуже — PR back-merge без проверки никогда не стал бы зелёным, и цепочка застряла бы навсегда. Поэтому job gate громко падает, когда секрета нет, а не идёт дальше, оставляя репозиторий в тупике.

    Scope workflow — не излишество: PR back-merge несут ветку целиком, и она может содержать изменение в .github/workflows/**. Без этого scope push отклоняется ровно в том случае, который важнее всего, — при распространении исправления CI.

    Текущее состояние: настроено и испытано. В v1.1.1 конвейер впервые замкнулся сам — tag-release пропустил шаг предупреждения, отправил тег с PAT, и это запустило release.yml, который опубликовал Release. Тег, отправленный с GITHUB_TOKEN, его бы не запустил; этот запуск — доказательство того, что токен действителен и имеет scope на push.

    Повторная публикация осиротевшего тега

    У release.yml есть workflow_dispatch с входом тега, и он существует из-за шести тегов выше. Один лишь триггер push: tags сделал бы провал необратимым: повторная публикация потребовала бы удалить и пересоздать тег, то есть переписать запись, чтобы исправить её следствие.

    gh workflow run release.yml -f tag=v1.1.0

    Три защиты, и каждая существует из-за конкретного режима отказа:

    защита против чего
    запустить его может только OWNER_HANDLE (режим solo) то же ограничение, что и у promote; триггер push здесь не проходит, потому что там авторизовал тег
    вход должен совпадать с ^v[0-9]+\.[0-9]+\.[0-9]+$ workflow_dispatch принимает свободный текст. Без этого -qa.1 опубликовал бы Release того, что никто не подтвердил как финальное
    отказ, если Release уже существует опубликованная заметка — это запись; молча перезаписать её значило бы стереть то, что кто-то уже прочитал или на что сослался

    И checkout делается на теге, а не на ref события. При dispatch github.ref_name — ветка по умолчанию; без этой предосторожности повторная публикация породила бы Release с именем main, с changelog main, без какой-либо ошибки.

    Dispatch работает только после того, как это дойдёт до main. Это проблема курицы и яйца из таблицы триггеров выше: workflow_dispatch читает workflow из ветки по умолчанию. Пока изменение только в dev, вход даже не появляется.

    Ruleset 2 — теги версий

    Имя: tags-de-release Enforcement: Active Цель: Tag → Include by pattern → v*

    правило значение
    Restrict creations ✅
    Restrict updates ✅
    Restrict deletions ✅

    Шаблон v* покрывает три формы, которые создаёт конвейер: -dev.N, -qa.N и финальную. Создавать их может только tag-release.

    Что запускает финальный тег и почему ничто из этого не обязательная проверка. Отправка vX.Y.Z параллельно запускает release.yml, build-runner-binaries.yml и publish-runner.yml. Их jobs никогда не появляются в таблице обязательных проверок выше, и это структурно, а не упущение: обязательные проверки удерживают pull request, а когда тег существует, PR уже смёржен. Тег удерживает ruleset — создаёт его только tag-release, и только после конвейера, в конце которого он запускается.

    Финальный тег также запускает install-e2e.yml, который испытывает опубликованный install.sh на чистой машине — а эфемерный runner Actions именно ею и является. С RN-549 он доходит до конца: пять звеньев, замыкающих установку, локальный агент поднят и ждёт, и первый проект runner подхвачен. Он не запускается в pull_request, и причина та же, что держит подпись вне PR: подписанный манифест существует только после финального тега, а запуск скрипта там дал бы ему дверь для пропуска проверки (RN-534). Следствие сказано, а не скрыто — PR, который меняет этот workflow, его не запускает, — а в каждом PR запускается scripts/dev/install-e2e.spec.ts, который проваливается, если триггер получит pull_request или если фраза, которую workflow ищет grep, перестанет существовать в install.sh.

    С ADR 0149 у build-runner-binaries.yml два job вместо одного: матрица build (четыре цели, fail-fast: false) и job checksums. С RN-565 у второго нет needs: на матрицу — он ждёт, с потолком, assets Release, а не самый медленный job, — поэтому цель, упавшая при сборке или так и не получившая runner, не лишает остальные подписанного манифеста. Он называет в логе, какие цели манифест не покрывает, потому что checksums.txt, перечисляющий три и молчащий о четвёртой, хуже никакого: тот, кто проверяет три, заключает, что проверил релиз.

    Цель darwin-x64 (Mac Intel) вышла из матрицы в ADR 0174, и причина измерена (AT-065, 2026-09-13): её метка macos-13 указывала на образ, который GitHub вывел из эксплуатации в декабре 2025 года, а замена на Intel, macos-15-intel, планируется за секунды и собирает, но проваливает --self-test-pty под Bun (onData из node-pty никогда не срабатывает — oven-sh/bun#25822, открыт). То же доказательство проходит под Node, поэтому Mac Intel устанавливает runner через npm install -g @brabo/runner. Запуск workflow с пустым входом tag — это репетиция: собирает и делает smoke, ничего не прикрепляя, и именно так это было измерено без создания тега.

    кто режим
    app/бот, запускающий workflow релиза Always

    Это исключение для push, предусмотренное политикой: версия рождается из workflow, никогда вручную. Тег, созданный вручную, не проходит проверку того, что финальный тег указывает на тот же коммит, что и последний -qa.N, а именно эта проверка не даёт опубликовать что-то отличное от проверенного.

    Как применить

    Интерфейс: Settings → Rules → Rulesets → New ruleset.

    Через API, если предпочитаете версионировать команду:

    gh api -X POST repos/daneiel/brabo/rulesets --input ruleset-permanentes.json
gh api repos/daneiel/brabo/rulesets --jq '.[] | "\(.name): \(.enforcement)"'

    TODO(humano): два файла .json с payload здесь не версионируются, потому что API rulesets требует repository_id и id приложений, различающиеся от установки к установке, — фиксированный файл скопировали бы неправильно. Если хотите их версионировать, сгенерируйте через gh api repos/daneiel/brabo/rulesets/<id> > docs/reference/... после применения через интерфейс, и этот документ начнёт указывать на них.

    Settings → Pages: источник — ветка gh-pages

    Применение ручное, по той же причине, что и у rulesets: репозиторий версионирует источник, GitHub получает применение.

    Settings → Pages → Build and deployment → Source: Deploy from a branch, с веткой gh-pages и папкой / (root).

    Уже применено. gh api repos/daneiel/brabo/pages возвращает "build_type": "legacy" с source.branch: "gh-pages", и все три ступени отвечают в сети.

    Промежуточный шаг стоит записи, потому что сбивает с толку: пока build_type был "workflow", docs-deploy.yml коммитил в gh-pages, и Pages ничего оттуда не отдавал — публикация оставалась в репозитории, не выходя в сеть, а старый сайт всё ещё отвечал из последнего артефакта actions/deploy-pages. Ничто в CI не краснеет в этом состоянии.

    Почему переключение обязательно, а не предпочтение: actions/deploy-pages публикует один артефакт как весь сайт и не умеет обновлять часть дерева, что несовместимо с подкаталогом на ступень. Полный дизайн, отброшенные альтернативы и исключение для push, которое это открывает, описаны в ADR 0034.

    ветка URL индексируется
    — (индекс трёх) https://daneiel.github.io/brabo/ ❌ noindex, follow
    main https://daneiel.github.io/brabo/prd/ ✅
    qa https://daneiel.github.io/brabo/qa/ ❌ noIndex
    dev https://daneiel.github.io/brabo/dev/ ❌ noIndex

    Все три стали симметричными в ADR 0071, который также объясняет сгенерированный корень и 404.html, перенаправляющий старые ссылки на стабильную ступень. ADR 0073 отделил ПУТЬ от ВЕТКИ: main публикуется в /prd/, потому что адрес называет среду для читающего. 404.html стал переписывать /brabo/main/<algo> в /brabo/prd/<algo> — старый каталог уходит из дерева, и keep_files: false его удаляет.

    Конфигурация Pages не меняется ни с одним из двух — источником остаётся ветка gh-pages в папке / (root); изменилось содержимое, которое workflow собирает перед push. И prd не ветка: её нет ни в одном ruleset, её нет в git, это лишь имя каталога в gh-pages.

    gh-pages НЕ входит в ruleset постоянных веток. Она не постоянная, и боту нужно пушить в неё — её включение заблокировало бы саму публикацию. Поэтому там же хватает GITHUB_TOKEN, без bypass и без BRABO_BOT_TOKEN.

    И она вне охвата Gitleaks, по причине, которая проявилась лишь позже. gitleaks detect сканирует каждый достижимый коммит, а не только историю HEAD, — а fetch-depth: 0 приносит все refs. Как только появилась gh-pages, собранный сайт попал в сканирование: 112 находок generic-api-key в одном коммите, все в dev/assets/js/*.js, — это имена файлов аватаров внутри минифицированного bundle со слишком высокой для правила энтропией. Это провалило PR продвижения #78, первый просканированный после её появления.

    ci.yml теперь удаляет refs/remotes/origin/gh-pages перед сканированием. Не через allowlist путей в .gitleaks.toml: он действовал бы для каждого коммита, и dev/, появившийся однажды в исходном коде, молча перестал бы сканироваться. Исключение ref исключает ровно те коммиты, которые не являются исходным кодом.

    Измерено gitleaks 8.30.1, версией CI: 133 коммита и 112 находок до, 132 и ни одной после — а PAT GitHub с реальной энтропией, подложенный в apps/api/src/, по-прежнему обнаруживается, что доказывает, что дыра не открылась.

    Метки семейств должны существовать

    pr-police применяет одну из четырёх меток, и gh pr edit --add-label падает, если метки нет, — что оставило бы PR без классификации, молча.

    gh label create trabalho        --color 0E8A16 --description "Work PR: taxonomy prefix for dev"
gh label create promocao        --color 1D76DB --description "Promotion between adjacent rungs, going up"
gh label create retropropagacao --color 5319E7 --description "Back-propagation between adjacent rungs, going down"
gh label create correcao-alta   --color D93F0B --description "hotfix: a fix that's born high on the ladder"

    Без || true намеренно: если команда упадёт, вам нужно это увидеть.

    Проверить, что всё на месте

    # do the rulesets exist and are they active?
gh api repos/daneiel/brabo/rulesets --jq '.[] | "\(.name): \(.enforcement)"'

# does the protection respond? (should be REJECTED)
git push origin HEAD:dev

    Вторая команда — тот тест, который важен. Ruleset, настроенный, но не проверенный, неотличим от отсутствующего — и разница проявляется только в тот день, когда кто-то пушит прямо в main.
