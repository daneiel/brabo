    Открытая поверхность api

    Каждый зарегистрированный маршрут — с классификацией аутентификации и обоснованием тех, что остаются открытыми. Решения — в ADR 0027.

    Этот документ — источник истины для теста, а не копия теста. apps/api/test/interfaces/route-surface.spec.ts поднимает приложение, перечисляет маршруты, зарегистрированные в runtime, и сравнивает их с таблицей ниже. Новый маршрут без строки здесь проваливает тест; строка, классификация которой расходится с реальной аннотацией, проваливает тест; осиротевшая строка (не совпадающая ни с одним маршрутом) проваливает тест. Документация не устаревает молча.

    Классификации

    значение что означает
    public @Public() — без токена. Каждый такой маршрут обоснован ниже
    engine-service EngineServiceGuard: X-Brabo-Service-Token, равный общему секрету. Это внутренняя поверхность api↔engine, вне JWT
    role:<role> аутентифицирован и ограничен RBAC домена (@RequireRole)
    jwt аутентифицирован, без требуемой в маршруте роли — область видимости задаётся самим ресурсом

    Пятнадцать публичных маршрутов

    До Фазы 6 их было четыре. Фаза 7a добавила сразу восемь — first-party auth, — ADR 0084 ещё два, вход через соцсети, а волна ключа устройства runner добавила прокси бинарника. Каждый обоснован ниже. Чтобы открыть ещё какой-либо, по-прежнему нужно менять утверждение в route-surface.spec.ts, которое перечисляет публичные маршруты буквально, чтобы вынудить обсуждение.

    Инфраструктура

    GET /live — liveness. Намеренно не обращается к базе: отвечает, пока процесс жив. Требование токена здесь заставило бы kubelet перезапускать pod при первом сбое на пути auth, превращая деградацию в полный отказ.

    GET /health — readiness, с select 1. То же рассуждение: вызывает kubelet, а он токена не несёт. Раскрывает только то, отвечает ли база.

    GET /metrics — scrape Prometheus, который тоже не несёт никакого токена. Доступ контролируется СЕТЬЮ, а не auth: NetworkPolicy открывает его только для namespace monitoring, а Ingress production блокирует путь. Без @Public() цель была бы down при всём остальном зелёном.

    GET /git/oauth/:provider/callback — возврат OAuth от GitHub/GitLab. Браузер пользователя приходит сюда от провайдера, без сессии api. Но маршрут не безусловный: параметр state проверяется HMAC (GIT_OAUTH_STATE_SECRET), и без валидного state вызов отклоняется.

    Эта гарантия стоит ровно столько, сколько стоит ключ, и поэтому у него больше нет значения по умолчанию: в production api отказывается стартовать с примерным ключом из репозитория, который публичен (ADR 0059, RN-093). С известным ключом этот маршрут на практике снова становится безусловным — любой может подписать state для любого проекта.

    GET /runner-releases/binary — проксирует standalone-бинарник runner из GitHub Releases, чтобы браузер никогда не общался с GitHub напрямую. Публичен по той же причине, что и /metrics/JWKS: сам бинарник не секрет, а требовать сессию для скачивания того самого инструмента, который позволяет аутентифицироваться, было бы шиворот-навыворот. platform — закрытый список разрешённых значений (linux-x64/linux-arm64/darwin-arm64 — три цели, которые собирает матрица релиза; darwin-x64 ушёл в ADR 0174, а win32-x64 — в ADR 0187, и оба отклоняются с собственным сообщением, указывающим на npm-пакет), никогда не подставляется сырым в URL GitHub — это закрывает вектор SSRF/инъекции пути, который оставил бы открытый параметр. Разрешённый URL asset (никогда не байты бинарника) кэшируется в памяти на несколько минут — только чтобы оставаться ниже rate limit GitHub для неаутентифицированных запросов при конкурентных скачиваниях; начиная с сессии 3 ФАЗЫ 29 разобранный checksums.txt — несколько сотен байт текста — мемоизируется в той же записи, поэтому хэш и бинарник всегда берутся из одного и того же релиза.

    Начиная с RN-525 (ADR 0149) маршрут больше не передаёт непроверенные байты: он сверяет sha256 скачанного с checksums.txt релиза и отвечает 502 с именованным motivo, когда это не удаётся, — в том числе когда релиз вообще не публикует манифест, что является отказом, а не байтами, отданными с предупреждением. Понимать гарантию следует узко: это целостность относительно манифеста, а не происхождение. Маршрут не проверяет подпись cosign манифеста (checksums.txt.bundle), так что тот, кто может переписать Release, переписывает оба файла и проходит. Оба способа закрыть это были измерены и пока отклонены — cosign в образе занимает 155 MB, а @sigstore/verify сделал бы маршрут @Public() зависимым от второго стороннего хоста (tuf-repo-cdn.sigstore.dev) для проверки того, чего пока не несёт ни один Release. Потребитель, который проверяет подпись, — это install.sh. Поскольку проверка хэша означает чтение всех байтов, загрузка идёт во временный файл под /tmp (emptyDir pod, смонтированный, потому что rootfs только для чтения) с потолком 256 MiB и отдаётся только после совпадения хэша — никогда не буферизуется в процессе на 512Mi.

    First-party auth

    Семь маршрутов /auth/* плюс JWKS. Все они должны быть публичными по одной и той же структурной причине: это путь, по которому access token ПОЛУЧАЮТ, а глобальный JwtAuthGuard его требует. Маршрут auth за guard запрашивал бы учётные данные, которые сам же выдаёт. logout — единственный, который мог бы быть аутентифицированным, и он намеренно таким не является: он уже несёт значимые учётные данные — refresh в cookie, с парой CSRF, — а выход должен работать даже с истёкшим access token.

    Эти маршруты защищает не rate limit. RateLimitGuard освобождает маршруты @Public() — намеренно, чтобы не душить /health до перезапуска pod kubelet. Эту поверхность удерживает прогрессивная блокировка по email и по IP внутри сценариев использования. Это не необязательное усиление: это единственная защита, которая здесь есть. См. RN-030 и RN-031.

    POST /auth/register — регистрация. Отвечает 202 как для нового адреса, так и для уже зарегистрированного; во втором случае ничего не создаётся, а владелец адреса получает уведомление. 409 Conflict, которого требовал бы здравый смысл REST, выдал бы список пользователей любому со словарём.

    POST /auth/login — аутентификация. Несуществующий email, неверный пароль и заблокированная учётная запись возвращают один и тот же ответ 401 и занимают одно и то же время (ветка без учётной записи сверяет с фиктивным хэшем с идентичными параметрами).

    POST /auth/refresh — ротация. Сам refresh token является учётными данными, поэтому маршрут не может требовать других.

    POST /auth/logout — отзывает семейство предъявленного токена. Всегда 204, даже для неизвестного токена: ответ 401 здесь был бы оракулом валидности токена.

    POST /auth/verify-email, POST /auth/request-password-reset, POST /auth/reset-password — потоки учётной записи. У того, кто приходит сюда, по определению ещё нет сессии. Учётные данные — одноразовый токен, пришедший по email; недействительная, истёкшая или уже использованная ссылка получают идентичный ответ.

    GET /.well-known/jwks.json — публичная половина пары Ed25519, которой подписываются access tokens. То же рассуждение, что и для /metrics: у потребителя нет токена, и требовать его означало бы запрашивать учётные данные для проверки учётных данных. Публикация открытого ключа — весь смысл формата; то, что никогда не может отсюда выйти, — компонент d JWK, зафиксированный тестом.

    Вход через соцсети (ADR 0084)

    GET /auth/oauth/:provider/start — перенаправляет прямо к провайдеру (GitHub/GitLab). Публичен по той же структурной причине, что и остальные семь: это сама точка входа, до появления сессии. state, который он генерирует, подписывается HMAC с СОБСТВЕННЫМ назначением (signSocialOauthState/RN-273) — никогда не тот же state, что у GET /git/oauth/:provider/callback выше, хотя оба маршрута подписывают ОДНИМ И ТЕМ ЖЕ ключом GIT_OAUTH_STATE_SECRET. Поле purpose в payload — то, что не даёт state одного потока быть принятым верификатором другого.

    GET /auth/oauth/:provider/callback — принимает возврат от провайдера. То же рассуждение, что и для callback подключения git: браузер приходит без сессии, state проверяется HMAC, а маршрут никогда не возвращает JSON — он всегда перенаправляет: на WEB_ORIGIN/ при успехе (с уже записанными cookies сессии) и на WEB_ORIGIN/login?oauth_error=1 при неудаче, не раскрывая причину в URL.

    Примечания

    • POST /workspaces/:workspaceId/projects решает, где агент будет писать, и именно поэтому это маршрут поверхности безопасности, а не только регистрации (ADR 0072/ ADR 0104, RN-169/RN-421/ RN-422). Тело получило executionMode (container — по умолчанию и привычное поведение, —, mounted, бывший local, переименованный, или runner) и workspacePath. В mounted/ runner указанный абсолютный путь становится корнем области видимости терминала из ADR 0055: то, что здесь вводится, — то, что агент может читать и писать. Ни одного нового маршрута и никакой смены роли (RequireRole('maintainer'), как и было) — изменилось то, насколько широко то, что маршрут предоставляет.

      Начиная с ADR 0142 (RN-501) ОБА режима, отличные от container, при создании проверяют ОДНО И ТО ЖЕ: только ЛЕКСИЧЕСКУЮ форму — абсолютный, без .., никогда не корень и не системная папка, никогда не пересекающийся с checkout Brabo ни в одном из направлений (RN-422/RN-423) — без какого-либо дискового I/O. mounted добавляет собственное правило: путь должен находиться внутри BRABO_PROJECTS_BASE, единственной папки машины, которую видят оба контейнера (ADR 0141), а без настроенной базы отказ сообщает, что РЕЖИМ недоступен в этой установке, вместо того чтобы винить путь.

      С точки зрения безопасности в этом изменении важно то, что НЕ сдвинулось. Указанный путь по-прежнему является корнем области видимости терминала, а лексический предикат по-прежнему его ограничивает — он выполняется при каждом выводе корня, в том числе при ЧТЕНИЯХ, потому что запись напрямую в базу — единственный способ обойти создание. Отложена была проверка ДИСКА (существует? это каталог? может ли этот процесс в него писать?), которая никогда ничего не ограничивала: она отвечала «это будет работать», а не «это разрешено». Теперь она выполняется в materializarWorkspaceMontado, когда Infra поднимает контейнер (и, как объявленное исключение, при конвертации режима), и правило базы применяется там повторно ДО mkdir -p — так что путь, записанный в обход продукта, не заставляет api создавать папку в любом месте, куда она дотягивается. Правило базы намеренно находится ВНЕ лексического предиката: тот выполняется при каждом чтении, и УНАСЛЕДОВАННЫЙ проект mounted вне базы начал бы падать только из-за того, что его прочитали. runner по-прежнему подтверждается самим runner, единственной стороной, имеющей власть над реальным хостом (RN-423, см. POST /internal/projects/:projectId/workspace-verification ниже); mounted теперь подтверждается материализацией, которая точно так же проставляет workspace_verified_at. После этого режим заморожен: UpdateProjectDto намеренно опускает оба поля, иначе PartialType(CreateProjectDto) открыл бы их в PATCH без какой-либо защиты.

Классификация называет МЕХАНИЗМ (BRABO_SERVICE_TOKEN в собственном заголовке, сравниваемый за постоянное время), а не отправителя, и секрет намеренно тот же: три сервиса работают в одном кластере и читают один и тот же Secret, так что второй секрет создавал бы впечатление разграничения, ничего не разграничивая (полное обоснование — в service-token.ts). Ценность маршрута — в направлении вызова: broker не ПОЛУЧАЕТ спецификацию контейнера, он приходит сюда ПРОЧИТАТЬ идентичность проекта, режим исполнения и действующее решение Arquiteto об образе и составляет спецификацию сам. Спецификация, путешествующая в теле запроса, поставила бы ограничение процесса, эквивалентного root, в зависимость от правоты вызывающего. Он не возвращает ни одного абсолютного пути — источник bind разрешается демоном относительно файловой системы ХОСТА, так что путь изнутри контейнера api молча смонтировал бы пустую папку. Вместо этого передаётся localizacao (RN-503, ADR 0144): локатор с дискриминатором, говорящий, какой из ДВУХ корней broker разрешает папку (gerenciada → PROJECT_WORKSPACES_HOST_ROOT, montada → BRABO_PROJECTS_HOST_BASE или indisponivel с причиной), плюс ОТНОСИТЕЛЬНЫЙ сегмент, который этот корень не покрывает. Api никогда не узнаёт, где эти корни находятся на хосте, а broker никогда ничего не узнаёт о проекте — ни одна из сторон в одиночку не может записать произвольный путь, и в этом ограничение. Broker отклоняет start, называя отсутствующий корень, никогда не переходя на другой, и повторно проверяет сегмент (.., абсолютный, пустой, NUL — всё отклоняется) плюс конкатенированный результат, прежде чем тот станет -v. Он также отбрасывает rationale, который существует для того, чтобы человек проверял решение, и не имеет потребителя в docker run.

PatAuthGuard работает вместо JwtAuthGuard на этом маршруте (@RequirePatAuth(), тот же структурный шаблон, что @ServiceRoute()/EngineServiceGuard, — обход по метаданным, никогда не if, который новый маршрут может забыть), и это ЕДИНСТВЕННОЕ место api, принимающее любой из этих форматов учётных данных: на любом другом маршруте brb_... обычным образом проваливает проверку JWT, как и JWT ключа устройства (его kid никогда не разрешается среди ключей собственного эмитента токенов сессии).     • GET /runner/projects классифицирован jwt и НЕ принимает никакого JWT сессии (RN-543, ADR 0154). Это маршрут, по которому агент МАШИНЫ узнаёт проекты, которые обслуживает, и это первый маршрут @RequirePatAuth() без :projectId в пути — что ровно то, ради чего он существует: вызывающий ещё не знает, какие проекты существуют. Два следствия, оба зафиксированы тестом:

      • Принимаются только учётные данные МАШИНЫ (runner_device_keys.project_id NULL). Учётные данные, привязанные к проекту, — PAT или ключ устройства из потока ADR 0118, — описывают проект и им нечего обнаруживать; PatAuthGuard отклоняет их с 403 и СОБСТВЕННЫМ сообщением, никогда не сообщением «не тот проект», которое солгало бы о причине. Сравнение, отклоняющее ключ-от-A-в-B, НЕ было удалено: оно исчезает только для null, и оба направления зафиксированы.
      • @RequireRole нет, потому что нет проекта, относительно которого разрешать роль. Минимум developer — ТОТ ЖЕ, что у runner-ticket, — применяется ПОСТРОЧНО внутри ListRunnerProjectsUseCase, единым правилом продукта (ResolveEffectiveRoleUseCase.forProject). Ничто не ослаблено: на выходе ровно тот набор проектов, для которых runner-ticket уже авторизовал бы этого пользователя. Автоматический классификатор читает @RequireRole и не видит механизма, поэтому попадает в jwt — то же приближение, которое этот документ уже поправляет прозой для runner-ticket выше. Маршрут никогда не касается JWT сессии: JwtAuthGuard воздерживается на маршрутах @RequirePatAuth(), а открытый ключ, который проверяет PatAuthGuard, берётся из runner_device_keys, никогда не от эмитента сессий.

      Он возвращает id проекта, имя, workspaceDirName и состояние проверки — никогда абсолютный путь. По проводу передаётся СЕГМЕНТ, а корень принадлежит тому, кто исполняет, — тот же инвариант, что у broker (ADR 0144) и у базы runner (ADR 0151).

      Начиная с RN-544 у маршрута есть ПОТРЕБИТЕЛЬ: запущенный без --project, brabo-runner вызывает его в начале и открывает одно подключение на каждый перечисленный проект — а начиная с RN-550, когда этот список приходит пустым, он продолжает вызывать с объявленной периодичностью (15s, 30s, затем 60s с повтором), пока не появится первый проект. У этого ожидания есть потолок со стороны сбоя, а не со стороны ожидания: десять вызовов подряд с ошибкой — и процесс выходит с 1, называя счётчик; любой ответ (в том числе пустой) обнуляет счётчик, а в момент, когда есть живое подключение, ожидание прекращается — при живом подключении список по-прежнему читается только в начале, по причине ниже. Каждое подключение имеет корень в <base>/<workspaceDirName> через те же защиты (resolverPastaDoProjetoNaBase, затем RN-434/RN-435). Три вещи об этом принадлежат этой странице. Во-первых, в engine ничего не изменилось: топик terminal:<projectId>, id сокета и ticket описывают ПОДКЛЮЧЕНИЕ, и N подключений удовлетворяют им байт в байт — отказ второму runner в том же проекте не затронут, как и зеркало (RN-516) и workspace_create (RN-532), которые уже передавались в разрешении join ТОГО подключения. Во-вторых, JWT обнаружения не несёт claim projectId — защита сравнивает payload.projectId !== request.params.projectId, и на маршруте без проекта в пути оба должны быть undefined; подпись там выдуманного id проекта была бы отклонена с 403, говорящим не то. В-третьих, runner никогда не угадывает вид собственного ключа: на диске ключ машины и ключ проекта — один и тот же файл (приватный JWK с kid), знает сервер, и именованный 403 передаётся с собственным сообщением и собственным исправлением (--project), а не сплющивается в общую ошибку подключения. Новый режим требует ОБОИХ — учётных данных машины и согласованной базы: без базы неоткуда вывести папку каждого проекта, а выдумать её означало бы записать на диск пользователя путь, на который он никогда не соглашался; без обоих запуск без --project по-прежнему печатает справку об использовании.

Ticket одноразовый, а встроенное автопереподключение повторяет ТЕ ЖЕ params — так что сокет, созданный без reconnectAfterMs, вечно повторяет мёртвый ticket. Это не гипотеза: apps/runner/src/channel.ts вышел таким, пока его собственный docblock утверждал обратное, и это было измерено в реальном использовании — один и тот же ticket отклонялся каждые ~5,13s (потолок внутреннего backoff библиотеки), 61 REFUSED CONNECTION TO EngineWeb.RunnerSocket за несколько часов и, в сумме с СОБСТВЕННОЙ политикой повторов runner, 530 запросов за минуту при потолке 300 req/min RATE_LIMIT_USER. Лимит — на пользователя, так что отказ в обслуживании пришёлся на БРАУЗЕР владельца учётной записи, в виде 429, — неаутентифицированная третья сторона не участвует, но плохо построенного клиента достаточно, чтобы запереть собственного пользователя снаружи. Переподключение — всегда собственная политика вызывающего, с новым ticket при каждой попытке; опция теперь ОБЯЗАТЕЛЬНА в типе (OpcoesDoSocket) и проверяется тестом на опцию, переданную в конструктор, поскольку тест, проверявший только «подключается», всё время проходил.

До ADR 0203 (RN-687) был третий, POST, через который браузер регистрировал только что сгенерированный открытый ключ Ed25519 (ADR 0118). Этот поток был выведен из эксплуатации, и маршрут ушёл вместе с ним, потому что другого вызывающего у него не было: ключи теперь рождаются на машине — brabo-runner device-key create (RN-551) генерирует пару и записывает приватную половину на диск, режим 600, в $XDG_CONFIG_HOME/brabo/ (иначе ~/.config/brabo/), — и регистрируются установщиком через внутренний маршрут ниже. Приватная половина по-прежнему никогда не пересекает провод; пересекают только открытый JWK и id записи. Чего у этого CLI намеренно нет — так это учётных данных для регистрации: регистрация остаётся за тем, кто владеет service token (установщик, ADR 0155 пункт 1), так что каждая сторона владеет ровно одним секретом и ни одна не видит секрет другой. Файл, который читает runner, никогда не существует без своего kid: create записывает имя .parcial, которое читатель игнорирует, а finish --id <id> проставляет и переименовывает. Ключи проекта, зарегистрированные браузером ДО ADR 0203, продолжают действовать: PatAuthGuard всё ещё их принимает, GET перечисляет, а DELETE отзывает. GET перечисляет ключи самого вызывающего, включая отозванные (RN-519), — это то, что делает отзыв достижимым, и до его появления осиротевший ключ (вкладка, закрытая посреди потока автоматической настройки) был невидим и вечен. Он никогда не возвращает открытый JWK: список существует для отзыва, а lastUsedAt: null — признак осиротевшего ключа. DELETE отзывает ключ самого вызывающего, идемпотентно, в том же формате, что и самостоятельный отзыв PAT. PatAuthGuard — это то, что ПОТОМ принимает JWT, подписанный приватной половиной этого ключа, в runner-ticket, отыскиваемый по заголовку kid, равному id этой таблицы; защита проверяет, что ключ не отозван, но никогда не срок действия — сам ключ не истекает, истекает только JWT с коротким TTL (≤60s, exp - iat), который runner каждый раз им подписывает. Начиная с RN-543 GET возвращает ДВА вида и ГОВОРИТ, какой есть какой (especie): ключ МАШИНЫ (projectId: null) обслуживает каждый проект своего владельца, поэтому появляется в листинге каждого проекта — без этого он был бы невидим и вечен на каждом экране, тот же дефект, который закрыла RN-519, возродившийся в новом виде. Маршрут, создающий ключи МАШИНЫ, — это POST /internal/machine-device-keys, ниже (RN-552) — другой маршрут, другие учётные данные и другой вызывающий. МАТЕРИАЛ ключа, который он регистрирует, производится на машине: brabo-runner device-key create (RN-551) генерирует пару Ed25519 локально и печатает только открытый JWK, так что приватная половина никогда не путешествует. Начиная с RN-547 install.sh сцепляет оба в конце установки и устанавливает unit машины с полученным ключом (ADR 0155) — именно это делает реальной, а не гипотетической, объявленную цену этого маршрута. Отзыв ключа МАШИНЫ просит engine сбросить живой runner в КАЖДОМ проекте в режиме runner, до которого дотягивается владелец, — один вызов {project, user} на проект, не затрагивая engine.

Они намеренно узкие — только ключи МАШИНЫ (ключ проекта отвечает 404, так же как несуществующий или чужой ключ, так что ничего не утекает) и только ключи ВЫЗЫВАЮЩЕГО (userId берётся из JWT сессии и входит в WHERE; ни один параметр не называет другого пользователя, а представление maintainer остаётся за рамками, как решила RN-519). DELETE — тот же отзыв, что у маршрута по проекту, делегированный тому же сценарию использования: он сбрасывает живые подключения, открытые С этим ключом, в каждом проекте (начиная с RN-685 целью является ключ, а не {project, user}); пока проекта нет, он только регистрирует отзыв — это всё, что можно остановить: ожидающий агент машины (RN-550) не имеет подключения, а его следующий ticket отклоняется.

    • Отзыв ключа устройства теперь достигает ЖИВОГО подключения, и цель — {project, user}, никогда {key} (RN-520, ADR 0147 пункт 6). DELETE блокировал только СЛЕДУЮЩИЙ ticket: уже подключённый brabo-runner держал канал terminal:<projectId> живым, выполняя одобренные команды с отозванным ключом, пока не отваливался сам. Теперь api просит engine (POST /internal/projects/:projectId/runner/disconnect) его сбросить, и engine дотягивается до pid канала — api никогда не говорит с каналом, а engine никогда не читает таблицу ключей. Точности, которой НЕТ, — по учётным данным, и это свойство пути ticket, а не предпочтение: runner_socket_tickets хранит project_id/user_id/kind и ничего больше, так что какой PAT или какой kid открыл тот сокет, умирает в PatAuthGuard и никогда не доходит до engine. Объявленная цена: runner ТОГО ЖЕ пользователя, подключённый с PAT или с другим ключом того же проекта, тоже падает — и переподключается сам, потому что следующий раунд запрашивает новый ticket, а всё ещё действительные учётные данные его получают. Runner другого пользователя в том же проекте остаётся работать. Сброс подключения — ПОБОЧНЫЙ ЭФФЕКТ: недоступный engine, отсутствие подключённого runner или timeout никогда не могут заставить DELETE (204, идемпотентный) упасть или стать 5xx — то же правило, что у rag_searches (RN-479) и mirror_sync_result (RN-517). Пересмотрено RN-685 (ADR 0201): целью теперь является КЛЮЧ. Ticket записывает, какие учётные данные его запросили (kid или id PAT), и отзыв просит engine (POST /internal/runner/disconnect-credential) аннулировать ожидающие tickets этих учётных данных и сбросить только runners, рождённые от них, — объявленная выше цена исчезла: runner того же пользователя с PAT или другим ключом остаётся работать. Отзыв PAT (собственного или в роли maintainer) теперь тоже сбрасывает его подключения. Подключение, открытое с ticket, предшествующим deploy (без учётных данных), по-прежнему падает по паре, а engine, не знающий маршрута, заставляет api вернуться к runner/disconnect; маршрут пары также остаётся целью удаления участника. Представление maintainer, которое есть у PAT (RN-427, перечислить/отозвать ЛЮБОГО пользователя), остаётся ЗА РАМКАМИ для ключей устройства — теперь по решению, а не по упущению: та пара родилась из реагирования на инцидент с циркулирующим ОБЩИМ секретом, а приватная половина ключа устройства никогда не покидает машину, которая её создала. Эта фраза говорила «браузер, который её создал», и RN-551 расширила изготовителя, не ослабив утверждения: терминал теперь второй генератор, а приватная половина по-прежнему никогда не путешествует — выходит открытый JWK. ИЗМЕНИЛОСЬ то, где она лежит: ключ, созданный в браузере, оседает в папке проекта, выбранной пользователем, ключ, созданный CLI, оседает в $XDG_CONFIG_HOME/brabo/ с режимом 600. Ни один из них не достижим для api, и от этого зависит решение выше.

Он engine-service, так что открывает его BRABO_SERVICE_TOKEN — который сам install.sh сгенерировал и записал с режимом 600, делая его доказательством контроля над МАШИНОЙ, а не над почтовым ящиком.       Учётная запись рождается с уже подтверждённым e-mail, и это единственное, что этот маршрут ослабляет, — для одного именованного случая, никогда для другого пути. Пароль вводится в TTY, читается без эха, хэшируется argon2id и отбрасывается: никогда в .env, никогда в маркере, никогда в логе и никогда не генерируется каким-либо кодом.

Закрытие потребовало бы advisory lock на отсутствие строк, а ограничение живёт не там — тот, кто дотягивается до этого маршрута, уже владеет service token, то есть уже контролирует установку.

Требование их здесь вынудило бы установщик создать на машине ровно ту живую сессию, которую тот ADR отказался создавать.

В теле нет userId: владелец — ЕДИНСТВЕННЫЙ пользователь установки, разрешаемый api, так что токен никогда не покупает выбор, какие учётные данные чеканить, — при нуле пользователей или более чем одном он отклоняет с 409 и ничего не записывает, та же форма условия, что у первой учётной записи (об установке, никогда об аргументе), и навсегда замолкает, как только у установки появляется команда. Регистрация ЗАМЕЩАЕТ: активные ключи машины владельца отзываются в той же транзакции, так что переустановленная машина — легитимный случай, а тысяча ключей машины невозможна — потолок по условию, а не по числу, которое стареет. Приватный JWK отклоняется по имени: присутствие d отвечает 400 с указанием, что пришло, по тому же доменному правилу, которое использует регистрация браузера, потому что хранение приватной половины — худший исход, который есть у этого маршрута.

Два пробела объявлены, а не спрятаны: здесь нет ни GET, ни DELETE (перечисление опубликовало бы инвентарь учётных данных человека тому, кто владеет только секретом машины; отзыв уже существует там, где есть владелец-человек), а в установке, где ещё нет ни одного проекта, ни один экран не дотягивается до ключа машины — именно поэтому регистрация замещает, а не оставляет сирот позади.

Сравнение оказалось в одном месте: autoMovimentoDoProprioPapel возвращает НАПРАВЛЕНИЕ вместо булева значения (вызывающему оно нужно, чтобы выбрать сообщение), а ehAutoRebaixamento сохраняется как его прочтение, чтобы ворота УДАЛЕНИЯ продолжали видеть только нижнюю половину, как решил ADR 0156.

По-прежнему engine-service: поле — момент, когда завершился ход разговорного агента, считанный из того же event log, который уже пишет engine, и оно лишь решает, как долго engine держит сессию открытой. Отказ происходит до какого-либо эффекта. Сообщение выбирается по handoffs проекта, прочитанным во ВСЕХ его сессиях, — поэтому оно может сказать «примите handoff к Arquiteto/Dev Lead». Оно раскрывает лишь то, что этот handoff существует, и его статус, которые любой viewer проекта уже читает через GET .../sessions/:sessionId/handoffs; оно никогда не называет ни сессию, ни пользователя.

    • Предложение handoff агенту, уже активному в проекте, — 409 agente_ja_ativo, а классификация не изменилась — человеческий маршрут POST .../sessions/:sessionId/handoffs остаётся role:developer, а внутренний — engine-service (RN-635, ADR 0182). В отличие от отказа выше, этот НАЗЫВАЕТ сессию: сообщение говорит, в какой сессии того же проекта получатель активен, потому что это текст, который агент читает как результат инструмента, и указатель, который нужен человеку, чтобы пойти с ним поговорить. Любой viewer проекта уже перечисляет его сессии и читает agent.activated в каждой, так что ничто не пересекает границу проекта. Те же маршруты теперь отвечают ТЕКУЩИМ предложением вместо всегда новой строки (desfecho), а внутренний принимает seAusente — ключ, который может заставить вызов только писать МЕНЬШЕ.

    • Внутренний POST /internal/sessions/:sessionId/handoffs теперь может ПРИНЯТЬ создаваемое им предложение Criativo→PO, а классификация не изменилась — по-прежнему engine-service (RN-658, ADR 0185). Engine не получает права активировать агента: решает api, на основании readiness.confirmed, записанного ЧЕЛОВЕКОМ через POST .../readiness (role:developer, тот же минимум, что и для принятия через карточку), и она записывает этого человека как актора. Engine не может подделать отметку — он никогда не пишет readiness.confirmed, — а предложение должно нести product_brief, рождённый после того клика, в той же сессии. POST .../agents/criativo/validate-necessity сохраняет маршрут и роль, без вызывающего в web (RN-657).

Возвращает ТЕКУЩУЮ сессию исполнения проекта — active с записанным execution.activated — или null; никогда самую свежую сессию проекта, которую читала вкладка Executores и которая молча меняла сессию в тот момент, когда после неё рождалась другая.

Поле — список id агентов с agent.activated в самой свежей сессии проекта (RN-630), вычисленный в том же проходе по сессиям, который уже даёт executionActivated и gatesEverOpened (RN-568). Никакие новые данные не читаются, никакие новые учётные данные не раскрываются — это то же имя, что уже фигурирует в token_usage.

    • PUT /projects/:projectId/agent-autonomy начал принимать actionType: "*" — «автоматический режим» (RN-153) — а классификация не изменилась: по-прежнему role:maintainer, как и соседний GET. Разница в том, что тело теперь РАЗРЕШАЕТ, а не в том, кто может вызвать: подстановочный знак предоставляет автономию для ЛЮБОГО типа действия агента сразу, а не по одному типу, как раньше. Разрешение (КОНКРЕТНОЕ правило всегда побеждает подстановочный знак) целиком живёт в репозитории (DrizzleAgentAutonomyRepository.findMode), никогда в decide() — которая по-прежнему получает только уже разрешённую PermissionPolicy, ровно как до появления подстановочного знака. Именно поэтому три абсолютных потолка — merge в защищённую ветку, instruction_patch, parallelize/raise_max_parallel — продолжают блокировать даже при подстановочном знаке в auto_approve (RN-154): они реагируют на current.policy === 'auto_approve', никогда на то, откуда она пришла, и ни одному исключению не пришлось войти в decide(), чтобы это продолжало действовать. ApprovalCard.tsx предлагает кнопку, которая записывает подстановочный знак, только клиенту, который уже знает, что у него maintainer/owner, — но реально роль гарантирует этот же @RequireRole('maintainer'), неизменный.

    • Маршрутизатор инструментов Jev — новый ИСХОДЯЩИЙ вызов, несущий контекст агента (ADR 0179, RN-625). Перед вызовом чата к модели OpenRouter api делает POST на https://openrouter.ai/api/alpha/decisions (Decisions API, альфа) с ключом OpenRouter owner workspace — ТЕМ ЖЕ ключом, который уже тратит чат, расшифрованным в том же сценарии использования, никогда не логируемым и никогда не возвращаемым. Передаётся state: id агента, последнее сообщение пользователя (обрезанное до 6.000 символов), начало системного сообщения (1.500) и до шести недавних вызовов инструментов с аргументами и результатами, обрезанными до 500 символов каждый, — плюс ИМЕНА и ОПИСАНИЯ инструментов, никогда их parameters. Это содержимое, которое вызов чата уже отправляет в ту же учётную запись OpenRouter, в меньшем объёме, но теперь оно доходит до второй модели (typesafe/jev-1.13) за ней. Любой сбой вызова приводит к полному каталогу.
