Superfície exposta da api

Toda rota registrada, com a classificação de autenticação e a justificativa das que ficam abertas. Decisões no ADR 0027.

Este documento é a fonte de verdade de um teste, não a cópia de um. apps/api/test/interfaces/route-surface.spec.ts sobe a aplicação, enumera as rotas registradas em runtime e as compara com a tabela abaixo. Rota nova sem linha aqui reprova o teste; linha cuja classificação difere da anotação real reprova o teste; linha órfã (que não casa com rota nenhuma) reprova o teste. A documentação não fica velha em silêncio.

As quinze rotas públicas​

Eram quatro até a Fase 6. A Fase 7a acrescentou oito de uma vez — auth first-party —, o ADR 0084 mais duas, o login social, e a onda da chave de dispositivo do runner acrescentou o proxy do binário. Cada uma é justificada abaixo. Abrir mais alguma continua exigindo mexer na asserção de route-surface.spec.ts, que lista as públicas literalmente para forçar a conversa.

Infraestrutura​

GET /live — liveness. Não toca o banco de propósito: responde enquanto o processo estiver vivo. Exigir token aqui faria o kubelet reiniciar o pod no primeiro soluço do caminho de auth, transformando uma degradação em queda total.

GET /health — readiness, com select 1. Mesmo raciocínio: quem chama é o kubelet, e ele não leva token. Revela só se o banco responde.

GET /metrics — scrape do Prometheus, que também não leva token nenhum. Exposição controlada pela REDE, não por auth: a NetworkPolicy só a abre para o namespace monitoring, e o Ingress de produção bloqueia o caminho. Sem @Public() o alvo apareceria down com todo o resto verde.

GET /git/oauth/:provider/callback — o retorno do OAuth do GitHub/GitLab. O navegador do usuário chega aqui vindo do provedor, sem sessão da api. Mas não é irrestrita: o parâmetro state é validado por HMAC (GIT_OAUTH_STATE_SECRET), e sem state válido a chamada é recusada.

Essa garantia vale exatamente o que vale a chave, e é por isso que ela deixou de ter default: em produção a api recusa subir com a chave de exemplo do repositório, que é pública (ADR 0059, RN-093). Com chave conhecida, esta rota volta a ser irrestrita na prática — qualquer um assina um state para o projeto que quiser.

GET /runner-releases/binary — faz proxy do binário standalone do runner a partir das GitHub Releases, para o navegador nunca falar com o GitHub direto. Pública pelo mesmo motivo de /metrics/JWKS: o binário em si não é segredo, e exigir sessão para baixar a própria ferramenta que permite alguém se autenticar seria às avessas. platform é uma lista fechada de permitidos (linux-x64/linux-arm64/darwin-arm64 — os três alvos que a matriz de release constrói; darwin-x64 saiu no ADR 0174 e win32-x64 no ADR 0187, e os dois são recusados com mensagem própria apontando para o pacote npm), nunca interpolada crua na URL do GitHub — fechando o vetor de SSRF/injeção de caminho que um parâmetro aberto deixaria. A URL resolvida do asset (nunca os bytes do binário) fica em cache na memória por alguns minutos, só para ficar abaixo do rate limit não autenticado do GitHub sob downloads concorrentes; desde a sessão 3 da FASE 29 o checksums.txt parseado — umas centenas de bytes de texto — é memoizado na mesma entrada, então hash e binário vêm sempre da mesma release.

Desde a RN-525 (ADR 0149) a rota não transmite mais bytes não verificados: ela confere o sha256 do que baixou contra o checksums.txt da release e responde 502 com motivo nomeado quando não consegue — inclusive quando a release não publica manifesto nenhum, que é recusa, nunca bytes servidos com aviso. Leia a garantia de forma estreita: é integridade contra o manifesto, não procedência. A rota não verifica a assinatura cosign do manifesto (checksums.txt.bundle), então quem consegue reescrever a Release reescreve os dois arquivos e passa. As duas formas de fechar isso foram medidas e recusadas por ora — cosign na imagem são 155 MB, e @sigstore/verify faria uma rota @Public() depender de um segundo host de terceiro (tuf-repo-cdn.sigstore.dev) para conferir algo que nenhuma Release ainda carrega. O consumidor que verifica a assinatura é o install.sh. Como verificar o hash significa ler todos os bytes, o download vai para um arquivo temporário sob /tmp (o emptyDir do pod, montado porque o rootfs é somente leitura) com teto de 256 MiB, e só é devolvido depois de o hash bater — nunca bufferizado no processo de 512Mi.

Auth first-party​

As sete rotas /auth/* mais o JWKS. Todas precisam ser públicas pelo mesmo motivo estrutural: são o caminho pelo qual um access token é OBTIDO, e o JwtAuthGuard global exige um. Uma rota de auth atrás do guard pediria a credencial que ela mesma emite. logout é a única que poderia ser autenticada, e não é, de propósito: ela já carrega a credencial que importa — o refresh no cookie, com o par de CSRF — e sair precisa funcionar mesmo com o access token expirado.

O que protege estas rotas não é o rate limit. O RateLimitGuard isenta as rotas @Public() — de propósito, para não estrangular o /health até o kubelet reiniciar o pod. O que segura esta superfície é o bloqueio progressivo por email e por IP, dentro dos casos de uso. Não é reforço opcional: é a única defesa que existe aqui. Ver RN-030 e RN-031.

POST /auth/register — cadastro. Responde 202 tanto para endereço novo quanto para já cadastrado; no segundo caso nada é criado e o dono do endereço recebe um aviso. Um 409 Conflict, que é o que o bom senso REST pediria, entregaria a lista de usuários a qualquer um com uma wordlist.

POST /auth/login — autenticação. Email inexistente, senha errada e conta bloqueada devolvem todos a mesma resposta 401, e levam o mesmo tempo (o ramo sem conta confere contra um hash fictício com parâmetros idênticos).

POST /auth/refresh — rotação. O próprio refresh token é a credencial, então a rota não pode exigir outra.

POST /auth/logout — revoga a família do token apresentado. Sempre 204, mesmo para token desconhecido: responder 401 aqui seria um oráculo de validade de token.

POST /auth/verify-email, POST /auth/request-password-reset, POST /auth/reset-password — fluxos de conta. Quem chega nelas ainda não tem sessão, por definição. A credencial é o token de uso único que veio por email; link inválido, expirado ou já usado recebem resposta idêntica.

GET /.well-known/jwks.json — a metade pública do par Ed25519 que assina os access tokens. Mesmo raciocínio de /metrics: o consumidor não tem token, e exigir um seria pedir credencial para validar credencial. Publicar a chave pública é todo o propósito do formato — o que nunca pode sair daqui é o componente d da JWK, travado por teste.

Login social (ADR 0084)​

GET /auth/oauth/:provider/start — redireciona direto para o provedor (GitHub/GitLab). Pública pelo mesmo motivo estrutural das outras sete: é o próprio ponto de entrada, antes de existir sessão. O state que ela gera é assinado por HMAC com propósito PRÓPRIO (signSocialOauthState/RN-273) — nunca o mesmo state do GET /git/oauth/:provider/callback acima, embora as duas rotas assinem com a MESMA chave GIT_OAUTH_STATE_SECRET. O campo purpose no payload é o que impede um state de um fluxo de ser aceito pelo verificador do outro.

GET /auth/oauth/:provider/callback — recebe o retorno do provedor. Mesmo raciocínio do callback da conexão de git: o navegador chega sem sessão, o state é verificado por HMAC, e a rota nunca devolve JSON — ela sempre redireciona, para WEB_ORIGIN/ no sucesso (com os cookies de sessão já gravados) e para WEB_ORIGIN/login?oauth_error=1 na falha, sem detalhar o motivo na URL.

Notas​

  • POST /workspaces/:workspaceId/projects decide onde o agente vai escrever, e é por isso que é uma rota de superfície de segurança, não só de cadastro (ADR 0072/ ADR 0104, RN-169/RN-421/ RN-422). O corpo ganhou executionMode (container — o padrão e o comportamento de sempre —, mounted, o antigo local, renomeado, ou runner) e workspacePath. Em mounted/ runner o caminho absoluto informado vira a raiz do escopo do terminal do ADR 0055: o que se digita aqui é o que o agente pode ler e escrever. Nenhuma rota nova, e nenhuma mudança de papel (RequireRole('maintainer'), como já era) — o que mudou é o alcance do que a rota concede.

    Desde o ADR 0142 (RN-501) os DOIS modos que não são container validam a MESMA coisa na criação: só a forma LÉXICA — absoluto, sem .., nunca a raiz nem uma pasta de sistema, nunca sobreposto ao checkout do Brabo em nenhum dos sentidos (RN-422/RN-423) — sem I/O de disco nenhum. mounted acrescenta uma regra própria: o caminho tem de estar dentro de BRABO_PROJECTS_BASE, a única pasta da máquina que os dois containers enxergam (ADR 0141), e sem base configurada a recusa diz que o MODO não está disponível nesta instalação em vez de culpar o caminho.

    A parte relevante para a segurança dessa mudança é o que NÃO se moveu. O caminho informado continua sendo a raiz do escopo do terminal, e o predicado léxico continua sendo o que o contém — ele roda em toda derivação da raiz, nas LEITURAS também, porque escrever direto no banco é a única forma de contornar a criação. O que foi adiado é a checagem de DISCO (existe? é diretório? este processo consegue escrever nele?), que nunca conteve nada: ela respondia "isto vai funcionar", não "isto é permitido". Ela roda agora em materializarWorkspaceMontado, quando a Infra sobe o container (e, como exceção declarada, na conversão de modo), e a regra da base é reaplicada ali ANTES do mkdir -p — então um caminho escrito fora do produto não faz a api criar pasta em qualquer lugar que ela alcance.

    A regra da base fica FORA do predicado léxico de propósito: aquele roda em toda leitura, e um projeto mounted LEGADO fora da base passaria a falhar só por ser lido. runner continua sendo confirmado pelo próprio runner, a única parte com autoridade sobre o host real (RN-423, ver POST /internal/projects/:projectId/workspace-verification abaixo); mounted passa a ser confirmado pela materialização, que carimba workspace_verified_at do mesmo jeito. O modo fica congelado depois: UpdateProjectDto omite os dois campos de propósito, senão PartialType(CreateProjectDto) os exporia num PATCH sem guarda nenhuma.

  • GET /workspaces/:workspaceId/containers agora lista TODO projeto do workspace, e a página que ele alimenta virou o caminho humano para SUBIR um container (RN-521, ADR 0136). O papel não mudou (viewer, como já era) e o escopo também não: ela continua respondendo só pelos projetos do workspace que o chamador enxerga. O que mudou foi o conjunto de linhas — um projeto que nunca provisionou container ficava AUSENTE e agora aparece com registrado: null, um TERCEIRO estado que não é stopped nem "não foi possível observar". A leitura continua limitada do mesmo jeito: três consultas em lote qualquer que seja o número de projetos, e no máximo TETO_DE_VERIFICACOES_POR_CARGA (20) chamadas ao broker por carga, com as linhas sem container nunca elegíveis e portanto nunca capazes de tirar a vez de uma real.

    Nada nesta página age diretamente. Parar, remover e subir são todos proposed_action, sempre com um HUMANO clicando, nunca um agente, e nenhum teto de decide.ts é tocado: os dois tipos de subida exigem maintainer, e container_remove fica no teto absoluto da família de comando privilegiado (RN-418) — nunca auto-aprovável, "sempre permitir" recusado na fonte. container_recreate (remove + sobe de novo, RN-934) entra no mesmo teto. A rede declarada (PUT .../container/network, maintainer, RN-932) só grava artefato — nada muda no Docker até a recriação aprovada. A tela ramifica a ação de subida por execution_mode exatamente como o backend (RN-497/RN-503): container/mounted propõem container_start (broker) e runner propõe container_start_via_runner (agente local), com o payload que o schema de cada um de fato aceita.

    As recusas da própria tela são honestidade, não imposição: ela não oferece o botão sem imagem decidida (o portão da RN-105, válido nos TRÊS modos desde a RN-494), nem para um projeto runner cuja pasta nenhum agente local jamais confirmou, nem para papel abaixo de maintainer — e diz qual dos três é, em texto. Quem recusa de verdade continua sendo o RolesGuard e os casos de uso. O papel lido aqui é o de WORKSPACE, não o papel efetivo do projeto (projectRole ?? workspaceRole, RN-471): um membro rebaixado dentro de um projeto ainda vê o botão e recebe 403, um custo declarado de não pagar um N+1 de project_members numa página que atravessa projetos.

  • PUT /projects/:projectId/mirror-path grava um caminho na máquina do USUÁRIO, e a api nunca vê essa máquina (RN-515, ADR 0147, ponto 4). Ela guarda o destino para onde a capacidade espelho copia o trabalho do projeto — uma pasta FORA da base montada, que é justamente por que um bind mount não a alcança e um agente local precisa alcançar.

    O mínimo é maintainer, o mesmo de execution-mode e projects-base acima, e pelo mesmo motivo: esta rota trata de um caminho no próprio sistema de arquivos do operador, não de metadado de projeto.

    O que a api consegue validar aqui é SÓ a forma LÉXICA, e a mensagem de recusa diz isso. Ela reusa caminhoDeWorkspaceLocalValido — absoluto, sem ../., nunca a raiz, nunca uma pasta de sistema, nunca sobreposto ao checkout do próprio Brabo — exatamente como a criação em runner faz (RN-423), e pelo mesmo motivo: não há disco aqui a quem perguntar. Ela NÃO exige BRABO_PROJECTS_BASE, porque estar fora da base é o objetivo.

    Duas recusas são próprias desta rota. O destino não pode estar dentro de workspacePath nem contê-lo — o mesmo laço visto dos dois lados, já que gravar o espelho dentro da própria origem faz o espelho copiar a si mesmo — e a comparação é por SEGMENTO (dentroDoEscopo), então /base-outra não está dentro de /base. E um projeto em execution_mode: container não pode ter destino nenhum: a origem dele é um volume gerenciado NO SERVIDOR, e o processo que copiaria roda na máquina do USUÁRIO, que não o enxerga. As duas são 400.

    A outra metade da guarda — resolver symlinks com realpath, para que um link em qualquer segmento do destino não aponte de volta para dentro da origem — é do RUNNER, na máquina onde os dois caminhos de fato existem. Esta rota não estabelece essa garantia; ela só descarta o laço ESCRITO. Limpar é mirrorPath: null, e a chave é obrigatória: omiti-la seria indistinguível de pedir para limpar, e limpar em silêncio é o defeito. Gravar o espelho nunca é proposed_action — é configuração que o usuário declarou, não um agente pedindo para agir.

  • GET /projects/:projectId/mirror-state é viewer, um degrau abaixo da rota que GRAVA o destino (RN-517, ADR 0147, ponto 7). Ela devolve o que a última rodada do espelho fez: qual dos três estados vale agora (never | synced | failed), a última sincronização bem-sucedida com as contagens dela, o destino congelado daquela rodada e o último erro.

    A assimetria com PUT .../mirror-path (maintainer) é deliberada e é a regra da RN-102 aplicada: o mínimo é do ENDPOINT, e este só LÊ. O próprio destino já vai em toda leitura do projeto (GET /projects/:projectId, viewer), então exigir maintainer aqui trancaria uma informação de quem já a vê no mesmo projeto — o pior dos dois defeitos, porque é invisível para quem perdeu a capacidade.

    Vale dizer o que ela NÃO expõe: nenhum nome de arquivo, nenhum conteúdo, nenhum caminho além do destino que o chamador já pode ler. As contagens são contagens.

  • GET /workspaces/:workspaceId/projects-base revela um pedaço da topologia do sistema de arquivos do operador, e é por isso que não é viewer (ADR 0141, RN-500). Ela devolve { projectsBase: string | null } — a única pasta do host montada por identidade nos containers api e engine, sob a qual vive todo projeto mounted. null é o estado normal de uma instalação que não oferece o modo Montado, e é assim que o assistente de projeto aprende a não oferecer um modo que esta instalação não consegue honrar.

    O mínimo é maintainer: o mesmo de POST /workspaces/:workspaceId/projects acima, porque decidir o que aquela rota oferece é a única serventia deste valor. Herdar viewer das leituras vizinhas projects-* — elas ficam lado a lado no mesmo controller — entregaria um caminho absoluto do host a todo mundo que consegue olhar o workspace, sem capacidade nenhuma em troca. workspaceId não entra no cálculo: a base é configuração da instalação, idêntica para todo workspace, e o parâmetro está lá só para dar um escopo ao RolesGuard.

    Desde o ADR 0161 (RN-573) a resposta também leva brokerConfigurado: boolean — se BROKER_URL está definido, lido por ContainerBrokerPort.configurado(). Ela revela um bit da topologia da instalação (existe ou não um broker com o socket do Docker), nunca o endereço dele, e o mínimo continua maintainer. O mesmo bit vai em toda linha de GET /workspaces/:workspaceId/containers (viewer, RN-574), um alargamento deliberado: aquela página precisa dizer ANTES do clique que container/mounted não sobem aqui, e quem consegue ver a página já podia inferir a ausência por naoObservado: broker-nao-configurado sempre que uma linha está provisioning/running. Ela diz que a variável existe, nunca que o broker responde.

  • GET /workspaces/:workspaceId/project-folders serve listagens de diretório a partir de um caminho informado pelo cliente, e toda a segurança dela é UMA contenção (RN-504, ADR 0141). Ela existe porque o assistente de projeto perdeu de uma vez os seus dois mecanismos de "procurar uma pasta": FolderBrowserModal navegava pelo websocket do RUNNER, e RunnerOnboardingPanel usava showDirectoryPicker, que devolve um handle do navegador e nunca um caminho absoluto. Com o runner saindo da criação de projeto, o navegador não tem como listar um sistema de arquivos — então a api lista, e a api só enxerga uma pasta: a base de projetos montados.

    A contenção é essa base e nada mais. path é opcional e o padrão é BRABO_PROJECTS_BASE; todo path informado tem de satisfazer dentroDaBaseDeProjetos — o mesmo dentroDoEscopo que o escopo do terminal do ADR 0055 usa, então /home/you/brabo2 NÃO está dentro de /home/you/brabo mesmo com a string começando igual. Sair da base é 400, não 403: 403 sugeriria que algum outro papel a veria, e nenhum vê. O pedido está malformado, não sub-autorizado. .. e . são recusados de saída em vez de resolvidos, pelo mesmo motivo que o predicado da criação os recusa — resolver é aceitar que o caminho lido não é o caminho pedido.

    Os tetos fazem parte do contrato, não são detalhe de implementação: só diretórios, no máximo 500 (ordenados ANTES do corte), nunca recursivo, entradas com prefixo de ponto excluídas, e symlinks informados mas nunca percorridos — então um link apontando para fora da base não é uma saída dela. O que é excluído é CONTADO (arquivos, simbolicos, truncado), então uma pasta cheia de código nunca volta parecendo vazia (RN-180). Não há POST companheiro: criar pasta é da materialização do workspace montado, nunca do seletor.

    O mínimo é maintainer, o mesmo de POST /workspaces/:workspaceId/projects e projects-base acima, e pelo mesmo motivo levado um passo adiante: projects-base revela UM caminho na máquina do operador, esta rota revela a TOPOLOGIA abaixo dele. Quem não pode criar projeto não tem nada a fazer com a lista de pastas onde um projeto poderia ser criado.

  • GET / é o "Hello World!" do scaffold do NestJS (src/app.controller.ts). Está atrás da guarda e não vaza nada, mas não serve para nada — candidata a remoção. Ficou registrada aqui em vez de removida, porque isso é decisão de produto, fora do escopo desta sessão.

  • GET /internal/projects/:projectId/git-remote é a única rota do produto que devolve um segredo DECIFRADO — o token de git do owner do workspace (ADR 0056). Ela existe porque o engine trabalha no sistema de arquivos e não tem a chave mestra; replicá-la no engine dobraria o raio de impacto do segredo mais sensível do produto. Duas propriedades a mantêm defensável: o origin que ela devolve é limpo (a credencial vem num campo separado, nunca embutida na URL), e o consumidor é obrigado a injetá-la por invocação, nunca em arquivo — ver Engine.Actions.GitAuth e o raciocínio disso na RN-076. Se esta rota um dia passar a devolver a URL já autenticada, o token acabaria em .git/config, dentro da pasta onde o dev agent tem leituras auto-aprovadas.

    No modo runner essa injeção por invocação viaja um salto a mais — o campo env da mensagem exec (RN-507) — e ela para na fronteira do container: a porta de Docker do produto não tem campo env, de propósito (ADR 0130), então um comando roteado para dentro do container por docker exec nunca consegue levar o token. Essa contenção se manteve; o que não se manteve foi o relato. Até a RN-558 o runner rodava esse comando mesmo assim, com o credential helper instalado e as variáveis vazias, e a falha de autenticação resultante era indistinguível de um token ruim ou de uma rede quebrada — no caminho comum, já que o container running registrado que a RN-507 exige só existe porque esse mesmo runner o subiu. O runner agora recusa o par (credencial presente, container ativo) antes de executar qualquer coisa, e o engine classifica a recusa com origem politica em vez de codigo. O texto da recusa não nomeia as variáveis nem os valores delas, só quantas eram. A credencial continua sem atravessar a fronteira do container, e desde o ADR 0193 (RN-676) ela não precisa: o engine marca o fetch autenticado (gitCredenciado: true, posto de um lugar só, RunnerRouter.exec_git_credenciado/5) e o runner roda ESSE comando no host, onde o env chega ao processo filho; os comandos do dev agent continuam indo para docker exec. A fronteira de confiança é a marca, não o env: um comando levando env SEM a marca continua recusado enquanto há container ativo, então o campo de credencial nunca vira uma saída do container. Nenhuma porta do ADR 0130 mudou.

  • As três rotas de leitura do PO — GET /internal/projects/:projectId/business-rules, GET /internal/projects/:projectId/backlog (RN-164) e GET /internal/projects/:projectId/product-metrics (RN-407) — não devolvem segredo nenhum e não aceitam nada além do id do projeto: nenhum termo de busca, nenhuma paginação, nenhum filtro. É de propósito. Uma rota de leitura para agente é uma superfície que o modelo escolhe chamar, e um parâmetro é onde o modelo escreve o que quiser; aqui não há onde escrever. O escopo é fechado ao projeto pelo caminho, e o custo por chamada é constante (três leituras no backlog, duas nas regras, uma consulta a proposed_actions filtrada por índice nas métricas de produto).

  • A leitura de contratos do dev agent — GET /internal/projects/:projectId/module-contracts (RN-684, ADR 0200) — segue a mesma regra: nenhum segredo, nada além do id do projeto, uma entrada por módulo do module_map vigente. É conteúdo que a chamada de chat já manda para a mesma conta do OpenRouter, numa fatia menor, mas que agora chega a um segundo modelo (typesafe/jev-1.13) por trás dela. A chave é por workspace (PUT /workspaces/:workspaceId/tool-router, role:owner, ligada por padrão) e só dispara com modelo de chat do OpenRouter. O roteador estreita o menu de ferramentas e nada mais: não consegue aprovar, negar nem alargar nada, e uma chamada que o modelo faça fora do menu continua virando Proposed Action sob a mesma política. Qualquer falha da chamada cai no catálogo inteiro.

  • POST .../actions/:actionId/approve_always ganhou desfecho e padraoGravado na resposta, e a classificação não mudou — continua role:developer (RN-642). A aprovação e o padrão gravado agora dividem uma transação; clicar numa ação que já estava APROVADA responde 201 com desfecho: "ja_aprovada" em vez de 409, e uma ação RECUSADA continua respondendo 409 (acao_ja_recusada) sem nada gravado. Os tetos da RN-418 e container_remove continuam recusados com 400 antes de qualquer estado ser lido, então o caminho idempotente nunca grava um padrão que o teto proíbe.

  • Um erro de git ganhou resposta nomeada nova: 409 merge_conflict — nenhuma rota, papel ou guard mudou (RN-704). GitProviderErrorFilter mapeia GitMergeConflictError (o merge do repositório local achou conflito) para 409 com os arquivos em conflito na mensagem; a ref de destino fica intacta e a pull request continua aberta. Pelo pipeline de aprovação a ação git_merge termina failed com essa mensagem, o mesmo caminho de GitPullRequestAlreadyMergedError.

  • GET /projects/:projectId/actions aceita status=failed — mesma rota, mesmo papel developer (RN-705). Até aqui só pending era aceito; failed lista as ações do projeto cuja execução falhou, e EXIGE actionType (400 sem ele), para que a leitura seja de um tipo e nunca o histórico inteiro. Devolve a mesma forma ProposedAction que a leitura de pendentes devolve; a ação de git falhada agora carrega o próprio kind, a mensagem de erro e, num conflito de merge, os nomes dos arquivos em conflito — caminhos do repositório que o mesmo papel já lê no diff.

  • A resposta do catálogo de modelos ganhou reasoningBudget — nenhuma rota, papel ou guard mudou (RN-914, ADR 0223). O campo (inteiro ou null) sai no DTO de modelo das leituras do catálogo que já existiam, com os mesmos papéis. É curadoria do produto (o orçamento de raciocínio provado por smoke), não dado do usuário nem segredo; a escrita é só por migration, sem rota nova.
