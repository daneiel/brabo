История фаз

Неизменяемая запись завершённых фаз Brabo, перенесённая из CLAUDE.md 2026-08-23 без переписывания. ДЕЙСТВУЮЩЕЕ состояние продукта живёт в CLAUDE.md, в RN (docs/business-rules.md) и в ADR — этот файл отвечает на вопрос «как мы сюда пришли», а никогда не «что действует сегодня». Принятый ADR никогда не редактируется; исправления ADR, записанные в этом тексте, остаются действительными там, где они есть.

Статус​

  • ФАЗА 1 (MVP) — ЗАВЕРШЕНА: IAM/RBAC, сессии с неизменяемым event log, чат с маршрутизатором LLM (Ollama + API), metering/бюджет токенов, конвейер proposed_actions + permissions.json, движок Elixir/OTP с супервизией и событием завершения.
  • ФАЗА 2 — ЗАВЕРШЕНА: GitProvider (Local/GitHub/GitLab) с контрактным набором тестов и capabilities, зашифрованные учётные данные, идемпотентный и возобновляемый через конвейер bootstrap Gitflow, мастер с прогрессом в реальном времени.
  • ФАЗА 3 — ЗАВЕРШЕНА: Harness (PromptAssembler, ToolLoop, ContextManager, InstructionFiles, Hooks), явные handoffs, агенты Criativo, PO и Arquiteto с артефактами и проверками в домене.
  • ФАЗА 4 — ЗАВЕРШЕНА: агенты выполнения (динамические dev по модулю в изолированных worktrees, QA и SecOps как gate-ы PR, проактивная Infra), блокировка защищённого merge, живая панель команды; настоящий Psicólogo и Anamnese с замкнутым циклом. Gate-ы проверены реальным выполнением (ADR 0020).
  • ФАЗА 5 — ЗАВЕРШЕНА: образы production non-root и CI (ADR 0024), Kubernetes с Kustomize, HPA по очереди Oban, NetworkPolicies и ESO (ADR 0025), graceful shutdown + OpenTelemetry + dashboards (ADR 0026), бэкап с протестированным restore, runbooks и hardening (ADR 0027).
  • ФАЗА DOC — ЗАВЕРШЕНА: docs/ как единственный источник по Diátaxis, сайт Docusaurus в website/, читающий из docs/, генерируемые справочники, docs/.docmap.yml + проверка дрейфа (docs:check) в CI, слой сообщества, проверенная MIT, механизм задокументирован в docs/explanation/documentation-workflow.md.
  • ФАЗА 6 — ЗАВЕРШЕНА: механизированная политика веток (ADR 0030) — pr-police, approval-ladder с двумя режимами, promote/tag-release с вычисляемой версией и якорем по дереву, backmerge gate с автоматическим обратным распространением, версионируемые rulesets. Конвейер проверен от начала до конца (v0.1.0 → v0.2.0), а цепочка hotfix подтверждена реальным выполнением.
  • ФАЗА 7 — ЗАВЕРШЕНА: first-party auth вместо Keycloak — argon2id, access Ed25519, ротация refresh с отзывом семейства, прогрессивный lockout, токены учётной записи и MailSender только в лог (ADR 0031, RN-030..033); атомарный переход с собственным эмитентом, RBAC нетронут, /internal/* с service token, cookie httpOnly + CSRF, миграция пользователей и полное удаление Keycloak (ADR 0032, RN-034/035); OpenAPI в 23 контроллерах с DTO, закреплёнными по типу, табличный тест, требующий метаданных, сгенерированный docs/reference/api/ с манифестом хешей (ADR 0033).
  • ФАЗА 8 — ЗАВЕРШЕНА С ОТСЕЧЕНИЕМ: иерархия агентов — области с единственным lead как внешним контактом, приватные внутренние делегирования (таблица delegations, area как TEXT), консолидированный вердикт с прослеживаемостью, сбой с источником; QA как область (Lead + Автоматизация + Производительность/Безопасность, внешний контракт gate-ов не изменён — набор тестов Фазы 4 зелёный без изменений); Infra как область с субагентом Workflows, генерирующим CI по provider-у; панель команды по областям и Psicólogo/Anamnese, нацеленные на субагентов (ADR 0038). ОТСЕЧЕНИЕ ОБЪЁМА того времени, ОТМЕНЁННОЕ ФАЗОЙ 14d: agent_areas/agent_area_members существуют с тех пор, по проекту, с настраиваемым max_parallel — заставила это область dev, первая ДИНАМИЧЕСКАЯ. Отсечённым остаётся только бюджет по области (реальными пределами бюджета остаются проект, сессия и task). Список в apps/web/src/lib/agents.ts уцелел для цвета, иконки и ПРАВИЛА адресации; участники dev берутся из таблицы.
  • ФАЗА 9 — ЗАВЕРШЕНА: контрактный набор LLMProvider, запущенный против существующих, база OpenAICompatibleProvider поверх node:http с timeout БЕЗДЕЙСТВИЯ, ошибка, нормализованная по code, двухслойные capabilities (ADR 0041); синхронизация каталога, где обнаруженная модель входит выключенной, исчезнувшая модель помечается, а не удаляется, цена заморожена в token_usage с append-only аудитом (ADR 0042); ModelPicker перегруппирован по происхождению с курированием. Шесть provider-ов 9b вошли через Фазу 11 (ADR 0043).
  • ФАЗА 10 — ЗАВЕРШЕНА: Bitbucket + GenericGitProvider сданы ЧЕРЕЗ dogfooding (первое реальное выполнение, где Brabo строил сам себя, в форке с ручным seed, партиями с перезапуском между tasks, Criativo обязателен в цепочке). Итоги записаны в Фазе 12d, в docs/explanation/primeiro-dogfooding.md — 17 находок с arquivo:linha настоящие; КОЛИЧЕСТВЕННАЯ половина (перезапуски, вмешательства, стоимость) осталась não medido, потому что таблица наблюдений так и не была заполнена. Три P1 по операбельности закрыла Фаза 12. Остальные 14 остаются открытыми и перечислены в итогах — не исправляйте попутно.
  • ФАЗА 11 — ЗАВЕРШЕНА: шесть provider-ов Фазы 9b как конфигурация поверх базы, каждый исследован с нуля по официальной документации (запрещено наследовать quirk); LLM_PROVIDER_NAMES с 3 до 9; DTO учётных данных и тестер подключения, выводимые из единого списка; capability объявляется только доказанной, с двумя откатами вживую (DeepInfra и Vultr); единственный новый hook в базе (parseErrorFrame, +31 строка), доказанно необходимый для OpenRouter (ADR 0043). Незакрытые smoke-тесты с настоящими учётными данными: поглощены ФАЗОЙ 13.
  • ФАЗА 12 — ЗАВЕРШЕНА: операбельность после dogfooding, три находки P1 закрыты и доказаны в одном выполнении (ADR 0047). 12a — принятие существующего репозитория: собственный маршрут, getRepo, проверяющий доступ до записи, origin (created|adopted) в обеих таблицах, и ПЛАН как шлюз — dry-run, описывающий расхождение и ничего не меняющий, пока решение пустое; повторное принятие сходится (ADR 0044, RN-045/046). 12b — перепланирование dev agent по событию: сохраняемая машина состояний (working|awaiting_gate|idle|idle_tripped), реагирующая на два события существующей outbox, awaiting_gate, удерживающий worktree (который принадлежит АГЕНТУ, а не task), пока gate не закончит, и circuit breaker с явным re-arm (ADR 0045, RN-047). 12c — продвижение story с полномочиями пользователя: story_promotion по проекту с manual как НОВЫМ значением по умолчанию (направленный backfill ставит существующие проекты в auto), proposed_ready как предложение, а не состояние, продвижение, переиспользующее TransitionStoryUseCase (мёртвый код находки #13), и отказ, возвращающий к PO с причиной, закреплённой в его сессии (ADR 0046, RN-048). 12d — Noop вошёл в машину состояний 12b; скрипт pnpm --filter api validacao:fase-12, который завершается != 0, когда критерий не выполняется, и извлекает улики из базы; итоги Фазы 10 записаны; docmap покрывает engine/dev и engine/agents. Незакрытое (выполнение проверки; объявленные ограничения Local/Noop): поглощено ФАЗОЙ 13.
  • Не рефакторьте готовое без явного запроса.

13b — ЗАВЕРШЕНА 2026-08-07 (v2.4.0)​

Вся цепочка доказана против НАСТОЯЩЕГО GitHub (daneiel/test), в десяти выполнениях: удалённое принятие → план с решением пользователя → ручное продвижение ОДНОЙ story → настоящий dev agent пишет код → commit, push и УДАЛЁННЫЙ PR → gate открывается → область делегирует и освобождает с обоснованием → субагент ПРИОСТАНАВЛИВАЕТСЯ на одобрении → отказ пользователя ВОЗОБНОВЛЯЕТ цикл → вердикт changes_requested от LLM. Ноль перезапусков engine. Merge исключён по замыслу (RN-014). 3. Сценарий — pnpm --filter api validacao:real, с фазами, разделёнными по СТОИМОСТИ (--ate adocao|backlog|execucao) — дешёвая запускается одна первой, и именно так ошибки конфигурации проявлялись до того, как стоили денег. ДВЕ остаются открытыми, и их аргумент стоит больше чисел: Z и AD (allowlist глаголов НЕ сходится: глагол, форма и вызов — разные пространства, и выполнения 6/7/8 застряли по одному на каждом), и AE (агент QA пытается исправить код, который судит, вопреки собственному промпту, — сдерживается двумя независимыми барьерами, allowlist и областью). Ни одна из двух не баг для исправления: это продуктовое решение, и они — в docs/explanation/achados-execucao-real.md.

Вывод, который сдаёт фаза и который важнее PR: путь к автономии НЕ проходит через ослабление политики. Он проходит через то, что агент ЖДЁТ решения, а не умирает, — что ADR 0057 сделал для gate-ов, расширив 0052.

ФАЗА 14 — ЗАВЕРШЕНА 2026-08-07 (что потребовало реальное выполнение)​

Выполнение hello world не прошло дальше первого хода и выявило дефекты, которые не ловил ни один набор тестов, потому что всё до этого работало с ЛОКАЛЬНОЙ моделью. Исправления уже внесены; остаётся функциональность, решённая пользователем во время выполнения.

14a — Операбельность агентов (ЗАВЕРШЕНА)​

  • Сбой хода стал ДОЛГОВЕЧНЫМ agent.error с источником, и агент ГОВОРИТ в нити; четыре разговорных агента перестали записывать пустой agent.response (RN-059). Путь ошибки, рассказанной в финальном frame-е, который не выдавал ни одного события, тоже закрыт.
  • Чат Criativo открывается приглашением, а не пустотой: он активируется и ждёт, пока пользователь заговорит первым, и экран теперь говорит об этом — в том числе что технология и код — НЕ его дело.
  • Ключ, который тратит агент, — ключ OWNER-а workspace (RN-058). Раньше ход искал учётные данные по SLUG агента в столбце UUID: ни один агент никогда не использовал provider с учётными данными, и работал только ollama.
  • Отчёт о расходах по ключам, только для владельца, с агентом, отделённым от человека (RN-060).
  • Bootstrap Gitflow в GitHub: только что созданный репозиторий отвечает 409 во всём Git Data API, и первый commit проходит через Contents API. Поддельный backend тестов лгал (404 там, где GitHub отвечает 409) — исправлено заодно, именно это держало набор тестов зелёным при сломанном продукте.

14b — Древовидная временная шкала (ЗАВЕРШЕНА)​

Одна ветвь на агента, от первой вехи до того, что он делает СЕЙЧАС, выведенная на 100% из event log, который экран уже получает. Хронологическая лента остаётся в столбце активности: она отвечает «что произошло», дерево отвечает «кто что делает».

Пересмотрено после ФАЗЫ 26 (без новой фазы, в том же духе точечного исправления, что 12d/ПОСЛЕ-ФАЗЫ 15): критерий открытия по умолчанию сменился с одного лишь «активен/стоит» на 5 агентов с самой СВЕЖЕЙ активностью — активный по-прежнему в приоритете (RN-118); каждая свёрнутая ветвь получила собственный счётчик НОВИЗНЫ, с «последним просмотренным» по агенту в read-state.ts (тот же механизм, что у колокольчика, теперь гранулярный); а tool.call/tool.result/agent.response стали раскрываться ПО ОТДЕЛЬНОСТИ (аргументы, результат, итерация), сгруппированные по границе итерации ToolLoop.

14c — Автоматическая проверка UI (ЗАВЕРШЕНА)​

Контраст стал тестом над design/tokens.css, с известным долгом, измеренным и закреплённым; макет (обрезанный текст, меню вне viewport, dropdown, обрезанный предком, цель < 24px) стал браузерным проверяющим в scripts/dev/validacao-visual.js. Без новой зависимости.

РАУНД exp001 — Criativo выполняет обещание (RN-163)​

Жалоба была: «Criativo не ответил после того, как сказал, что исправит и попробует снова», и фраза буквально была в коде — run_turn_capturing/1 вызывал модель ОДИН раз, отправлял инструменты и возвращался. Результат инструмента попадал в историю в памяти, и никто его больше не читал, поэтому обещанное исправление происходило, только если пользователь присылал другое сообщение.

Criativo был единственным разговорным агентом без цикла tool use; он получил такой же, как у PO, с собственным пределом 12. Что важно сверх исправления: решать, что объявляется, стал предел, а не фиксированный текст — обещание повторной попытки входит во фразу, только когда ещё есть ход, чтобы его выполнить. Исчерпанный предел стал рассказанным agent.error (po_server в этом случае заканчивал молча, и это был следующий очевидный долг — закрытый чуть ниже RN-166), а сбой инструмента перестал быть agent.response — в event log он был неотличим от обычного ответа и не называл никакого источника, ровно то, что RN-059 закрыла для сбоя хода.

РАУНД exp001 — PO читает уже существующее, и с него спрашивают (RN-164..166)​

Это не фаза: это дефект, найденный реальным ИСПОЛЬЗОВАНИЕМ, и происхождение важно, потому что ни один набор тестов его бы не поймал. Backlog вышел с эпиком и ни одной историей — значит, без задачи, значит, выполнение застряло без какой-либо ошибки. Расследование нашло четыре наложенные причины, и первые три — одна и та же: PO не мог знать и не мог предупредить.

  1. У PO было четыре инструмента, и все — ЗАПИСИ. Контекст собирался ОДИН раз, на kickoff, из 200 последних событий СЕССИИ — с этого момента он больше ничего не перечитывал: не знал, какие правила существуют, какие он уже покрыл и что сам уже создал. Вошли listar_regras_de_negocio и listar_backlog (RN-164), обслуживаемые двумя внутренними маршрутами с областью ПРОЕКТА — и область здесь ключевая: чтение по сессии было ровно тем, что скрывало ранее захваченное правило. Они переиспользуют уже существовавшую трубопроводку (listByTypeForProject, ListBacklogUseCase, computeCoverage); не хватало маршрута, метода в клиенте и инструмента.
  2. Ничто не требовало историю после эпика, и цикл заканчивался молча. Эпик без истории стал ЯВНЫМ исходом — backlog.epic_without_story, долговечным, по образцу RN-059 (RN-165), — а предел итераций PoServer начал выдавать toolloop.limit_reached, ТОТ ЖЕ тип, что у ToolLoop, который разговорные агенты никогда не выдавали, имея собственный цикл (RN-166).
  3. Инструкция kickoff не говорила ни слова о том, что делать, когда не хватает информации, — а перед пробелом без инструкции модель выбирает между выдумыванием и остановкой. Остановка — то, что она сделала. Третий выход стал записан, с инструментом для его применения: ask_structured_questions, ТОТ ЖЕ, что у Criativo (RN-162), теперь объявленный и PO.

Два решения замысла, важные за пределами этого случая: только create_story, который удался, гасит обязательство эпика (история, отклонённая api, ничего не покрыла, и обращение с ней так, будто покрыла, — это замена одного молчания другим); а требование — по СЛУЧАЮ, сообщается один раз, никогда не тревога, повторяющаяся каждый ход, пока кто-нибудь не научится её игнорировать.

РАУНД exp001 — нить читается так, как происходит ход (RN-172/173)​

То же происхождение, что у других: ИСПОЛЬЗОВАНИЕ, а не сценарий. Четыре жалобы на экран Сессии — handoff PO появлялся НАД его последней репликой, одобрение поднималось в середину ответа Arquiteto и опускалось только когда он заканчивал, карточка одобрения «плохо свёрстана», и прокрутка не следовала за разговором.

Расследование выяснило, что упорядочивание было ВЕРНЫМ, и в этом урок раунда. RN-155 верна event log; а лог говорит, что po_server.ex#run_turn/2 выдаёт в ТОЙ ЖЕ итерации agent.response, ЗАТЕМ tool.call для offer_handoff и ТОЛЬКО ПОТОМ рекурсирует к заключительной реплике — значит, seq handoff честно МЕНЬШЕ, чем у последней реплики. То же для proposed_action.created. Исправление, следовательно, не в упорядочивании: это объявленное правило ПРЕДСТАВЛЕНИЯ (RN-172), в отдельном проходе (afundarDesfechos) ПОСЛЕ sort по seq — а не компаратор из трёх членов, который никто не смог бы обосновать через год.

То, что не даёт ходам смешиваться, — три барьера, и каждый существует из-за реального случая: ход (у границы между двумя ходами может не быть ВИДИМОГО элемента — agent.activated открывает ход и не становится элементом нити), автор (в сессии выполнения несколько агентов пишут, ни разу не дав пользователю сказать, и все остаются в одном ходе) и не-исход (два исхода подряд сохраняют порядок между собой — Infra перед Dev Lead).

RN-173 закрывает две другие жалобы, и они были одной и той же: эффект прокрутки зависел только от [events.length, streamingText], а actions — ОТДЕЛЬНЫЙ запрос — пришедшая карточка выталкивала разговор с экрана, ничего не прокручивая. Зависимость исправлена, плюс ResizeObserver над содержимым для того, до чего НИ ОДИН список зависимостей не дотягивается (сворачивание Disclosure, перекомпоновка Markdown). Защита в 120px от конца остаётся нетронутой, намеренно: нить следует за разговором, а не захватывает чтение того, кто прокрутил вверх.

РАУНД exp001 — нить говорит, кто говорит, с какой моделью и что спрашивает (RN-171/174/175/176)​

То же происхождение: ИСПОЛЬЗОВАНИЕ. Четыре жалобы на экран Сессии, и три из них разделяют один урок — продукт знал информацию и не показывал её.

Вопрос по центру, и с выходом (RN-171). Жалоба была буквальной: «sempre dê a opção de input do usuário quando ele seleciona Escreva». Модель предлагала вариант вроде «Напишите сами», а в форме негде было писать — схема ask_structured_questions не умела выразить «помимо этих, что угодно». allowOther вошёл в select со значением по умолчанию true, и асимметрия — аргумент: список, закрытый по ЗАБЫВЧИВОСТИ, стопорит разговор, и пользователь не может разблокировать его извне; список, открытый по ошибке, предлагает лишнее поле. Интерфейсный sentinel никогда не попадает в backend, а кнопка отправки по-прежнему требует всего заполненного (backend в любом случае отклоняет с 400). Блок также стал центрированным с пределом 560px от ApprovalCard и получил аватар: это был единственный элемент нити, ни к чему не выровненный.

Действие, запускающее ход, взводит индикатор (RN-174). Анимация «думает» уже существовала — не хватало ПОКРЫТИЯ. Два действия экрана запускают синхронный ход в engine и ничего не включали: ответ на форму (AnswerStructuredQuestionUseCase переиспользует SendAgentMessageUseCase) и возврат истории PO (ReturnStoryUseCase вызывает reviseStory, то есть handle_call({:revise, …})). Канал Phoenix не закрывает эту дыру: пока join ещё идёт (RN-108), у agent.status «working» нет слушателя, и он теряется.

Модель — для ВСЕХ (RN-175). Предпосылка, что дефект был у PO, не подтвердилась: четыре разговорных агента записывают modelName начиная с RN-146, с зелёным тестом. Никогда не записывал ToolLoop — путь каждого агента выполнения и gate — и чат без активного агента в api. Ни одного нового вызова: RunLlmTurnUseCase уже возвращал поле в теле. Экран перестал писать одинокое слово «modelo» (которое читается так, будто модель так и называется) и стал читаемым chip-ом; без данных он ГОВОРИТ, что они не были записаны, — угадывание по текущему binding приписало бы старому ответу модель, которой, возможно, даже не существовало, — та же ошибка, которую предотвращает замороженная цена из RN-044.

Таблица в Markdown становится таблицей (RN-176). Было возможно два выхода, и выбран поддерживать таблицу в Markdown чата, с Table дизайн-системы. Отображение artifact.module_map в нити было ОТКЛОНЕНО по уже зафиксированному решению: это ДЕЙСТВУЮЩЕЕ состояние проекта, а не артефакт, датированный сессией (RN-159), и он живёт в Обзоре. Кроме того, запрос касался таблицы внутри сообщения — и исправление служит любому агенту, который её напишет, а не только Карте модулей. Разделительная строка остаётся обязательной (GFM), поэтому проза с | никогда не становится таблицей по ошибке.

РАУНД exp001 — панель группирует, упорядочивает и говорит, чего не показывает (RN-177..181)​

То же происхождение, что у других: ИСПОЛЬЗОВАНИЕ, а не сценарий. Пять жалоб на панель контекста и лог Сессии, и урок раунда один — панель показывала срез так, будто это целое, в трёх разных измерениях одновременно: скрывала шесть типов событий, не предлагая альтернативы, читала от самого старого к самому новому и обрезала сессию на 200 событиях, не говоря об этом.

Источник как новая классификация (RN-177). ActivityKind отвечает «о каком ПРЕДМЕТЕ говорит событие» и определяет иконку и цвет; origem отвечает «из какого СЛОЯ оно пришло», и именно он делает историю читаемой — eventos, sistema, llm, harness, agente, usuario, выводимые из СУЩЕСТВУЮЩИХ данных (actor.kind и префикс type). Приоритет — то, что делает её предсказуемой, и он задан порядком if: механизм побеждает актора (tool.call принадлежит harness, кто бы ни был), а актор побеждает префикс агента (chat.message существует с обеих сторон). 5 самых свежих остаются открытыми, а остальное сворачивается по источнику, в обоих местах — в панели лога и в нити, где ось инвертирована (нить идёт по возрастанию, поэтому история оказывается ВВЕРХУ). Фильтр машинного шума по-прежнему включён по умолчанию: его причина не изменилась (116 из 193 реальных событий), изменилось то, что он стал ВЫБОРОМ, а не свершившимся фактом.

Порядок и пагинация (RN-178). Четыре раздела стали убывающими, и кнопка «Carregar mais antigos» как следствие сменила сторону — прежний аргумент с обратным знаком. Бизнес-правила свыше 5 пагинируются, причём страница разрешается через clamp, а не эффектом синхронизации.

Дерево PO (RN-179). backlog.task_created никогда не попадал в панель; теперь эпик → история → задача образуют дерево по СВЯЗИ, которую событие уже несёт (epicId/storyId), никогда по соседству в логе — узел без загруженного родителя поднимается в корень, а не подвешивается наугад.

Предел, который стал видимым (RN-180), — самый ценный пункт. Панель читала 200 событий через prop и не могла сказать, что их больше. Она стала читать пагинированную историю RN-099 (тот же queryKey, что у хвоста, НОЛЬ лишних запросов — RN-090/091), получила pager, который у ActivityFeed был всегда, но ни одно место вызова не передавало, а заметка считает, сколько не хватает, ВЫЧИТАНИЕМ по seq, как колокольчик из RN-100. Производные разделы читают baixados (всё уже пришедшее), а не окно ленты, иначе стали бы показывать МЕНЬШЕ, чем раньше.

Делегирование в нити (RN-181). delegation.completed|failed|dispensed существовали только в панели лога: gate открывался и закрывался без какого-либо знака того, что снизу была вторая попытка. Они стали компактным уведомлением в формате RN-157, с фразой из classifyEvent — той же, что в панели. Внешний контракт области не меняется (ADR 0038): нить рассказывает то, что записал lead, и не начинает адресовать субагента.

ПРОГРАММА 28 — Волна 1, фронт A: тема перестаёт быть недостижимой (RN-182..185)​

Светлая тема существовала в design/tokens.css, имела тест паритета и была описана в design/README.md так, будто это экран, — и ничто в apps/web не писало data-theme. Единственный способ её увидеть — вписать атрибут в DevTools. Оба теста контраста знали и говорили об этом: один утверждал через expect, что ТРИ пары светлой темы проваливаются, — «запись того, что наследуется, а не гарантия того, что отображается». Пока это длилось, аргумент был честным — измерять экран, который никто не может открыть, значит измерять намерение. С приходом кнопки темы он меняет знак.

Boot — это ФАЙЛ (apps/web/public/theme-boot.js), синхронный в <head>, до бандла. Два зафиксированных побочных эффекта: пять пар, являющихся долгом в тёмной, ПРОХОДЯТ в светлой, а «известное исключение дизайн-системы» (--on-accent поверх --accent, 3,20:1) исчезает в светлой — исправление, которое описывал комментарий теста, затемнение до --terracota-500, — как раз то, что стала делать светлая.

Пять из восьми значений --syn-* из handoff были ОТКЛОНЕНЫ измерением ( худшее, --syn-cm, даёт 2,32:1 в светлой). Где handoff проваливается, действует измеренное число: это та же линейка, что и для шрифтов. secops-runtime как скрипт-отчёт (RN-375..377, ADR 0091)​

Решённое владельцем продукта досрочное введение роли secops-runtime (docs/fluxo.yml, camada_seguranca, ранее proposto), не дожидаясь объявленного триггера («production с реальным трафиком, после DEPLOY_ENABLED + активного platform»). Входит только то, чего триггер НЕ требует: pnpm --filter api relatorio:seguranca-runtime читает rate_limit_hits — данные, которые RateLimitGuard из ADR 0027 уже записывает, в том числе при трафике dev/CI, — и производит рейтинг корзин (user:<uuid>/ip:<endereço>, два единственных записываемых формата; без маршрута и причины, которых таблица никогда не хранила) и временное распределение по фиксированным срезам. Это СКРИПТ, а не агент LLM и не GenServer: по данным нечего решать, только агрегировать.

Автоматическое обнаружение инцидентов, реагирование на инцидент и постмортем безопасности остаются ВНЕ — они зависят от того же несработавшего триггера, — и отчёт перечисляет их в ПОСТОЯННОМ разделе «não medido», не симулируя примерный инцидент и не выдумывая числа (тот же принцип, что у ADR 0041/0042/0077). Хранимое окно коротко по замыслу (DomainGaugesCollector.pruneRateLimit удаляет hits старше 2 × RATE_LIMIT_WINDOW_MS, 240s по умолчанию), и отчёт объявляет оба окна — НАСТРОЕННОЕ и НАБЛЮДАЕМОЕ, — никогда не давая второму выдать себя за историю длиннее, чем она есть.

platform получает первую сдачу: отчёт телеметрии по требованию (RN-385/386, ADR 0092)​

Осознанное решение владельца продукта досрочно ввести часть роли platform (docs/fluxo.yml, camada_plataforma) — чей status остаётся planned и чья ativacao остаётся синхронизированной с DEPLOY_ENABLED, которого не существует. pnpm --filter api relatorio:telemetria [--projeto <uuid>] [--json] — это СКРИПТ (не агент LLM, не GenServer), который читает по требованию ТЕ ЖЕ вопросы, которые DomainGaugesCollector уже собирает для scrape Prometheus, — активные/closing сессии по проекту, заблокированные tasks по проекту, состояние последнего бэкапа (всегда ГЛОБАЛЬНОЕ, никогда по проекту, потому что продукт делает бэкап всей базы), — и завершается после печати. SQL-запросы ПОВТОРЕНЫ, а не импортированы из коллектора: его методы приватны и заканчиваются записью в gauge Prometheus, без чистой половины «только запрос», которую можно было бы переиспользовать, не привязывая CLI-скрипт к жизненному циклу @Injectable.

«N агентов онлайн» в dashboard — ЖИВОЙ статус, никогда историческое присутствие (RN-409, ADR 0097)​

Принятое и объявленное в ADR 0097 следствие: запрос предполагает, что тот, кто эксплуатирует продукт, мигрирует обе стороны вместе (db:migrate И engine:migrate), и падает громко/видимо, если мигрировала только api — без try/catch, скрывающего ошибку.

Сессия выполнения больше не закрывается при ожидающем dev agent (RN-411)​

Исправление дефекта, найденного в РЕАЛЬНОЙ сессии выполнения, а не пункт сценария: пять dev agents поднялись, стали idle_tripped (RN-047, circuit breaker), застряв в ожидании, пока пользователь разблокирует задачу за задачей, а 30-секундный heartbeat сессии (Engine.Sessions.SessionServer) закрыл сессию из-под них, пока ручная разблокировка продолжалась. 413 в PR и Executores «без выполнения» — оба конца и цепочка (RN-412, ADR 0098)​

Это не запланированная фаза: исправление, запрошенное реальным ИСПОЛЬЗОВАНИЕМ («nas PRs sempre está estourando entity too large»), плюс родственный дефект вкладки Executores, появляющейся пустой при реально идущей работе. Расследование нашло их сцепленными: gate умирает с 413 → dev-ы застревают в dev.awaiting_gate → это состояние не удерживало сессию (пробел RN-411) → 30-секундный heartbeat закрывает сессию из-под них → вкладка требует активной сессии и исчезает со всем roster.

Причина 413 была в API Brabo, а не в provider-е LLM — комментарии, приписывавшие ошибку provider-у (runtime.exs, terminal_executor.ex, docker-compose.yml), были неверны; FalhaDeTurno.origem({413, _}) уже классифицировал её как "codigo", и был прав. apps/api/src/main.ts никогда не настраивал предел тела Express — действовало значение по умолчанию 100 KB, намного ниже 8 MB, которые принимает Phoenix, в самом тяжёлом направлении транспорта (engine → api, POST /internal/sessions/:sessionId/llm-turn, который пересылает ВСЮ историю на каждой итерации ToolLoop). API_JSON_BODY_LIMIT (по умолчанию 10 MB) закрывает транспортный конец.

Второй конец, без которого поднятие лимита лишь отложило бы переполнение: ContextManager engine (ADR 0098) имел ДВА дефекта, которые делали компактизацию недостижимой до переполнения тела — estimate/1 считал только content, поэтому сообщения assistant, полные toolCalls, стоили в оценке ~ноль токенов; а окно компактизации использовало только context_window (128.000 токенов у агентов gate), что давало ~350 KB до компактизации — далеко после любого разумного транспортного предела. ЭФФЕКТИВНОЕ окно теперь min(context_window, teto_de_transporte), с обрезкой всегда на ГРАНИЦЕ ИТЕРАЦИИ ToolLoop (никогда не отделяя assistant с toolCalls от role: "tool", которые на него отвечают, — это сломало бы протокол tool-use provider-а).

Локальный runner — выполнение на машине пользователя (RN-418/419/420, ADR 0102/0103)​

Запрос владельца продукта: агент, работающий на МАШИНЕ ПОЛЬЗОВАТЕЛЯ, в локальной папке проекта, через стандартный терминал пользователя, — плюс настоящий интерактивный терминал во вкладке Code. Два изменения, одно зависит от другого.

Политика (ADR 0102 — ГЛОБАЛЬНОЕ решение, явно подтверждённое владельцем продукта после автоматического предупреждения безопасности об изменении): git push/PR/deploy (RN-106) и sudo/doas (новые) выходят из безусловного deny и становятся АБСОЛЮТНЫМ ПРЕДЕЛОМ — безусловным require_approval, в ТОМ ЖЕ блоке и по ТОМУ ЖЕ шаблону, что соседние пределы (current.policy === 'auto_approve'), никогда не автоодобряемым ни через agent_autonomy (подстановка "*"), ни через permissions.json. Щель, которую исходный deny затыкал силой, закрыта в ИСТОЧНИКЕ: ApproveAlwaysActionUseCase/patternForAction отказываются записывать шаблон в allow для действия с внешним git-эффектом или привилегированной командой — «sempre permitir» одобряет только экземпляр, никогда шаблон, для этих двух случаев. Без этой второй половины предел был бы декоративным. sudo/doas совпадают по ГЛАГОЛУ в comandoPrivilegiadoNoComando (external-effect.ts), обходя все сегменты команды, — тот же принцип, что у efeitoExternoNoComando.

Runner (apps/runner, новый workspace Node/TS, ADR 0103): CLI (brabo-runner --project <id> --dir <pasta> --token brb_...), который пользователь запускает на своей машине, подключается к ENGINE через НОВЫЙ канал Phoenix (/runner, топик terminal:<projectId>), аутентифицированный ОДНОРАЗОВЫМ тикетом (тот же шаблон RN-108, но тикет ВЫПУСКАЕТСЯ ENGINE — схема "engine", собственная миграция — и запрашивается api через внутренний HTTP-маршрут, инвертируя поток тикета сессии). Выполняет exec (УЖЕ ОДОБРЕННУЮ команду агента — маршрутизация в TerminalExecutor происходит только ПОСЛЕ привычного конвейера decide()/proposed_action, никогда до) в $SHELL пользователя, и интерактивный режим PTY для вкладки Terminal (pty_open/pty_data/ pty_input/pty_resize/pty_close — engine делает чистый RELAY, никогда не интерпретируя байты). Только ОДИН runner на проект (Engine.Runners.Registry, :global, исключительность :global.register_name/3); режим runner БЕЗ проверенного workspace или БЕЗ подключённого runner-а явно ОТКАЗЫВАЕТ — никогда не падает в System.cmd/bind-mount, которых для проекта runner не существует (пересмотрено ADR 0104/RN-423, см. выше; откат на привычный путь по-прежнему действует, но только для container/mounted). PTY — действие аутентифицированного ПОЛЬЗОВАТЕЛЯ, не проходит через proposed_action, но аудируется (terminal.session.started/ended в event log, в том числе когда вкладка падает без явного pty_close).

Граница безопасности runner-а — НЕ sandboxing, это аутентификация (CLI предъявляет Personal Access Token УЧЁТНОЙ ЗАПИСИ пользователя) + привычный конвейер одобрения + согласие пользователя запускать CLI на собственной машине, с его привилегиями. apps/runner/src/guard.ts проверяет cwd внутри корня лексическим разрешением, но объявлен BEST-EFFORT, а не настоящей гарантией.

PAT закрыл пробел токена автоматизации (ADR 0105/RN-424..426). Настоящая находка Волны 1 — «у продукта нет механизма ДОЛГОЖИВУЩЕГО токена учётной записи для автоматизации, поэтому runner повторяет вход браузера (cookie/CSRF, сохранённые в ~/.brabo/runner-credentials.json)» — была закрыта в Волне 2: personal_access_tokens (brb_…, хеш HMAC-SHA256+ pepper через hashDeToken(), никогда argon2 — неверно для секрета ВЫСОКОЙ энтропии) выпускается в Настройках проекта, с областью ОДНОГО проекта, отзываемый, с опциональным истечением. apps/runner/src/auth.ts полностью потерял интерактивный вход, cookies и файл учётных данных — он лишь проверяет формат и передаёт --token/BRABO_ACCOUNT_TOKEN, НИКОГДА не записываемый CLI на диск. PAT никогда не аутентифицирует вне POST .../runner-ticket, по ПОСТРОЕНИЮ (IS_PAT_ROUTE_KEY/ @RequirePatAuth() + PatAuthGuard) — никогда ветка в глобальном JwtAuthGuard, которая позволила бы RolesGuard авторизовать PAT для любого маршрута роли пользователя.

maintainer отзывает PAT другого пользователя (RN-427), закрывая пункт, который ADR 0105 пока объявил вне объёма (реагирование на инцидент — уволенный dev с утекающим токеном). Расширение той же модели, без нового ADR: ОТДЕЛЬНЫЕ маршруты (GET .../personal-access-tokens/all, DELETE .../personal-access-tokens/:tokenId/admin), область по projectId вместо userId — самоотзыв каждого пользователя (RN-426) не меняется.

ADR 0104 — Волна 1 ЗАВЕРШЕНА (RN-421/422/423): ADR 0072 и 0103 никогда не разговаривали друг с другом — RN-170 требовал bind-mount при создании, а маршрутизация в runner (RN-420) переиспользовала тот же флаг workspace_mode == 'local' без какого-либо bind-mount, поэтому настоящее использование runner-а по-прежнему было обязано проходить проверку смонтированной папки. workspace_mode (2 значения) стал execution_mode (container/mounted/runner, миграция 0048) — RN-170 (теперь RN-422) начинает действовать только для mounted; runner рождается с путём, проверенным только ЛЕКСИЧЕСКИ (без I/O), и workspaceVerifiedAt: null, продвигаемым в проверенный, когда runner подключается и подтверждает путь на ХОСТЕ (POST /internal/projects/:projectId/workspace-verification, RN-423) — runner — ИСТОЧНИК ИСТИНЫ пути, перезаписывающий то, что было набрано в мастере. Engine.Actions.TerminalExecutor.decisao_de_execucao/1 получил ЧЕТЫРЕ выхода: маршрутизирует только при проверенном workspace И подключённом runner-е; без любого из двух явно ОТКАЗЫВАЕТ — никогда не падает в System.cmd/bind-mount от mounted, которых для проекта runner не существует.

Находка реализации, исправляющая ADR (который не редактируется — исправление живёт здесь и в backlog.md): фраза ADR 0104 о том, что конвертация между тремя режимами существующего проекта «становится разрешённой без пересоздания проекта», НЕВЕРНА. ИНСТРУМЕНТ РАЗРАБОТКИ — pnpm bootstrap​

Терминальное меню в scripts/dev/bootstrap.sh, группирующее то, что делается изо дня в день: Docker, K8s, Database и Test. Существует, потому что эти команды живут в ТРЁХ местах, которые не разговаривают, — package.json, Makefile и скрипты в deploy/k8s//docker/ — а заученное знание гниёт.

Оно ничего не переизобретает: каждый лист вызывает уже существующую команду. Режим --print-commands разрешает всё дерево без TTY и без выполнения, и именно на нём работает тест (scripts/dev/bootstrap.spec.ts) — TUI не тестируется модульно, но отображение меню→команда — да, и ошибается именно оно. Ноль новых зависимостей; цвета берутся из design/tokens.css в 24-битном ANSI с деградацией до 256 цветов и до отсутствия цвета.

Вывод выполняющейся команды ПРОКРУЧИВАЕТСЯ (колесо мыши в SGR, j/k, PageUp/PageDown, G для возврата в конец). Не хватало не чтения колеса: не хватало СМЕЩЕНИЯ — tail -n умеет показывать только конец, — поэтому окно стало срезом через sed -n 'a,bp', тестируемым без TTY через --print-window. Два следствия, которые объявляет подвал: прокрутка назад ЗАМОРАЖИВАЕТ окно (как less +F, иначе перерисовка с частотой 5 Hz отменяет прокрутку), а отслеживание мыши, включаемое только на экране выполнения, выключается при ЛЮБОМ выходе — \e[?1006l\e[?1000l в restaurar_terminal, который покрывает trap на EXIT. Парсер escape — общий CSI (читает до финального байта): чтение двух фиксированных байтов оставляло остаток последовательности в буфере, а поскольку меню трактует [1-9] как выбор, поворот колеса запускал пункты меню.

Три зафиксированных решения: Create готовит с нуля, а Deploy публикует в уже существующую среду (поэтому выбор по сервису есть только у Deploy); в K8s работает только All, а Api/Engine/Web появляются ВЫКЛЮЧЕННЫМИ, а не исчезают, потому что меню должно говорить, чего продукт не делает; и Database › Delete пересоздаёт расширение pgvector, поскольку docker/postgres/init.sql выполняется только при первой инициализации тома — чистый DROP SCHEMA заставил бы следующую миграцию упасть, а поскольку engine делит ту же базу, восстановление требует db:migrate И engine:migrate.

Docker › Reset total (scripts/dev/reset-total.sh) объединяет всю эту последовательность в один лист — preflight, up --build --wait ( --wait из Compose v2.17+ — это «пока всё не станет здоровым», без цикла здоровья, написанного вручную), тот же DROP SCHEMA, что у Delete, db:migrate + engine:migrate и seed — с СОБСТВЕННЫМ экраном подтверждения (confirmar_reset, требует набрать RESET), отличным от экрана Delete (который требует ИМЯ базы), и без предусловия Delete «postgres уже запущен», потому что именно эта команда поднимает compose с нуля. Seed (apps/api/src/db/seed.ts) получил шаг, активирующий учётные данные provider-а из .env, переиспользуя ТЕ ЖЕ переменные <PROVIDER>_TEST_KEY, которые уже используют smoke-тесты LLM (apps/api/test/infrastructure/llm/*.smoke.spec.ts), — одно соглашение об именах, два потребителя; provider без заданной переменной не входит, без ошибки, и учётные данные остаются у OWNER-а (RN-058).

Исправлено в шести местах, нёсших неверное значение как КОД — docker-compose.yml/.prod.yml, .env.example, docker/ollama/pull-models.sh, scripts/dev/verificar-modelos-ollama.sh, deploy/k8s/base/ollama/job-model-loader.yaml и RN-415 в docs/business-rules.md — без касания ADR 0099/0100 (принятых) и исторического повествования этого же раздела CLAUDE.md, которые описывают то, что было запрошено/решено тогда, а не текущее операционное значение.
  2. Серьёзнее и старше — Database › Delete (пункт 3.4, существующий с создания меню) никогда не удалял по-настоящему: DROP SCHEMA public CASCADE не достаёт до engine.* (Ecto/Oban живёт в СОБСТВЕННОЙ схеме, engine) и до drizzle.__drizzle_migrations (управление drizzle-kit живёт в СОБСТВЕННОЙ схеме, drizzle). Автономный бинарник runner-а (2026-08-23, RN-451/452, ADR 0112)​

Пункт backlog ADR 0104 («standalone binary, pkg/bun build --compile»), спутник ADR 0106 (распространение через npm). Явное решение владельца продукта: по-настоящему ЕДИНЫЙ бинарник, полная матрица с Windows с v1 — более дешёвая альтернатива («бинарник + папка node-pty-native/ рядом») была предложена и отклонена.

bun build --compile встраивает нативный .node из node-pty через with { type: 'file' } и извлекает его в НАСТОЯЩИЙ ВРЕМЕННЫЙ каталог в runtime (native-pty-loader.ts) — необходимо, потому что node-pty разрешает собственный addon через require() по ВЫЧИСЛЯЕМОМУ пути (lib/utils.js#loadNativeModule), который Bun не умеет встроить сам (build проходит, runtime выбрасывает Cannot find module, протестировано до проектирования исправления). Пять платформ (linux-x64/linux-arm64/darwin-x64/darwin-arm64/win32-x64), каждая собрана на своём НАТИВНОМ runner-е (.github/workflows/build-runner-binaries.yml, триггер финального тега, тот же шаблон, что publish-runner.yml), бинарник прикреплён к уже существующему Release.

Честная проверка, по платформам: только linux-x64 был действительно выполнен в этой среде (build:bin+smoke:bin зелёные, многократно — именно при запуске настоящего бинарника проявились два бага ниже). Остальные четыре — особенно Windows, с ТРЕМЯ нативными файлами вместо одного — были продуманы чтением исходного кода node-pty, ни разу не выполненные на реальной машине той ОС; их первое настоящее выполнение — СЛЕДУЮЩИЙ тег версии, а не этот PR. Ни один платформенный fallback не был применён превентивно — ничто в этом расследовании не ДОКАЗАЛО, что какая-либо из пяти не работает так; если настоящий тег покажет, что да, это станет новым пунктом, а не сегодняшним предположением.

Два дефекта, найденные только запуском скомпилированного бинарника, а не чтением API: --external node-pty должен быть в команде bun build, даже при отсутствии какого-либо статического import node-pty в коде — fallback await import(...) (используемый только вне бинарника) всё равно обнаруживается и встраивается Bun и падает в runtime с обманчивой ошибкой; и защите автозапуска (ADR 0106) понадобилась вторая ветка — process.argv[1] внутри бинарника — ВИРТУАЛЬНЫЙ путь (/$bunfs/root/...), до которого realpathSync не дотягивается, выбрасывая ENOENT вне любого try/catch до того, как main() будет вызван.

Сессия 6 (RN-547) связала пять команд цепочкой и закрепила три правила: упавшее среднее звено ничего не откатывает, становится именованной строкой в финальном блоке, и скрипт ВСЕГДА завершается с 0 (откат потребовал бы удалить учётную запись и отозвать ключ, а маршрута для этого нет, и не должно быть такого, который установщик вызывает сам); идемпотентность — это HTTP-КОД, и 409 — ОЖИДАЕМЫЙ исход, а не сбой, с 000, обрабатываемым отдельно, чтобы «api не поднялась» не читалось как «api отказала»; а пароль передаётся через STDIN curl, никогда через argv, потому что /proc/<pid>/cmdline читаем любым пользователем машины. Находка этой сессии: --help ЛГАЛ месяцами («ESTA VERSÃO NÃO INSTALA NADA»), потому что печатает заголовок, являющийся комментарием, а правило, запрещающее говорить о «сессиях фазы», читало только строки кода. Сессия 7 (RN-548) дала потребителя метке вида, и решение было о ЧЕСТНОСТИ: с ключом и без живого подключения — самый частый случай — экран говорит две вещи, которые знает, и называет две, которых не знает (зарегистрированный ключ — не работающий агент, список — от вашей УЧЁТНОЙ ЗАПИСИ, а не этого браузера), тон accent и никогда success. Сессия 8 (RN-549) — единственная, которая могла доказать всё вместе, и она РАСШИРИЛА workflow, который ФАЗА 29 уже имела, вместо создания второго. Её центральное решение — СИГНАЛ: perguntarEstado отображает activating в rodando — обоснованно, — поэтому systemctl is-active и service status --machine дали бы зелёный процессу, который умрёт через две секунды; выбранный сигнал — СТРОКА, которую агент пишет при входе в ожидание, которая существует только после того, как он прочитал ключ, взял тикет, поговорил с api и получил ПУСТОЙ список, и которая — ЗАПИСАННЫЙ ФАКТ, а не выборка состояния. Исход доказывается через API, а не через браузер, потому что субъект утверждения — АГЕНТ, а то, что он наблюдает, — GET /runner/projects; браузер создал бы проект через тот же маршрут с лишним слоем, падающим по посторонним причинам, а утверждение по-прежнему было бы строкой журнала. И E2E остаётся ВНЕ pull_request, со следствием, объявленным, а не скрытым (PR, который его написал, его не выполнил): открыть эту дверь — значит дать установщику способ пропустить проверку происхождения, что отвергает ADR 0150, — отсюда половина, работающая в PR, — это ТЕСТ (scripts/dev/install-e2e.spec.ts), охраняющий два способа, которыми workflow может молча сгнить: ослабленный gate и переписанная фраза install.sh (из-за которой утверждения не падают, а ИСЧЕЗАЮТ). Проявились два дефекта, оба невидимые, потому что workflow никогда не запускался: ответы TTY начинались с nao-migrar, что на чистой машине попадает на вопрос МАРКЕРА и заставляло скрипт выходить с 0, говоря «Nada foi gravado»; и НАХОДКА, оставшаяся находкой, — опубликованный install.sh ничего сам не поднимает на чистой машине, потому что docker/docker-compose.install.yml (вместе с ./postgres/init.sql) не является asset-ом Release, не входит в подписанный checksums.txt, и он его нигде не скачивает, так что тот, кто следует curl … install.sh из runbook, умирает на «no such file or directory» ПОСЛЕ того, как уже проверил подпись и записал .env. Исправление — решение между подписанным asset-ом и clone, и это отдельная сдача. Что фаза оставила ОБЪЯВЛЕННЫМ и не сделанным: отзыв по-прежнему достигает {projeto, usuário} и никогда {chave}, и теперь это стоит дороже (роняет агента во ВСЕХ проектах этой машины); нет экрана, где перечислить и отозвать ключ устройства, а фаза добавила вид для перечисления, не построив экран, — пробел стал БОЛЬШЕ, намеренно; один процесс на машину — единая точка отказа, цена замысла; и install --machine по-прежнему не знает, является ли ключ этой папки действительно ключом машины, потому что на диске оба вида — один и тот же файл, а знает это сервер

Golden-set QA снова измеряет и запускается по расписанию, еженедельно (AT-076/AT-149, ADR 0168)​

Две сдачи, одно человеческое решение между ними. AT-067 измерила, что время укладывается в ubuntu-latest без GPU и что инструмент не измерял: начиная с RN-502 npm test проекта container без контейнера running отклоняется, а seed никогда его не поднимал — 0/6 по построению. Мейнтейнер выбрал «путь 1», и AT-076 его сдала: seed поднимает контейнер каждого случая путём PRODUCTION (module_map → маршрутизация → container_start, предложенный Infra и одобренный владельцем → ExecuteContainerStartUseCase → broker → running через машину состояний), с node:24.11.1-bookworm-slim, закреплённым по digest, нетронутой RN-502 и контейнером, который не поднимается, становящимся ИМЕНОВАННОЙ ошибкой, проваливающей ExUnit (раньше {:skip, _} из тела молча проходил зелёным). Два раунда в CI дали 3/6 и 3/6 против пола 1/6, с разными случаями, за 52 и 86 min job-а. AT-149 закрыла периодичность: ЕЖЕНЕДЕЛЬНО (суббота 01:17 UTC, плюс workflow_dispatch, никогда pull_request), в golden-set-qa.yml, по образцу golden-set-rag.yml. Еженедельно, а не еженощно, потому что раунд стоит до 86 min и МЕНЯЕТСЯ — тот же итог по разным случаям, — и одного в неделю достаточно, чтобы пол обнаружил падение. timeout-minutes: 150 по худшему измеренному случаю. Вердикт — вердикт самого теста; workflow добавляет лишь две защиты ИНСТРУМЕНТА (строка счёта должна существовать, а в event log не может быть отказа RN-502) и, при сбое, печатает логи, как у RAG, — без issue. Образ для pull до seed ЧИТАЕТСЯ из константы seed, никогда из второго литерала, потому что docker run broker-а работает под управляющим пределом 30 s (RN-604). Раунд доказательства, с временным триггером push, удалённым до PR, был 36327281774: снова 3/6, ноль отказов RN-502, 10 min mix golden_set.qa и 13 min 41 s job-а. Объявлено: у broker-а CI нет пяти слоёв compose, heartbeat закрывает сессии seed, пока QA ещё в них работает (без видимого эффекта), а PR, затрагивающий workflow, его не выполняет.

Аутентифицированный git выполняется на хосте runner-а, код — в контейнере (AT-116, ADR 0193, RN-676)​

2026-10-01, раунд 36. RN-558 закрыла половину МОЛЧАНИЯ — аутентифицированный git fetch в режиме runner, при запущенном контейнере, перестал выполняться с пустыми переменными и стал отклоняться с меткой credencial-nao-atravessa-o-container, — и объявила другую половину незакрытым ADR, потому что каждый известный вариант затрагивал порт сдерживания ADR 0130. Консультативная сессия без агента просит агента (AT-254, RN-682)​

2026-10-01, раунд 36. Отзыв нацелен на ключ, а не на пару {projeto, usuário} (AT-013, ADR 0201, RN-685)​
