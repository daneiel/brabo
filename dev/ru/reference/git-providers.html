Провайдеры git

Brabo работает поверх настоящего git-репозитория, и эту роль выполняют три бэкенда: Local (bare-репозитории на диске), GitHub и GitLab. Доменный код не знает, какой из них используется, — он общается с единым контрактом.

Решения — в ADR с 0001 по 0005 и 0028.

Контракт​

GitProviderContract, в packages/shared/src/index.ts. В контракте пятнадцать операций — десятая появилась в Фазе 4a вместе с гейтами PR; 11-я и 12-я — в ФАЗЕ 26 вместе с вкладкой Код (только чтение); 13-я, 14-я и 15-я — в ФАЗЕ 26b, фундамент объявленных задолженностей той же вкладки (blame, навигируемые PR, богатая ветка — пока без экрана, который бы их потреблял):

getRepoGitRepo

Две операции чтения (ФАЗА 26)​

listTree перечисляет один уровень дерева, никогда всё дерево: вкладка Код навигирует по запросу, а запрашивать всё в большом репозитории — это усилитель трафика, который фаза запрещает. Отсутствующий path или "" — это корень; каждая запись несёт полный path и name (лист).

getPullRequestDiff нормализует diff в status (added|modified|removed|renamed), additions, deletions и patch. patch — это string | null, и различие важно: null означает не вернулся (бинарный файл или patch слишком большой для ответа), тогда как "" означал бы «вернулся пустым». Слияние двух случаев заставило бы экран сказать «без изменений» для изменённого бинарного файла.

Оба отсутствия следуют словарю, который уже использовал getFileContent, — null, а не исключение, — чтобы вкладка Код обрабатывала «не существует» единообразно.

Пределы. Обе операции обрезают и сообщают об этом через truncated: true. Числа живут в apps/api/src/domain/git/git-read-limits.ts (1000 записей на уровень, 300 файлов на diff) и не в packages/shared, который на 100% состоит из типов, — export const там переживает tsc и ломает загрузку api в продакшене (охраняется apps/api/test/packages-shared-so-tipos.spec.ts).

Три фундаментальные операции (ФАЗА 26b — RN-110/111/112)​

Фундамент для трёх объявленных задолженностей вкладки Код (blame, богатый выпадающий список веток, навигируемый список PR) — экран каждой из них — это последующая волна, в трёх отдельных агентах. Все три следуют словарю отсутствия, который уже использовали getFileContent/listTree/getPullRequestDiff: null, никогда не исключение, когда ресурса не существует.

blame(ref, path) аннотирует каждую строку коммитом, который последним её затронул, — sha, автор, дата, первая строка сообщения. Это единственная операция, говорящая на GraphQL: в REST API GitHub нет blame, только в GraphQL API (repository.object(expression:).blame(path:)). GitLab использует RepositoryFiles.allFileBlames; Local — git blame --porcelain. Она обрезает на GIT_BLAME_LINE_LIMIT (2000 строк).

listPullRequests(state?) возвращает GitPullRequestSummary[] — id, номер, заголовок, автор, состояние, ветки, updatedAt, — не GitPullRequest[], который является типом ЗАПИСИ (открыть/слить) и никогда не имел ни заголовка, ни автора. local перечисляет из ТОГО ЖЕ бокового хранилища PR Фазы 4a. Обрезает на GIT_PR_LIST_LIMIT (100, одна страница, без следующей пагинации).

listBranchesDetailed(defaultBranch) — отдельная операция, а не расширение listBranches, — почему, смотрите в таблице capabilities ниже. Каждая обогащённая ветка получает ahead/behind (относительно defaultBranch, которую ВЫЗЫВАЮЩИЙ уже знает и передаёт, — спрашивать её снова у провайдера стоило бы лишнего вызова) и связанный открытый PR, если он есть. null в обоих числах, когда провайдер не может их вычислить (осиротевшая ветка, несвязанная история), — честная деградация, никогда не выдуманное число. Обрезает на GIT_BRANCH_DETAIL_LIMIT (30 веток).

Предел ВЫЗОВА и предел ПОТРЕБЛЕНИЯ (ФАЗА 26b)​

Два числа выше ограничивают то, что провайдер возвращает за один вызов. HTTP-поверхность, которая их потребляет, имеет собственные пределы в том же файле, и они отвечают на другой вопрос: сколько ВЫЗОВОВ может породить один запрос клиента. listTree дёшев один раз и дорог тысячу раз.

Различие вынуждает поиск вкладки Код, который не является операцией этого контракта — ни у одного из трёх провайдеров его нет. У GitHub и GitLab есть платформенный поиск по коду со своей семантикой и ограничениями; LocalGitProvider — это bare-репозиторий, и ничего подобного у него нет. Объявить его здесь означало бы либо 13-ю операцию с capability false в local (вкладка, исчезающая у одного провайдера), либо словарь одной платформы, просачивающийся в нормализованный контракт, который существует как раз чтобы это предотвратить.

Поэтому он составлен на уровне приложения (application/use-cases/git/read-project-code.use-case.ts) поверх listTree + getFileContent, с тремя бюджетами — пройденные каталоги, открытые файлы и возвращённые вхождения — плюс кэш с коротким TTL (domain/git/git-read-cache.ts), чтобы навигация и поиск не повторяли одни и те же вызовы. Платят учётные данные owner рабочего пространства (RN-058/RN-082), а rate limit — провайдера; см. RN-095 и ADR 0060.

Capabilities​

Не каждый бэкенд умеет всё, и это объявляется, а не обнаруживается при сбое:

interface GitProviderCapabilities {
  readonly protectBranch: boolean;
  readonly pullRequests: boolean;
  readonly listTree: boolean;
  readonly pullRequestDiff: boolean;
  readonly blame: boolean;
  readonly pullRequestsList: boolean;
  readonly branchesDetailed: boolean;
}
провайдерprotectBranchpullRequestslistTreepullRequestDiffblamepullRequestsListbranchesDetailed
Local❌✅✅✅✅✅✅
GitHub✅✅✅✅✅✅✅
GitLab✅✅✅✅✅✅✅

Две capabilities ФАЗЫ 26 и три ФАЗЫ 26b равны true у всех трёх, потому что контрактный набор тестов проверяет их у всех трёх — это тот же критерий ADR 0041/0042, который действует и для git: capability объявляется только после доказательства, а без доказательства объявляется false и деградирует. Local выполняет их через git ls-tree/git diff/git blame --porcelain/git rev-list --left-right --count в bare-репозитории, без какой-либо платформы за ним, — это единственный из трёх провайдеров, тестируемый против НАСТОЯЩЕГО git (local-git-provider.contract.spec.ts); GitHub и GitLab работают против фальшивых бэкендов msw, а реальные smoke-тесты ({github,gitlab}-provider.smoke.spec.ts) по-прежнему пропускаются без GITHUB_TEST_TOKEN/GITLAB_TEST_TOKEN в окружении — та же ситуация, уже задокументированная в ФАЗЕ 13a для провайдеров LLM.

pullRequestsList заслуживает отдельного замечания: исходное предположение состояло в том, что у local не будет PR, «у концепции единственного репозитория нет PR», — оно не подтвердилось. Боковое хранилище PR Фазы 4a (самодостаточное для dev agents) уже является источником, и все три capabilities local оказались true.

Одна объявленная деградация, и она касается ДАННЫХ, а не операции: GitLab не возвращает размер файла в листинге дерева (в RepositoryTreeSchema нет такого поля, а запрашивать его по каждой записи стоило бы одного запроса на файл), поэтому size там возвращается null. Операция существует и работает; не хватает одной колонки.

Провайдер Local реализует PR внутри себя (нет сервера, чтобы их размещать, но поток существует) и не реализует защиту веток — нет платформы, чтобы её применить. Вызов protectBranch у него бросает GitNotSupportedError, явную ошибку, никогда не молчаливый no-op (RN-028).

Capability — не барьер. Защита веток платформы — это эшелонированная защита. Недопустимый merge предотвращает предел в домене, который работает одинаково у всех трёх провайдеров, включая Local, у которого нет никакой защиты (RN-006). ADR 0028 документирует расхождение между GitHub и GitLab и почему оно не меняет гарантию.

Нормализованные ошибки​

Каждый провайдер переводит ошибку своей платформы в один из этих классов. Домен никогда не видит ни 422 от GitHub, ни fatal: от git:

ошибкакогда
GitRepoAlreadyExistsErrorсоздание уже существующего репозитория
GitRepoNotFoundErrorрепозиторий не существует или нет доступа
GitBranchNotFoundErrorветка не существует
GitBranchAlreadyExistsErrorсоздание уже существующей ветки
GitPermissionDeniedErrorучётные данные действительны, прав недостаточно
GitNotSupportedErrorоперация вне capabilities данного провайдера
GitCredentialConnectionTestFailedErrorпроверка подключения учётных данных не прошла — не доходит до HTTP: TestStoredCredentialUseCase перехватывает её и возвращает refused (ADR 0050)
GitProviderAuthErrorучётные данные недействительны или истекли
InvalidOauthStateErrorstate OAuth не совпадает

Общего базового класса нет, и это решено, а не забыто: ADR 0002 фиксирует, что абстрактный GitError рассматривался и был отвергнут, так как не окупается, пока ни одному HTTP-фильтру он не нужен.

Различие, наиболее важное на практике, — GitPermissionDeniedError против GitProviderAuthError: первое означает «токен действителен, но не может этого делать», второе — «токен не работает». Перепутав их, пользователя отправят заново аутентифицироваться, когда проблема была в scope.

Повторы​

Только при чтении, никогда при изменении (ADR 0003).

Алгоритм — Full Jitter от AWS: sleep = random(0, min(maxDelay, base · 2^attempt)), по умолчанию 4 попытки. apps/api/src/infrastructure/git/retry.ts.

Асимметрия — это всё решение: повторить listBranches, превысивший время, безвредно; повторить commitFiles, который мог пройти, создаёт дублирующий коммит. Когда невозможно узнать, произошло ли изменение, правильный ответ — завершиться ошибкой и дать человеку посмотреть.

Контрактный набор тестов​

Единый набор — apps/api/test/contract/git-provider.contract.ts — запускается против всех трёх провайдеров. Именно он гарантирует, что «работает в Local» не превратится в «работает только в Local».

Это также механизм, который держит capabilities честными: провайдер, объявляющий protectBranch: true, должен пройти тесты защиты; объявляющий false — должен бросать GitNotSupportedError. Неверное объявление ломает набор в обе стороны.

Набор сопровождают две проверки, в apps/api/test/contract/git-provider-contract-callers.spec.ts. Первая проверяет, что заголовок набора перечисляет ровно тех, кто его вызывает. Вторая — пункт 33 ФАЗЫ 26: операция контракта без потребителя в src/ проваливает CI — операция, которую реализуют три провайдера и никто не вызывает, — это постоянный груз, и ничто не доказывает, что она работает на реальном пути.

Клапан, позволяющий фазе выдать контракт раньше маршрутов, узкий и именованный: отображение SEM_CONSUMIDOR_AINDA, рядом с каждой операцией в котором записана фаза, что будет её потреблять. Он закрывается сам — как только у операции появляется потребитель, запись начинает проваливать проверку, вынуждая автора маршрута её удалить.

Отображение пусто с ФАЗЫ 26b, и опустошил его механизм, а не чья-то память: как только application/use-cases/git/read-project-code.use-case.ts начал вызывать listTree и getPullRequestDiff, второй тест провалился, указав обе записи по имени. Пусто, а не удалено — клапан остаётся доступным для следующего контракта, который родится раньше потребителя.

:::caution Фальшивка должна лгать так же, как удалённый сервис Набор запускается против фальшивых бэкендов (msw) для удалённых провайдеров, и фальшивка ЩЕДРЕЕ настоящего API оставляет набор зелёным, пока продукт ломается. Так случилось с пустым репозиторием: фальшивый GitHub отвечал 404 на несуществующий ref, настоящий GitHub отвечает 409 Git Repository is empty, и bootstrap умирал на самом первом шаге каждого нового проекта на GitHub — при полностью зелёном наборе. Добавляя случай в фальшивку, сверяйте ответ с живым API, а не с тем, что кажется разумным. :::

Первый коммит в пустом репозитории​

Только что созданный репозиторий GitHub не имеет ни одного коммита (auto_init: false), и там весь Git Data API отвечает 409 — refs, blobs, trees, commits. Собрать через него первый коммит невозможно. Работает Contents API (PUT /repos/:owner/:repo/contents/:path), который создаёт файл, коммит и ветку за один раз; именно его использует commitFiles, когда обнаруживает, что репозиторий пуст.

С одним файлом — случай bootstrap, который коммитит по одному на шаг — получается ровно один коммит, как обещает контракт. С несколькими первый рождается через Contents API (именно он создаёт ветку), а остальные входят во второй коммит обычным путём: два коммита вместо одного — объявленная деградация, потому что альтернативой было бы отклонить начальный коммит с несколькими файлами.

LocalGitProvider ничего этого не проходит: его git init --bare принимает первый коммит обычным путём.

Bootstrap Gitflow​

Пять шагов, подготавливающих репозиторий проекта: постоянные ветки (dev, qa, main), защиты там, где провайдер их поддерживает, и базовые файлы.

Их было шесть: был шаг create_rc_branch, создававший ступень rc между qa и main. Ступень ушла из политики по ADR 0030, а шаг ушёл из bootstrap позже, когда заметили несоответствие, — продукт создавал, защищал и документировал в репозитории пользователя лестницу из четырёх ступеней, от которой сам же отказался. Значение create_rc_branch остаётся в enum bootstrap_step базы: у старых bootstrap есть строки с ним, а шаг, который действительно произошёл, не стирается.

Два свойства, оба протестированы (ADR 0005, RN-029):

Идемпотентность — каждый шаг проверяет перед действием. Двукратный запуск ничего не дублирует.

Возобновляемость — упал на шаге 4? Возобновление начинается с 4, а не с 1.

Каждый шаг выпускает собственное событие, и возможны пять исходов:

событиеозначает
bootstrap.step_startedначался
bootstrap.step_completedвыполнил работу
bootstrap.step_skippedуже было сделано — это успех
bootstrap.step_degradedзавершился без capability (защита веток в Local)
bootstrap.step_failedупал; возобновление начинается здесь

skipped и degraded существуют отдельно от completed намеренно: bootstrap, пропустивший всё, потому что репозиторий уже был готов, — это иной исход, чем сделавший всё, а запущенный без защиты веток отличается от обоих. Слить все три в «ok» значило бы потерять ровно ту информацию, которая кому-то понадобится потом.

Принять существующий репозиторий (Фаза 12a)​

Проект может указывать на репозиторий, который уже существует, вместо того чтобы создавать новый. project_repositories.origin говорит, какой из двух случаев (RN-046).

Принятие использует только то, что уже было в контракте: getRepo проверяет доступ — существовал с Фазы 2, и ни один use case его не вызывал, — а диагностика использует listBranches и getFileContent. Ни один новый метод не вошёл в контракт, и контрактный набор тестов остался нетронутым.

Bootstrap НЕ запускается при принятии. Результат — план: сериализованный список того, что он сделал бы, полученный вызовом check() каждого шага — того же, что обеспечивает идемпотентность, — ничего не выполняя. Затем пользователь одобряет план целиком или принимает репозиторий как есть и отказывается от bootstrap (RN-045).

событиеозначает
bootstrap.repository_adoptedрепозиторий стал принадлежать проекту; в нём ничего не изменено
bootstrap.plan_approvedпользователь одобрил — только с этого момента bootstrap запускается в принятом репозитории
bootstrap.adopted_as_isпользователь отказался от bootstrap; план сохраняется как доказательство того, что не было применено

Расходящаяся защита — это наличие × отсутствие, и только. Контракт выставляет GitBranch.protected как булево значение, а ADR 0028 отложил нормализованную ProtectionPolicy — поэтому план может сказать «qa не защищена → применил бы» и «main уже защищена → не трогает», но не может сказать, что существующая защита требует двух ревьюеров, а наша потребовала бы одного. Ветка с ЧАСТИЧНОЙ защитой считается незащищённой и может быть перезаписана — всегда в рамках одобренного плана.

Ветка, которую шаблон не знает (develop, release/*), становится информационной диагностикой и никогда не трогается: у принятого репозитория та политика, какая есть.

Решение — в ADR 0044.

Учётные данные​

Токены git — это секреты пользователя: шифруются envelope encryption, один DEK на запись, никогда в открытом виде ни в базе, ни в логах. Таблица — project_git_connections, и она участвует в ротации мастер-ключа вместе с учётными данными LLM — см. runbook.

Регистрация использует собственный enum в базе (credential_provider), объединённый с провайдерами LLM только на уровне типа TypeScript, без смешения enum (ADR 0004).

Два пути подключения: PAT (вставленный токен) и OAuth (GitHub и GitLab). OAuth требует настроенных GITHUB_OAUTH_CLIENT_ID/_SECRET или пары GitLab; без них — только PAT (конфигурация).

Чего не существует​

Bitbucket и GenericGitProvider — вне рамок — это не забытый бэклог, а решение. Добавить новый провайдер — значит реализовать все пятнадцать операций, честно объявив capabilities, и пройти контрактный набор тестов.

Записи через вкладку Код тоже не существует. Семь операций чтения (listTree, getPullRequestDiff, blame, listPullRequests, listBranchesDetailed, плюс getFileContent и составной поиск) — только для чтения, и всё. Сохранение файла через вкладку — будущая фаза, и когда она придёт, запись — это внешний эффект: она рождается как proposed_action, как всякое изменение git. Проверяемым, а не только намерением, это делает то, что у CodeController нет ни одного глагола записи — ни @Post, ни @Put, ни @Patch, ни @Delete, — даже после того как ФАЗА 26b добавила в него три маршрута.
