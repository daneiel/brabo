# Конфигурация

Вся конфигурация задаётся **переменными окружения**. Файла конфигурации
приложения нет — есть `permissions.json`, но это политика проекта, а не
конфигурация процесса.

Два версионируемых файла читаются во время выполнения и конфигурацией не
являются, хотя их легко с ней спутать: `permissions.json` выше и
`docs/gates.yml` ([ADR 0054](../adr/0054-gates-como-registro-declarativo.md)),
декларативный реестр gates. Ни у одного из них нет переменной окружения,
указывающей путь, — реестр находится поднятием от `__dirname`, — и ни один не
меняет поведение при редактировании в production: реестр ОПИСЫВАЕТ gates, а не
применяет их. Он едет внутри образа api; см.
[runbook](../runbook.md#registro-de-gates).

Едет реестр и **ничего из того, на что он указывает**. `evidencia` gate
`teste`/`ci` называет файлы под `apps/api/test/`, `scripts/ci/` и `.github/`, и
ни одного из них в образе нет. Проверка существования этих целей поэтому —
утверждение о репозитории, проверяемое в CI, а не процессом, обслуживающим
`GET /gates`, — поэтому api читает реестр, не разыскивая их. Раньше она
разыскивала и отвечала `500` в каждой установке
([RN-070](../business-rules/custo.md#rn-070)).

> **`up --wait` доказывает только то, у чего есть healthcheck.** В compose для
> разработки у `api`, `engine` и `web` их не было, поэтому
> `docker compose up --wait` считал их готовыми в момент старта контейнера — до
> того, как процесс начинал слушать. Так контейнер мог умереть через секунды,
> а команда всё ещё сообщала об успехе. Теперь все три несут ту же проверку,
> которую образы production уже объявляют в Dockerfile (`/health` в api и
> engine, затрагивающий базу; `/` на сервере Vite). Брокер контейнеров получил
> свою в отдельном изменении; у `postgres` и `neo4j` они были всегда. Ничего
> здесь не является переменной окружения — это написано потому, что на
> `--wait` полагаются скрипты, а сервис без healthcheck заставляет его лгать.

Значения по умолчанию ниже извлечены из кода, а не из прежней документации.
Колонка **когда ломается** — та часть, что экономит время: почти у каждой
переменной есть умолчание, работающее в разработке, и особый режим отказа в
production.

> **Переменная доходит до процесса, только если compose её отображает.**
> `docker compose` не передаёт окружение хоста внутрь контейнера: переменная
> доходит, если — и только если — она записана в `environment:` этого сервиса
> (или в `env_file`). Это не мелочь: именно так `ANAMNESE_ENABLED` и
> `PSYCHOLOGIST_ENABLED` молча стали недостижимы, пока три места в коде
> обещали, что пауза от 2026-08-10 отменяется через `X=true` и перезапуск.
> Измеренные внутри работающего контейнера engine, они вернулись пустыми, и
> `runtime.exs` упал в `"false"` — без ошибки где-либо. Каждый булев флаг,
> который читает engine, теперь отображён в трёх файлах compose (dev,
> production и установка — установочный только с AT-202), с умолчанием самого
> кода, кроме двух ключей загрузки фоновых агентов, которые production и
> установка намеренно выключают, и `scripts/ci/flags-do-engine-no-compose.spec.ts`
> проваливает сборку для следующего, которого не окажется
> ([RN-540](../business-rules.md#rn-540)).
> Kubernetes исключён из этого правила намеренно: Deployment/ConfigMap ничего
> не перехватывает, так что там нет сломанного ключа, который нужно чинить.

> **Умолчания разработки намеренно небезопасны.** Значения вроде
> `dev-master-key-change-me` существуют, чтобы `pnpm dev` поднимался без
> церемоний. В production их нужно заменить — и для шести из них процесс
> **отказывается** стартовать без замены (api или engine, помечены 🔒). Пять
> следуют образцу
> [ADR 0059](../adr/0059-segredo-do-state-de-oauth-sem-default.md)/[RN-093](../business-rules/custo.md#rn-093):
> отсутствующее, равное публичному литералу-примеру или слишком короткое
> значение роняет загрузку. См. [RN-114](../business-rules/custo.md#rn-114) о
> четырёх, присоединившихся к исходному `GIT_OAUTH_STATE_SECRET`.

## Compose установки (`docker-compose.install.yml`)

Compose, работающий на **установленной** машине, берёт пять образов продукта из
**обязательных переменных**, без умолчания — `install.sh` записывает их в
`.env`:

| переменная | что |
|---|---|
| `BRABO_API_IMAGE` | полная ссылка на образ api; `ghcr.io/…@sha256:…`, когда источник GHCR, `brabo-api:prod`, когда собран локально |
| `BRABO_ENGINE_IMAGE` | то же для engine |
| `BRABO_WEB_IMAGE` | то же для web |
| `BRABO_BACKUP_IMAGE` | то же для job резервного копирования (под profile `backup`) |
| `BRABO_BROKER_IMAGE` | то же для брокера контейнеров ([ADR 0162](../adr/0162-broker-publicado-e-oferecido-pelo-instalador.md)). Записывается **независимо от того**, включён ли брокер: Compose интерполирует весь файл до фильтрации по profile, так что `${VAR:?…}` в выключенном сервисе всё равно отклоняет файл (измерено) |

Они намеренно `${VAR:?…}`. С умолчанием отсутствующая переменная подняла бы
половину стека на образе, который никто не выбирал, и ошибка проявилась бы как
странное поведение, а не как отказ.

Их **нет** в сгенерированном инвентаре ниже: генератор обходит `apps/`, а эти
читает Compose, а не код продукта
([RN-527](../business-rules.md#rn-527)).

**Брокер** есть в этом compose с [ADR 0162](../adr/0162-broker-publicado-e-oferecido-pelo-instalador.md),
**выключенный**, под profile `container-broker`, и `install.sh` включает его,
только когда спрашивает и ответ «s» ([RN-575](../business-rules.md#rn-575)).
Тогда он записывает четыре строки — все вместе или ни одной:

| переменная | что записывает `install.sh` |
|---|---|
| `COMPOSE_PROFILES` | `container-broker` — читается Compose из `--env-file`, так что `up -d --wait` поднимает брокер без флага |
| `BROKER_URL` | `http://broker:8090` — сторона api; без неё api никогда не вызывает брокер |
| `DOCKER_GID` | gid сокета, **видимый изнутри контейнера**, измеренный самим образом брокера; сбой измерения — именованный отказ, никогда умолчание `999` |
| `PROJECT_WORKSPACES_HOST_ROOT` | `<DockerRootDir>/volumes/brabo_project_workspaces/_data`, вычисляется до подъёма и сверяется с реальным `Mountpoint` тома после него |

`BRABO_PROJECTS_HOST_BASE` не записывается: compose выводит её из
`BRABO_PROJECTS_BASE`, как в compose валидации. Включение или выключение позже
описано в [runbook](../runbook.md#broker-na-instalacao).

О **локальных моделях** (Ollama, profile `llm`) спрашивают сразу после брокера
([RN-691](../business-rules.md#rn-691)). Ответ «s» сначала измеряет свободный
порт хоста и записывает:

| переменная | что записывает `install.sh` |
|---|---|
| `OLLAMA_PORT` | `11434` или первый свободный порт до `11443`, когда что-то (нативный Ollama) уже слушает там; весь занятый диапазон — именованный отказ, без записи чего-либо |
| `COMPOSE_PROFILES` | `llm`, вместе с `container-broker` в ОДНОЙ строке, только когда приняты оба (`container-broker,llm`) — две строки не складываются, побеждает последняя |

Без них проверка семантического дубликата пропускается. Включение позже — в
[runbook](../runbook.md#modelos-locais-na-instalacao).


## api

### Основные

| переменная | умолчание | когда ломается |
|---|---|---|
| `DATABASE_URL` | `postgres://brabo:brabo@localhost:5432/brabo` | без неё ничего не поднимается |
| `PORT` | `3000` | — |
| `API_JSON_BODY_LIMIT` | `10mb` | потолок тела JSON, которое принимает api, применяемый к парсеру, зарегистрированному в `main.ts`, до любого маршрута. Существует, чтобы изменение транспортного потолка engine (`TRANSPORT_MAX_BODY_BYTES`, 8 MiB) не требовало нового deploy — умолчание оставляет запас над ним. Слишком маленький — и ход с большим контекстом возвращается как **413** |
| `NODE_ENV` | — | `production` включает строгий CORS и проверку ключей |
| `API_PUBLIC_URL` | `http://localhost:3000` | используется в callbacks OAuth git; неверная = сломанный callback |
| `ENGINE_URL` | `http://localhost:4000` в коде, `http://engine:4000` в Compose | синхронные команды api→engine падают. **Оставьте её пустой в `.env`**: заданная там, она побеждает умолчание Compose, и api пытается говорить с `localhost:4000` изнутри собственного контейнера — каждая активация сессии умирает с `ECONNREFUSED`, и frontend не двигается с места. У каждого окружения уже есть правильное умолчание без этой строки |
| `ENGINE_PUBLIC_URL` | то же, что `ENGINE_URL` | используется только для сборки `engineWsUrl` (WebSocket), возвращаемого в `POST .../runner-ticket`/`.../terminal-ticket` — runner и web могут быть ВНЕ кластера, поэтому внутренний адрес (`http://engine:4000`) не подходит; `ENGINE_URL` по-прежнему используется в обычных синхронных вызовах api→engine (RN-419) |
| `BRABO_VERSION` | `dev` | становится `service.version` в resource OpenTelemetry — так узнают, какая сборка породила трассу. Образ релиза внедряет тег через `ARG` из `docker-bake.hcl`; вне релиза остаётся `dev`. **Не** появляется в `/health`, который намеренно не возвращает версию (см. `description` маршрута) |
| `MIGRATIONS_FOLDER` | `./src/db/migrations` | — |

### Безопасность 🔒

| переменная | умолчание | когда ломается |
|---|---|---|
| `CREDENTIALS_MASTER_KEY` 🔒 | `dev-master-key-change-me` **только вне production** | оборачивает DEKs. **В production api отказывается стартовать**, если её нет, если это умолчание выше (публичное — оно в `.env.example`) или если в ней меньше 16 символов (RN-114). Это лишь проверка ЗАГРУЗКИ: замена на **действительный, но другой** ключ без перезаворачивания всё равно делает все учётные данные нечитаемыми без какой-либо ошибки — сбой проявляется при первом использовании. См. [ротацию](../runbook.md#rotacao-da-chave-mestra) |
| `CREDENTIALS_MASTER_KEY_PREVIOUS` | — | только во время ротации. Присутствует = api пробует предыдущий ключ, когда текущий не подходит |
| `GIT_OAUTH_STATE_SECRET` 🔒 | `dev-oauth-state-secret-change-me` **только вне production** | подписывает `state` OAuth; слабый = CSRF в потоке подключения git. **В production api отказывается стартовать** без него, с умолчанием выше (публичным — оно в `.env.example`) или с менее чем 16 символами. Генерируйте `openssl rand -base64 32`. См. [ADR 0059](../adr/0059-segredo-do-state-de-oauth-sem-default.md) и [RN-093](../business-rules/custo.md#rn-093) |
| `WEB_ORIGIN` 🔒 | `http://localhost:${WEB_PORT}` | **в production api отказывается стартовать**, если её нет или она равна `*`. CORS строгий для каждого окружения. **Порт — часть значения**: web на `:5174` — другой origin и блокируется — см. [ADR 0037](../adr/0037-cors-do-engine-e-a-porta-como-contrato.md). В composes умолчание **выводится из `WEB_PORT`**, так что смена порта тянет за собой CORS; ручное задание `WEB_ORIGIN` перекрывает вывод, и поддерживать согласованность становится вашей ответственностью |
| `WEB_PORT` | `5173` (dev) · `8088` (prod) | опубликованный порт web на хосте. Ни один сервис её не читает — она **питает умолчание `WEB_ORIGIN`** в composes, и именно это не даёт порту и CORS разойтись |

### Auth first-party

Auth живёт в домене api, а после перехода является и единственным эмитентом.
Решения в
[ADR 0031](../adr/0031-auth-first-party-argon2id-e-rotacao-de-refresh.md) и
[ADR 0032](../adr/0032-corte-do-keycloak-e-sessao-em-cookie.md).

| переменная | умолчание | что делает |
|---|---|---|
| `AUTH_JWT_SECRET` 🔒 | `dev-auth-jwt-secret-change-me` **только вне production** | фраза, из которой пара Ed25519 access token **выводится** через scrypt — ни один приватный ключ не коммитится. **В production api отказывается стартовать**, если её нет, если это умолчание выше (публичное — оно в `.env.example`) или если в ней меньше 16 символов (RN-114) |
| `AUTH_JWT_SECRET_PREVIOUS` | — | принимается **только для проверки** во время ротации; входит в JWKS и никогда не подписывает |
| `AUTH_TOKEN_PEPPER` 🔒 | `dev-auth-token-pepper-change-me` **только вне production** | ключ HMAC хэша непрозрачных токенов (refresh, привязки аккаунтов, PATs) и ключа корзины блокировки. **Собственный секрет — больше не падает в `AUTH_JWT_SECRET`** ([RN-613](../business-rules/autenticacao.md#rn-613)). **В production api отказывается стартовать**, если его нет, если это любое из значений-примеров этого репозитория или если в нём меньше 16 символов. Установка, работавшая без него, должна задать его **текущим** `AUTH_JWT_SECRET`, иначе всех разлогинит — см. [runbook](../runbook.md#rotacao-do-auth-jwt-secret) |
| `AUTH_ACCESS_TOKEN_TTL_MS` | `900000` | 15 мин |
| `AUTH_REFRESH_TOKEN_TTL_MS` | `1209600000` | 14 дней |
| `AUTH_REFRESH_ABSOLUTE_TTL_MS` | `2592000000` | абсолютный потолок семейства, считая от входа — без него ротация даёт вечную сессию |
| `AUTH_REGISTRATION_ENABLED` | `true` | любое значение, отличное от `"false"`, оставляет регистрацию открытой |
| `AUTH_LOCKOUT_ENABLED` | `true` | то же соглашение |
| `AUTH_LOCKOUT_WINDOW_MS` | `900000` | скользящее окно подсчёта |
| `AUTH_LOCKOUT_THRESHOLDS` | `5:30,8:300,12:900` | лестница корзины по email, `сбои:секунды` |
| `AUTH_LOCKOUT_IP_THRESHOLDS` | `20:30,30:120` | лестница корзины по IP, мягче и с коротким потолком |
| `AUTH_EMAIL_TOKEN_TTL_MS` | `172800000` | подтверждение email, 48 ч |
| `AUTH_RESET_TOKEN_TTL_MS` | `3600000` | сброс пароля, 1 ч |
| `AUTH_SET_PASSWORD_TTL_MS` | `604800000` | установка первого пароля (мигрированный пользователь), 7 дней — дольше сброса, потому что получатель его не запрашивал |
| `AUTH_IP_ATTEMPT_THRESHOLD` | `60` | потолок попыток по IP на маршрутах auth |
| `AUTH_MAIL_LOG_TOKENS` | `false` | **только dev**: печатает в лог токен подтверждения/сброса |

> **Потолок лестницы по email намеренно равен окну.** При скользящем окне
> настойчивый сдвигает окно и остаётся заблокированным, пока настаивает;
> переставший возвращается с чистым окном. Потолок **больше** окна создал бы
> блокировку, которую окно не может представить, и потребовал бы постоянной
> колонки `locked_until` с очередью разблокировки. Не трогайте одно без другого.

> **Ротация `AUTH_TOKEN_PEPPER` разлогинивает всех** и аннулирует ожидающие
> токены подтверждения и сброса. В отличие от ключей, у pepper **нет**
> `_PREVIOUS`. См. [runbook](../runbook.md).

> **Докуда доходят переменные `_PREVIOUS`.** `AUTH_JWT_SECRET_PREVIOUS`,
> `CREDENTIALS_MASTER_KEY_PREVIOUS` и `BRABO_SERVICE_TOKEN_PREVIOUS` отображены
> в `environment:` трёх composes (dev, production и установка) как `${X:-}` —
> api получает все три, engine и брокер получают
> `BRABO_SERVICE_TOKEN_PREVIOUS` ([RN-595](../business-rules/autenticacao.md#rn-595)).
> Пустое значение равносильно отсутствию для каждого читателя, так что вне
> ротации ничего не меняется; во время неё достаточно задать их в `.env` и
> пересоздать сервис. До RN-595 они не были отображены нигде, а `docker compose`
> не передаёт окружение хоста, так что ротация молча превращалась в жёсткую
> замену. **В Kubernetes они доходят до Pods через хранилище секретов**
> (AT-220): `ExternalSecret` вытягивает весь объект `brabo` через
> `dataFrom.extract`, так что присутствующий там `_PREVIOUS` попадает в
> `brabo-secrets`, а отсутствующий просто там отсутствует. Цена в том, что
> каждый ключ этого объекта становится переменной окружения api, engine,
> migrations и backup — объект хранилища не может хранить ничего другого.
> Процедура в [runbook](../runbook.md#rotacao-no-kubernetes).

### Настоящий SMTP (MailSender)

`MailSender` отправляет настоящий email только с `MAIL_TRANSPORT=smtp` —
умолчание `log` (ссылка/токен идут в лог api, `AUTH_MAIL_LOG_TOKENS` выше), в
том числе в production: отправка email — выбор оператора. Решение в
[ADR 0096](../adr/0096-smtp-real-no-mailsender.md).

| переменная | умолчание | что делает |
|---|---|---|
| `MAIL_TRANSPORT` | `log` | `log` (умолчание) или `smtp`. Любое другое значение падает в `log` |
| `SMTP_HOST` 🔒 | — | хост SMTP-провайдера. **Только с `MAIL_TRANSPORT=smtp`**: в production api отказывается стартовать, если его нет, если он из одних пробелов или если это значение-пример, опубликованное в `.env.example` (RN-114) |
| `SMTP_PORT` | `587` | порт провайдера — `587` это STARTTLS, `465` — неявный TLS (`SMTP_SECURE=true`) |
| `SMTP_SECURE` | `false` | `true` включает неявный TLS на соединении (обычно порт 465) |
| `SMTP_USER` 🔒 | — | пользователь auth SMTP. То же требование, что и `SMTP_HOST`, в production |
| `SMTP_PASSWORD` 🔒 | — | пароль/токен auth SMTP. То же требование, что и `SMTP_HOST`, в production — **никогда не появляется в логе** |
| `SMTP_FROM` | — | отправитель в формате `"Имя <email@домен>"` (или только email). То же требование, что и `SMTP_HOST`, в production, плюс проверка формата |

> Тело email — **простой текст**, без HTML: порт `MailSender` не несёт
> структуры для богатого тела, а шаблонизатор был бы поверхностью инъекции без
> выгоды. Ссылка использует `WEB_ORIGIN` (выше).

### Seed для разработки

Потребляются `pnpm --filter api seed`, а не работающей api. Без внешнего IdP
отсюда берутся учётные данные для входа в локальный web и в smoke.

#### Проект в режиме Mounted: одна база, монтируемая по идентичности

С [ADR 0072](../adr/0072-projeto-local-ou-container.md) проект может родиться в
режиме **Mounted** (прежний `local`, переименованный
[ADR 0104](../adr/0104-execution-mode-tres-valores-e-workspace-verificado-pelo-runner.md))
— код живёт в папке пользователя, и `PROJECT_WORKSPACES_ROOT` **не участвует** в
его корне.

Путь проекта — данные проекта (`projects.workspace_path`), выбираемые при
создании и никогда не переменная окружения. ОКРУЖЕНИЕ предоставляет **базу**,
под которой живут эти папки, — `BRABO_PROJECTS_BASE`, одну на установку
([ADR 0141](../adr/0141-base-unica-dos-projetos-montados.md),
[RN-500](../business-rules.md#rn-500)):

```bash
# .env — ABSOLUTO. `~` não é expandido pelo Compose.
BRABO_PROJECTS_BASE=/home/voce/projetos-brabo
```

Писать эту строку вручную не нужно. С
[ADR 0146](../adr/0146-base-consentida-no-bootstrap.md) `pnpm bootstrap` →
**Docker › Base de projetos** запускает `scripts/dev/consentir-base.mjs`, который
предлагает `$HOME/projetos-brabo`, отклоняет то, что пересекается с checkout
Brabo или с `PROJECT_WORKSPACES_HOST_DIR` (два корня с противоположными
владельцами — общая папка заставила бы проект Mounted с именем `loja` упасть
поверх проекта Container, чей `workspace_dir_name` тоже `loja`), **доказывает** на
macOS и Windows, что Docker действительно видит папку, монтируя её, и только
затем записывает переменную.

Доказательство — это монтирование, а не чтение `settings.json` Docker Desktop:
этот файл не документирован, меняется между версиями и платформами и описывает
то, что настроил пользователь, а не то, что сделает daemon, — то же правило,
которое продукт уже применяет к providers LLM, где capability объявляется только
тогда, когда доказана выполнением. У него **три** исхода, и они не
схлопываются: доказано, отклонено (переменная не записывается) и *доказать не
удалось* — нет локального образа для монтирования, — тогда переменная
записывается, и вслух сообщается, что доказательство не выполнялось.

Запущенный из меню, он только **информирует**: каждый пункт меню bootstrap
намеренно запускается со stdin из `/dev/null`, так что спрашивать он не может.
Чтобы выбрать, запустите `node scripts/dev/consentir-base.mjs` в собственном
терминале.

```yaml
# docker/docker-compose.yml — em `api` E `engine`, já escrito
    volumes:
      - ${BRABO_PROJECTS_BASE:-brabo_projects_base}:${BRABO_PROJECTS_BASE:-/data/brabo-projects-base}
```

Оператор задаёт это **один раз** и перезапускает `api` + `engine`; ничего не
редактируется по проекту, никогда. До этого каждый смонтированный проект
требовал вручную написанной строки bind-mount в обоих сервисах и перезапуска —
который убивает каждый ход агента, сокет терминала и вызов LLM в полёте в
установке.

Монтирование выполняется по **идентичности** (`$X:$X`): тот же абсолютный путь
на хосте и внутри обоих контейнеров. Именно это сохраняет честной строку,
которую вводит пользователь и которую экран показывает обратно, и именно поэтому
`projectScopeRoot` (api) и `Engine.Actions.Workspace.workspace_dir/2` (engine) не
нуждаются в слое трансляции.

**Это не `PROJECT_WORKSPACES_HOST_DIR`, и они никогда не могут указывать на одну
папку.** Управляемый workspace именуется `workspace_dir_name` (UNIQUE), а
смонтированный проект именуется пользователем, так что `<base>/loja` и
container-проект, чья папка называется `loja`, столкнулись бы, и bootstrap
репозитория запустил бы `git init` внутри чужого проекта. В ADR есть два других
довода.

Когда переменная **не задана**, режим Mounted не предлагается — никогда не
предлагайте режим, который установка не может выполнить. А `pnpm dev`
**отказывается подниматься**, когда база пересекается с checkout Brabo в любом
направлении; эта проверка живёт в preflight, потому что он работает на хосте, а
api может сравнивать только с `process.cwd()` (`/workspace` внутри собственного
контейнера). См. [runbook](../runbook.md#projeto-no-modo-local).

## web

Web статический, обслуживается nginx. Он читает конфигурацию из **двух**
источников, и различие важно:

| источник | когда | как |
|---|---|---|
| `import.meta.env.VITE_*` | **build** | встраивается в bundle. Изменение требует пересборки |
| `window.__BRABO_CONFIG__` | **runtime** | отдаётся в `/config.js`, генерируемом entrypoint контейнера |

Поэтому один и тот же образ обслуживает все окружения: `/config.js`
переписывается при загрузке. `VITE_*` — fallback для разработки.

| переменная | для чего |
|---|---|
| `VITE_API_URL` | адрес api |
| `VITE_ENGINE_URL` | адрес engine (канал Phoenix) |
| `VITE_LOG_LEVEL` | уровень JSON-логгера браузера (умолчание `info`). В кластере решает ключ `WEB_LOG_LEVEL` из `brabo-config`, который entrypoint пишет в `/config.js` — `VITE_*` важна только в локальной сборке |
| `VITE_BRABO_VERSION` | версия, показываемая в подвале экранов auth (умолчание `dev`). **Единственная, задаваемая при сборке по выбору, а не из-за ограничения** — см. ниже |

Пустая страница после deploy — почти всегда `/config.js`, указывающий на
`localhost`, — smoke деплоя проверяет именно это.

### Почему версия не идёт через `/config.js`

URL принадлежат **окружению**: один образ должен говорить с api staging и с api
production, и для этого `/config.js` и существует (ADR 0024). Версия
принадлежит **артефакту** — образ `brabo-web:1.1.2` не должен быть способен
сообщить что-то иное. Если бы она приходила из `/config.js`, подвал стал бы
редактируемым полем вместо идентичности, а неверный ConfigMap заставил бы экран
лгать о том, какая сборка работает.

Весь путь, от commit до экрана: `release.yml` вычисляет
`versao=${TAG#v}` → передаёт как `VERSION` в `docker buildx bake` → цель
`web` в `docker-bake.hcl` превращает её в `VITE_BRABO_VERSION` →
`ARG`/`ENV` в `docker/web/Dockerfile.prod` открывает её для `pnpm build` → Vite
встраивает её в `import.meta.env` → `runtime-config.ts` её читает → `AuthLayout`
её показывает. Тот же `VERSION` питает `BRABO_VERSION` образа api
(ADR 0036).

## Резервное копирование

Потребляются образом резервного копирования, а не приложениями — как CronJob в
Kubernetes и как `docker compose run --rm backup …` в установке через compose.
Подробности в [Восстановлении](../runbook.md#restore); обоснование — в
[ADR 0152](../adr/0152-backup-de-volumes-contra-compose.md).

**Назначение — одно из двух, и выбор делается `BACKUP_DIR`.** Задайте её — и
резервная копия идёт на диск; оставьте пустой — и она идёт в S3, что и делает
CronJob Kubernetes. Пять переменных `BACKUP_S3_*` перестали быть безусловно
обязательными: это конфигурация *одного* назначения, а требование bucket до
возможности миграции требует инфраструктуры, которую установка на одной машине
никогда не просила.

| переменная | умолчание | примечание |
|---|---|---|
| `BACKUP_DIR` | — (S3) | **каталог** назначения. Задана ⇒ диск; пуста ⇒ S3. В сервисе compose умолчание `/backups` |
| `BRABO_BACKUP_HOST_DIR` | `backup_local` (именованный том) | путь хоста, монтируемый в `/backups`. Умолчание с именованным томом годится для проверки резервной копии; для миграции это **неверное** назначение, потому что `docker compose down -v` удаляет его вместе с тем, что он должен был сохранить |
| `BACKUP_S3_ENDPOINT` / `BACKUP_S3_BUCKET` | — | S3-совместимое назначение; обязательны только когда `BACKUP_DIR` пуста |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | — | учётные данные bucket |
| `BACKUP_KEEP_DAILY` | `7` | хранение по **количеству**, а не по возрасту |
| `BACKUP_KEEP_WEEKLY` | `4` | — |
| `GIT_REPOS_DIR` | `/data/git-repos` | bare-репозитории проектов provider `local`. Отсутствует ⇒ шаг **пропускается с сообщением** (CronJob Kubernetes не монтирует этот том) |
| `RESTORE_DB` | — | имя базы-назначения восстановления |
| `RESTORE_PREFIX` | `daily/` | `weekly/` для восстановления из еженедельной копии |
| `RESTORE_GIT_PREFIX` | `git-daily/` | `git-weekly/` для еженедельной копии bare-репозиториев |
| `RESTORE_GIT_FORCE` | — | `1` разрешает распаковку **поверх** существующих bare-репозиториев. Выключено по умолчанию: наложение двух состояний репозитория даёт смесь, на которую ни один `git` не пожалуется |
| `RESTORE_ADMIN_URL` | — | соединение с правом `CREATEDB`; в production отдельно от `DATABASE_URL` |

Четыре префикса, а не два: `daily/` и `weekly/` хранят дампы Postgres,
`git-daily/` и `git-weekly/` — архивы bare-репозиториев. Они разделены, потому
что хранение идёт по **количеству** — два вида архивов под одним префиксом
заставили бы «хранить 7» означать три с половиной резервные копии.

Эти не читаются нашим кодом — они принадлежат контейнеру `ollama` и находятся
здесь, потому что являются самой частой причиной странного поведения агента.
Таблица симптомов — в
[окружении инференса](../runbook.md#ambiente-de-inferencia).

| переменная | почему |
|---|---|

| `OLLAMA_MAX_LOADED_MODELS` | при высоком `OLLAMA_KEEP_ALIVE` модели накапливаются, пока не кончится память |
| `OLLAMA_KEEP_ALIVE` | как долго модель остаётся резидентной |

> образ в `docker/`, он закреплён как
> `ollama/ollama:0.40.3@sha256:…`

> поведение инференса, изменившееся между двумя `docker compose pull`, перестало
> быть возможной причиной: ничего не сдвинется, если кто-то не отредактирует
> digest. Повышение версии — [процедура из runbook](../runbook.md#subindo-imagem-de-terceiro),
> и `scripts/ci/imagens-pinadas.ts` отклоняет повышение, затрагивающее лишь
> часть мест, где встречается тег.

## Брокер контейнеров

Брокер ([ADR 0130](../adr/0130-broker-de-container.md)) — единственный процесс
продукта, говорящий с daemon Docker на сервере, и единственный сервис со
смонтированным `/var/run/docker.sock`. **Локально он поднимается с `pnpm dev`; в
production он под `profiles: ["container-broker"]`.** Два файла compose
расходятся намеренно ([ADR 0146](../adr/0146-base-consentida-no-bootstrap.md),
пункт 3) — не унифицируйте их.

Когда-то он был выключен по умолчанию в обоих под тем доводом, что его ещё
ничто не вызывало. Эта предпосылка умерла: у него четыре реальных вызывающих, и
[ADR 0144](../adr/0144-a-segunda-raiz-do-broker.md) заставил режим **Mounted**
поднимать контейнер через брокер — так что при выключенном profile стандартный
локальный режим заканчивался `BrokerIndisponivelError`. Асимметрию поддерживает
то, что сокет означает на каждой стороне: у запускающего `pnpm dev` он уже есть
(он запускает `docker compose`), тогда как в production это реальная граница
привилегий, и оператор — не разработчик.

Это меняет **когда** брокер работает, но никогда **что** он принимает: пять слоёв
сдерживания нетронуты, и он по-прежнему получает `projectId` плюс одну из пяти
операций, без параметра где-либо, куда можно было бы записать `privileged` или
свободный `-v`.

Подъём по умолчанию обнажил дефект, который прежде никогда не имел значения:
локальный образ устанавливал зависимости при START, а единственная сеть брокера
— `internal: true`, так что registry недостижим — контейнер умирал с
`getaddrinfo EAI_AGAIN registry.npmjs.org`, а без healthcheck `up --wait` всё
равно печатал `Healthy`. Теперь зависимости ставятся при BUILD, и у сервиса есть
healthcheck; сеть не тронута, и трогать её не следует. Эксплуатационные детали
— в [runbook](../runbook.md#broker-de-container).

В production поднимайте его явно:

```bash
docker compose -f docker/docker-compose.prod.yml \
  --profile container-broker up -d broker
```

| переменная | умолчание | когда ломается |
|---|---|---|
| `BROKER_URL` | `http://broker:8090` в compose **dev**; пусто в production и в установке (читается **api**) | Пусто — НОРМАЛЬНОЕ состояние: читающий наблюдаемое состояние контейнера говорит тогда «не наблюдалось», а не наследует зарегистрированное ([RN-486](../business-rules.md#rn-486)), и api отвечает `brokerConfigurado: false`, так что создание проекта предлагает только `runner` ([RN-573](../business-rules.md#rn-573)). Локально брокер поднимается по умолчанию, так что compose dev по умолчанию направляет её на сервис, который он поднимает ([RN-599](../business-rules.md#rn-599)) — значение в `.env` всё равно побеждает. Composes production и установки намеренно без умолчания: там брокер под profile, и включающий его записывает URL |
| `BROKER_PORT` | `8090` | Порт, на котором слушает брокер. Он НИЧЕГО не публикует на хосте — только api достигает его через сеть `internal: true` compose |
| `BRABO_SERVICE_TOKEN` 🔒 | `dev-service-token-change-me` в разработке | ТОТ ЖЕ секрет api ↔ engine, в том же заголовке. При `NODE_ENV=production` брокер отказывается стартовать, когда он пуст, когда это публичный литерал репозитория или в нём меньше 16 символов — правило RN-114, которое здесь охраняет процесс, говорящий с Docker хоста. `BRABO_SERVICE_TOKEN_PREVIOUS`, когда задан, проходит то же правило, кроме обязательности: обрезается, и в production брокер отказывается стартовать, если это публичный литерал или в нём меньше 16 символов ([RN-601](../business-rules/autenticacao.md#rn-601)) |
| `API_URL` | `http://api:3000` | Откуда брокер ЧИТАЕТ решение Архитектора. Он не получает спецификацию контейнера; он сам приходит за ней ([RN-485](../business-rules.md#rn-485)) |
| `PROJECT_WORKSPACES_HOST_ROOT` | — | Корень папок проектов **на ХОСТЕ**, а не внутри какого-либо контейнера. Без неё `start` отказывает, называя эту переменную, а остальные четыре операции продолжают работать. Не путайте с `PROJECT_WORKSPACES_ROOT`, это путь внутри контейнеров: `-v` разрешается DAEMON по файловой системе хоста, и путь изнутри api заставил бы его создать и смонтировать ПУСТУЮ папку |
| `DOCKER_GID` | `999` (compose) | gid группы `docker` хоста (`getent group docker \| cut -d: -f3`). Сокет `root:docker`, а брокер работает без root, поэтому compose использует `group_add`. Умолчание самое распространённое и неверно во многих дистрибутивах. С [ADR 0146](../adr/0146-base-consentida-no-bootstrap.md) это важно на КАЖДОЙ машине разработки, а не только там, где кто-то включил profile — ошибка не ломает загрузку, она ломает использование: каждая операция умирает с «permission denied» на сокете, и это проявляется только когда кто-то предлагает `container_start`. `pnpm dev` сообщает состояние этой переменной при каждом запуске ([RN-512](../business-rules.md#rn-512)) и говорит «не применимо» на машине без группы `docker`, вместо того чтобы её обвинять |

`PROJECT_WORKSPACES_HOST_ROOT` не может выводиться из управляемого тома Docker.
В compose **dev** она выводится из `PROJECT_WORKSPACES_HOST_DIR` (выше) —
поэтому, оставив ту незаданной, как в только что скопированном `.env.example`,
вы оставляете брокер без корня, а режим `container` без контейнера: стек
поднимается здоровым, а `container_start` заканчивается отказом. `pnpm dev`
сообщает об этом при каждом запуске, по образцу `DOCKER_GID`, и никогда не
отказывается подниматься ([RN-599](../business-rules.md#rn-599)). Он также
сообщает о случае с `~`: Compose раскрывает `~` в источнике bind-mount, который
используют `api`/`engine`, но НЕ в переменной, которую получает брокер
(измерено `docker compose config`), так что пишите путь УЖЕ РАСКРЫТЫМ. А явный
`PROJECT_WORKSPACES_HOST_ROOT`, отличающийся от папки, которую монтируют
`api`/`engine`, сообщается как расходящийся — контейнер получил бы папку, в
которую агенты никогда не писали. Замена управляемого тома папкой хоста не
переносит то, что уже лежит в томе `project_workspaces`: данные остаются там,
просто перестают быть тем, что видят `api` и `engine`.

`BRABO_PROJECTS_HOST_BASE` — ВТОРОЙ корень брокера — база проектов
**Mounted**, тоже на хосте
([ADR 0141](../adr/0141-base-unica-dos-projetos-montados.md),
[ADR 0144](../adr/0144-a-segunda-raiz-do-broker.md)). В отличие от верхнего, его
не нужно заполнять: compose выводит его из `BRABO_PROJECTS_BASE`, который уже по
определению путь хоста (это то, что `api` и `engine` монтируют по
идентичности). Задавайте его явно, только если daemon Docker достигает этой
папки по другому пути.

Именно он позволяет проекту **Mounted** иметь контейнер
([RN-503](../business-rules.md#rn-503)): api отправляет дискриминированный
локатор (`localizacao.tipo` — `gerenciada` или `montada`) плюс относительный
сегмент, и брокер разрешает его относительно соответствующего корня. Два корня
никогда не заменяют друг друга. Отсутствие этого заставляет `start` проекта
`mounted` отказать с **503**, НАЗЫВАЯ переменную, не трогая контейнер — падение
в `PROJECT_WORKSPACES_HOST_ROOT` смонтировало бы папку другого проекта, потому
что управляемый корень именуется `workspace_dir_name`, а база именуется
пользователем.

## Пользователь контейнеров dev (сборка) {#dev-container-user-build-time}

Тоже не читаются нашим кодом и даже не являются переменными окружения
*runtime*: это `build.args` Docker для трёх образов dev
(`docker/api/Dockerfile`, `docker/web/Dockerfile`, `docker/engine/Dockerfile`),
считываемые один раз при `docker compose build` и встраиваемые в `USER`, от
которого работает каждый контейнер. Они существуют, чтобы контейнеры работали с
**тем же UID/GID, что и ваш пользователь хоста**, а не root — всё, что пишется в
bind mount (`apps/api/dist`, workspace проекта в режиме выполнения `mounted`),
уже ваше, без последующего `sudo chown`.

| переменная | умолчание | почему |
|---|---|---|
| `DEV_UID` | `1000` | ваш `id -u`. НЕ читается из `${UID}` оболочки — в bash он только для чтения и по умолчанию не экспортируется в окружение, так что файл compose всегда видел бы его пустым |
| `DEV_GID` | `1000` | ваш `id -g`, то же рассуждение |

`1000`/`1000` совпадает с самой распространённой конфигурацией Linux одного
разработчика и с пользователем `node`, который уже есть в `node:26-alpine`
(базовый образ `api`/`web`) — когда ваша пара совпадает, Dockerfiles
переиспользуют этого пользователя, а не создают нового. Окружению, в котором
контейнеры уже работали от root до этого изменения, нужен разовый `chown`
именованных томов `node_modules`/`_build`/`deps`/`.mix`/`.hex` (или
`docker compose down -v`, чтобы дать им пересоздаться) — см. примечание в
[Первых шагах](../getting-started.md).

Composes production и установки отличаются: engine работает из образа
production под фиксированным пользователем `engine` (uid/gid `1000`, без
`DEV_UID`), с `read_only: true` и tmpfs в `/home/engine`. Этот tmpfs объявлен
`uid=1000,gid=1000,mode=0700` — это не переменная — потому что semgrep (gate
SecOps) пишет туда `~/.semgrep`; созданный от root, скан ничего не возвращает,
и gate одобряет без статического анализа
([RN-707](../business-rules.md#rn-707), runbook
[Gate SecOps застрял на «SAST не запускался»](../runbook.md#semgrep-do-gate)).

Оба образа engine закрепляют semgrep аргументом сборки `SEMGREP_VERSION`
(`1.171.0`, одинаковым в `docker/engine/Dockerfile` и `Dockerfile.prod`,
поддерживаемым одинаковым `scripts/ci/semgrep-do-engine.spec.ts`). Это аргумент
сборки, а не переменная runtime — ничего не идёт в `.env`. Без закрепления pip
взял 1.179.0, которая не публикует wheel `musllinux`: в образе Alpine пакет
приходил из sdist без `semgrep-core`, и каждый скан падал. Повышение версии —
это выбор релиза с wheel `musllinux` на PyPI и изменение обоих Dockerfiles в
одном PR.

Образы engine работают на **Elixir 1.20.4 / OTP 29.1.1** поверх Alpine 3.24
(builder `hexpm/elixir:1.20.4-erlang-29.1.1-alpine-3.24.2`, runtime
`alpine:3.24.2`, оба по digest — [ADR 0209](../adr/0209-engine-em-otp-29.md)).
OTP ниже 29.1 аварийно завершается при загрузке под musl 1.2.6 из Alpine 3.24
на хостах, чей CPU имеет AMX (`sys_sigaltstack(): Internal error`); не
понижайте OTP, не понизив musl. Ничего не идёт в `.env`.

Ни один из шести Dockerfiles не использует corepack (Node 25+ его больше не
несёт, AT-360): сборка устанавливает pnpm из tarball registry, сверяемого с
sha512, записанным в самом Dockerfile, — аргументы сборки `PNPM_VERSION`
(`11.3.0`, тот же, что `packageManager` в `package.json`, чтобы pnpm никогда не
пытался скачать другую версию в runtime) и `PNPM_SHA512`. Это аргументы сборки,
а не переменные runtime, и в `.env` задавать нечего: повышение pnpm — это
изменение `packageManager`, `PNPM_VERSION` в workflows и двух аргументов в шести
Dockerfiles в одном PR — см. раздел runbook об образе брокера.

## Переменные инструментов (не продукта)

Всё выше — **продукт**: то, что эксплуатирующий установку задаёт в `.env`
deploy. Далее — **инструменты**: читаются только CI и теми, кто разрабатывает
Brabo. Ничто из этого не принадлежит `.env` оператора, и это различие — причина,
по которой инвентарь ниже помечает каждый источник.

### Демонстрационные скрипты и seed — `apps/api/scripts/`

Они ведут реальных агентов против локального Ollama, поэтому получают **имя
модели** и **срок**. У всех есть умолчание, и ни один не обязателен.

| переменная | умолчание | что меняет |
|---|---|---|
| `DEMO_MODEL` | `qwen2.5-coder:7b` | модель, которую использует каждый демонстрационный скрипт, если одна из нижеследующих не перекрывает её для конкретной роли |
| `DEMO_QA_MODEL` | `DEMO_MODEL` | только агент QA, в демонстрациях gates PR — чтобы судить моделью, отличной от той, что написала код |
| `DEMO_WORKFLOWS_MODEL` | `DEMO_MODEL` | только агент Infra в демонстрации workflows GitHub |
| `DEMO_MODEL_LEVE` | `qwen2.5-coder:7b` | **лёгкая** модель Психолога (та, что использует дешёвый проход) |

### Браузерный E2E — `e2e/`

`e2e/` не входит в workspace ([ADR 0120](../adr/0120-e2e-de-navegador-contra-o-compose-de-producao.md)) и запускается против
**compose production**, поэтому его адреса — опубликованные порты, а не порты
dev. Учётные данные — от аккаунта seed, те же, что создаёт `docker/smoke.sh`.
Инвентарь обходит каждый `.ts` под `e2e/`, **включая specs Playwright** — там
spec и есть код, читающий окружение, а не модульный тест рядом с ним (AT-124).

| переменная | умолчание | что меняет |
|---|---|---|

| `E2E_WEB_URL` | `http://localhost:8088` | `baseURL`, который открывает Playwright, и origin, от которого зависит утверждение о CSRF |
