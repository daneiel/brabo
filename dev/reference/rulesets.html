    Rulesets do repositório

    Esta página é a fonte versionada da proteção. Aplicá-la no GitHub é um passo manual — o repositório não tem como proteger a si mesmo, e essa assimetria é intencional: quem afrouxa a proteção tem de ser uma pessoa, com registro.

    A política que estas regras aplicam está em Política de branches.

    Estado atual: gh api repos/daneiel/brabo/rulesets devolve 0. Nada aplicado ainda. Até lá, tudo aqui é intenção declarada, não proteção real.

    Pré-requisito: as três branches precisam existir

    A escada tem três degraus, e um ruleset não mira o que não existe.

    git fetch origin
git push origin origin/dev:refs/heads/qa

    dev e main já existem. qa nasce de dev — a escada começa vazia e é preenchida pelas promoções.

    A branch rc foi removida da escada. Se ela ainda existir no remoto de um clone antigo, apague-a: git push origin --delete rc. Uma branch permanente que não está na escada é um convite para uma PR mirar um degrau que não existe mais.

    Ruleset 1 — as três branches permanentes

    Nome: permanentes Enforcement: Active Alvo: Branch → Include by pattern, três entradas: dev, qa, main

    Um ruleset para as três, não três rulesets: a exigência é idêntica em todas. O que difere entre degraus é quem aprova, e isso é decidido pelo approval-ladder a partir do destino, não pela proteção.

    Regras a marcar

    regra valor por quê
    Restrict deletions ✅ apagar a main por acidente é irreversível pela interface
    Block force pushes ✅ force-push numa branch permanente reescreve o que já foi promovido; a tag do degrau acabaria apontando para um commit inexistente
    Require a pull request before merging ✅ esta é a regra central: nenhuma mudança entra sem PR
    ↳ Required approvals 0 quem conta é o approval-ladder, que conhece o modo e o destino. O número nativo do GitHub não distingue dev de main
    ↳ Dismiss stale approvals on push ✅ aprovação de um commit antigo não conta — o que foi aprovado não é o que vai ser mergeado
    ↳ Require review from Code Owners ✅ o CODEOWNERS põe o dono como revisor de tudo
    Require status checks to pass ✅ ver a lista abaixo
    ↳ Require branches to be up to date ❌ forçaria um rebase a cada merge na dev; a CI já roda sobre o merge commit
    Block merge queue — não usado

    Required approvals = 0 não é afrouxamento. O GitHub só sabe contar; ele não sabe que a main exige PO + gestão e a dev exige um dev, nem que no modo solo a PR do próprio dono passa sem revisão. Pôr 1 aqui quebraria o modo solo: o dono não consegue aprovar a própria PR pela interface, e a PR ficaria presa para sempre. A exigência real mora no approval-ladder, que é check obrigatório — e check obrigatório não se burla.

    pull_request_target exige que o workflow esteja na branch DEFAULT. Estar na branch de base da PR não basta. Isso foi medido, não suposto: com pull_request_target, o pr-police teve zero execuções, enquanto o approval-ladder e o docs-check — que usam pull_request — rodaram normalmente a partir do mesmo commit. Como a default é a main e ela só avança pela escada que o próprio check guarda, o gatilho seria um problema de ovo e galinha. Os dois usam pull_request.

    De onde o GitHub lê cada workflow — três famílias, três respostas. Isso custou três descobertas separadas durante esta fase, e não está óbvio em lugar nenhum:

    gatilho lê o workflow de consequência aqui
    pull_request, push a branch do evento funciona desde a primeira PR
    pull_request_target a branch default não rodava: a main está atrás
    workflow_dispatch a branch default nem aparece na lista de workflows

    Os dois últimos criam um problema de ovo e galinha quando a branch default está desatualizada: o workflow que faz a esteira andar precisa já estar na main para poder ser disparado. O contorno foi rodar o script promote à mão na primeira promoção — o mesmo script, só o gatilho manual. Depois que a main recebe os workflows, o dispatch funciona para sempre.

    Um check obrigatório que nunca roda trava a PR para sempre. É por isso que o gatilho do ci.yml cobre as três branches permanentes — antes da FASE 6 ele só disparava em PRs para a dev, e exigir estes checks numa promoção dev→qa produziria uma PR eternamente pendente. O gatilho push foi removido: com pull_request cobrindo tudo, ele só duplicava execuções. Ao acrescentar um job novo à CI, ou ele entra nesta lista, ou fica de fora de propósito e alguém escreve por quê.

    E um check obrigatório que não REEXECUTA fica colado num veredito velho. Este é o outro lado da lição acima, e custou a uma PR uma falha equivocada.

    Os padrões de pull_request são opened, reopened e synchronize — nenhum deles cobre mudar a base. E mudar a base é rotina: o GitHub abre a PR contra a branch default, e o autor depois a corrige para a dev. Na PR #71, Drift, gerados e build rodou nos primeiros meia dúzia de segundos, contra origin/main...HEAD, e falhou em sete arquivos que já tinham sido revisados e mergeados na #70. O redirecionamento não o reexecutou; o vermelho ficou.

    o check depende de… precisa de edited? quem
    só do HEAD não ci.yml — testa o commit, e a base não muda o resultado (exceto a decisão de pular do job de imagens desde a AT-303 — ver "Consequência para o critério de edited" acima)
    da BASE, ou do CORPO da PR sim pr-police, approval-ladder, promotion-check, backmerge-gate, docs-check

Como não é obrigatório, o job pode ser pulado sem deixar a PR pendente — e ele é pulado em toda PR aberta por um bot. A action se recusa a rodar com ator não humano ("Workflow initiated by non-human actor: <name> (type: Bot)"), então sem esse if o check falha toda vez. A condição agora testa o type do autor, espelhando ehAutorBot (scripts/ci/pr-police.ts), com o sufixo [bot] do login como rede de segurança — o GitHub não permite [ num login humano, então ele não se forja.

Mesmo permitindo o ator, a revisão não teria credencial, e um check que falha por falta de segredo é pior que um pulado: ele se lê como defeito de código.

    O que uma PR entre branches permanentes não consegue cumprir

    Drift, gerados e build é obrigatório, então roda em toda PR — mas o passo de drift se declara inaplicável quando o head é uma branch permanente do próprio repositório (promoção dev→qa, qa→main; back-merge main→qa, qa→dev). Os outros passos do job — docmap, gerados e build do site — continuam rodando: só dependem do HEAD, e valem em qualquer degrau.

    O motivo é o mesmo do claude-review, com um agravante. Redundância, primeiro: uma PR entre branches permanentes não tem autoria, ela empacota commits cujo drift já foi cobrado na PR para a dev, arquivo por arquivo. Cobrar de novo é cobrar a mesma dívida em cada degrau. Mas, ao contrário da revisão por LLM, aqui a exigência era impossível de cumprir — e foi o que reprovou a #72, a promoção do ciclo v1.0.1, por arquivos de docker/** que vieram da #70:

    a saída aparente por que ela não existe
    atualizar a doc na PR de promoção o promotion-check exige um intervalo limpo — o head tem de ser a ponta da origem. Commitar ali reprova o outro check obrigatório
    repetir o docs-not-needed: da PR original o corpo da PR de promoção é gerado pelo promote; a justificativa da #70 não atravessa o degrau
    pôr o rótulo em toda promoção é ensinar a usar a válvula de escape por reflexo, até ela não significar mais nada — o contrário do que o .docmap.yml pede

    O filtro mora dentro do passo, não num if: no job, seguindo o mesmo princípio que o promotion-check registra: um check obrigatório indexado por sha que não roda deixa a PR pendente para sempre. O passo roda, decide que não se aplica e escreve isso no resumo — em vez de sumir.

    Um head chamado main vindo de um fork não é promoção. É a branch de trabalho de um terceiro, e passa pelo drift como qualquer outra. É por isso que a condição casa o nome e exige o mesmo repositório — a mesma ressalva que o pr-police aplica ao classificar a família da PR.

    Bypass

    quem modo para quê
    o ator do BRABO_BOT_TOKEN Always escrever .release/gate.json na main

    Nenhuma pessoa tem bypass — nem o dono. Este é do bot, e existe por um motivo sem contorno: o gate trava as branches, e uma PR para abrir a trava seria bloqueada pelo próprio gate. O commit fica no git log, com data e conteúdo, e o tag-release o reconhece pelo que ele toca (.release/ e nada mais), não por quem ele diz ser.

    Aviso sobre o alcance do bypass. Os rulesets do GitHub concedem bypass ao ator, não a um caminho: quem consegue escrever .release/gate.json na main consegue, tecnicamente, escrever qualquer coisa. Não há como restringir por caminho na interface. O que de fato limita é o workflow — ele só escreve aquele arquivo — e o histórico, onde qualquer outro commit direto salta aos olhos na hora. Registrado pelo que é: uma limitação da ferramenta, não uma decisão.

    O segredo BRABO_BOT_TOKEN

    PAT clássico com os escopos repo + workflow, em Settings → Secrets and variables → Actions:

    gh secret set BRABO_BOT_TOKEN --body '<token>'

    Não é conveniência. Duas coisas dependem dele, e as duas falham em silêncio sem ele:

    o quê por quê
    a tag disparar o Release uma tag criada com GITHUB_TOKEN não dispara workflow
    as PRs de back-merge nascerem com checks uma PR aberta com GITHUB_TOKEN não dispara workflow

    É a regra do GitHub contra recursão, e ela já cobrou o preço: a Release da v0.2.0 nunca foi publicada por causa dela. O segundo caso é pior — uma PR de back-merge sem check nunca ficaria verde, e a cadeia travaria para sempre. É por isso que o job do gate falha alto quando o segredo não existe, em vez de seguir e deixar o repositório num beco sem saída.

    O escopo workflow não é exagero: as PRs de back-merge levam a branch inteira, e ela pode conter uma mudança em .github/workflows/**. Sem esse escopo o push é recusado exatamente no caso que mais importa — propagar uma correção de CI.

    Estado atual: configurado e exercitado. Na v1.1.1 a esteira fechou sozinha pela primeira vez — o tag-release pulou o passo de aviso, empurrou a tag com o PAT, e isso disparou o release.yml, que publicou a Release. Uma tag empurrada com GITHUB_TOKEN não o dispararia; esse disparo é a prova de que o token é válido e tem escopo de push.

    Seis tags seguem órfãs — v0.2.0, v0.3.0, v0.3.1, v1.0.0, v1.0.1 e v1.1.0 — do período em que o segredo não existia. O PAT não as recupera: ele só vale para tags novas. Para elas, o procedimento está abaixo.

    Republicando uma tag que ficou órfã

    O release.yml tem workflow_dispatch com uma entrada de tag, e ele existe por causa das seis acima. Só o gatilho push: tags tornaria a falha irreversível: republicar exigiria apagar e recriar a tag, isto é, reescrever o registro para corrigir o efeito dele.

    gh workflow run release.yml -f tag=v1.1.0

    Três guardas, e cada uma existe por causa de um modo de falha concreto:

    guarda contra o quê
    só o OWNER_HANDLE pode dispará-lo (modo solo) mesma restrição do promote; o gatilho de push não passa por aqui, porque ali quem autorizou foi a tag
    a entrada tem de casar ^v[0-9]+\.[0-9]+\.[0-9]+$ workflow_dispatch aceita texto livre. Sem isso, -qa.1 publicaria uma Release de algo que ninguém validou como final
    recusa se a Release já existe uma nota publicada é um registro; sobrescrevê-la em silêncio apagaria o que alguém já leu ou linkou

    E o checkout é feito na tag, não na ref do evento. Num dispatch, github.ref_name é a branch default — sem esse cuidado, republicar geraria uma Release chamada main, com o changelog da main, sem erro nenhum.

    O dispatch só funciona depois que isto chega à main. É o problema de ovo e galinha da tabela de gatilhos acima: workflow_dispatch lê o workflow da branch default. Enquanto a mudança está só na dev, a entrada nem aparece.

    Ruleset 2 — tags de versão

    Nome: tags-de-release Enforcement: Active Alvo: Tag → Include by pattern → v*

    regra valor
    Restrict creations ✅
    Restrict updates ✅
    Restrict deletions ✅

    O padrão v* cobre as três formas que a esteira cria: -dev.N, -qa.N e a final. Só o tag-release pode criá-las.

    O que uma tag final roda, e por que nada disso é check obrigatório. Empurrar vX.Y.Z dispara release.yml, build-runner-binaries.yml e publish-runner.yml em paralelo. Os jobs deles nunca aparecem na tabela de checks obrigatórios acima, e isso é estrutural e não omissão: checks obrigatórios seguram uma pull request, e quando uma tag existe a PR já foi mergeada. O que segura a tag é o ruleset — só o tag-release a cria, e só depois da esteira ao fim da qual ele roda.

    Uma tag final também dispara o install-e2e.yml, que exercita o install.sh publicado numa máquina limpa — que é o que um runner efêmero das Actions é. Desde a RN-549 ele vai até o fim: os cinco elos que fecham a instalação, o agente local de pé e esperando, e o primeiro projeto runner sendo pego. Ele não roda em pull_request, e o motivo é o mesmo que mantém a assinatura fora das PRs: o manifesto assinado só existe depois de uma tag final, e fazer o script rodar ali seria dar a ele uma porta para pular a verificação (RN-534). A consequência é dita em vez de escondida — a PR que escreve uma mudança neste workflow não o roda —, e o que roda em toda PR é scripts/dev/install-e2e.spec.ts, que reprova se o gatilho ganhar pull_request ou se uma frase que o workflow procura com grep deixar de existir no install.sh.

    Desde o ADR 0149, o build-runner-binaries.yml tem dois jobs em vez de um: a matriz build (quatro alvos, fail-fast: false) e um job checksums. Desde a RN-565 o segundo não tem needs: na matriz — ele espera, com teto, pelos assets da Release e não pelo job mais lento —, então um alvo que falhou no build, ou nunca ganhou runner, não nega aos outros um manifesto assinado. Ele nomeia no log quais alvos o manifesto não cobre, porque um checksums.txt que lista três e se cala sobre o quarto é pior que nenhum: quem verifica os três conclui que verificou a release.

    O alvo darwin-x64 (Mac Intel) saiu da matriz no ADR 0174, e a causa é medida (AT-065, 2026-09-13): o rótulo macos-13 dele apontava para uma imagem que o GitHub aposentou em dezembro de 2025, e o substituto Intel, macos-15-intel, é agendado em segundos e constrói, mas reprova o --self-test-pty sob o Bun (o onData do node-pty nunca dispara — oven-sh/bun#25822, aberto). A mesma prova passa sob o Node, então um Mac Intel instala o runner com npm install -g @brabo/runner. Uma execução do workflow com a entrada tag vazia é um ensaio: constrói e faz o smoke sem anexar nada, e foi assim que isso foi medido sem cortar uma tag.

    Bypass

    quem modo
    o app/bot que roda o workflow de release Always

    Esta é a exceção de push que a política prevê: uma versão nasce de um workflow, nunca à mão. Uma tag criada à mão não passa pela verificação de que a tag final aponta para o mesmo commit do último -qa.N, e é exatamente essa verificação que impede publicar algo diferente do que foi validado.

    Como aplicar

    Interface: Settings → Rules → Rulesets → New ruleset.

    Pela API, se preferir versionar o comando:

    gh api -X POST repos/daneiel/brabo/rulesets --input ruleset-permanentes.json
gh api repos/daneiel/brabo/rulesets --jq '.[] | "\(.name): \(.enforcement)"'

    TODO(humano): os dois arquivos .json de payload não são versionados aqui porque a API de rulesets exige repository_id e ids de app que variam por instalação — um arquivo fixo seria copiado errado. Se quiser versioná-los, gere com gh api repos/daneiel/brabo/rulesets/<id> > docs/reference/... depois de aplicar pela interface, e este documento passará a apontar para eles.

    Settings → Pages: a fonte é a branch gh-pages

    Aplicação manual, pelo mesmo motivo dos rulesets: o repositório versiona a fonte, o GitHub recebe a aplicação.

    Settings → Pages → Build and deployment → Source: Deploy from a branch, com a branch gh-pages e a pasta / (root).

    Já aplicado. gh api repos/daneiel/brabo/pages devolve "build_type": "legacy" com source.branch: "gh-pages", e os três degraus respondem no ar.

    O passo intermediário vale o registro, porque confunde: enquanto o build_type era "workflow", o docs-deploy.yml commitava na gh-pages e o Pages não servia nada dali — a publicação ficava no repositório sem ir ao ar, com o site antigo ainda respondendo a partir do último artefato do actions/deploy-pages. Nada na CI fica vermelho nesse estado.

    Por que a troca é obrigatória e não preferência: o actions/deploy-pages publica um artefato como o site inteiro e não sabe atualizar parte de uma árvore, o que é incompatível com um subdiretório por degrau. O desenho completo, as alternativas descartadas e a exceção de push que isso abre estão no ADR 0034.

    branch URL indexado
    — (índice dos três) https://daneiel.github.io/brabo/ ❌ noindex, follow
    main https://daneiel.github.io/brabo/prd/ ✅
    dev https://daneiel.github.io/brabo/dev/ ❌ noIndex

    Os três ficaram simétricos no ADR 0071, que também explica a raiz gerada e o 404.html que encaminha links antigos ao degrau estável. O ADR 0073 separou o CAMINHO da BRANCH: a main publica em /prd/, porque o endereço nomeia o ambiente para quem lê. O 404.html passou a reescrever /brabo/main/<algo> para /brabo/prd/<algo> — o diretório antigo sai da árvore, e keep_files: false o remove.

    A configuração do Pages não muda com nenhum dos dois — a fonte continua sendo a branch gh-pages na pasta / (root); o que mudou é o conteúdo que o workflow monta antes de empurrar. E prd não é uma branch: não está em ruleset nenhum, não existe no git, e é só o nome de um diretório na gh-pages.

    A gh-pages NÃO entra no ruleset das branches permanentes. Ela não é permanente, e o bot precisa empurrar nela — incluí-la travaria a própria publicação. É também por isso que o GITHUB_TOKEN basta ali, sem bypass e sem BRABO_BOT_TOKEN.

    E ela fica fora do escopo do Gitleaks, por um motivo que só apareceu depois. O gitleaks detect varre todo commit alcançável, não só o histórico do HEAD — e fetch-depth: 0 traz todas as refs. Assim que a gh-pages nasceu, o site construído entrou na varredura: 112 achados generic-api-key num único commit, todos em dev/assets/js/*.js, que são nomes de arquivo de avatar dentro de um bundle minificado com entropia alta demais para a regra. Isso reprovou a PR de promoção #78, a primeira varrida depois da estreia dela.

    O ci.yml agora apaga refs/remotes/origin/gh-pages antes de varrer. Não por uma allowlist de caminho no .gitleaks.toml: ela valeria para todo commit, e um dev/ que um dia aparecesse no código-fonte deixaria de ser varrido em silêncio. Excluir a ref exclui exatamente os commits que não são fonte.

    Medido com o gitleaks 8.30.1, a versão da CI: 133 commits e 112 achados antes, 132 e nenhum depois — e um PAT do GitHub com entropia real plantado em apps/api/src/ continua sendo detectado, o que prova que não se abriu um buraco.

    Os rótulos de família precisam existir

    O pr-police aplica um dos quatro rótulos, e gh pr edit --add-label falha se o rótulo não existe — o que deixaria a PR sem classificação, em silêncio.

    gh label create trabalho        --color 0E8A16 --description "Work PR: taxonomy prefix for dev"
gh label create promocao        --color 1D76DB --description "Promotion between adjacent rungs, going up"
gh label create retropropagacao --color 5319E7 --description "Back-propagation between adjacent rungs, going down"
gh label create correcao-alta   --color D93F0B --description "hotfix: a fix that's born high on the ladder"

    Sem || true de propósito: se o comando falhar, você precisa ver.

    Conferir que está de pé

    # do the rulesets exist and are they active?
gh api repos/daneiel/brabo/rulesets --jq '.[] | "\(.name): \(.enforcement)"'

# does the protection respond? (should be REJECTED)
git push origin HEAD:dev

    O segundo comando é o teste que importa. Um ruleset configurado mas não conferido é indistinguível de um ruleset ausente — e a diferença só aparece no dia em que alguém empurra direto na main.
