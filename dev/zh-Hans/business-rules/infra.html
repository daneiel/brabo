    RN-433 — 终端 socket 在超时后放弃，ENGINE_PUBLIC_URL 的默认值可由浏览器访问，端点不重复路径

    三个叠加的缺陷。前两个是在调查症状时发现的；第三个只在修正前两个之后才出现——没有它们，浏览器永远到达不了 engine，也就无法揭示底下的路径缺陷。只修正一个会让其他的依然存在：

    1. ENGINE_PUBLIC_URL（RN-419）在 docker/docker-compose.yml 中从来没有任何默认值——只有 ENGINE_URL（http://engine:4000，一个只在 Compose 网络内部解析的主机名）。代码的后备（process.env.ENGINE_PUBLIC_URL ?? process.env.ENGINE_URL ?? …， request-runner-ticket.use-case.ts）悄悄地落到错误的值上，浏览器试图对一个它永远无法解析的主机名打开 WebSocket。docker/docker-compose.yml 在 api 服务中加入了 ENGINE_PUBLIC_URL: ${ENGINE_PUBLIC_URL:-http://localhost:4000}——与 VITE_ENGINE_URL 在 web 服务中已使用的相同默认值，原因也相同。
    2. 即使 URL 正确，一个永远打不开的传输（engine 宕机、防火墙、未来错误的重新配置）也没有任何上限： apps/web/src/lib/terminal-channel.ts 从未向 Socket 传递 reconnectAfterMs，于是 phoenix.js 落入它的默认退避，自己永远尝试重连——模块自己的 docblock 早已声明“没有自动重连”的意图（与 session-channel.ts/RN-108 相同的标准），但实际上从未兑现。没有 onError/onClose 调用 handlers.onErro，TerminalPanel 就卡在 'carregando'（RN-088——每个屏幕都区分加载中/错误/空——被悄悄违反）。修正方法是让 reconnectAfterMs 返回一个几乎永远不会触发的值（24 小时，与 session-channel.ts 相同的模式），并设置一个自己的 8 秒超时 （TIMEOUT_CONEXAO_MS）：如果在此之前 onOpen 没有触发，模块就以可操作的消息调用 handlers.onErro 并断开连接。
    3. 真正阻止连接的缺陷，被上面两个掩盖了：terminal-channel.ts 把 '/runner/websocket' 拼接到一个 api 已经返回完整的 engineWsUrl 上——ws://host:porta/runner （engineWsUrlPublico()）——而 phoenix.js 的 Socket 自己还会在构造函数中自行追加 /websocket （this.endPoint = ${endPoint}/websocket）。结果以 GET /runner/runner/websocket/websocket 打到 engine，被 Phoenix.Router.NoRouteError 拒绝——在这次修正的端到端验证期间于 engine 日志（docker logs brabo-engine-1）中得到确认。apps/runner/src/channel.ts（CLI 一侧）早已做对了——把 engineWsUrl 原样传给 Socket，不做改动——而 terminal-channel.ts 的测试从未发现，因为 getTerminalTicket 的模拟使用的 engineWsUrl（http://engine.local，没有 /runner）不反映 api 的真实契约；一并修正。 修复：terminal-channel.ts 改为直接使用 engineWsUrl（只做防御性的 .replace(/^http/, 'ws')），不拼接任何路径。

    针对 exp001 端到端验证（runner 模式，没有真实的 brabo-runner 连接）：修正之前，标签页永远转圈；修正之后，engine 日志显示 CONNECTED TO EngineWeb.RunnerSocket → JOINED terminal:<projectId> → pty_resize descartado — sem runner conectado，屏幕在不到 1 秒内显示带有 brabo-runner 命令的 RunnerOnboardingPanel——从不是第 2 项的 8 秒超时，后者作为 engine 真正宕机情况下的安全网保留。

    • 位置： docker/docker-compose.yml、.env.example、 apps/web/src/lib/terminal-channel.ts
    • 测试： apps/web/src/lib/terminal-channel.test.ts（永不打开的 socket 在超时内调用 onErro，没有 phoenix 的自动重连；模拟的 engineWsUrl 已修正以反映真实契约——已带 /runner，没有 /websocket——正常路径的断言改为要求 Socket 使用的 URL 与 ticket 的 engineWsUrl 相同，没有拼接）
    • ADR： 无——缺陷修正，恢复 ADR 0103/0104 和模块自己的 docblock 早已声明为意图的行为
    • 来源： 在 runner 模式下手动测试新项目时发现；第 3 项只在浏览器中针对真实 engine 端到端验证第 1/2 项的修正时才出现

    RN-500 构建了基准目录，并说明了它缺失时该做什么—— projectsBase: null，不提供“挂载文件夹”模式。缺少的是有人请求配置它：产品中没有任何东西这样做，结果是一个就绪的模式对安装者来说无法到达。

    同意步骤位于 pnpm bootstrap（Docker › Base de projetos），建议 $HOME/projetos-brabo 并接受输入的其他路径。这个名称不是偏好：.env.example 已经用 ~/brabo-projetos 作为 PROJECT_WORKSPACES_HOST_DIR（产品管理的根目录）的示例，给两个变量建议同一个名称就是走进 ADR 0141 拒绝的冲突——<base>/loja 会落在与一个 workspace_dir_name 也是 loja 的 container 项目相同的物理文件夹中，引导程序会在另一个项目内执行 git init。

    名称只是规避；保护靠机制。 validarBase 拒绝任何在两个方向上与 Brabo 的检出（RN-500 已有的守卫）或 PROJECT_WORKSPACES_HOST_DIR（新规则）重叠的候选，还拒绝 ~、相对路径和根目录。拒绝适用于输入的路径，而不只是默认值；一个选得好的默认值只是避免让拒绝成为用户看到的第一件事。

    Docker Desktop 的共享通过挂载来证明，从不从 settings.json 读取。 那个文件没有文档，在不同版本之间以及 macOS 与 Windows 之间都会变化，并且描述的是用户配置了什么——而不是守护进程会做什么。这与 ADR 0041/0042 的“capability 只有在被执行证明时才声明”是同一标准，应用于宿主机。证明是一个哨兵，而不是干巴巴的 ls：空文件夹和未共享的文件夹会产生同样的空列表，所以脚本写入一个文件并询问容器是否看到它。只在 macOS 和 Windows（process.platform）上；在 Linux 上没有共享列表，检查是存在性和可写性。这是产品的第二个平台守卫，与第一个（runner 中的 validarDirDentroDoHomeNoLinux）对称：每个都只在限制有意义的地方进行限制。

    证明有三种结果，它们不折叠：已证明；被否决（变量不被写入，拒绝点名路径以及在哪里添加它）；以及无法证明——没有本地 Docker 镜像可用于挂载——它会写入变量并大声说出证明没有运行，附上之后运行它的命令。“我没能看”变成“一切都好”，正是一个未共享的基准会以容器带着空文件夹启动的形式到达用户的方式，远离做出选择的屏幕。

    没有 TTY 时，该步骤报告而什么都不做。 bootstrap.sh 的菜单项以来自 /dev/null 的 stdin 运行——有意如此，否则任何读取 stdin 的东西都会抢走用户的方向键——因此从那里脚本只能报告，输出会说出提问的命令。这与 perguntarUsoDoOllama 的设计相同，它在没有终端时应用默认值并提示，而不是卡住。一个在 CI 管道中自行“同意”的同意脚本是对这个词的否定。出于同样的原因，preflight.mjs 报告基准目录的状态而从不提问：答案是某人磁盘上的一个路径，不存在可以静默应用的默认值。

    mkdir -p 只在接受和校验之后才发生——从一个尚未通过拒绝检查的路径创建文件夹，就是在进程能到达的任何地方创建文件夹。已存在的值未经确认从不被覆盖。

    broker 在本地 compose 中默认启动（RN-512）

    RN-512 — broker 只在本地 compose 中离开 profiles，DOCKER_GID 开始在 preflight 中被报告

    broker 诞生于 profiles: ["container-broker"] 之下，理由是 ADR 0130 自己写的：“dar acesso ao Docker do host a um processo que nada chama ainda seria uma mudança de postura para toda máquina de desenvolvimento, em troca de nada”。两半都已失效。“没有东西调用它”是假的，自 ADR 0133/0134/0136 起——broker 有四个真实调用方。而当 ADR 0144 让 mounted 经由 broker 启动容器、ADR 0146 让 mounted 成为本地默认值时，“换来的什么都没有”就不再描述这种交换：profile 关闭时，默认模式以 BrokerIndisponivelError 结束。

    于是它在 docker/docker-compose.yml 中离开了 profiles——只在那里。在 docker/docker-compose.prod.yml 中 profile 保留，两个文件开始有意地分歧。

    这种不对称在于 socket 在两边意味着什么。 运行 pnpm dev 的人已经拥有 Docker 的 socket——他在运行 docker compose，针对的是自己宿主机的守护进程——所以 broker 获得它并不授予运维人员本就没有的任何东西。边际攻击面是 broker 自己的 HTTP，它不发布端口，位于只有 api 能到达的 internal: true 网络中，并以恒定时间比较 BRABO_SERVICE_TOKEN。在生产中计算恰恰相反：socket 是真正的权限边界，运维人员不是开发者，而这个阶段的任何东西都不改变生产安装的默认模式。

    五层约束不被触碰。 这改变的是 broker 何时运行，从不改变它接受什么：它继续接收 projectId 和五种操作之一，继续去 api 读取 Arquiteto 的决定，继续没有任何可以写入 privileged、cap_add、 network: host 或自由 -v 的参数。约束从来就不是 profile。

    环境后果，以及为什么它获得了报告。 DOCKER_GID 不再只对有意开启 profile 的人重要——按定义那个人是在留意它的——而是对任何运行 pnpm dev 的人都有效。socket 在宿主机上是 root:docker，而 broker 的进程以非 root 运行；compose 的 group_add 赋予它该组，默认值 999 最常见，但在好几个发行版中是错的。弄错不会让启动失败——broker 正常启动——却会让使用失败：每个操作都在 socket 上以 permission denied 死掉，症状在很久之后、有人提议 container_start 时才出现。因此 preflight.mjs 开始在每次 pnpm dev 时报告状态。

    报告有三种结果，它们不折叠：一致；不一致（附上有效值的来源——configurado × default——因为两者需要不同的指示）；以及不适用，当机器没有 docker 组时。第三种既不是错误也不是“没能查看”：在 macOS 和 Windows 上 Docker Desktop 不使用 unix 组，而在 rootless Docker 中 socket 属于用户自己。把缺失当作不一致，会指控一半的机器有它们并不存在的缺陷——与 baseSobrepoeOCheckout 对未知检出返回 false 的谨慎相同。并且它只报告，从不阻断：pnpm dev 照样启动。

    离开 profiles 还不够，缺陷只在第一次默认启动时才出现。 开发镜像在构建时以 root 用 corepack 准备 pnpm，却以 uid 1000 运行，后者读不了那个缓存；没有缓存，corepack 会在启动时尝试下载 pnpm，而 broker 唯一的网络是 internal: true——尝试以 getaddrinfo EAI_AGAIN registry.npmjs.org 失败，容器在启动五秒后以 1 退出。该服务也没有 healthcheck，所以 up --wait 打印 Healthy，完全重置在进程已死的情况下宣布“重置完成”。只要服务位于 profile 之下，这就从未出现：有意开启它的人本来就在留意。修正把 registry 从运行时路径中移除——pnpm install 迁移到构建步骤，COREPACK_HOME 改为一个属于运行时 uid 的目录——并且不打开网络，那是上面五层中的第一层。由于三个 node_modules 是挂载在镜像安装内容之上的命名卷，而 Docker 只为空卷播种，docker/broker/entrypoint.sh 会把这三个与保存在 /workspace 之外的一份副本进行对账，该副本带有构建时 pnpm-lock.yaml 的 sha256 标记——同一个标记与目录树中的 lockfile 比较时，会提示镜像已过时而不拒绝启动。生产 compose 没有这个问题：Dockerfile.prod 早已在构建阶段安装，从最终镜像中删除了 corepack，并且已经有 HEALTHCHECK。自 AT-360 起没有镜像再使用 corepack（Node 25+ 不再自带它）：pnpm 从 registry 的 tarball 安装，对照记录在 Dockerfile 中的 sha512 校验，放到 /usr/local/bin，COREPACK_HOME 从 dev 的 broker 中移除——版本与 packageManager 相同，启动时就没有可读的缓存，也没有要尝试的下载（在 --network none 下测量）。

    • 位置： docker/docker-compose.yml（broker 服务，没有 profiles，带 healthcheck）和 docker/docker-compose.prod.yml（带 profiles，以及阻止统一两者的注释）；docker/broker/Dockerfile（按 sha512 固定的 pnpm、构建时的 pnpm install 以及 /opt/broker-deps 中的副本）； docker/broker/entrypoint.sh（三个卷的对账和 lockfile 提示）；scripts/dev/docker-gid.mjs（avaliarDockerGid、 mensagemDoDockerGid、GID_PADRAO_DO_COMPOSE——纯决策）； scripts/dev/preflight.mjs（relatarDockerGid、gidDoGrupoDocker）
    • 测试： scripts/dev/docker-gid.spec.ts——正常路径、两种不一致（缺少默认值和错误值）、没有 docker 组时的“不适用”，以及恰好正确的默认值

    FASE 29 — 一行安装：为所发布的东西签名

    RN-527 — 安装从「自己的」compose 启动，按所选镜像，并在说已安装之前核对健康状况

    由 RN-575 修订（ADR 0162）： broker 服务开始存在于这个 compose 中，在 profile container-broker 下默认关闭，只有经同意才由安装程序开启；必需的镜像是「五个」。本规则的其余部分照常有效。

    docker/docker-compose.install.yml 是在安装者机器上运行的东西，它不是 docker-compose.prod.yml。三处差异，各有原因：

    • 五个镜像来自必需变量（${BRABO_API_IMAGE:?…}），没有默认值。有默认值的话，缺失的变量会用一个没人选择的镜像启动半个栈，错误会表现为奇怪的行为而不是拒绝；
    • 任何地方都没有 build: 块：这个文件不构建，这正是它的要点；
    • 这里不存在 broker 服务，因为它的镜像没有发布（docker-bake.hcl 有四个目标）。已声明的后果：使用 --source=ghcr 时，mounted 项目不启动容器（ADR 0150，决定 7）。

    docker-compose.prod.yml 保持不变——它自称是校验用的 compose，是 docker/smoke.sh 有意在本地构建时使用的，把它提升会破坏这种用途。两个文件的代价已声明，防止分歧的上限是机械的： scripts/dev/composes-em-conformidade.spec.ts 在安装用的 compose 获得了校验用 compose 没有的服务、卷或端口，有任何 build: 残留，或第三方镜像放宽到不同 tag 时否决。

    镜像来源是选择，而「官方」是校验的结果。 --source=ghcr（默认）从 Release 的 images.json 按 digest 解析；--source=local 运行 docker buildx bake，并要求工作树干净且位于 tag 上——从脏工作树构建的镜像不是它自称的那个版本，标记会记录一个谎言。

    密钥只生成一次并持久保存。 RN-114 的五个加上 NEO4J_PASSWORD，用 openssl rand 生成，模板与 docker/smoke.sh:31-57 相同——包括 NEO4J_PASSWORD 用 -hex 而不是 -base64 这一细节，因为 / 会破坏 NEO4J_AUTH 的解析。.env 在接收内容「之前」被创建为空文件且模式为 600：以用户的 umask 创建再收紧，会让密钥在一段窗口期内可读，而这恰恰是不能有这种窗口的文件。

    而 .env 是一个由「COMPOSE」解析的文件，要针对它来证明（AT-083）。SECRET_KEY_BASE 来自 openssl rand -base64 64，它在 64 个字符处「换行」：密钥的 88 个字符分成两行，第二行孤零零地留在 .env 中。在 100 次生成中测得，Compose 拒绝了 49 次（"unexpected character in variable name"），「接受」了 51 次——密钥被截断为 64 个字符，这仍然是 Phoenix 的最小值，因此毫无警告地启动了。现在所有 base64 都经过 segredo_base64（| tr -d '\n'），文件由 escrever_env 写入——是函数，而不是 main 的主体，这样 spec 写入的就是安装所写的「同一个」文件。

    没有 migrate 步骤，也不应该有： compose 以 service_completed_successfully 把 api → migrate-api 串联起来，up --wait 会等待。第二个下令迁移的地方会成为同一真相的第二个来源。

    安装程序在断言之前先询问。 在 up --wait——它已经等待健康检查——之后，它访问 api 和 engine 的 /health，然后才说已安装。这是 reset-total.sh 付出代价才学会的尺子：它曾在 api 处于 Exited (1) 时宣布「reset completo」。

    位置： install.sh（根目录）、docker/docker-compose.install.yml。 测试： scripts/dev/install.spec.ts（计划，没有 TTY 也没有副作用）和 scripts/dev/composes-em-conformidade.spec.ts（两个 compose 之间的分歧）；scripts/dev/install-env.spec.ts 通过真实的函数生成密钥和 .env，把文件交给 docker compose config 对照安装用 compose，并要求「每个」密钥「完整」到达各服务（没有 docker compose 时跳过并点明原因），旧的生成方式被固定为否决。 来源： FASE 29，第 4 次会话（ADR 0150）。安装 runner（第 7 次会话）和迁移之前的安装（第 6 次会话）仍不在范围内，--print-plan 将它们声明为 nao-nesta-versao。

    备份覆盖作为真相来源的「两个」卷，并且无需集群即可运行（RN-528）

    RN-528 — git_local_repos 进入备份，目标可以是磁盘，compose 的恢复复用「同样」的三项校验

    备份原本只覆盖一个数据库，只在一个地方运行。三个后果，第三个是需要写代码的：make test-restore 需要 kubectl、一个集群以及命名空间中的 CronJob brabo-backup，而 docker-compose.prod.yml 没有任何 backup 服务——镜像由 bake 构建，只在 k8s 中使用。迁移一个 compose 安装没有「经过证明」的路径。

    先分类再复制。 容易的做法是「备份所有卷」，而这是错的：七个卷中，neo4j_data 和 project_workspaces 是「派生」的，ollama_data 可以重新获取，brabo_projects_base 属于用户。复制它们会给人覆盖的印象，却没有增加任何可恢复性。真相来源有「两个」：pgdata——早已覆盖，作为逻辑转储，绝不是运行中 Postgres 数据目录的拷贝——以及 git_local_repos，没有任何备份覆盖它。provider 为 local 的项目把裸仓库存放在里面，它「无法」从 Postgres 重建：event log 保存的是叙事，不是 git 对象。runbook 的文字说的正相反（"the real repositories live in GitHub/GitLab"），正是这句话解释了这个卷为何多年没有覆盖——它对 github/gitlab 成立，而对 local 根本没有上游。

    仓库归档的保证是已声明的，而且比「快照」要弱。 没有任何东西被静默（quiesce）。所保证的是「按引用」的一致性——git 先写对象再移动 ref，并通过原子 rename 替换 ref，所以跨越一次 git push 的 tar 拿到的是旧值或新值，绝不会是半个。 「不」保证的是全局瞬间（tar 在一段时间内遍历目录树），也不保证对象的连通性（镜像中有意不含 git）。而并发的 gc 删除 packfile 会变成「失败」而不是不完整的归档：tar 的状态被捕获到一个文件中，因为在 POSIX sh 中管道的状态是最后一个命令的状态——没有这一步，不完整的归档会宣称自己是好的，而说谎的备份比失败的备份更糟，因为只有后者会变成告警。*.lock 被排除：恢复一个孤立的锁会产生一个所有 git 都拒绝操作的仓库。

    目标为磁盘，S3 可选。 五个 S3 变量不再是必需的，成为它们在实践中早已是的东西——「某一个」目标的配置。定义了 BACKUP_DIR 就选择磁盘；不存在则为 S3，这就是 k8s 的 CronJob 无需改动一行就能继续运行的方式。推断（而不是一个必需的目标变量）正是让那条路径保持不变的东西：显式目标会在部署那天、而不是提交那天弄坏 CronJob。四个前缀而不是两个（daily/、weekly/、git-daily/、git-weekly/），因为保留是按「数量」计算的：一个前缀下的两类文件会让「保留 7 个」意味着三个半备份。

    compose 的恢复改变的是外壳，绝不是判断。 test-restore-compose.sh 通过与生产相同的镜像和相同的命令触发一次「真实」备份，并调用「同一个」brabo-restore，带有「同样」的三项校验（表列表对照源头、备份窗口内关键表的计数、session_events 的 seq 的稠密连续性）。 deploy/k8s/test-restore.sh 保持不变——把它们统一起来会让 compose 路径依赖 kubectl，而这正是它存在就是为了避免的依赖。restore.sh 仍然不触碰「源」数据库，这一属性不因迁移的便利而妥协。只有 compose 能要求的一步是第三步：校验仓库归档，因为在 k8s 中那个卷甚至不挂载到 pod 中（跳过是正确的），而在 compose 下它是挂载的（跳过就是虚假的绿色）。

    恢复仓库是「兄弟」命令，而不是另一个的阶段——这是两个产物、两种判断，合并它们会让 git 的失败否决 event log 的校验。它默认只做校验，只有带 --restaurar 才写入；拒绝在已有仓库之上解压（两种状态的混合不会报任何错误，只会在某次历史错误的 fetch 中显现）；并且——真实执行中的发现——当卷不接受写入时，在 tar 「之前」拒绝，并点名 --user 0:0。git_local_repos 由三个 uid 不同的镜像共享，带着最先挂载它的那一方的所有者（实测：1000:1000，模式 0755），而本镜像以 uid 70 运行。当解压以 root 运行时，解出的内容会被交还给「目录」的所有者，绝不留为 root：否则卷会完好地回来却毫无用处，api 和 engine 都无法写入刚刚恢复的东西。

    Neo4j 获得的是重新投影，不是备份。 在一个于另一时刻恢复的 Postgres 旁边恢复一个可能过时的投影，会得到两个源自不同时刻的派生状态，没有任何东西能调和它们。重新投影并未在这里构建（那是 BRB-018）：在它存在之前，迁移的安装诞生时图是「空」的——已知且点名的降级，不是数据丢失，因为 RAG 存在于 pgvector 中并随转储一起到来。自 RN-569 起它已存在（grafo:reprojetar），空图会一直持续到有人运行它。

    RN-530 — 迁移要求「经过证明」的备份：安装程序只有在恢复之后才获得删除的权利

    在现有安装之上安装不被提供：要么迁移，要么停下。在另一版本的卷上执行 up，是那种不会提前告警的破坏。

    迁移有一个顺序，中间那一步赋予了它意义： 备份 → 「证明」能恢复 → 询问 → 删除 → 安装 → 恢复。

    证明不是过分小心。没人尝试恢复过的备份只是一个文件，而发现这一点的时机不是在 down -v 之后——因此安装程序在任何删除之前运行 docker/backup/test-restore-compose.sh（与 restore.sh 「同样」的三项校验，ADR 0152）。失败的备份或失败的证明会中断迁移而不删除任何东西，消息会说明备份留在哪里。

    备份的目标是「宿主机」上的一个文件夹，这正是迁移与丢失之间的区别所在：compose 的默认值是具名卷 backup_local，down -v 会把它与想要保留的东西一起删除。

    迁移删除的：安装的具名卷（包括 pgdata）、容器和网络。它绝不删除的：项目基目录——当 BRABO_PROJECTS_BASE 指向宿主机上的文件夹时，compose 中的那一行是 bind-mount，down -v 不碰 bind——、镜像文件夹（RN-516）以及刚刚证明过的备份。

    Postgres 的转储不会自动恢复到新数据库上：brabo-restore 对照一个测试数据库进行校验，绝不覆盖源头（ADR 0152），而在已有数据的数据库上恢复是安装程序不会自行采取的破坏性操作。本地 git 仓库则会——它们是本会空着诞生的真相来源。

    RN-599 — 在开发 compose 中 api 自行找到 broker，托管文件夹的缺失在每次启动时被说明

    自 RN-512 起 broker 在「开发」compose 中默认启动，但 api 收到的是空的 BROKER_URL（${BROKER_URL:-}，而该行在 .env.example 中被注释掉）。结果，在 9月26日负责人的测试中测得：broker 就在旁边运行，brokerConfigurado 却为 false，项目创建只放行 runner（RN-573）。两条规则关闭这一点：

    1. BROKER_URL 在开发 compose 中有默认值，且只在那里。 默认值是 http://broker:8090——「同一个」文件声明的服务和端口（BROKER_PORT），测试把两者锁在一起：指向别处的默认值会把「没有 broker」换成「broker 不可达」。.env 中的值仍然优先。「生产」和「安装」compose 有意保持 ${BROKER_URL:-}：在那里 broker 位于 profiles: ["container-broker"] 之下，开启它的人写入 URL（install.sh，经询问——RN-575）。那里的默认值会让没有 broker 的安装的 api 断言它有一个。
    2. preflight.mjs 「报告」托管文件夹，仿照 DOCKER_GID。 没有 PROJECT_WORKSPACES_HOST_DIR 时，api 和 engine 使用托管卷 project_workspaces（没有宿主机路径），broker 没有 PROJECT_WORKSPACES_HOST_ROOT——开发 compose 由前者「推导」它——，栈健康地启动，而默认的 container 模式的 container_start 以被拒绝告终。报告有四种不坍缩的结果：ausente、ok、nao-absoluta（~：Compose 在 api/engine 的 bind-mount 源中展开它，但「不」在 broker 收到的变量中展开——用 docker compose config 测得）以及 divergente（显式的 PROJECT_WORKSPACES_HOST_ROOT 与 api 和 engine 挂载的文件夹不同，包括它们挂载的是卷的情况）。每条消息都说明症状和修复办法。它「绝不」拒绝启动，也「绝不」写入 .env：答案是某人磁盘上的一个路径，而把卷换成文件夹会隐藏已经在卷中的东西（数据留在那里，只是不再被看到）——消息也说明这一点。

    仍然开放的： pnpm bootstrap 「不」提供这个文件夹。那样做就是第二个 consentir-base.mjs（在 TTY 中询问、以正确所有者创建文件夹、一起写入「两个」变量、决定如何处理已有数据的 project_workspaces 卷），这是另一条战线。
