    O receio registrado abaixo — que cada um merecia decisão própria — não apontava para quatro DECISÕES diferentes, só para três checagens em lugares diferentes: passphraseAtual() (auth-key-material.ts), tokenDeServicoAtual() (service-token.ts) e o construtor de EnvelopeEncryptionService, cada um com a MESMA regra do resolveOauthStateSecret() (ausente/exemplo/curto derruba o boot em produção).     Revisão externa de 2026-08-28, item #13 — containers de dev rodavam como root — FEITO. docker/api/Dockerfile, docker/web/Dockerfile e docker/engine/Dockerfile não tinham diretiva USER, então tudo o que eles escreviam no bind mount (node_modules, apps/api/dist, e o que um agente gerasse dentro de um projeto em modo de execução mounted) caía no host com dono root — o README e o guia de primeiros passos desta documentação documentavam um contorno manual sudo chown -R $USER ... em vez de corrigir a classe do problema. As imagens Dockerfile.prod já eram non-root; isto era só de dev.

    A correção mapeia o usuário do container para o UID/GID do HOST em vez de rodar como root e limpar depois: build args DEV_UID/DEV_GID (lidos do .env/do ambiente via docker-compose.yml, default 1000/1000), nomeados DEV_* de propósito porque ${UID} é somente leitura no bash e não é exportado para o ambiente por padrão — lê-lo direto do arquivo de compose sempre veria vazio. Cada Dockerfile cria um grupo/usuário com esse UID/GID só quando ele não colide com um que a imagem base já traz (node:24-alpine já tem node em 1000:1000) e troca com USER <uid>:<gid> — numérico, então não importa qual nome de usuário acaba dono desse id. Todos os passos que exigem root (apk add, pip install, os downloads de gitleaks/hadolint/actionlint) ficam ANTES da troca; na imagem do engine, _build/deps/.mix/.hex — sob /root porque mix local.hex/mix local.rebar escrevem lá, montados como volumes nomeados pelo docker-compose.yml — recebem mkdir+chown para o UID/GID alvo antes do USER, então um volume nomeado novinho herda o dono certo na primeira montagem (o Docker popula um volume novo com o que já existe naquele caminho na imagem).

    Provado rodando a stack real (DEV_UID=$(id -u) DEV_GID=$(id -g) docker compose -f docker/docker-compose.yml up --build postgres api web engine): os três containers subiram com zero erros de EACCES/permissão, e apps/api/dist no host ficou com dono o usuário do host, não root. Um detalhe real, não um bloqueio: volumes nomeados criados por um ambiente anterior a esta correção (*_node_modules, engine_build, engine_deps, engine_mix, engine_hex) ainda guardam conteúdo escrito pelos containers root antigos — atualizar exige um chown único desses dados de volume existentes (ou derrubar os volumes com docker compose down -v e deixar o próximo up recriá-los), documentado no README e no guia de primeiros passos junto com as instruções de DEV_UID/DEV_GID.
