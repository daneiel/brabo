    RN-423 — The runner CONFIRMS the path; without confirmation, the command is refused — it never falls into the container

    The runner is the source of truth for a runner project's path, not what was typed in the wizard. Right after the Phoenix channel connects (terminal:<projectId>, :runner role), apps/runner/src/index.ts pushes workspace_confirm with the --dir it received on the command line. The engine passes it on (Engine.Sessions.EngineApiClient.confirm_workspace/4) to POST /internal/projects/:projectId/workspace-verification (ConfirmProjectWorkspaceUseCase), which:

    1. Refuses with 400 if the project isn't in runner mode;
    2. Revalidates the path with the SAME lexical predicate as creation (RN-422) — even coming from the runner, system root and overlap with Brabo remain forbidden;
    3. OVERWRITES workspacePath with the normalized path and writes workspaceVerifiedAt = now() — without requiring equality with what was typed at creation: the runner rules;
    4. Is IDEMPOTENT — reconnecting reporting the SAME path rewrites nothing (changed: false); a DIFFERENT path rewrites, because the runner remains the source of truth at each reconnection;
    5. With no session in the project yet (ProjectSession.latest_id/1 returns nil): the UPDATE happens all the same, only the project.workspace_verified event (and the evidence for the workspace-verificado gate) is absent — the SAME degradation that pty_open/pty_close already accept (RN-108/RN-420). An accepted and declared gap, not a silent one.

    Engine.Actions.TerminalExecutor.decisao_de_execucao/1 gained FOUR outputs, not two: runner with workspace_verified_at: nil refuses (:recusar_nao_verificado); verified runner without a connected runner refuses (:recusar_runner_desconectado); verified and connected runner routes (:rotear_runner); any other mode follows the usual path (:caminho_de_sempre). The two refusals NEVER fall into System.cmd — a runner project has no bind-mount, and "falling to the usual path" would be executing blindly in a folder the engine's process doesn't see. The same refusal applies in the race (Registry said connected at the start of run/3, but the runner dropped before the dispatch answered).

    • Where: apps/api/src/application/use-cases/iam/confirm-project-workspace.use-case.ts, apps/api/src/interfaces/http/internal/internal-projects.controller.ts (POST :projectId/workspace-verification), apps/engine/lib/engine/actions/terminal_executor.ex (decisao_de_execucao/1), apps/engine/lib/engine_web/channels/terminal_channel.ex (handle_in("workspace_confirm", ...)), apps/engine/lib/engine/sessions/engine_api_client.ex (confirm_workspace/4), apps/runner/src/channel.ts (enviarWorkspaceConfirm), apps/runner/src/index.ts
    • Test: apps/api/test/application/use-cases/iam/confirm-project-workspace.use-case.spec.ts, apps/engine/test/engine/actions/terminal_executor_test.exs (describe "roteamento pro runner local"), apps/engine/test/engine_web/channels/terminal_channel_test.exs (describe "workspace_confirm"), apps/runner/src/channel.spec.ts (enviarWorkspaceConfirm after the join)
    • Edge case: docs/gates.yml registers workspace-verificado as severidade: warn — what really locks is the engine's explicit refusal, the gate is only the record/evidence.
    • Architectural decision: ADR 0104

    The mirror copies the work to the user's folder (RN-516)

    RN-516 — The mirror destination travels in the join GRANT, the mirror copies the git list in one direction only and never deletes, and the trigger is a named moment — never a watcher

    Half B of session 6 of PHASE 28: the espelho capability (RN-514, ADR 0147) comes to EXIST. RN-515 decided where the destination lives and did not copy any file; this one decides how it reaches the local agent, what is copied and when.

    The destination travels in the join grant, never in runner configuration. The join reply of the terminal:<projectId> channel is no longer empty for the :runner role: when the project has a declared destination (projects.mirror_path) and the espelho capability was granted, it carries %{espelho: %{destino: "<caminho>"}}. The runner keeps this in estado.destinoDoEspelho, which dies with the connection, and refuses mirror_sync for a destination not granted to it on that connection (ADR 0147, point 4). Never an environment variable, never a local file: a global destination would make project B's artifact land in project A's folder, and the user would find that out through the content, not through an error.

    A declared consequence, and it is the price: changing the destination with the runner connected requires reconnecting it. The grant belongs to the join, and a new destination arriving through another door would be exactly the global configuration the rule refuses.

    A non-null mirror_path now REQUIRES the capability. It does not enter the map by execution_mode — what requires it is a project DATUM, not the mode (and mounted and runner can have a destination while container cannot). This is the first REAL case of the refusal mechanism RN-514 left implemented and never firing: a brabo-runner older than this version connected to a project with a destination stops connecting, with a named refusal (JoinRecusadoError, fatal and with no retry). It is opt-in — it only happens where someone configured a destination — and the cost is declared in ADR 0147 itself.

    The THREE refusals of the guard, and the realpath pass is not redundant. apps/runner/src/espelho-guard.ts is a sibling of guard.ts, not an extension of it: it reuses semBarraFinal/dentroDoEscopo/realpathMaisProximo and the double lexical-then-realpath pass of validarCwdDentroDaRaiz, and inherits in writing the same TOCTOU caveat — it is best-effort, not a security boundary. It refuses (1) a symlink escaping the destination, (2) a destination that contains the workspace and (3) a destination inside the workspace; (2) and (3) are the same loop in opposite directions, and with the identity bind of ADR 0141 writing the mirror inside the source makes the mirror copy itself. The api already refused the lexical half (RN-515) and says, in the code itself, that it is only the lexicon — it has no disk on which to resolve a symlink on the user's computer. destino/atalho -> /caminho/do/projeto passes through there unseen, and it is here that it is resolved.

    A difference in mechanism, found while implementing: realpathMaisProximo falls back to the first ancestor that exists, and the mirror destination almost never exists (it is the mkdir -p of this round that creates it). Collapsing both sides onto the ancestor would make /base-outra and /base both become /, and the guard would refuse every sibling folder. That is why the second pass resolves the ancestor and puts the suffix back — a symlink can only live in a segment that exists, so what remains never hides any link. Refusal (1) also has a second half, per file (caminhoNoDestino): a destino/sub that links to /etc would make the copy of sub/passwd write outside, with the destination itself perfectly valid.

    One direction, and it NEVER deletes. Workspace → destination. Never --delete, never unlink, never rm. A file deleted in the workspace remains in the destination, and that is a decision, not carelessness: the user's folder is not a replica, it is an accumulation — an agent that deletes a file in someone's personal folder because of a git clean on the other side is the surprise the product exists not to produce. Overwriting a file that changed is expected; removing never is. The price, declared in the ADR: the destination only grows, and no automatic mechanism cleans it.

    What is copied is the GIT LIST, and nothing else. The tracked files (git ls-files) plus the untracked ones that are not ignored (git ls-files --others --exclude-standard), with -z (git quotes and escapes a path with a space or accent without it). That is exactly "the work": it skips node_modules, dist, build output and .git itself without keeping any exclusion list, which would age with every new stack — the project's .gitignore is already the list, maintained by whoever maintains the project. The workspace is a git repository by construction (the product provisions Gitflow in it and materializes it with git init/fetch/checkout), so the precondition belongs to the PRODUCT, not an assumption about the machine. Git that fails or a folder that is not a repository fail with a named reason — never a cp -r of everything as a plan B, which is how an entire node_modules would end up in someone's personal folder.

    Two properties verified and declared, not hidden: a nested git repository comes back as ONE directory entry and is not descended into — the worktree of each dev agent (<workspace>/.worktrees/<agent_id>) is one of those, so the mirror shows the main checkout, never the work still isolated in a worktree; and a symlink at the source is skipped, because following the link would bring content from outside the project into the personal folder. What is left out is COUNTED (pulados/recusados), never swallowed. And there is no "did it change?" heuristic: always copying costs bytes that are already equal, while skipping by size+mtime would make the mirror silently not copy a file that changed.

    Its OWN predicate, and the mirror does not require Docker. Engine.Runners.RunnerReadiness stays byte for byte as it is (ADR 0147, point 3) — Engine.Runners.Espelho does not call it, does not extend it and receives nothing from it. The mirror has TWO preconditions, confirmed workspace and connected runner, and not the third that RN-507 added (container REGISTERED running). A RunnerReadiness with a "skip container" flag is precisely the mechanism by which that third one would fall by accident for exec in a future refactoring, and ADR 0145 exists so that it does not fall. And the mirror legitimately does not need it: the third exists because there were two possible executions and the wrong one was invisible; a file copy on the user's machine has no container to fall from. It also does not ask for the execution_mode — whoever already decided that was the api when writing the destination (RN-515 refuses container), and repeating the decision would be the second source of the same rule.

    Trigger by a NAMED MOMENT, never a watcher. The engine pushes mirror_sync from a point in the code that has a name — today the successful commit (EngineWeb.ActionCommandController, git_commit). Never fs.watch: a watcher is unbounded work triggered by anything — a dependency install, a build, and worse, by the mirror's own writes, which is a loop — and would run continuously on the user's machine without anyone having asked, which is the opposite of what "local agent" should mean. The push is fire-and-forget: no from, no pending_execs and no mirror_sync_result, because whoever triggered it is in the middle of something else and the sync telemetry is point 7 of the ADR, from another session. A mirror failure becomes a local log, never an exception that takes the runner down and never silence.

    It is NOT a proposed_action, and must not become one. Writing the mirror is configuration the user declared, not an agent asking to act — ADR 0147 is explicit about it, and syncing via a terminal command would fall into the scope of ADR 0055 and become a queue of routine approvals, eroding the ceiling that gives the click its meaning.

    The TWO halves of the unit file do NOT have the same syntax, and WorkingDirectory= goes WITHOUT quotes. ExecStart= is parsed with unquoting and word splitting — that is why each argument goes in quotes —, and WorkingDirectory= is not: systemd takes the whole rest of the line as the path. Treating the two as if they were the same cost an entire release: with quotes the value no longer starts with /, the unit is refused at load (Loaded: bad-setting, WorkingDirectory= path is not absolute) and never starts — in both kinds, in no installation at all. Reading back accepts both forms, and that is a deliberate debt to whoever already has a broken unit on disk: status and uninstall need to keep reaching its folder. Whoever is in that state fixes it by reinstalling — install overwrites the whole file.

    And there is a THIRD syntax in the same file: Environment= (AT-095). It is a LIST of space-separated assignments, with unquoting and C-style escaping, and it also expands specifiers. Written raw — as the XDG_CONFIG_HOME of the MACHINE unit and the PATH of both kinds came out —, Environment=XDG_CONFIG_HOME=/home/dan/50%off com espaco reached the service as /home/dan/50popff: %o expanded and com/espaco discarded by the word splitting. That is why the WHOLE assignment goes in quotes (Environment="VAR=valor"), with \ and " escaped by backslash and % as %%; $ is not escaped there (Environment= does not expand variables). The --dir of ExecStart= had the same class and went along: each argument still goes in quotes, and now \ becomes \\, % becomes %% and $ becomes $$ (the variable substitution of ExecStart=). A line break in PATH/XDG_CONFIG_HOME is REFUSED before writing — in a unit file it is a new directive, not a value. None of this changes the READING back: it only reads the WorkingDirectory=, and neither of the two environment values is read from disk. The proof is the EFFECTIVE VALUE, not verify (which approves the broken form): the very systemd --test --user --unit=<u>, over a temporary units folder, dumps the resolved configuration, and the test compares what systemd UNDERSTOOD with what was written.

A failing deactivation becomes a warning and the file is removed anyway — a unit the manager no longer recognizes is no reason to leave the file behind.

    And uninstall SAYS what it did not do: the key left the disk, not the server. The corresponding public key remains in runner_device_keys, and revoking it is something else (DELETE /projects/:projectId/runner-device-keys/:deviceKeyId, ADR 0147 point 6). A "removed" that let the person think they had revoked would be worse than removing nothing. The LaunchAgent log is also not deleted: it is the user's record of what happened, and deleting it was not asked for.

    status answers FOUR states, and they do not collapse (RN-088): not installed, installed and running, installed and stopped, and installed and I could not ask. The first answer comes from the DISK — is there a unit file? —, and that is why it stays right on a machine where the manager does not exist; only afterwards is the manager asked. A spawn that failed (binary absent from the PATH) never becomes "the manager said no": they are different answers, separated at the source, and a word this CLI does not know how to interpret also falls into "could not ask" instead of becoming "stopped" by guesswork. Each state has its own sentence and its own exit code (0 / 3 / 4 / 5, with 1 and 2 left out because they already mean generic failure and usage error in this CLI): a single exit(1) for the three "not running" ones would collapse through the code exactly what the sentence separates.

    Nothing here is a proposed_action. It is the user running a command on their own machine, about their own service — not an agent asking to act. service is dispatched before lerArgumentos, because none of the three subcommands connects to anything and what matters most (status) needs to work in a folder whose configuration is broken, which is precisely when someone asks.

    The machine agent waits for the first project, and the key is born in the terminal (RN-550/551, PHASE 30)

    RN-550 — With ZERO connections the local agent does NOT exit: it waits and re-queries the list; with a live connection the query is still only at start

    Session 8 of PHASE 30. RN-544 made an empty list a NORMAL state and the process exit with 0, saying "create a project in Runner mode and bring the agent up again — the list is queried only at start". That contradicted, in writing, ADR 0155 point 5 — "it waits… when the person creates the first project on the web, the agent is already there" — and broke exactly the case the phase pursues: the new installation, which is the installation with ZERO projects. The installer brought up the agent, the agent found there was nothing and went away, and the person who created the first project minutes later would go back to the terminal without ever having been told about it.

    The rule is ASYMMETRIC, and the asymmetry is the design:

    conexões > 0  →  a lista é consultada SÓ no start   (a RN-544 fica byte a byte)
conexões = 0  →  reconsulta, com cadência declarada

    And it does NOT undo RN-544's decision. That session's argument remains whole: a list that comes back SMALLER is ambiguous — project deleted, converted mode, role revoked, or a transient 500 disguising itself as the three —, and taking down a LIVE connection because of that ambiguity would trade a right state for a guess. With zero connections there is nothing to take down and no ambiguity at all: any project that shows up is pure gain, and no decision is made about what disappeared. The re-query STOPS the moment the first non-empty list arrives, and from then on the behavior is byte for byte today's — the waiting module is not called again while the process lives.

    The exit 0 argument fell because its premise fell. RN-544 wrote that "staying up with zero connections would be an 'active' service that does nothing, and the unit's status would start to lie" — and that depended on the process doing nothing. It is that premise this RN removes: it re-queries, with a declared cadence, and SAYS it is doing so. active (running) becomes true, and what lied was the exit with 0, which left the new installation without an agent precisely in the minute the person was going to create the first project.

    The cadence escalates and STABILIZES: 15s, 30s, 60s, and the last one repeats forever. The two short steps exist because the case to serve is that of someone creating the first project NOW; a ceiling of minutes would make the agent show up after the person gave up looking. The 60s plateau is the steady-state price — ONE request per minute, from one installation, against a route that returns the list of the credential's own owner. Growing beyond that would save traffic nobody is paying for and worsen the only thing the wait delivers.

    There is a ceiling, and it is on FAILURES, never on waiting. Waiting has no limit — waiting is the normal state of a new installation, and can last days. What has a ceiling are CONSECUTIVE query failures: ten, and then the process exits with 1 NAMING the number, as the connection loop already does with TETO_DE_TENTATIVAS_SEGUIDAS and for the same reason (not hammering the api forever when the problem is not transient). A query that ANSWERS resets the counter — including when it answers EMPTY, which is success, because the empty list is the right answer. The constant is SEPARATE on purpose, with the same value: one counts failures to CONNECT and the other, failures to LIST, and tying them would make a change in connection cadence touch, without anyone asking, the time a new installation waits before giving up. CredencialNaoEDeMaquinaError (the 403 by key kind, RN-544) does not count toward the ceiling: it is fatal on the spot, because a project key does not become a machine key by waiting one more minute.

    Staying up silently would be worse than exiting. "Waiting" and "stuck" are the same picture to whoever reads journalctl, so the process states the cadence when entering the wait, says when the first project shows up, and beats a HEARTBEAT every 30 queries (half an hour, on the plateau) reporting how many queries there have been. Not every query becomes a line, also on purpose: one log per minute, forever, is the noise that buries the lines that matter.

    Restart=on-abnormal stays byte for byte, in BOTH unit kinds (RN-545), and nothing in them changes. Measured: on-abnormal restarts on SIGNAL, watchdog or timeout — never on exit code, neither 0 nor 1. The exit with 0 was never what prevented the service from being restarted; what prevented it is that on-abnormal looks at no code at all. The real effect of the change is the opposite of what was feared: the MACHINE unit, which is the one running this mode, now stays active (running) for real instead of ending in inactive (dead) seconds after starting — and service status --machine now answers rodando (0) where before it answered parado (3) on a new installation. The PROJECT unit is not affected in any line: it runs the projeto mode, which never gets here.

    One exception, declared: a NON-empty list whose projects are all refused still exits with 1. That is also zero connections, and even so it does not wait — because there each refusal names a concrete local defect (a segment escaping the base, a folder that is a file) with its own fix, and re-querying would repeat the same refusals indefinitely, burying in the log the line that says what to fix. The wait is for "no project exists yet", never for "it exists and I cannot serve it".

    The chain, measured. Engine.Runners.RunnerReadiness.verificar/1 (runner_readiness.ex:52) requires a REGISTERED running container before ANY operation of Engine.Actions.Workspace.RunnerGit — including the initial authenticated git fetch, which comes out of fetch!/3 (runner_git.ex:226, via exec/4 at :288). With containerAtivo set, tratarExec routes the command into the container (index.ts:728–730, and the new refusal at :693), and the exec operation of packages/docker-port has no env field — on purpose (ADR 0130: no free -e at all). The env field RN-507 added to the exec/exec_result pair (RunnerRouter.exec/5, runner_router.ex:50; ExecMessage.env, apps/runner/src/channel.ts:62) is only applied on the HOST path, where apps/runner/src/exec.ts:94 MERGES it over process.env.

    Result: the moment RN-507 lets the authenticated fetch run, the container is almost always already up on the SAME runner — and that is where the credential (ADR 0056, GitAuth.env_de_auth/1) was discarded, silently, with no error. git ran with the ephemeral helper installed by -c and the two variables EMPTY, and exited with an authentication failure — indistinguishable from an invalid token, wrong permission or network down. The person hunted the wrong thing, and the product said nothing.

    The fix is the NAMED outcome, not delivering the credential. The docker exec still has no env field — touching that is changing the containment door, and it is an ADR decision, not a cut (see the gap declared below). What changes is that the pair (env present, active container) stops being executed and starts being refused, with a mark, a message and an origin.

    What refuses is the RUNNER, and only it can. It is the only process that knows both halves at the same time: that the command carries a credential and that it goes inside the container. The engine does not know the second, and that was MEASURED: estado.containerAtivo is born null on each runner execution (index.ts:1449) and is only set by tratarContainerStart, so a running container REGISTERED in the database does not imply an active container in that process — a restarted runner with the container up routes to the HOST, and there the credential arrives normally. Moving the check up to RunnerReadiness or to RunnerGit would refuse a path that works. And RunnerReadiness stays BYTE FOR BYTE as it is: it gains no flag nor fourth precondition — it is the same rule RN-516 already stated about not hanging a "skip container" flag on it.

    The MARK is a PROTOCOL constant, not a message detail. MARCA_DE_CREDENCIAL_NAO_ENTREGUE (index.ts) and @marca (credencial_de_git.ex) carry the SAME token, and it is through it — not through the sentence — that the engine recognizes the refusal after it has crossed a rescue and become a loose string. Changing only one side breaks no compilation: the refusal keeps happening and only the CLASSIFICATION goes back to being wrong, which is the exact form of the defect this RN closes. Neither of the two suites reaches the other language (ExUnit does not read TypeScript, the runner's vitest does not read Elixir), so the guard lives in scripts/ci/, with the other tests that read the whole repository as text.

    The origin is politica, and the choice points to ACTION. The four of ADR 0020 do not assign blame, they say what to do. This is not a clause nobody wrote (codigo) nor a network that went down (infra): it is the containment of ADR 0130 working as designed, against a case it did not foresee. Whoever reads politica knows there is no bug to hunt — there is a pending product decision. Engine.Runners.CredencialDeGit.desfecho/1 adds ONE case and reclassifies no other: any other worktree failure keeps byte for byte {"falha ao preparar o worktree", "codigo"}, in BOTH dev agents (the real one and the Noop, which exists to exercise THIS path and not a copy of it).

    The CONTAINMENT refusal wins, and the order is a decision. It comes AFTER validarCwdDentroDaRaiz (guard.ts): a command pointed outside the root needs to hear that, because there a containment boundary is being refused, while here there is a missing capability. Collapsing the two would make an out-of-scope command look like a credential problem — the same diagnosis defect, with another sign.

    The Anamnese switched back on: eligible subject and profile fact (RN-680)

    RN-688 — The runner binary reads the PTY with its own reader under Bun, and the self-test proves the SECOND read

    Under Bun (the bun build --compile binary, ADR 0112), the tty.ReadStream with which node-pty reads the PTY's master side is an fs.ReadStream, and the first read with no data from the non-blocking fd RAISES as EAGAIN: the stream destroys itself, closes the fd, and no onData arrives after that (oven-sh/bun#25822). The binary's interactive terminal stopped after the first chunk of output on all THREE Unix platforms; Linux passed the proof only because the first read already brought the echo and the answer together.

    The rule: under Bun and outside Windows, node-pty's spawn runs with the tty.ReadStream swapped for its own reader that reads the SAME fd with fs.read and, on EAGAIN, WAITS and retries (from 4 ms, doubling up to 32 ms, back to the minimum on every piece of data); EIO or zero bytes is the end. The swap applies only DURING the spawn and is restored even when it throws; under Node the module comes back INTACT. The fd and the child process remain the real ones — nothing simulates output. And --self-test-pty makes TWO rounds, the second after a pause with nothing to read: it is the pause that forces the read through an EAGAIN, and it is through it that the old reader fails on Linux too. When it fails, the self-test says why (chunks, the child's output, a probe on a second PTY and the stream's events) — the verdict does not change.

    It was the probe that measured Windows: there the read side is ConPTY's named pipe, opened by node-pty as a net.Socket, without an fd the reader could take over, and the pipe ends after the first chunk — which is why win32-x64 left the matrix (ADR 0187) instead of getting a workaround.
