    配置

    所有配置都通过环境变量完成。应用没有配置文件——存在的是 permissions.json，它是项目的策略，而不是进程的配置。

    有两个受版本控制的文件会在运行时被读取，它们不是配置，但很容易与配置混淆：上面的 permissions.json，以及 docs/gates.yml（ADR 0054），即 gate 的声明式注册表。两者都没有指向某个路径的环境变量——注册表是从 __dirname 向上查找得到的——并且在生产环境中编辑它们都不会改变行为：注册表描述 gate，而不执行 gate。它随 api 镜像一起发布；参见 runbook。

    随镜像发布的是注册表，而不是它所指向的任何东西。teste/ci 类 gate 的 evidencia 指向 apps/api/test/、scripts/ci/ 和 .github/ 下的文件，而这些都不在镜像里。因此，核对这些目标是否存在是关于仓库的断言，由 CI 负责，而绝不由提供 GET /gates 的进程负责——所以 api 读取注册表时不会去找它们。它曾经去找过，结果在每个安装中都返回 500（RN-070）。

    up --wait 只能证明有 healthcheck 的服务。 在开发用的 compose 中，api、engine 和 web 原本都没有 healthcheck，所以 docker compose up --wait 在容器启动的那一刻就认为它们已就绪——早于进程开始监听。正因如此，容器可能在几秒后死掉，而命令仍在宣告成功。现在这三者都带有与生产镜像在 Dockerfile 中早已声明的相同检查（api 和 engine 上是会访问数据库的 /health；Vite 服务器上是 /）。容器 broker 在另一次变更中获得了自己的 healthcheck；postgres 和 neo4j 一直都有。这里没有任何环境变量——之所以写出来，是因为脚本依赖的正是 --wait，而没有 healthcheck 的服务会让它撒谎。

    下面的默认值是从代码中提取的，而不是来自以前的文档。出错时一列是最省时间的部分：几乎每个变量都有一个在开发环境可用的默认值，以及一种在生产环境中特有的失败方式。

    变量只有在 compose 映射了它时才会进入进程。 docker compose 不会把宿主机的环境传进容器：变量当且仅当写在该服务的 environment:（或某个 env_file）中时才会到达。这不是细节；正是这样，ANAMNESE_ENABLED 和 PSYCHOLOGIST_ENABLED 悄无声息地变得无法设置，而代码中有三处承诺 2026-08-10 的暂停可以通过 X=true 加一次重启来撤销。在运行中的 engine 容器内测量，它们的值为空，runtime.exs 落到了 "false"——没有任何地方报错。现在 engine 读取的每个布尔开关都映射在全部三个 compose 文件中（开发、生产和安装——安装用的那个自 AT-202 起），使用代码自身的默认值，只有生产和安装有意关闭的两个后台 agent 启动开关除外；scripts/ci/flags-do-engine-no-compose.spec.ts 会让下一个缺失的开关构建失败（RN-540）。Kubernetes 有意不受此规则约束：Deployment/ConfigMap 不拦截任何东西，所以那里没有需要修复的断开的键。

    开发环境的默认值是故意不安全的。 像 dev-master-key-change-me 这样的值存在，是为了让 pnpm dev 不费周折地启动。在生产环境中必须替换它们——其中六个如果不替换，进程会拒绝启动（api 或 engine，标记为 🔒）。其中五个遵循 ADR 0059/RN-093 的模式：缺失、等于公开的示例字面值或过短都会让启动失败。参见 RN-114，了解加入最初的 GIT_OAUTH_STATE_SECRET 的那四个。

    安装用 compose（docker-compose.install.yml）

    在已安装的机器上运行的 compose 从必填变量获取产品的五个镜像，没有默认值——由 install.sh 写入 .env：

    变量 含义
    BRABO_API_IMAGE api 镜像的完整引用；来源是 GHCR 时为 ghcr.io/…@sha256:…，本地构建时为 brabo-api:prod
    BRABO_ENGINE_IMAGE 同上，用于 engine
    BRABO_WEB_IMAGE 同上，用于 web
    BRABO_BACKUP_IMAGE 同上，用于备份 job（在 profile backup 下）
    BRABO_BROKER_IMAGE 同上，用于容器 broker（ADR 0162）。无论 broker 是否开启都会写入：Compose 在按 profile 过滤之前会插值整个文件，所以关闭的服务中的 ${VAR:?…} 仍然会让文件被拒绝（已测量）

    它们故意写成 ${VAR:?…}。如果有默认值，缺失的变量会让一半的栈运行在没人选择过的镜像上，错误会表现为奇怪的行为，而不是拒绝。

    它们不在下面生成的清单中：生成器扫描 apps/，而这些变量由 Compose 读取，不是由产品代码读取（RN-527）。

    自 ADR 0162 起，broker 在这个 compose 中，处于关闭状态，位于 profile container-broker 下，install.sh 只有在询问且回答为 "s" 时才开启它（RN-575）。届时它会写入四行，要么全写，要么都不写：

    变量 install.sh 写入的内容
    COMPOSE_PROFILES container-broker——由 Compose 从 --env-file 读取，所以 up -d --wait 无需参数即可启动 broker
    BROKER_URL http://broker:8090——api 一侧；没有它，api 永远不会调用 broker
    DOCKER_GID 从容器内部看到的 socket 的 gid，用 broker 自己的镜像测量；测量失败是有名称的拒绝，绝不使用默认的 999
    PROJECT_WORKSPACES_HOST_ROOT <DockerRootDir>/volumes/brabo_project_workspaces/_data，在启动前计算，并在启动后与卷的真实 Mountpoint 核对

    BRABO_PROJECTS_HOST_BASE 不会被写入：compose 从 BRABO_PROJECTS_BASE 推导它，与验证用 compose 相同。之后开启或关闭的方法见 runbook。

    本地模型（Ollama，profile llm）紧接在 broker 之后询问（RN-691）。回答 "s" 会先测量宿主机上的一个空闲端口，然后写入：

    变量 install.sh 写入的内容
    OLLAMA_PORT 11434，或者当已有东西（原生 Ollama）在那里监听时，取到 11443 为止的第一个空闲端口；整个范围都被占用时是有名称的拒绝，不写入任何内容
    COMPOSE_PROFILES llm；只有两者都被接受时，才与 container-broker 写在同一行（container-broker,llm）——两行不会叠加，最后一行生效

    没有它们，语义重复检查会被跳过。之后开启的方法见 runbook。

    第一方认证

    认证位于 api 的领域中，自切换之后也是唯一的签发方。决策见 ADR 0031 和 ADR 0032。

    变量 默认值 作用
    AUTH_JWT_SECRET 🔒 dev-auth-jwt-secret-change-me，仅限非生产环境 一个短语，access token 的 Ed25519 密钥对通过 scrypt 从它派生——没有任何私钥被提交。在生产环境中，如果它缺失、等于上面的默认值（公开的——在 .env.example 里）或少于 16 个字符，api 拒绝启动（RN-114）
    AUTH_JWT_SECRET_PREVIOUS — 轮换期间仅用于验证；进入 JWKS，永远不签名
    AUTH_TOKEN_PEPPER 🔒 dev-auth-token-pepper-change-me，仅限非生产环境 不透明 token（refresh、账户关联、PAT）哈希以及锁定桶键所用的 HMAC 密钥。独立的密钥——不再回退到 AUTH_JWT_SECRET（RN-613）。在生产环境中，如果它缺失、等于本仓库中任何示例值或少于 16 个字符，api 拒绝启动。 曾在没有它的情况下运行的安装，需要用当前的 AUTH_JWT_SECRET 来定义它，否则所有人都会被登出——参见 runbook
    AUTH_ACCESS_TOKEN_TTL_MS 900000 15 分钟
    AUTH_REFRESH_TOKEN_TTL_MS 1209600000 14 天
    AUTH_REFRESH_ABSOLUTE_TTL_MS 2592000000 token 家族的绝对上限，从登录时算起——没有它，轮换会授予永久会话
    AUTH_REGISTRATION_ENABLED true 任何不同于 "false" 的值都保持注册开放
    AUTH_LOCKOUT_ENABLED true 同样的约定
    AUTH_LOCKOUT_WINDOW_MS 900000 计数的滑动窗口
    AUTH_LOCKOUT_THRESHOLDS 5:30,8:300,12:900 按邮箱分桶的阶梯，失败次数:秒数
    AUTH_LOCKOUT_IP_THRESHOLDS 20:30,30:120 按 IP 分桶的阶梯，更宽松，上限更短
    AUTH_EMAIL_TOKEN_TTL_MS 172800000 邮箱验证，48 小时
    AUTH_RESET_TOKEN_TTL_MS 3600000 密码重置，1 小时
    AUTH_SET_PASSWORD_TTL_MS 604800000 设置首个密码（迁移的用户），7 天——比重置更长，因为收件人并没有主动请求
    AUTH_IP_ATTEMPT_THRESHOLD 60 认证路由上每个 IP 的尝试上限
    AUTH_MAIL_LOG_TOKENS false 仅限开发：在日志中打印验证/重置 token

    按邮箱阶梯的上限故意等于窗口。 使用滑动窗口时，坚持尝试的人会推动窗口，只要还在尝试就一直被锁定；停下来的人会在窗口清空后恢复。大于窗口的上限会造成窗口无法表示的锁定，需要一个持久化的 locked_until 列和解锁队列。不要只改其中一个。

    轮换 AUTH_TOKEN_PEPPER 会让所有人登出，并使待处理的验证和重置 token 失效。与密钥不同，pepper 没有 _PREVIOUS。参见 runbook。

    _PREVIOUS 变量能到达哪里。 AUTH_JWT_SECRET_PREVIOUS、CREDENTIALS_MASTER_KEY_PREVIOUS 和 BRABO_SERVICE_TOKEN_PREVIOUS 以 ${X:-} 的形式映射在全部三个 compose（开发、生产和安装）的 environment: 中——api 接收这三个，engine 和 broker 接收 BRABO_SERVICE_TOKEN_PREVIOUS（RN-595）。在每个读取方中，空值都等同于缺失，所以在轮换之外什么都不会变；轮换期间，只需在 .env 中定义它们并重建服务。在 RN-595 之前，它们哪里都没有映射，而 docker compose 不会传递宿主机的环境，于是一次轮换会悄无声息地变成直接替换。 在 Kubernetes 中，它们通过密钥保险库到达 Pod（AT-220）：ExternalSecret 用 dataFrom.extract 拉取整个 brabo 对象，所以其中存在的 _PREVIOUS 会进入 brabo-secrets，不存在的就根本不在那里。代价是这个对象中的每个键都会成为 api、engine、migrations 和 backup 的环境变量——保险库中的这个对象不能存放其他任何东西。操作步骤见 runbook。

    Mounted 模式的项目：一个基础目录，按同一路径挂载

    自 ADR 0072 起，项目可以以 Mounted 模式创建（即以前的 local，由 ADR 0104 改名）——代码位于用户的文件夹中，PROJECT_WORKSPACES_ROOT 不参与其根目录。

    项目的路径是项目的数据（projects.workspace_path），在创建时选定，从来不是环境变量。环境提供的是这些文件夹所在的基础目录——BRABO_PROJECTS_BASE，每个安装一个（ADR 0141，RN-500）：

    # .env — ABSOLUTO. `~` não é expandido pelo Compose.
BRABO_PROJECTS_BASE=/home/voce/projetos-brabo

    你不需要手写这一行。自 ADR 0146 起，pnpm bootstrap → Docker › Base de projetos 会运行 scripts/dev/consentir-base.mjs，它建议 $HOME/projetos-brabo，拒绝与 Brabo 检出目录或 PROJECT_WORKSPACES_HOST_DIR 重叠的路径（两个所有者相反的根目录——共用一个文件夹会让名为 loja 的 Mounted 项目落到 workspace_dir_name 同样是 loja 的 Container 项目头上），在 macOS 和 Windows 上通过实际挂载来证明 Docker 确实能看到这个文件夹，然后才写入变量。

    证明靠的是一次挂载，而绝不是读取 Docker Desktop 的 settings.json：那个文件没有文档，随版本和平台变化，描述的是用户配置了什么，而不是 daemon 会做什么——这与产品对 LLM provider 采用的规则相同：capability 只有在经执行证明后才会声明。它有三种结果，且互不合并：已证明、已拒绝（变量不写入）以及无法证明——没有可挂载的本地镜像——这种情况会写入变量，并明确说明证明没有运行。

    通过菜单运行时，它只报告：bootstrap 菜单的每一项都故意以 /dev/null 作为 stdin 运行，所以它无法提问。要自己选择，请在你自己的终端中运行 node scripts/dev/consentir-base.mjs。

    # docker/docker-compose.yml — em `api` E `engine`, já escrito
    volumes:
      - ${BRABO_PROJECTS_BASE:-brabo_projects_base}:${BRABO_PROJECTS_BASE:-/data/brabo-projects-base}

    运维人员只需定义一次并重启 api + engine；永远不需要按项目编辑任何东西。在此之前，每个挂载的项目都需要在两个服务中手写一行 bind-mount 并重启一次——这会杀死安装中所有进行中的 agent 回合、终端 socket 和 LLM 调用。

    挂载是按同一路径的（$X:$X）：在宿主机和两个容器中是同一个绝对路径。正是这一点让用户输入、界面回显的字符串保持真实，也正因如此，projectScopeRoot（api）和 Engine.Actions.Workspace.workspace_dir/2（engine）不需要转换层。

    它不是 PROJECT_WORKSPACES_HOST_DIR，也绝不能指向同一个文件夹。 托管的 workspace 以 workspace_dir_name（UNIQUE）命名，而挂载的项目由用户命名，所以 <base>/loja 和文件夹名为 loja 的 container 项目会冲突，仓库的 bootstrap 会在别人的项目里运行 git init。ADR 中有另外两个理由。

    变量未定义时，不提供 Mounted 模式——绝不提供安装无法兑现的模式。并且当基础目录与 Brabo 检出目录在任一方向上重叠时，pnpm dev 拒绝启动；这项检查放在 preflight 中，因为它在宿主机上运行，而 api 只能与 process.cwd()（自己容器内的 /workspace）比较。参见 runbook。

    web

    web 是静态的，由 nginx 提供服务。它从两个来源读取配置，这个区别很重要：

    来源 何时 方式
    import.meta.env.VITE_* 构建时 嵌入 bundle。修改需要重新构建

    变量 用途
    VITE_API_URL api 地址

    为什么版本不经过 /config.js

    URL 属于环境：同一个镜像需要与 staging 的 api 和生产的 api 通信，这正是 /config.js 存在的意义（ADR 0024）。版本属于产物——镜像 brabo-web:1.1.2 不应该能报告别的东西。如果来自 /config.js，页脚就会变成一个可编辑字段而不是身份标识，一个错误的 ConfigMap 就会让界面对正在运行的构建撒谎。

    从提交到界面的完整路径：release.yml 计算 versao=${TAG#v} → 作为 VERSION 传给 docker buildx bake → docker-bake.hcl 的 web 目标把它转换为 VITE_BRABO_VERSION → docker/web/Dockerfile.prod 的 ARG/ENV 把它暴露给 pnpm build → Vite 把它嵌入 import.meta.env → runtime-config.ts 读取它 → AuthLayout 显示它。同一个 VERSION 也为 api 镜像的 BRABO_VERSION 提供输入（ADR 0036）。

    备份

    由备份镜像使用，而不是由应用使用——在 Kubernetes 中作为 CronJob，在 compose 安装中作为 docker compose run --rm backup …。详情见恢复；理由见 ADR 0152。

    容器 broker

    broker（ADR 0130）是产品中唯一与服务器上 Docker daemon 通信的进程，也是唯一挂载了 /var/run/docker.sock 的服务。在本地它随 pnpm dev 启动；在生产环境中它位于 profiles: ["container-broker"] 之下。 两个 compose 文件故意不同（ADR 0146，第 3 点）——不要把它们统一。

    它曾经在两者中都默认关闭，理由是还没有任何东西调用它。这个前提已经不成立：它有四个真实调用方，ADR 0144 让 Mounted 模式通过 broker 启动容器——所以在 profile 关闭时，默认的本地模式以 BrokerIndisponivelError 告终。支撑这种不对称的是 socket 在两边的含义：运行 pnpm dev 的人已经拥有它（他在运行 docker compose），而在生产环境中它是一道真实的权限边界，运维人员也不是开发者。

    这改变的是 broker 何时运行，绝不改变它接受什么：五层隔离都完好无损，它仍然接收一个 projectId 外加五种操作之一，任何地方都没有可以写入 privileged 或任意 -v 的参数。

    默认启动暴露了一个以前从未要紧过的缺陷：本地镜像在启动时安装依赖，而 broker 唯一的网络是 internal: true，所以无法访问任何 registry——容器以 getaddrinfo EAI_AGAIN registry.npmjs.org 死掉，而由于没有 healthcheck，up --wait 仍然打印 Healthy。现在依赖在构建时安装，服务也有了 healthcheck；网络没有改动，也不应改动。运维细节见 runbook。

    在生产环境中，显式启动它：

    docker compose -f docker/docker-compose.prod.yml \
  --profile container-broker up -d broker
    变量 默认值 出错时
    BROKER_URL 开发 compose 中为 http://broker:8090；生产和安装中为空（由 api 读取） 为空是正常状态：读取容器观测状态的地方会说"未观测"，而不是沿用登记的状态（RN-486），api 返回 brokerConfigurado: false，于是创建项目时只提供 runner（RN-573）。在本地 broker 默认启动，所以开发 compose 默认把它指向自己启动的服务（RN-599）——.env 中的值仍然优先。生产和安装用的 compose 故意没有默认值：在那里 broker 位于 profile 之下，开启它的人写入 URL
    BROKER_PORT 8090 broker 监听的端口。它不在宿主机上发布任何东西——只有 api 能通过 compose 的 internal: true 网络访问它
    BRABO_SERVICE_TOKEN 🔒 开发中为 dev-service-token-change-me 与 api ↔ engine 相同的密钥，放在同一个头里。当 NODE_ENV=production 时，如果它为空、是仓库中的公开字面值或少于 16 个字符，broker 拒绝启动——这是 RN-114 的规则，在这里守护的是一个与宿主机 Docker 通信的进程。BRABO_SERVICE_TOKEN_PREVIOUS 定义后遵循同样的规则，只是不是必填：去除空白，在生产环境中如果它是公开字面值或少于 16 个字符，broker 拒绝启动（RN-601）
    API_URL http://api:3000 broker 从这里读取架构师的决定。它不接收容器规格；而是主动来取（RN-485）
    PROJECT_WORKSPACES_HOST_ROOT — 项目文件夹在宿主机上的根目录，而不是任何容器内部的。没有它，start 会拒绝并指出这个变量，其他四种操作照常工作。不要把它与 PROJECT_WORKSPACES_ROOT 混淆，后者是容器内的路径：-v 由 daemon 针对宿主机文件系统解析，使用 api 内部的路径会让它创建并挂载一个空文件夹
    DOCKER_GID 999（compose） 宿主机 docker 组的 gid（getent group docker | cut -d: -f3）。socket 是 root:docker，而 broker 以非 root 运行，所以 compose 使用 group_add。默认值是最常见的，但在多个发行版上是错的。自 ADR 0146 起，这在每台开发机上都很重要，而不仅是有人开启了 profile 的地方——设错不会让启动失败，而是让使用失败：每个操作都会因 socket 上的 "permission denied" 而失败，而这只有在有人提议 container_start 时才会出现。pnpm dev 每次运行都会报告这个变量的状态（RN-512），在没有 docker 组的机器上会说"不适用"，而不是指责它

    PROJECT_WORKSPACES_HOST_ROOT 无法从托管的 Docker 卷推导出来。在开发 compose 中，它从 PROJECT_WORKSPACES_HOST_DIR（见上文）推导——所以不定义后者（刚复制的 .env.example 的状态）会让 broker 没有根目录，让 container 模式没有容器：栈健康地启动，而 container_start 以拒绝告终。pnpm dev 每次运行都会报告这一点，方式与 DOCKER_GID 相同，并且从不拒绝启动（RN-599）。它也会报告 ~ 的情况：Compose 会在 api/engine 使用的 bind-mount 来源中展开 ~，但不会在 broker 接收的变量中展开（用 docker compose config 测得），所以请写入已展开的路径。显式设置且与 api/engine 所挂载文件夹不同的 PROJECT_WORKSPACES_HOST_ROOT 会被报告为不一致——容器会收到一个 agent 从未写入过的文件夹。把托管卷换成宿主机文件夹不会迁移 project_workspaces 卷中已有的内容：数据留在那里，只是不再是 api 和 engine 看到的东西。

    BRABO_PROJECTS_HOST_BASE 是 broker 的第二个根目录——Mounted 项目的基础目录，同样位于宿主机上（ADR 0141，ADR 0144）。与上面那个不同，它不需要填写：compose 从 BRABO_PROJECTS_BASE 推导它，后者按定义就是宿主机路径（是 api 和 engine 按同一路径挂载的东西）。只有当 Docker daemon 通过另一条路径访问该文件夹时，才显式定义它。

    正是它让 Mounted 项目可以拥有容器（RN-503）：api 发送一个带判别字段的定位符（localizacao.tipo——gerenciada 或 montada）以及相对路径段，broker 针对相应的根目录解析它。两个根目录永远不会互相替代。缺少它会让 mounted 项目的 start 以 503 拒绝，并指出变量名，不触碰任何容器——回退到 PROJECT_WORKSPACES_HOST_ROOT 会挂载另一个项目的文件夹，因为托管根目录以 workspace_dir_name 命名，而基础目录由用户命名。

    开发容器的用户（构建时）

    同样不由我们的代码读取，甚至也不是运行时环境变量：它们是三个开发镜像（docker/api/Dockerfile、docker/web/Dockerfile、docker/engine/Dockerfile）的 Docker build.args，在 docker compose build 时读取一次，并嵌入每个容器运行所用的 USER。它们的存在是为了让容器以与你宿主机用户相同的 UID/GID 运行，而不是 root——写入 bind mount 的一切（apps/api/dist、mounted 执行模式下的项目 workspace）本来就属于你，之后不需要 sudo chown。

    变量 默认值 原因
    DEV_UID 1000 你的 id -u。不从 shell 的 ${UID} 读取——它在 bash 中是只读的，默认不导出到环境，所以 compose 文件总是看到它为空
    DEV_GID 1000 你的 id -g，道理相同

    1000/1000 与单个开发者最常见的 Linux 配置一致，也与 node:26-alpine（api/web 的基础镜像）自带的 node 用户一致——当你的组合匹配时，Dockerfile 会复用这个用户而不是新建一个。已经有在此变更之前以 root 运行的容器的环境，需要对命名卷 node_modules/_build/deps/.mix/.hex 做一次 chown（或执行 docker compose down -v 让它们被重建）——参见快速开始中的说明。

    生产和安装用的 compose 不同：engine 从生产镜像以固定用户 engine（uid/gid 1000，没有 DEV_UID）运行，带有 read_only: true 和挂载在 /home/engine 的 tmpfs。这个 tmpfs 声明为 uid=1000,gid=1000,mode=0700——不是变量——因为 semgrep（SecOps 的 gate）会在那里写 ~/.semgrep；如果以 root 创建，扫描不返回任何结果，gate 会在没有静态分析的情况下通过（RN-707，runbook O gate de SecOps está preso em "SAST não rodou"）。

    两个 engine 镜像都用构建参数 SEMGREP_VERSION 固定 semgrep（1.183.0，在 docker/engine/Dockerfile 和 Dockerfile.prod 中相同，由 scripts/ci/semgrep-do-engine.spec.ts 保持一致）。它是构建参数，不是运行时变量——.env 中什么都不用写。没有固定时，pip 取到了 1.179.0，而它不发布 musllinux wheel：在 Alpine 镜像中，包来自不含 semgrep-core 的 sdist，所有扫描都失败了。升级版本就是选择一个在 PyPI 上有 musllinux wheel 的 release，并在同一个 PR 中修改两个 Dockerfile。

    engine 镜像运行于 Alpine 3.24 上的 Elixir 1.20.4 / OTP 29.1.1（builder hexpm/elixir:1.20.4-erlang-29.1.1-alpine-3.24.2，runtime alpine:3.24.2，两者都按 digest——ADR 0209）。低于 29.1 的 OTP 在 CPU 带有 AMX 的宿主机上、在 Alpine 3.24 的 musl 1.2.6 下启动时会中止（sys_sigaltstack(): Internal error）；不要在不降级 musl 的情况下降级 OTP。.env 中什么都不用写。

    六个 Dockerfile 都不使用 corepack（Node 25+ 不再附带它，AT-360）：构建从 registry 的 tarball 安装 pnpm，并与写在 Dockerfile 中的 sha512 核对——构建参数 PNPM_VERSION（11.3.0，与 package.json 中 packageManager 相同，这样 pnpm 永远不会在运行时尝试下载另一个版本）和 PNPM_SHA512。它们是构建参数，不是运行时变量，.env 中没有要定义的东西：升级 pnpm 就是在同一个 PR 中修改 packageManager、各 workflow 的 PNPM_VERSION 以及六个 Dockerfile 中的两个参数——参见 runbook 中关于 broker 镜像的一节。
