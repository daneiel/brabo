    Broker контейнеров

    Broker (ADR 0130) — единственный процесс продукта, который говорит с демоном Docker, и единственный сервис со смонтированным /var/run/docker.sock. Не монтируйте этот сокет больше нигде.

    Локально он поднимается с pnpm dev; в production — нет. Эта асимметрия — решение (ADR 0146, пункт 3), а не недосмотр: не «унифицируйте» два файла compose. Тот, кто запускает pnpm dev, уже имеет сокет Docker (он запускает docker compose против демона собственного хоста), поэтому передача его broker-у не даёт ничего, чего у оператора ещё нет. В production сокет — настоящая граница привилегий, а оператор — не разработчик, поэтому там он остаётся под profiles: ["container-broker"].

    До этого решения broker по умолчанию был выключен в обоих файлах с аргументом, что «его пока ничто не вызывает». Это перестало быть правдой: у него четыре реальных вызывающих (ADR 0133/ 0136), а ADR 0144 заставил режим Pasta montada поднимать свой контейнер через broker — так что при выключенном profile локальный режим по умолчанию заканчивался BrokerIndisponivelError. Этот отказ по-прежнему то, что вы получаете, когда broker действительно отсутствует: ИМЕНОВАННЫЙ failed, никогда не падение и никогда не молчаливый откат к запуску вне контейнера.

    Что ещё нужно задать — это gid, и ошибка в нём не ломает загрузку, она ломает использование:

    # o gid do grupo docker do seu host — o default do compose (999) é o mais
# comum e está errado em várias distribuições
getent group docker | cut -d: -f3

# no .env
#    DOCKER_GID=<o número acima>
#    PROJECT_WORKSPACES_HOST_DIR=/home/you/brabo-projects    # JÁ EXPANDIDO; deriva HOST_ROOT
#    GIT_LOCAL_REPOS_HOST_DIR=/home/you/brabo-projects-bare
#    BRABO_PROJECTS_BASE=/home/you/projetos-brabo            # deriva HOST_BASE

docker compose -f docker/docker-compose.yml --env-file .env up -d api engine broker

    BROKER_URL в этом списке больше нет: у compose dev значение по умолчанию — http://broker:8090, сервис, который он поднимает (RN-599). До этого значения по умолчанию api отвечала brokerConfigurado: false рядом со здоровым broker-ом, и создание проекта предлагало только runner. Значение в .env по-прежнему побеждает; у compose production и установки значения по умолчанию нет — намеренно.

    Контейнер проекта работает от имени владельца папки проекта (ADR 0180, RN-627): api читает uid и gid папки, и broker запускает его с --user <uid>:<gid> и HOME=/tmp. Именно это позволяет dev agent писать в /work под --cap-drop ALL. Две вещи, которые нужно знать, когда это не работает: папка root, нечитаемая или отсутствующая, приводит к прежнему поведению (root внутри контейнера, без записи в папку другого uid — npm install отвечает EACCES); а уже существующий контейнер меняется только при пересоздании (container_remove, затем container_start).

    pnpm dev также сообщает об управляемой папке при каждом запуске (RN-599): при незаданной PROJECT_WORKSPACES_HOST_DIR api/engine используют управляемый том, broker не получает PROJECT_WORKSPACES_HOST_ROOT, и container_start заканчивается отказом — при здоровом стеке. Он сообщает также о ~ в пути (Compose раскрывает его в bind mount, но не в переменной broker-а) и о явном PROJECT_WORKSPACES_HOST_ROOT, отличающемся от папки, которую монтирует api. Как и предупреждение о gid, он никогда не блокирует и никогда не пишет в .env; замена тома на папку не переносит содержимое тома — см. перенос workspaces.

    pnpm dev сообщает о состоянии DOCKER_GID при каждом запуске (RN-512), сравнивая его с реальной группой вашей машины, именно для того, чтобы расхождение не обнаружилось слишком поздно — когда кто-то предлагает container_start и каждая операция умирает с permission denied на сокете. Предупреждение никогда не блокирует, а на машине вообще без группы docker (Docker Desktop, rootless) оно говорит, что вопрос неприменим, вместо того чтобы обвинять вас в дефекте.

    В production поднимайте его явно:

    docker compose -f docker/docker-compose.prod.yml \
  --profile container-broker up -d broker

    В установке, выполненной через install.sh, broker — тот же сервис из опубликованного образа, и установщик спрашивает, включать ли его — см. broker в установке (ADR 0162).

    У broker-а ДВА корня, и ни один не заменяет другой (RN-503, ADR 0144). PROJECT_WORKSPACES_HOST_ROOT — место, где живут проекты режима Container; BRABO_PROJECTS_HOST_BASE — место, где живут проекты режима Pasta montada, и compose выводит его из BRABO_PROJECTS_BASE, так что задания базы обычно достаточно. Какого бы ни не хватало, отказ называет его и не трогает ни одного контейнера. Переход к другому корню смонтировал бы папку не того проекта — управляемый корень именуется по workspace_dir_name, база именуется вами, и одно и то же имя означает разные папки в каждом из них.

    Чтобы проверить, что он запущен, — из api, единственного сервиса, который до него дотягивается (сеть broker — internal: true, и сервис не публикует ни одного порта, поэтому curl с вашего хоста не сработает, и в этом весь смысл):

    docker compose -f docker/docker-compose.yml --env-file .env exec -T api \
  node -e "fetch('http://broker:8090/health').then(r=>r.text()).then(console.log)"
# esperado: {"status":"ok","servico":"broker"}

    /health говорит о ПРОЦЕССЕ, никогда о демоне. Перезапуск broker-а не чинит упавший Docker, а healthcheck, падающий по этой причине, породил бы цикл перезапусков, который ничего не решает.

    Локальный образ устанавливает зависимости при BUILD, и это не оптимизация. Единственная сеть broker-а — internal: true, поэтому в runtime нет доступного registry: образ, который запускал corepack/pnpm install при старте, умирал с getaddrinfo EAI_AGAIN registry.npmjs.org и завершался с 1. Исправление убрало registry с пути runtime (pnpm install как шаг build), вместо того чтобы открыть сеть — сеть является первым из пяти слоёв сдерживания. Начиная с AT-360 ни один образ не использует corepack (Node 25+ его больше не содержит): каждый Dockerfile устанавливает pnpm из tarball registry, проверенного по sha512, записанному в Dockerfile (PNPM_SHA512), в /usr/local/bin. Его версия совпадает с packageManager в package.json, поэтому pnpm никогда не пытается ничего скачать в runtime — измерено на образе dev под --network none: pnpm --version печатает 11.3.0, и /health отвечает. Обновление pnpm означает совместное изменение packageManager, PNPM_VERSION и PNPM_SHA512 (npm view pnpm@<v> dist.integrity, в hex).

    Два следствия, с которыми вы столкнётесь:

    • Три node_modules — именованные тома, смонтированные поверх того, что установил образ, а Docker заполняет том из образа, только когда том ПУСТ. Поэтому docker/broker/entrypoint.sh сверяет их с копией, хранящейся вне /workspace и помеченной sha256 того pnpm-lock.yaml, с которым был собран образ. Первая загрузка после --build пишет sincronizando… и занимает несколько секунд; последующие ничего не пишут.
    • Изменение зависимости broker-а требует up -d --build broker. Entrypoint сравнивает свою метку с lockfile рабочего дерева и ПРЕДУПРЕЖДАЕТ, когда они различаются. Он предупреждает, а не отказывается загружаться: у broker-а нет зависимостей runtime, кроме ссылки workspace на @brabo/docker-port, и замена предупреждения недоступностью была бы хуже.

    У сервиса также есть healthcheck (wget к 127.0.0.1:8090/health изнутри контейнера — он не публикует порт, а в node:26-alpine нет curl). Без него up --wait сообщал Healthy в момент старта контейнера, и scripts/dev/reset-total.sh объявлял «reset completo» с broker-ом, умершим пятью секундами раньше.

    Перенос workspaces в локальную папку

    Задание PROJECT_WORKSPACES_HOST_DIR/GIT_LOCAL_REPOS_HOST_DIR (Первые шаги) заменяет том Docker указанной папкой — но не копирует то, что уже было в старом томе. Тому, у кого уже есть созданные проекты и кто не хочет потерять работу, нужно скопировать содержимое до замены:

    pnpm dev:down
docker run --rm \
  -v brabo-dev_project_workspaces:/de \
  -v "$(realpath ~/brabo-projetos)":/para \
  alpine sh -c 'cp -a /de/. /para/'
docker run --rm \
  -v brabo-dev_git_local_repos:/de \
  -v "$(realpath ~/brabo-projetos-bare)":/para \
  alpine sh -c 'cp -a /de/. /para/'
# defina as duas variáveis no .env, depois:
pnpm dev

    Имя тома (brabo-dev_project_workspaces) несёт префикс проекта Compose (name: brabo-dev в docker/docker-compose.yml, ADR 0170) — проверьте через docker volume ls. У среды dev, созданной до ADR 0170, данные ещё лежат под brabo_*: сначала см. Перенос среды dev в brabo-dev. Старый том продолжает существовать и после (Compose не удаляет том, вышедший из употребления); удалите его через docker volume rm, когда будете уверены, что копирование сработало.

    Проект в режиме Pasta montada: база проектов

    Симптом: мастер проекта даже не предлагает Pasta montada; или предлагает, а api отвечает 400, сообщая, что папка не существует изнутри api.

    Оба случая проистекают из одного факта: проект в режиме Pasta montada хранит код в вашей папке, а api и engine добираются до неё, только если она смонтирована в их контейнеры. Изменилось (ADR 0141, RN-500) то, кто это устраивает и как часто: теперь есть одна база, настраиваемая оператором один раз, и каждый смонтированный проект живёт внутри неё. Вам больше никогда не нужно править compose для каждого проекта.

    Что делать — один раз, для всей установки. Поддерживаемый путь — шаг согласия (ADR 0146), который предлагает папку, отклоняет ту, что пересекается с checkout-ом Brabo или с PROJECT_WORKSPACES_HOST_DIR, проверяет на macOS/Windows, что Docker её видит, создаёт её и записывает переменную:

    node scripts/dev/consentir-base.mjs

    Запускайте его в своём терминале. pnpm bootstrap → Docker › Base de projetos запускает тот же скрипт, но может только сообщить: каждый пункт меню намеренно запускается со stdin из /dev/null, поэтому он не может задавать вопросы.

    Ручная запись строки по-прежнему работает:

    # .env — caminho ABSOLUTO. O `~` NÃO é expandido pelo Compose.
BRABO_PROJECTS_BASE=/home/voce/projetos-brabo

    docker compose -f docker/docker-compose.yml --env-file .env up -d api engine

    Вот и всё. Отныне проект в режиме Pasta montada попадает куда-то под /home/voce/brabo и больше не требует настройки.

    Самой папке пока не обязательно существовать (ADR 0142, RN-501). Создание проекта Pasta montada проверяет только ФОРМАТ пути плюс «находится под базой»; папка создаётся позже, когда Infra поднимает контейнер проекта, — именно это позволяет мастеру для начала ПРЕДЛОЖИТЬ <base>/<slug do projeto>. Между этими двумя моментами workspacePath указывает на папку, которой там ещё нет, а workspaceVerifiedAt проекта равен null; конвертация существующего проекта в Pasta montada — единственное исключение и создаёт папку сразу, потому что переносит permissions.json внутрь неё.

    Поэтому 400 при создании теперь означает лишь одно из двух, и оба называют то, что имеют в виду: путь не находится под базой (сообщение называет базу и предлагает <base>/<nome>), или BRABO_PROJECTS_BASE вообще не настроена (сообщение говорит, что РЕЖИМ недоступен в этой установке). Папка, которую api не может создать или до которой не может добраться, проявляется позже, как ИМЕНОВАННЫЙ failed в действии container_start — никогда не 500, и жизненный цикл контейнера при этом не помечается provisioning.

    Смонтированные проекты получают настоящий контейнер, и он работает на СЕРВЕРЕ (RN-503, ADR 0144). Поскольку база доступна демону Docker хоста, container_start проекта Pasta montada идёт в broker, точно как режим Container, — он перестал требовать подключённого brabo-runner. Только режим Runner по-прежнему идёт в runner, на собственной машине пользователя, потому что та папка находится там, где этот сервер её не видит. Локально broker уже запущен — он идёт вместе с pnpm dev начиная с ADR 0146, именно потому, что это путь режима по умолчанию; в production ему всё ещё нужен --profile container-broker. Этот же шаг — момент, когда создаётся папка выше, в таком порядке: демон делает bind-mount только той папки, которая уже существует.

    Почему мастер скрывает режим Pasta montada. Без BRABO_PROJECTS_BASE api сообщает projectsBase: null, и вариант даже не предлагается. Это сделано намеренно: предложение режима, который установка не может обеспечить, порождает проект, который ломается позже, на первом инструменте первого агента, далеко от экрана, где было принято решение. Режим Container (по умолчанию) и режим Runner не затронуты и продолжают работать без этой переменной.

    Почему один и тот же путь с обеих сторон. База монтируется по идентичности — /home/voce/brabo:/home/voce/brabo — в api и engine одинаково. Путь записывается ОДИН раз в projects.workspace_path и читается обоими процессами (RN-169); это также строка, которую экран показывает вам обратно. Монтирование в другое место заставило бы engine писать туда, где api не читает, и заставило бы экран показывать путь, который не существует ни на вашей машине, ни на их.

    Проверьте, что контейнеры видят на самом деле:

    docker compose -f docker/docker-compose.yml exec api    ls -la /home/voce/brabo
docker compose -f docker/docker-compose.yml exec engine ls -la /home/voce/brabo

    Не направляйте базу на сам checkout Brabo. pnpm dev отказывается поднимать стек, когда BRABO_PROJECTS_BASE содержит или содержится в клонированном вами репозитории, — он называет оба пути и останавливается. Эта проверка живёт в preflight и больше нигде — намеренно: api сравнивает путь проекта с process.cwd(), который внутри её контейнера равен /workspace, поэтому она не может увидеть ваш настоящий checkout. Без защиты preflight клонирование Brabo в $HOME/brabo и задание базы на ту же папку проходит любую проверку и запускает dev agents внутри собственного дерева продукта — тот самый сбой, для предотвращения которого существует ADR 0055.

    Выберите выделенную папку. Всё под базой доступно изнутри контейнеров продукта. Не направляйте её на весь ваш $HOME и не направляйте на папку, где хранятся другие ваши секреты.

    Известные ограничения, объявленные, а не скрытые. Symlink под базой, указывающий за её пределы, разрешается внутри контейнеров иначе, поскольку цель не смонтирована, — браузер папок отказывается спускаться по symlink-ам, а дисковая проверка ловит расхождение как именованный сбой. И эта версия поддерживает одну базу: код, который живёт в другом месте, нужно перенести внутрь неё.

    Переход со старых монтирований по проектам. Поддерживаемый путь отныне — база; перенесите эти папки внутрь неё и уберите написанные вручную строки, когда будет возможность.

    Не путайте это с режимом Container. Проект в режиме Container (по умолчанию) продолжает использовать PROJECT_WORKSPACES_ROOT и процедуру переноса выше; режим Pasta montada никогда не трогает этот корень, и база никогда не является той же папкой, что этот корень (ADR 0141 объясняет, почему их смешение привело бы к тому, что два проекта попадут в одну папку).

    База проектов runner-а

    Симптом: brabo-runner завершается с кодом 2, сообщая base de projetos recusada (…), или начинает с печати base de projetos: nenhuma configurada, когда вы ожидали базу, или говорит, что он Seguindo SEM base.

    Это другая база, не та, что в Проект в режиме Pasta montada. Та (BRABO_PROJECTS_BASE) принадлежит СЕРВЕРУ и является единственной папкой, которую видят контейнеры; эта принадлежит машине пользователя и является местом, где локальный агент создаёт папку каждого проекта (ADR 0151, RN-529). Это никогда не одна и та же переменная, никогда не один и тот же файл, и они никогда не проверяются друг против друга.

    Откуда runner её читает, по порядку:

    1. --base <caminho absoluto> в командной строке;
    2. $XDG_CONFIG_HOME/brabo/runner.json — с откатом на ~/.config/brabo/runner.json — в форме {"base": "/abs/path"}.
    cat "${XDG_CONFIG_HOME:-$HOME/.config}/brabo/runner.json"
# {"base":"/home/you/projetos-brabo"}

    Отсутствие базы — это нормально. Runner без базы продолжает обслуживать свой проект точно так же, как всегда; чего он не может — это разместить папку проекта, созданного позже. Стартовая строка всегда говорит, в каком из двух состояний вы находитесь.

    Эта папка перестала быть только конфигурацией: начиная с RN-551 это также место, куда brabo-runner device-key create кладёт приватный ключ устройства машины (brabo-runner-device-key.jwk.json, режим 600) — см. Ключ устройства через терминал. Делайте её бэкап как бэкап секрета или не делайте бэкап вовсе и выполните сопряжение заново: ключ отзываем и заменяем, и больше ничто в продукте не может его прочитать.

    Отказы и почему их обработка различается. База отклоняется, когда она относительная, содержит .., равна /, указывает на существующий файл, находится вне $HOME в Linux (то же правило, что у --dir начиная с RN-434), или находится внутри папки текущего проекта (или равна ей) — последнее заставило бы каждый новый проект рождаться внутри этого. При получении из --base это завершает процесс с кодом 2; при получении из файла это печатается в stderr, и runner продолжает без базы, потому что убивать агента, обслуживающего проект, из-за конфигурации, которую он ещё даже не использует, было бы непропорционально. Файл, который существует и не объявляет base, — это отсутствие, а не отказ.

    Проект вне базы — не проблема. --dir проверяется точно так же, как всегда, и база в этом не участвует: база — правило СОЗДАНИЯ. Не «чините» устаревший проект, перенося его внутрь базы, чтобы что-то заглушить, — ничто не жалуется.

    Агент машины: одно подключение на проект

    Симптом: brabo-runner запущен без --project и либо напечатал блок использования, либо сказал nenhum projeto em modo "runner" para esta conta, либо обслужил одни проекты и отклонил другие.

    Начиная с RN-544 (ADR 0154) запуск без --project — настоящий режим: агент запрашивает GET /runner/projects и открывает одно подключение на проект, укоренённое в <base>/<workspaceDirName>. Режим с --project никак не изменился. Чтение вывода:

    • Sem --project, este runner só roda como agente de MÁQUINA… — нет согласованной базы. Требуются оба условия, и по разным причинам: учётные данные машины — то, что принимает маршрут, база — откуда берётся папка каждого проекта. См. базу выше.
    • a api recusou a descoberta de projetos: esta credencial está presa a um PROJETO — 403. Используемые учётные данные (PAT или ключ устройства из потока браузера) называют проект, и обнаруживать нечего. Запустите его с --project <projectId> вместо этого или выполните сопряжение ключа машины — материал ключа создаётся прямо здесь (brabo-runner device-key create, см. ниже), а регистрация публичной половины — то, что делает установщик. На диске оба вида — один и тот же файл, поэтому runner не угадывает: сервер — авторитет, и его сообщение передаётся дословно.
    • nenhum projeto em modo "runner" para esta conta — nada a atender AINDA — это нормальное состояние новой установки, и начиная с RN-550 процесс остаётся запущенным и продолжает спрашивать: 15s, затем 30s, затем 60s между вызовами, повторяя бесконечно, пока не появится первый проект.     Unit в состоянии bad-setting и никогда не стартует

    Симптом: service install сообщил об успехе, файл unit на диске, и тем не менее ничего не работает:

    $ systemctl --user status brabo-runner.service
   Loaded: bad-setting (Reason: Unit brabo-runner.service has a bad unit file setting.)
   Active: inactive (dead)
brabo-runner.service:16: WorkingDirectory= path is not absolute: "/home/<you>/.config/brabo"

    Причина. Unit-ы, записанные до этого исправления, заключали рабочий каталог в кавычки (WorkingDirectory="/home/…"). Две половины файла unit не разделяют синтаксис: ExecStart= интерпретируется со снятием кавычек и разделением на слова, поэтому каждый аргумент заключается в кавычки; WorkingDirectory= — нет: systemd берёт остаток строки как путь. С кавычками значение перестаёт начинаться с /, unit отклоняется при загрузке и никогда не стартует — в любом из видов (по проекту и по машине одинаково, RN-518 и RN-545).

    Исправление: переустановите. service install перезаписывает файл целиком, поэтому нет шага починки и нечего править вручную:

    brabo-runner service install --machine \
  --dir "${XDG_CONFIG_HOME:-$HOME/.config}/brabo" \
  --api-url http://localhost:3000
# ou, para uma unit por projeto, de dentro da pasta daquele projeto:
brabo-runner service install

    status и uninstall продолжают работать с unit в сломанном состоянии — папка считывается обратно в любой из форм, — так что ничего не застревает, если вы предпочтёте сначала её удалить.

    Связанное, но другое: unit, который загружается, но стартует не в той папке. WorkingDirectory= проходит раскрытие спецификаторов, поэтому буквальный % в пути нужно писать как %%; CLI теперь его экранирует, но вручную отредактированный unit с /home/you/50%off молча стартует в /home/you/50<os-id>ff — абсолютный, принятый и неверный. Проверяйте разрешённое значение, никогда не файл:

    systemctl --user show -p WorkingDirectory brabo-runner.service

    То же относится к окружению, которое unit замораживает (AT-095). Unit-ы, записанные до этого исправления, несли Environment=XDG_CONFIG_HOME=<pasta> и Environment=PATH=<caminho> без кавычек, а Environment= как разделяет по пробелам, так и раскрывает спецификаторы: с XDG_CONFIG_HOME=/home/you/50%off com espaco служба получала /home/you/50<os-id>ff — загружается, стартует, и агент машины ищет базу и ключ устройства в папке, которой не существует, ничего не сообщая. CLI теперь записывает присваивание целиком в кавычках (Environment="XDG_CONFIG_HOME=…", с экранированными \, " и %). Исправление: переустановите, как выше. Проверьте, что разрешил systemd:

    systemctl --user show -p Environment brabo-runner.service

    Ключ устройства через терминал

    Симптом: машине нужен ключ устройства, а браузера для запуска автоматической настройки с экрана проекта нет — новая установка, машина без экрана или агент машины выше, отказывающий с esta credencial está presa a um PROJETO.

    Начиная с RN-551 (ADR 0155, пункт 4) пара генерируется на машине, в два шага:

    # 1) gere aqui; a JWK PÚBLICA é a única coisa no stdout
PUB=$(brabo-runner device-key create)

# 2) registre essa chave pública na api — quem tem a credencial para
#    registrar faz isso; o CLI nunca fala com a api
ID=$(… POST {"name":"…","publicKeyJwk":'"$PUB"'} … | jq -r .id)

# 3) carimbe o id do registro como o `kid` da JWK e escreva o arquivo de verdade
brabo-runner device-key finish --id "$ID"
    • Два шага — из-за kid. Он ЯВЛЯЕТСЯ id записи на сервере (RN-475) и существует только после регистрации публичной половины; приватный ключ, записанный до него, бесполезен, и CLI отклоняет его навсегда. Поэтому create пишет brabo-runner-device-key.jwk.json.parcial — имя, которое читатель игнорирует, — а finish пишет настоящий. Файл, который читает runner, никогда не существует без kid — прерывание между двумя шагами оставляет .parcial, который runner игнорирует и который называет следующий create.
    • Где: $XDG_CONFIG_HOME/brabo/ (иначе ~/.config/brabo/), рядом с runner.json, в режиме 600; --dir <pasta> пишет в другое место (например, в папку проекта). Эта папка — то, куда должен указывать --dir unit-а машины (brabo-runner service install --machine --dir <pasta>, RN-545) — runner читает ключ из папки, в которой он РАБОТАЕТ, никогда не из глобального пути, который он угадывает.
    • stdout — для скриптов, stderr — для людей. create печатает только публичный JWK; finish — только путь к готовому файлу.
    • Отказы: finish без create (нечего штамповать), без --id, с --id, внутри которого всё ещё целый JSON-ответ, .parcial, который не является приватным JWK Ed25519, и — в обеих командах — ПОЛНЫЙ ключ, уже лежащий на месте. У последнего нет --force: молчаливая замена ключа уже сопряжённой машины оставила бы агента, подписывающего ключом, которого сервер не знает. Отзовите текущий ключ (RN-519), удалите файл, затем снова create.
    • CLI не утверждает, какого вида ключ. На диске ключ машины и ключ проекта — один и тот же файл; решает маршрут, который зарегистрировал публичную половину.

    Когда установщик не завершает установку

    Симптом: install.sh завершился блоком «O que ficou pendente», или у новой установки есть вход, через который никто не может пройти, нет ключа устройства машины или нет запущенной службы агента.

    Начиная с RN-547 (ADR 0155) установщик завершает установку: он создаёт первую учётную запись, регистрирует ключ устройства этой машины и устанавливает unit машины. Цепочка такова:

    1. POST /internal/first-account (RN-546) — учётная запись рождается уже подтверждённой, потому что MAIL_TRANSPORT равен log и установщик не включает SMTP;
    2. brabo-runner device-key create (RN-551) — пара Ed25519 генерируется на машине; передаётся только публичная половина;
    3. POST /internal/machine-device-keys (RN-552) — возвращённый id становится kid приватного JWK (RN-475);
    4. brabo-runner device-key finish --id <id>;
    5. brabo-runner service install --machine (RN-545).

    Ничто никогда не откатывается, и каждый сбой назван. Установщик всегда завершается с 0: compose запущен, а уже выполненные звенья полезны сами по себе. То, что не удалось, печатается в конце с точной командой для повтора.

    • service install --machine отказал. Это обычный случай на машине разработчика, а не граничный: он отказывает, когда unit по проекту уже установлен, и --force нет — два процесса боролись бы за один проект, и сервер отказал бы одному из них. Отказ называет uninstall каждого найденного unit. Удалите их, затем снова выполните последний шаг, который напечатал установщик:

      brabo-runner service uninstall --project <projectId>   # para cada uma nomeada
brabo-runner service install --machine \
  --dir "${XDG_CONFIG_HOME:-$HOME/.config}/brabo" \
  --api-url http://localhost:3000

      Папка в --dir — та, куда был записан ключ, — никогда не папка проекта, в которой лежал бы brabo-runner.config.json и которая заставила бы unit стартовать в режиме проекта, молча обслуживая один проект, называя себя агентом машины.

    • Регистрация ключа не удалась. …jwk.json.parcial намеренно остаётся на месте. Он инертен — runner не читает это имя — и установщик не удаляет его: timeout после commit в api неотличим от timeout до него, так что этот файл может быть единственной копией приватной половины ключа, который уже зарегистрирован. Запустите установщик снова или завершите вручную, если знаете id записи (brabo-runner device-key finish --id <id>). Следующий device-key create назовёт его и заменит.

    • Шаг учётной записи сообщил, что в установке уже есть пользователь. Это 409, и это ожидаемый исход, а не сбой — второй запуск или миграция (RN-530), чей restore вернул пользователей. Войдите существующей учётной записью. Шаги ключа машины и службы в этом случае пропускаются по замыслу: выпускать долговременные учётные данные для того, кто не просил их в этом запуске, — не дело установщика.

    • Пароль отклонён. Политика — доменная, та же, что использует регистрация, и о ней становится известно только после POST — поэтому установщик спрашивает снова, до трёх раз, и превращает исчерпанный предел в незавершённую строку, а не прерывает уже запущенную установку. Он никогда не записывает пароль никуда: ни в .env, ни в маркер, ни в лог. В маркер попадает только e-mail (ownerEmail, schemaVersion: 3).

    • Без TTY. Установщик сообщает и завершается с 0 до того, как что-либо записать. Запускайте его из терминала, как скачанный файл — curl -fsSLO …/install.sh && bash install.sh — никогда curl … | sh (загрузка становится stdin процесса и убивает каждый вопрос) и никогда sh -c "$(curl …)", который не может проверить собственный хеш. Оба отклоняются по имени; см. Установка.

    • Агент запущен, но ничего не обслуживает. Это нормальное состояние новой установки: он ждёт и снова опрашивает, пока не появится первый проект в режиме runner (RN-550). См. Агент машины.

    Папка проекта так и не появляется на машине пользователя

    Симптом: ожидалось, что папка проекта появится под базой runner-а, а она не появилась. В логе engine есть строка, начинающаяся с workspace_create: o projeto <id> não criou pasta —, и папка отсутствует.

    Сообщение называет, какое из двух предусловий не выполнено (RN-532, ADR 0151, пункты 3–6), и они единственные два — контейнер не требуется, намеренно: требовать его было бы циклично, поскольку проект runner доходит до зарегистрированного контейнера running только после того, как runner поднимет его поверх той самой папки, для создания которой существует это сообщение.

    • nenhum brabo-runner está conectado a este projeto agora — запустите агента для этого проекта; флаги см. в базе выше.
    • não declarou a capacidade workspace no join — подключённый бинарник либо старше этой версии, либо работает без согласованной базы. Оба исправления — в предыдущем разделе: запустите установщик или запустите runner с --base. Отказ назван намеренно, потому что у двух причин разные исправления; сам join НЕ отклоняется, так что runner продолжает нормально обслуживать свой проект.
    • o brabo-runner recusou criar a pasta — сообщение несёт причину самого runner-а: segmento (сегмент вышел за базу — защита отказала, ничего не создано), nao-e-pasta (цель уже существует как файл; этот CLI никогда его не перезаписывает), mkdir (права или диск) или git (git init/clone не удался — папка СУЩЕСТВУЕТ, и никакой план Б намеренно не пробовался).
    • não respondeu ... a tempo — большой clone может превысить предел. Проверьте машину runner-а; на стороне сервера ничего не остаётся записанным наполовину, потому что запись происходит только через workspace_confirm.

    Папка, которая уже существует как git-репозиторий, — это успех, а не ошибка: операция идемпотентна и сообщает ja-era-repositorio в логе runner-а.

    Аутентифицированный clone в режиме Runner отклоняется, пока контейнер запущен

    Симптом: dev agent в проекте runner блокируется при подготовке worktree, и диагностика говорит, что учётные данные не удалось передать, называя credencial-nao-atravessa-o-container. Источник заблокированной задачи — politica, а не codigo.

    Это не баг, который надо ловить, и именно это вам говорит источник (RN-558). Учётные данные аутентифицированного remote (ADR 0056) могут передаваться только в поле env сообщения exec, а это поле действует только для пути хоста: у порта Docker продукта нет поля env, намеренно (ADR 0130, без свободного -e). Когда runner поднял контейнер проекта, он направляет каждую команду внутрь него — так что учётным данным некуда деваться.

    До RN-558 команда всё равно выполнялась, с пустыми переменными, и вы видели обычный сбой аутентификации. Теперь она отклоняется до выполнения, и ничего не запускается. Отказ никогда не печатает ни имён, ни значений переменных, только их количество.

    Начиная с ADR 0193 (RN-676) этот отказ больше не происходит на обычном пути: engine помечает аутентифицированный fetch (gitCredenciado), и актуальный runner выполняет его на хосте даже при запущенном контейнере — та же папка, смонтированная в /work. Если вы всё ещё его видите, подключённый brabo-runner старше этого изменения и не читает метку.

    Что делать:

    1. Обновите brabo-runner на машине пользователя и перезапустите его (или его службу). Это и есть исправление.
    2. Если обновить сейчас нельзя: остановите контейнер проекта (страница /containers, «Parar») и дайте worktree материализоваться — на пути хоста учётные данные передаются нормально, и начальный fetch проходит. Затем снова поднимите контейнер; clone идемпотентен и не повторяется.

    Локальный репозиторий (без токена) не затронут, как и проекты container и mounted — они никогда не проходят этим путём. Не затронут и workspace_create, который выполняется на хосте.

    Что остаётся открытым, объявлено: учётные данные по-прежнему не проходят через docker exec. Закрыть это — значит решить, как операция с учётными данными говорит с docker exec без поля env, и каждый известный вариант затрагивает границу сдерживания — это ADR, а не попутное исправление.

    Контейнеры dev пишут от имени вашего пользователя, а не root

    Симптом: что-то, что контейнер dev api, web или engine записал в bind mount — apps/api/dist, node_modules, файл, который агент сгенерировал внутри проекта в режиме выполнения mounted, — принадлежит root на вашем диске, и его редактирование или удаление без sudo не удаётся.

    Это было ожидаемо: образы dev (docker/api/Dockerfile, docker/web/Dockerfile, docker/engine/Dockerfile — в отличие от Dockerfile.prod, уже не-root начиная с ADR 0024) не имели директивы USER и работали от root. Теперь они работают с тем же UID/GID, что и ваш пользователь хоста, через build args DEV_UID/DEV_GID (Конфигурация), так что этот класс проблем не должен вернуться.

    Если вы всё ещё это видите:

    1. Подтвердите свою пару через id -u/id -g. Если это не 1000/1000, задайте DEV_UID/DEV_GID в .env (см. .env.example) и пересоберите: docker compose -f docker/docker-compose.yml build api web engine.

    2. Среда, предшествующая этому исправлению. Именованные тома (*_node_modules, engine_build, engine_deps, engine_mix, engine_hex) всё ещё хранят содержимое, записанное старыми контейнерами от root, — совершенно новый именованный том наследует правильного владельца при первом монтировании, но существующий не исправляется задним числом. Обнулите его один раз, либо удалив тома (docker compose -f docker/docker-compose.yml down -v — безопасно для этих, это воспроизводимые артефакты build, никогда не источник истины), либо выполнив над ними chown на месте:

      docker run --rm -v brabo-dev_api_app_node_modules:/v alpine chown -R "$(id -u):$(id -g)" /v
# repita para os outros volumes node_modules/_build/deps/.mix/.hex

      Совершенно новые тома (первый clone или машина, на которой запускался только установщик, не определяющий ни один из этих томов) падали по-другому: api и web завершались с EACCES: permission denied, mkdir '/workspace/node_modules/.pnpm', потому что новый том наследует владельца пути в образе, а этого пути там не было, поэтому он рождался root:root (AT-172). docker/api/Dockerfile и docker/web/Dockerfile теперь создают три точки монтирования node_modules и выполняют над ними chown до USER. Точки монтирования внутри bind mount на вашем диске — отдельная половина: Docker создаёт отсутствующую на хосте как root (он оставил packages/shared/node_modules с владельцем root в checkout-е), и никакой образ не может этого изменить. pnpm dev запускает scripts/dev/preflight.mjs, который заранее создаёт их от вашего имени; docker compose up, запущенный вручную, его пропускает, поэтому выполните pnpm dev:preflight один раз перед первым ручным up.

    3. Для файла, уже записанного агентом в папку проекта в режиме mounted на хосте, исправление — тот же sudo chown -R $USER <pasta>, который этот раздел предписывал для всего репозитория, — теперь он точечный для существовавших ранее файлов, а не постоянный обходной путь.

    4. Два тома ДАННЫХ — другой случай, и down -v для них НЕ безопасен. /data/git-repos и /data/project-workspaces монтируются в api и engine как именованные тома. Именованный том рождается с владельцем того, что существует по этому пути в образе, — а когда пути не существует, он рождается root, оставляя не-root процесс за бортом. Образы dev начали создавать их и выполнять chown до USER лишь недавно; образы production делали это всегда. Симптом — не файл, который вы не можете редактировать на своём диске: это git init --bare у LocalGitProvider, умирающий с permission denied: /data/git-repos/<slug>.git, и permissions.json каждого проекта, которому негде записаться, — то есть provisioning репозитория невозможен.

      В отличие от томов артефактов build выше, эти два хранят источник истины (локальные bare-репозитории, worktrees по проектам), так что их удаление теряет данные. Исправьте их на месте:

      docker run --rm -v brabo-dev_git_local_repos:/v alpine chown -R "$(id -u):$(id -g)" /v
docker run --rm -v brabo-dev_project_workspaces:/v alpine chown -R "$(id -u):$(id -g)" /v

      Том, созданный после исправления, уже поднимается с правильным владельцем. Когда вы добавляете новый именованный том, создайте каталог в образе: забыть — это не ошибка build, это permission denied в runtime.

    Полный сброс среды dev

    bash scripts/dev/reset-total.sh      # ou: pnpm bootstrap → Docker › Reset total

    Пересобирает образы, удаляет базу данных, выполняет миграции и заново заполняет данными — учётные данные provider-ов, уже лежащие в .env (<PROVIDER>_TEST_KEY), возвращаются активными у владельца, так что вам не нужно каждый раз заново вводить их в интерфейсе. Он не удаляет и не пересоздаёт ни одного тома — node_modules, _build/deps, pgdata (удаляются только схемы внутри него), neo4j, локальные bare-репозитории и workspaces проектов — всё это выживает, — и он говорит об этом в начале и рядом со строкой успеха (AT-181). Это намеренно консервативный выбор: удаление томов выбросило бы workspaces и локальные репозитории, потерять которые никто не просил.

    Цена в том, что сброс никогда не воспроизводит первый clone. Дефект, который проявляется только с томом, которого ещё не существует, — как том node_modules, рождавшийся root (AT-172), — проходит через любой сброс незамеченным. Чтобы проверить этот путь, используйте одноразовый проект compose, никогда не этот скрипт и никогда не ваш проект brabo-dev (и не brabo, имя установки):

    docker compose -p brabo-primeiro-clone -f docker/docker-compose.yml build engine
docker compose -p brabo-primeiro-clone -f docker/docker-compose.yml \
  run --rm --no-deps engine ls -ldn /root/.mix /root/.hex \
  /workspace/apps/engine/_build /workspace/apps/engine/deps
docker compose -p brabo-primeiro-clone -f docker/docker-compose.yml down -v

    run создаёт тома этого проекта с нуля и не публикует порт, поэтому не конфликтует с вашим запущенным стеком. Так измерено для engine 2026-09-25 (AT-182): _build, deps, .mix и .hex рождаются с владельцем DEV_UID:DEV_GID, и mix local.hex/local.rebar/deps.get проходят от имени не-root пользователя. Две вещи он оставляет после себя: пустые точки монтирования _build/deps, которые он создаёт внутри вашего checkout-а, с владельцем root (удалите их однострочником alpine из таблицы ниже), и собранный им образ.

    Порядок — это суть, и он не обсуждается:

До ADR 0170 dev и установка были одним проектом Docker, и DROP SCHEMA этого скрипта попал бы в базу установки.
    2. preflight, затем предпосылки хоста (AT-203), затем build — медленная часть, выполняемая, пока ваша среда ещё запущена. Миграции и seed выполняются на ХОСТЕ, с apps/engine/deps/_build и node_modules checkout-а — не с томами контейнеров и не с тем, что обновляет build образа. Отказ здесь говорит RESET NÃO COMEÇOU … Nada foi parado nem apagado: база цела.

Эти два и никакие другие: именно они держат живое подключение к Postgres из compose (пул Drizzle api над public/drizzle, Ecto/Oban engine над engine). web — сервер Vite и не говорит ни с одной базой, neo4j — другая база, которую этот сброс не трогает, а broker говорит с api только по HTTP.
    4. up postgres, DROP SCHEMA, migrate.
    5. up --wait всего, затем seed.
    6. Запрашивает /health у api и engine и / у web, печатает docker compose ps и только затем завершает.

Seed затем падал на шаге, активирующем сессию (api → engine), с ECONNREFUSED, а скрипт всё равно печатал «reset completo» — фиксированный echo в конце скрипта, который никогда ничего не спрашивал о том, что он только что сделал.

    Если он остановится посередине, он скажет об этом и назовёт шаг (RESET INCOMPLETO — parou em: <passo>), и ответ — запустить его снова: он каждый раз удаляет схемы, поэтому второй запуск начинается с того же чистого листа, что и первый. Запуск только pnpm --filter api seed для восстановления теперь тоже безопасен — seed идемпотентен и переиспользует демонстрационные workspace, проект и сессию вместо их дублирования (и не добавляет повторно 5 событий сессии).

    Перенос среды dev в brabo-dev

    Начиная с ADR 0170 compose dev (docker/docker-compose.yml) — это проект Docker brabo-dev: контейнеры brabo-dev-api-1, brabo-dev-postgres-1…, тома brabo-dev_pgdata, brabo-dev_neo4j_data…, сеть brabo-dev_default. Compose установки (docker-compose.install.yml) остаётся brabo, как и уже существующие установки. Раньше оба были brabo — одним проектом Docker: подъём одного поверх другого пересоздавал контейнеры и подключал их к базе другого (измерено 2026-09-19: база установки получила миграцию dev), а reset-total.sh удалил бы схемы установки.

    Что меняется для вас, если вы уже разрабатывали здесь: следующий pnpm dev создаёт НОВЫЕ пустые тома brabo-dev_*. Ваши данные остаются там, где были, в томах brabo_*, нетронутыми — ничто в этом изменении не удаляет том. Preflight предупреждает, пока их видит (он никогда не отказывает из-за этого и никогда не удаляет). Выберите один из двух путей.

    Как отличить тома dev от томов установки. Оба несут метку com.docker.compose.project=brabo, поэтому один префикс ничего не говорит. Что говорит:

    docker volume ls --filter label=com.docker.compose.project=brabo \
  --format '{{.Name}}\t{{.Label "com.docker.compose.volume"}}'
docker ps -a --filter label=com.docker.compose.project=brabo \
  --format '{{.Names}}\t{{.Label "com.docker.compose.project.config_files"}}'
    • Тома, которые объявляет только compose dev, — api_*_node_modules, web_*_node_modules, broker_*_node_modules, engine_build, engine_deps, engine_mix, engine_hex — доказывают, что среда dev использовала имя brabo. Установка их никогда не создаёт.
    • Тома, которые объявляют оба compose, — pgdata, neo4j_data, neo4j_logs, ollama_data, git_local_repos, project_workspaces, brabo_projects_base — сами по себе неоднозначны. Если ни одного контейнера установки не существует (вторая команда не показывает docker-compose.install.yml) и вы никогда не устанавливали Brabo на эту машину, это ваши старые данные dev. Если устанавливали, они могут принадлежать установке (или быть смесью после аварии, которую закрывает этот ADR): не копируйте и не удаляйте их, пока не узнаете. backup_local существует только в установке.

    Путь A — перенести данные (базу, граф, локальные bare-репозитории и workspaces; тома артефактов build не стоят копирования, новые заполняются сами при первой загрузке):

    # 1. a stack antiga para baixo, SEM -v (ela pode ainda estar rodando como `brabo`).
#    SÓ quando o segundo comando acima não listou nenhum container de instalação:
#    `-p brabo down` derrubaria uma instalação do mesmo jeito.
docker compose -p brabo -f docker/docker-compose.yml --env-file .env down
# 2. crie os volumes novos (vazios) sem iniciar nada
docker compose -f docker/docker-compose.yml --env-file .env create
# 3. copie, volume a volume
for v in pgdata neo4j_data neo4j_logs git_local_repos project_workspaces ollama_data; do
  docker volume inspect "brabo_$v" >/dev/null 2>&1 || continue
  docker run --rm -v "brabo_$v":/de -v "brabo-dev_$v":/para \
    alpine sh -c 'cp -a /de/. /para/'
done
# 4. suba como brabo-dev
pnpm dev

    cp -a сохраняет владельцев и режимы, что важно для pgdata (образ Postgres отклоняет каталог данных, владельцем которого он не является) и для двух томов данных (см. Контейнеры dev пишут от имени вашего пользователя выше). Postgres должен быть остановлен, пока копируется его каталог, — для этого и нужен шаг 1.

    Путь B — начать с нуля: просто запустите pnpm dev, затем bash scripts/dev/reset-total.sh, чтобы выполнить миграции и заполнить новую базу. Старые тома остаются на диске, пока вы их не удалите.

    Удаление старых томов — только после того, как новый стек заработал, и только тех, что вы доказали как принадлежащие dev (тома установки — данные, которые вы бы потеряли):

    docker volume rm brabo_api_root_node_modules brabo_engine_build  # …um a um, pelo nome

    Ни один скрипт не делает этого за вас — намеренно: docker volume rm для brabo_pgdata установки — единственная ошибка здесь, которую нельзя отменить.

    Локальный deploy

    Поднимает весь Brabo в локальном кластере и проверяет его smoke-тестом. Решения — в ADR 0025.

    Предварительные требования

    Обязательны в PATH: docker, kubectl, kustomize, jq, openssl.

    k3d и helm устанавливать не нужно — bootstrap устанавливает их в ~/.local/bin, в зафиксированной версии с проверенной контрольной суммой. Убедитесь, что этот каталог есть в PATH.

    Ресурсы: весь стек (Postgres, Prometheus, два operator-а и три приложения) требует около 4 GiB свободной памяти.

    Подъём

    make deploy-local           # constrói as imagens, sobe o cluster, instala, valida
make deploy-local-clean     # o mesmo, sem reconstruir as imagens

    В итоге: web на http://localhost:8088, api на :3000, engine на :4000 — те же порты, что в docker-compose.prod.yml, намеренно (ADR 0025, решение 10). Bootstrap запускает seed, который создаёт уже подтверждённого owner@brabo.dev с паролем из BRABO_SMOKE_PASSWORD (по умолчанию brabo12345678) — именно с ним вы входите через собственный вход web.

    Seed запускается после rollout-ов (его последний шаг активирует сессию, что заставляет api вызвать engine), а bootstrap продолжает только после проверки, что вход возвращает 200. Эта проверка — по результату, а не по процессу, и она существует, потому что предыдущая такой не была: wait --for=condition=Ready=false удовлетворяется подом, который так и не запустился, и поэтому bootstrap объявлял «usuário do smoke pronto», пока вход возвращал 401.

    Seed идемпотентен. Повторный запуск над заполненной базой — это нормальный случай (BRABO_KEEP_CLUSTER=1): демонстрационные workspace, проект и сессия находятся и переиспользуются, никогда не дублируются, и переиспользованная сессия не получает пять событий заново (apps/api/src/db/seed.ts, docblock в начале). Второй запуск больше не умирает на workspaces_slug_unique. Bootstrap по-прежнему решает по входу, а не по фазе пода, и по-прежнему удаляет под в конце, чтобы он не провалил шаг 1 smoke.sh, который требует, чтобы все поды были здоровы.

    Это занимает порты pnpm dev. Одинаковые порты — то, что делает smoke.sh действительным для обоих режимов, а цена в том, что они не сосуществуют: при запущенном кластере pnpm dev не может опубликовать порт api, и 5173 никогда не открывается. Обратите внимание, что web меняет порт между режимами — 8088 здесь, 5173 там. Чтобы вернуться к разработке:

    make k8s-down && pnpm dev

    pnpm dev:preflight говорит, в каком режиме вы находитесь, без догадок. Оба рассмотрены в Первых шагах.

    Другие цели:

    make smoke-k8s        # só o smoke test, contra o cluster rodando
make hpa-test         # prova que o HPA do engine escala pela fila
make k8s-validate     # renderiza os overlays e valida contra o schema (sem cluster)
make k8s-logs         # últimas linhas de api, engine e web
make k8s-down         # remove o cluster

    Переменные: BRABO_SKIP_BUILD=1 (использует образы демона), BRABO_KEEP_CLUSTER=1 (переиспользует кластер), BRABO_CLUSTER_TOOL=kind, BRABO_SKIP_OBSERVABILITY=1 (без Tempo, Loki, Collector, Alloy и Grafana — AT-177). Последняя — явный отказ для запланированных проверок, и значение по умолчанию не меняется: make deploy-local по-прежнему поднимает весь стек. Prometheus и prometheus-adapter остаются в любом случае, потому что HPA engine масштабируется по oban_queue_depth через External Metrics API, которую они обслуживают. Независимые релизы helm (ESO, CNPG, metrics-server, Prometheus) устанавливаются параллельно; каждый пишет собственный лог, печатаемый только при сбое.

    Проверка тега конвейера

    make deploy-local TAG=v0.2.0-qa.1

    Конвейер Фазы 6 не делает deploy — он заканчивается тегом. TAG= — способ увидеть в локальном кластере то, что этот тег зафиксировал: bootstrap делает отсоединённый checkout тега и собирает образы из этого commit-а.

    Он отказывается работать с грязным деревом, вместо того чтобы угадывать, что делать с вашей незавершённой работой. По завершении вы оказываетесь в отсоединённом HEAD; команда для возврата появляется в логе.

    Проверка: никакой. Ни один workflow не передаёт TAG=: запланированный propriedades.yml собирает дерево checkout-а, никогда не тег, поэтому отсоединённый checkout в deploy/k8s/bootstrap.sh (и его отказ при грязном дереве) выполняется только когда кто-то его набирает. То, что он поднимает затем, — тот же bootstrap и smoke из Локального deploy, которые доказаны.

    Deploy образов релиза

    Начиная с ADR 0119 каждый финальный тег публикует образы production в GHCR (ghcr.io/daneiel/brabo-{api,engine,web,backup,broker}, публичные — ни одного imagePullSecret нигде) и регистрирует опубликованное по digest в .release/images.json. Пятый, broker контейнеров (ADR 0162), предназначен для установок — в overlay нет Deployment broker-а, и make imagens-do-release записывает только остальные четыре.

    Overlays этого репозитория держат newTag: REPLACE_WITH_DIGEST — маркер. Репозиторий никогда не объявляет, какой релиз в production — это объявляете вы, в момент deploy:

    # 1. pegue o registro da release de que você está fazendo deploy
gh release download v3.2.0 --pattern images.json --dir .release

# 2. escreva os digests dela no overlay
make imagens-do-release OVERLAY=prod      # ou OVERLAY=staging

# 3. leia o diff antes de aplicar qualquer coisa
git diff deploy/k8s/overlays/prod/kustomization.yaml

    Ошибка CORS

    Сообщение браузера называет назначение вызова, но никогда не причину. Сначала читайте источник (origin), который в нём указан, — это и есть полезная информация (ADR 0037):

    Access to fetch at 'http://localhost:3000/health' from origin
'http://localhost:5174' has been blocked by CORS policy
                     ^^^^ esta parte é o diagnóstico

    Если origin не тот, что вы ожидаете (:5174 вместо :5173, другой хост, https вместо http), проблема в origin, а не в CORS.

    В compose WEB_ORIGIN выводится из WEB_PORT — изменение WEB_PORT в .env (рекомендация первых шагов для занятого порта) сразу сдвигает и принимаемый origin, поэтому это конкретное расхождение больше не происходит. Что ещё вызывает это: кто-то передал --port напрямую в Vite вне compose (ADR 0037 заставил Vite отказываться стартовать в этом случае, через strictPort, вместо того чтобы молча стартовать на другом порту), web раздаётся другим путём, или WEB_ORIGIN задана вручную и перекрыла вывод. Исправьте origin или добавьте его в WEB_ORIGIN — в обоих сервисах, которые читают одну и ту же переменную.

    Если origin верный, проверьте, что каждый сервис отвечает на самом деле. curl не делает CORS, поэтому показывает сырой заголовок — ровно то, на что смотрит браузер:

    # api — espera-se access-control-allow-origin + allow-credentials
curl -sI http://localhost:3000/health -H "Origin: http://localhost:5173" \
  | grep -i access-control

# engine — espera-se access-control-allow-origin + vary: origin
curl -sI http://localhost:4000/health -H "Origin: http://localhost:5173" \
  | grep -i access-control

# preflight, que é onde falta de allow-headers aparece
curl -sI -X OPTIONS http://localhost:3000/auth/login \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type,x-csrf-token" \
  | grep -i access-control

    Пустой вывод — это находка: сервис не распознал origin. Неверная или отсутствующая WEB_ORIGIN либо неверный порт.

    Preflight без заголовка, который отправляет web, — другой вид сбоя, и самый обманчивый: список allowedHeaders в api явный, и ни один тест не делает preflight, поэтому новый заголовок клиента проходит CI и ломается только в браузере. Сегодняшний список: Content-Type, Authorization, X-CSRF-Token, traceparent.

    Три вещи, которые не являются проблемой CORS, как бы они ни были на неё похожи:

    • api ↔ engine. CORS — механизм браузера; там вызывает серверный HTTP-клиент, который игнорирует эти заголовки. Сбой на этом пути — это service token (401/403 — см. ротацию) или неверный адрес (ECONNREFUSED — см. сессия не выходит из created).
    • Канал Phoenix замолкает. WebSocket не проходит через CORS. Отказывает check_origin endpoint-а, тоже питаемый WEB_ORIGIN, и отказ появляется в логе engine — а не в консоли браузера как ошибка CORS.
    • /metrics engine заблокирован в браузере. Это намеренно: внутренняя метрика не предназначена для чтения JavaScript-ом страницы. Используйте curl.

    Сессия не выходит из created

    Симптом: активация сессии ничего не делает. «Abrir sessão criativa» создаёт сессию, а экран не двигается; «Ativar sessão» — тоже. В логе api POST /projects/:id/sessions/:id/transition возвращает 500:

    TransitionSessionUseCase.activate ✗ TypeError
  ↳ HttpApiToEngineClient.startSession ✗ TypeError: fetch failed
      caused by: AggregateError [ECONNREFUSED]

    Активация сессии — первый шаг, который переходит в engine (api запрашивает супервизируемую сессию по внутреннему HTTP), поэтому именно здесь проявляется неверный ENGINE_URL — и не раньше, потому что ничто другое на пути создания не выходит за пределы api.

    Подтвердите изнутри контейнера — именно там адрес имеет значение (brabo-dev-api-1 в compose dev; в установке — brabo-api-1, ADR 0170):

    docker exec brabo-dev-api-1 node -e '
for (const u of ["http://engine:4000/health", "http://localhost:4000/health"]) {
  fetch(u, { signal: AbortSignal.timeout(5000) })
    .then((r) => console.log(u, "->", r.status))
    .catch((e) => console.log(u, "-> FAILED:", e.cause?.code ?? e.message));
}'
docker exec brabo-dev-api-1 sh -c 'echo $ENGINE_URL'

    engine:4000, отвечающий 200, в то время как localhost:4000 даёт ECONNREFUSED, при ENGINE_URL=http://localhost:4000, — законченный диагноз: внутри контейнера localhost — это сама api.

    Причина обычно в .env, а не в compose. pnpm dev передаёт .env как --env-file, и значение там побеждает ${ENGINE_URL:-http://engine:4000} из compose. Исправление: удалите (или закомментируйте) строку ENGINE_URL в вашем .env и пересоздайте api —

    docker compose -f docker/docker-compose.yml --env-file .env up -d api

    — потому что каждая среда и без неё несёт правильное значение по умолчанию: compose указывает на сервис engine, а api, запущенная на хосте, падает на http://localhost:4000 собственным кодом. Задавать переменную имеет смысл только для указания на engine, который не является ни одним из этих двух. Это относится и к compose production, использующему ту же интерполяцию; в Kubernetes значение приходит из ConfigMap и всегда было http://engine:4000.

    Две проверки, прежде чем винить адрес, если ENGINE_URL верна:

    • Engine запущен? docker compose ps engine и curl -sI http://localhost:4000/health. ECONNREFUSED при верном адресе означает, что сервис недоступен, а не неправильно настроен.
    • Сессия, которая активируется и сама закрывается ~30s спустя, — не эта проблема. Посмотрите на termination_reason: heartbeat_timeout означает, что активация сработала и никто не вошёл в канал Phoenix — ожидаемое поведение при активации вне интерфейса (SESSION_HEARTBEAT_TIMEOUT_MS). conversation_idle_timeout — другое: разговорный агент ждал пользователя дольше SESSION_CONVERSATION_IDLE_TIMEOUT_MS (8h), отсчитываемых от конца его хода (RN-581). Чтобы изменить этот предел, задайте переменную в .env (все три compose передают её в engine) или, в Kubernetes, добавьте элемент env: в patch engine в overlay: deploy/k8s/ намеренно её не пишет, потому что отсутствующая там переменная уже даёт значение по умолчанию 8h из кода (AT-153). 409 с reason: "sessao_encerrada" после этого — закрытая сессия, отказывающая в разговоре: откройте новую сессию.

    Вкладка Terminal навсегда застревает на «Abrindo terminal...»

    Симптом: в проекте в режиме runner (ADR 0103/0104) вкладка Código → Dev → Terminal никогда не выходит из скелета загрузки. Консоль браузера показывает, в тугом цикле с растущим backoff:

    socket do terminal com erro {"erro":"[object Event]"}
socket do terminal fechado

    Это WebSocket браузера, так и не дотягивающийся до engine, а не проблема runner-а — это происходит даже до подключения какого-либо brabo-runner. Три наложенные причины, все закрытые RN-433:

    1. ENGINE_PUBLIC_URL разрешается во внутреннее имя хоста Docker. Тикет, который api отдаёт браузеру (POST .../terminal-ticket), несёт engineWsUrl, собранный из ENGINE_PUBLIC_URL, — отличной от ENGINE_URL (RN-419), которая предназначена для вызовов api→engine внутри сети compose. docker/docker-compose.yml теперь задаёт ENGINE_PUBLIC_URL: ${ENGINE_PUBLIC_URL:-http://localhost:4000} в сервисе api (то же значение по умолчанию, что VITE_ENGINE_URL уже использует для web). Подтвердите изнутри контейнера:

      docker exec brabo-dev-api-1 sh -c 'echo $ENGINE_PUBLIC_URL'
# esperado: http://localhost:4000 (ou o endereço público real do seu engine)

      Пустое значение здесь в среде, собранной до этого исправления, означает, что код откатился на ENGINE_URL (http://engine:4000) — имя хоста, которое разрешается только внутри сети Docker, никогда из браузера. Исправление: пересоберите/пересоздайте контейнер api, чтобы новое значение по умолчанию compose вступило в силу, или задайте ENGINE_PUBLIC_URL явно в .env, если настоящий публичный адрес engine другой (туннель, другой хост).

    2. Сокет, который никогда не открывается, повторял попытки вечно и молча. Независимо от адреса выше — даже по-настоящему недоступный engine (выключен, за firewall) должен проявляться как ошибка, а не крутиться вечно. apps/web/src/lib/terminal-channel.ts теперь сдаётся через 8s, если сокет не открылся, и показывает RunnerOnboardingPanel с практичным сообщением вместо того, чтобы оставаться в цикле стандартного переподключения WebSocket браузера.

    3. URL сокета дублировал путь. Настоящая блокировка после того, как первые две были исправлены: terminal-channel.ts приклеивал /runner/websocket к engineWsUrl, который api уже возвращает полным (ws://host:port/runner), — а собственный конструктор Socket из phoenix.js снова добавляет /websocket к любому endpoint-у, который получает. Engine получал GET /runner/runner/websocket/websocket и отклонял его (Phoenix.Router.NoRouteError), что видно в docker logs brabo-dev-engine-1 как подключение, которое никогда не уходит дальше REFUSED CONNECTION.     Runner заваливает api мёртвым тикетом

    Симптом: web начинает отвечать 429 на запросы самого человека, без необычной активности с его стороны; и/или проект в режиме runner выглядит без локального агента (задачи dev застряли в dev.blocked_by_container, RunnerReadiness отказывает), в то время как brabo-runner явно работает на его машине.

    Как подтвердить. В логе engine ищите ОДИН И ТОТ ЖЕ тикет, который отклоняется снова и снова с фиксированным интервалом около 5,13 s:

    docker logs brabo-dev-engine-1 2>&1 | grep 'REFUSED CONNECTION TO EngineWeb.RunnerSocket' | tail -20

    Десятки таких за несколько часов, все с одной и той же строкой тикета, — это сигнатура. ~5,13 s — не произвольное число: это предел внутреннего backoff reconnectAfterMs в phoenix.js.

    Причина. Тикет сокета — одноразовый (RN-108); встроенный auto-reconnect библиотеки повторяет ТЕ ЖЕ params, поэтому он повторяет тикет, который был израсходован при первом подключении и больше никогда не будет принят. Одна версия apps/runner/src/channel.ts вышла с этим auto-reconnect ВКЛЮЧЁННЫМ — в то время как docblock самого модуля утверждал, что он нейтрализован. Наложившись на СОБСТВЕННУЮ политику повторов runner-а (которая корректна: свежий тикет на каждый раунд, backoff, предел последовательных попыток), это дало измеренные 530 запросов за одну минуту против предела 300 req/min у RATE_LIMIT_USER, четыре минуты подряд выше лимита. Лимит — на пользователя, и именно поэтому 429 появился в браузере владельца учётной записи, а не где-то рядом с runner-ом.

    Второе следствие хуже: пока он застрял в этом цикле, runner не подключён, поэтому RunnerReadiness (RN-507) отказывает, и проект выглядит не имеющим локального агента — часть того, что читается как «контейнер не поднимается», — это вот это.

    Исправление. Обновите бинарник brabo-runner (или переустановите с экрана проекта). На сервере ничего менять не нужно: rate limiter сделал свою работу, а engine был прав, отклоняя каждый из этих тикетов. Если наводнение ещё продолжается, остановка runner-а прекращает его сразу, и 429 исчезают по мере того, как скользящее окно опустошается (одна минута).

    api отказывается стартовать из-за секрета OAuth

    Симптом: при NODE_ENV=production api умирает в начале с сообщением о GIT_OAUTH_STATE_SECRET — отсутствует, задана примерным значением из репозитория или слишком короткая.

    Это не регрессия, и не обходите её. Этот ключ подписывает state OAuth для git, а state — то, что не даёт подделать публичный callback. До ADR 0059 api стартовала со значением по умолчанию, опубликованным прямо здесь, в этом репозитории, — у того, кто видит эту ошибку, до сих пор поток подключения git был открыт любому. Сбой загрузки — это запоздало пришедшее предупреждение.

    export GIT_OAUTH_STATE_SECRET="$(openssl rand -base64 32)"

    В Kubernetes значение приходит из brabo-secrets, под одноимённым ключом объекта brabo в хранилище секретов, который deploy/k8s/base/common/externalsecrets.yaml забирает целиком, — если ошибка появилась там, проблема в том, что хранилище не отдаёт ключ, и путь — Диагностика deploy.

    Смена ключа инвалидирует state-ы в полёте: тот, кто в этот момент находится посреди «подключить GitHub», получает отказ и проходит поток заново. Поскольку TTL state — 10 минут, это и есть окно — миграции не требуется, и ни одно уже установленное подключение не затрагивается (сохранённый токен не зависит от этого ключа).

    Симптом: нажатие «Entrar com GitHub»/«Entrar com GitLab» на экране входа уходит к provider-у и возвращается с ошибкой САМОГО PROVIDER-А (redirect_uri_mismatch в GitHub, «The redirect URI included is not valid» в GitLab) — даже не доходит до /auth/oauth/:provider/callback.

    Это не баг продукта — не хватает регистрации на стороне provider-а. Социальный вход (ADR 0084) переиспользует ТОТ ЖЕ OAuth App, который уже использует подключение git (GITHUB_OAUTH_CLIENT_ID/GITLAB_OAUTH_CLIENT_ID, ни одной новой переменной), но у каждого ПОТОКА свой redirect_uri, и provider требует, чтобы ВСЕ, которые может запросить api, были заранее зарегистрированы:

    • Подключение git (уже существовало): ${API_PUBLIC_URL}/git/oauth/<provider>/callback
    • Социальный вход (новый): ${API_PUBLIC_URL}/auth/oauth/<provider>/callback

    Зарегистрируйте второй в конфигурации OAuth App (GitHub: Settings → Developer settings → OAuth Apps; GitLab: Settings → Applications) — GitHub принимает несколько callback URL в одном App, GitLab тоже. Отдельный App или новые client id/secret не нужны.

    Четыре родственных секрета тоже не стартуют со значением по умолчанию

    Симптом: при NODE_ENV=production api (или, для SECRET_KEY_BASE и BRABO_SERVICE_TOKEN, релиз :prod engine, который отклоняет те же значения токенов начиная с RN-601) умирает в начале с сообщением об AUTH_JWT_SECRET, BRABO_SERVICE_TOKEN, CREDENTIALS_MASTER_KEY или SECRET_KEY_BASE — отсутствует, задан примерным значением из репозитория или слишком короткий.

    Та же причина, что у секрета OAuth выше, и та же рекомендация: это не регрессия, и не обходите её. ADR 0059 уже объявлял эти четыре как незакрытые — тот же шаблон, только ещё не повторённый, — и RN-114 его закрыла. Каждый защищает своё:

    • публичный AUTH_JWT_SECRET = любой может вывести пару, подписывающую access token, и подделать действительный.
    • публичный BRABO_SERVICE_TOKEN = любой может вызывать /internal/* в обход EngineServiceGuard.
    • публичный CREDENTIALS_MASTER_KEY = любой может расшифровать хранилище учётных данных пользователя (ключи LLM, токены git).
    • SECRET_KEY_BASE (engine) уже имел raise в runtime.exs — дефект был лишь в том, что compose маскировал этот raise публичным fallback-значением.
    export AUTH_JWT_SECRET="$(openssl rand -base64 32)"
export BRABO_SERVICE_TOKEN="$(openssl rand -base64 32)"
export CREDENTIALS_MASTER_KEY="$(openssl rand -base64 32)"
export SECRET_KEY_BASE="$(openssl rand -base64 64)"

    В Kubernetes ничего не меняется по той же причине, что и для GIT_OAUTH_STATE_SECRET: все четыре уже приходили из brabo-secrets, под одноимённым ключом объекта brabo, который deploy/k8s/base/common/externalsecrets.yaml забирает целиком.

    Граф знаний (NEO4J_URI/NEO4J_USER/NEO4J_PASSWORD, ADR 0099) следует тому же правилу, с одним отличием: у NEO4J_URI и NEO4J_USER есть безопасное значение по умолчанию для разработки (bolt://neo4j:7687, neo4j — это не секреты, и docker-compose.prod.yml их уже предоставляет); только у NEO4J_PASSWORD нет публичного значения по умолчанию, по той же причине, что и у четырёх выше, — и без него загрузка api падает в GraphStore.onModuleInit (neo4j-config.ts) ЕЩЁ ДО того, как сам Neo4j откажется стартовать (entrypoint официального образа требует пароль из 8+ символов; пустой NEO4J_AUTH первым роняет контейнер neo4j).

    export NEO4J_PASSWORD="$(openssl rand -hex 24)"

    В разработке ключевая переменная — NEO4J_URI, и по умолчанию она пуста. Сервис neo4j работает в profile по умолчанию compose dev, так что сервер запущен независимо от того, говорит с ним кто-то или нет; api подключается, только когда NEO4J_URI задана. Раскомментируйте её в .env (bolt://neo4j:7687) и пересоздайте api — тогда GraphStore пишет Neo4j conectado — constraints do grafo garantidas вместо NEO4J_URI/NEO4J_USER/NEO4J_PASSWORD ausentes. Пользователь и пароль приходят в контейнер с теми же значениями по умолчанию, что сервис neo4j использует для NEO4J_AUTH, поэтому задавайте их только чтобы СМЕНИТЬ пароль, и смена там меняет обе стороны разом.

    До того как это было подключено, docker-compose.yml вообще не передавал три переменные сервису api, а у сервиса нет env_file — так что блок, который .env.example документировал с рождения графа, ни к чему не приводил, и его раскомментирование ничего не включало. docker-compose.prod.yml предоставлял их с первого дня (поэтому затронута была только разработка): здоровый Neo4j стоял рядом с api, сообщающей об отсутствующих переменных, бесконечно.

    HEX, а не base64. Entrypoint Neo4j читает NEO4J_AUTH как usuario/senha и разделяет по ПЕРВОЙ косой черте — пароль base64 может содержать / (в алфавите есть / и +), и это ломает разбор с Invalid value for NEO4J_AUTH, роняя контейнер neo4j в цикл перезапусков. Это действительно случилось: smoke-тест CI упал так после merge, который по ошибке вернул -base64. В hex нет ни /, ни +, ни =.

    docker/smoke.sh уже генерирует пять эфемерных переменных выше (четыре родственных плюс NEO4J_PASSWORD, её — в hex) при каждом запуске — так job CI «Build, scan e smoke das imagens de produção» поднимает docker-compose.prod.yml без единого закоммиченного секрета.

    Смена AUTH_JWT_SECRET или BRABO_SERVICE_TOKEN без танца с _PREVIOUS даёт тот же эффект, что уже задокументирован в Ротации ключей auth; смена CREDENTIALS_MASTER_KEY без переупаковки даёт тот же эффект, что уже задокументирован в Ротации мастер-ключа. Эта проверка при ЗАГРУЗКЕ не меняет ни одну из двух процедур — она лишь не даёт ключу попасть в production в виде публичного литерала из этого репозитория.

    Настоящий SMTP в MailSender

    MailSender отправляет настоящую почту, только когда MAIL_TRANSPORT=smtp, — значение по умолчанию log (привычное поведение), в том числе в production: отправка настоящей почты — явный выбор оператора (ADR 0096). Полную таблицу SMTP_* см. в Конфигурации.

    Симптом неполной конфигурации: при NODE_ENV=production и MAIL_TRANSPORT=smtp api умирает в начале, жалуясь на SMTP_HOST, SMTP_USER, SMTP_PASSWORD или SMTP_FROM — тот же шаблон сообщения, что у четырёх родственных секретов (RN-408), но БЕЗ публичного значения по умолчанию, которое есть у них: здесь правило вступает в игру только когда оператор выбрал smtp.

    export MAIL_TRANSPORT=smtp
export SMTP_HOST=smtp.seu-provedor.com
export SMTP_PORT=587
export SMTP_USER=usuario-do-provedor
export SMTP_PASSWORD="$(sua-credencial-do-provedor)"
export SMTP_FROM="Brabo <nao-responda@seu-dominio.com>"

    SMTP_PASSWORD — секрет ИНФРАСТРУКТУРЫ сервиса (простая переменная окружения, как AUTH_JWT_SECRET), а не секрет ПОЛЬЗОВАТЕЛЯ — он не проходит через envelope encryption, и у него нет собственной процедуры ротации, кроме замены переменной и перезапуска (политику ротации этих учётных данных решает provider SMTP). В Kubernetes ключ попадает в объект brabo хранилища секретов, как любой другой, и доходит до brabo-secrets без изменения манифеста — deploy/k8s/base/common/externalsecrets.yaml забирает объект целиком.

    Если почта не приходит даже без ошибки загрузки: ищите в логе api falha ao enviar e-mail via SMTP (type/получатель видны, тело и токен НИКОГДА не появляются — то же правило, что у LogMailSender), и проверьте учётные данные собственным SMTP-клиентом provider-а, прежде чем подозревать Brabo.

    k3d — по умолчанию даже при установленном kind

    Это не предпочтение. k3s поставляется со встроенным контроллером NetworkPolicy; kindnet из kind не реализует NetworkPolicy и молча игнорирует манифесты. В кластере kind политики этой фазы существуют в etcd без какого-либо эффекта, и deploy выглядел бы проверенным, не проверив половину пункта 4 объёма. Smoke-тест предупреждает, когда кластер их не применяет.

    Что покрывает smoke-тест

    1. Каждый под Ready — не только Running. Под, чья проверка readiness падает, остаётся Running вечно, не получая трафика.

    2. Ни одного контейнера с runAsUser: 0.

    3. Вход в POST /auth/login пользователем из seed — проверяет argon2id, выпуск access token и cookies сессии.

    4. workspace → project → session. Этот шаг пересекает весь набор NetworkPolicies: создание сессии заставляет api вызвать engine по внутреннему HTTP, с service token. Сессия создаётся с kind: consultiva — обязательным начиная с ФАЗЫ 20 (RN-097) — и она consultiva намеренно: smoke-тест проверяет создать → активировать → закрыть и никогда не активирует выполнение, которое в консультативной сессии возвращает 409.

      Этот шаг доказывает, что у маршрута есть потребитель вне web. Когда kind стал обязательным, набор тестов api прошёл с 1562 тестами, а упал именно smoke-тест, потому что он единственный вызывает маршрут как внешний клиент, без mock, против образа production.

    5. Раздельные пробы (/live и /ready для engine, /live для api) и /config.js web, указывающий на URL кластера.

    6. oban_queue_depth с метками queue и state в /metrics.

    7. external.metrics.k8s.io, отдающий метрику — сбой prometheus-adapter молчалив, поэтому мы спрашиваем агрегированный API напрямую.

    Диагностика deploy

    403 на /internal/* или 401 в вызовах api к engine

    У обоих симптомов одна причина: service token не совпадает между двумя сторонами (api отказывает с 403, plug engine — с 401). Проверьте, что обе нагрузки читают одно и то же значение:

    kubectl -n brabo get secret brabo-secrets -o jsonpath='{.data.BRABO_SERVICE_TOKEN}' | base64 -d | sha256sum
kubectl -n brabo exec deploy/engine -- sh -c 'printf %s "$BRABO_SERVICE_TOKEN" | sha256sum'

    Сравнение хеша вместо значения позволяет не печатать секрет в терминале. Если они расходятся, у пода engine старая версия Secret: kubectl -n brabo rollout restart deploy/engine. Если совпадают, заголовок не проходит: проверьте, что BRABO_SERVICE_TOKEN задан в обеих нагрузках — у engine есть значение по умолчанию для разработки (dev-service-token-change-me), поэтому забытая только там переменная даёт ровно этот симптом, без ошибки загрузки, — и что ни один прокси на пути не вырезает незнакомые заголовки.

    Вход возвращает 401 всем после deploy

    Почти всегда это новый AUTH_JWT_SECRET, пропустивший шаг сосуществования: access token исчезает вместе с ним, но симптом проявляется на refresh. Правильная процедура — в Ротации ключей auth.

    ExternalSecret никогда не становится Ready

    SecretStore читает исходный Secret brabo, созданный императивно bootstrap-ом. Подтвердите, что он существует и что RBAC на месте:

    kubectl -n brabo get secret brabo
kubectl -n brabo describe secretstore brabo-secret-store

    Начиная с AT-220 ExternalSecret забирает объект brabo целиком из хранилища (dataFrom.extract) вместо перечисления каждого ключа. Два следствия для диагностики:

    • Отсутствующий ключ больше не мешает ему стать Ready. brabo-secrets создаётся без него, и сбой проявляется у того, кому нужен ключ: Pod с secretKeyRef (NEO4J_PASSWORD в Neo4j, BACKUP_S3_ACCESS_KEY/ BACKUP_S3_SECRET_KEY в локальном S3) остаётся в CreateContainerConfigError, а api или engine отказываются стартовать в production, называя переменную. Объект в хранилище должен содержать DATABASE_URL, SECRET_KEY_BASE, CREDENTIALS_MASTER_KEY, GIT_OAUTH_STATE_SECRET, AUTH_JWT_SECRET, AUTH_TOKEN_PEPPER, BRABO_SERVICE_TOKEN, RELEASE_COOKIE, BACKUP_S3_ENDPOINT, BACKUP_S3_BUCKET, BACKUP_S3_ACCESS_KEY, BACKUP_S3_SECRET_KEY и NEO4J_PASSWORD — список, который deploy/k8s/bootstrap.sh создаёт локально. Сравните то, что пришло:

      kubectl -n brabo get secret brabo-secrets -o go-template='{{range $k, $v := .data}}{{$k}}{{"\n"}}{{end}}'

    • Всё в этом объекте доходит до Pod-ов. Каждый ключ становится переменной окружения api, engine, двух Job-ов миграции и CronJob бэкапа (envFrom: brabo-secrets). Не храните в brabo ничего, чего эти процессы не должны видеть; секрет другого потребителя идёт в другой объект.

    HPA engine в <unknown>

    По порядку, от наиболее к наименее вероятному:

    # 1. o engine está expondo a métrica?
kubectl -n brabo exec deploy/engine -- wget -qO- http://127.0.0.1:4000/metrics | grep oban_queue_depth

# 2. o Prometheus a está coletando?
kubectl -n monitoring port-forward svc/prometheus-server 9090:80
# depois: http://localhost:9090 -> Status -> Targets

# 3. o adapter a está servindo?
kubectl get --raw "/apis/external.metrics.k8s.io/v1beta1/namespaces/brabo/oban_queue_depth?labelSelector=state%3Davailable"

    Если (1) отвечает, а (3) нет, проблема в правиле в deploy/k8s/helm/prometheus-adapter-values.yaml.

    Job миграции не применяется повторно

    Spec у Job неизменяем: пока предыдущий Job ещё в кластере, повторное применение с новым образом падает. Bootstrap уже удаляет оба перед применением; вручную:

    kubectl -n brabo delete job migrate-api migrate-engine --ignore-not-found
kubectl apply -k deploy/k8s/overlays/local

    bin/engine rpc отвечает eaddrinuse

    Диапазону портов распределения Erlang (ERL_AFLAGS) нужно больше одного порта: работающий узел занимает первый, а rpc поднимает скрытый узел, которому нужен другой. Настроенный диапазон — 9100–9110, открытый в NetworkPolicy.

    Проверка, что реплики engine в кластере

    Без кластера Erlang :global.trans из Workspace.ensure! ничего не сериализует, и две реплики запускают конкурентный git init в одном и том же общем каталоге:

    kubectl -n brabo exec deploy/engine -- /app/bin/engine rpc 'IO.inspect(Node.list())'

    Должны быть перечислены другие поды. Пустой список при более чем одной реплике — это дефект.

    Секреты: откат на sealed-secrets

    По умолчанию — External Secrets Operator. Где он неприменим, замените ExternalSecret в deploy/k8s/base/common/externalsecrets.yaml на SealedSecret, сохранив то же имя Secret (brabo-secrets) и те же ключи — больше ничего в deploy менять не нужно, потому что всё потребляет его через secretRef.

    kubectl create secret generic brabo-secrets \
  --dry-run=client -o yaml \
  --from-literal=DATABASE_URL=... \
  --from-literal=SECRET_KEY_BASE=... \
  | kubeseal --format yaml > deploy/k8s/overlays/<env>/sealed-brabo-secrets.yaml

    SealedSecret шифруется для публичного ключа данного кластера и может версионироваться. Простой Secret — никогда.

    Проверка: никакой. Ничто в репозитории не запускает kubeseal, а запланированный кластер (propriedades.yml) материализует brabo-secrets через External Secrets, так что этот путь никогда не проверялся. Прежде чем доверять ему, поднимите кластер с SealedSecret на месте и запустите make smoke-k8s: его первый шаг требует, чтобы каждый под был Ready, а под, чей secretRef указывает на Secret, который так и не материализовался, таковым не является.

    Известные ограничения этой среды

    • RWO вместо RWX. Работает, потому что в кластере один узел, а RWO означает «один УЗЕЛ», а не «один под». В настоящем кластере эта конфигурация разместила бы api и engine на разных узлах, и git push dev agent падал бы с remote unpack failed.
    • Нет pgvector в Postgres от CloudNativePG. Сегодня ни одна миграция не создаёт расширение, и ни одного столбца vector нет.
    • У .gitlab-ci.yml нет локальной статической проверки (Фаза 8c, ADR 0039). Субагент Workflows области Infra проверяет workflows GitHub Actions через actionlint (зафиксирован в docker/engine/Dockerfile(.prod), тот же шаблон, что hadolint/gitleaks); эквивалентного офлайн-бинарника для GitLab CI нет — официальному линтеру нужен живой экземпляр. Задокументированный пробел, а не выдуманное полурешение.

    Rollout engine

    Решения — в ADR 0026.

    Engine размещает процессы сессий. Неаккуратное падение реплики до Фазы 5 оставляло каждую сессию этого пода висеть в active без какого-либо процесса — никогда не продвигаясь, никогда не закрываясь.

    Что происходит во время rollout, по порядку

    фаза сколько времени что происходит
    preStop до 45s (SHUTDOWN_DRAIN_TIMEOUT_MS) Engine.Shutdown.drain/1: /ready становится 503, /internal/sessions отклоняет новые сессии, и каждая сессия этого узла предлагается живому партнёру
    передача по сессии 5s (@handoff_timeout_ms) :erpc.call, чтобы другой узел взял процесс
    не принята — становится closing с причиной node_shutdown, затем closed_abnormally
    SIGTERM остаток из 90s (terminationGracePeriodSeconds) дерево супервизии падает

    90s выбраны намеренно: 45s на drain плюс запас на разборку BEAM. Снижение terminationGracePeriodSeconds без снижения timeout drain заставляет kubelet убить под посреди передачи — именно так воссоздаётся баг, для предотвращения которого существует drain.

    Выполнение rollout

    kubectl -n brabo rollout restart deployment/engine
kubectl -n brabo rollout status  deployment/engine --timeout=300s

    При одной реплике нет партнёра для принятия: каждая активная сессия закончится closed_abnormally / node_shutdown. Это правильно, а не сбой — но если цель была никого не прерывать, сначала масштабируйте до 2:

    kubectl -n brabo scale deployment/engine --replicas=2

    Доказательство, что сирот не осталось

    make rollout-test

    Открывает 5 активных сессий, выполняет rollout и требует, чтобы каждая была в одном из двух состояний: active с живым владельцем :global (принята) или closed_abnormally с node_shutdown (дренирована). Любая другая комбинация проваливает тест — в особенности active без владельца, что является операционным определением сироты.

    Он сохраняет улики, которые старые поды уносят с собой (AT-078). До rollout restart deploy/k8s/rollout-evidencia.sh начинает писать в ROLLOUT_EVIDENCE_DIR (mktemp -d, если не задана; путь печатается в конце):

    файл что
    engine-<pod>.log kubectl logs -f каждого пода engine — уже запущенных (весь лог, с загрузки), которых rollout убивает, и каждого пода, созданного позже, — подключается, как только тот становится Running
    final-<pod>.log копия без follow подов, ещё работающих в конце, покрывающая упавший logs -f
    events.log kubectl get events -w пространства имён, с собственными временными метками каждого события (SuccessfulRescale, ScalingReplicaSet, Killing…)
    replicas.log каждые 2 s (EVIDENCIA_INTERVALO, который spec сокращает): <epoch> <spec.replicas do Deployment> <ready> <HPA current> <HPA desired>

    Что попадает в бэкап, а что намеренно нет

    Существует семь именованных томов; два являются источником истины, и только они копируются. Классификация — это ADR 0152, и смысл её проведения в том, что «бэкап каждого тома» стоит места, скрывая то, что важно.

    том природа в бэкапе?
    pgdata источник истины — event log, действия, pgvector, всё да, как логический дамп. Никогда не файловая копия каталога данных: копирование работающего Postgres даёт бэкап, который может не восстановиться
    git_local_repos источник истины — bare-репозитории проектов provider-а local да, и именно здесь была дыра. Он не восстанавливается из Postgres: event log хранит повествование, а не объекты git

    Что гарантирует архив bare-репозиториев — и чего не гарантирует

    Ничто не замораживается: репозитории копируются, пока api и engine могут в них писать. Что именно это даёт:

    • Гарантировано. Согласованность по ссылке. Git пишет объекты до того, как сдвинуть ref, и меняет ref атомарным rename (или перезаписью packed-refs под lock, тоже через rename). tar, пересекающийся с git push, захватывает ref в старом или новом значении, никогда не половину — и в новом случае объекты, до которых она дотягивается, уже на диске.
    • Гарантировано. Частичный архив проваливает запуск, а не проходит как хороший. Конкурентный git gc может удалить packfile между тем, как tar перечислил каталог и прочитал его; код выхода tar захватывается в файл (в POSIX sh статус конвейера — статус последней команды), и ненулевой превращается в строку failed в backup_runs, что и вызывает алерт. Запустите снова.
    • Гарантировано. Архив читаем от начала до конца до того, как что-либо будет записано, — brabo-restore-git — это pg_restore --list на стороне git. Обрезанный tar имеет правдоподобный размер, и только его чтение это показывает.
    • Не гарантировано. Какой-либо глобальный момент. tar обходит дерево за некоторый период, поэтому два репозитория — или две ref одного — могут быть из разных моментов. Неважно для git, который проверяет по ref; важно для того, кто читает «бэкап 03:17» как один снимок.
    • Не гарантировано. Связность объектов. Ничто здесь не запускает git fsck: в образе бэкапа намеренно нет git. Доказывается целостность контейнера, а не содержимого.
    • Не копируются. Файлы *.lock и objects/tmp_*. Восстановление осиротевшего lock даёт репозиторий, где каждый git отказывается работать, с сообщением, которое никогда не упоминает бэкап.

    Перед восстановлением: бэкап существует и годен ли он?

    select finished_at, kind, status, object_key,
       pg_size_pretty(size_bytes) as tamanho, error_message
  from backup_runs
 order by finished_at desc
 limit 10;

    Три вещи в этом выводе важнее последней строки:

    • Недавний status = 'failed' при старом успехе — опасный случай: бэкап есть, только старый. Алерт Last backup run failed покрывает ровно это.
    • Резкое падение size_bytes между запусками указывает на обрезанный дамп, и один размер его не выдаёт — его ловит pg_restore --list в скрипте.
    • Ни одной строки означает, что CronJob ни разу не отработал успешно. Тогда проблема не в restore.

    В Kubernetes:

    make test-restore

    В установке compose — без кластера, без kubectl:

    make test-restore-compose

    Оба запускают настоящий бэкап (тот же образ, та же команда, что работает в production, — не импровизированный pg_dump, который тестировал бы путь, которым никто не пользуется), восстанавливают в brabo_restore_test, проверяют и удаляют базу. Используйте их, когда цель — проверить бэкап, а не восстановить данные.

    Две обёртки намеренно разделены: их объединение сделало бы путь compose зависимым от kubectl, а это та зависимость, которой он существует, чтобы не иметь. Что не дублируется — это суждение: обе запускают один и тот же brabo-restore с теми же тремя проверками. Обёртка compose добавляет третий шаг, которого кластер не может запросить: она проверяет архив bare-репозиториев, потому что в Kubernetes том git_local_repos не смонтирован в под бэкапа и шаг законно пропускается, тогда как в compose он смонтирован, и пропуск был бы ложным зелёным.

    Обе доказываются каждую неделю в propriedades.yml: make test-restore (и его намеренная поломка, make test-restore-mutacao) в job-е кластера, и make test-restore-compose — с проверкой bare-репозиториев, которую делает только путь compose, — во втором job-е, restore-compose, на другом runner-е (AT-195). Миграция установщика тоже запускает вариант compose.

    Настоящее восстановление во время инцидента

    Скрипт brabo-restore восстанавливает в НОВУЮ базу и никогда не трогает исходную — намеренно. Восстановление поверх живой базы необратимо и почти всегда является неверным решением в первые минуты инцидента.

    1. Поднимите Job восстановления, указывающий на нужное вам имя базы:

    kubectl -n brabo create job restore-manual --from=cronjob/brabo-backup \
  --dry-run=client -o yaml \
| sed -e 's|\["brabo-backup"\]|["brabo-restore"]|' \
| kubectl -n brabo apply -f -

kubectl -n brabo set env job/restore-manual RESTORE_DB=brabo_recuperado
kubectl -n brabo logs -f job/restore-manual

    Чтобы восстановить из еженедельной копии вместо последней ежедневной: RESTORE_PREFIX=weekly/.

    2. Проверьте, что вернулось — те же вопросы, что задаёт скрипт, теперь своими глазами:

    -- quantas tabelas voltaram (compare com a origem, não com um número
-- fixo: toda migration nova muda esta contagem)
select count(*) from information_schema.tables
 where table_schema = 'public' and table_type = 'BASE TABLE';

-- o event log é denso por sessão: esta consulta tem de voltar VAZIA
select session_id, count(*), min(seq), max(seq)
  from session_events
 group by session_id
having count(*) <> max(seq) - min(seq) + 1 or min(seq) <> 1;

    3. Повысьте восстановленную базу, направив на неё DATABASE_URL и перезапустив api и engine. Это последний шаг и единственный разрушительный:

    kubectl -n brabo patch secret brabo-secrets --type merge \
  -p "{\"data\":{\"DATABASE_URL\":\"$(printf '%s' "$NOVA_URL" | base64 -w0)\"}}"
kubectl -n brabo rollout restart deployment/api deployment/engine

    Secret материализуется External Secrets из provider-а. Прямой patch перезаписывается при следующем refreshInterval (1h): измените также значение в provider-е, иначе система молча вернётся к старой базе в течение часа — посреди восстановления.

    Проверка: шаги 1 и 2 — это brabo-restore, который make test-restore запускает каждую неделю, а два запроса шага 2 — те, которые задаёт себе docker/backup/restore.sh. Шаг 3 — patch DATABASE_URL и перезапуск api и engine против восстановленной базы — никогда не выполнялся: проверка удаляет brabo_restore_test по завершении и никогда не направляет на неё работающую api.

    Чего НЕ покрывает restore

    • Учётные данные пользователей становятся нечитаемыми, если CREDENTIALS_MASTER_KEY другой. Дамп несёт упакованные DEK, а не ключи. Восстановление в среду с другим мастер-ключом возвращает целую базу с бесполезными учётными данными LLM и git. См. Ротация мастер-ключа.
    • Ничто из пользователей не остаётся за бортом. Начиная с отказа от Keycloak (ADR 0032) нет отдельной базы IdP: идентичности, учётные данные argon2id, refresh-токены и event log auth живут все в одном Postgres и попадают в этот дамп. Что не выживает — их чтение, если AUTH_TOKEN_PEPPER другой, — то же рассуждение, что для мастер-ключа выше.
    • brabo-restore восстанавливает базу, и только её. Bare-репозитории — это родственная команда brabo-restore-git — см. Восстановление bare-репозиториев. Это отдельные команды, а не две фазы одной, потому что это два артефакта с двумя суждениями: сбой git не может провалить проверку event log, а обратное было бы хуже.
    • Worktrees агентов (project_workspaces) не копируются, и это не нужно: WorktreeManager пересоздаёт их из bare-репозитория. Теряется незакоммиченная работа в процессе.
    • Настоящие репозитории живут в GitHub/GitLab — это было написано здесь и было неверно, и именно поэтому том годами оставался без бэкапа. Это верно для проектов provider-ов github/gitlab; для проекта provider-а local нигде нет upstream, и bare-репозиторий в git_local_repos и есть код, который произвели агенты.
    • Это не PITR. Гранулярность — последний дамп; всё, что записано после него, теряется. Если это неприемлемо, путь — архивирование WAL в CloudNativePG, что вне объёма этой фазы.

    Восстановление bare-репозиториев

    Проверка ничего не стоит и ничего не пишет — это еженедельный жест, и начиная с AT-195 его выполняет запланированный job restore-compose из propriedades.yml (через make test-restore-compose, см. автоматизированный путь):

    docker compose -f docker/docker-compose.prod.yml run --rm backup brabo-restore-git

    Восстановление — жест, выполняемый раз на инцидент, и его нужно набрать:

    docker compose -f docker/docker-compose.prod.yml \
  run --rm --user 0:0 backup brabo-restore-git --restaurar

    Две вещи об этой команде, обе измеренные, а не предположенные:

    • --user 0:0 здесь не опционален. git_local_repos разделяется тремя образами, работающими с тремя разными uid (api как node, engine как engine, образ бэкапа как uid 70). Том принадлежит тому, кто смонтировал его первым, режим 0755: uid 70 его читает и не может писать. Без root команда отказывает до извлечения, называя это исправление, — она не обнаруживает проблему посреди tar, оставляя том записанным наполовину.
    • Извлечённое возвращается владельцу каталога, а не остаётся под root. Иначе том вернулся бы целым и бесполезным: api и engine, не-root, не смогли бы писать в только что восстановленное, и симптом проявился бы долго после restore, и ничто бы на него не указывало.

    Она отказывается извлекать поверх существующих репозиториев. Наложение двух состояний репозитория даёт смесь, на которую не жалуется ни один git и которую никто не замечает, пока fetch не вернёт неверную историю. Опустошите том или передайте RESTORE_GIT_FORCE=1, если наложение — действительно то, что вам нужно.

    Проверка: shell-функции за обоими жестами доказываются в каждом PR scripts/ci/backup-lib.spec.ts — архивирование и восстановление совпадают в оба конца, ни один *.lock не копируется, обрезанный архив отклоняется при чтении, назначение, в которое невозможно писать, отклоняется до tar. Сами команды, в образе бэкапа против настоящего тома, выполняются через make test-restore-compose (половина, которая проверяет, никогда --restaurar), каждую неделю в propriedades.yml. Этот job сначала создаёт bare-репозиторий в томе (git init --bare, как делает LocalGitProvider) и проваливается, если вердикт его не называет: при пустом томе brabo-restore-git отвечает «nada a restaurar» и завершается с 0, что было бы зелёным, не прочитавшим ни одного архива.

    Потеря графа (Neo4j)

    neo4j_data не входит ни в один бэкап, и это решение, а не недосмотр (ADR 0152, решение 4). Восстановление, возможно, устаревшей проекции рядом с Postgres, восстановленным в другой момент, даёт два производных состояния из разных моментов без чего-либо, что бы их примирило. Правильный ответ для производной памяти — перепроецировать из источника — и такая команда существует (RN-569):

    # Kubernetes (o script vem dentro da imagem da api)
kubectl -n brabo exec deploy/api -- node scripts/reprojetar-grafo.js
kubectl -n brabo exec deploy/api -- node scripts/reprojetar-grafo.js --project <project-uuid>

# compose de instalação (mesma imagem do Kubernetes)
docker compose -f docker/docker-compose.install.yml exec api node scripts/reprojetar-grafo.js

# um checkout de dev (DATABASE_URL e NEO4J_* apontando para o banco e o grafo)
pnpm --filter api grafo:reprojetar
pnpm --filter api grafo:reprojetar -- --project <project-uuid>

    Ожидаемый вывод:

    [reprojetar] escopo: event log inteiro
[reprojetar] eventos: 4 projetados, cursor 01M2DTREY0TBKHCHG9NWXYF0A4
[reprojetar] sessões fechadas: 2 projetadas

[reprojetar] resultado

  eventos projetados=4  sessões fechadas projetadas=2  falhas=0
  grafo agora (inteiro): nós=80  arestas=80

    Что она делает и что гарантирует:

    • Тот же перевод, что у живого проектора. Событие → узел/ребро живёт в одном классе (GraphEventTranslator), вызываемом как прямым проектором, так и этой командой. Она читает handoff.offered, psychologist.hypothesis_proposed и anamnese.profile_updated из session_events, а Interacao каждой сессии в closed/closed_abnormally — из sessions (закрытие сессии не оставляет события в логе).
    • Идемпотентна и никогда не удаляет. Каждая запись — MERGE по естественному ключу: двойной запуск даёт тот же граф, и повторный запуск — это способ повторить попытку после сбоя посередине. Она только добавляет или сходится; узел, уже находящийся в графе, остаётся.
    • Пакетами, по курсору. session_events обходится в порядке id (ULID, первичный ключ), по 200 строк за раз — никогда вся таблица в памяти. Строка прогресса печатает курсор; --after-event <id> возобновляет фазу событий после него. Начать заново так же безопасно, только медленнее.
    • Она не трогает outbox, поэтому api может оставаться запущенной. Живой проектор хранит свой прогресс в outbox_events.processed_at (aggregate_type = 'graph_projection'); эта команда не читает и не пишет эту таблицу, поэтому не может украсть, переоткрыть или пометить строку. Обе пишут через MERGE по одним и тем же ключам.
    • Она падает с именем, никогда как молчаливый успех. Не настроенный или недоступный Neo4j отклоняется до чтения лога (иначе пустой объём «сработал» бы с нулём спроецированных); Neo4j, падающий посередине, останавливает работу на последнем завершённом событии; неизвестный --project отклоняется без какой-либо записи; элемент с несогласованным payload подсчитывается, называется, и запуск завершается с 1 в конце.

    Чего она не восстанавливает, и единственная оговорка о порядке:

    • PromptTemplate/PromptVersion не берутся из event log. Их источник — каталог prompts/: отправьте их заново через node scripts/dev/seed-prompts.ts (идемпотентно по хешу).
    • PerfilAnamnese — снимок с ключом пользователь + измерение, без проекта. Побеждает последний записавший. Запуск с --project повторно выполняет только события профиля этого проекта, поэтому может оставить снимок на последнем значении этого проекта, когда другой проект записал более новое. Полный запуск (без --project) обходит весь лог по порядку и восстанавливает глобальное последнее — используйте его после потери графа; приберегите --project для точечного ремонта.
    • Полный запуск требует окна обслуживания, без предела по времени, и сколько он длится на большом логе, не измерено — см. Выполнение полной перепроекции про окно, строку прогресса и как узнать, сколько осталось.

    Доказательство — make test-reprojecao (apps/api/test/scripts/reprojetar-grafo.spec.ts): он строит сценарий с прямым проектором, удаляет этот подграф, перепроецирует, сравнивает количество узлов и рёбер плюс список ключей и перепроецирует снова. Ему нужен запущенный Neo4j, и без него он пропускается — у job-а CI api нет Neo4j, поэтому там он пропускается. Он намеренно не зависит от того, был ли бэкап.

    То же доказательство запускается и внутри локального кластера: make test-reprojecao-k8s (deploy/k8s/test-reprojecao.sh) — четвёртая цель запланированного propriedades.yml (см. Запланированные доказательства свойств). Он запускает команду ровно так, как этот раздел велит запускать её при инциденте (kubectl exec deploy/api -- node scripts/reprojetar-grafo.js --project <id>), против Postgres и Neo4j кластера, в проекте, который он создаёт сам. Начиная с AT-191 его сценарий проверяет все четыре пути перевода GraphEventTranslator — handoff.offered, psychologist.hypothesis_proposed, ссылающийся на сообщение как на улику, anamnese.profile_updated для собственного пользователя и Interacao закрытой сессии — и требует 9 узлов и 6 рёбер до очистки, после восстановления и после второго запуска (измерено в запуске 36498776825). Psicólogo и Anamnese остаются на паузе: доказательство добавляет события, которые они записали бы, и проверяет, что перепроекция из них восстанавливает.

    Пустой граф до запуска этого имеет названный эффект: чтения, зависящие от графа, деградируют. RAG не затронут — он живёт в pgvector, который находится внутри дампа.

    Выполнение полной перепроекции: окно обслуживания, без предела по времени

    Полная перепроекция (графа или папки артефактов) — редкая операция восстановления, и она выполняется в окне обслуживания, без предела по времени — решение мейнтейнера (2026-09-27). Ничто в продукте не обрывает её по времени, не предупреждает, когда она долго идёт, и не планирует её: она идёт столько, сколько потребует event log, и вы планируете окно под это.

    Сколько это на логе размера production, не измерено. Единственный реальный запуск пока — compose разработки (98 событий в session_events, 2,5 s от начала до конца); пропорциональная экстраполяция из этого не является измерением, поэтому засеките первый полный запуск вашей установки и сохраните это число для следующего окна.

    Отслеживание прогресса. Команда печатает одну строку на пакет — каждые 200 событий читаемых ею типов — перед итоговым результатом, так что запуск, который ещё печатает, ещё обходит лог:

    [reprojetar] eventos: 200 projetados, cursor 01M2DTREY0TBKHCHG9NWXYF0A4
[reprojetar] eventos: 400 projetados, cursor 01M2DV3K8Q2S7ZB1CXN4W6Y9HR
...
[reprojetar] sessões fechadas: 200 projetadas
[reprojetar-artefatos] artefatos: 200 projetados, cursor 01M2DTREY0TBKHCHG9NWXYF0A4

    Число — сколько было спроецировано (неудавшиеся элементы печатаются в собственной строке и подсчитываются в falhas= в конце). Строка не несёт итога. Чтобы узнать, сколько осталось, спросите Postgres, с курсором последней строки — только чтение, поэтому безопасно, пока запуск продолжается:

    -- grafo, fase de eventos: quantos no total, e quantos ainda depois do cursor
SELECT count(*) AS total,
       count(*) FILTER (WHERE id > '<cursor>') AS remaining
  FROM session_events
 WHERE type IN ('handoff.offered', 'psychologist.hypothesis_proposed',
                'anamnese.profile_updated');

-- grafo, segunda fase (a Interacao de cada sessão fechada)
SELECT count(*) FROM sessions WHERE status IN ('closed', 'closed_abnormally');

-- pasta de artefatos
SELECT count(*) AS total,
       count(*) FILTER (WHERE id > '<cursor>') AS remaining
  FROM session_events
 WHERE type IN ('artifact.note', 'artifact.business_rule',
                'artifact.decision_record', 'artifact.product_brief',
                'artifact.module_map', 'artifact.module_routing',
                'artifact.project_image', 'artifact.c4_diagram',
                'artifact.prototipo_navegavel', 'artifact.plano_de_teste',
                'artifact.threat_model', 'artifact.insight',
                'artifact.rfc_staff');

-- quando o evento do cursor foi escrito (os ids são ULIDs, ordenados por tempo)
SELECT created_at FROM session_events WHERE id = '<cursor>';

    Добавьте AND session_id IN (SELECT id FROM sessions WHERE project_id = '<project-uuid>') к подсчёту, когда у запуска есть --project. Списки типов — те, которые читают команды (EVENTOS_DO_LOG_PROJETAVEIS в apps/api/src/application/graph-projection/graph-event-translator.ts, ARTIFACT_PROJECTABLE_EVENT_TYPES в apps/api/src/domain/artifacts/artifact-projection-events.ts); если какой-то из файлов получил новый тип, подсчёт здесь его недосчитает.

    Чего это решение не добавляет. Ни предела, ни предупреждения, ни перепроекции, разделённой на окна или запланированной продуктом. --project и --after-event остаются ровно тем, чем были, — точечным ремонтом и возобновлением после прерывания — и не являются способом уместить полное восстановление в более короткое окно: запуск с --project не может восстановить глобальный снимок PerfilAnamnese (выше), а возобновление посреди версионируемого типа артефакта может оставить более старую версию (ниже). Полный запуск и есть восстановление. Прерывать его безопасно — идемпотентность выше действует, — и повторный запуск с начала всегда корректен, только медленнее.

    Потеря папки артефактов (docs/)

    Каждый артефакт, который выпускают агенты, живёт только в event log; папка docs/ проекта — его проекция (ADR 0148), поэтому она не входит ни в один бэкап, и это решение, а не недосмотр (ADR 0152 рассуждает так же о графе). Восстановление базы не возвращает её само по себе: строки outbox, двигающие живой проектор, уже помечены как обработанные, поэтому ничто не переписывает папку. Команда, которая переписывает, существует (RN-590):

    # Kubernetes (o script vem dentro da imagem da api)
kubectl -n brabo exec deploy/api -- node scripts/reprojetar-artefatos.js
kubectl -n brabo exec deploy/api -- node scripts/reprojetar-artefatos.js --project <project-uuid>

# compose de instalação (mesma imagem do Kubernetes)
docker compose -f docker/docker-compose.install.yml exec api node scripts/reprojetar-artefatos.js

# um checkout de dev (DATABASE_URL apontando para o banco)
pnpm --filter api artefatos:reprojetar
pnpm --filter api artefatos:reprojetar -- --project <project-uuid>

    Ожидаемый вывод:

    [reprojetar-artefatos] escopo: event log inteiro
[reprojetar-artefatos] artefatos: 6 projetados, cursor 01M2DTREY0TBKHCHG9NWXYF0A4

[reprojetar-artefatos] resultado

  artefatos projetados=6  falhas=0

    Что она делает и что гарантирует:

    • Тот же перевод, что у живого проектора. Событие → папка, имя файла и Markdown живут в одном классе (ArtifactEventTranslator), вызываемом как прямым проектором, так и этой командой.
    • Идемпотентна и никогда не удаляет. Имя файла — функция события (версионируемые типы: <tipo>.md; append-only: с seq), поэтому двойной запуск перезаписывает те же файлы тем же содержимым, и повторный запуск — это способ повторить попытку. Файл, который вы создали в docs/, остаётся.
    • Пакетами, по курсору. session_events обходится в порядке id, по 200 строк за раз; --after-event <id> возобновляет после напечатанного курсора.
    • Она не трогает outbox, поэтому api может оставаться запущенной.
    • Она падает с именем, никогда как молчаливый успех. Неудавшаяся запись (переполненный диск, недоступная папка, проект, чья папка исчезла) подсчитывается и называется по событию, не останавливает остальное, и запуск завершается с 1 в конце. Неизвестный --project отклоняется без какой-либо записи.

    Куда она пишет и чего не покрывает:

    • Ей нужно видеть тот же диск, что и api. Папка разрешается той же функцией, что использует проектор (container/runner: <PROJECT_WORKSPACES_ROOT>/<workspace_dir_name>/docs/; mounted: внутри папки проекта). Запускайте её в образе api, с томами api.
    • Она пишет в текущее местоположение проекта. Конвертация режима не перемещает docs/ (код конвертации её никогда не трогает), поэтому файлы, записанные до неё, остаются в старом месте; перепроекция воссоздаёт их в текущем.
    • Версионируемые типы показывают последнее событие, поэтому не возобновляйте посреди них. module_map, module_routing, project_image и c4_diagram перезаписывают файл; полный запуск заканчивается последней выпущенной версией, тогда как --after-event, начинающийся между двумя версиями, может оставить более старую.
    • Чего она не читает: типы вне проецируемого списка (qa_verdict, secops_verdict, task_blocked, infra_delegation_files) никогда не были файлами и не воссоздаются.
    • Она выполняется в окне обслуживания, без предела по времени, как и граф: строка прогресса и запросы для её отслеживания — в Выполнение полной перепроекции. Сколько она длится на большом event log, не измерено; команду безопасно прерывать и запускать снова.

    Доказательство — apps/api/test/scripts/reprojetar-artefatos.spec.ts: он строит сценарий с прямым проектором на настоящем Postgres и настоящем диске, удаляет папку, перепроецирует, сравнивает каждый путь и содержимое и перепроецирует снова. Он запускается в каждом PR. Команда в том виде, как этот раздел велит запускать её при инциденте, — node scripts/reprojetar-artefatos.js внутри образа api — доказывается make test-reprojecao-artefatos-k8s (deploy/k8s/test-reprojecao-artefatos.sh, AT-198), родственником цели кластера для графа: он создаёт собственный проект с artifact.note через API, ждёт, пока живой проектор его запишет, удаляет папку docs/<agente>/ агента внутри пода api, запускает собственный скрипт образа с --project и требует, чтобы восстановленный файл имел тот же sha256, что записал живой проектор, — затем запускает снова и требует тот же хеш (идемпотентность). Он запускается в запланированном .github/workflows/propriedades.yml и, как и его родственник, не зависит ни от какой другой цели.

    Когда restore не удаётся

    симптом вероятная причина
    no backup under .../daily/ не тот bucket, не те учётные данные, или CronJob ни разу не запускался
    not an intact custom dump загрузка прервана; используйте предыдущий объект или weekly/
    pg_restore failed с ошибкой расширения целевой базе нужны те же расширения (pgvector); в CNPG они приходят из кластера, а не из дампа
    missing tables in the restored copy дамп другой версии схемы — скрипт говорит, КАКИХ не хватает; сверьте дату объекта с самой свежей миграцией
    out of window в критической таблице количество не совпадает с временной меткой дампа: разберитесь перед повышением
    server version mismatch pg_dump в Job — 16; кластер другой major-версии отклоняет подключение
    timeout Job-а база слишком велика для activeDeadlineSeconds; повысьте значение в Job, а не в CronJob
    destination inaccessible … does not accept writes с BACKUP_DIR каталог существует, но uid контейнера не может в него писать. Это намеренно проверка записи, а не существования: назначение только для чтения прошло бы ls и провалило бы дамп, с ошибкой, появляющейся после pg_dump и указывающей не туда
    tar of the bare repos exited with N что-то изменилось под репозиториями посреди чтения — скорее всего, конкурентный git gc. Запуск помечается failed, а не выдаёт частичный архив. Запустите снова
    there are N bare repo(s) … and NO archive у этого тома нет покрытия: архива нет, а репозитории есть. Отсутствие при пустоте — норма и сообщается иначе
    does not accept writes by this user (uid 70) при --restaurar случай с владельцем общего тома — восстанавливайте с --user 0:0, см. Восстановление bare-репозиториев

    Запланированные доказательства свойств

    make test-restore, make rollout-test и make hpa-test доказывают свойства, а не конфигурацию — бэкап, который выполняется каждую ночь и не восстанавливается, проходит все пять алертов brabo-alerts.yaml. До BRB-009 они запускались, только когда кто-то их набирал. .github/workflows/propriedades.yml теперь запускает их по расписанию, в кластере k3d на runner-е, размещённом GitHub:

    1. устанавливает k3d, helm и kubectl по зафиксированной контрольной сумме;
    2. запускает deploy/k8s/bootstrap.sh — тот же bootstrap, что запускает make deploy-local, собирая четыре образа production из дерева checkout-а (без registry, без секрета) — с BRABO_SKIP_OBSERVABILITY=1 (AT-177): ни одно из доказательств не читает Tempo, Loki, Collector, Alloy или Grafana, и это единственное отличие от кластера, который даёт вам make deploy-local;
    3. запускает make smoke-k8s, затем make hpa-test, make rollout-test и make test-restore, в порядке Makefile, каждый — даже когда предыдущий упал (сломанный HPA не может скрыть сломанный restore);
    4. запускает make test-restore-mutacao (AT-126, BRB-009), доказательство доказательства: он делает настоящий бэкап, затем создаёт таблицу (zz_mutacao_restore) в источнике, которой нет в дампе, — ровно «дамп без одной таблицы» — и запускает тот же brabo-restore. Он проходит, только если restore его отклоняет и называет эту таблицу (строка лога faltando: zz_mutacao_restore); если restore одобряет или отклоняет по другой причине, шаг падает и открывает собственный issue.     Ротация ключей auth

    Решения — в ADR 0031 и ADR 0032.

    У first-party auth три секрета с очень разными последствиями при замене. Спутать первые два — дорогая ошибка здесь.

    AUTH_JWT_SECRET — ротация без недоступности

    Пара Ed25519, подписывающая access token, выводится из него. Ротация — тот же трёхшаговый танец, что и для мастер-ключа (ниже):

    1. AUTH_JWT_SECRET_PREVIOUS получает старое значение; AUTH_JWT_SECRET получает новое. Перезапустите api.
    2. Оба ключа появляются в /.well-known/jwks.json, и оба проверяют; подписывает только новый. Api выдаёт WARN один раз на процесс, при первой проверке или чтении JWKS после загрузки (предыдущий ключ выводится по требованию, а не при старте), пока это длится.
    3. Через 15 минут (TTL access token) ни один токен старого ключа не выживает. Удалите AUTH_JWT_SECRET_PREVIOUS и перезапустите.

    Никто не разлогинивается: refresh-токены хешируются с AUTH_TOKEN_PEPPER, а не с этим ключом, и начиная с RN-613 pepper обязателен и никогда не заимствуется у этого ключа.

    Порядок, если эта установка старше RN-613: сначала pepper, потом JWT. До RN-613 незаданный pepper молча откатывался на AUTH_JWT_SECRET — а compose production и установки даже не передавали AUTH_TOKEN_PEPPER в api, так что это касалось каждой установки compose. Теперь api отказывается стартовать без pepper, с сообщением о том, что делать. Миграция, которая никого не разлогинивает:

    1. Задайте AUTH_TOKEN_PEPPER равным текущему значению AUTH_JWT_SECRET (скопируйте его; не генерируйте новый). Перезапустите api. Хеши токенов побайтно те же, что были, поэтому каждый refresh-токен и PAT продолжает работать. install.sh делает этот шаг сам, когда находит прежний .env в папке, из которой запускается, и сообщает об этом в терминале, не печатая значение; в Kubernetes AUTH_TOKEN_PEPPER уже был в ExternalSecret.
    2. Только затем выполните ротацию AUTH_JWT_SECRET тремя шагами выше. Отныне два секрета независимы, и pepper, равный старому секрету JWT, — ожидаемое состояние, а не остаток.

    Если кто-то повернёт JWT до разделения, в версии до RN-613 эта ротация была заменой pepper: все разлогинены, каждая открытая ссылка e-mail/сброса умирает, и каждый PAT перестаёт аутентифицировать — глобальный выход, описанный в следующем разделе. Отменить нельзя, кроме как вернув старое значение в качестве AUTH_TOKEN_PEPPER (что оживляет старые неистёкшие токены и инвалидирует всё, выданное в промежутке). Начиная с RN-613 ошибка не происходит молча: без pepper api не стартует. Единственный способ всё ещё в неё попасть — сгенерировать новый pepper во время миграции вместо копирования текущего секрета JWT — тот же глобальный выход.

    Проверка: apps/api/test/infrastructure/security/ed25519-access-token-issuer.spec.ts (describe "rotação de chave"); для pepper — apps/api/test/infrastructure/security/auth-key-material.spec.ts (describe "pepperAtual (RN-613)": отказ при загрузке и его сообщение), apps/api/test/application/use-cases/auth/rotacao-dos-segredos.spec.ts (describe "a migração do RN-613": refresh, захешированный через старый откат, остаётся действительным при pepper, заданном как старый секрет JWT, и переживает ротацию JWT) и scripts/dev/install-env.spec.ts (.env, который установщик пишет в обоих случаях, через docker compose config).

    AUTH_TOKEN_PEPPER — глобальный выход, без полумер

    Это ключ HMAC для хеша refresh-токенов и токенов учётной записи. Его замена инвалидирует, всё сразу:

    • каждый refresh-токен в обращении — все разлогинены;
    • каждую открытую ссылку подтверждения e-mail и сброса пароля;
    • каждый personal access token (PAT) — runner, запущенный с --token, перестаёт аутентифицироваться (ключи устройств не затронуты);
    • счётчики блокировки: каждая заблокированная учётная запись разблокируется.

    Пароли выживают (argon2id, без pepper): люди снова входят как обычно. Отклонённый так refresh появляется как refresh_unknown в auth_events, а не как refresh_reuse_detected.

    AUTH_TOKEN_PEPPER_PREVIOUS нет, и это осознанное решение: принимать двойную проверку в каждом refresh навсегда ради сценария, который случается раз в жизни, не окупается. Если вам нужно его сменить — например, при подозрении на утечку базы, — предупредите людей заранее: симптом для пользователя — быть разлогиненным без видимой причины и видеть, что ссылка сброса говорит «expirado».

    Api не перестаёт стартовать с новым pepper. Она просто перестаёт узнавать какой-либо старый токен. Если поддержка сообщает «все были разлогинены одновременно», эта переменная — первое место, куда смотреть, — и, в версии до RN-613, где она никогда не была задана, AUTH_JWT_SECRET. Без него она перестаёт стартовать в production: см. порядок миграции выше.

    Проверка: apps/api/test/application/use-cases/auth/rotacao-dos-segredos.spec.ts (RN-597).

    BRABO_SERVICE_TOKEN — ротация без недоступности, с обеих сторон

    Это общий секрет, аутентифицирующий трафик api ↔ engine (RN-035). Он не имеет ничего общего с сессией пользователя: ошибка в нём никого не разлогинивает, она ломает внутреннюю связь.

    Танец тот же, что для AUTH_JWT_SECRET, с той разницей, что он выполняется в обеих нагрузках — и порядок важен, потому что каждая сторона отправляет текущий и принимает оба:

    1. BRABO_SERVICE_TOKEN_PREVIOUS получает старое значение в api и engine; BRABO_SERVICE_TOKEN получает новое в обоих. Перезапустите оба. В production api, engine и broker проверяют старое значение по тому же правилу, что и новое, поэтому если старое значение — публичное значение по умолчанию или короче 16 символов, каждый из них отказывается стартовать на этом шаге и называет переменную (RN-598, RN-601). Уход со слабого токена, таким образом, означает пропуск _PREVIOUS и оплату этого окном 403/401, описанным ниже.
    2. Пока обе стороны запущены с новой переменной, трафик работает в любой комбинации старых и новых подов — именно это делает rollout безопасным на полпути.
    3. Когда rollout обоих Deployment-ов закончен, удалите BRABO_SERVICE_TOKEN_PREVIOUS и перезапустите.

    Пропуск шага 1 и простая замена текущего значения дают 403/401 в течение всего окна, пока старый под остаётся с любой из сторон, — симптом из диагностики выше.

    Проверка: в api — apps/api/test/infrastructure/security/service-token.spec.ts (describe "rotação do BRABO_SERVICE_TOKEN") и apps/api/test/interfaces/engine-service.guard.spec.ts; в engine — apps/engine/test/engine_web/plugs/verify_service_token_test.exs и apps/engine/test/engine/runtime_service_token_test.exs (правило загрузки); в broker — apps/broker/src/config.spec.ts.

    Где переменные _PREVIOUS доходят до процесса. Во всех трёх compose (docker-compose.yml, docker-compose.prod.yml, docker-compose.install.yml) все они отображены в environment: сервиса, который их читает, пустые по умолчанию — достаточно задать одну в .env и пересоздать сервис (RN-595; охраняется scripts/ci/previous-nos-composes.spec.ts, который выводит список из кода). В Kubernetes они доходят до Pod-ов через хранилище секретов (AT-220): ExternalSecret (deploy/k8s/base/common/externalsecrets.yaml) забирает объект brabo целиком через dataFrom.extract, так что существующий там _PREVIOUS попадает в brabo-secrets, а несуществующего там просто нет — без сбоя синхронизации вне ротации. Они никогда не перечисляются по одному: элемент data, у которого отсутствует свойство, проваливает синхронизацию всего Secret, а отсутствующий _PREVIOUS — нормальное состояние. В любом случае проверьте внутри контейнера (printenv), прежде чем доверять шагу 2.

    Выполнение в Kubernetes

    Тот же танец, где объект brabo в provider-е секретов играет роль .env. В локальном кластере этот объект — Secret brabo, созданный bootstrap-ом; в staging/prod — запись provider-а, на которую указывает SecretStore.

kubectl -n brabo get secret brabo-secrets -o go-template='{{range $k, $v := .data}}{{$k}}{{"\n"}}{{end}}' | grep _PREVIOUS

kubectl -n brabo exec deploy/api -- printenv AUTH_JWT_SECRET_PREVIOUS

    4. Выведите его из обращения, когда условие самой ротации выполнено (15 min для AUTH_JWT_SECRET, оба rollout-а завершены для BRABO_SERVICE_TOKEN, falhas=0 и ноль ожидающих для мастер-ключа): удалите ключ _PREVIOUS из объекта brabo, снова принудительно синхронизируйте (шаг 2 — ключ исчезает из brabo-secrets, а не остаётся) и снова перезапустите (шаг 3). До перезапуска Pod-ы держат старое значение в памяти, и api продолжает предупреждать, что идёт ротация.

      kubectl -n brabo patch secret brabo --type json -p \
  '[{"op":"remove","path":"/data/AUTH_JWT_SECRET_PREVIOUS"}]'

Начиная с AT-146 те же четыре шага выполняются каждую неделю для CREDENTIALS_MASTER_KEY, внутри репетиции мастер-ключа (make test-rotacao-chave-mestra-k8s, см. В каждом PR выполняется scripts/ci/previous-nos-composes.spec.ts, который проваливается, если ExternalSecret перестаёт использовать dataFrom.extract или перечисляет _PREVIOUS в data:.

    Учётная запись заблокирована lockout-ом

    Lockout короткий (от 30s до 15 минут) и разрешается сам: скользящее окно опустошается. Endpoint-а разблокировки нет — намеренно, см. RN-031. Если нужно разблокировать кого-то прямо сейчас:

    -- A chave é um HMAC do e-mail, não o e-mail. Ache-a pelo evento recente:
select subject_key, count(*), max(occurred_at)
  from auth_events
 where kind in ('login_failure', 'login_blocked_user')
   and occurred_at > now() - interval '30 minutes'
 group by subject_key order by 3 desc;

delete from auth_lockout_hits where bucket_key = '<subject_key>';

    Успешный сброс пароля тоже разблокирует учётную запись.

    Ротация мастер-ключа

    Решения — в ADR 0027.

    CREDENTIALS_MASTER_KEY упаковывает DEK, шифрующие секреты пользователя: ключи API LLM и токены git. Он ротируется периодически и обязательно после любого подозрения на утечку.

    Что поставлено на карту

    Замена переменной и перезапуск api с одним ключом делает каждые существующие учётные данные нечитаемыми, все разом, без ошибки загрузки — сбой проявляется только при первом использовании, как «não foi possível decifrar», и пути назад нет, кроме восстановления старого ключа.

    Поэтому у ротации три шага, а не один. Во время среднего два ключа сосуществуют:

    переменная роль
    CREDENTIALS_MASTER_KEY ТЕКУЩИЙ ключ — всегда используется для шифрования
    CREDENTIALS_MASTER_KEY_PREVIOUS предыдущий ключ — пробуется, только когда текущий не подходит

    Две таблицы хранят конверты: user_credentials и project_git_connections.

    Начиная с RN-563 каждый конверт несёт также key_id — отпечаток ключа, который его упаковал. Именно он делает прогресс шага 2 отвечаемым на SQL. В 3 часа ночи о нём важны две вещи:

    • Он никогда не решает, открывается ли строка. Чтение по-прежнему пробует текущий ключ и откатывается на предыдущий; AES-GCM аутентифицирует, и он — авторитет. Метка — это метаданные, и строка, чья метка не согласуется с конвертом, всё равно корректно переупаковывается (ADR 0158).
    • key_id IS NULL означает «записано до появления этого столбца», никогда «в текущем ключе». В установке, предшествующей ему, всё равно NULL до первой ротации, и запросы ниже считают это ожидающим — что и есть честный ответ.

    Возьмите текущий отпечаток из собственного лога api; она печатает строку при загрузке:

    kubectl -n brabo logs -l app.kubernetes.io/name=api --tail=200 \
  | grep 'chave mestra corrente'
# chave mestra corrente: key_id=4f2b91c0a77e13d5

    Сначала: оцените объём

    select 'user_credentials' as tabela, count(*) from user_credentials
union all
select 'project_git_connections', count(*) from project_git_connections;

    Переупаковка — один UPDATE на строку. Тысячи строк занимают секунды; порядок величины полезно знать до начала.

    1. Опубликуйте оба ключа

    Сгенерируйте новый и опубликуйте оба в provider-е секретов, сохранив старый в CREDENTIALS_MASTER_KEY_PREVIOUS:

    openssl rand -hex 32   # a chave nova

    В локальном кластере исходный Secret создаётся bootstrap-ом; в staging/prod значение идёт в provider, из которого читает External Secrets. Затем перезапустите api, чтобы она загрузила оба:

    Публикация CREDENTIALS_MASTER_KEY_PREVIOUS в объекте brabo provider-а помещает его в brabo-secrets при следующей синхронизации (ExternalSecret забирает объект целиком) — принудительно синхронизируйте и подтвердите, что он пришёл, как в Выполнении в Kubernetes, затем перезапустите. В compose это .env плюс пересоздание api.

    kubectl -n brabo rollout restart deployment/api
kubectl -n brabo rollout status  deployment/api

    Подтвердите, что api в режиме ротации — она намеренно предупреждает в логе, и предупреждение называет оба отпечатка, с которыми сравнивают запросы ниже:

    kubectl -n brabo logs -l app.kubernetes.io/name=api --tail=50 \
  | grep CREDENTIALS_MASTER_KEY_PREVIOUS
# ... rotação em andamento (atual key_id=<NEW>, anterior key_id=<OLD>). ...

    С этого момента ничто не ломается: новый секрет сразу рождается в новом ключе, старый секрет остаётся читаемым через предыдущий. Можно остановиться в этом состоянии на часы, если нужно, — но не на недели: приём двух ключей удваивает поверхность утёкшего ключа, что и является причиной, по которой вы ротируете.

    2. Переупакуйте хранилище

    kubectl -n brabo exec deploy/api -- node scripts/rewrap-deks.js

    Ожидаемый вывод — скрипт печатает по-португальски, и вот что он действительно пишет (apps/api/src/scripts/rewrap-deks.ts, main):

    [rewrap] resultado

  user_credentials         total=12  re-embrulhados=12  já na chave atual=0  falhas=0
  project_git_connections  total=3   re-embrulhados=3   já na chave atual=0  falhas=0

[rewrap] concluído. Agora remova CREDENTIALS_MASTER_KEY_PREVIOUS e reinicie a api.

    Счётчики: re-embrulhados, já na chave atual и falhas. Есть два других исхода. Когда ничего не нужно было переупаковывать, последняя строка — [rewrap] nada a fazer — o acervo já está na chave atual.. Когда какая-то строка не удалась, каждая идёт в stderr как [rewrap] <tabela>#<id>: <motivo>, запуск заканчивается [rewrap] <N> registro(s) não abriram com nenhuma das duas chaves. NÃO remova CREDENTIALS_MASTER_KEY_PREVIOUS até resolver., а код выхода — 1.

    Свойства, важные, если что-то прервёт скрипт:

    • Идемпотентен. Повторный запуск считает уже конвертированные строки как já na chave atual и ничего не перезаписывает. Прервали? Запустите снова.
    • Меняется только конверт. Шифротекст секрета остаётся побайтно тем же, поэтому остановка посередине оставляет хранилище согласованным: часть в новом ключе, часть в старом, и обе читаемы, пока PREVIOUS существует.
    • falhas > 0 блокирует шаг 3. Это строки, которые не открываются ни одним ключом — обычно пришедшие из другой среды или от прерванной предыдущей ротации с уже выброшенным ключом. Скрипт идентифицирует каждую по id и называет, ПОЧЕМУ она не удалась, — строка из другой среды («embrulhado pela chave <kid>»), строка, чья метка не согласуется с конвертом («rótulo incoerente ou registro adulterado»), и строка вообще без метки — три разных диагноза с тремя разными ответами. Не удаляйте PREVIOUS: без него вы потеряете и то, что ещё открывалось.

    Прервали и хотите знать, где остановились? Спросите базу, а не запускайте скрипт снова ради счётчика — с <NEW>, текущим отпечатком из лога выше:

    select 'user_credentials' as tabela, count(*) as pendentes
  from user_credentials       where key_id is distinct from '<NEW>'
union all
select 'project_git_connections', count(*)
  from project_git_connections where key_id is distinct from '<NEW>';

    is distinct from, никогда <>: строки с key_id IS NULL должны считаться ожидающими, а <> молча их отбросил бы.

    3. Выбросьте старый ключ

    Только после falhas=0 и ответа 0 на запрос выше в обеих таблицах. Они говорят разное, и вам нужно и то и другое: falhas=0 означает, что ничто не отказалось открыться в этом запуске, а запрос означает, что ничего не осталось позади, — включая строки, до которых предыдущий, прерванный запуск так и не добрался.

    # remova CREDENTIALS_MASTER_KEY_PREVIOUS do provedor, depois
kubectl -n brabo annotate externalsecret brabo-secrets force-sync="$(date +%s)" --overwrite
kubectl -n brabo rollout restart deployment/api

    Проверьте, что предупреждение о ротации исчезло из лога и что существующие учётные данные всё ещё работают (самый прямой путь — экран учётных данных проекта или любой ход агента, использующий ключ LLM).

    Проверка без ожидания инцидента

    У всего цикла есть именованная проверка, и она выполняется в CI (RN-562):

    pnpm --filter api test -- test/scripts/rewrap-deks.spec.ts

    Этот spec проводит последовательность этой страницы против настоящего Postgres и обеих таблиц: шифрует с K1, публикует K2, переупаковывает, выбрасывает K1 и всё ещё расшифровывает. Он также фиксирует два свойства, на которые опирается эта процедура, — идемпотентность (второй запуск сообщает re-embrulhados=0) и нечитаемую строку, которая подсчитывается и называется, не прерывая остальные.

    Более узкое покрытие тех же примитивов в памяти — включая случай, когда не работает ни один ключ, и случай, когда метка key_id лжёт, — живёт в test/infrastructure/security/envelope-encryption.service.spec.ts.

    rewrap также работает в любой среде: в тестовой полный цикл вручную укладывается в несколько минут.

    Запускалась ли по-настоящему? Нет. Ответ мейнтейнера (2026-09-27): эта ротация ни разу не выполнялась в реальной среде. Так что spec выше — не страховочная сетка под отработанной процедурой: до AT-146 он был единственным доказательством и никогда не касался образа, ExternalSecret или перезапуска api.

    Репетиция в кластере, каждую неделю (AT-146). make test-rotacao-chave-mestra-k8s (deploy/k8s/test-rotacao-chave-mestra.sh) выполняет три шага этой страницы против локального кластера, с той же механикой: он записывает учётные данные LLM со случайным значением через API и проверяет, что каждый конверт открывается сегодняшним ключом; шаг 1 публикует новый ключ и старый как _PREVIOUS в исходном Secret brabo (локальная замена provider-а — никогда не напрямую brabo-secrets), принудительно синхронизирует ExternalSecret, ждёт прихода _PREVIOUS, перезапускает api и требует предупреждения о ротации с обоими отпечатками; шаг 2 требует ожидающих строк по запросу выше, запускает node scripts/rewrap-deks.js из образа (falhas=0), требует ноль ожидающих и запускает снова (nada a fazer); шаг 3 удаляет _PREVIOUS из источника, требует, чтобы он исчез из brabo-secrets после синхронизации, перезапускает api, требует строку загрузки с новым отпечатком и отсутствия предупреждения о ротации, и проверяет, что каждый конверт открывается только новым ключом — и что учётные данные из начала расшифровываются в то же значение (сравнение по sha256 внутри пода; значение никогда не покидает его). Вердикт — код выхода. Это последняя цель запланированного .github/workflows/propriedades.yml, потому что она меняет секрет и перезапускает api, и оставляет кластер на новом ключе без _PREVIOUS — завершённая ротация, а не половинчатая. Первый зелёный запуск: 36502355798 (2026-09-29, 47 s).

    Чего репетиция не покрывает, объявлено: строк project_git_connections (создание подключения git через API проверяет токен у настоящего provider-а, а у кластера доказательства нет выхода в сеть — таблица читается проверяющим и rewrap, обычно с 0 строк; её конверт — тот же код, доказанный на обеих таблицах spec-ом выше), и provider секретов staging/production (здесь источник — локальный Secret, который читает SecretStore overlay; ExternalSecret и operator — настоящие). Это репетиция в одноразовом кластере, не ротация реальной среды: «ни разу не запускалась по-настоящему» остаётся правдой, пока кто-то не повернёт ключ в такой.

    Взаимодействие с restore

    Восстановление дампа в среде с другим мастер-ключом возвращает целую базу с бесполезными учётными данными. Дамп несёт упакованные DEK, а не ключ. Если вы восстановили бэкап production в тестовой среде и учётные данные не открываются, это не повреждение: это не тот ключ — и начиная с RN-563 вы можете подтвердить это сравнением, а не методом исключения, прочитав key_id любой строки и поставив его рядом со строкой chave mestra corrente в логе загрузки api. См. Restore.

    Именно поэтому мастер-ключ — часть плана восстановления: бэкап базы без соответствующего ключа не восстанавливает секреты пользователя.

    Когда что-то идёт не так

    симптом причина
    api стартует без предупреждения о ротации, но скрипт требует PREVIOUS переменная так и не дошла до пода; ESO пересинхронизирует только каждый refreshInterval (1h)
    falhas равно общему числу опубликованный PREVIOUS — не тот ключ, который упаковал хранилище
    já na chave atual равно общему числу без предыдущего запуска у обеих переменных одно значение — сервис в этом случае игнорирует PREVIOUS
    учётные данные перестают работать ПОСЛЕ шага 3 какая-то строка осталась позади; немедленно переопубликуйте PREVIOUS и запустите скрипт снова. Запрос прогресса шага 2 — то, что это предотвращает, и это проверка, которую надо запускать первой
    запрос ожидающих отвечает полным числом в базе, которую ещё никто не ротировал ожидаемо: key_id пишется начиная со следующей записи, поэтому у установки до RN-563 он NULL везде до первой ротации. NULL намеренно считается ожидающим — «не знаю, какой ключ» не означает «уже в текущем»
    rewrap говорит, что строка в ключе, который не является ни текущим, ни предыдущим строка пришла из другой среды — чаще всего это дамп, восстановленный между установками. См. Взаимодействие с restore ниже; key_id строки против key_id из лога загрузки api говорит с первого взгляда

    Инцидент стоимости

    Агенты тратят токены на каждом ходу, а агент, застрявший в цикле, тратит быстро. Этот раздел — для момента, когда почасовая стоимость взлетает и кто-то должен решить, что отрезать.

    Сигнал

    Алерт Custo por hora acima do limite срабатывает, когда прогнозируемые расходы превышают USD 5/час в любом проекте:

    max(sum by (project) (rate(brabo_llm_cost_micros_total[10m])) * 3600 / 1000000)

    Алерт — предупреждение, а не тормоз. Настоящий тормоз — доменные budgets, и они действуют по проекту/сессии, никогда глобально (RN-019).

    1. Какой проект, какой агент

    Grafana → панель Brabo · visão executiva → панель стоимости по проекту. Или прямо из базы, которая также даёт вам агента и модель:

    select s.project_id,
       tu.actor_id                             as agente,
       tu.model_name,
       count(*)                                as chamadas,
       sum(tu.cost_micros) / 1e6               as usd,
       round(avg(tu.latency_ms))               as latencia_media_ms
  from token_usage tu
  join sessions s on s.id = tu.session_id
 where tu.created_at > now() - interval '1 hour'
 group by 1, 2, 3
 order by usd desc
 limit 20;

    Два прочтения меняют действие:

    • Один агент, доминирующий в списке с множеством коротких вызовов, означает цикл: ToolLoop, повторяющий тот же инструмент без сходимости.
    • Мало вызовов и высокая стоимость означают дорогую модель на дешёвой работе — неверный binding, а не цикл.

    2. Проверьте бюджет

    select b.project_id, b.session_id,
       b.limit_micros / 1e6  as limite_usd,
       b.spent_micros / 1e6  as gasto_usd,
       round(100.0 * b.spent_micros / nullif(b.limit_micros, 0)) as pct,
       b.policy
  from budgets b
 order by pct desc nulls last;

    policy определяет поведение на пределе:

    • block — вызов отклоняется. Это значение по умолчанию и то, что вам нужно в production.
    • allow — предел становится простой записью; расходы продолжаются. Проект в allow, тратящий много, не останавливается сам. Проверьте это прежде всего: это самая частая причина «бюджет не удержал».

    3. Отрежьте расходы

    В порядке обратимости, от самого мягкого к самому радикальному.

    a) Выведите агентов из автоматической автономии. Они перестают действовать сами и снова требуют одобрения на каждое действие, не теряя контекста:

    update agent_autonomy
   set mode = 'require_approval', updated_at = now()
 where project_id = '<projeto>'
   and mode = 'auto_approve';

    agent_autonomy.mode — это enum permission_policy (auto_approve | require_approval | deny) — значения manual нет, и предыдущая версия этого шага использовала его и сразу падала. and mode = 'auto_approve' намеренный: без него update превратил бы каждую строку deny проекта в require_approval, ослабив ровно то, что кто-то закрыл. Строки "*" (автоматический режим, RN-153) покрываются тем же update.

    Чего этот шаг не отрезает: шаблон в allow в permissions.json проекта по-прежнему автоматически одобряет совпадающее — decide() читает файл после agent_autonomy, и файл может поднять решение обратно до auto_approve (apps/api/src/domain/actions/decide.ts, decide). Если расходы идут от команд, которые файл разрешает, переходите к (c).

    SQL-блоки этого раздела выполняются против мигрированной схемы apps/api/test/runbook/sql-do-incidente-de-custo.spec.ts, который также проверяет, что (a) меняет auto_approve и оставляет deny в покое — недопустимое значение или переименованный столбец здесь проваливает набор тестов api, а не инцидент.

    b) Смените binding модели на локальную. Ollama стоит ноль; качество падает, расходы останавливаются сразу:

    -- veja o binding vigente e o escopo que o resolve
select scope, scope_id, model_id from model_bindings where scope_id = '<projeto>';

    Затем направьте binding проекта на модель local через экран настроек (побеждает наиболее конкретная область: сессия > агент > проект > workspace — RN-020).

    c) Снизьте предел и убедитесь, что это block. Заставляет сам домен отклонять следующие вызовы:

    update budgets
   set policy = 'block',
       limit_micros = least(limit_micros, spent_micros + 1000000)  -- +1 USD
 where project_id = '<projeto>';

    d) Закройте сессии проекта. Последнее средство: прерывает работу в процессе. Используйте обычный переход (closing), никогда kill пода — убийство пода не закрывает сессию, а лишь создаёт сироту (см. Rollout engine).

    4. После

    • У Psicólogo уже есть улики. Если причиной был цикл агента, его анализ указывает на целевого агента, и Anamnese может предложить patch инструкции. Исправление инструкции — то, что не даёт этому повториться; возня с бюджетом лишь покупает время.
    • Проверьте, что алерт дошёл. Правила живут в Grafana, а не в Prometheus: если Grafana была недоступна, предупреждения не было, и тишина не означала здоровья.

    Чего этот раздел не исправляет

    Уже понесённые расходы. Metering — это запись, а не возврат: token_usage считает потраченное, и ничто здесь не возвращает деньги от provider-а. Единственная настоящая профилактика — policy = 'block' с разумным пределом до инцидента.

    Наблюдаемость

    Как отслеживать сессию, находить стоимость и диагностировать, когда данных нет. Решения — в ADR 0026.

    Локальная наблюдаемость, без кластера

    Всё ниже этого подраздела предполагает запущенный кластер. Для метрик и логов без подъёма Kubernetes есть overlay Compose (ADR 0070):

    pnpm dev:obs     # sobe a stack de dev + Prometheus, Loki, Alloy e Grafana
pnpm obs:down    # derruba só os quatro, deixando os apps de pé

    Команда заканчивается проверкой того, что поднялось, — если в каждой строке ok, в панели есть данные; если она жалуется, она говорит, какой части не хватило.

    Проверка: эта финальная проверка — scripts/dev/observabilidade-pronta.mjs, и это самопроверка, а не доказательство — она выполняется только когда кто-то поднимает overlay, и у неё нет ни spec, ни workflow. Изменение, ломающее overlay, проявится в следующий раз, когда кто-то запустит pnpm dev:obs.

    инструмент адрес для чего
    Grafana http://localhost:3001 панели и логи, без входа
    Logs http://localhost:3001/d/brabo-logs по одному сервису или все три вместе
    Prometheus http://localhost:9090 проверить цель и сырые ряды
    Loki http://localhost:3100 прямой запрос (обычный путь — Grafana)

    Панели — ТЕ ЖЕ, что в кластере: Compose монтирует deploy/k8s/observability/dashboards/ напрямую, и UID источников данных (brabo-prometheus, brabo-loki) те же. Новая панель работает в обеих средах без копирования.

    Чего этот overlay не делает: трассировки. Без OpenTelemetry Collector посередине нет Tempo, и это решение, а не недосмотр (ADR 0026, решение 9). trace_id по-прежнему попадает в лог, и этого достаточно, чтобы сопоставить api и engine вручную.

    Три вещи, которые сбивают людей с толку и которые стоит знать, прежде чем открывать issue:

    1. Пустая панель стоимости/токенов ожидаема на новой базе. Эти метрики имеют метки (project, provider), а в prom-client метрика с метками не существует до первого наблюдения. Один вызов LLM — и ряд появляется.
    2. В Loki идут только api, engine и web. Postgres и Ollama исключены из-за шума; сам стек наблюдаемости исключён, потому что в том же проекте Compose он поглощал бы собственный лог в цикле.
    3. Уровень OUTRO — это строка продолжения дерева pino-pretty, у которой нет собственного уровня. Это не потерянный лог.

    Где что находится

    инструмент локальный адрес для чего
    Grafana http://localhost:3001 панели, трассы, логи, алерты
    Prometheus kubectl -n monitoring port-forward svc/prometheus-server 9090:80 проверить цель и сырые ряды
    Tempo источник данных Grafana трассы
    Loki источник данных Grafana логи

    Две панели в папке Brabo: visão executiva (стоимость/час и токены/мин по проекту, активные сессии, решения по действиям) и visão operacional (очередь Oban по состоянию, задержка p50/p95 LLM по provider-у, заблокированные задачи, сессии по реплике).

    Отслеживание сессии от корня до вызова инструмента

    1. Возьмите trace_id сессии. Это среднее поле traceparent, хранящегося в sessions.trace_parent:

      # 00-<trace_id>-<span_id>-01
curl -sS -H "Authorization: Bearer $TOKEN" \
  http://localhost:3000/projects/$PROJ/sessions/$SESS | jq -r .traceParent

    2. В Grafana → Explore → источник данных Tempo → вкладка TraceQL вставьте trace_id. Дерево возвращается с session.create (api) в корне и под ним agent.turn → tool.call / llm.turn / gate.scanner (engine).

    3. Из span-а кнопка Logs for this span переходит к строкам Loki с этим trace_id. Обратный путь — от строки лога к трассе — ссылка TraceID, появляющаяся в деталях строки.

    4. Стоимость этой сессии: панель visão executiva фильтрует по проекту. Для точного значения по сессии источник — база (token_usage.cost_micros), а не метрика — метрика намеренно агрегирована по проекту и provider-у, чтобы не создавать ряд на каждую сессию.

    Когда в Tempo нет трассы

    Название этого раздела изменилось вместе с поведением (ADR 0035), и различение — первый шаг диагностики: span создаётся всегда, в любой среде. OTEL_EXPORTER_OTLP_ENDPOINT управляет ЭКСПОРТОМ. Поэтому «не вижу трассы в Grafana» и «трассы нет» — это разные проблемы.

    Прежде всего посмотрите, на чьей стороне сбой, — лог отвечает сам:

    kubectl -n brabo logs -l app.kubernetes.io/name=api --tail=20 | grep -o '"trace_id":"[^"]*"' | head
    • В логе есть trace_id, в Tempo трассы нет → проблема в экспорте: следуйте пунктам 1–4 ниже.
    • В логе нет trace_id → проблема в контексте, и это реже: либо startTracing() api не выполнился (см. apps/api/src/tracing-boot.ts — он должен быть первым import в main.ts), либо Engine.Telemetry.Otel.setup/0 не был вызван до дерева супервизии.

    По порядку, от наиболее к наименее вероятному:

    1. Переменная не задана. Без OTEL_EXPORTER_OTLP_ENDPOINT span создаётся и отбрасывается в конце, поэтому trace_id в логе есть, а в Tempo ничего. В разработке это ожидаемо (без collector); в кластере это дефект.

    kubectl -n brabo exec deploy/api -- printenv OTEL_EXPORTER_OTLP_ENDPOINT
kubectl -n brabo exec deploy/engine -- printenv OTEL_EXPORTER_OTLP_ENDPOINT

    2. NetworkPolicy блокирует. Это самый тихий сбой из всех: span-ы создаются, отправка падает, а всё остальное остаётся зелёным.

    kubectl -n brabo get networkpolicy allow-otlp-egress
kubectl -n brabo logs -l app.kubernetes.io/name=engine --tail=50 | grep -i "error exporting"

    3. Неверный протокол. Экспортёр Elixir говорит на HTTP/protobuf (4318), а не gRPC. Направление его на 4317 даёт socket_closed_remotely в каждом пакете.

    4. Collector ничего не получает.

    kubectl -n monitoring logs deploy/otel-collector-opentelemetry-collector --tail=30

    Когда панель пуста

    Почти всегда — имя метрики. Имена упоминаются строкой в трёх местах, которые друг друга не видят: панели, правила алертов и этот runbook. Сверьте с тем, что сервис реально отдаёт:

    curl -sS http://localhost:3000/metrics | grep '^brabo_' | cut -d'{' -f1 | sort -u
kubectl -n brabo exec deploy/engine -- wget -qO- http://127.0.0.1:4000/metrics | grep -E '^(brabo|oban)_'

    А если сервис её отдаёт, но в Prometheus её нет, проблема в сборе:

    kubectl -n monitoring port-forward svc/prometheus-server 9090:80
# depois: http://localhost:9090/targets — os jobs são `brabo-api` e `brabo-engine`

    Когда в Loki нет логов

    Alloy — это DaemonSet, и он читает /var/log/pods узла, фильтруя по пространству имён brabo.

    kubectl -n monitoring logs -l app.kubernetes.io/name=alloy --tail=30 | grep -i error

    Предупреждения tailer stopped ... pods not found нормальны после rollout — Alloy продолжает гнаться за подами, которые уже удалены.

    Приложения не могут говорить с Loki напрямую, и это намеренно: allow-otlp-egress открывает только 4317/4318. Чтобы запросить извне:

    kubectl -n monitoring port-forward svc/loki 3100:3100
curl -sS -G http://localhost:3100/loki/api/v1/query_range \
  --data-urlencode '{app="api"} | json | trace_id != ""' --data 'limit=5'

    Алерты

    Провизионированы и видны в Alerting → Alert rules (папка Brabo), из deploy/k8s/observability/alerts/brabo-alerts.yaml. Правила несут заголовки на португальском — именно их вы ищете в Grafana:

    алерт (заголовок в Grafana) серьёзность срабатывает через что исследовать
    Fila do Oban crescendo sem consumo critical 10 min ни одной реплики engine в Ready; пул Postgres исчерпан; worker застрял на job-е
    Sessão presa em closing warning 15 min drain не завершился, или переход в closed не удался
    Custo por hora acima do limite warning 5 min какой проект и какой агент; доменный бюджет остаётся жёстким контролем
    Backup do Postgres atrasado — последний хороший бэкап старше 26 h critical сразу CronJob не запустился, или запустился и упал — brabo_backup_last_status различает эти случаи; см. Restore. «Бэкапа никогда не было» (-1) его не вызывает
    Última execução do backup falhou warning сразу хороший вчерашний бэкап может ещё существовать, и именно поэтому этот алерт остаётся незамеченным днями; причина — в backup_runs.error_message

    Это правила Grafana, а не Prometheus (отклонение зафиксировано в ADR 0026): они перестают вычисляться, если Grafana падает. Нет ни Alertmanager, ни настроенного назначения уведомлений.

    Известные ограничения

    • Ни одна настоящая трасса агента не наблюдалась от начала до конца: проверка этого требует настроенного LLM (Ollama или ключ API). Механизм проверен генерацией span-ов прямо в трассу сессии.
    • Web не экспортирует собственные span-ы — он генерирует traceparent и отправляет его в заголовке, а api принимает его как родителя. Логи браузера идут в консоль, а не в Loki.
    • Короткое хранение: Tempo 24h, Loki 24h, Prometheus 2h. Это локальная среда.

    Реестр gate-ов

    Gate-ы потока объявляются в docs/gates.yml (ADR 0054). Две операционные вещи стоит знать.

    Файл путешествует внутри образа. docker/api/Dockerfile.prod копирует его на обоих этапах, так же как делает с миграциями, а .dockerignore явно включает его обратно — весь docs/ игнорируется, и это единственный файл оттуда, являющийся данными production, а не документацией. В runtime он лежит в /app/docs/gates.yml; загрузчик поднимается от __dirname, пока не найдёт его, без переменной окружения.

    Нечитаемый файл не роняет api. Загрузка ленивая: тот, кто вызывает GET /internal/gates, получает ошибку, а остальной процесс продолжает работу. Если маршрут возвращает ошибку, проверьте, что файл попал в образ:

    kubectl -n brabo exec deploy/api -- cat /app/docs/gates.yml | head -5

    Пустой или отсутствующий означает, что образ собран без него — вероятно, тронутый .dockerignore или build из контекста без docs/.

    Реестр путешествует; то, на что он указывает, — нет. Gate teste/ci называет файлы под apps/api/test/, scripts/ci/ и .github/, и ни одного из них нет в образе. Пока это не было разделено, загрузчик требовал эти файлы в runtime, и маршрут отвечал 500 в каждой установке — измерено на v6.1.0 как двенадцать 5xx примерно за 55 минут, с RegistroDeGatesInvalido, перечисляющим одиннадцать целей как «não existe». Воспроизведите старый сбой так:

    docker exec <api> node -e "require('/app/infrastructure/gates/gate-registry.loader').carregarRegistro()"

    В исправленном образе это ничего не печатает. Если выбрасывает RegistroDeGatesInvalido, называя .spec.ts или workflow, образ до исправления (RN-070); если выбрасывает, называя содержимое gate (gate block без script, gate active без улик), неверен сам реестр, и исправлять нужно в репозитории.

    Экран этот сбой не показывает: PrGateTimeline откатывается на полный конвейер, когда GET /gates падает (RN-084), так что единственным сигналом был лог api. docker/smoke.sh теперь вызывает оба маршрута, обслуживающих реестр, против образа production: GET /gates с bearer пользователя и GET /internal/gates с service token. Одна функция проверяет тело обоих и проваливается на 500, на пустом списке и на реестре без merge-protegida. Именно это не даёт сбою вернуться молча. Токен приходит в curl через stdin (--config -), никогда через argv, поэтому не появляется ни в ps, ни в логе CI.

    Чтобы увидеть реестр так, как его видит api, уже проверенным:

    kubectl -n brabo exec deploy/api -- \
  curl -sH "x-brabo-service-token: $BRABO_SERVICE_TOKEN" localhost:3000/internal/gates

    Измерение прохождения НЕ запускается в production: это pnpm --filter api validacao:gates, из репозитория, против базы. См. docs/explanation/gates.md.

    Среда инференса

    Когда агент отвечает пусто, обрезанно, крайне медленно или «забывает» собственные инструкции, проблема почти никогда не в доменном коде — она здесь. Первые пять причин были найдены в девяти последовательных запусках демо gate-ов и зафиксированы в ADR 0020; все переменные вынесены в docker-compose.yml.

    переменная симптом, когда она неверна
    GPU сервис ollama без зарезервированного устройства оставляет GPU простаивать и работает на 100% на CPU: промпт из ~7.000 токенов занимает ~50s только на приём. Override опционален (docker-compose.gpu.yml, pnpm dev:gpu), вынесен из основного compose, потому что без nvidia-container-toolkit на хосте резервирование не даёт сервису стартовать
    OLLAMA_CONTEXT_LENGTH значение по умолчанию 4096 молча обрезает промпт, рассчитанный на 128k. Агент теряет собственные инструкции и начинает имитировать схему инструментов — то, что остаётся в конце контекста
    OLLAMA_MAX_LOADED_MODELS при высоком OLLAMA_KEEP_ALIVE модели накапливаются: 15,2 GB резидентных весов на машине с 15 GB, и агент отвечает пусто из-за нехватки памяти
    OLLAMA_REQUEST_TIMEOUT_MS слишком короткий timeout для большой модели на длинном промпте
    OLLAMA_MODE (bootstrap dev, RN-461, ADR 0114) застряла в host после того, как нативный Ollama на машине разработчика был удалён или остановлен, — каждый ход локальной LLM падает с ECONNREFUSED против http://host.docker.internal:<porta>, а сервис ollama из compose так и не поднимается, чтобы подстраховать (он стоит за profiles: ["local-llm"], и именно эта переменная держит этот profile выключенным). Исправление: Docker › Reconfigurar Ollama в pnpm bootstrap, который очищает OLLAMA_MODE/OLLAMA_HOST в .env и заставляет обнаружение снова спросить при следующем Create/Reset total
    START_OUTBOX_DRAIN / START_ANAMNESE Psicólogo и Anamnese потребляют ходы LLM параллельно с агентами выполнения и рвут соединение dev посреди цикла
    TOOL_LOOP_MAX_ITERATIONS* слишком НИЗКИЙ предел — и агент останавливается, ничего не сдав, с iteration limit reached и источником model, что обманчиво, потому что модель не вынесла никакого неверного суждения и даже не дошла до суждения. Предел — по ТИПУ (RN-085): 8 для разговорных агентов, 60 для dev agent и QA. Прежде чем поднимать его, проверьте, ЕСТЬ ли у агента token_budget_micros; без него предел — единственная существующая защита от расходов
    TERMINAL_OUTPUT_MAX_BYTES слишком высокое значение возвращает режим сбоя, ради предотвращения которого предел существует: вывод каждой команды остаётся в истории цикла и путешествует в КАЖДОМ следующем ходе. Дело не в окне контекста: самый большой успешный вызов в запуске, впервые это выявившем, имел всего 28.993 входных токена (RN-074)
    API_JSON_BODY_LIMIT (api) / TRANSPORT_MAX_BODY_BYTES (engine) у 413 request entity too large в gate-е QA/SecOps причина была в самой api Brabo, а не в provider-е — у Express никогда не был настроен предел тела, и действовало значение по умолчанию 100 KB против 8 MB, которые принимает Phoenix на самом тяжёлом участке engine→api (POST .../llm-turn, который пересылает всю историю на каждой итерации). API_JSON_BODY_LIMIT (по умолчанию 10 MB) закрывает этот конец; TRANSPORT_MAX_BODY_BYTES (по умолчанию 8 MiB) — предел, который компактизация контекста engine соблюдает ПОВЕРХ окна модели, чтобы сработать до того, как тело превысит лимит HTTP (RN-412, ADR 0098)

    Осторожно — защита не очищает очередь. START_ANAMNESE=false блокирует новые постановки в очередь, но не старые. Уже бывало 20 AnamneseWorker-ов, накопившихся в executing от предыдущих запусков, которые выполняются при следующей загрузке независимо от защиты. Очередь нужно вычистить, а не только выключить защиту.

    Включение Anamnese или Psicólogo: две переменные, а не одна. Оба были поставлены на паузу 2026-08-10 по продуктовому решению, а не из-за бага. Psicólogo по-прежнему на паузе; Anamnese была снова включена владельцем 2026-10-01 (RN-680) — ANAMNESE_ENABLED возвращается к значению по умолчанию true в коде и во всех трёх compose, а раунд без подходящего субъекта не делает вызова LLM и говорит почему в логе engine (sem_sujeito_elegivel). Снова поставить её на паузу — ANAMNESE_ENABLED=false. ANAMNESE_ENABLED / PSYCHOLOGIST_ENABLED — продуктовые флаги (может ли произойти НОВЫЙ раунд?); START_ANAMNESE — ключ загрузки (планируется ли вообще периодический tick?). Периодической Anamnese нужны оба в true; у Psicólogo нет ключа загрузки, потому что его автоматический триггер — закрытие сессии.

    До RN-540 два флага *_ENABLED не были отображены в сервисе engine ни одного из compose, а docker compose не передаёт окружение хоста — поэтому их задание в .env молча ничего не делало, в то время как три места в коде обещали, что пауза обратима. Теперь они отображены, со значением по умолчанию из самого кода (false в обоих файлах на тот момент; ANAMNESE_ENABLED — true начиная с RN-680). Compose установки (docker/docker-compose.install.yml) был третьим файлом и остался вне этого исправления; начиная с AT-202 он отображает те же флаги с теми же значениями по умолчанию, и scripts/ci/flags-do-engine-no-compose.spec.ts проверяет все три файла и проваливает build при следующем булевом флаге, который не будет отображён или получит значение по умолчанию, отличное от кода (START_OUTBOX_DRAIN и START_ANAMNESE намеренно false в compose production, и spec объявляет это расхождение по имени). Compose установки нёс тот же false — скопированный из production вместе с мотивом production («он существует для проверки образов»), — а начиная с AT-219 повторяет true из кода. Это был дефект установки, а не выбор ради экономии: START_OUTBOX_DRAIN — единственное, что дренирует outbox api в engine, поэтому в установке на одной машине закрытая сессия никогда не останавливала свои процессы, а dev agent, ждущий одобрения, gate-а или контейнера, никогда не будился. Ни один из ключей не тратит токены при выключенных продуктовых флагах: при ANAMNESE_ENABLED=false kickoff/0 Anamnese не планирует ни одного job-а, а drain ставит в очередь Psicólogo только при PSYCHOLOGIST_ENABLED=true. В установке Anamnese, таким образом, включена или выключена только ANAMNESE_ENABLED (по умолчанию true начиная с RN-680). В Kubernetes исправлять было нечего — Deployment/ConfigMap ничего не перехватывает, а brabo-config никогда не нёс этих переменных. Оба флага читаются при загрузке: измените их и выполните docker compose up -d engine.

    Семантический gate на маленькой модели

    QA — роль, которая хуже всего укладывается в локальную 7B: суждение меняется между запусками, что делает демо исполняемым критерием приёмки, а не регрессионным тестом. Чтобы сделать его надёжным, направьте DEMO_QA_MODEL на модель API — binding по агенту (область agent, побеждающая project) существует ровно для этого.

    Сама машина gate-ов не меняется: неизменный порядок, возврат в ту же ветку, предел исправлений, вердикты как артефакт и терминальный awaiting_user — всё это проверено ExUnit (RN-014, RN-015).

    Установка

    curl -fsSLO https://github.com/daneiel/brabo/releases/latest/download/install.sh && bash install.sh

    Скачайте файл, затем запустите его через bash. Две более короткие формы, которые кажутся эквивалентными, таковыми не являются, и скрипт отклоняет обе по имени, до того как что-либо скачать, печатая строку выше:

    • Никогда curl … | sh. Причина механическая, а не стилистическая: когда скрипт приходит через pipe, stdin процесса является загрузкой, поэтому любой read читает байты самого скрипта или упирается в EOF. Установщик, который не может задавать вопросы, должен был бы сам выбирать расположение папок на чужой машине (RN-526).
    • И не sh -c "$(curl …)" — это была задокументированная форма до AT-083, и она никогда не работала. Скрипт проверяет собственный хеш по подписанному манифесту, а под X -c "…" нет файла, от которого считать хеш: $0 — имя оболочки. С dash в роли sh (Debian, Ubuntu) он умирал ещё раньше, на set -o pipefail. Ключа для пропуска этой самопроверки нет и не будет (ADR 0150) — исправление в том, чтобы существовал файл. Запуск под оболочкой, не являющейся bash, — тоже отдельный именованный отказ.

    Скрипт проверяет собственное происхождение, прежде чем что-либо делать, — подпись checksums.txt Release-а, а затем собственный хеш внутри этого проверенного манифеста. Сбой на любом шаге — именованный отказ, никогда не предупреждение.

    Ему нужен один из sha256sum (coreutils, Linux) или shasum -a 256 (идёт с macOS), чтобы сделать что-либо из этого, и он определяет, какой, до первой загрузки — а не посреди проверки. Отсутствие обоих — собственный отказ, называющий оба инструмента и говорящий, что ничего не было скачано; это отсутствующая зависимость операционной системы, и она намеренно не сформулирована как отказы по хешу ниже. Это два разных исхода, требующих разного — один исправляется установкой, другой остановкой, — и измерение AT-091 провело черту между ними: sha256sum: command not found на macOS проявлялось как «o cosign baixado NÃO bate com o hash pinado neste script. Isso não é um aviso: pare e investigue.», что одновременно блокировало каждую установку на macOS и учило читателя игнорировать эту фразу. --print-plan не нуждается ни в одном из инструментов и объявляет, какие скрипт принимает (conferir-hash).

    Обнаружение имеет предел 5s на вызов Docker, который оно делает (docker compose ls говорит с демоном, а медленный или остановленный демон за живым сокетом повесил бы всё до первого вопроса). Достижение предела — не ошибка: это тот же исход, что отсутствие Docker вовсе, а остальные сигналы всё равно читаются.

    Без TTY он сообщает и завершается с 0: печатает найденное и команду для запуска в терминале. Это намеренно, и это та же форма, что уже есть у consentir-base.mjs.

    Что он никогда не удаляет: вашу базу проектов и вашу папку зеркала. Именованные тома удаляются только с подтверждением, будучи перед этим перечислены по одному.

    Он поднимает стек из собственного compose (docker/docker-compose.install.yml), который берёт образы из переменных и ничего не собирает, — и он скачивает этот compose из Release (RN-570, ADR 0160). Четыре файла путешествуют с установщиком как assets brabo-install-*, в том же подписанном checksums.txt, который покрывает бинарник runner-а: compose, postgres/init.sql и ollama/pull-models.sh, которые он монтирует bind-mount-ом, и backup/test-restore-compose.sh, который запускает миграция. Сразу после проверки самого себя — до любого вопроса, до любой записи — скрипт скачивает все четыре и сверяет каждый хеш с этим манифестом. Три именованных отказа, все на нетронутой машине:

    сообщение начинается с означает сделайте
    «a Release não publica …» Release старше ADR 0160, или её шаг публикации упал посередине установите из checkout-а репозитория на этом теге или дождитесь следующего релиза
    «o manifesto assinado não cobre …» манифест существует, но в нём нет строки для этого asset-а то же, что выше, — Release неполон
    «… NÃO bate com o manifesto assinado» скачанный файл — не то, что описывает подписанный манифест остановитесь и обращайтесь с этим как с инцидентом; не пытайтесь обойти

    Проверенные копии записываются под docker/ в папке, из которой вы запустили скрипт, — той же папке, где .env, — только когда они впервые понадобятся. То, что там уже было (compose предыдущей версии, при обновлении), заменяется, никогда не читается, и скрипт называет то, что заменил; изнутри git-checkout-а на другом commit-е это оставляет git status грязным.

Для этих тегов запускайте установщик из checkout-а репозитория на устанавливаемом теге.

    На пути миграции доказательство восстановления (test-restore-compose.sh) получает .env установки через BRABO_ENV_FILE (передаётся в Compose как --env-file), потому что Compose ищет .env рядом с файлом compose — а не в каталоге, из которого вы запускаете. Если вы запускаете доказательство вручную против установки, сначала экспортируйте BRABO_ENV_FILE=/caminho/para/.env; путь, которого не существует, отклоняется, никогда не заменяется другим файлом. Неудавшееся доказательство по-прежнему ничего не удаляет (RN-530).

    Два источника:

    install.sh                  # --source=ghcr (default): por digest, assinatura verificada
install.sh --source=local   # buildx bake; exige árvore limpa numa tag

    Секреты генерируются один раз и сохраняются в .env с режимом 600 — файл создаётся пустым и запертым до получения содержимого, потому что окно, в котором секреты читаемы всеми, — ровно то, чего у этого файла не может быть.

    Шага migrate нет, и не должно быть: compose связывает цепочкой api → migrate-api с service_completed_successfully, поэтому up --wait ждёт миграций. Второе место, упорядочивающее миграции, было бы вторым источником той же истины.

    После подъёма стека он спрашивает, прежде чем утверждать: /health у api и engine, и только затем говорит, что установил.

    Он устанавливает локального агента — бинарник проверяется по подписанному манифесту и кладётся через install -m 0755, поэтому ручного chmod нет (RN-531) — и спрашивает ОДНУ базу, записывая её с обеих сторон: BRABO_PROJECTS_BASE в .env и base в runner.json runner-а. Release без бинарника для этой платформы не прерывает установку: он говорит об этом и указывает на npm install -g @brabo/runner.

    Поверх существующей установки он мигрирует или останавливается — up на томах другой версии — это ущерб, который не предупреждает. Порядок: бэкап → ДОКАЗАТЬ, что он восстанавливается → спросить → удалить → установить → восстановить, и доказательство посередине — то, что даёт установщику право удалять (RN-530).

    Broker контейнеров в установке

    Проекты в режимах Container и Pasta montada работают внутри контейнера, и поднимает этот контейнер broker (ADR 0144). Без него ни один из режимов никогда не выполняется: container_start заканчивается failed с BrokerIndisponivelError, а dev agents остаются в dev.blocked_by_container. Режим Runner от него не зависит — там локальный агент использует Docker вашей машины.

    Начиная с ADR 0162 broker — пятый опубликованный образ (ghcr.io/daneiel/brabo-broker, по digest, подписанный, как и остальные четыре), и в compose установки есть сервис — выключенный по умолчанию, под тем же profile container-broker, что и compose проверки. Установщик спрашивает («Ligar o broker de container? [s/N]»), сразу после базы проектов, и говорит текстом, что даёт его включение: broker получает сокет Docker этой машины, и тот, кто командует broker-ом, командует вашим Docker. Сдерживают его пять слоёв ADR 0130: ни одного опубликованного порта, сеть (internal: true, без интернета), до которой дотягивается только api, service token, пять операций над контейнером ОДНОГО проекта и spec, которую broker составляет из того, что решил Arquiteto, — нет запроса, который включил бы privileged, сеть хоста или свободный -v.

    ответ что происходит
    s / sim он измеряет группу сокета изнутри контейнера (собственный образ broker-а, без сети, только чтение, сокет подключён через --mount, чтобы отсутствующий сокет был ошибкой, а не пустой папкой, созданной на вашем хосте), вычисляет, где Docker хранит том управляемой папки, и записывает COMPOSE_PROFILES=container-broker, BROKER_URL=http://broker:8090, DOCKER_GID и PROJECT_WORKSPACES_HOST_ROOT в .env — все четыре вместе
    Enter, n, что угодно другое выключен. .env не получает ни одной из четырёх строк, и итоговая сводка говорит «Broker de container: DESLIGADO»
    без терминала выключен, и он об этом говорит — ни один вопрос не задаётся там, где никто не может ответить

    COMPOSE_PROFILES в --env-file — то, что заставляет up -d --wait поднять broker без каких-либо флагов в командной строке, — измерено на Compose v5.5.1. Переменная образа, BRABO_BROKER_IMAGE, записывается независимо от того, включаете вы его или нет: Compose интерполирует весь файл до фильтрации по profile, поэтому обязательная переменная в выключенном сервисе всё равно отклоняет файл.

    Включение позже (та же папка, что .env):

#    sem rede; é este o número de que o compose precisa
docker run --rm --network none --read-only --entrypoint stat \
  --mount type=bind,source=/var/run/docker.sock,target=/var/run/docker.sock \
  "$(grep '^BRABO_BROKER_IMAGE=' .env | cut -d= -f2)" -c '%F %g' /var/run/docker.sock
# esperado: socket <gid>

# 2. onde o Docker guarda o volume da pasta gerenciada
docker volume inspect --format '{{.Mountpoint}}' brabo_project_workspaces

#    COMPOSE_PROFILES=container-broker
#    BROKER_URL=http://broker:8090
#    DOCKER_GID=<gid do passo 1>
#    PROJECT_WORKSPACES_HOST_ROOT=<caminho do passo 2>

# 4. recrie — a api também, para ela pegar o BROKER_URL
docker compose -f docker/docker-compose.install.yml --env-file .env up -d --wait

# 5. pergunte antes de afirmar
docker compose -f docker/docker-compose.install.yml --env-file .env exec -T api \
  node -e "fetch('http://broker:8090/health').then(r=>r.text()).then(console.log)"
# esperado: {"status":"ok","servico":"broker"}

    Выключение: удалите четыре строки из .env, затем удалите контейнер broker-а и пересоздайте api без BROKER_URL:

    docker compose -f docker/docker-compose.install.yml --env-file .env \
  --profile container-broker rm -sf broker
docker compose -f docker/docker-compose.install.yml --env-file .env up -d --wait

    up --remove-orphans первый шаг не выполняет — измерено: сервис под выключенным profile остаётся определённым в файле, поэтому его контейнер не сирота и продолжает работать. Ничего в ваших проектах не удаляется; проекты Container и Pasta montada перестают выполняться, и экран проекта перестаёт их предлагать (ADR 0161).

    Проверка: включение при установке доказано — вопрос и его отказы через scripts/dev/install-broker.spec.ts в каждом PR, а весь путь через .github/workflows/install-e2e.yml на каждом финальном теге, который отвечает да и требует включённого broker-а, api, до него дотягивающейся, и COMPOSE_PROFILES и BROKER_URL, записанных в .env. Включение позже пятью командами выше и выключение не имеют проверки: ничто их не запускает, а оговорка про up --remove-orphans была измерена один раз вручную.

    Локальные модели в установке

    Сразу после broker-а install.sh спрашивает Ligar os modelos locais? [s/N] (RN-691). Он заранее называет цену — диск под образ Ollama и модели, которые ollama-model-loader скачивает при старте, RAM, пока модель загружена, — и что теряется без них: проверка семантических дубликатов историй и правил пропускается, и у агентов нет локальной модели. Включает их только набранное «s»; без терминала они остаются выключенными.

    Проверка: вопрос, измерение порта и строки .env доказываются scripts/dev/install-llm.spec.ts в каждом PR. E2E установки отвечает нет (скачивание моделей стоило бы ГБ на тег), поэтому подъём с profile llm не имеет сквозной проверки.

    Проверка опубликованного артефакта

    Каждый финальный тег подписывает то, что публикует, через cosign keyless — подписывающая идентичность — сам workflow, и ни одного ключа на хранении нигде нет (ADR 0149, RN-524). Вот как проверяете вы, вне CI.

    Обеим командам нужны оба флага --certificate-*. Это не опциональное украшение: без них cosign принял бы действительную подпись от кого угодно, а это ровно тот сбой, ради предотвращения которого существует весь этот механизм.

    Образ, по digest

    # O digest vem do .release/images.json, que é um asset da Release
# — nunca de uma tag, que é um ponteiro móvel.
DIGEST=$(gh release download vX.Y.Z --pattern images.json --output - \
  | jq -r '.imagens[] | select(.alvo == "api") | .digest')

cosign verify \
  --certificate-identity-regexp '^https://github.com/daneiel/brabo/\.github/workflows/release\.yml@' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "ghcr.io/daneiel/brabo-api@${DIGEST}"

    Бинарники runner-а

    Подписанный checksums.txt покрывает четыре цели (у Mac Intel нет бинарника начиная с ADR 0174 — он использует npm install -g @brabo/runner), поэтому у проверки два шага: подпись манифеста, затем бинарник против манифеста.

    gh release download vX.Y.Z --pattern 'checksums.txt*' --pattern 'brabo-runner-*'

cosign verify-blob \
  --bundle checksums.txt.bundle \
  --certificate-identity-regexp '^https://github.com/daneiel/brabo/\.github/workflows/build-runner-binaries\.yml@' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  checksums.txt

# Só depois de o manifesto ser provado autêntico é que conferir o binário quer
# dizer alguma coisa — um checksums.txt que ninguém verificou é um arquivo que o
# atacante também consegue escrever.
sha256sum -c checksums.txt --ignore-missing

    Когда проверка не проходит

    Не устанавливайте. У подписи, которая не проверяется, ровно два прочтения — артефакт не тот, что опубликовал конвейер, или конвейер его не публиковал, — и ни одно не является поводом продолжать. Проверьте, совпадает ли регулярное выражение идентичности с workflow, который действительно опубликовал этот тег ( повторная публикация через workflow_dispatch подписывается той же идентичностью), и затем обращайтесь с этим как с инцидентом, а не как с шумом.

    Чего это НЕ покрывает: подписи кода операционной системы для бинарников runner-а — нотаризации macOS и Authenticode Windows. Они требуют платной идентичности подписи и являются отдельным пунктом backlog-а; система по-прежнему будет предупреждать при первом запуске.

    Письменное предложение исходного кода, внутри каждого опубликованного артефакта

    Подпись отвечает на вопрос «это то, что опубликовал конвейер?». Второй вопрос путешествует с тем же образом и имеет другой ответ: где исходный код GPL-программ внутри него?

    Образ engine встраивает git, busybox, libgcc/libstdc++ и ещё 18 пакетов apk под GPL, плюс четыре сканера, которые engine вызывает через exec. Их запуск как отдельных процессов не заражает Brabo, который остаётся MIT, — но распространение образа требует, чтобы получатель мог получить соответствующий исходный код. Начиная с ADR 0119 это распространение происходит на каждом финальном теге.

    Письменное предложение — это THIRD_PARTY_NOTICES.md, и оно лежит внутри образа, потому что у того, кто запускает docker pull, нет репозитория:

    docker run --rm --entrypoint sh ghcr.io/daneiel/brabo-engine:vX.Y.Z \
  -c 'cat /usr/share/doc/brabo/THIRD_PARTY_NOTICES.md'

    Он называет каждый компонент, точную версию и лицензию, что позволяет любому добраться до upstream-релиза каждого.

    Начиная с AT-120 тот же файл, по тому же пути и в той же форме (владелец root, 0644, скопирован до USER), лежит внутри каждого опубликованного образа — brabo-api, brabo-web, brabo-broker и brabo-backup помимо brabo-engine — и рядом с бинарниками runner-а как asset THIRD_PARTY_NOTICES.md Release-а, покрытый тем же подписанным checksums.txt (RN-524). Таково было решение мейнтейнера, и оно консервативное: ни один артефакт не объявлен освобождённым. Замените brabo-engine на любой из остальных четырёх в команде выше. До AT-120 эта команда падала с «Permission denied» на образе engine: BuildKit применяет COPY --chmod=0644 и к каталогу, который создаёт COPY, поэтому у /usr/share/doc/brabo не было бита исполнения, и не-root пользователь образа не мог через него пройти. Каждый Dockerfile теперь заранее создаёт каталог 0755. Для runner-а:

    gh release download vX.Y.Z --repo daneiel/brabo \
  --pattern THIRD_PARTY_NOTICES.md --pattern checksums.txt
sha256sum -c --ignore-missing checksums.txt

    Если этого файла нет в артефакте, артефакт не должен распространяться. scripts/ci/oferta-de-fonte-na-imagem.spec.ts не даёт случайно удалить каждый COPY и asset Release-а, а шаг A oferta de fonte está dentro das cinco imagens в ci.yml считывает файл обратно из каждого собираемого образа и сравнивает его с checkout-ом — но только настоящий тег доказывает опубликованный артефакт.

    Файл также фиксирует то, что не решено: вынос сканеров в собственный sidecar, освобождающий образ engine от copyleft, остаётся открытым как выбор архитектуры, а не соответствия.

    Подъём стороннего образа

    Каждый сторонний образ в docker/ и deploy/k8s/ зафиксирован по digest, с тегом, откуда он пришёл, записанным внутри ссылки, перед digest (ADR 0159, ADR 0178). Workflows в .github/workflows/ не хранят литерал образа: их services: читают ссылку из compose dev через imagens-do-compose.yml (ADR 0197), поэтому обновление compose обновляет и CI:

    image: neo4j:5.26-community@sha256:d9cfe82983d27f5a75b3aaae8f316d04f9a698a3b7f6103a508f7caf8362f255

    Dockerfile принимает ту же форму в строке FROM — никогда не комментарий в её конце: парсер Docker принимает # только в начале строки, а # в конце заставляет build упасть с «FROM requires either one or three arguments»:

    FROM alpine:3.24@sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6 AS runtime

    Это заморозка. Начиная с ADR 0197 экосистемы Dependabot docker-compose ( compose в docker/) и docker (строки FROM в docker/*/ и манифесты в deploy/k8s/) каждую неделю предлагают обновление, одним сгруппированным PR на экосистему, в dev. Ревью этого PR — шаги 1 и 4 этой процедуры. Два случая по-прежнему возвращаются сюда:

    • neo4j и ollama живут в compose И в deploy/k8s/base/, а две экосистемы никогда не делят PR. Когда registry переопубликует ТОТ ЖЕ тег с другим digest, оба PR проваливаются на lint («тот же inline-тег, два digest-а»); объедините оба обновления в один PR с шагом 3 ниже.
    • Два образа, которые не читает ни одна экосистема (ниже).

    Чтобы сдвинуть один вручную — скажем, neo4j с 5.26-community на 5.27-community:

    # 1. Confirme que a tag resolve para um ÍNDICE (uma manifest list). Se não,
#    o pin perde o multi-arch e o linux/arm64 para de funcionar.
docker manifest inspect neo4j:5.27-community | head -3
#    → "mediaType": "application/vnd.oci.image.index.v1+json"
#      (ou …distribution.manifest.list.v2+json)

# 2. Leia o digest do índice.
docker buildx imagetools inspect neo4j:5.27-community --format '{{.Manifest.Digest}}'

# 3. Escreva `neo4j:5.27-community@<digest>` EM TODO LUGAR onde a referência antiga aparece.
#    Não em .github/workflows/: os workflows leem pgvector e ollama do
#    compose de dev (ADR 0197), e o lint reprova um literal ali.
grep -rn 'neo4j:5.26-community@sha256' docker/ deploy/k8s/

# 4. O lint prova.
node scripts/ci/imagens-pinadas.ts

    Два образа обновляются этой же процедурой, вручную, что бы ни делал Dependabot: imageName CloudNativePG в deploy/k8s/overlays/local/db/cluster.yaml (ни одна экосистема не читает этот ключ) и образ случая QA golden-set, IMAGEM_DO_GOLDEN_SET_QA в apps/api/scripts/golden-set-qa-container.ts (константа TypeScript, читаемая golden-set-qa.yml).

    Шаг 3 — не опциональная бюрократия: проверка отклоняет один и тот же inline-тег, несущий два разных digest-а, потому что compose dev и кластер, утверждающие одну версию, при этом выполняя разные байты, — это то, как зелёный CI перестаёт что-либо значить. Между compose dev и CI больше нечего выравнивать: CI читает compose.

    Чтобы дать НОВОМУ workflow сторонний сервис, никогда не пишите ссылку в workflow: добавьте образ сервиса в docker/docker-compose.yml, строку в IMAGENS_DOS_WORKFLOWS в scripts/ci/imagens-do-compose.ts, соответствующий output в .github/workflows/imagens-do-compose.yml (его spec проваливается, если они расходятся), а в workflow — job imagens: с uses: ./.github/workflows/imagens-do-compose.yml плюс image: ${{ needs.imagens.outputs.<nome> }}.

    Добавление совместимого provider-а

    Относится к любому provider-у, говорящему на диалекте /chat/completions OpenAI, — а это практически каждый хаб и каждый управляемый сервис инференса. База уже существует (ADR 0041); то, что вы пишете, — конфигурация, а не разбор.

    1. Прочитайте официальную документацию до первой строки

    Четыре вещи должны прийти из документации provider-а, а не из догадки: baseUrl, заголовок auth, формат usage в потоке и особенности потоковой передачи. Запишите просмотренный URL и дату в начале файла конфигурации — это единственный способ узнать через месяцы, не устарела ли конфигурация.

    То, что расходится со стандартом OpenAI, становится флагом в базе, никогда не разбросанным if. Если расхождение не укладывается в существующий флаг, добавьте его — и только потому, что этому настоящему provider-у он нужен.

    2. Напишите конфигурацию

    // apps/api/src/infrastructure/llm/<provider>-provider.ts
export function meuProviderConfig(baseUrl = BASE_URL): OpenAICompatibleConfig {
  return {
    name: 'meu-provider',
    baseUrl,
    capabilities: { streaming: true, toolCalling: true, listModels: true },
    authHeaders: (apiKey) => ({ Authorization: `Bearer ${apiKey ?? ''}` }),
    flags: { streamOptionsIncludeUsage: true, maxTokensField: 'max_tokens' },
    // Só se o catálogo dele devolve mais que `{ data: [{ id }] }`:
    // parseCatalogo: (corpo) => ...,
    // Só se for um HUB (informa quem de fato serviu a requisição):
    // extrairUpstreamProvider: (frame) => ...,

}

    Экспортируйте функцию конфигурации, а не только класс: именно на неё набор контрактных тестов направляет поддельный сервер. Копия конфигурации, написанная внутри теста, прошла бы зелёной, даже если бы production-конфигурация расходилась.

Они не могут жить вместе: packages/shared — на 100% типы: значение, экспортированное оттуда, ломает образ production api при загрузке с ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING, и apps/api/test/packages-shared-so-tipos.spec.ts проваливается до того, как дойдёт туда.     Набранная вручную цена приходит с manual_pricing: true. Это защищает строку от синхронизации цен: для provider-а, который не отдаёт цену в каталоге, ручное число — единственное существующее.

    Если provider отдаёт GET /models, не заполняйте весь каталог — пусть синхронизация его обнаружит. Она записывает модели выключенными, а владелец включает нужное через экран курирования (RN-043).

    Если каталог provider-а публикует модальность (принимает изображение, генерирует изображение) или reasoning, выдавайте их в его parseCatalogo — и только когда это говорит официальная документация. Поле, которое provider не объявляет, остаётся опущенным, никогда не false: undefined сохраняет то, что уже было записано, а false стёр бы данные, курированные вручную (RN-056).

    Процедуры и как проверяется каждая из них

    Каждая процедура эксплуатации на этой странице, с файлом, который её доказывает, и тем, что запускает это доказательство. Разделы диагностики (что делать, когда что-то выглядит не так) и разделы среды разработки здесь не перечислены: это способы найти причину, а не процедуры, которые могут пройти или провалиться.

    • verification называет spec, скрипт, workflow или цель make, которые доказывают процедуру, или начинается с None и говорит об этом. Частичное доказательство называет, что оно покрывает и чего не покрывает.
    • schedule говорит, что запускает её без того, чтобы кто-то помнил: запланированный workflow (weekly), каждый pull request (every PR), каждый финальный тег (every tag) или manual — кто-то должен помнить.

    Заголовки таблицы и слова-классы столбца schedule намеренно остаются на английском: это машинный словарь, который читает pnpm docs:check. Он читает эту таблицу и проваливается, когда файл в verification отсутствует в репозитории, цели make нет в Makefile, ячейка пуста или говорит «см. ниже», якорь не является заголовком этой страницы, или workflow в schedule не имеет триггера, который утверждает ячейка (schedule: для weekly, pull_request для every PR, push: tags для every tag). Как это работает — в Как документация остаётся живой.
