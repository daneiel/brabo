Authentication

These RNs came out of business-rules.md without changing a comma of the content: the single page was over 640 KB and these two sections alone were half of it. The #rn-NNN anchors remain identical — only the file that hosts them changed.

First-party auth rules. All of them hold in the api domain, which since 7.2 is also the issuer of access tokens — Keycloak left in an atomic cut, with no coexistence period. Decisions in ADR 0031 and ADR 0032.

RN-030 — Presenting an already-used refresh revokes the whole family​

Each refresh consumes the presented token and issues a child with the same family_id and the same family_started_at. Presenting a token that was already consumed is the signature of a theft — someone is using a copy — and the response is to revoke every live token of that family, with a security event.

The legitimate user is logged out along with it. That is the correct behavior, not a defect: on the server side, a client double-submit and a thief's replay are identical.

  • Where: apps/api/src/domain/auth/refresh-token.ts:50 + application/use-cases/auth/refresh.use-case.ts:98
  • Test: test/application/use-cases/auth/rotacao-e-reuso.spec.ts
  • Edge case: whoever presents a token from an already revoked family is a downstream victim, not a new theft: it records refresh_revoked and does not fire a second cascade. Without that distinction, each tab of the legitimate user would raise a false alarm during the incident.
  • Origin: ADR 0031

RN-031 — Login failure is counted per e-mail and per IP, and the lockout escalates​

A 15-minute sliding window in Postgres, without Redis. Two buckets per attempt and the most restrictive wins: e-mail (5 failures → 30s, 8 → 5min, 12 → 15min) and IP (20 → 30s, 30 → 2min). A successful login clears the e-mail bucket; the IP one drains only over time.

The bucket key is the normalized e-mail, never the user id. With the id, the bucket would only exist after finding the account, and the lockout itself would become an existence oracle.

  • Where: apps/api/src/domain/auth/lockout-policy.ts:97 + infrastructure/persistence/drizzle/drizzle-login-throttle.ts:74
  • Test: test/application/use-cases/auth/lockout.spec.ts
  • Edge case: while locked, the attempt is not recorded. If it were, an attacker would keep the victim's account locked forever just by continuing to try — the lockout would become a denial of service against the one it protects.
  • Why: the IP bucket cannot be cleared on success; whoever has a valid account would reset the window at will and spray guesses without limit.
  • Origin: ADR 0031

RN-032 — No response distinguishes an existing account from a nonexistent one​

Any response other than the uniform failure is only reachable after a successful password check. On login, nonexistent e-mail, wrong password and locked account return the same 401 and spend the same time — the no-account branch verifies against a dummy hash generated with the same parameters as the real one. On registration and on the reset request, known and unknown addresses return 202.

  • Where: apps/api/src/application/use-cases/auth/login.use-case.ts:79 + register.use-case.ts:74
  • Test: test/application/use-cases/auth/enumeracao.spec.ts
  • Edge case: the per-e-mail lockout check runs after argon2, not before. Exiting earlier is the optimization any reviewer would suggest, and it is exactly the leak — the test turns red if someone introduces it.
  • Edge case: the user MIGRATED from Keycloak (exists in users, with no row in auth_credentials) also gets the uniform 401 — and the "set password" link is sent silently. Answering password_pending would confirm that the address exists and that it is a legacy account. That is why findByEmail is a LEFT JOIN in a single query: two chained queries would make this branch pay one extra round trip to the database, and the clock would reveal what the body hides.
  • Why: what is claimed is "no branch skips the expensive work and none produces a distinguishable response", not constant time. See the consequences in the ADR.
  • Origin: ADR 0031, migrated-user edge case in ADR 0032

RN-033 — Verification and reset tokens are valid only once​

Consumption by conditional UPDATE with returning: the UPDATE itself is the guard. Zero rows covers nonexistent, of another purpose, already consumed, invalidated and expired — all with the same response. Requesting a new link invalidates the previous one. Completing a reset revokes all of the user's sessions and issues no tokens.

  • Where: apps/api/src/infrastructure/persistence/drizzle/account-token.repository.ts:76
  • Test: test/application/use-cases/auth/tokens-de-conta.spec.ts
  • Edge case: two simultaneous submissions do not both pass. The race is the normal case, not the exception: corporate e-mail scanners open every link of every message, so the robot usually consumes the token before the human clicks.
  • Why: the reset issues no session on purpose — logging in directly from a link received by e-mail would make compromising the e-mail equal to taking over the account, with no second step.
  • Origin: ADR 0031

RN-034 — The web session lives in an httpOnly cookie, with CSRF​

The refresh token goes in a brabo_refresh cookie (httpOnly, SameSite=Strict, Path=/auth, Secure in production) and does not appear in the body of any response. The access token, of 15 minutes, stays in memory on the client and travels in Authorization: Bearer.

/auth/refresh and /auth/logout require X-CSRF-Token equal to the brabo_csrf cookie, compared in constant time.

  • Where: apps/api/src/interfaces/http/auth/session-cookies.ts:53 + interfaces/http/auth/auth.controller.ts
  • Test: test/interfaces/session-cookies.spec.ts
  • Edge case: a CSRF failure is 403, not 401. With 401 the client would try to renew the session and enter a loop — the credential is fine, what is wrong is the request.
  • Why: also returning the refresh in the body would cancel out httpOnly — an XSS reading the login response would be enough, and it would take the long session instead of the 15 minutes of the access token.
  • Origin: ADR 0032

RN-035 — Internal engine ↔ api traffic requires the service secret​

The 32 /internal/* routes are @ServiceRoute(): they stay outside the user JWT and outside the rate limit. What authenticates is the EngineServiceGuard, comparing X-Brabo-Service-Token with BRABO_SERVICE_TOKEN in constant time. The same secret holds in both directions, and BRABO_SERVICE_TOKEN_PREVIOUS is accepted only on verification, so that rotation has no unavailability window.

  • Where: apps/api/src/interfaces/http/auth/engine-service.guard.ts:44 + infrastructure/security/service-token.ts + apps/engine/lib/engine_web/plugs/verify_service_token.ex
  • Test: apps/engine/test/engine_web/plugs/verify_service_token_test.exs, test/interfaces/route-surface.spec.ts and, for rotation on the api side (previous accepted only on verification, the caller sends the current one, once the previous is removed the old one fails), test/infrastructure/security/service-token.spec.ts (describe "rotação do BRABO_SERVICE_TOKEN") and test/interfaces/engine-service.guard.spec.ts (RN-597)
  • Edge case: the rate limit exemption comes from the route METADATA, not from the guard. The RateLimitGuard is an APP_GUARD and runs before any controller guard — when it decides, the EngineServiceGuard has not run yet.
  • Origin: ADR 0032

RN-597 — Changing the pepper is a global logout​

The pepper that keys the HMAC of opaque tokens has no _PREVIOUS, and changing it has a consequence, not a procedure: every refresh token in circulation, every open e-mail verification and password reset link, and every personal access token (PAT) can no longer be found, because the hash recomputed with the new pepper does not match the stored one. The refused refresh records refresh_unknown (and not refresh_reuse_detected), the link says "Link inválido ou expirado", and the lockout buckets change key — a locked account unlocks. The PASSWORD survives (argon2id with per-record salt, no pepper): changing the pepper costs a login, never an account, and the api starts normally with the new value.

Until RN-613, a pepper without its own value fell back to AUTH_JWT_SECRET, and rotating the JWT was also rotating the pepper, with all the consequences above. Since then the pepper is mandatory in production and never borrowed from the JWT.

  • Where: apps/api/src/infrastructure/security/auth-key-material.ts:212 (pepper), :228 (hashDeToken), :247 (baldeDeEmail); apps/api/src/interfaces/http/auth/pat-auth.guard.ts:142
  • Test: test/application/use-cases/auth/rotacao-dos-segredos.spec.ts, against the test Postgres
  • Edge case: the TARGET of "changing" includes the mistake of whoever separates the pepper from the JWT by generating a new value instead of copying the current one — it is the same change, and logs out the same way (pinned in the same spec, "a ordem errada").
  • Origin: ADR 0031, AT-196

RN-613 — AUTH_TOKEN_PEPPER is mandatory and its own; whoever migrates sets it with the current AUTH_JWT_SECRET​

The HMAC pepper of opaque tokens (refresh, account links, PATs, lockout bucket) no longer falls back to AUTH_JWT_SECRET. The silent fallback (AUTH_TOKEN_PEPPER ?? passphraseAtual()) turned every "zero-downtime" JWT rotation into a pepper change, and it was the COMMON path: the production and installation composes did not even pass the variable through. In production the api REFUSES to start without it, and the refusal states the fix — "defina com o valor ATUAL de AUTH_JWT_SECRET para não deslogar ninguém" —, because the obvious fix (generating a random one) is the one that logs everyone out. With the pepper equal to the old JWT the hash is byte for byte the previous one, refresh tokens and PATs remain valid, and from then on the JWT rotates on its own. A pepper equal to the JWT is NOT refused: it is the legitimate state of every migrated installation. The JWT rules (RN-114) apply: blank, the two example literals from the repository and fewer than 16 characters bring down the boot. Outside production a development default of its OWN applies (dev-auth-token-pepper-change-me), never the JWT's.

The install.sh does the migration: a NEW installation generates a random pepper; if there is a previous .env in the folder, it is READ (never executed) before being overwritten, and its pepper is kept — or, without a pepper, it is born with its AUTH_JWT_SECRET. The terminal says where the value came from, never the value.

  • Where: apps/api/src/infrastructure/security/auth-key-material.ts:168 (pepperAtual), :212 (pepper); apps/api/src/main.ts:46 (the boot check); install.sh:702 (valor_no_env_anterior), :734 (gerar_segredos), :831 (dizer_a_origem_do_pepper); the variable in the three composes (docker/docker-compose.yml, docker-compose.prod.yml, docker-compose.install.yml), in docker/smoke.sh and in .env.example
  • Test: test/infrastructure/security/auth-key-material.spec.ts (describe "pepperAtual (RN-613)": refusal without pepper even with JWT, the message, the examples, the floor, equal to the JWT accepted, the dev default); test/application/use-cases/auth/rotacao-dos-segredos.spec.ts (describe "a migração do RN-613": the refresh stored with the OLD formula remains valid with the pepper equal to the old JWT and survives the JWT change; the AUTH_JWT_SECRET describe: without pepper outside production, changing the JWT does not log out); scripts/dev/install-env.spec.ts (describe "o AUTH_TOKEN_PEPPER do instalador (RN-613)", against docker compose config, whole value)
  • Edge case: the installer only sees the .env of the folder it runs in. An installation whose .env lives elsewhere, a custom compose and Kubernetes with ExternalSecret do the migration by hand, through the runbook — in Kubernetes the AUTH_TOKEN_PEPPER property already existed in the ExternalSecret and in bootstrap.sh, and a provider that lacks it already failed the sync. And the installer migration wipes the volumes (ADR 0150): the refresh only survives for whoever restores the Postgres dump, which is the case that matters.
  • Origin: AT-210 (finding from AT-196), maintainer decision: migration with the current value

RN-595 — Every _PREVIOUS a service reads reaches it through the three composes, empty by default​

The three zero-downtime rotations (AUTH_JWT_SECRET, BRABO_SERVICE_TOKEN, CREDENTIALS_MASTER_KEY) depend on the process seeing the old value in a _PREVIOUS variable during the window. Compose does not pass the host environment through, and none of the three was in the environment: of any compose: setting the _PREVIOUS in .env had no effect, and whoever followed the runbook performed, without knowing, the dry swap that rotation exists to avoid. Now the api receives the three, and the engine and the broker receive BRABO_SERVICE_TOKEN_PREVIOUS, in the dev, production and installation composes, always with an EMPTY default — set means rotation in progress, and a filled default would leave the installation forever in the middle of one. Empty is the same as absent in the three readers.

  • Where: docker/docker-compose.yml, docker/docker-compose.prod.yml and docker/docker-compose.install.yml (services api, engine and broker); the readers are apps/api/src/infrastructure/security/auth-key-material.ts:136 (passphraseAnterior), apps/api/src/infrastructure/security/service-token.ts:92 (tokenDeServicoAnterior), apps/api/src/infrastructure/security/envelope-encryption.service.ts:93, apps/engine/config/runtime.exs:70 and apps/broker/src/config.ts:85
  • Test: scripts/ci/previous-nos-composes.spec.ts — DERIVES from the code of the three services the list of _PREVIOUS read and fails the one that is missing, or comes with a non-empty default, in any of the three composes; the "ExternalSecret do k8s" block fails the ExternalSecret without dataFrom.extract, a _PREVIOUS in data: and the api/engine Deployment without envFrom: brabo-secrets
  • Kubernetes (AT-220, maintainer decision): the Pods read envFrom: brabo-secrets, and the ExternalSecret (deploy/k8s/base/common/externalsecrets.yaml) pulls the WHOLE brabo object from the store via dataFrom.extract — the _PREVIOUS comes in when it exists and leaves when it is removed, on the next sync. It cannot be listed in data:: ESO has no optional key, and an absent property (the normal state) fails the sync of the whole Secret. Declared cost: EVERY key of the object becomes an api, engine, migrations and backup variable, and a MANDATORY key that is absent no longer fails the sync — the consumer is what flags it. Sync through a real ESO was exercised by hand on a disposable k3d, not in CI
  • Origin: AT-201 (finding from AT-196), same class as RN-540; Kubernetes half in AT-220

RN-598 — The PREVIOUS service token goes through the same rule as the current one​

During rotation, BRABO_SERVICE_TOKEN_PREVIOUS opens /internal/* just as much as the current one. It goes through ONE rule, the same as the current one (exigirTokenDeProducao), and no copy of it. Surrounding whitespace is discarded, and a value made only of whitespace counts as absent. In production, the public development literal (dev-service-token-change-me) and a value with fewer than 16 characters after the trim BRING DOWN the api boot, with a message naming BRABO_SERVICE_TOKEN_PREVIOUS. Before this, the variable was compared raw: a previous with the example value opened the internal door to anyone who had read this repository, without any error. Mandatoriness is the only part of the current one's rule that is NOT copied, because outside rotation the absent previous is the normal state. A previous equal to the current one (after the trim) still does not count as rotation.

  • Where: apps/api/src/infrastructure/security/service-token.ts:63 (exigirTokenDeProducao), :92 (tokenDeServicoAnterior); apps/api/src/main.ts:50 (tokenDeServicoAnterior), which runs at boot next to the current one
  • Test: test/infrastructure/security/service-token.spec.ts (describe "tokenDeServicoAnterior (RN-598)")
  • Edge case: this RN is the api side. The engine and the broker apply the same rule since RN-601.
  • Origin: AT-205 (finding from AT-196)

RN-601 — The engine and the broker apply the api's rule to both service tokens​

The three processes that compare the service token use the same rule as RN-598, each in its own language. Surrounding whitespace is discarded, and a value made only of whitespace counts as absent. In production, an absent BRABO_SERVICE_TOKEN, the public development literal (dev-service-token-change-me) or a value with fewer than 16 characters after the trim BRING DOWN the boot, with a message naming the variable. The last two refusals also apply to BRABO_SERVICE_TOKEN_PREVIOUS when it is set. A previous equal to the current one does not count as rotation. Outside production only the trim applies, and an empty current one falls back to the dev default.

Before, the engine read both raw in config/runtime.exs: no trim, no floor, and in production it started with the public default when the variable was missing (and with the empty string when the compose passed it empty). Only the api refusing to start protected the installation. The broker already applied the rule to the current one, but to the previous only the trim.

Two divergences of form, declared. In the engine, "production" is config_env() == :prod (the release), and not NODE_ENV, which it does not read; the production image is always a :prod release. And the rule stays inline in runtime.exs, not in a lib/ module, because in a release that file runs in a config provider before the application code is loaded.

Consequence: every process that evaluates that runtime.exs in a :prod release needs the token, including the migration (bin/engine eval Engine.Release.migrate()). That is why the migrate-engine service of the production and installation composes started receiving BRABO_SERVICE_TOKEN and BRABO_SERVICE_TOKEN_PREVIOUS, without default. The CI smoke showed it: without them, the migration died before migrating. The Kubernetes migration Job already received them through the envFrom of brabo-secrets.

  • Where: apps/engine/config/runtime.exs:85 (exigir_token_de_servico_de_producao), :105 (service_token), :121 (service_token_previous); apps/broker/src/config.ts:89 (anterior), :125 (exigirTokenDeProducao)
  • Test: apps/engine/test/engine/runtime_service_token_test.exs (evaluates the real runtime.exs via Config.Reader.read!/2, with env: :prod and :dev); apps/broker/src/config.spec.ts (describe "lerConfiguracao — produção, o token ANTERIOR (RN-601)")
  • Edge case: the rule is copied in the three processes, not shared: they are three languages or runtimes, and no test checks that the three copies remain equal. The floor counts characters (String.length in Elixir, .length in TS), which only differs for a token outside ASCII.
  • Origin: AT-216 (finding from AT-205)

RN-128 — sessionId/projectId/agent/agentId are validated BEFORE becoming a URL segment of the internal request to the engine​

HttpApiToEngineClient interpolates these values in a template string to build the /internal/* URL — with no DTO/class-validator in between, just like RN-127: they come from @Param/session lookup without a validation pipe at some point of the chain, and nothing guarantees their shape before interpolation. A malicious value could inject an extra path segment or characters that break the built URL — the EngineServiceGuard authenticates the CALLER (RN-035), it does not CHECK what the caller sends in the URL.

garantirSegmentoDeUrlInterna reuses the same width as NOME_DE_PASTA_VALIDO (RN-092/109) — hex, hyphen and underscore, 1 to 64 chars — and is called in TWO places, covering ALL the methods that interpolate an id in a URL, not only the ones CodeQL reported:

  • inside postCommand, which most methods already use (startAgent, sendAgentMessage, confirmReadiness, cancelAgentTurn, offerInfraHandoff, invalidateInstructions, startExecution, acceptParallelization, rearmDevAgent, reviseStory) — the caller lists the (nome, valor) tuples it already interpolated into the path, and postCommand validates ALL of them before building the request;
  • directly in reanalyzeSession/runAnamnese, which do not go through postCommand (they need to distinguish 503 from a transport failure) and that is why they were the only two points CodeQL reached.

The happy path does not change: sessionId/projectId are always a UUID from the database, and agent/agentId are always a short slug.

  • Where: apps/api/src/infrastructure/http-clients/api-to-engine-client.ts (garantirSegmentoDeUrlInterna, postCommand)
  • Test: apps/api/test/infrastructure/http-clients/api-to-engine-client.spec.ts (a malformed id is refused BEFORE touching the network — proven by pointing ENGINE_URL to a port nothing listens on — and the happy path does make the request)
  • Origin: CRITICAL CodeQL alert (internal request URL built with an unvalidated value) blocking the qa→main promotion, found during PR #256; same pattern as RN-092

RN-105 — Without an image decided by the Arquiteto, the container does not start and Code does not open​

The Code tab (GET /projects/:id/code/*, ADR 0060) answers 409 while the project is in sem_decisao — the initial state of every project. sem_decisao becomes decidido only when the Arquiteto emits artifact.project_image through the choose_project_image tool, with an OCI image with an explicit tag (latest refused), rationale and network posture.

The check lives in the SAME funnel as the path containment of RN-095 (ReadProjectCodeUseCase.alvo), and not in each of the seven routes (tree, file, search, PR diff, blame, PR list and detailed branches, FASE 26b) — a check duplicated in seven callers is a check that one day diverges in one of them (ADR 0058). Count corrected here: this record said "four routes" since FASE 26, and became outdated when FASE 26b added the last three to the same funnel without anyone revising this number.

The artifact has no table: it is the event itself in the event log, versioned (version grows with each emission, the current one is the one with the highest version), the same way as artifact.module_map. Revising the image is emitting a new version, never overwriting the previous one.

  • Where: apps/api/src/domain/containers/project-container.ts, apps/api/src/application/use-cases/containers/decidir-imagem-do-projeto.use-case.ts, apps/api/src/application/use-cases/containers/obter-container-do-projeto.use-case.ts, apps/api/src/application/use-cases/git/read-project-code.use-case.ts (method portaoDoContainer), apps/engine/lib/engine/harness/tools/choose_project_image.ex
  • Test: apps/api/test/domain/containers/project-container.spec.ts, apps/api/test/application/use-cases/containers/container-do-projeto.use-case.spec.ts, apps/api/test/application/use-cases/git/read-project-code.use-case.spec.ts ("o portão do container" block)
  • Edge case: 409 and not 403 — nothing is wrong with the requester or with their permission; the resource does not exist yet IN THIS STATE. And it is not 404: the tab exists, it is just not unlocked. The message says what is missing, so the screen shows the reason instead of a mute error (RN-088).
  • Origin: ADR 0065

RN-106 — git push, PR and deploy do not go out through the terminal — even within the project scope​

REVISED by RN-418 (ADR 0102, GLOBAL decision of the product owner): the deny this record describes became an ABSOLUTE CEILING (unconditional require_approval) — the rest of this entry is history, faithful to what held until the revision.

Inside the project container the agent is free (ADR 0065): the verb allowlist of ADR 0055 does not converge (findings Z and AD — verb, form and invocation are distinct spaces), and the way out is the wall, not a longer list. But three effects cross the wall and reach the world, and the user's decision was verbatim: "agente livre para o que quiser desde que não seja comandos de git ligado ao deploy e ao PR — estas ações ainda devem ser humanas".

decide() recognizes git push, git remote add/set-url, git merge, the provider CLIs (gh pr create, gh pr merge, glab mr create/merge, releases and workflow dispatch) and the common deploy commands (kubectl apply, helm upgrade, terraform apply, docker push, npm publish, ...) by token PREFIX, ignoring global flags in between (git -C /tmp push matches). Any segment of the compound command that matches is deny — not require_approval: "always allow" writes the pattern into allow, and one click would be enough for the second door to stay open forever. deny beats allow at any stage, and it is applied BEFORE any permissive stage in decide().

Denying does not take power away from the agent: the message redirects to the TYPED action (git_push, git_merge, pr_open) — which is born a proposed_action, has its own minimum role and records in the event log what was pushed and where. It is the path the dev agent already uses (agent_io.ex proposes git_push); what changes is that it is now guaranteed by deny, not just agreed by convention.

  • Where: apps/api/src/domain/actions/external-effect.ts, apps/api/src/domain/actions/decide.ts ("FRONTEIRA DO CONTAINER" block)
  • Test: apps/api/test/domain/actions/external-effect.spec.ts, apps/api/test/domain/actions/decide.spec.ts (describe "a fronteira do container")
  • Edge case: the boundary does NOT override the merge lock on a protected branch (RN-014, always manual) nor the path scope (RN-095/ADR 0055) — the three rules coexist, each one vetoing for a different reason.
  • Origin: ADR 0065

RN-107 — The Code tab has a FOURTH state: blocked by a pending decision​

The three states of RN-088 (loading/error/empty) do not describe sem_decisao (RN-105): it is not loading (the api already answered), it is not error (it answered CORRECTLY) and it is not empty (no data is missing — a DECISION is missing, which is something else). Treating sem_decisao as "empty" would show an editor without files, inviting one to think the repository is empty; treating it as "error" would make the screen suggest "try again" for something only the Arquiteto resolves.

The tab asks for the container state BEFORE trying to read code (GET /projects/:id/container), instead of waiting for the first tree or file to return 409 — the same check the api already does in the ReadProjectCodeUseCase funnel (RN-105), only asked first, so the fourth state is born as its own message and not as the footer of a generic error. While blocked, the screen re-queries on its own every 15s — once decided, the image does not change without new human action, and re-querying a stable state would be the same family of unnecessary traffic as PÓS-FASE 15.

The presentation of the fourth state was EXTRACTED to ContainerImageGateNotice (apps/web/src/components/ContainerImageGate.tsx) — a usage finding: the PRs tab (apps/web/src/routes/code/PrListAndDiff.tsx, consumed by ProjectPrsTab.tsx and by CodeDiffPanel.tsx) calls getCodePullRequests/ getCodeDiff, which go through the SAME funnel (RN-105) and can return the SAME 409 — but, unlike this tab, without asking first. It showed that 409 in the generic error banner with "Tentar de novo", the wrong affordance for a state only the Arquiteto resolves. isContainerImageGateError (apps/web/src/lib/api-client.ts) identifies the cause by status === 409 — the only cause of ConflictException in ReadProjectCodeUseCase.alvo — and PrListAndDiff swaps the banner for ContainerImageGateNotice when it matches, without a pre-check of its own (it reacts to the 409 of the query that was going to run anyway).

  • Where: apps/web/src/routes/ProjectCodeTab.tsx, apps/web/src/routes/ProjectCodeTab.module.css, apps/web/src/components/ContainerImageGate.tsx (shared presentation), apps/web/src/routes/code/PrListAndDiff.tsx (consumer reactive to the 409), apps/web/src/lib/api-client.ts (isContainerImageGateError)
  • Test: apps/web/src/routes/ProjectCodeTab.test.tsx ("o gate"), apps/web/src/routes/code/CodeDiffPanel.test.tsx, apps/web/src/routes/ProjectPrsTab.test.tsx ("o gate do container não é erro genérico")
  • Edge case: the front-end check does NOT replace the api's — it is a UX convenience. If the api changes state between the gate query and the actual read, the read route still refuses with 409 (RN-105); the front only avoids the common case of showing the empty editor for an instant. RN-150 — search_workspace has a ceiling on hit COUNT and on BYTES, each with its own marker​

Found in a PR review: search_workspace (dev agents and the two QA/gate agents, qa_tools.ex and qa_performance_seguranca_agent.ex — the latter only has read_file/search_workspace, without Terminal, on purpose) returned ALL search results, with no ceiling at all — the same class as finding S (Engine.Actions.TerminalExecutor.truncate/2) and as the read_file fix (Engine.Harness.Tools.ReadFile.truncate/2): the result stays in the loop history and travels in every following turn, and a large tree is enough to blow the provider's {413, "request entity too large"}.

Two independent ceilings, because the search overflows in two different ways:

  1. Hit count — a tree with thousands of files matching the term produces thousands of - caminho lines even if no individual file is large. Truncating only by BYTES at the end would still pay the cost of scanning and reading the content of each of those files before building the string. That is why the count ceiling (SEARCH_WORKSPACE_MAX_HITS, default 500) lives in WorkspaceFiles.search/3, which already STOPS consuming the search as soon as it finds enough hits — the pipeline runs over a Stream, and Enum.take(stream, max_hits + 1) only reads from the source what it needs to produce the first max_hits + 1 results. The "+1" is what allows saying there WERE more without continuing to scan the rest to count the exact total — counting the total would pay again the I/O the ceiling exists to avoid, so the marker says "showing the first N" and never invents a total.
  2. Bytes of the final text — even with limited hits, very long paths can produce a large string. Byte ceiling (SEARCH_WORKSPACE_MAX_BYTES, default 32,768), same pattern as terminal_output_max_bytes/read_file_max_bytes — its OWN variable, it does not reuse the other two: same class of overflow, diverging one should not require touching the others.

The truncation marker is addressed to the MODEL, not to the human: it says what was cut (hits and/or bytes) and instructs to refine the search term — the same spirit as the TerminalExecutor/ReadFile markers.

RN-163 — The Criativo keeps the promise to try again​

Each Criativo turn runs a bounded tool-use loop, with a ceiling of 12 trips to the model — the same design the PO and the Arquiteto already had. Before, the model was called ONCE per turn: the tool result was appended to the in-memory history and nobody read it again, so the sentence "vou corrigir e tentar de novo" — literal in the code — was only fulfilled if the user sent another message. For whoever used it, the Criativo simply stopped answering after saying it was going to fix it.

Four consequences, and each one is a rule:

  1. A tool error is input, not the end of the line. The reason goes back to the model as a tool message and the loop calls the model again, which re-emits it corrected WITHIN the same turn.
  2. Nothing is announced that the code will not execute. The retry sentence is decided after dispatching the tools and knowing how many rounds are left: with a round available, the agent says it will fix it; without a round, it does not promise.
  3. The tool failure became a durable agent.error, with origin (RN-059) — it was an agent.response, indistinguishable in the event log from a normal response. origem: infra when the api refused the append_event; origem: modelo for the payload the model wrote (wrong key, origin that is not a list, duplicated rule, system-emitted type). The payload carries tool and retentativa.
  4. An exhausted ceiling does not end in silence. It becomes an agent.error with reason: "limite_de_iteracoes" and origem: modelo, the same reading as the ToolLoop's toolloop.limit_reached. The event name is NOT reused: this agent does not run inside the ToolLoop, and the event would lie about who produced it.

Two boundaries of the loop, both deliberate: a successful ask_structured_questions ends the turn (the ball is with the user, and the answers come back in a future turn — RN-162); and a turn that had a failure in some round closes with a CONSOLIDATED outcome in the thread, so the last word is not the error of a round that was already corrected later.

RN-170 — A Local path is validated at CREATION, and the refusal teaches​

REVISED by RN-422 (ADR 0104): creation validation started to DIVERGE by mode — mounted (the renamed local) keeps touching the disk as described here, runner validates only the LEXICON, without I/O — the rest of this entry is history, faithful to what held until the revision.

Creating a project in local mode with a path the api cannot reach produces a project that hangs later — on the first tool of the first agent, far from the screen where the decision was made. That is why creation refuses with 400, and the message says what needs to be done.

The path must be:

  1. absolute, with no .. or . in any segment (the stored path is the path that is read; /srv/app/../../etc is /etc and does not look like it);
  2. existing and a folder inside the api container;
  3. writable by the process (access(W_OK|X_OK)) — the images run non-root (ADR 0024), and a host folder with another owner arrives mounted as read-only in practice;
  4. outside the root and the system folders (/, /etc, /usr, /var, /data… and everything below them): the project root is the scope that AUTHORIZES the agent's terminal (ADR 0055), and a project rooted at /etc turns "the agent writes in its project" into "the agent rewrites the container";
  5. with no overlap with the Brabo checkout, in BOTH directions — the folder that CONTAINS the monorepo and the folder INSIDE it. The second case is the problem that ADR 0055 reports actually happening.

The stored path is the normalized one, not the raw string: validating one string and storing another is how validation stops holding the next day. A workspacePath sent together with workspace_mode: container is REFUSED, not ignored — a field silently discarded becomes "but I configured it".

The LEXICAL part (items 1, 4 and 5) runs also on read, on each derivation of projectScopeRoot: the only way to bypass creation is to write directly into the database, and what is gained there is a terminal scope at /. The DISK part (items 2 and 3) runs only at creation, where the user can still fix it.

The refusal for a missing folder brings the mount instruction — the file, the two services and the line (- <caminho>:<caminho>), with the pointer to the runbook. Mounting only in the api produces a project the api accepts and the engine does not see: it validates what it sees, and has no way of knowing what is mounted in the other container.

RN-183 — The theme preference has one source, and the <html> attribute is the truth​

Reading, writing, toggling and observing the theme is apps/web/src/lib/tema.ts — the button lives in the shell and consumes that API, it never writes data-theme on its own.

Three decisions inside it:

Separating them would require a JOIN on every hybrid search (Onda 4) and would open room for the two to diverge — a passage with a vector but no lexical entry, or vice versa — with no database mechanism preventing it. One row, one source of truth for both halves of the search.

  • Where: apps/api/src/db/schema/rag.ts (chunks table)
  • Test: apps/api/test/infrastructure/persistence/chunk.repository.spec.ts (the three specs write and read both columns on the same row)
  • ADR: 0079

RN-221 — search_vector is never written by the application — it is a GENERATED column​

search_vector is GENERATED ALWAYS AS (to_tsvector('portuguese', content)) STORED. No use case, repository or script writes to it — Postgres keeps it consistent with content by construction, ready in the same transaction as the INSERT, without depending on any LLM provider answering (unlike embedding, which only arrives when an indexing pipeline exists).

  • Where: apps/api/src/db/schema/rag.ts (search_vector column)
  • Test: apps/api/test/infrastructure/persistence/chunk.repository.spec.ts ("grava um chunk de docs com vetor e devolve o search_vector gerado pela GENERATED ALWAYS AS")
  • ADR: 0079

RN-222 — The vector dimension is documented, not guessed, and embedding arrives after the chunk​

chunks.embedding is vector(768) — the real dimension of Ollama's nomic-embed-text, the only provider that today declares capabilities.embeddings: true (RN-191, ADR 0075). A vector index has a FIXED dimension: changing the embedding model in the future is a new migration, never a runtime parameter. The column is NULLABLE: this table stores the CHUNK (cut text), and the VECTOR may arrive later via an asynchronous indexing pipeline that does not exist yet (Onda 4) — without that, chunking would have to wait for embedding, mixing two failures of different nature (document parsing versus a network call to a provider) in a single atomic write.

  • Where: apps/api/src/db/schema/rag.ts (embedding column)
  • Test: apps/api/test/infrastructure/persistence/chunk.repository.spec.ts ("grava um chunk de docs com vetor..." writes with embedding filled; the other two specs write without it, confirming nullability)
  • ADR: 0079; RN-191

RN-223 — The vector index is HNSW, not IVFFlat, because the table is born empty​

IVFFlat needs rows already loaded to train the lists (lists) and performs poorly if built over an empty table — which is exactly the state of this table at birth, with no indexing pipeline yet (Onda 4). HNSW builds the graph incrementally, insertion by insertion, with no training step — good from the first row. vector_cosine_ops because it is the metric text embeddings generally expect (the similarity ranking should not change with the vector's magnitude).

  • Where: apps/api/src/db/migrations/0045_shallow_randall.sql (chunks_embedding_idx)
  • ADR: 0079

RN-224 — The migration creates the pgvector extension by itself, idempotently​

The 0045 migration runs CREATE EXTENSION IF NOT EXISTS vector before creating the table, instead of assuming docker/postgres/init.sql has already run — that file only executes on the FIRST initialization of the Postgres volume, and an environment with an old volume may not have the extension. IF NOT EXISTS is idempotent: local (where the extension was already installed) and a new environment go through the same line with no difference in behavior.

  • Where: apps/api/src/db/migrations/0045_shallow_randall.sql
  • ADR: 0079

RN-225 — A migration that may require operator privilege is born in breaking/​

Creating an extension requires the application role to have CREATEDB (or the extension to be marked "trusted" by the DBA). Locally the role is a superuser, but nothing guarantees that in production — managed Postgres providers often do not give superuser to the application. If the migration fails there, it is an OPERATOR action before the deploy (running CREATE EXTENSION vector; once, as superuser), not a product bug — the CLAUDE.md criterion for being born in breaking/ instead of feature//bugfix/.

  • Where: branch breaking/tabela-de-chunks, apps/api/src/db/migrations/0045_shallow_randall.sql (a comment that documents the decision inside the migration itself)
  • ADR: 0079

RN-226 — ChunkRepository covers only basic write/read; createMany is a batch operation​

The port only has create, createMany, findById and listByProject — hybrid search (vector + lexical, weights, threshold) belongs to Onda 4 (G2) and deliberately does NOT come in here: the port stores data, the use case decides what to do with it. createMany exists because an indexing cuts N passages of a document/session at once, avoiding N round trips per indexed document.

  • Where: apps/api/src/application/ports/chunk-repository.port.ts, apps/api/src/infrastructure/persistence/drizzle/chunk.repository.ts
  • Test: apps/api/test/infrastructure/persistence/chunk.repository.spec.ts ("createMany grava um lote e listByProject filtra por escopo, sem misturar docs e session")
  • ADR: 0079

RN-227 — The session status badge covers the 5 real states, not the handoff's 4​

The handoff asks for 4 badges (ativa/aguardando/fechada/abortada) for the 5 real states of the machine (created/active/closing/closed/closed_abnormally). closed_abnormally→abortada and created→aguardando are direct. closing is NOT merged with "fechada": it gets its own badge ("encerrando", tone accent, pulsing), because in closing the outcome (closed or closed_abnormally) is not yet known — calling it "fechada" would lie about that.

  • Where: apps/web/src/routes/ProjectSessionsTab.tsx (SELO_DO_STATUS)
  • Test: apps/web/src/routes/ProjectSessionsTab.test.tsx — describe "ProjectSessionsTab — selo de status (RN-227)"

RN-228 — The pill filter groups the 2 states without their own pill by TRAJECTORY​

The handoff's pill filters (todas/ativas/fechadas/abortadas) only cover 4 of the 5 states. created (aguardando) goes into the "Ativas" pill — it has not reached anywhere yet, it is a "session in play". closing goes into the "Fechadas" pill — it is already on its way to closing without error. Each row's BADGE (RN-227) is never rewritten by the filter; the pill only groups.

  • Where: apps/web/src/routes/ProjectSessionsTab.tsx (correspondeAoFiltro)
  • Test: apps/web/src/routes/ProjectSessionsTab.test.tsx — describe "filtro pill agrupa os 2 estados sem pill própria (RN-228)"

RN-229 — The Criativo tab's "cost of the month" KPI is the ACTOR's consumption, not the project total​

It reuses getMySpend(projectId, 30) — the SAME queryKey that ProjectSpendTab.tsx#MeuConsumo uses for the member's view (RN-101, ADR 0063), with no new aggregation. It NEVER shows the project total summing everyone (porProjeto in getWorkspaceSpendReport), because that data is owner-only and the Criativo tab is seen by any member of the project — showing the overall total would leak other people's spending to whoever RN-060/101 does not authorize to see it.

  • Where: apps/web/src/routes/ProjectSessionsTab.tsx (CriativoKpis)
  • Test: apps/web/src/routes/ProjectSessionsTab.test.tsx — describe "KPIs da aba Criativo", cases "caminho feliz" and "CASO DE FALHA"

RN-230 — The "ideation → commit rate" KPI is declared absent, never computed​

There is, nowhere in the product, a link between a creative session and the commit it produced. The Criativo tab shows "—" with the sentence "não medido: sessão não é vinculada a commit hoje" instead of inventing a calculation — the same class of error that ADR 0042 already refuses for a model score.

  • Where: apps/web/src/routes/ProjectSessionsTab.tsx (CriativoKpis)
  • Test: apps/web/src/routes/ProjectSessionsTab.test.tsx — "'Taxa ideação → commit' é DECLARADA ausente — nunca um número calculado"
