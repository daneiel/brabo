    RN-413 — Шаблоны промптов живут вне кода, версионируемые в графе

    До этой поставки каждый промпт агента был встроенным heredoc на Elixir — идентичности (Engine.Harness.Agents), kickoff у PO/Arquiteto/Dev Lead/UX/Infra, промпт суммаризации ContextManager. Шаблон промпта теперь может жить как (:PromptTemplate {name})-[:HAS_VERSION]-> (:PromptVersion {version, body, hash, active}) в Neo4j, записываемый через POST /internal/graph/prompt-templates и читаемый через GET /internal/graph/prompt-templates/:name. Upsert идемпотентен по хэшу — двойная запись ОДНОГО И ТОГО ЖЕ содержимого не создаёт новую версию, возвращается только уже существующая версия с тем же хэшем.

    Первая партия извлечена в prompts/*.md (front-matter name/version, плейсхолдеры задокументированы в разделе "Variáveis" для фрагментов, которые в исходном .ex были интерполяцией): ux-designer-identity, psychologist-kickoff, anamnese-kickoff, context-manager-summarize. scripts/dev/seed-prompts.ts читает prompts/*.md, вычисляет sha256-хэш тела и отправляет его на эндпоинт выше. Ни один .ex в этой поставке не редактировался — четыре GenServer по-прежнему содержат встроенный текст; потребление шаблонов из графа (источник :graph у InstructionFiles, приоритет db > graph > dir > root) — следующая Волна, объявленная вне этого.

    • Где: apps/api/src/application/use-cases/graph/upsert-prompt-template.use-case.ts, get-prompt-template.use-case.ts; apps/api/src/interfaces/http/internal/internal-graph.controller.ts; prompts/*.md, prompts/README.md; scripts/dev/seed-prompts.ts (SECAO_DE_DOCUMENTACAO, corpoSemDocumentacao, parseFrontMatter)
    • Тест: сценарии использования с замоканным GraphStore (upsert с тем же хэшем не дублирует) + интеграционный тест против реального Neo4j, корректно пропускаемый при недоступности; scripts/dev/seed-prompts.spec.ts (разбор front-matter, детерминированный хэш, некорректный шаблон проваливается с понятным сообщением; и начиная с AT-244 — обход ВСЕХ prompts/*.md: засеянное тело не содержит раздела документации, каждый плейсхолдер встречается в нём ровно один раз, а суммаризатор получает ходы ровно один раз тем же render, что у engine)

    Начиная с AT-244 раздел "## Variáveis" каждого файла НЕ засевается: тело шаблона заканчивается на строке ## Variáveis, и сидер отбрасывает всё с неё и далее. Раньше тело несло весь раздел — документацию, цитирующую те же {{placeholders}}, что и тело, — и поскольку каждый потребитель заменяет ВСЕ вхождения (String.replace/3), при включённом graph_templates_enabled? модель получала документацию и данные ДВАЖДЫ: суммаризатор ContextManager — ходы вдвойне, kickoff Psicólogo и Anamnese — журнал событий вдвойне, а идентичность UX (за graph_instruction_templates_enabled?) — документацию в каждом ходе. Форма была у всех четырёх файлов; разрез живёт в СИДЕРЕ, а не в render, потому что render у каждого потребителя свой, а вопрос "что есть тело" — о файле, который читает только сидер. Версии повышены (anamnese-kickoff и ux-designer-identity до "2", psychologist-kickoff и context-manager-summarize до "3") с ТЕМ ЖЕ текстом промпта. Само по себе не закрывается в уже засеянной установке: АКТИВНАЯ версия в графе остаётся старой, с документацией, пока scripts/dev/seed-prompts.ts не будет запущен снова — хэш тела изменился, поэтому сидер создаёт новую версию и деактивирует предыдущую. При выключенных флагах (по умолчанию) дефекта никогда не было: действует встроенный текст, у которого этого раздела никогда не было.

    RN-415 — Модели Ollama гарантированы при загрузке, деградация RAG объявлена

    nomic-embed-text (RAG_EMBEDDING_MODEL) никогда не подтягивался автоматически — реальный баг, не только этой функции: entrypoint сервиса ollama подтягивал только llama3.2:1b, и RAG в любом чистом окружении МОЛЧА деградировал до только-лексики, без какого-либо признака того, что это происходит. Новый сервис ollama-model-loader (одноразовый, docker-compose.yml dev и prod), читающий OLLAMA_REQUIRED_MODELS (по умолчанию gemma3:1b,yi-coder:1.5b,nomic-embed-text), добавочный к существующему сервису ollama — его entrypoint остаётся нетронутым.

    Деградация перестала быть молчаливой: rag_search (RN-414) и гибридный поиск api уже возвращали degraded: true, когда эмбеддинг сбоил, — не хватало ПОТРЕБИТЕЛЯ, который сделал бы этот флаг видимым. Теперь, когда инструмент существует, сама модель видит предупреждение в отформатированном тексте, а model-loader снижает вероятность деградации изначально.

    • Где: docker/docker-compose.yml, docker/docker-compose.prod.yml, docker/ollama/pull-models.sh; deploy/k8s/base/neo4j/, deploy/k8s/base/ollama/job-model-loader.yaml (шаблон, НЕ подключённый ни к одной kustomization — в deploy/k8s/ ещё нет Service ollama, на который можно указать, и подключение сегодня вызвало бы CrashLoopBackOff при каждом реальном деплое)
    • Тест: scripts/dev/verificar-modelos-ollama.sh, выполненный сквозным образом с реальной маленькой моделью (all-minilm), чтобы не платить стоимость в несколько ГБ из продакшен-списка на общей машине
    • Источник: находка при закладке графа знаний — см. ADR 0100

    Терминал локального runner, навсегда застрявший в "Открытие терминала..." (RN-433)

    Найдено при тестировании нового проекта в режиме runner (ADR 0103/0104) и открытии Code → Dev → Терминал: экран никогда не выходил из скелета загрузки, а консоль показывала socket do terminal com erro/socket do terminal fechado в цикле, с растущей задержкой до стабилизации на ~5-6 с — паттерн backoff ПО УМОЛЧАНИЮ у phoenix.js.

    RN-433 — Сокет терминала сдаётся после таймаута, значение по умолчанию ENGINE_PUBLIC_URL достижимо ИЗ БРАУЗЕРА, а эндпоинт не дублирует путь

    Три наложенных дефекта. Первые два найдены при расследовании симптома; ТРЕТИЙ проявился только после исправления первых двух — без них браузер никогда не достигал engine, чтобы обнаружить баг пути под ними. Исправление лишь одного оставляет остальные в силе:

    1. У ENGINE_PUBLIC_URL (RN-419) никогда не было никакого значения по умолчанию в docker/docker-compose.yml — только ENGINE_URL (http://engine:4000, имя хоста, которое разрешается ТОЛЬКО внутри сети Compose). Запасной вариант кода (process.env.ENGINE_PUBLIC_URL ?? process.env.ENGINE_URL ?? …, request-runner-ticket.use-case.ts) молча падал в неверное значение, и браузер пытался открыть WebSocket к имени хоста, которое он никогда не разрешит. docker/docker-compose.yml получил ENGINE_PUBLIC_URL: ${ENGINE_PUBLIC_URL:-http://localhost:4000} в сервисе api — ТО ЖЕ значение по умолчанию, что VITE_ENGINE_URL уже использует в сервисе web, по той же причине.
    2. Даже с правильным URL у транспорта, который НИКОГДА не открывается (engine не работает, firewall, неверная будущая перенастройка), не было никакого потолка: apps/web/src/lib/terminal-channel.ts никогда не передавал reconnectAfterMs в Socket, поэтому phoenix.js падал в свой backoff ПО УМОЛЧАНИЮ и пытался переподключаться сам вечно — сам докблок модуля уже объявлял намерение "без автоматического переподключения" (та же линейка, что у session-channel.ts/RN-108), но на практике оно никогда не выполнялось. Без onError/onClose, вызывающих handlers.onErro, TerminalPanel застревал в 'carregando' (RN-088 — каждый экран различает загрузку/ошибку/пустоту — молча нарушена). Исправлено через reconnectAfterMs, возвращающий значение, которое практически никогда не срабатывает (24 ч, тот же паттерн, что у session-channel.ts), и СОБСТВЕННЫЙ таймаут 8 с (TIMEOUT_CONEXAO_MS): если onOpen не сработает раньше, модуль вызывает handlers.onErro с практичным сообщением и отключается.

    Согласие на базу, на хосте (RN-511)

    RN-511 — Базу СОГЛАСОВЫВАЮТ один раз на хосте, общий доступ доказывается МОНТИРОВАНИЕМ, а без терминала шаг сообщает, а не соглашается

    RN-500 построила базу и сказала, что делать, когда её нет, — projectsBase: null, и режим "Смонтированная папка" не предлагается. Не хватало того, кто попросил бы её настроить: в продукте этого не делало ничто, и в результате готовый режим оказался недостижим для тех, кто устанавливает.

    Шаг согласия живёт в pnpm bootstrap (Docker › Base de projetos), предлагает $HOME/projetos-brabo и принимает другой введённый путь. Имя — не предпочтение: .env.example уже использует ~/brabo-projetos как пример PROJECT_WORKSPACES_HOST_DIR, корня, которым управляет ПРОДУКТ, и предложение одного и того же имени для двух переменных было бы шагом внутрь коллизии, которую отверг ADR 0141, — <base>/loja попал бы в ту же физическую папку, что проект container, чей workspace_dir_name тоже loja, и bootstrap сделал бы git init внутри чужого проекта.

    Имя — лишь уклонение; защита — механизм. validarBase отклоняет любого кандидата, пересекающегося — в ОБОИХ направлениях — с checkout Brabo (защита, которая уже была у RN-500) или с PROJECT_WORKSPACES_HOST_DIR (новое правило), а также отклоняет ~, относительный путь и корень. Отказ действует для ВВЕДЁННОГО пути, а не только для значения по умолчанию; хорошо выбранное значение по умолчанию лишь избавляет пользователя от того, чтобы отказ был первым, что он видит.

    Общий доступ Docker Desktop доказывается МОНТИРОВАНИЕМ, никогда не чтением settings.json. Этот файл не задокументирован, меняется между версиями и между macOS и Windows и описывает то, что пользователь НАСТРОИЛ, а не то, что сделает демон. Это та же линейка "capability объявляется только тогда, когда доказана выполнением" из ADR 0041/0042, применённая к хосту. Доказательство — сторожевой файл, а не сухой ls: пустая папка и папка без общего доступа дают одинаковый пустой листинг, поэтому скрипт пишет файл и спрашивает, видит ли его контейнер. Только в macOS и Windows (process.platform); в Linux нет списка общего доступа, и проверка — существование и запись. Это ВТОРАЯ платформенная защита продукта, симметричная первой (validarDirDentroDoHomeNoLinux, в runner): каждая ограничивает лишь там, где ограничение что-то значит.

    У доказательства три исхода, и они не схлопываются: доказано; провалено (переменная не записывается, а отказ называет путь и где его добавить); и не удалось доказать — нет локального образа Docker для монтирования, — что записывает переменную и громко говорит, что доказательство не выполнялось, с командой, чтобы выполнить его позже. "Не смог посмотреть", ставшее "всё в порядке", — ровно то, как база без общего доступа дошла бы до пользователя в виде контейнера, поднимающегося с пустой папкой, вдали от экрана, где был сделан выбор.

    Без TTY шаг СООБЩАЕТ и ничего не делает. Пункт меню bootstrap.sh выполняется со stdin из /dev/null — намеренно, иначе всё, что читает stdin, отбирает у пользователя стрелки, — поэтому оттуда скрипт может только сообщить, а вывод называет команду, которая спрашивает. Это тот же дизайн, что у perguntarUsoDoOllama, который без терминала применяет значение по умолчанию и предупреждает, а не зависает. Скрипт согласия, который "соглашается" сам в CI-конвейере, — отрицание самого слова. По той же причине preflight.mjs сообщает состояние базы и никогда не спрашивает: ответ — это путь на чьём-то диске, и не существует значения по умолчанию, которое можно применить молча.

    mkdir -p происходит только после согласия и проверки — создавать папку по пути, ещё не прошедшему отказы, значит создавать папку где угодно, куда дотягивается процесс. А уже присутствующее значение никогда не перезаписывается без подтверждения.

    Брокер по умолчанию поднимается в локальном compose (RN-512)

    RN-512 — Брокер выходит из profiles в ЛОКАЛЬНОМ compose и только в нём, а DOCKER_GID начинает сообщаться в preflight

    Брокер родился под profiles: ["container-broker"] с обоснованием, которое написал сам ADR 0130: "дать доступ к Docker хоста процессу, который ещё ничто не вызывает, было бы изменением позиции для каждой машины разработки взамен ни на что". Обе половины умерли. "Ничто его не вызывает" — ложь начиная с ADR 0133/0134/0136 — у брокера четыре реальных вызывающих. А "взамен ни на что" перестало описывать обмен, когда ADR 0144 заставил mounted поднимать контейнер ЧЕРЕЗ БРОКЕР, а ADR 0146 сделал mounted локальным значением по умолчанию: с выключенным профилем режим по умолчанию заканчивается BrokerIndisponivelError.

    Поэтому он выходит из profiles в docker/docker-compose.yml — и только там. В docker/docker-compose.prod.yml профиль ОСТАЁТСЯ, и два файла начинают намеренно расходиться.

    Асимметрия — в том, что означает сокет на каждой стороне. Тот, кто запускает pnpm dev, уже имеет сокет Docker — он запускает docker compose против демона собственного хоста, — поэтому получение его брокером не даёт ничего, чего у оператора уже нет. Предельная поверхность — HTTP самого брокера, который не публикует порт, живёт в сети internal: true, достижимой только api, и сравнивает BRABO_SERVICE_TOKEN за постоянное время. В продакшене расчёт противоположный: сокет — настоящая граница привилегий, оператор — не разработчик, и ничто в этой фазе не меняет режим по умолчанию продакшен-установки.

    Пять слоёв сдерживания не затрагиваются. Это меняет то, когда работает брокер, никогда то, что он принимает: он по-прежнему получает projectId и одну из пяти операций, по-прежнему идёт в api читать решение Arquiteto и по-прежнему не имеет никакого параметра, куда можно записать privileged, cap_add, network: host или свободный -v. Сдерживанием никогда не был профиль.

    Следствие для окружения и почему оно получило сообщение. DOCKER_GID перестаёт иметь значение только для того, кто намеренно включал профиль, — человека, который по определению обращал на него внимание, — и начинает действовать для любого, кто запускает pnpm dev. Сокет на хосте — root:docker, а процесс брокера работает не от root; group_add в compose даёт ему группу, а значение по умолчанию 999 самое распространённое и неверно в нескольких дистрибутивах. Ошибка не ломает загрузку — брокер поднимается нормально, — она ломает ИСПОЛЬЗОВАНИЕ: каждая операция умирает с permission denied на сокете, а симптом появляется гораздо позже, когда кто-то предлагает container_start. Поэтому preflight.mjs начинает сообщать состояние при каждом pnpm dev.

    У сообщения три исхода, и они не схлопываются: совпадает; расходится (с источником действующего значения — configurado × default, — потому что оба требуют разных инструкций); и неприменимо, когда на машине нет группы docker. Третий — не ошибка и не "не смог": в macOS и Windows Docker Desktop не использует unix-группу, а в rootless Docker сокет принадлежит самому пользователю. Считать отсутствие расхождением значило бы обвинить половину машин в дефекте, которого у них нет, — та же осторожность, что у baseSobrepoeOCheckout, возвращающего false для неизвестного checkout. И он сообщает, никогда не блокирует: pnpm dev поднимается так же.

    Выйти из profiles было недостаточно, и дефект проявился лишь при первом подъёме по умолчанию. Образ разработки готовил pnpm через corepack от root при сборке и работал как uid 1000, который не читает этот кэш; без кэша corepack пытается скачать pnpm при старте, а единственная сеть брокера — internal: true, — попытка умирала с getaddrinfo EAI_AGAIN registry.npmjs.org, и контейнер выходил с 1 через пять секунд после подъёма.     RN-528 — git_local_repos входит в резервную копию, назначением может быть диск, а restore для compose переиспользует ТЕ ЖЕ три проверки

    Гарантия архива репозиториев заявлена, и она меньше, чем «snapshot». Ничто не quiesced. Гарантируется согласованность ПО ССЫЛКЕ — git записывает объекты до перемещения ref и меняет ref атомарным rename, так что tar, пересекающий git push, получает старое или новое значение, никогда половину. НЕ гарантируются глобальный момент (tar обходит дерево в течение периода) и связность объектов (в образе намеренно нет git). А параллельный gc, удаляющий packfile, становится СБОЕМ, а не частичным архивом: статус tar записывается в файл, потому что в POSIX sh статус конвейера — это статус последней команды, — без этого неполный архив объявлял бы себя хорошим, а лгущая резервная копия хуже падающей, потому что только вторая становится тревогой. *.lock исключается: восстановление осиротевшего lock даёт репозиторий, в котором любой git отказывается работать.

    Восстановление репозиториев — команда-БРАТ, а не фаза другой — это два артефакта с двумя суждениями, и их объединение заставило бы сбой git провалить проверку event log. По умолчанию она проверяет и пишет только с --restaurar; отказывается распаковывать поверх существующих репозиториев (смесь двух состояний не поднимает никакой ошибки и проявляется только в fetch с неправильной историей); и — находка реального прогона — отказывает ДО tar, когда том не принимает запись, называя --user 0:0. git_local_repos делят три образа с разными uid, и у него владелец того, кто смонтировал его первым (измерено: 1000:1000, режим 0755), тогда как этот образ работает как uid 70.     RN-530 — Миграция требует ДОКАЗАННОЙ резервной копии: установщик получает право удалять только после восстановления

    Установка поверх существующей установки не предлагается: либо миграция, либо остановка. up поверх томов другой версии — тот вид ущерба, который не предупреждает.

    У миграции есть порядок, и смысл ему придаёт средний шаг: резервная копия → ДОКАЗАТЬ, что восстанавливается → спросить → удалить → установить → восстановить.

    Доказательство — не перестраховка. Резервная копия, которую никто не пытался восстановить, — это просто файл, и узнавать это нужно не после down -v — поэтому установщик запускает docker/backup/test-restore-compose.sh (ТЕ ЖЕ три проверки restore.sh, ADR 0152) до любого удаления. Упавшая резервная копия или упавшее доказательство прерывают миграцию, ничего не удаляя, а сообщение говорит, где осталась резервная копия.
