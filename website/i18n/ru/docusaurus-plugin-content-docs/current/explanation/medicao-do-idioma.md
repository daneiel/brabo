# Измерение эвристики языка {#measuring-the-language-heuristic}

> AT-160 (EP-028, HS-053). Измеряемая эвристика — та, что предложила
> спецификация AT-080 («A — собственная эвристика, без зависимостей»).
> Начиная с AT-163 ([RN-624](../business-rules.md#rn-624)) продукт её
> выполняет: api определяет с её помощью язык автора и СПРАШИВАЕТ, прежде
> чем что-либо изменится. Пороги продукта **предварительные** — см.
> [Предварительные пороги продукта](#the-products-provisional-thresholds).

## Что существует {#what-exists}

Инструмент живёт в `scripts/idioma/` и запускается Node репозитория (type
stripping, без шага сборки). **Никаких новых зависимостей**: эвристика — это
список маркеров и регулярные выражения, а извлечение общается с Postgres
через `psql` внутри контейнера базы.

Сама эвристика живёт в **api** —
`apps/api/src/domain/iam/heuristica-de-idioma.ts`, — а `scripts/idioma/heuristica.ts`
лишь реэкспортирует её, поэтому инструмент измеряет ровно тот код, который
выполняет продукт. Это направление вынужденное: api не достаёт ни до
`scripts/`, ни до какого-либо runtime-пакета без шага сборки, а
`packages/shared` содержит только типы. В файле нет импортов, поэтому Node
запускает его из `scripts/` через type stripping (команды `idioma:*` глушат
сопутствующее предупреждение о "typeless package"), а у `scripts/idioma/` есть
собственный `tsconfig.json` — единственное отличие в отключении
`verbatimModuleSyntax`, который отвергает любой `export` модуля CommonJS,
как в api. Сначала пробовали файл `.mts`: он прошёл обе проверки типов и
сборку, но сломал все скрипты `ts-node` в api. Правило о том, *что
является доказательством* (`evidenciasDoAutor`), переехало вместе с
эвристикой, и извлечение реального корпуса использует то же правило.

| файл | роль |
|---|---|
| `heuristica.ts` | реэкспортирует эвристику api: очистка, контрастная оценка, кандидат и предварительные параметры, выборка из 10 сообщений, гистерезис и правило доказательства |
| `corpus-sintetico.jsonl` | **версионируемый** синтетический корпус — каждая строка написана вручную для инструмента, `origem: "sintetico"` |
| `sequencias-sinteticas.json` | синтетические диалоги для пути выборки и гистерезиса |
| `medicao.ts` / `medir.ts` | инструмент и его CLI |
| `extrair.ts` | извлекает **реальный** корпус из локального event log в файл вне git |
| `rotular.ts` | разметка реального корпуса с подсказками, в терминале |

## Два корпуса и где живёт каждый {#the-two-corpora-and-where-each-one-lives}

Решение сопровождающего (AT-168, ответ 5) — **реальный + синтетический**. У
них противоположные правила хранения:

- **Синтетический** — версионируется, ревьюится как код. Покрывает девять
  обязательных случаев AT-080 (опечатки, настоящий испанский, английский,
  смешанный текст, "ok", код, логи, цитаты на другом языке) плюс
  португальский, насыщенный английским жаргоном, встроенные идентификаторы
  и языки вне трёх (французский, итальянский, немецкий, галисийский,
  каталанский, нидерландский) — список языков открыт (AT-168, ответ 2).
- **Реальный** — сообщения самого пользователя в **локальном** event log.
  Никогда не попадает в git, в fixture, в лог CI или в тело PR.
  `extrair.ts` и `corpus.ts` отвергают любое место назначения внутри
  checkout, а файл записывается с правами 600 в
  `$XDG_CACHE_HOME/brabo/corpus-idioma/` (иначе `~/.cache/…`). Отчёт никогда
  не печатает текст элемента — только id, метки и счётчики, — поэтому его
  вывод можно вставить в PR.

То, что извлечение считает доказательством, следует очистке AT-080: только
события, актор которых — **пользователь** (ответ агента никогда не является
доказательством, поэтому испанский ответ модели не может подпитывать
определение), и в структурированной форме — только **ответы**:
склеенный `chat.message`, который api записывает сразу после, и чьи метки
— текст агента, пропускается.

Помощник разметки **не** подставляет заранее догадку эвристики: её
принятие нажатием ENTER привязало бы метку именно к тому, что метка
призвана измерять. ENTER принимает язык, который владелец объявляет через
`--padrao`.

Метки: код BCP-47 (`pt-BR`, `es`, `fr`…), `und` (решать нечего: "ok", только
код, только лог) или `mul` (смешанный, без доминирующего языка). Оценка:
`pt`/`es`/`en` должны получить свой язык; `und`, `mul` и любой другой язык
должны получить `indeterminado` — единственный правильный ответ, который
может дать им эвристика трёх языков. `indeterminado` на решаемом элементе —
это **упущенное покрытие** (известное предпочтение сохраняется); неверный
язык — это **ошибка**, а `falso es` считается отдельно, потому что это тот
дефект, ради устранения которого существует эпик.

## Как запускать {#running-it}

```bash
# synthetic corpus (the default)
pnpm --filter @brabo/scripts idioma:medir

# the owner's real corpus, on the owner's machine
pnpm --filter @brabo/scripts idioma:extrair --container brabo-dev-postgres-1
pnpm --filter @brabo/scripts idioma:rotular --padrao pt-BR
pnpm --filter @brabo/scripts idioma:medir --real
```

`--container` запускает `psql` внутри этого контейнера с единственным
`SELECT` только на чтение в `session_events` (`--usuario`/`--banco` по
умолчанию `brabo`/`brabo` из compose); `--database-url <url>` использует
вместо этого `psql` хоста. Повторный запуск извлечения сохраняет
существующие метки и добавляет новые сообщения без метки.

## Числа на синтетическом корпусе (2026-09-28) {#numbers-on-the-synthetic-corpus-2026-09-28}

123 размеченных элемента, 7 последовательностей, параметры-кандидаты AT-080
(минимум 20 слов, порог 0,8, отрыв 0,3, 10 сообщений / 2 000 символов,
гистерезис 2). Два списка маркеров: `at080` — список из спецификации,
дословно; `ampliada` — больший список, написанный этим инструментом **до**
запуска на корпусе (частые служебные слова, отсутствующие в двух других
языках). Корпус тот же, поэтому `ampliada` этими числами не подтверждается —
сказать может реальный корпус.

По сообщениям, параметры-кандидаты:

| метка | n | `at080` верно | `at080` не определено | `ampliada` верно | `ampliada` не определено |
|---|---|---|---|---|---|
| pt | 56 | 26 (46,4%) | 30 | 30 (53,6%) | 26 |
| es | 20 | 6 (30,0%) | 14 | 7 (35,0%) | 13 |
| en | 14 | 6 (42,9%) | 8 | 6 (42,9%) | 8 |
| und | 15 | 15 (100%) | 0 | 15 (100%) | 0 |
| mul | 5 | 5 (100%) | 0 | 5 (100%) | 0 |
| другие языки | 13 | 10 | 0 | 9 | 0 |

Вердикты с неверным языком: **ни одного на элементе `pt`/`es`/`en`** ни в
одном из списков. Все они на языках вне трёх — `at080`: французский → pt
(`ê` в *arrêté*), **галисийский → es** (единственный `falso es`),
нидерландский → en; `ampliada`: французский → es, немецкий → pt и → en,
нидерландский → en.

Очистка удалила больше половины слов у **нуля** решаемых элементов.

Семь синтетических последовательностей заканчиваются там, где ожидается, с
не более чем допустимым числом переключений, в обоих списках — включая
португальский с длинной цитатой на испанском, целое сообщение на испанском
посреди португальского и португальский, плотно насыщенный английским
жаргоном.

CPU на этой машине: `at080` 11,7 мкс на сообщение и 49 мкс на оценку выборки
из 10 сообщений; `ampliada` 16,8 мкс и 60 мкс. Зависит от машины; важен
порядок величины.

## Что говорят числа {#what-the-numbers-say}

- **Со списком `at080` порог и отрыв никогда не срабатывают.** 66 из 67
  элементов, которые хоть что-то набирают, набирают для одного языка
  (уверенность = 1,0), поэтому перебор порога от 0,5 до 1,0 ничего не
  меняет. Минимум слов — единственная действующая ручка: по сообщениям
  решаемые элементы приходят к своему языку в 42,2% случаев при 20 словах,
  58,9% при 10 и 66,7% без минимума — при 20 он выбрасывает каждое короткое
  сообщение с опечатками и большую часть технических.
- **Снятие минимума позволяет решать смешанному тексту.** Без минимума
  `at080` превращает три из пяти смешанных сообщений в `en` или `pt`, а
  `ampliada` также решает два элемента `und` как `en` — код без ограждения
  (`const total = itens.reduce(…)`) и вывод pnpm
  (`ELIFECYCLE  Test failed. See above for more details.`) проходят через
  очистку, которая знает только огороженный код и форматы логов,
  перечисленные в AT-080.
- **Отрыв 0,3 избыточен при пороге 0,8** в любом списке: при трёх языках
  победитель с ≥ 0,8 оказывается минимум на 0,6 выше второго.
- **Значимая единица — выборка, а не сообщение**: в последовательностях окно
  из 10 сообщений приходит к языку с сообщениями, которые по отдельности
  были бы `indeterminado`. Единственное испанское сообщение в португальском
  окне делает выборку `indeterminado`, пока оно находится в окне
  (последовательность `q03`): ни переключения, но и ни подтверждения.
- **Ошибки — в открытом списке языков.** При трёх языках пользователь,
  пишущий по-галисийски или по-французски, может услышать, что пишет
  по-испански или по-португальски. По правилу AT-168 определение лишь
  *спрашивает*, а пользователь подтверждает, поэтому цена — неверный
  вопрос, но это всё равно единственный режим отказа эвристики здесь.

Это синтетические числа: корпус написан той же рукой, что и эвристика.
Пороги AT-163 должны были бы прийти из реального корпуса.

## Предварительные пороги продукта {#the-products-provisional-thresholds}

AT-163 должна была выйти с *каким-то* числом до появления реального
корпуса, поэтому api читает `PARAMETROS_PROVISORIOS` — **предварительные, не
откалиброванные** и так и объявленные в [RN-624](../business-rules.md#rn-624):

| параметр | предварительный | кандидат AT-080 | почему |
|---|---|---|---|
| список маркеров | `at080` | — | `ampliada` выигрывает 4 пункта в pt и дважды ошибается на немецком; ни один из двух не подтверждён реальными данными |
| минимум слов (по выборке) | **10** | 20 | покрытие решаемых элементов 42,2% → 58,9% при **тех же** трёх неверных вердиктах (французский, галисийский, нидерландский — языки вне трёх); ниже 10 начинает решать смешанный текст |
| порог / отрыв | 0,8 / 0,3 | 0,8 / 0,3 | на синтетическом корпусе никогда не срабатывают, поэтому выбрать лучшее число пока не из чего |
| выборка | 10 сообщений / 2 000 символов | то же | — |
| гистерезис | 2 | 2 | — |

Гистерезис **пересчитывается, но никогда не хранится**: api читает последние
11 доказательств и проверяет, согласны ли две последние оценки выборки. CPU
на этой машине, синтетический корпус: 11,6 мкс на очистку и
классификацию сообщения, 110 мкс на определение (11 сообщений, две
оценки). Чтение обслуживается частичным индексом в `session_events`:
0,056 мс против 13,5 мс последовательного сканирования, измерено на 200 000
событий.

Для перекалибровки: запустите реальный корпус (`idioma:medir --real`), а
затем измените `PARAMETROS_PROVISORIOS` в api — это единственное место,
откуда продукт их читает, и инструмент импортирует тот же файл (его отчёт
продолжает перебирать кандидатов AT-080).

## Платная проверка языковой ориентации (AT-167, 2026-09-29) {#paid-validation-of-the-language-orientation-at-167-2026-09-29}

> Протокол — из AT-082, с решениями AT-169: бюджет US$ 5, 5 прогонов на
> случай и ветвь, порог приёмки «в обработанной ветви **ноль** испанских
> ответов там, где ожидается pt-BR, и правильный язык **≥ 95%** в C01–C04 и
> C06–C15», тестируемая модель `deepseek/deepseek-v4.1-flash`, модель
> сравнения `anthropic/claude-haiku-4.5`, потолок дополнительной стоимости
> 50 входных токенов на вызов. Код в `d48f99f8e` (`dev` от 2026-09-29).

### Где запускается и что является (и что не является) продуктом {#where-it-runs-and-what-is-and-is-not-the-product}

Скрипт вне продукта, `scripts/idioma/validar.ts` (чистая часть — матрица,
оценка, отчёт — в `validacao.ts`, протестированная `validacao.spec.ts`). Он
вызывает OpenRouter **напрямую** и ничего не пишет в базу. То, что продукт
отправляет модели, **читается из файлов продукта при каждом запуске**,
никогда не копируется — чтение выбрасывает исключение, называя то, чего не
нашло, если файл изменит форму:

- ориентация (RN-622/623): `@textos`, общая фраза, оговорка об артефакте,
  `@forma_curta` и `@ferramentas_de_artefato` из
  `apps/engine/lib/engine/harness/idioma_da_resposta.ex`, отправляемая как
  ПОСЛЕДНЕЕ сообщение, `role: "system"`, в каждом вызове обработанного хода
  (включая итерации инструментов) и никогда не сохраняемая в истории;
- промпт резюме и его фраза о языке (RN-621) из
  `apps/engine/lib/engine/harness/context_manager.ex`;
- персона Criativo (`CRIATIVO_INSTRUCTIONS`), два его инструмента с
  настоящими описаниями и результаты инструментов, которые возвращает
  продукт.

Заявленные отличия от продукта: system prompt — только персона (без слоёв
`ContextBuilder`); сжатие **принудительное** перед пятым ходом C04 (с
сохранением двух последних сообщений, `keep_recent` продукта), с
тестируемой моделью в роли резюмирующей; возобновление (C15) — история,
восстановленная как текст, в форме `Engine.Agents.Reidratacao`; не более 4
вызовов модели за ход (Criativo допускает 12); и `max_tokens` ограничен 4000
(продукт его не передаёт). Upstream-провайдер **не** был зафиксирован —
записан по каждому вызову как смешивающий фактор. Baseline = код до
RN-621/622: без ориентации **и** со старым промптом резюме (AT-169, ответ
4: проверка измеряет совокупность, отдельного baseline для старого
резюме нет).

Разрешённый язык автора каждого сообщения — часть случая: `pt-BR` для Ana
(C01–C05, C07–C11, C13–C15), `en` для Bob (C06 как определённый и
подтверждённый `en`, C12 как явное предпочтение `en` при письме
по-португальски); язык проекта `pt-BR`. C05 ожидает **pt-BR**: по ответу 4
AT-168 определение лишь *спрашивает*, поэтому разрешённый язык автора
остаётся pt-BR до подтверждения.

Первый запуск нулевого шага с `max_tokens` 1000 был **отброшен**:
рассуждения DeepSeek израсходовали весь потолок в 7 вызовах, и ответ
вернулся пустым (два резюме превратились в запасной текст продукта). Его
записи лежат отдельно в папке вывода; пустой ответ теперь считается
`falha`, а не `indeterminado`.

### Нулевой шаг: не воспроизведено {#step-zero-not-reproduced}

Только baseline, `deepseek/deepseek-v4.1-flash`, C01–C04, 5 прогонов: **0
испанских ответов из 35 оценённых** (35 pt, 0 неопределённых). Сообщение от
13.09 (испанский в ответ на португальский ввод) **не воспроизведено**,
поэтому никакое улучшение *именно этого* дефекта нельзя приписать
обработке. Запуск продолжился, потому что порог AT-169 абсолютен в
обработанной ветви, а остальные случаи (C05, C06, C12, C16, C17)
действительно показывают, что baseline отвечает на неверном языке.

### Против порога {#against-the-threshold}

### Дополнительная стоимость ориентации {#incremental-cost-of-the-orientation}

Парные `prompt_tokens` **первого** вызова каждого диалога (вход идентичен в
обеих ветвях, кроме ориентации), взятые из `usage` OpenRouter, никогда не
оценённые:

| модель | ориентация | пар | Δ входных токенов |
|---|---|---|---|
| DeepSeek | pt-BR (108 символов) | 75 | 32 (каждая пара) |
| DeepSeek | en + оговорка об артефакте (128 символов) | 15 | 27 |
| Haiku | pt-BR | 75 | 30 |
| Haiku | en + оговорка об артефакте | 15 | 27 |

Всё ниже потолка в 50 токенов. По входной цене каталога это около
US$ 0,0000096 за вызов у DeepSeek и US$ 0,00003 у Haiku — верхняя граница,
поскольку DeepSeek обслужил большую часть входа из кеша (кешированные
токены возвращаются; стоимость вызова с кешем находится внутри
`usage.cost`, не разделённая по сообщениям). Ориентация идёт в каждом
вызове хода, поэтому ход с итерациями инструментов оплачивает её по разу
на итерацию.

Классификатор ни разу не назвал верным неверный ответ и неверным — верный;

- Поэтому решение по C11 важно только при принятой форме. Если форма
  засчитана как сбой, DeepSeek не проходит при любом C11, и находка, на
  которую нужно реагировать, — не C11, а форма: в обработанной ветви 8 из
  15 ответов C06+C12 у DeepSeek несут португальский текст внутри
  английского ответа (6 только в форме, 2 вперемешку), а 7 — чистый
  английский, включая формы. Модель способна написать форму
  по-английски — делает это примерно в половине случаев.
  **Откуда это взялось (AT-282, [RN-667](../business-rules.md#rn-667)):**
  само описание инструмента говорило модели, что `label` — это «текст
  вопроса, **em pt-BR**», — вторая языковая инструкция, фиксированная, вне
  фасада, конкурирующая с ориентацией в конце в каждом вызове. Теперь оно
  гласит «no idioma da sua resposta» и не называет язык; сама ориентация не
  изменилась. Измерение «после» **не запускалось** (не было ключа
  OpenRouter на машине, где делалось изменение) и ожидает владельца — C06 и
  C12, обработанная ветвь, 5 прогонов, с потолком бюджета из RN.

Что такое C11 в данных. 5 обработанных отказов DeepSeek: у 3 перевод на

### Часть B — дело в позиции ориентации? (AT-279) {#part-b--is-it-the-position-of-the-orientation-at-279}

Гипотеза: для моделей Anthropic OpenRouter поднимает сообщение `system` из
конца в верхний system prompt, теряя его новизну. Проверка: C12
(предпочтение автора `en`, сообщения на pt-BR), `anthropic/claude-haiku-4.5`,
первый ход, 5 прогонов на позицию, текст ориентации **прочитан из
продукта** (он был `Respond in English (en), unless the user explicitly asks for another language
in this message. Write project artifacts in pt-BR.`), меняется только
позиция:

1. `ultima-system` — как сегодня (`idioma_da_resposta.ex:231`, `role: "system"`
   в конце);
2. `system-fundido` — дописана к первому `system` (персона + ориентация);
3. `sufixo-user` — суффикс последнего сообщения `user`, **без** добавленного
   `system`;
4. `ultima-system-e-sufixo-user` — `system` в конце **плюс** та же фраза как
   суффикс.

| позиция | попаданий классификатора | прочтение |
|---|---|---|
| 1 `ultima-system` (как сегодня) | 0/5 | 5 на португальском, включая формы |
| 2 `system-fundido` | 0/5 | 5 на португальском |
| 3 `sufixo-user` | 0/5 | 5 на португальском |
| 4 `ultima-system-e-sufixo-user` | 0/5 | 5 на португальском |
| контроль: 1, без оговорки об артефакте | 0/5 | 5 на португальском |
| контроль: 3, без оговорки об артефакте | 0/5 | 5 на португальском |

Четыре позиции прочитаны целиком, два контроля — частично, и все 30
ответов также проверены на служебные слова английского (ни одного ни в
одном): все 30 — на португальском, проза и форма. Дефект позиции 1
**воспроизведён** (0/5, как 0/10 платного запуска), и **ни одна позиция его
не исправляет** — даже та, где ориентация находится внутри самого
последнего сообщения пользователя и `system` в конце нет. Гипотеза **не
подтверждается**. Подсчёты токенов промпта показывают, что текст дошёл до
модели в каждой позиции (2 426, 2 427, 2 427 и 2 454 входных токена: +1 для
двух простых размещений и +28 для двойного), так что сообщение не
отбрасывается. Контроль исключает и вторую подозрительную фразу: оговорка
об артефакте ("Write project artifacts in pt-BR.", RN-623) тоже не причина
(0/10 без неё).

Чего это не исключает и что не измерялось: второй ход (запускался только
первый, из-за бюджета — в платном запуске второй ход тоже был неверен 5/5);
более сильная формулировка (фраза гласит "unless the user explicitly asks",
и португальский ввод можно так прочитать); язык самой персоны
(`CRIATIVO_INSTRUCTIONS` — на португальском); и upstream (все 30 вызовов
обслужил Amazon Bedrock, поэтому эффект upstream отделить нельзя). DeepSeek
следует той же ориентации в том же случае — его обработанные ответы C12
были прозой на английском в 8 из 10, — что указывает на модель, а не на
размещение.

**Предлагаемое изменение: никакого по позиции.** Единственное место, где
позиция была бы изменена, если бы это помогло, —
`Engine.Harness.IdiomaDaResposta.anexar/4`
(`apps/engine/lib/engine/harness/idioma_da_resposta.ex:231`, `messages ++
[%{"role" => "system", …}]`), вызываемое обоими путями `llm_turn` в
`apps/engine/lib/engine/sessions/engine_api_client.ex:609` и `:661`. Оно
остаётся как есть. Следующая работа, если владелец хочет, чтобы Haiku
подчинялся `en` при португальском вводе, — проверить формулировку и язык
персоны (список выше) этим же скриптом.

**Расходы** (сумма `usage.cost` каждого ответа, никогда не счётчик `/key`):
US$ 0,0980 на четыре позиции (20 вызовов) и US$ 0,0505 на два контроля (10
вызовов) — **US$ 0,1485** из потолка US$ 0,20, 30 вызовов, ни один не упал.
