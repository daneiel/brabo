阶段历史

Brabo 已完成阶段的不可变记录，于 2026-08-23 从 CLAUDE.md 原样移出，未作改写。产品当前的状态位于 CLAUDE.md、RN（docs/business-rules.md）和 ADR 中——本文件回答的是“如何走到这里”，从不回答“今天什么有效”。已接受的 ADR 从不编辑；本文中记录的 ADR 更正在其所在位置依然有效。

状态​

  • 第 1 阶段（MVP）——已完成：IAM/RBAC、带不可变 event log 的会话、带 LLM 路由器的聊天（Ollama + API）、token 的计量/预算、proposed_actions 管道 + permissions.json、带监督和终止事件的 Elixir/OTP 引擎。
  • 第 2 阶段——已完成：带契约测试套件和 capabilities 的 GitProvider（Local/GitHub/GitLab）、加密凭据、通过管道实现的幂等且可恢复的 Gitflow bootstrap、带实时进度的向导。
  • 第 3 阶段——已完成：Harness（PromptAssembler、ToolLoop、ContextManager、InstructionFiles、Hooks）、显式 handoff、带产物和领域校验的 Criativo、PO 和 Arquiteto agent。
  • 第 4 阶段——已完成：执行型 agent（在隔离 worktree 中按模块动态生成的 dev、作为 PR gate 的 QA 和 SecOps、提议式的 Infra）、受保护的合并锁、实时团队面板；真正的 Psicólogo 和闭环的 Anamnese。gate 经真实执行验证（ADR 0020）。
  • 第 5 阶段——已完成：非 root 生产镜像和 CI（ADR 0024），带 Kustomize 的 Kubernetes、按 Oban 队列的 HPA、NetworkPolicy 和 ESO（ADR 0025），graceful shutdown + OpenTelemetry + 仪表盘（ADR 0026），经测试可恢复的备份、运维手册和加固（ADR 0027）。
  • DOC 阶段——已完成：docs/ 作为采用 Diátaxis 的唯一来源，website/ 中读取 docs/ 的 Docusaurus 站点，生成的参考文档，docs/.docmap.yml + CI 中的漂移检查（docs:check），社区层，已核实的 MIT，机制记录在 docs/explanation/documentation-workflow.md 中。
  • 第 6 阶段——已完成：机械化的分支策略（ADR 0030）——pr-police、带两种模式的 approval-ladder、带计算版本和按目录树锚定的 promote/tag-release、带自动反向传播的 backmerge gate、版本化的 ruleset。流水线端到端演练（v0.1.0 → v0.2.0），hotfix 链路经真实执行验证。
  • 第 7 阶段——已完成：取代 Keycloak 的 first-party auth——argon2id、Ed25519 access、带家族吊销的 refresh 轮换、渐进式 lockout、账号 token 和仅记日志的 MailSender（ADR 0031，RN-030..033）；以自有签发者进行原子切换，RBAC 不变，/internal/* 使用 service token，httpOnly cookie + CSRF，用户迁移并彻底移除 Keycloak（ADR 0032，RN-034/035）；23 个 controller 上的 OpenAPI，DTO 按类型锁定，表格测试要求元数据，生成带哈希清单的 docs/reference/api/（ADR 0033）。
  • 第 8 阶段——带裁剪地完成：agent 层级——以唯一 lead 作为对外联系人的领域、私有的内部委派（delegations 表，area 为 TEXT）、可追溯的合并结论、带来源的失败；QA 作为领域（Lead + 自动化 + 性能/安全，gate 的外部契约不变——第 4 阶段的测试套件无需修改即为绿色）；Infra 作为领域，带有按 provider 生成 CI 的 Workflows 子 agent；按领域划分的团队面板，以及以子 agent 为目标的 Psicólogo/Anamnese（ADR 0038）。 当时的范围裁剪，已被第 14d 阶段撤销： agent_areas/agent_area_members 自那以后按项目存在，max_parallel 可配置——迫使这一点的是 dev 领域，第一个动态领域。仍被裁剪的只有按领域的预算（真正的预算上限仍然是项目、会话和任务）。 apps/web/src/lib/agents.ts 中的列表保留了颜色、图标和寻址规则；dev 的成员来自表。
  • 第 9 阶段——已完成：针对现有 provider 运行的 LLMProvider 契约测试套件，基于 node:http、带空闲超时的 OpenAICompatibleProvider 基础，按 code 规范化的错误，两层 capabilities（ADR 0041）；目录同步——新发现的模型以禁用状态进入，消失的模型被标记而不是删除，价格冻结在 token_usage 中并带有仅追加的审计（ADR 0042）；按来源重新分组并带策展的 ModelPicker。 第 9b 的六个 provider 由第 11 阶段引入（ADR 0043）。

  • 第 11 阶段——已完成：第 9b 阶段的六个 provider 作为基础之上的配置，每个都对照官方文档从零调研（禁止继承怪癖）；LLM_PROVIDER_NAMES 从 3 个增加到 9 个；凭据 DTO 和连接测试器派生自单一列表；capability 只在经证明时才声明，现场有两次回退（DeepInfra 和 Vultr）；基础中唯一的新 hook（parseErrorFrame，+31 行）由 OpenRouter 证明为必要（ADR 0043）。 使用真实凭据的 smoke 待办：由第 13 阶段吸收。
  • 第 12 阶段——已完成：dogfooding 之后的可运维性，三个 P1 发现在一次执行中关闭并证明（ADR 0047）。 12a——采纳已有仓库：独立路由、getRepo 在写入前校验访问权限、两张表中的 origin（created|adopted），以及作为闸门的计划——描述差异、在决定为空期间不做任何更改的 dry-run；重新采纳会收敛（ADR 0044，RN-045/046）。 12b——按事件重新调度 dev agent：持久化的状态机（working|awaiting_gate|idle|idle_tripped）对现有 outbox 的两个事件作出反应，awaiting_gate 保留 worktree（它是按 agent 而不是按任务的）直到 gate 结束，并带有显式 rearm 的断路器（ADR 0045，RN-047）。 12c——以用户权威推进故事：按项目的 story_promotion，以 manual 作为新的默认值（定向回填把已有项目设为 auto），proposed_ready 作为提议而非状态，推进复用 TransitionStoryUseCase（发现 #13 的死代码），拒绝会把原因固定在 PO 的会话中退回给他（ADR 0046，RN-048）。 12d——Noop 进入了 12b 的状态机；脚本 pnpm --filter api validacao:fase-12 在标准不满足时以非 0 退出，并从数据库提取证据；第 10 阶段的收获已写成；docmap 覆盖 engine/dev 和 engine/agents。 待办（执行验证；声明的 Local/Noop 限制）：由第 13 阶段吸收。

途中关闭了七个 P1，全部由执行而非测试发现：W（队列为空时 dev agent 会死掉）、Y（搜索无法区分为空与未找到）、AA（git 凭据由点击者而不是付费者解析——RN-082）、AB（gate 把待决事项称作基础设施失败——ADR 0057）、AC（重定向让任何命令都无法批准）、路径范围中的 ReDoS（CodeQL HIGH），以及 postgrex 的 CVE。

14d——完成：并行度由 LEAD 决定，由你授权​

分四个 PR 交付（#181、#182、#183、#184）。ADR 0053 变为已接受，彻底撤销了三项裁剪（Dev Lead、通过 module_map 的动态领域，以及通用的领域机制）。

  1. 领域变成了数据：按项目的 agent_areas/agent_area_members，max_parallel 默认 2。迫使这一点的是 dev 领域——第一个动态领域，其成员是 module_map 中每个模块各一个。无法在代码中枚举的东西必须是数据。
  2. 上限属于会话，而不属于模块（RN-083）。按模块计数会允许 N 个模块 × 2 而无需任何授权——换了个名字的旧漏洞。超过上限就变成 proposed_action。
  3. 可在配置中按领域配置，需要 maintainer，理由与激活执行相同：修改上限就是在不询问的情况下决定产品花多少钱。
  4. 当授权变成例行公事时，Anamnese 会提议调高——三次批准且没有拒绝（RN-086）。一次拒绝就会撤销这个信号：如果你曾经拒绝过，说明上限在发挥作用。
  5. Dev Lead 存在了（RN-087），对话型，在已经交付给 Infra 的同一次确认中接收 Arquiteto 的 handoff，并提出计划：每个模块几个 agent 以及原因。dev-<modulo> 不再能通过 handoff 寻址——ADR 0038 的规则开始对 dev 生效，就像它早已对 QA 和 Infra 生效一样。

发现 X 在这里关闭（RN-085）：TOOL_LOOP_MAX_ITERATIONS 变成了按类型的上限——对话型 8，执行和 gate 60。谁能调高的标准不是“谁干得多”：而是谁底下有 token_budget_micros 在控制花费。infra-workflows 使用重型工具却保持在 8，因为它在没有预算的情况下运行。

该阶段自身的三个缺口，是我在写下一个切片时发现的，而且全是同一种失败：上限规则带着绿色测试合入，但产品并不演练它——没有任何路由调用该用例，批准动作并不执行任何东西，而该类型可以被 permissions.json 自动批准（由 RN-086 关闭）。测试零件不等于测试通往它的路径。

按声明的决定不在范围内（ADR 0053 第 5 项）：“Ativar execução”按钮更换所有者。同一项也声明过的、经由 delegations 表以 area = "dev" 进行的 Dev Lead → dev-<modulo> 委派，已不再超出范围——由 ADR 0094 关闭（fluxo.yml × 代码审计，第 2 波，RN-405）。按钮仍可撤销；执行仍走当前路径，gate 之后的修正仍直接交给打开 PR 的 dev。

三条耗费了 CI 周期、值得作为规则的运维教训：

  1. PR 上的 CodeQL 绿色不能证明旧告警已关闭——PR 检查报告的是新告警。告警在默认分支的扫描中关闭，也就是说，只有在修复到达 main 之后。

  3. 位于另一个函数中的屏障，CodeQL 看不到——这就是三个 js/path-injection 在修复后仍然存在的原因。保留了集中检查（RN-092），在面板上付出代价：在每个调用方重复它，就会成为某天出现分歧的检查。

这一轮教会我们的、比清单更有价值的东西：最大的修复（RN-155）对任何测试套件都不可见，因为缺陷在于比较两个不同的数值空间，而它们碰巧都是 number——event.seq（无间隙，按会话）与 action.seq （proposed_actions.seq，整张表的全局 bigserial，由系统中每个项目和每个会话共享，并在 schema 中被记录为有意的对照）。只有在表还小时，顺序才看起来是对的。修复没有发明新字段：它使用了 ProposeActionUseCase 已经在同一个事务中写入的 proposed_action.created 事件，其 payload.actionId 指回该动作。

能读懂的会话消息流（RN-155..159）——排序（见上）；5s 指示器使用固定文本 "Reunindo informações..." 而不是插入 agent 名称，后者已出现在标题中（RN-156）；PO 创建史诗/故事变成紧凑提示，而不是与真正回复同等视觉权重的气泡（RN-157）；聊天中带高亮的轻量 Markdown，用自有正则解析器，零新依赖、没有 dangerouslySetInnerHTML，并且只渲染 agent 的输出——人输入的内容保持字面（RN-158）；以及按 agent 分组、使用 RN-138 的 Disclosure 的“Artefatos gerados”，每个产物都导航到它所在的位置（RN-159）。module_map/C4 按已记录的决定被排除：它是项目的当前状态，而不是按会话标注日期的产物。

exp001 轮次——PO 读取已有内容并被督促（RN-164..166）​

这不是阶段：这是真实使用发现的缺陷，来源很重要，因为任何测试套件都抓不到。backlog 产出了史诗而没有任何故事——因此没有任务，因此执行被卡住而没有任何错误。调查发现四个叠加的原因，前三个其实是同一个：PO 没有办法知道，也没有办法提醒。

  1. PO 有四个工具，全部是写入工具。 上下文只在 kickoff 时组装一次，取自会话最近的 200 个事件——此后它再也不重新读取任何东西：它不知道存在哪些规则、已覆盖了哪些，甚至不知道自己已经创建了什么。加入了 listar_regras_de_negocio 和 listar_backlog（RN-164），由两个限定在项目范围的内部路由提供——范围正是要点：按会话读取恰恰是之前隐藏已捕获规则的原因。它们复用已有的管道（listByTypeForProject、ListBacklogUseCase、 computeCoverage）；缺的是路由、客户端中的方法和工具。
  2. 史诗之后没有任何东西督促故事，并且循环沉默地结束。没有故事的史诗变成了显式结果——backlog.epic_without_story，持久化，遵循 RN-059 的模式（RN-165）——PoServer 的迭代上限开始发出 toolloop.limit_reached，与 ToolLoop 相同的类型，而对话型 agent 因为有自己的循环从未发出过它（RN-166）。
  3. kickoff 指令对信息缺失时该怎么做只字未提——面对没有指令的缺口，模型只能在编造和停止之间选择。它选择了停止。第三条出路被写了下来，并附上行使它的工具：ask_structured_questions，与 Criativo 相同（RN-162），现在也提示给了 PO。

两个超出本案例价值的设计决定：只有成功的 create_story 才能清偿史诗的义务（被 api 拒绝的故事什么也没覆盖，把它当作覆盖了就是用一种沉默替换另一种）；督促按发生次数进行，只报告一次，从不是每个回合都重复、直到有人学会忽略它的告警。

exp001 轮次——消息流按回合发生的方式阅读（RN-172/173）​

与其他轮次相同的来源：使用，而不是脚本。关于会话界面的四条抱怨——PO 的 handoff 出现在他最后一句话的上方，审批跳到 Arquiteto 回复的中间、直到他说完才落下来，审批卡片“排版糟糕”，以及滚动不跟随对话。

调查发现排序是正确的，这就是这一轮的教训。RN-155 忠实于 event log；日志说的是 po_server.ex#run_turn/2 在同一次迭代中先发出 agent.response，然后是 offer_handoff 的 tool.call，之后才递归进入收尾发言——因此 handoff 的 seq 确实小于最后一句话的。proposed_action.created 也一样。所以修复不在排序：它是一条声明的呈现规则（RN-172），在按 seq 的 sort 之后的单独一遍中（afundarDesfechos）——而不是一个一年后没人能解释的三项比较器。

防止回合相互混合的是三道屏障，每一道都源于一个真实案例：回合（两个回合之间的边界可能没有可见的条目——agent.activated 打开回合，但不会成为消息流中的条目）、作者（在执行会话中，多个 agent 在用户一次都没说话的情况下写入，它们都处于同一个回合）以及非结果（两个连续的结果保持彼此之间的顺序——Infra 先于 Dev Lead）。

exp001 轮次——消息流说明谁在说话、用哪个模型、问的是什么（RN-171/174/175/176）​

exp001 轮次——面板会分组、排序，并说明它没有显示什么（RN-177..181）​

与其他轮次相同的来源：使用，而不是脚本。关于会话的上下文面板和日志的五条抱怨，这一轮的教训只有一个——面板把一个切片当作全部来显示，而且同时在三个不同维度上：它隐藏了六种事件类型却不提供替代方式，按从旧到新的顺序阅读，并且在没有说明的情况下把会话截断在 200 个事件。

来源作为新的分类（RN-177）。 ActivityKind 回答“事件谈论的是什么主题”，决定图标和颜色；origem 回答“它来自哪一层”，正是它让历史可读——eventos、sistema、llm、 harness、agente、usuario，派生自存在的数据（actor.kind 和 type 的前缀）。优先级让它可预测，体现在 if 的顺序中：机制胜过行动者（一个 tool.call 属于 harness，不管是谁），行动者胜过 agent 前缀（chat.message 在两边都存在）。最近的 5 个保持展开，其余按来源折叠，在两个地方都是如此——日志面板和消息流，在消息流中轴是反向的（消息流是升序的，所以历史在顶部）。机器噪声过滤器仍然默认开启：它的理由没有变（193 个真实事件中有 116 个），变化的是它成了一种选择，而不是既成事实。

顺序和分页（RN-178）。 四个部分都改为降序，“Carregar mais antigos”按钮也因此换到另一边——还是之前的论证，只是符号反了过来。超过 5 条的业务规则会分页，页码通过 clamp 而不是同步副作用来解析。

PO 的树（RN-179）。 backlog.task_created 从未进入面板；现在史诗 → 故事 → 任务形成一棵树，依据事件本身已携带的关联（epicId/storyId），从不依据日志中的邻近关系——父节点未加载的节点会上升到根部，而不是靠猜测挂上去。

开始显现的上限（RN-180），这是最有价值的一项。 面板通过 prop 读取 200 个事件，无法说明还有更多。它改为读取 RN-099 的分页历史（与尾部相同的 queryKey，零额外请求——RN-090/091），获得了 ActivityFeed 一直都有、但没有任何调用点传入的分页器，注释通过对 seq 做减法统计还缺多少，就像 RN-100 的铃铛一样。派生部分读取 baixados（已经到达的全部内容），而不是动态的窗口，否则它们会显示得比之前更少。

28 计划——第 1 波，A 前线：主题不再无法访问（RN-182..185）​

28 计划——第 5 波，I 前线：社交登录撤销 ADR 0031 backlog 的禁令（RN-272..283，ADR 0084）​

产品所有者的明确请求，清楚其安全后果——禁令只对 GitHub/GitLab 解除；MFA、OIDC provider 和通用联合仍不在范围内（参见“O que NÃO fazer”）。 SocialLoginCallbackUseCase 最终落到与密码登录相同的 EmitirSessaoUseCase——没有第二种会话格式。它复用现有的 OAuth 客户端，但 state 有自己的用途 （purpose: 'social_login'，在任何其他字段之前检查）：从不接受把 git 连接到项目这一连接流程的 state，那会是权限提升。新表 social_identities（migration 0047），键为 (provider, provider_user_id)——从不是电子邮件/登录名。三步决策：已知身份 → 登录；电子邮件与现有账号匹配并且已由 provider 验证 → 关联（如果账号的电子邮件尚未验证，则一并验证）；电子邮件匹配但未验证 → 拒绝——输入的电子邮件不是所有权的证明，接受它会打开账号接管的口子；没有对应账号 → 置备一个没有密码的新账号，与 Keycloak 迁移时相同的“待定”状态。复用 git 连接的同一个 OAuth 应用——零新环境变量，只是每个流程的 redirect_uri/scope 不同；操作者需要在 provider 中登记第二个回调，这一动作正是 breaking/ 分支的理由。

analytics/delivery-metricas 变成报告（RN-320..322，ADR 0089）​

它基于 dev agent 三个 git 动作（git_commit/pr_open/git_merge，只取 status: 'executed'）的 proposed_actions.execution_result 真正测量：真实漏斗（多少会话产生了提交 / 打开了 PR / 合并了 PR，以及各阶段之间的转化——计数的是会话，不是动作）、真实的前置时间（会话从第一次提交到第一次合并，依据执行的 updated_at，而不是提议的）以及真实的部署频率（合并到 PROTECTED_BRANCHES 分支，按天，通过引用与 docs/gates.yml 的 backmerge gate 交叉——后者的证据是 CI，超出了只读数据库的脚本的能力范围）。

secops-runtime 作为报告脚本（RN-375..377，ADR 0091）​

产品所有者决定提前引入 secops-runtime 角色 （docs/fluxo.yml，camada_seguranca，之前为 proposto），而不等待声明的触发器（“有真实流量的生产，在 DEPLOY_ENABLED + platform 激活之后”）。只有触发器不需要的部分进入：pnpm --filter api relatorio:seguranca-runtime 读取 rate_limit_hits——ADR 0027 的 RateLimitGuard 已经在写入的数据，包括在 dev/CI 流量下——并生成桶的排行（user:<uuid>/ip:<endereço>，仅有的两种记录格式；没有路由也没有原因，表从未保存过它们）以及固定时间片的时间分布。它是脚本，不是 LLM agent 也不是 GenServer：对数据没有要做的决定，只有聚合。

自动事件检测、事件响应和安全事后复盘仍然排除在外——它们依赖同一个未触发的触发器——报告把它们列在一个永久的“não medido”一节中，不模拟示例事件，也不编造数字（与 ADR 0041/0042/0077 相同的原则）。保留的窗口按设计很短 （DomainGaugesCollector.pruneRateLimit 删除早于 2 × RATE_LIMIT_WINDOW_MS 的命中，默认 240s），报告声明两个窗口——配置的和观察到的——从不让后者冒充比实际更长的历史。

platform 获得第一个交付：按需遥测报告（RN-385/386，ADR 0092）​

产品所有者有意识地提前引入 platform 角色的一部分 （docs/fluxo.yml，camada_plataforma）——其 status 仍为 planned，其 ativacao 仍与不存在的 DEPLOY_ENABLED 同步。 pnpm --filter api relatorio:telemetria [--projeto <uuid>] [--json] 是一个脚本（不是 LLM agent，不是 GenServer），按需读取 DomainGaugesCollector 已经为 Prometheus 抓取所收集的相同问题——按项目的活跃/closing 会话、按项目被阻塞的任务、最后一次备份的状态（总是全局的，从不按项目，因为产品备份的是整个数据库）——打印后即结束。SQL 查询是复制的，而不是从采集器导入的：采集器的方法是私有的，并且以写入 Prometheus gauge 结束，没有可以复用的纯“只查询”的一半，复用会把 CLI 脚本耦合到一个 @Injectable 的生命周期上。

本地 runner——在用户机器上执行（RN-418/419/420，ADR 0102/0103）​

产品所有者的请求：agent 在用户的机器上、在项目的本地目录中、通过用户的默认终端运行——外加 Code 标签页中真正的交互式终端。两项变更，一项依赖另一项。

策略（ADR 0102——全局决定，在一条关于该变更的自动安全警告之后，由产品所有者明确确认）： git push/PR/部署（RN-106）和 sudo/doas（新增）从无条件的 deny 变为绝对上限——无条件的 require_approval，与相邻上限位于同一区块、采用相同模式（current.policy === 'auto_approve'），永远不能被 agent_autonomy（通配符 "*"）或 permissions.json 自动批准。原先的 deny 强行堵住的缝隙在源头被关闭：ApproveAlwaysActionUseCase/patternForAction 拒绝为带 git 外部效果或特权命令的动作在 allow 中写入模式——对于这两种情况，“sempre permitir”只批准该实例，从不批准模式。没有这另一半，上限就只是装饰。sudo/doas 在 comandoPrivilegiadoNoComando （external-effect.ts）中按动词匹配，扫描命令的所有段，与 efeitoExternoNoComando 原则相同。

Runner（apps/runner，新的 Node/TS workspace，ADR 0103）：用户在自己机器上运行的 CLI （brabo-runner --project <id> --dir <pasta> --token brb_...），通过新的 Phoenix 通道连接到 ENGINE （/runner， 主题 terminal:<projectId>），由一次性ticket 认证（与 RN-108 模式相同，但 ticket 由 ENGINE 签发——schema "engine"，有自己的 migration——由 api 通过内部 HTTP 路由请求，与会话 ticket 的流程相反）。它在用户的 $SHELL 中执行 exec（已经批准的 agent 命令——TerminalExecutor 中的路由只在一贯的 decide()/proposed_action 管道之后发生，从不在之前），并为终端标签页提供交互式 PTY 模式（pty_open/pty_data/ pty_input/pty_resize/pty_close——engine 做纯粹的中继，从不解释字节）。每个项目只有一个 runner（Engine.Runners.Registry、 :global，:global.register_name/3 的排他性）；runner 模式在没有已验证的 workspace 或没有已连接的 runner 时会显式拒绝——从不退回到 System.cmd/bind-mount，对 runner 项目来说那并不存在 （由 ADR 0104/RN-423 修订，见上文；退回到一贯路径的行为仍然有效，但只针对 container/mounted）。PTY 是已认证用户的动作，不经过 proposed_action，但会被审计（event log 中的 terminal.session.started/ended，包括标签页在没有显式 pty_close 的情况下掉线时）。

runner 的安全边界不是沙箱——而是认证（CLI 出示用户账号的 Personal Access Token）+ 一贯的审批管道 + 用户同意以自己的权限在自己的机器上运行 CLI。apps/runner/src/guard.ts 通过词法解析校验 cwd 位于根目录之内，但它被声明为尽力而为，不是真正的保证。

PAT 填补了自动化 token 的缺口（ADR 0105/RN-424..426）。 第 1 波的真实发现——“产品没有用于自动化的长期账号 token 机制，所以 runner 复制了浏览器的登录（cookie/CSRF 持久化在 ~/.brabo/runner-credentials.json 中）”——在第 2 波中关闭：personal_access_tokens（brb_…，通过 hashDeToken() 的 HMAC-SHA256+pepper 哈希，从不用 argon2——它不适用于高熵机密）在项目配置中签发，限定于一个项目，可吊销，可选过期。apps/runner/src/auth.ts 完全去掉了交互式登录、cookie 和凭据文件——只校验格式并转发 --token/BRABO_ACCOUNT_TOKEN，CLI 从不把它写入磁盘。PAT 从构造上从不在 POST .../runner-ticket 之外认证（IS_PAT_ROUTE_KEY/ @RequirePatAuth() + PatAuthGuard）——从不是全局 JwtAuthGuard 中的一个分支，那会让 RolesGuard 为用户角色的任何路由授权 PAT。

maintainer 可以吊销其他用户的 PAT（RN-427），关闭了 ADR 0105 暂时声明为超出范围的条目（事件响应——离职的 dev 的 token 泄露）。同一模型的扩展，没有新 ADR：单独的路由（GET .../personal-access-tokens/all、 DELETE .../personal-access-tokens/:tokenId/admin），范围按 projectId 而不是 userId——每个用户的自我吊销（RN-426）不变。

runner 的独立二进制（2026-08-23，RN-451/452，ADR 0112）​

ADR 0104 的 backlog 项（“standalone binary，pkg/bun build --compile”），是 ADR 0106（通过 npm 分发）的伴随项。产品所有者的明确决定：真正的单一二进制，从 v1 起就是包含 Windows 的完整矩阵——更便宜的替代方案（“二进制 + 旁边的 node-pty-native/ 目录”）被提出并被拒绝。

bun build --compile 通过 with { type: 'file' } 嵌入 node-pty 的原生 .node，并在运行时把它解压到一个真实的临时目录（native-pty-loader.ts）——这是必要的，因为 node-pty 通过一个计算出的路径的 require() 解析自己的插件 （lib/utils.js#loadNativeModule），Bun 无法自行嵌入（构建通过，运行时抛出 Cannot find module，在设计修复之前已测试过）。五个平台 （linux-x64/linux-arm64/darwin-x64/darwin-arm64/win32-x64），每个都在自己的原生 runner 上构建 （.github/workflows/build-runner-binaries.yml，最终 tag 触发，与 publish-runner.yml 同样的模式），二进制附加到已有的 Release 上。

按平台诚实地验证：只有 linux-x64 在这个环境中真正执行过（build:bin+smoke:bin 为绿色，反复执行——正是运行真实二进制时下面两个 bug 才出现）。其他四个——尤其是 Windows，有三个原生文件而不是一个——是通过阅读 node-pty 的源代码推理出来的，从未在该操作系统的真实机器上执行过；它们的第一次真实执行是下一个版本 tag，而不是这个 PR。没有预防性地按平台应用任何回退——这次调查中没有任何东西证明五个之中有哪一个以这种方式无法工作；如果某个真实 tag 表明确实如此，那会成为新的条目，而不是今天的假设。

两个只有在运行编译出的二进制时才发现、而不是阅读 API 发现的缺陷： --external node-pty 必须出现在 bun build 命令中，即使代码中没有任何对 node-pty 的静态 import——回退用的 await import(...)（只在二进制之外使用）无论如何都会被 Bun 发现并嵌入，并在运行时以误导性的错误失败；自动运行守卫（ADR 0106）需要第二个分支——二进制内部的 process.argv[1] 是一个虚拟路径（/$bunfs/root/...），realpathSync 无法到达，会在尝试 main() 之前、在任何 try/catch 之外抛出 ENOENT。

转换已有项目的 execution_mode（RN-447..450，ADR 0111）​

第 28 阶段（第 5 次会话）——本地 agent 的 join 不再沉默（RN-514，ADR 0147 第 1 点）​

从未启动的 broker（RN-512 的更正）（RN-512，ADR 0130/0146）​

brabo-runner service install|uninstall|status，而先例为零（apps/runner/ 中没有任何提到 systemd/launchd 的地方；模型是前台运行、被 SIGINT 杀掉）。始终是用户级——systemd --user/LaunchAgent——root 是拒绝而不是警告：guard.ts 的 docblock 把“以用户自己的权限运行”声明为三条真实边界的前提，而 root 服务会让尽力而为的 cwd 守卫成为已批准命令与磁盘之间的唯一屏障。Windows 是具名拒绝（第三种机制，不是两者的变体）。每个项目一个 unit，因为服务器已经强制每个项目一个 runner——按目录命名会产生两个永远不会同时启动的 unit，第二个会表现为连接失败而不是安装错误；在 Linux 上，文件放在 systemd 查找的地方 （$XDG_CONFIG_HOME/systemd/user，否则 ~/.config）。Restart=on-abnormal，从不用 on-failure（在 plist 中为 KeepAlive/Crashed）：runner 的 exit 1 是致命的 join 拒绝（RN-514）或重试上限用尽，重启就是 CLI 拒绝自行进行的那种循环。服务通过设备密钥认证，从不通过 token——把它写进 unit 会让它留在磁盘上，而这个 CLI 从未把凭据写到磁盘。uninstall 通过读取 unit 的目录、从不是 cwd，删除三者（没有 unit 时只能用 --dir——猜测会删除另一个项目的密钥），并说明密钥已从磁盘移除、但没有在服务器上吊销。status 以各自的句子和代码回答四种状态（0/3/4/5），第一个答案来自磁盘——所以在没有管理器的机器上它依然正确；失败的 spawn 从不变成“管理器说不”。BRB-031 不在这里关闭

第 29 阶段（第 2 次会话）——流水线为它发布的东西签名（RN-524，ADR 0149）​

产品什么都没签名：.github/、scripts/ 或 docker/ 中不存在 cosign/sigstore/attestation，唯一的来源证明是 runner 的 npm 包的 --provenance。release.yml 发布四个镜像时没有 id-token: write；build-runner-binaries.yml 用 gh release upload 上传五个二进制，别无其他——而已有的 sha256sum -c 验证的是第三方二进制，这是仓库懂得应用、却从未应用到自己身上的模式。现在镜像按 DIGEST 签名（从不按 tag，那是可移动的指针），二进制获得一个已签名的 checksums.txt，由一个等待矩阵完成的 checksums 作业产生——不是五个签名，因为验证了四个而忘了第五个的人不会知道自己忘了。该作业故意是 if: always()（矩阵为 fail-fast: false），并且点名清单没有覆盖的内容。两个 workflow 都先验证再发布。按本仓库的历史选择 keyless：私钥会是又一个 CI 机密，而 PAT 已经静默过期过一次（ADR 0139）。验证流程在运维手册中，两个 --certificate-* 标志为必需——没有它们，cosign 会接受任何人的有效签名。为镜像和二进制关闭 BRB-005；操作系统代码签名和下载代理被排除在外，已声明

第 29 阶段（第 3 次会话）——还不会安装的安装程序（RN-526，ADR 0150）​

install.sh 在根目录诞生，版本化并由 Release 提供。形式是 sh -c "$(curl …)"，从不是 curl|sh，原因是机制上的：用管道时，进程的 stdin 就是下载内容，每次 read 都会读到脚本自身的字节或遇到 EOF——一个不提问的安装程序会自行决定在别人的机器上把目录创建在哪里。它验证自己的来源（RN-524 的 checksums.txt 签名，以及它自身在已验证清单之内的哈希），使用固定版本的 cosign，并以 sha256sum 对照写在脚本中的哈希检查；检测会在提问之前点名它发现的东西；没有 TTY 时报告并以 0 退出；并且从不删除用户目录——项目 base 和镜像目录不在任何确认的范围之内，依据镜像的规则（RN-516）。标记文件在 $XDG_STATE_HOME/brabo/ 中，从不在 ~/.brabo/ 中，后者是按项目的。这个版本不安装任何东西，并且会说明这一点，而不是沉默地结束。 --print-plan/--print-state 在没有 TTY、没有网络、没有副作用的情况下公开决策——以 bootstrap.sh 的 --print-commands 为模板，测试方式相同。运行时发现两个 bash bug，属于同一类：在 set -e+pipefail 下，结果为假的 [ cond ] && 赋值 会杀死脚本，一个没有匹配的 ls 会让整个命令替换失败——而在一个正常情况就是“什么也没找到”的函数中。仓库根目录没有被任何 docmap 覆盖（根目录的 glob 是字面名称）；instalador 规则诞生

第 29 阶段（第 4 次会话）——安装从自己的 compose 启动（RN-527，ADR 0150）​

docker/docker-compose.install.yml 诞生，由生产 compose 生成，在三点上不同：四个镜像来自必需变量 （${BRABO_API_IMAGE:?…}——如果有默认值，缺少变量时会用一个没人选择的镜像启动半个栈，错误会变成奇怪的行为而不是拒绝），没有 build: 留存，并且**broker 服务不存在**，因为它的镜像没有发布（bake 有四个目标）——使用 --source=ghcr 时，mounted 不会启动容器，compose 在 BROKER_URL 的注释中说明了这一点。docker-compose.prod.yml 保持不变：它自称是验证用 compose，是 smoke.sh 在本地构建时使用的。维护两个文件的代价已声明，上限是机械的—— composes-em-conformidade.spec.ts 会因多出的服务/卷/端口、残留的 build: 以及被放松的第三方镜像而失败。计划中的两件事在接触磁盘时就死了，原因相反：migrate 不是一个步骤 （compose 以 service_completed_successfully 串联 api→migrate-api，两个地方都下令迁移会是同一事实的两个来源），以及不复用 smoke.sh（它会构建安装程序已按 digest 下载的东西，并在最后停掉整个栈）——取而代之，安装程序在断言之前先询问，请求两者的 /health

第 29 阶段（第 6 次会话）——迁移需要已证明的备份（RN-530，ADR 0150/0152）​

在已有安装之上安装不被提供——要么迁移，要么停止：在另一个版本的卷上执行 up 是不会预警的损坏。顺序是备份 → 证明 → 询问 → 删除 → 安装 → 恢复，中间这一步正是赋予安装程序删除权的东西：一个没有人尝试恢复过的备份只是一个文件，而发现这一点的时机不该是在 down -v 之后。证明运行 test-restore-compose.sh（ADR 0152 的同样三项校验）；失败的备份或证明会停止迁移，不删除任何东西。目标是主机目录——compose 的默认值是 backup_local 卷，down -v 会把它与想要保留的东西一起删除。Postgres 的 dump 不会被自动恢复到有数据的数据库上（这是破坏性的，brabo-restore 从不触碰源库）；本地 git 仓库会，因为它们会以空的状态诞生

第 29 阶段（第 8-10 次会话）——协议、选择器和 E2E（RN-532..534，ADR 0149/0150/0151）​

第 29 阶段（第 8 次会话）——本地 agent 的 base 有了使用方（RN-532，ADR 0151 第 3–6 点）​

RN-529 构建了 BASE，并书面声明没有任何东西使用它。加入了 workspace_create/workspace_create_result 这一对，采用 exec/exec_result 的请求-响应模板——从不采用 workspace_confirm 的模板，后者是单向的（{:noreply, socket}，不会推回任何东西），这一精确点本阶段早已与“workspace.verified 不存在”一起记录过。只有相对路径段穿过网络（ADR 0130/0144 的不变量：持有根目录的是执行者），绝对路径段会被词法拒绝。确认复用已有的 workspace_confirm，正是它省下了整整一条前线：没有诞生任何新的写入路由，engine 仍然不写这张表，为 workspace_verified_at 盖章的路径仍然只有一条——以顺序作为机制（confirm 在结果之前，因为两者按顺序到达同一个通道进程，而 confirm 的处理程序是同步的）。workspace 能力在代码进入的同一次会话中进入词汇，两侧皆然——RN-514 用 espelho 做了相反的赌注，它之所以有回报只是因为有人去督促——并且它是四个能力中唯一一个其声明取决于那次执行的状态的：runner 只在有经同意的 base 时才声明它，服务器正是通过这一行、而不是别的任何东西，知道 base 存在（engine 不读用户的磁盘）。没有人在 join 时要求它，这是有意的：在 runner 中要求它会因为一个该项目也许永远用不到的功能而成为 breaking/ 和 MAJOR。独立的谓词 （Engine.Runners.PastaDoProjeto），两个前置条件，RunnerReadiness 逐字节不变——在这里第三个前置条件比不必要更糟，它会是循环的：runner 项目只有在 runner 启动容器之后才会有 running 的容器，而容器建立在这条消息要创建的目录之上。它也不询问 workspace_verified_at（在这里那是结果），也不询问模式。两个前置条件在不同的地方回答，因为“经同意的 base”是连接的属性（socket.assigns，从不是表）：通道在推送之前就拒绝，以同一个 ref 返回 motivo: "sem-base"，采用模块所期望的格式——从不是超时。五个不会合并的具名原因、带有自己结果的幂等性（ja-era-repositorio 是成功），并且 estado.dir 不变。它不是 proposed_action，也没有任何上限获得例外

第 29 阶段（第 5 次会话）——备份开始覆盖丢了会痛的东西（ADR 0152，RN-528）​

备份只覆盖一个数据库，只在一个地方运行：make test-restore 是 Kubernetes 路径（需要 kubectl、集群和 CronJob），而 docker-compose.prod.yml 没有任何 backup 服务——迁移 compose 安装没有经过证明的路径。决定首先拒绝容易的做法（“备份所有卷”），并对七个卷进行分类：neo4j_data 和 project_workspaces 是派生的，ollama_data 可以重新获取， brabo_projects_base 属于用户——复制它们只会给人覆盖的印象，而不增加可恢复性。事实来源有两个，发现在于第二个： git_local_repos 不在任何备份中，而 provider 为 local 的项目把 bare 仓库保存在那里——它无法从 Postgres 重建（event log 保存的是叙事，不是 git 对象），所以丢失这个卷就是丢失 agent 的代码。运维手册的文字曾断言相反（"the real repositories live in GitHub/GitLab"），正是它解释了多年来没有覆盖的原因：这对 github/gitlab 成立，而对 local 没有上游。归档的保证是声明的，比“快照”更弱——按引用的一致性（git 在移动 ref 之前写入对象，并通过原子 rename 替换 ref），没有全局时间点，也没有 git fsck（镜像故意不包含 git）；并发的 gc 变成失败而不是部分归档，tar 的状态被记录到一个文件中，因为在 POSIX sh 中管道的状态是最后一个命令的状态。五个 S3 变量不再是必需的，而成为一个目标的配置（BACKUP_DIR 选择磁盘；缺失时为 S3——这种推断正是让 CronJob 保持原样的原因）。make test-restore-compose 触发真实备份，并以同样的三项校验调用同一个 brabo-restore：改变的是外壳，从不是判断，而 deploy/k8s/test-restore.sh 保持原样（合并会让 compose 版本依赖 kubectl）；restore.sh 仍然不触碰源数据库。恢复仓库是同类命令（brabo-restore-git，默认只验证，只有 --restaurar 才写入），而不是另一个命令的阶段——两个产物、两种判断，合并会让 git 失败导致 event log 校验失败。运行时发现、阅读不会发现的问题：该卷由三个使用不同 uid 的镜像共享，其所有者是最先挂载它的一方（测得 1000:1000，模式 0755），而镜像以 uid 70 运行——提取会在中途失败，留下写了一半的卷；现在它会在 tar 之前拒绝并点名 --user 0:0，以 root 提取的内容会交还给目录的所有者，否则卷会完好无损地回来却毫无用处（非 root 的 api 和 engine 无法写入刚恢复的内容）。Neo4j 获得的是重新投影而不是备份——这里没有构建（BRB-018）：迁移后的安装诞生时图谱为空，这是具名的降级而不是数据丢失（RAG 位于 pgvector 中，在 dump 之内）

.parcial，finish 写入真正的名字——runner 读取的文件永远不会缺少 kid，RN-475 的缺陷从构造上变得不可能。api 一半（RN-552）声明了代价而不是隐藏它：凭据是 service token，泄露的 token 将能够制造持久凭据——因此三项约束位于路由中而不是文本中（请求体中没有 userId；注册会在同一事务中替换所有者活跃的机器密钥，所以重装的机器可以通过，而一千把密钥因条款而不可能，无需会过时的数字；带 d 的 JWK 会被点名拒绝）。第 6 次会话（RN-547）串联了五条命令并确定了三条规则：中间环节失败不会撤销任何东西，它会在最后的区块中变成一行具名条目，脚本总是以 0 退出（撤销需要删除账号和吊销密钥，而没有这样的路由，也不应该有一个让安装程序自行调用的路由）；幂等性就是 HTTP 代码，409 是预期结果而不是失败，000 被单独处理，以免“api 没启动”被读作“api 拒绝了”；密码通过 curl 的 STDIN 传递，从不通过 argv，因为 /proc/<pid>/cmdline 对机器上的任何用户都可读。该次会话的发现：--help agent，这个列表属于你的账号而不是这个浏览器），使用 accent 色调，从不用 success。第 8 次会话 （RN-549）是唯一能证明整体的一次，它扩展了第 29 阶段已有的 workflow，而不是创建第二个。它的核心决定是信号： perguntarEstado 把 activating 映射为 rodando——这是有道理的——所以 systemctl is-active 和 service status --machine 会对一个两秒后就会死掉的进程给出绿色；所选的信号是 agent 进入等待时写下的那一行，它只有在 agent 读取了密钥、拿到 ticket、与 api 通信并收到空列表之后才存在，并且它是一个记录下来的事实，而不是对状态的采样。结果通过 API 而不是浏览器证明，因为断言的主体是 AGENT，它观察的是 GET Infra Lead 通过输入框对话（AT-141，ADR 0175，RN-617）​

RN-584（AT-098）去掉了聊天的默认接收者，并书面留下了一个产品问题：Infra Lead 会对话吗？维护者在 2026-09-27 回答是，附带 RN-584 本身提出的条件——先解决回合。Infra Lead 的回合整个在 handle_call/handle_cast 中运行：没有接受、没有“Parar”、不在 TurnoOrfao 范围内，循环的第 14 步沉默地结束，而 180 s 的上限小于容器 propose_action 的 225 s（RN-605）。kickoff 是 cast，不会卡住点击，但会卡住进程——AT-089 测得 8.4 分钟——期间的消息会在队列中等待。第 1 步把三种回合（kickoff、gate 修正、消息）放进 TurnoAssincrono，Workflows 的整合在 Task 之内；在回合进行中到达的 gate 修正获得了一个队列，因为没有 from 的 TurnoAssincrono 会丢弃它。第 2 步给了 infra message/2 子句（agente_sem_conversa 拒绝被移除）、“Parar”的 via_for，以及在 AGENTES_DE_CHAT 中的位置；对它的 handoff 的接受保留在 RN-499 的专用卡片中，消息流中的卡片按名称排除它。SOLO_CONVERSATIONAL_AGENTS 没有改变：Infra Lead 是领域 lead。已声明：它没有获得结构化问题，也没有 backlog 读取。

带凭据的 git 在 runner 的主机上运行，代码在容器中（AT-116，ADR 0193，RN-676）​

2026-10-01，第 36 轮。RN-558 关闭了沉默的那一半——在 runner 模式下、容器运行时，认证的 git fetch 不再以空变量运行，而是带着标记 credencial-nao-atravessa-o-container 被拒绝——并把另一半声明为待定 ADR，因为所有已知选项都触及 ADR 0130 的隔离端口。所有者的决定（10月1日）选择了不触及它的那个：带凭据的 git 操作在主机上，代码在容器中。事先测得：engine 中唯一带 env 的 exec 是 RunnerGit.fetch!/3 的 fetch；没有通过 exec 的带凭据 push 或 clone（创建目录时的 clone 本来就在主机上运行，RN-532）；目录在两侧相同（estado.dir 挂载在 /work）。所选的判别依据是 engine 的显式标记（gitCredenciado: true，只由 RunnerRouter.exec_git_credenciado/5 设置），而不是已有的 env——以 env 为键，任何带 env 的命令都会逃出容器。RN-558 的拒绝缩小后保留下来，用于没有标记的 env，实际上变成了“早于 ADR 0193 的 runner”的意思。证明是 AT-111，两侧皆有：在 runner 中，使用 GitAuth 辅助程序的真实 git credential fill 和 git fetch origin 在容器活跃时于主机上成功；在 engine 中，经过真实 TerminalChannel 的链条以 {:ok, _} 结束。ExUnit 没有在交付环境中运行（repo.hex.pm 403），留给 CI。

没有 agent 的咨询型会话会要求选择一个 agent（AT-254，RN-682）​

2026-10-01，第 36 轮。在 9月29日的真实使用中，一个没有 agent 的咨询型会话回答“我无法访问之前的对话”：没有接收者的消息进入 POST .../chat 的 SSE，它只把当前文本发送给绑定的模型——没有历史，没有系统 prompt——并以模型名称作为行动者记录回复。所有者的决定（10月1日）是要求一个 agent，而不是给自由聊天提供历史。事先测得：界面是该路由唯一的客户端（种子打印的 curl 是开发提示，用于创意型会话），而用例 SendChatMessageUseCase 有第二个合理的使用方——provider 的 smoke，它们在没有 agent 的会话中把它当作端到端的工具使用。因此 api 的拒绝位于路由中，作为独立的守卫，用例保持不变。在界面上，没有 agent 时，接收者一行开始带有手动 handoff 本身的选择器——一贯的动作，现在放在它是让消息有目标的唯一方式的地方——Criativo 被排除在列表之外，因为咨询型会话承诺它不会进入。

吊销针对的是密钥，而不是 {projeto, usuário} 对（AT-013，ADR 0201，RN-685）​

2026-10-01，第 36 轮。RN-520 让吊销能够触及活跃连接，以 {projeto, usuário} 为目标，因为凭据的身份在 PatAuthGuard 中就消失了；ADR 0154 把 "按密钥吊销" 列为它不做的事，而 PR #534 给了机器密钥同样的对，逐项目应用。AT-013 因范围和决定一直被阻塞，直到所有者选择（10月1日）：按密钥，带 ADR，改动 engine。事先测得：ticket 由 {userId, kind} 生成，socket 只保存项目/用户/kind，通道比较的是用户——同一用户使用 PAT 或另一把密钥的 runner 会一起掉线；机器密钥在 api 列表之外项目中的连接会保持运行；吊销之前签发的 ticket 在吊销之后仍能进入；吊销 PAT 不会让任何东西掉线。交付内容：ticket 中两个可空列（Ecto migration，这张表属于 engine——Drizzle 的日志停留在 0068），guard 在授权之后记录凭据，socket 的 id 加入凭据的种类和 id，以及一条 runner/disconnect-credential 路由，它作废待处理的 ticket，并询问集群中的每个 runner 是否源于该凭据。AT-013 的禁令（不能不再断开原本会断开的东西）变成了两个过渡部件：遗留连接在该行的项目中按对掉线，没有该路由的 engine 会让 api 回退到按对。按对的方式保留为移除成员的目标。界面只改变了确认文本（RN-561）。runner 没有改变。ExUnit 没有在交付环境中运行（repo.hex.pm 403），留给 CI。
