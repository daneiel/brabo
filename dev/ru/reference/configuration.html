Configuração

Toda a configuração é por variável de ambiente. Não há arquivo de configuração da aplicação — o que existe é o permissions.json, que é política do projeto, não configuração de processo.

Dois arquivos versionados são lidos em tempo de execução e não são configuração, embora seja fácil confundi-los com ela: o permissions.json acima e o docs/gates.yml (ADR 0054), o registro declarativo de gates. Nenhum dos dois tem variável de ambiente que aponte um caminho — o registro é achado subindo a partir de __dirname — e nenhum muda comportamento ao ser editado em produção: o registro DESCREVE os gates, não os aplica. Ele viaja dentro da imagem da api; veja o runbook.

O que viaja é o registro e nada daquilo para que ele aponta. A evidencia de um gate teste/ci nomeia arquivos sob apps/api/test/, scripts/ci/ e .github/, e nenhum deles está na imagem. Conferir que esses alvos existem é, portanto, uma afirmação sobre o repositório, cobrada no CI, nunca pelo processo que serve GET /gates — por isso a api lê o registro sem procurá-los. Ela já procurou, e respondia 500 em toda instalação (RN-070).

up --wait só prova o que tem healthcheck. No compose de desenvolvimento, api, engine e web não tinham nenhum, então docker compose up --wait os dava como prontos no instante em que o container subia — antes de o processo escutar. Foi assim que um container podia morrer segundos depois com o comando ainda anunciando sucesso. Os três agora carregam a mesma checagem que as imagens de produção já declaram no Dockerfile (/health na api e no engine, que toca o banco; / no servidor do Vite). O broker de containers ganhou a dele numa mudança à parte; postgres e neo4j sempre tiveram. Nada aqui é variável de ambiente — está escrito porque o --wait é aquilo em que os scripts confiam, e um serviço sem healthcheck o faz mentir.

Os defaults abaixo foram extraídos do código, não de documentação anterior. A coluna quando falha é a parte que economiza tempo: quase toda variável tem um default que funciona em desenvolvimento e um modo de falha específico em produção.

Uma variável só chega ao processo se o compose a mapear. O docker compose não repassa o ambiente do host para dentro do container: a variável chega se — e somente se — estiver escrita no environment: daquele serviço (ou num env_file). Isso não é detalhe; foi assim que ANAMNESE_ENABLED e PSYCHOLOGIST_ENABLED ficaram inalcançáveis em silêncio enquanto três lugares do código prometiam que a pausa de 2026-08-10 se revertia com X=true e um reinício. Medidas dentro do container do engine em execução, voltaram vazias e o runtime.exs caiu em "false" — sem erro em lugar nenhum. Toda flag booleana que o engine lê está mapeada agora nos três arquivos de compose (dev, produção e instalação — o de instalação só desde a AT-202), com o default do próprio código, salvo as duas chaves de boot dos agentes de fundo que produção e instalação desligam de propósito, e scripts/ci/flags-do-engine-no-compose.spec.ts reprova o build para a próxima que não estiver (RN-540). O Kubernetes fica de fora dessa regra de propósito: um Deployment/ConfigMap não intercepta nada, então ali não há chave quebrada a consertar.

Os defaults de desenvolvimento são inseguros de propósito. Valores como dev-master-key-change-me existem para que o pnpm dev suba sem cerimônia. Em produção eles precisam ser trocados — e para seis deles o processo recusa subir sem a troca (api ou engine, marcados com 🔒). Cinco seguem o padrão do ADR 0059/RN-093: ausente, igual ao literal público de exemplo ou curto demais derruba o boot. Veja a RN-114 para as quatro que se juntaram ao GIT_OAUTH_STATE_SECRET original.

Compose de instalação (docker-compose.install.yml)​

O compose que roda numa máquina instalada pega as cinco imagens do produto de variáveis obrigatórias, sem default — o install.sh as escreve no .env:

variávelo quê
BRABO_API_IMAGEreferência completa da imagem da api; ghcr.io/…@sha256:… quando a origem é o GHCR, brabo-api:prod quando construída localmente
BRABO_ENGINE_IMAGEo mesmo, para o engine
BRABO_WEB_IMAGEo mesmo, para o web
BRABO_BACKUP_IMAGEo mesmo, para o job de backup (sob o profile backup)
BRABO_BROKER_IMAGEo mesmo, para o broker de containers (ADR 0162). Escrita esteja ou não o broker ligado: o Compose interpola o arquivo inteiro antes de filtrar por profile, então um ${VAR:?…} num serviço desligado ainda recusa o arquivo (medido)

Elas são ${VAR:?…} de propósito. Com default, uma variável ausente subiria metade da stack numa imagem que ninguém escolheu, e o erro apareceria como comportamento estranho em vez de recusa.

Elas não estão no inventário gerado abaixo: o gerador varre apps/, e estas são lidas pelo Compose, não por código do produto (RN-527).

O broker está neste compose desde o ADR 0162, desligado, sob o profile container-broker, e o install.sh o liga só quando pergunta e a resposta é "s" (RN-575). Então ele escreve quatro linhas, juntas ou nenhuma:

variávelo que o install.sh escreve
COMPOSE_PROFILEScontainer-broker — lida pelo Compose a partir do --env-file, então up -d --wait sobe o broker sem flag
BROKER_URLhttp://broker:8090 — o lado da api; sem ela a api nunca chama o broker
DOCKER_GIDo gid do socket visto de dentro de um container, medido com a própria imagem do broker; falhar na medição é recusa nomeada, nunca o default 999
PROJECT_WORKSPACES_HOST_ROOT<DockerRootDir>/volumes/brabo_project_workspaces/_data, calculado antes da subida e conferido contra o Mountpoint real do volume depois dela

BRABO_PROJECTS_HOST_BASE não é escrita: o compose a deriva de BRABO_PROJECTS_BASE, como no compose de validação. Ligar ou desligar depois está no runbook.

Os modelos locais (Ollama, o profile llm) são perguntados logo depois do broker (RN-691). Responder "s" mede antes uma porta livre do host e escreve:

variávelo que o install.sh escreve
OLLAMA_PORT11434, ou a primeira porta livre até 11443 quando algo (um Ollama nativo) já escuta ali; a faixa inteira ocupada é recusa nomeada, sem escrever nada
COMPOSE_PROFILESllm, junto com container-broker numa linha SÓ quando os dois foram aceitos (container-broker,llm) — duas linhas não somam, a última vence

Sem elas a checagem de duplicata semântica é pulada. Ligar depois está no runbook.

A auth mora no domínio da api, e desde o corte é também a única emissora. Decisões no ADR 0031 e no ADR 0032.

O teto da escada por email é igual à janela de propósito. Com janela deslizante, quem insiste empurra a janela e fica bloqueado enquanto insistir; quem parou volta com a janela limpa. Um teto maior que a janela criaria um bloqueio que a janela não consegue representar, e exigiria uma coluna locked_until persistente com fila de desbloqueio. Não mexa num sem o outro.

Rotacionar o AUTH_TOKEN_PEPPER desloga todo mundo e invalida os tokens de verificação e de redefinição pendentes. Diferente das chaves, o pepper não tem _PREVIOUS. Veja o runbook.

Até onde as variáveis _PREVIOUS chegam. AUTH_JWT_SECRET_PREVIOUS, CREDENTIALS_MASTER_KEY_PREVIOUS e BRABO_SERVICE_TOKEN_PREVIOUS estão mapeadas no environment: dos três composes (dev, produção e instalação) como ${X:-} — a api recebe as três, o engine e o broker recebem BRABO_SERVICE_TOKEN_PREVIOUS (RN-595). Vazio é o mesmo que ausente em todo leitor, então fora de uma rotação nada muda; durante uma, basta defini-las no .env e recriar o serviço. Antes da RN-595 elas não estavam mapeadas em lugar nenhum e o docker compose não repassa o ambiente do host, então uma rotação virava troca seca em silêncio. No Kubernetes elas chegam aos Pods pelo cofre de segredos (AT-220): o ExternalSecret puxa o objeto brabo inteiro com dataFrom.extract, então um _PREVIOUS presente ali cai em brabo-secrets e um ausente simplesmente não está lá. O preço é que toda chave desse objeto vira variável de ambiente de api, engine, migrations e backup — o objeto do cofre não pode guardar mais nada. O procedimento está no runbook.

SMTP real (MailSender)​

O MailSender só manda email de verdade com MAIL_TRANSPORT=smtp — o default é log (link/token vão para o log da api, AUTH_MAIL_LOG_TOKENS acima), inclusive em produção: mandar email é opção do operador. Decisão no ADR 0096.

variáveldefaulto que faz
MAIL_TRANSPORTloglog (default) ou smtp. Qualquer outro valor cai em log
SMTP_HOST 🔒—host do provedor SMTP. Só com MAIL_TRANSPORT=smtp: em produção a api recusa subir se ele falta, se é só espaço ou se é o valor de exemplo publicado no .env.example (RN-114)
SMTP_PORT587porta do provedor — 587 é STARTTLS, 465 é TLS implícito (SMTP_SECURE=true)
SMTP_SECUREfalsetrue liga TLS implícito na conexão (tipicamente a porta 465)
SMTP_USER 🔒—usuário da auth SMTP. Mesma exigência de SMTP_HOST em produção
SMTP_PASSWORD 🔒—senha/token da auth SMTP. Mesma exigência de SMTP_HOST em produção — nunca aparece em log
SMTP_FROM—remetente, no formato "Nome <email@dominio>" (ou só o email). Mesma exigência de SMTP_HOST em produção, mais a validação do formato

O corpo do email é texto puro, sem HTML — a porta MailSender não carrega estrutura para corpo rico, e um motor de template seria superfície de injeção sem ganho. O link usa WEB_ORIGIN (acima).

Tráfego interno 🔒​

O segredo compartilhado que autentica api ↔ engine. A mesma variável dos dois lados — cada um envia o valor atual e aceita os dois, e é isso que torna a rotação possível sem indisponibilidade (RN-035).

variáveldefaulto que faz
BRABO_SERVICE_TOKEN 🔒dev-service-token-change-me só fora de produçãovai no cabeçalho X-Brabo-Service-Token e é o que o EngineServiceGuard compara em tempo constante. Em produção a api recusa subir se ele falta, se é o default acima (público — está no .env.example) ou se tem menos de 16 caracteres (RN-114)
BRABO_SERVICE_TOKEN_PREVIOUS—aceito só para verificação, durante a rotação. Quando definido, passa pela mesma regra do token atual: o espaço em volta é aparado, e em produção a api recusa subir se ele é o default público ou tem menos de 16 caracteres. Diferente do atual, nunca é obrigatório (RN-598)

Definir só o valor NOVO de um lado (sem passar pela dança do _PREVIOUS) não quebra o boot de ninguém: o sintoma é 403 em /internal/* e 401 nas chamadas da api ao engine. Procedimento no runbook. A checagem de BOOT acima (RN-114) é outra coisa: ela só falha com o default público ou com a variável ausente/curta, não com divergência entre os dois lados.

Projeto no modo Mounted: uma base, montada por identidade​

Desde o ADR 0072, um projeto pode nascer no modo Mounted (o antigo local, renomeado pelo ADR 0104) — o código mora numa pasta do usuário e PROJECT_WORKSPACES_ROOT não participa da raiz dele.

O caminho de um projeto é dado do projeto (projects.workspace_path), escolhido na criação e nunca variável de ambiente. O que o AMBIENTE fornece é a base sob a qual essas pastas moram — BRABO_PROJECTS_BASE, uma por instalação (ADR 0141, RN-500):

# .env — ABSOLUTO. `~` não é expandido pelo Compose.
BRABO_PROJECTS_BASE=/home/voce/projetos-brabo

Você não precisa escrever essa linha à mão. Desde o ADR 0146, pnpm bootstrap → Docker › Base de projetos roda scripts/dev/consentir-base.mjs, que propõe $HOME/projetos-brabo, recusa o que se sobreponha ao checkout do Brabo ou a PROJECT_WORKSPACES_HOST_DIR (duas raízes com donos opostos — compartilhar uma pasta faria um projeto Mounted chamado loja cair em cima de um projeto Container cujo workspace_dir_name também é loja), prova no macOS e no Windows que o Docker enxerga mesmo a pasta montando-a, e só então escreve a variável.

A prova é uma montagem, nunca a leitura do settings.json do Docker Desktop: esse arquivo não é documentado, muda entre versões e plataformas, e descreve o que o usuário configurou, não o que o daemon vai fazer — a mesma regra que o produto já aplica aos providers de LLM, onde capability só é declarada quando provada por execução. Ela tem três desfechos e eles não colapsam: provado, recusado (a variável não é escrita) e não deu para provar — sem imagem local para montar — que escreve a variável e diz em voz alta que a prova não rodou.

Rodado pelo menu, ele só informa: todo item do menu do bootstrap roda com stdin de /dev/null de propósito, então não pode perguntar. Para escolher, rode node scripts/dev/consentir-base.mjs no seu próprio terminal.

# docker/docker-compose.yml — em `api` E `engine`, já escrito
    volumes:
      - ${BRABO_PROJECTS_BASE:-brabo_projects_base}:${BRABO_PROJECTS_BASE:-/data/brabo-projects-base}

O operador define isso uma vez e reinicia api + engine; nada é editado por projeto, nunca. Antes disso, todo projeto montado precisava de uma linha de bind-mount escrita à mão nos dois serviços e de um reinício — que mata todo turno de agente, socket de terminal e chamada de LLM em voo na instalação.

A montagem é por identidade ($X:$X): o mesmo caminho absoluto no host e dentro dos dois containers. É isso que mantém honesta a string que o usuário digita e a tela mostra de volta, e é por isso que projectScopeRoot (api) e Engine.Actions.Workspace.workspace_dir/2 (engine) não precisam de camada de tradução.

Ela não é PROJECT_WORKSPACES_HOST_DIR, e nunca pode apontar para a mesma pasta. Um workspace gerenciado é nomeado por workspace_dir_name (UNIQUE) e um projeto montado é nomeado pelo usuário, então <base>/loja e um projeto container cuja pasta se chama loja colidiriam, com o bootstrap do repositório rodando git init dentro do projeto de outra pessoa. O ADR tem os outros dois motivos.

Com a variável não definida, o modo Mounted não é oferecido — nunca ofereça um modo que a instalação não consegue honrar. E o pnpm dev recusa subir quando a base se sobrepõe ao checkout do Brabo em qualquer sentido; essa checagem mora no preflight porque ele roda no host, e a api só consegue comparar com process.cwd() (/workspace dentro do próprio container). Veja o runbook.

Por que a versão não passa pelo /config.js​

URLs são do ambiente: a mesma imagem precisa falar com a api de staging e com a de produção, e é para isso que o /config.js existe (ADR 0024). A versão é do artefato — a imagem brabo-web:1.1.2 não deveria conseguir informar outra coisa. Se viesse do /config.js, o rodapé viraria um campo editável em vez de uma identidade, e um ConfigMap errado faria a tela mentir sobre qual build está rodando.

O caminho inteiro, do commit à tela: o release.yml calcula versao=${TAG#v} → passa como VERSION ao docker buildx bake → o alvo web do docker-bake.hcl a converte em VITE_BRABO_VERSION → o ARG/ENV do docker/web/Dockerfile.prod a expõe ao pnpm build → o Vite a embute em import.meta.env → o runtime-config.ts a lê → o AuthLayout a mostra. O mesmo VERSION alimenta o BRABO_VERSION da imagem da api (ADR 0036).

Broker de containers​

O broker (ADR 0130) é o único processo do produto que fala com um daemon Docker no servidor, e o único serviço com /var/run/docker.sock montado. Localmente ele sobe com o pnpm dev; em produção fica sob profiles: ["container-broker"]. Os dois arquivos de compose divergem de propósito (ADR 0146, ponto 3) — não os uniformize.

Ele já foi desligado por padrão nos dois, sob o argumento de que nada o chamava ainda. Essa premissa morreu: ele tem quatro chamadores reais, e o ADR 0144 fez o modo Mounted subir o container pelo broker — então, com o profile desligado, o modo local padrão terminava em BrokerIndisponivelError. O que sustenta a assimetria é o que o socket significa de cada lado: quem roda pnpm dev já o tem (está rodando docker compose), enquanto em produção ele é uma fronteira real de privilégio e o operador não é o desenvolvedor.

Isso muda quando o broker roda, nunca o que ele aceita: as cinco camadas de contenção estão intactas, e ele continua recebendo um projectId mais uma de cinco operações, sem parâmetro em lugar nenhum onde escrever privileged ou um -v livre.

Subir por padrão foi o que expôs um defeito que nunca tinha importado: a imagem local instalava as dependências no START, e a única rede do broker é internal: true, então não há registry a alcançar — o container morria com getaddrinfo EAI_AGAIN registry.npmjs.org, e sem healthcheck o up --wait ainda imprimia Healthy. As dependências agora se instalam no BUILD e o serviço tem healthcheck; a rede não foi tocada, e não deve ser. O detalhe operacional mora no runbook.

Em produção, suba-o explicitamente:

docker compose -f docker/docker-compose.prod.yml \
  --profile container-broker up -d broker

PROJECT_WORKSPACES_HOST_ROOT—A raiz das pastas de projeto no HOST, não dentro de container nenhum. Sem ela, start recusa nomeando esta variável e as outras quatro operações continuam funcionando. Não a confunda com PROJECT_WORKSPACES_ROOT, que é o caminho dentro dos containers: o -v é resolvido pelo DAEMON contra o sistema de arquivos do host, e um caminho de dentro da api o faria criar e montar uma pasta VAZIA
DOCKER_GID999 (compose)O gid do grupo docker do host (getent group docker | cut -d: -f3). O socket é root:docker e o broker roda sem root, então o compose usa group_add. O default é o mais comum e está errado em várias distribuições. Desde o ADR 0146 isso importa em TODA máquina de desenvolvimento, não só onde alguém ligou o profile — errar não quebra o boot, quebra o uso: toda operação morre com "permission denied" no socket, e isso só aparece quando alguém propõe container_start. O pnpm dev informa o estado desta variável a cada execução (RN-512), e diz "não se aplica" numa máquina sem grupo docker em vez de acusá-la

PROJECT_WORKSPACES_HOST_ROOT não pode ser derivada de um volume Docker gerenciado. No compose de dev ela deriva de PROJECT_WORKSPACES_HOST_DIR (acima) — então deixar essa sem definir, o estado de um .env.example recém copiado, deixa o broker sem raiz e o modo container sem container: a stack sobe saudável e o container_start termina recusado. O pnpm dev informa isso a cada execução, no mesmo molde do DOCKER_GID, e nunca recusa subir (RN-599). Ele informa também o caso do ~: o Compose expande ~ na origem do bind-mount que api/engine usam, mas NÃO na variável que o broker recebe (medido com docker compose config), então escreva o caminho JÁ EXPANDIDO. E um PROJECT_WORKSPACES_HOST_ROOT explícito que difere da pasta que api/engine montam é informado como divergente — o container receberia uma pasta em que os agentes nunca escreveram. Trocar o volume gerenciado por uma pasta do host não migra o que já está no volume project_workspaces: os dados ficam lá, só deixam de ser o que api e engine enxergam.

BRABO_PROJECTS_HOST_BASE é a SEGUNDA raiz do broker — a base dos projetos Mounted, também no host (ADR 0141, ADR 0144). Diferente da de cima, ela não precisa ser preenchida: o compose a deriva de BRABO_PROJECTS_BASE, que já é um caminho do host por definição (é o que api e engine montam por identidade). Defina-a explicitamente só se o daemon Docker alcança essa pasta por outro caminho.

É ela que permite a um projeto Mounted ter container (RN-503): a api envia um localizador discriminado (localizacao.tipo — gerenciada ou montada) mais o segmento relativo, e o broker o resolve contra a raiz correspondente. As duas raízes nunca se substituem. Faltar esta faz o start de um projeto mounted recusar com 503, NOMEANDO a variável, sem tocar em container — cair em PROJECT_WORKSPACES_HOST_ROOT montaria a pasta de outro projeto, porque a raiz gerenciada é nomeada por workspace_dir_name e a base é nomeada pelo usuário.

Usuário dos containers de dev (build)​

Também não lidas pelo nosso código, e nem são variável de ambiente de runtime: são build.args do Docker para as três imagens de dev (docker/api/Dockerfile, docker/web/Dockerfile, docker/engine/Dockerfile), consultados uma vez no docker compose build e embutidos no USER com que cada container roda. Existem para que os containers rodem com o mesmo UID/GID do seu usuário do host em vez de root — tudo o que é escrito num bind mount (apps/api/dist, um workspace de projeto no modo de execução mounted) já é seu, sem sudo chown depois.

variáveldefaultpor quê
DEV_UID1000o seu id -u. NÃO é lido do ${UID} do shell — ele é somente leitura no bash e não é exportado para o ambiente por padrão, então o arquivo de compose sempre o veria vazio
DEV_GID1000o seu id -g, mesmo raciocínio

1000/1000 casa com a configuração Linux mais comum de um desenvolvedor só e com o usuário node que o node:26-alpine (a imagem base de api/web) já traz — quando o seu par casa, os Dockerfiles reaproveitam esse usuário em vez de criar um novo. Um ambiente que já tem containers rodando como root de antes dessa mudança precisa de um chown único dos volumes nomeados node_modules/_build/deps/.mix/.hex (ou de docker compose down -v para deixá-los ser recriados) — veja a nota em Primeiros passos.

Os composes de produção e de instalação são diferentes: o engine roda da imagem de produção como o usuário fixo engine (uid/gid 1000, sem DEV_UID), com read_only: true e um tmpfs em /home/engine. Esse tmpfs é declarado uid=1000,gid=1000,mode=0700 — não é variável — porque o semgrep (o gate de SecOps) escreve ~/.semgrep ali; criado como root, o scan não devolve nada e o gate aprova sem análise estática (RN-707, runbook O gate de SecOps está preso em "SAST não rodou").

As duas imagens do engine pinam o semgrep com o argumento de build SEMGREP_VERSION (1.171.0, o mesmo em docker/engine/Dockerfile e Dockerfile.prod, mantidos iguais por scripts/ci/semgrep-do-engine.spec.ts). É argumento de build, não variável de runtime — nada vai no .env. Sem pin, o pip pegou a 1.179.0, que não publica wheel musllinux: na imagem Alpine o pacote vinha do sdist sem semgrep-core e todo scan falhava. Subir a versão é escolher uma release com wheel musllinux no PyPI e mudar os dois Dockerfiles no mesmo PR.

As imagens do engine rodam Elixir 1.20.4 / OTP 29.1.1 sobre Alpine 3.24 (builder hexpm/elixir:1.20.4-erlang-29.1.1-alpine-3.24.2, runtime alpine:3.24.2, as duas por digest — ADR 0209). OTP abaixo de 29.1 aborta no boot sob a musl 1.2.6 do Alpine 3.24 em hosts cuja CPU tem AMX (sys_sigaltstack(): Internal error); não desça o OTP sem descer a musl. Nada vai no .env.

Nenhum dos seis Dockerfiles usa corepack (o Node 25+ não o traz mais, AT-360): o build instala o pnpm do tarball do registry, conferido contra um sha512 escrito no próprio Dockerfile — os argumentos de build PNPM_VERSION (11.3.0, o mesmo do packageManager em package.json, para o pnpm nunca tentar baixar outra versão em runtime) e PNPM_SHA512. São argumentos de build, não variáveis de runtime, e não há nada a definir no .env: subir o pnpm é mudar o packageManager, o PNPM_VERSION dos workflows e os dois argumentos nos seis Dockerfiles no mesmo PR — veja a seção do runbook sobre a imagem do broker.
