    RN-411 — 第四个待处理工作信号：dev agent 说的是 dev.*，而不是 agent.status

    这是通过真实使用而非测试发现的：在一个执行会话中，五个 dev agent 启动后变为 idle_tripped（RN-047 的熔断器，卡住等待用户手动解除某个任务的阻塞），而 30 秒的心跳 （Engine.Sessions.SessionServer.handle_info(:heartbeat_timeout, state)）在工作——以及对人的决定的等待——仍在继续时，从底下关闭了会话。

    GetSessionPendingWorkUseCase 针对同一问题早已有第三个信号 （RN-064）：智能体已激活、之后没有 idle，就会保持会话。但这个信号只读取 agent.status，即对话型智能体（Criativo/PO/Arquiteto/Dev Lead/UX Designer/Staff/Infra）的词汇。Engine.Dev.DevAgentServer（经由 Engine.Dev.AgentIo）从不发出 agent.status——它在会话事件日志中使用自己的词汇：dev.started、dev.working、 dev.awaiting_gate、dev.awaiting_approval、dev.idle、 dev.idle_tripped、dev.blocked、dev.blocked_by_container、 dev.error。一个有 dev agent 正在工作或卡住的执行会话，按第三个信号总是返回 pending: false，因为它根本没有 agent.status。

    第四个信号查找会话中已出现的每个 actor.id （dev-<modulo>/dev-<modulo>-2，与 RN-195 相同的键）的最后一个 dev.* 事件——与第三个信号相同，但针对多种事件类型而不是一种，因为 dev agent 的状态不是一个带可变 payload.status 的类型，而是每次转换各自不同的事件类型。标准：当最后一个是 dev.working、dev.blocked 或 dev.idle_tripped 时 pending: true——三者都意味着“有工作在进行，或需要人来行动”，而卡住等待解除阻塞就是待处理工作（这正是会话在真实执行中被关闭时用户正在做的事）。只有 dev.idle（没有任何任务可取，真正排空了）不计入。

    dev.awaiting_gate 和 dev.awaiting_approval 作为最后一个事件，最初不触发这个信号——它们被排除在当时决定的标准之外。awaiting_gate 是一个已知的残余缺口；RN-412 关闭了它，连同 awaiting_approval（通过一个新论据，而不是原来的那个——见 RN-412）。

    dev.blocked_by_container 是之后加入的，基于同样的论据和同样真实的发现。该类型诞生于 RN-502/ADR 0143——dev agent 在项目有已记录的 running 容器之前不认领任务——而用例的 DEV_EVENT_TYPES 列表没有跟上。由于用例查询的正是这个列表，该事件变得不可见：api 甚至看不到它来忽略它。在 exp004 的真实运行中（会话 f782257e），五个 dev agent 在 22:41:38 发出了 dev.started 和 dev.blocked_by_container，engine 在 22:42:07 因 heartbeat_timeout 关闭——整整 30 秒——而该会话的事件在 13 分钟和 32 分钟后仍在到达。每个智能体最后一个可见的事件是 dev.started，它被有意排除在标准之外。五个智能体都在等待一个人启动容器，这正是其他信号已在使用的待处理工作的定义。

    关于该列表是“完整的词汇，经直接阅读 engine 代码确认”的断言，在写下时是真的——而正是它悄悄地过时了。现在让它保持为真的是机制：scripts/ci/vocabulario-de-eventos-dev.spec.ts 从 apps/engine/lib/**/*.ex 提取 dev.* 类型，并在它们与用例的两个列表不一致时失败，指出缺少的类型。它比较而不是生成（agent-areas.ts 的先例），因为这一对中只有一半是可推导的：DEV_EVENT_TYPES 是机械的，DEV_PENDING_TYPES 是判断——哪些状态意味着“需要人来行动”。

    同一种漂移在 WEB 中还有第三个实例，该机制已经把它也覆盖了。DEV_STATUS_EVENTS （apps/web/src/lib/agent-status.ts），团队面板用它来说明每个 dev agent 的状态，也不认识 dev.blocked_by_container 和 dev.awaiting_approval——而在那里后果不是不可见，而是撒谎：两者都落入 switch 的 default: return 'trabalhando'，于是在 exp004 中，面板说五个已经停了好几个小时、等待人启动容器的 dev agent 正在工作。两者都映射到 aguardando，与 dev.awaiting_gate 已经使用的状态相同（智能体在它之外的某件事发生之前不会继续），AgentStatus 中没有新状态；dev.error 以前不在任何列表中，因而让面板回退到之前的 dev.working，现在映射到 falhou。列表不再是列表：它变成了映射 tipo -> AgentStatus，这去掉了 default，使得不回答一个类型意味着什么就无法添加它。交叉测试获得了 engine × web 这一对，还有一项 api 没有的要求——对每个类型做出显式决定，要么映射，要么在 DEV_STATUS_EVENTS_FORA 中声明（tipo -> motivo，目前为空）——因为在面板中，某个 dev.* 类型可以合理地无关紧要；不可以的是因为遗忘而被排除。

    RN-498 — RAG 的 golden-set 在 CI 中真正运行，定时——gate 仍然是 warn

    RN-490 记录了 RAG 的 golden-set（ADR 0132）以手动 mix golden_set.rag 诞生、“从不在 CI 中”，原因与 QA 的 golden-set（ADR 0123）相同：没有 API LLM 的密钥或新的基础设施，就无法在 CI runner 中运行真正的 Ollama。这条 RN 关闭了这一半——只针对 RAG，从不针对 QA——用一个专门的工作流 （.github/workflows/golden-set-rag.yml，schedule + workflow_dispatch），在真实的 Ollama 服务中拉取 nomic-embed-text（与产品其余部分固定的版本相同，如今是 0.34.4），并真正运行 mix golden_set.rag。

    让这对 RAG 可行而对 QA 不可行的区别： RAG 的 golden-set 只调用 embedding 模型——CPU、确定性、没有采样——从不调用做判断的聊天模型，而那正是 QA 的 golden-set 所需要的（昂贵，本质上测量的是非确定性的东西，正如 ADR 0123 本身记录的真实轮次在 6 次中命中 1 到 5 次不等）。ubuntu-latest，没有任何 GPU，在这里足够——对 QA 则不够。QA 的 golden-set 因这条 RN 没有任何改变：仍然完全手动，在 CLAUDE.md 中是 TODO(humano)。

    severidade: warn（docs/gates.yml）仍然是 warn，而原因变了。 不再是“没有带 LLM 的 CI”——而是节奏：工作流是定时的（每晚 + 手动触发），从不按 pull_request 运行。block 会承诺一个并不存在的合并锁——与第 2 步时已经成立的推理相同，现在应用于正确的原因。检索命中率的回退会在 24 小时内（或立即，通过 workflow_dispatch）变成可见的趋势信号，从不是阻断 PR 的 gate——这一权衡被产品负责人明确接受，考虑到每个窗口都要拉取模型并运行 17 次检索（几分钟）的成本。

    工作流中不需要生成任何密钥。 seed-golden-set-rag.ts 从不定义 NODE_ENV，而 api 在生产中会以示例字面值拒绝的四个密钥（RN-114）只在 NODE_ENV === 'production' 时才检查——脚本落入开发分支，毫无怨言地使用开发字面值，不同于 docker/smoke.sh，它有意以 NODE_ENV=production 启动，因此用 openssl rand 生成自己的密钥。

    test_helper.exs 中对 :golden_set_rag 标签的永久排除（RN-490）不变。 它保护普通的 mix test——包括任何有 Ollama 运行的开发者的机器——从不保护新的工作流，后者显式调用 mix golden_set.rag，与一直以来手动运行时所需的方式相同。

    测量后修正：上面的工作流一次都没有绿过。 连续五次定时运行（2026年9月5日至9日）都失败了，而且有三个叠加的缺陷，每一个都掩盖了下一个：

    1. mix golden_set.rag 是一个调用 test 的别名，而 Mix 在 :test 环境之外拒绝这样做——** (Mix) "mix test" is running in the "dev" environment——在运行任何东西之前。apps/engine/mix.exs 中的 def cli 改为为两个 golden-set 任务声明 preferred_envs：正是这一点让这条简短的、各处唯一记录的命令无需环境前缀就能工作。要求调用者使用 MIX_ENV=test，就是把修正转嫁给所有教授这条命令的文字——以及再次忘记的人。

    RN-524 — 发布的产物由工作流身份签名，在同一次运行中校验，校验失败时拒绝而不是警告

    每个正式 tag 都为它发布的东西签名，并在发布 Release 之前校验所签的东西：

    • 五个镜像按 DIGEST 签名（本规则写下时是四个；第五个 broker 随 ADR 0162 加入），读自 .release/images.json——绝不按 tag。tag 是可移动的指针：为 :5.0.0 签名，证明的是签名那一刻该 tag 指向的东西，而不是有人下载时它所指向的东西。digest 是清单早已记录、生产 overlay 早已应用的东西（ADR 0119）；
    • runner 的二进制（本规则诞生时是五个目标，自 ADR 0174 去掉 darwin-x64 后是四个）由一个签名的 checksums.txt 覆盖，而不是每个二进制一个签名——校验了三个而忘了第四个的人无从知道自己忘了；
    • 签名是 keyless 的（GitHub Actions 的 OIDC）：签名的身份就是工作流本身，不存在托管的私钥。自有密钥对意味着又一个 CI 密钥，而本仓库已经见过一个 PAT 悄无声息地过期并否决了两次 tag-release 运行（ADR 0139）；
    • 校验失败是点名的拒绝，绝不是警告。 点一下就能接受的警告，就是不存在的校验。

    清单声明它覆盖了什么。矩阵有意设为 fail-fast: false，所以一个没有构建成功的目标不会妨碍其他四个拥有清单——但作业会在日志中点名被排除的目标，因为列出四个而对第五个沉默的 checksums.txt 比没有更糟：校验了四个的人会以为自己校验了整个发布。这一半曾是书面意图加上没有兑现它的机制：在 needs: build 下，一个构建失败的目标不是不妨碍，而是把它「推迟」了一天——见 RN-565，它让这一半成真并测出了这个数字。

    install.sh 完成安装（RN-547，FASE 30）

    RN-549 — 干净机器上的 E2E 证明「整个」安装：五个环节、在运行中等待的代理，以及无人回到终端即被接手的第一个项目

    FASE 30 的第 8 次会话，最后一次——也是唯一能回答整个阶段所追问问题的一次：在一台干净的机器上，install.sh 结束时本地代理是否在运行且已配对，人是否无需回到终端就能以 Runner 模式创建第一个项目？ 在此之前，答案是一个书面意图：RN-547 串联了五个命令，并以书面形式声明在它的测试中 brabo-runner 是 shell 替身、api 是 node:http——"o que se prova é o ENCADEAMENTO, nunca a integração"。

    测试装置不是在这里诞生的：它被「扩展」了。 .github/workflows/install-e2e.yml 自 FASE 29（RN-534）起就存在，已经在 Actions 的临时 runner 中运行已发布的安装程序——字面意义上就是一台干净的机器，没有 Brabo、没有 .env、没有标记。它证明的东西止步于 .env：计划、状态、三个绝不删除的承诺、无 TTY 路径，以及在模拟 TTY 下的启动。第二个工作流会为了测量便宜的一面而重复昂贵的一面（等待 Release、下载、校验签名）。

    它「不」在 pull_request 中运行，后果是声明出来的，而不是藏起来的。 安装程序对照 Release 的已签名 checksums.txt 校验自身来源（RN-526），后者只在正式 tag 之后存在；让它在 PR 中运行的唯一方式是给它一扇「跳过」校验的门——ADR 0150 拒绝的那扇门，一旦打开就对任何人有效，而不只是 CI。因此：写下这个 E2E 的 PR 并没有执行它，它的检查在没有演练其新增内容任何一行的情况下通过。这与 RAG golden-set 的决定（ADR 0138）相同，原因也相同。

    由此有了在 PR 中「运行」的那一半，这就是它存在的理由。 只在 tag 中运行的工作流，其错误会在 tag 中出现，那时发布已在推出，没人再看那个弄坏它的 PR。scripts/dev/install-e2e.spec.ts 测量这个 E2E 悄无声息地腐烂的两种已知方式：有人放宽闸门（在触发器中加上 pull_request，或传入一个跳过校验的标志），以及有人改写 install.sh 中的一句话——于是工作流中的每个 grep 都不再匹配任何东西，断言不是失败，而是「消失」。提示的金丝雀是推导出来的，而不是背下来的：TTY 的回答按文件、按顺序传入，安装程序中新增的一个 read -r 会让之后的所有回答错位——基目录会变成密码——，所以测试会数提示的个数，并让人去看回答文件。

    E2E 开始证明的东西，每条断言都有归属。 RN-547 的五个环节，逐一针对「真实」的 api 和二进制——账户（RN-546）、在机器上生成的密钥对和盖上的 kid（RN-551）、公钥的登记（RN-552）以及按机器的 unit（RN-545）。再加上在「磁盘」而不是输出上测量的 RN-475 不变量（runner 读取的文件有 kid、有 d，并且 finish 完成时 .parcial 已消失），.env、标记和日志中都没有密码，以及标记中存在 ownerEmail。

    「否定」证明最有价值，那就是待办块的缺席。 RN-547 要求在一个点名的最终块中报告每个失败的环节——并照样以 0 退出。一个看退出码的 E2E 会在五个环节坏了四个的情况下给出绿色。"Nenhuma pendência" 是断言五个都完成的唯一方式，包括工作流说不出名字的那些。

    代理「在运行」并等待的信号是那「一行」，绝不是管理器的状态——这一选择是本 E2E 的核心决定。 perguntarEstado 把 activating 映射为 rodando（RN-088，有道理：「启动中」不是「已停止」），所以 systemctl is-active 和 brabo-runner service status --machine 都会对一个两秒后就会死掉的进程回答在运行。这恰恰是固定的 sleep 所掩盖的竞态，而在这里测量错误的产物——磁盘上的一个二进制、一个写好的 unit——是 E2E 不证明任何东西就给出绿色的最容易的方式。所选的信号是进程在「进入」等待时写下的那一行（RN-550）：它只在代理从磁盘读取了机器密钥、拿到票据、和真实的 api 对话并收到一个「空」列表之后才存在——一次性证明了配对和等待。而且它不是 状态采样：它是已经写进 journal、不会撤销的事实。所以带上限地等待它不是竞态——要么它出现，要么上限耗尽，该步骤失败并显示整个 journal。service status --machine 在它之后进入，作为退出码回答了运维者将看到的内容的确认，绝不取代它。

    阶段的结果由 API 测量，而不是由浏览器。 断言的主体是「代理」，不是页面：它观察的是 GET /runner/projects（RN-543），api 的一个事实。浏览器会通过「同一」路由创建项目，多一层会因与承诺无关的原因失败的东西——而且不会让断言更强，因为断言仍然是代理 journal 中的那一行。浏览器层是存在的（e2e/，ADR 0120），它回答的是另一个问题（三个源、httpOnly cookie、CSRF），有自己的 lockfile，并假定生产 compose 在运行：把它拖到这里，会让安装程序的 E2E 依赖于在一台本应干净的机器上安装的第二个测试装置。证明向导是 web 套件的工作，那里已经覆盖了。这一步测量的是整条链：在终端中诞生的账户通过登录，无需任何验证链接；RN-410 的个人 workspace 存在；项目以 runner 诞生；代理在 RN-550 的 15s/30s/60s 节奏内自行接手它。

    幂等性由 E2E 无需重新安装就能到达的那一半来测量。 api 对第二次 first-account 确实回应 409——使用「生成」的密码，绝不是常量，因为 exigirSenhaValida 在冲突「之前」运行，弱密码会得到 400，测量的就是错误的东西。安装程序如何「处理」这个 409（保持沉默，而不变成待办）是 HTTP 状态码的分类，在 install-fechamento.spec.ts 中针对测试服务器覆盖：在这里重复它需要第二次完整安装，那会走「迁移」路径（RN-530）——经证明的备份、删除、重建——是另一项交付。

    这个 runner 与干净机器之间唯一的分歧来自「环境」，并已点名。 在真实机器上，安装者有登录会话，systemd --user 已经在运行；Actions 作业以非交互方式运行，没有会话，没有会话时 systemctl --user 没有可以对话的总线——service install --machine 会因为一个不属于产品的原因变成待办，而 E2E 会「证明」一个实验室故障。loginctl enable-linger 让用户管理器运行起来；它不是安装程序的标志，不跳过任何校验，也不改变 unit 的行为。

    编写它时出现了两个缺陷，两者都是不可见的，因为工作流从未运行过。 第一个在测试装置本身：回答文件以 nao-migrar 开头，在干净机器上它会落到「标记」的问题上——它不匹配 s|S|sim|SIM，脚本说 "Nada foi gravado" 并以 0 退出，而紧随其下的标记断言就会失败。迁移问题位于 if [ -n "$marcador" ] || [ -n "$sinais" ] 之下，而在干净机器上两者都为空：这个问题不会出现。已更正为「七个」真实回答。

    第二个是「发现」，有意没有在这里修复。 已发布的 install.sh 无法在干净机器上独自启动任何东西：它用 docker compose -f docker/docker-compose.install.yml 启动栈，这是一个相对于其运行目录的「相对」路径——而这个文件不是 Release 的资产，不进入已签名的 checksums.txt（RN-524），脚本也不在任何地方下载它（它唯一下载的是 cosign、清单、自身哈希和 runner 二进制）。compose 还 bind-mount 了 ./postgres/init.sql，所以是「三个」文件而不是一个。按照 runbook 的 sh -c "$(curl … install.sh)" 操作的人，会在已经校验签名、选定基目录并写入 .env 之后，死于 "no such file or directory"。修复意味着决定 compose 是成为已签名的资产，还是安装程序改为克隆——这是另一项交付，不是在发现这个漏洞的 E2E 中顺手要做的事。工作流按 tag 手工带来这三个文件，在一个「说明」这是发现的步骤中；PR 中的测试要求两半（该步骤存在，并且安装程序仍在不下载的情况下使用 compose），而安装程序自行获取它们的那一天，测试会失败——那时正确的做法是删除这个步骤，而不是放宽测试。

    「未」纳入的： 任何跳过来源校验的门；apps/ 未被触碰（发现变成了报告，而不是顺手的修复）；没有第二个安装程序 E2E 工作流；没有放宽任何闸门——尤其是，E2E 仍然不在 pull_request 中。

    设备密钥获得界面，界面说明吊销的范围（RN-561）

    RN-565 — 已签名的清单随 Release「已有」的东西发出，不等待永远构建不出来的平台

    已签名的 checksums.txt（RN-524）是另外两条规则的前提：没有它，GET /runner-releases/binary 以 release_sem_manifesto 拒绝（RN-525），install.sh 拒绝它自己（RN-526）——在所有平台上，包括那些正常附加了二进制的平台。一个延迟的清单不是延迟的清单：对在这段间隔内安装的人来说，它就是缺失的清单。

    测量，针对现有的三个 tag。 在 v4.0.0、v4.0.1 和 v5.0.0 中，darwin-x64 目标（macos-13）在队列中停留了 24h00m01s，被 Actions 的上限取消——三个中都是「同一个」数字，这说明它从未被调度。其他四个作业最多在 4m18s 内结束（v4.0.1 中的 linux-x64，17:38:28Z → 17:42:44Z）。checksums 作业带有 needs: build：always() 保证它会「运行」（被取消的依赖也覆盖在内），却从不保证「何时」运行。

    规则： 清单作业不依赖矩阵。它等待的是 Release 的资产，而不是作业——带上限——，并发布存在的东西，在日志中点名它没有覆盖的内容。一个目标的缺失是预期的结果（::notice::），绝不是错误；Release 的缺失仍然是点名的错误，因为这个工作流只「附加」、从不创建；而没有任何附加的二进制仍然是错误，因为一个空的 checksums.txt 会断言发布没有二进制，而实际发生的是整个矩阵都失败了。

    二进制的上限是 1200 秒，这个数字不是随意的： 它是 build 作业本身的 timeout-minutes: 20——一个有 runner 的目标在开始后最多可能花费的时间。它有意不覆盖的是排队时间，而不覆盖排队时间正是全部要点。所有目标都到达时循环会提前退出，这是正常路径。

    作业「所做」的事情一样都没变。 它仍然从资产（而不是那里为空的 dist-bin/）组装清单，用 cosign keyless 签名，并在附加之前校验——RN-524 不变，一个清单而不是五个签名。而在上限「之后」才附加的目标也不会成为孤儿：--clobber 本来就是为此存在的，重做清单就是用同一个 tag 执行一次 workflow_dispatch。

    本规则「不」做的： darwin-x64 仍然构建不出来。更换标签、去掉该平台或为 runner 付费是负责人的决定，而清单不能依赖它——正是因为依赖它，清单才一直发不出来。

    之后在 AT-065 中测量（2026-09-13，通过演练用的 workflow_dispatch）： macos-13 是没有 runner 的标签（GitHub 已于 2025 年 12 月退役该镜像；在队列中 30 分钟，被取消，run 34769280227）。macos-15-intel 在 3–22 秒内调度并构建，但在 --self-test-pty 上失败，因为在 Bun 下，node-pty 的 onData 不交付子进程的输出（oven-sh/bun#25822，仍开放）；同样的证明在同一 runner 上在 Node 下通过（run 34770476634）。 待定的决定不再是关于 runner 的，而是等待 Bun 还是去掉该平台。上面的规则不因此改变。

    于 2026-09-27 决定（ADR 0174，AT-065）： 该平台已移除。 矩阵变为「四个」目标，ALVOS_ESPERADOS 随之调整——缺失正是对照它来声明的，把 darwin-x64 留在那里会让每个清单永远宣布一个本是决定的缺失。Mac Intel 使用 npm install -g @brabo/runner（在 Node 下，同样的证明能通过）：install.sh 说明这一点而不尝试下载，代理 GET /runner-releases/binary 以指向 npm 的自己的 400 拒绝 darwin-x64，浏览器面板甚至不请求下载。本 RN 的规则不变：它仍适用于任何失去 runner 的目标，而当矩阵、api 的列表、安装程序的 case 和浏览器的列表出现分歧时，scripts/ci/alvos-do-runner.spec.ts 会失败。
