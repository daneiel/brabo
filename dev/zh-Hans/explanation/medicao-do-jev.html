Jev 工具路由器的测量

AT-237（EP-029，HS-063）。一次产品之外的测量：apps/ 中没有任何代码 导入这里的代码，数据库中不写入任何东西，这里也不声称任何产品收益——那属于 AT-239，它比较有路由器和没有路由器的轮次。被测量的路由器是 AT-235 所规定的； 它所依赖的决定来自 AT-236。

于 2026-09-29 针对本地 dev 实例（compose 项目 brabo-dev）测量，仓库处于 d48f99f8ec。第二轮——state 的变体、等价类、拟合/验证划分、top-2 以及 按原因划分的差距——在下文。

全部位于 scripts/jev/，用仓库的 Node 运行（type stripping，无构建步骤， 无新依赖）。

步骤，而不是工具调用​

路由器在每次调用聊天模型时咨询一次，在 provider.chat 之前（AT-235）。一个 步骤可以携带多个工具调用——Criativo 的一次响应里有十个 emit_artifact，dev 的 一次响应里有 terminal + read_file——因此对每个 tool.call 询问一次 Jev，会提出 产品从不提出的问题，而且所用的 state 已经包含同一步骤中的兄弟调用。

event log 没有步骤标记（AT-235，缺口 1），所以边界来自 token_usage：api 在 engine 写入该响应的 tool.call 之前为每次 LLM 调用写入一行。同一会话、同一 执行者在两条连续行之间的所有 tool.call 属于同一个步骤。由此得出三种标签：

  • 只有一个工具的步骤（对它的一次或多次调用）：标签 = 该工具；
  • 异构步骤（两个不同的工具）：命中 = Jev 的选择是其中之一——但把菜单限制为 一个工具会砍掉其余的；
  • 在其行之后没有 tool.call 的步骤：模型以文本作答（或失败）。这是 responder_sem_ferramenta 用这种方法唯一能得到的标签——brief 预期一个都没有； 步骤边界给出了七个。

时刻作为固定宽度、带微秒的 UTC 文本进行比较：用量行和一个步骤的第一个 tool.call 有时落在同一毫秒。

发送的 state​

AT-235 的格式，从步骤之前已存在的内容中截取：agente；pedido——对会话型 智能体，是用户写的最后一条 chat.message；对 dev agents 和任务 gates，是 dev.working 中任务的标题；contexto——智能体的身份加上项目的 agent_instructions 行（如果存在）（系统提示词的两层，而不是组装后的完整提示词）； passos_recentes——该执行者在该会话中的最后 6 次调用，参数和结果截断为 500 个 字符。问题是一个 choice，其 criteria 是目录的 {name: description} 加上保留的 responder_sem_ferramenta。

请求发往 POST https://openrouter.ai/api/alpha/decisions，模型为 typesafe/jev-1.13。对 AT-235 的一处更正，经过测量：questions 是一个按问题 id 索引的对象，不是列表——列表形式会收到 400 expected record, received array。响应是 answers.<id>.{choice, probabilities, confidence}、usage.{input_tokens, output_tokens, cost}、一个 id（gen-dec-…），以及 model 中一个带日期的快照 （本次执行的每个响应中都是 typesafe/jev-1.13-20260917）。

回放看不到的东西​

  • 循环的第一条消息。 ToolLoop 智能体（dev agents、gates、Anamnese、 Infra-Workflows）从一条在代码中组装的用户消息开始——任务、用户故事、模块映射 ——它从不进入 event log。回放对 dev agents 和任务 gates 只有任务标题，对 qa-estrategia、appsec、anamnese 和 infra-workflows 什么都没有。产品的 state 会携带这条消息。qa-estrategia 的 0/16（Jev 每次都回答 responder_sem_ferramenta）测量的既是 Jev 也是回放的盲区；这些行是下限，不应 决定任何事。
  • 系统提示词的其余部分。 contexto 是身份和项目指令行，不是组装后的提示词 （业务规则、任务状态、文件）。
  • 标签是否正确。 选择工具的模型不是基准真相；157 个步骤被标为可疑并单独报告 （"无可疑"）。干净步骤上的一致率（31%）低于总体（47%）：可疑步骤大多是 dev agents 失败的 terminal 调用，Jev 也倾向于选择它——因此标错的步骤不能解释 分歧。
  • 效果。 受限的菜单会改变模型接下来的行为；回放只是把一个选择与记录下来的 选择比较。轮次是否变得更短、更快或更便宜，是 AT-239 的事。

数字之外的两个发现​

  • 异构步骤很常见： 295 个中有 36 个（12%）。把菜单限制为一个工具会把每个这样 的步骤变成至少两个步骤——AT-235 的缺口 1，现在有了计数。
  • AT-235 中目录同步的风险（缺口 3）是真实的，只是换了个名字： GET /api/v1/models 不列出 typesafe/jev-1.13，但列出了 typesafe/jev-router——一个聊天路由器，价格为 -1。模型同步会把它当作聊天 模型（非活动）导入。在此记录，未作修改。

第二轮（2026-09-29）：差距在哪里​

在第一轮之后由负责人提出：重复测量，尝试达到至少 90%，并准确说出差距在 哪里。未达到。 在验证步骤上，Jev 的 top-1 按等价为 73%（95% CI 66–79%， n = 160），严格为 66%（58–73%）；它的 top-2 达到 90%（84–94%）。本节其余部分 是协议、数字，以及对剩余 43 个 top-1 错误的人工阅读。同一实例，与第一轮相同的 保留：一个小项目、一天、一个聊天模型；不声称任何产品收益（那是 AT-239）。仓库 处于 bc7f4c0738，分支 test/replay-do-jev-v2。

协议（在任何执行之前写下）​

  • 只用产品在运行时、在步骤之前能产生的东西。 目标步骤的任何内容都不进入 state：既不包括它调用的工具，也不包括参数、结果，也不包括模型在同一步骤中写的 文本（Passo.texto 只从之前的步骤读取；variantes.spec.ts 对每个变体断言 目标步骤的调用、参数、结果和文本都不存在）。每个新字段都有其在 engine 中的来源， 引用在 scripts/jev/variantes.ts 的文件头中。
  • 等价类在运行前固定于 scripts/jev/equivalencia.ts，依据工具的语义，并与 严格规则（第一轮的规则，使 47% 仍可比较）并列报告。三层累积： E1 命令只读取/列出/搜索的 terminal（ls、find、cat、pwd、grep、 head、git status/log/diff……——复合命令按最强的片段计，执行 > 写入 > 读取）≡ read_file/search_workspace；E2 read_file ≡ search_workspace； E3 写文件的 terminal（重定向、heredoc、tee、sed -i、cp、mv、 touch）≡ write_file。故意不对称：Jev 选择 terminal 只对 terminal 调用 有效，而一个执行的命令（npm、node、rm、mkdir、git commit……）除了 terminal 不等价于任何东西。标题数字是完整规则（E1+E2+E3），严格规则并列。 看到结果后没有重新分类任何东西；这些类仍然判错的 3 个错误在下文照此计数。
  • 拟合 × 验证按执行划分，而不是按步骤。 一组是一次 ToolLoop 执行（dev agent 的一个任务、一轮 gate），对会话型智能体则是该智能体的整个会话。各组按名称的哈希 排序，每组进入到目前为止步骤较少的那一半——确定性的，且对任何结果不可见。 328 个合格步骤：167 个拟合，161 个验证（下面的 n 计的是有工具的步骤：161 和 160）。变体只在拟合上迭代；验证在之后、每个变体问一次。一个已声明的事件： 在最初几次拟合执行后，我发现 Anamnese 的 skip_proficiency / emit_proficiency 也会结束循环，于是把它们加入了用于组装 state 的执行边界 列表。若用更正后的列表做划分，也会把 167 个拟合步骤中的 154 个移到验证，因此 划分保留了第一次请求之前的列表（FERRAMENTAS_DE_FIM_DA_DIVISAO），只有 state 使用更正后的列表。依赖边界的四个 state 变体在拟合上重新问了一遍（US$ 0,075， 在花费记录中以 .descartado 保存）。
  • 冻结的快照。 dev 数据库在会话期间继续接收来自其他工作的步骤（结束时 335 行 用量对比开始时 333 行）；分析运行在 333 行的快照上，事件截止到相同的序号 （--dados-cache）。自第一轮以来新增的 26 个步骤（302 个已回答 → 328 个合格） 全部是拟合那一半中 Anamnese 的步骤。
  • 花费上限 US$ 1,00，针对 usage.cost 之和，在每次请求前与输出目录的累计 总额（.jsonl 和 .descartado）核对。花费：US$ 0,414，共 4 604 次请求 （见"延迟与成本"）。

上限：覆盖率没有说的​

覆盖率是端到端准确率的上限，不是准确率。 菜单包含正确的工具；智能体的模型仍需 在选项中选中它。标签（"聊天模型调用的工具"）是智能体从完整目录中做出的选择，因此 完整菜单按构造就是 100%，而受限菜单只会损失。不借助产品可以说的，对验证上的 P3， 把 160 个步骤分开：

  • 99（62%，54–69%）：菜单中的每个工具都正确，因此智能体的任何选择都正确—— 下限。
  • 46 个是"有争议的"：恰好一个选项正确，由智能体自己决定——28 个只有上一个工具 正确，18 个只有 Jev 的选择正确。总是选上一个工具的智能体结果为 127/160 = 79%； 总是选 Jev 选择的，117/160 = 73%（又是第二轮的基线）；抛硬币的，76%。一个比两者 选得都好的智能体——这正是全部赌注——落在 79% 与上限 91% 之间。
  • 其余 15 个在菜单之外：无论智能体做什么都丢失。

所以端到端的范围是 62% 到 91%，落在哪里取决于智能体的模型对情境的理解程度，而 回放看不到这一点。只有实时测试（AT-239）能回答。

工具定义上的节省​

目录原本有每个工具的描述（catalogo.json），现在还有 definicoes：每个工具完整 spec/0（名称、描述和参数 schema）的字节大小，由 engine 序列化（catalogo.exs， 重新运行；文件其余部分没有变化）。token 是字节除以 4，这是整个回放使用的近似值。 在验证上，P3 从每次调用 746 个定义 token 降到 138——少 608 个 token，减少 81%：一个 dev agent 的八个工具重 3 068 字节，一个两项菜单约重 500。P1 节省 596， P2 节省 644（对该一半步骤的平均值；拟合那一半节省较少，因为 Anamnese 保留完整 目录）。

这值多少是另一个问题。对 Jev 的调用本身读取约 1 870 个 token（US$ 0,0000769）， 所用模型比智能体的模型便宜得多；定义上的节省是每次调用智能体模型的 608 个 token。 平衡点是每百万 token US$ 0,126 的输入价格（0,0000769 / 608）：高于它，节省就能支付 对 Jev 的调用，不考虑缓存。缓存是陷阱：provider 会缓存请求的前缀，工具定义在 最前面，而一个逐步变化的菜单会改变前缀——节省可能在缓存未命中中被吐回去。这需要 实时测量，也是下面的测试记录缓存 token 比率的原因。

  • 执行前写下的缓存保留，正是在 DeepSeek 上发生的事。 菜单削减了提示词（token −26%），但逐步变化，于是缓存前缀被打破：来自缓存的份额从 84% 降到 45%，而聊天账单 在发送更少 token 的情况下上升了 ×1,9。在此之上，Jev（每次执行 US$ 0,0004）是 一整次关闭执行成本的三分之一。
  • 在 Haiku 上任何一组都没有缓存（工具不发送 cache_control，它所移植的产品线上 形式也不发送），因此提示词 token 的 −40% 直接进入账单：每次执行 −31%，Jev 占其 2%。
  • 延迟跟随聊天的速度，正如 AT-239 所预期。 对 Jev 的调用是串行的（DeepSeek 执行 中每次调用 p50 232 ms / p95 358 ms，Haiku 中 217 / 319 ms）：在 13 s 的 Haiku 执行 中它被少一个步骤所吸收；在 3 s 的 DeepSeek 执行中它给中位数增加 1,5 s。
  • 质量：Haiku 上相差一次执行，区间重叠（60%–98% 对 72%–100%）——在这五个小任务 上，既没有证据表明路由器有助于质量，也没有证据表明它有害。

建议（已测量——由负责人决定）​

限制，按执行前写下的规则：在聊天模型没有生效的提示词缓存、且慢到额外一次串行调用 微不足道的地方保持路由器开启（Haiku 类，每百万 US$ 1,00/5,00），在 provider 的大部分 输入来自缓存且聊天很快的地方关闭（DeepSeek 类）。支持这一点的数字就是上面规则中的 行：Haiku 成本 ×0,62、延迟 ×0,95，无质量损失；DeepSeek 成本 ×2,21、延迟 ×1,45，无 质量收益。

这不涵盖什么，以及限制需要什么：

  • 只测量了 dev agents（ToolLoop）。 之前的解读——对七个会话型智能体没有证据 ——仍然成立；这里的任何东西都不延伸到它们。
  • 区分是按模型的，而产品的开关是按 workspace 的 （PUT workspaces/:workspaceId/tool-router）。按模型（或按"缓存生效"）的限制并不 存在；创建它是一个新决定和一项新改动，这里没有做。在那之前，按 workspace 测得的选择 是：如果它的智能体运行在没有缓存的 Haiku 类模型上就开启，如果运行在有缓存的 DeepSeek 类模型上就关闭。
  • 样本和任务都很小（每组 10 次执行，五个 4 到 16 步的任务）。成本和延迟的比率 宽到足以读出；一次执行的质量差异则不然。
  • 缓存的效果取决于 provider 的缓存，不只是速度：开启了提示词缓存的 Haiku workspace 很可能会向 DeepSeek 那一行移动。未测量。

执行之前这里的临时建议（限制：dev agents 开启，会话型智能体关闭）被上面规则的结论 取代，正如那一段所说的那样。
