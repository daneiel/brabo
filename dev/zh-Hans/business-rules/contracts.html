    RN-028 — 由 capability 决定，而不是提供方的名称

    不支持的操作（本地提供方上的分支保护）在 capabilities 中声明，并以 GitNotSupportedError 拒绝——永远不会静默失败。

    共有四种 capability：自第 2 阶段起的 protectBranch 和 pullRequests，以及自 FASE 26 起的 listTree 和 pullRequestDiff（Code 标签页，只读）。规则并没有因它们而改变——改变的是覆盖范围。而声明的标准仍然是证明：只有当测试套件在该提供方上执行了它时，capability 才是 true；没有证明就声明为 false 并降级（与 ADR 0041/0042 的标准相同）。

    • 位置： packages/shared/src/index.ts（GitProviderCapabilities）；两个读取操作的上限在 apps/api/src/domain/git/git-read-limits.ts 中，不放在 shared 中，因为 shared 100% 是类型
    • 测试： 唯一的契约套件 test/contract/git-provider.contract.ts，针对三个提供方运行
    • 来源： ADR 0001

    RN-087 — Dev Lead 是执行的唯一外部地址

    存在一个对话型 agent dev-lead，它接收 Arquiteto 的 handoff（自 RN-672 起，来自 Infra，项目容器处于 running），并提议执行计划：每个模块多少个 agent 以及为什么。它不写代码——它分配工作并为之负责。

    在它之前，RN-083 中"由 lead 决定"这句话没有主人。 Arquiteto 完成后，执行由一个按钮启动，中间没有人评估有多少工作。

    dev-<modulo> 不再能通过 handoff 寻址。 这不是新的例外：这是 ADR 0038 的规则——外部 handoff 只寻址区域的 lead 或没有区域的 agent——开始像对 QA 和 Infra 一样对 dev 生效。在没有 Dev Lead 时，它们是没有区域的 agent，因此是有效目标；成为成员后，就不再是了。

    dev 区域是第一个动态区域，正是它迫使使用谓词：成员是 module_map 的每个模块一个，由 Arquiteto 决定，每个项目都不同，因此没有可枚举的列表。dev-lead 与成员匹配相同的 dev- 前缀，排除它的是通用规则lead 永远不是自己区域的成员——它适用于任何区域，只存在于一处。第一个版本在三处重复这个排除，变异检查表明没有一份副本是测试可达的：每一份都能在另一份被变异时存活。

    计划是 proposed_action（由 ADR 0086、RN-284 修订）。 在这次变更之前，计划成为简单的事件，没有审批：理由是提议没有外部效果——花费发生在 agent 启动时，上限在那里要求授权；把提议变成待决定的动作会让你对同一件事决定两次。对 docs/fluxo.yml × 代码的审计发现，自 ADR 0085 起流程就已经把这个输出声明为 via: proposed_action，而代码从未被调整为一致——产品所有者判定是代码错了：计划是会话将在并行上花多少钱的第一个真实决定，用户开始在看到一次真正的审批之后才决定激活执行，而不只是读到消息流中的一行。旧的教训没有消失——它正是 propose_execution_plan 没有进入 decide.ts 绝对上限块的原因（见 RN-284）。

    成功的计划结束回合——在没有暂停的路径上。** 在第一次真实执行中，Dev Lead 在同一会话中登记了两次 execution.plan_proposed——文本不同，总数相同——因为循环回到了模型，它又提议了一次。事件日志是不可变的：留下了两份提议，没有任何东西说明哪个有效。工具 spec 中"只用一次"的指示是请求，不是保证；保证的是循环停止。自 ADR 0086 起，当提议处于 pending 时，结束回合的是暂停的停止（RN-284）——立即成功（auto_approved/executed/approved，见 RN-284）继续以一贯的方式关闭循环。

    是成功，而不是"调用了工具"：被拒绝的计划（空的，或某个模块零个 agent）让循环继续，否则拒绝会变成回合结束，模型永远没机会修正。这道防护的第一个版本只看工具名称，就有这个缺陷——是由行为测试发现的，而不是靠阅读。

    空计划，或某个模块零个 agent 的计划，在提议任何东西之前就被拒绝——提议一旦创建，就是用户的真实决定，而一个提议了一半的计划无从撤回。

    • 位置： apps/engine/lib/engine/agents/dev_lead_server.ex 和 dev_lead_tools.ex；寻址规则在 apps/api/src/domain/agents/agent-areas.ts；handoff 在 application/use-cases/agents/offer-infra-handoff.use-case.ts
    • 测试： apps/engine/test/engine/agents/dev_lead_tools_test.exs, dev_lead_server_test.exs（o plano ENCERRA o turno、o plano recusado NÃO encerra o turno）， apps/api/test/domain/agents/agent-areas.spec.ts（o dev de módulo DEIXOU de ser endereçável、`dev-lead` É endereçável, apesar do prefixo）和 test/application/use-cases/agents/offer-infra-handoff.use-case.spec.ts
    • 来源： ADR 0053，FASE 14d； 审批机制由 ADR 0086 修订

    RN-110 — blame 是 GitProviderContract 的第 13 个操作，与其他读取使用相同的缺失词汇

    FASE 26 中声明的 blame 待办事项的基础（还没有界面使用它——在下一波中到来）。blame(ref, path) 返回 GitBlame | null，null 的含义与在 getFileContent/ listTree 中完全相同：该 ref 中文件缺失，或 ref 不存在。同一个标签页有两种"不存在"的词汇，会让界面以两种方式处理同一种情形——这与之前两个操作已经适用的理由相同。

    每个提供方用自己的手段计算，因为没有公共端点：GitHub 的 REST 中没有 blame（只有 GraphQL——这是该提供方唯一使用 GraphQL 的操作），GitLab 有 repository/files/:path/blame，本地则来自 git blame --porcelain，这是三者中唯一在本次会话中针对真实仓库测试过的（另外两个只针对契约测试的假后端——环境中没有 GITHUB_TEST_TOKEN/GITLAB_TEST_TOKEN，针对真实 API 的证明由手动 smoke 完成）。GIT_BLAME_LINE_LIMIT（2000）截断真正巨大的文件——在内容路由中已经按字节截断，但 blame 在决定之前会从提供方读取整个文件。

    RN-111 — listPullRequests 是 GitProviderContract 的第 14 个操作；可浏览列表按 id 打开同一个 diff

    CodeDiffPanel.tsx 在一个可点击的列表中使用 listPullRequests(state?) （id/编号/标题/作者/状态/分支，带按状态的过滤）；点击一项会复用已经存在的同一个按 id 的 diff 流程——没有新的读取路径，只是让人到达 id 而不必记住它。已经知道 id 的人（例如从审批页来的）仍然可以直接粘贴。

    listPullRequests(state?) 为每个 PR 返回一个摘要 （GitPullRequestSummary：id、编号、标题、作者、状态、分支、 updatedAt）——而不是 GitPullRequest，后者是写入（打开/合并）的类型，从未有过标题或作者，因为两个操作都不需要。独立的类型避免写入获得只有读取才使用的字段。

    local 有 PR——Fase 4a 的 sidecar 存储已经是来源，而题述中的假设（"纯本地仓库的概念中不存在 PR"）站不住：自那以后 dev agent 的自包含模式一直在创建本地 PR。三个能力都是 true。GIT_PR_LIST_LIMIT（100）只有一页，没有后续分页——这是供人浏览的，而不是历史同步。

    RN-112 — listBranchesDetailed 是独立的操作，与 listBranches 分开

    丰富下拉菜单的基础，现在由 CodeBranchPicker.tsx 使用 （ahead/behind、PR 徽章——FASE 26b 之后的那一波关闭了 CodeShell.tsx 声明的待办事项）。决定是不扩展 listBranches——最初的第 13 个操作，Gitflow 的 bootstrap 调用它，而不需要这些：丰富信息的代价是每个分支多一次对提供方的调用（GitLab 中是两次，它没有一次调用就返回比较两侧的端点，不像 GitHub 的 compareCommitsWithBasehead 和本地的 git rev-list --left-right --count）。把这个代价附加到每次分支的采纳/创建上，会把 bootstrap 变成一次昂贵的扫描。两个操作在契约中共存：listBranches 给 bootstrap，listBranchesDetailed（第 15 个）给代码标签页——GitBranchDetail 只在形式上扩展 GitBranch，从不在调用者的契约上扩展。

    ahead/behind 总是相对于仓库的默认分支 （ListBranchesDetailedInput.defaultBranch，调用者已经知道——再向提供方要一次，就是为了重新发现已经有的东西而多调用一次）。当提供方无法计算时（孤儿分支、无关的历史），两者都为 null，这是诚实的降级，绝不是编造的数字。GIT_BRANCH_DETAIL_LIMIT（30）出于 FASE 26 第 34 项同样的流量原因进行截断——没有它，一个有数百个分支的仓库每次打开下拉菜单就会变成数百次调用。

    • 位置： packages/shared/src/index.ts（ListBranchesDetailedInput、 GitBranchDetail、GitBranchDetailList、GitBranchPullRequestRef、 能力 branchesDetailed），apps/api/src/infrastructure/git/{github, gitlab,local}-provider.ts，git-read-limits.ts （GIT_BRANCH_DETAIL_LIMIT），read-project-code.use-case.ts（方法 branches），code.controller.ts（GET /projects/:id/code/branches）； 在 web 中，apps/web/src/lib/api-client.ts（getCodeBranches）和 apps/web/src/routes/code/CodeBranchPicker.tsx——下拉菜单本身，从 CodeShell.tsx 打开
    • 测试： git-provider.contract.ts（"listBranchesDetailed" 块）， read-project-code.use-case.spec.ts（"branches detalhadas" 块）， apps/web/src/routes/code/CodeBranchPicker.test.tsx
    • 边界情况： branches() 方法位于与其他六个读取相同的用例中（ReadProjectCodeUseCase），而不是靠近 bootstrap——它是代码标签页的读取，具有与其他读取相同的凭据解析和相同的容器闸门（RN-105）；把它当作 bootstrap 的操作会把两者都重复一遍。分支列表之外的 ref（tag 或 sha）仍然可达——下拉菜单的页脚有一个手动输入框，因为 listBranchesDetailed 不枚举这两样东西。

    RN-341 — QA 策略是 qa-lead 的第二个时刻，并且从不挂起

    docs/fluxo.yml 把 qa-estrategia 角色声明为 proposto，拆分标准写在注册表本身中：“pode ser o próprio qa-lead em segundo MOMENTO, não necessariamente agente novo — a separação é de entregável”。ADR 0090 恰好构建了这一点：Engine.Gates.QaEstrategiaAgent 是无状态模块（不是 GenServer），由 Engine.Gates.QaLeadServer.run_design/3 触发——在同一个 qa-lead 进程中一个新的、附加的入口，不触碰 run/2（一贯的路径，PR 评审，绑定到 DevAgentState.find_by_task_id）。

    上下文是轻量的**，交付物的分离正体现在这里。** Engine.Gates.QaEstrategiaContext.fetch/3 只获取用户故事（来自 EngineApiClient.list_backlog/1，PO 已经在读的树——RN-164）和当前的 module_map（来自 EngineApiClient.get_infra_context/2，Infra Lead 消费的同一个 GetInfraContextUseCase，这里只用 moduleMap 字段）——没有 dev_state，没有 worktree_path：implementavel gate 在 dev 之前运行，那时还不存在 dev agent、worktree 或 task_id。api 中没有新路由——这两个函数早已存在。

    从不挂起。 工具注册表（ReadFile、SearchWorkspace、 EmitPlanoDeTeste）不包含 terminal 也不包含 write_file——这是 Engine.Harness.Hooks.ActionPipeline 拦截以创建 proposed_action 的仅有的两个工具。没有任何调用经过操作流水线，这个智能体的 ToolLoop 永远不会产生 :pending，run_design/3 在自己的 handle_cast 中同步运行——没有挂起/恢复机制，与 QA 领域的其余部分不同。

    迭代上限保持 8（对话型），而不是 60（gate）——是有意为之，不是缺口。 这个智能体在没有 token_budget_micros 的情况下运行——还没有任务，也没有任务预算。RN-085 的标准不是“谁工作量大”：而是“在迭代上限之外是什么在约束花费”。下面没有预算，提高上限会放大最坏情况而没有任何东西来遏制——这与 infra-workflows 即使使用工具也保持在 8 的原因相同。"qa-estrategia" 没有在 Engine.Harness.Iteracoes.tipo/1 中获得自己的子句：落入默认值是正确的决定。

    交付物——emit_plano_de_teste（综述、可验证的可执行标准、通用且不绑定框架的自动化策略——这是本战线的范围决定，写在模型读取的 spec/0 中，而不是代码中的校验）——变成制品 artifact.plano_de_teste （ArtifactEmitter.emit/5，schema 经过校验，criteriosExecutaveis 不能为空），位于调用 run_design/3 的同一个会话的事件日志中——assess_implementability（RN-340）之后就在那里读取它。失败（迭代上限、预算、模型停下而没有发出）从不是沉默的：带来源的持久 agent.error，与 RN-059 标准相同。

    自 RN-674（ADR 0192）起，时刻变了。 第二个时刻仍然属于 qa-lead，没有新智能体，并且仍然从不挂起；但它在交付之后运行，在 run/2 循环的开始，带着 dev 的 worktree 和 diff 中的文件——run_design/3 和 QaEstrategiaContext 被移除，制品获得了 taskId。上限仍是 8，现在下面有任务的预算。

    RN-605 — 镜像拉取是 start 的一个「具名」步骤，在控制上限之下，超时会说明大镜像启动不了

    Docker 端口的 start 原本不做拉取：是 docker run 在内部做的，在 TIMEOUT_DE_CONTROLE_MS（30 秒）之下。在 AT-234 中用守护进程替身（镜像缺失、45 秒拉取、不休眠、无网络）复现：超时以 ComandoDeDockerFalhouError 发出——「docker run … terminou com código -1: (sem saída de erro)」——，在 broker 中变成 origem: null 的 502，到达 api 时没有名字。而杀掉 CLI 会「取消」拉取（在 Docker 29.8.0、containerd 上测得）：在随后的 60 秒内镜像仍然缺失，所以「o pull pode seguir no daemon」这句话不成立。

    在测量过的四种出路中（约 300 秒的自有上限、异步 start、在镜像决定时提前拉取、只给名字），维护者决定了 D——只给名字（2026-09-27）。规则：

    1. 拉取是显式的。 在 run 之前先 image inspect；已存在的镜像不会被再次下载（与 run 的 --pull missing 相同）。缺失时，在「同样」30 秒的控制上限下执行 docker pull——没有更大的上限。
    2. 超时有名字。 PullExcedeuTetoError，来源 infra，带有镜像、上限和完整的后果：拉取被取消，镜像仍然缺失，大镜像无法经由这条路径启动，修复办法是事先在宿主机上下载。在断言这一点之前，适配器检查守护进程（docker version）：守护进程宕机仍是 DockerIndisponivelError。因其他原因失败的拉取走一贯的路径（ComandoDeDockerFalhouError，没有来源，ADR 0128）。
    3. 名字会穿过去。 broker 以 origem: 'infra' 回应 504，api 在 BrokerRecusouError 中转发它——origem 有值，绝不是 null。在 runner 模式中，同一个适配器在用户机器上运行，消息在 container_start_result 中到达。
    4. 等待 start 的一方的上限计算完整的最坏情况：resolver 的两个 ps、image inspect、pull、run 以及诊断用的 docker version——六次控制调用（CHAMADAS_DE_CONTROLE_NO_START）。api 等待 10 + 6 × 30 + 5 = 195 秒（TETO_DE_MUTACAO_MS）；engine 在 RunnerRouter 中，start 等待 6 × 30 + 5 = 185 秒，stop/remove 等待 4 × 30 + 5 = 125 秒（以前是 60 秒，少于 resolver 加操作）。
    5. engine 的 propose_action 等待 api 在其内部进行的执行。 自动批准的 container_start、container_start_via_runner 和 container_stop 在同一个请求中被「执行」（ProposeActionUseCase），而调用落入 Req 的 15 秒默认值——一个长的 start 即使没有拉取也会以传输超时返回。现在它带有 225 秒的 receive_timeout（api 的上限 + 30 秒），在 api 中镜像为 TETO_DO_PROPOSE_ACTION_DE_CONTAINER_NO_ENGINE_MS；两边的测试核对 broker < api < engine 以及 runner < engine。container_remove 不在其中：它从不以自动批准诞生。

    RN-738 — 停止项目容器是即时的，/containers 的行在决定时重新读取

    • 规则： 每个项目容器都以 --init 启动——这是 docker run 组装的「常量」，在 DockerViaCli 中，绝不是 spec 的字段（隔离就是类型，ADR 0130）；对 broker 和 runner 都适用，它们使用同一端口。等待命令（sleep infinity）是没有 SIGTERM handler 的 PID 1，而内核不会向 PID 1 递送默认动作的信号：docker stop 会等 10 秒然后杀掉（Exited (137)）。在一次性容器中测得：没有 --init 时 10.25 秒，有时 0.20 秒。在 /containers 页面，决定待处理操作（批准、拒绝、始终允许）会使 ['containers-overview'] 和 ['container-lifecycle', projectId] 失效，在 finally 中——调用失败或掉线时也一样——并把 promise 返回给卡片。没有新的轮询（RN-579/632）。

    RN-807 — 超出上限的 exec 以超时返回，命令在容器内被杀死

    • 规则： exec（属于 DockerPort）是否超出上限，除 killed 之外还由「时钟」决定（已用时间 ≥ 上限），因为 docker exec 客户端会捕获 SIGTERM（来自 timeout，属于 execFile） 并以代码 0 退出——测得：上限 3 秒下的 sleep 30; echo FIM 返回 erro: null、stdout: ""，适配器返回 exitCode: 0。超出 120 秒的 agent 命令返回「exit 0」，QA 批准了会卡住的测试套件。现在超时返回 exitCode: -1、timedOut: true 以及超时标记。杀死客户端并不会杀死命令：exec 把命令（仍作为「一个」参数，原封不动）包在一个 sh 中，该 shell 把自己的 PID——进程组和会话的领导者，因为运行时都做 setsid，在每个 docker exec 上——写到容器的 /tmp 中；超时时，适配器通过这个 PID 杀死整个「进程组」（SIGKILL），在一次内部调用中，端口上没有新操作（ADR 0130）。测量后被否决：使用 busybox 的 timeout，在 sh -c 内——看守进程随客户端一起死掉，sleep 存活。如果杀死失败（例如 /tmp 不可写），标记会说明进程可能存活。
    • 位置： packages/docker-port/src/docker-cli.ts:269（estourouOTeto）， packages/docker-port/src/docker-cli.ts:455（matarExecEstourado）
    • 测试： packages/docker-port/src/docker-cli.spec.ts（"erro nulo depois do teto É estouro"；"no estouro mata o grupo do comando DENTRO do container"； "o comando que estoura volta timedOut e MORRE dentro do container"，针对真实 Docker，没有守护进程时跳过）
    • 来源： AT-482

    RN-820 — 守护进程重启时项目容器会自行恢复

    • 规则： docker run（由 DockerViaCli 组装）带有 --restart unless-stopped 作为「常量」，与 RN-738 的 --init 并列——spec 不增加字段，ADR 0130 的隔离不变。重启的守护进程（系统更新）会重新启动项目容器；明确的 docker stop（生命周期的 container_stop）「不」会被撤销，因为 unless-stopped 不会重启手动停止的——绝不用 always。测得：unless-stopped 容器用 docker stop 停止后保持 exited，RestartCount=0。
