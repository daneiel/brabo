    BRB 登记表

    BRB-NNN 发现在维护者的 vault（07-backlog/Backlog de Melhorias (Brabo)）中提出 并排定优先级，那里保存全部 33 项，含优先级、工作量、来源、提案和一个"完成标准"。那份登记 是一项发现是什么以及它是否已关闭的来源。

    本文件是仓库能够验证的那一部分。由 FASE 29 第 1 次会话创建 （fase-29-instalacao-de-uma-linha.md）。

    覆盖标准

    从 BRB-001 到 BRB-033 的每个 id 恰好有一行，按数字顺序排列。直到 2026-09-27，本页 只列出代码能够证明或反驳的发现——33 项中的 11 项——其余在这里不可见，其中包括 vault 已经 测得为已修正的六项（AT-186）。每个 id 一行不花任何代价，并让证据的缺失变得可见而不是沉默。 每一行包含：

    • vault 中的状态——于 2026-09-27 从 vault 的登记中复制。这是维护者的决定，从不在 这里决定。
    • 在此测得——仓库所显示的内容，于 2026-09-27 针对 dev 在 34c1c83bdc 上测得，除非 证据另有日期。
    • 证据——该测量背后的 文件:行、PR 或运行。

    主题位于本仓库之外的发现（vault 自身的笔记、产品决定、付费凭据）仍然有一行，标记为 此处不可验证，并附原因。一个毫无信息的 id 会带一个 TODO(humano)——目前没有。vault 中 新的 BRB-NNN 在第一次提到它的同一变更中在这里获得它的行。

    为什么有这个文件

    BRB-018 是下面第二条规则在实践中的样子。本文件诞生时，代码中关于它的任何东西都没有改变 ——没有写任何重投影——但仓库获得了说明它为什么仍然开放、以及开放期间花费多少的能力， 因此这一行先于修正存在。该命令现在存在（RN-569）；这一行保留，是因为集群中的证明不存在。

    有两个 id——BRB-005 和 BRB-031——在这里的五份文档中以散文形式被引用，却没有任何人能核对 的状态。其他 id 对本仓库完全不可见：在整个磁盘上搜索只返回这两个。

    代价是测量出来的，不是想象出来的。FASE 29 的规划把六个 BRB 项列为前提或风险；逐一针对 dev 核对显示，其中两个描述的缺陷在这里早已修正，而第三个仅凭 id 就被误读了——见下面的 BRB-004，它讲的并不是大家以为的那个标签。

    由此有两条规则：

    • 状态以 文件:行 为依据，测量得出，绝不凭记忆。
    • vault 拥有发现；仓库拥有证据。 当两者在某件事是否仍在发生上意见不一时，仓库胜出——它就 是被描述的那个东西。一项是否正式关闭仍然是维护者在 vault 中的决定。

    "在此测得"中的用词是什么意思

    这些用词有意不同。已修正会是维护者的判断，记录在 vault 中。缺陷不再复现是本仓库能够 诚实断言的全部：该发现描述的行为不是代码今天的行为，在该行的日期测得。已实现，尚未实践 更弱：代码存在，能够运行的测试都通过，但该路径只在本仓库触及不到的地方执行——在 CI 中一个真正 的 release 标签上。把它称为"已修正"就是声称一个没有人拥有的证明。仍然复现和部分复现说明 该发现的行为仍然存在，全部或部分。此处不可验证说明该发现关于本仓库不保存的东西。关闭该项—— 并决定修正是否覆盖了该发现所要求的一切——留在提出该发现的地方。

    BRB-004 是这种区分值得其代价的原因。按 id 读，它看起来像在 #419 中关闭的 ollama:latest 固定。 在 vault 中读，它要求的是digest，而当时没有任何镜像有。id 不是描述——而正是这种误读让它保持 开放，尽管针对 uses: 的姊妹规则自 #419 起就已有机制。

    修改一行

    id、标题和优先级逐字从 vault 复制，vault 中的状态也是；"在此测得"的状态和证据在这里测量。当 vault 改变一行的状态，或当本仓库的变更改变了能被证明的内容时，该行才会改变——绝不为了捏造一项发现。
