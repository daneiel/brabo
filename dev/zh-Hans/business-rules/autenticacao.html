认证

这些 RN 从 business-rules.md 中拆出，内容一字未改：单页已超过 640 KB， 仅这两个部分就占了一半。锚点 #rn-NNN 保持不变——只是承载它们的文件变了。

first-party 认证的规则。它们都在 api 的领域中生效，而自 7.2 起 api 也是访问 token 的签发者——Keycloak 在一次原子切换中退出，没有共存期。 决策见 ADR 0031 和 ADR 0032。

RN-030 — 重新出示已使用过的 refresh 会吊销整个家族​

每次 refresh 都会消耗所出示的 token，并签发一个具有相同 family_id 和相同 family_started_at 的子 token。出示一个已被消耗的 token 是盗用的特征——有人在使用副本——回应是吊销该家族所有存活的 token，并产生安全事件。

合法用户也会一并被登出。这是正确的行为，而不是缺陷：在服务器一侧，客户端的重复提交与窃贼的重放是完全相同的。

  • 位置： apps/api/src/domain/auth/refresh-token.ts:50 + application/use-cases/auth/refresh.use-case.ts:98
  • 测试： test/application/use-cases/auth/rotacao-e-reuso.spec.ts
  • 边界情况： 出示已被吊销家族的 token 的人是下游受害者，而不是新的盗用：记录 refresh_revoked，不触发第二次级联。没有这个区分，在事件期间合法用户的每个标签页都会产生一次误报。
  • 来源： ADR 0031

RN-031 — 登录失败按邮箱和按 IP 计数，锁定逐级升级​

Postgres 中 15 分钟的滑动窗口，不用 Redis。每次尝试两个桶，更严格的胜出：邮箱（5 次失败 → 30s，8 → 5min，12 → 15min）和 IP（20 → 30s，30 → 2min）。成功登录会清空邮箱的桶；IP 的桶只随时间排空。

桶的键是规范化后的邮箱，绝不是用户 id。用 id 的话，桶只有在找到账户之后才会存在，锁定本身就会成为账户存在性的预言机。

  • 位置： apps/api/src/domain/auth/lockout-policy.ts:97 + infrastructure/persistence/drizzle/drizzle-login-throttle.ts:74
  • 测试： test/application/use-cases/auth/lockout.spec.ts
  • 边界情况： 处于锁定期间，尝试不被记录。如果被记录，攻击者只要不断尝试就能让受害者的账户永远被锁住——锁定会变成针对它所保护之人的拒绝服务。
  • 原因： IP 的桶不能在成功时清空；拥有一个有效账户的人可以随意把窗口清零，无限制地喷洒猜测。
  • 来源： ADR 0031

RN-032 — 没有任何响应能区分账户存在与否​

任何不同于统一失败的响应，都只有在一次成功的密码校验之后才可能得到。在登录中，不存在的邮箱、错误的密码和被锁定的账户返回相同的 401，耗费相同的时间——没有账户的分支会对照一个用与真实哈希相同参数生成的虚拟哈希进行校验。在注册和重置请求中，已知和未知的地址都返回 202。

  • 位置： apps/api/src/application/use-cases/auth/login.use-case.ts:79 + register.use-case.ts:74
  • 测试： test/application/use-cases/auth/enumeracao.spec.ts
  • 边界情况： 按邮箱的锁定检查在 argon2 之后运行，而不是之前。提前退出是任何审阅者都会建议的优化，而它恰恰就是泄漏——如果有人引入它，测试会变红。
  • 边界情况： 从 Keycloak 迁移来的用户（存在于 users 中，在 auth_credentials 中没有行）同样收到统一的 401——并且"设置密码"的链接会被静默发出。响应 password_pending 会确认该地址存在并且是遗留账户。这就是为什么 findByEmail 是单次查询中的 LEFT JOIN：两次串联的查询会让这个分支多付一次数据库往返，时钟就会泄露响应体所隐藏的东西。
  • 原因： 所断言的是"没有任何分支跳过昂贵的工作，也没有任何分支产生可区分的响应"，而不是常数时间。后果见 ADR。
  • 来源： ADR 0031， 迁移用户的边界情况见 ADR 0032

RN-033 — 验证和重置 token 只能使用一次​

通过带 returning 的条件 UPDATE 消耗：UPDATE 本身就是防护。零行涵盖不存在、用途不同、已消耗、已作废和已过期——都给出相同的响应。请求新链接会作废之前的链接。完成重置会吊销用户的所有会话，并且不签发 token。

  • 位置： apps/api/src/infrastructure/persistence/drizzle/account-token.repository.ts:76
  • 测试： test/application/use-cases/auth/tokens-de-conta.spec.ts
  • 边界情况： 两次同时提交不会都通过。竞争是正常情形，而不是例外：企业邮件扫描器会打开每封邮件中的每个链接，因此机器人通常在人点击之前就消耗了 token。
  • 原因： 重置刻意不签发会话——直接通过邮件收到的链接登录，会让攻破邮箱等同于接管账户，而没有第二步。
  • 来源： ADR 0031

RN-034 — web 会话存在于带 CSRF 的 httpOnly cookie 中​

refresh token 放在 cookie brabo_refresh 中（httpOnly、SameSite=Strict、 Path=/auth，生产环境中 Secure），并且不出现在任何响应体中。15 分钟的 access token 保存在客户端内存中，通过 Authorization: Bearer 传输。

/auth/refresh 和 /auth/logout 要求 X-CSRF-Token 等于 cookie brabo_csrf，以常数时间比较。

  • 位置： apps/api/src/interfaces/http/auth/session-cookies.ts:53 + interfaces/http/auth/auth.controller.ts
  • 测试： test/interfaces/session-cookies.spec.ts
  • 边界情况： CSRF 失败是 403，不是 401。如果是 401，客户端会尝试续期会话并陷入循环——凭据是好的，错的是请求。
  • 原因： 在响应体中也返回 refresh 会抵消 httpOnly——一个 XSS 读取登录响应就够了，它会带走长期会话，而不是 access 的 15 分钟。
  • 来源： ADR 0032

RN-035 — engine ↔ api 的内部流量要求服务密钥​

32 条 /internal/* 路由都是 @ServiceRoute()：它们位于用户 JWT 之外，也位于速率限制之外。认证的是 EngineServiceGuard，以常数时间比较 X-Brabo-Service-Token 与 BRABO_SERVICE_TOKEN。同一个秘密在两个方向上都有效，BRABO_SERVICE_TOKEN_PREVIOUS 只在校验时被接受，使轮换没有不可用的窗口。

  • 位置： apps/api/src/interfaces/http/auth/engine-service.guard.ts:44 + infrastructure/security/service-token.ts + apps/engine/lib/engine_web/plugs/verify_service_token.ex
  • 测试： apps/engine/test/engine_web/plugs/verify_service_token_test.exs、 test/interfaces/route-surface.spec.ts，以及针对 api 一侧的轮换（之前的值只在校验时被接受，调用方发送当前值，移除之前的值后旧值失效）的 test/infrastructure/security/service-token.spec.ts （describe "rotação do BRABO_SERVICE_TOKEN"）和 test/interfaces/engine-service.guard.spec.ts（RN-597）
  • 边界情况： 速率限制的豁免来自路由的元数据，而不是 guard。RateLimitGuard 是 APP_GUARD，在任何 controller 的 guard 之前运行——它作出决定时，EngineServiceGuard 还没有运行。
  • 来源： ADR 0032

RN-597 — 更换 pepper 等于全局登出​

为不透明 token 的 HMAC 提供密钥的 pepper 没有 _PREVIOUS，更换它会带来后果，而不是一个流程：每个流通中的 refresh token、每个未完成的邮箱验证和密码重置链接，以及每个个人访问 token（PAT）都不再能被找到，因为用新 pepper 重新计算的哈希与已存储的不匹配。被拒绝的 refresh 记录 refresh_unknown（而不是 refresh_reuse_detected），链接显示 "Link inválido ou expirado"，锁定桶的键会改变——被锁的账户解锁。密码不受影响（argon2id，每条记录有 salt，没有 pepper）：更换 pepper 的代价是一次登录，绝不是一个账户，api 用新值正常启动。

在 RN-613 之前，没有自己值的 pepper 会落到 AUTH_JWT_SECRET 上，JWT 的轮换也就是 pepper 的轮换，带有上面所有的后果。自那以后，pepper 在生产环境中是必需的，绝不从 JWT 借用。

  • 位置： apps/api/src/infrastructure/security/auth-key-material.ts:212 (pepper), :228 (hashDeToken), :247 (baldeDeEmail); apps/api/src/interfaces/http/auth/pat-auth.guard.ts:142
  • 测试： test/application/use-cases/auth/rotacao-dos-segredos.spec.ts， 针对测试用 Postgres
  • 边界情况： "更换"的目标包括这样一种错误：把 pepper 与 JWT 分开的人生成了一个新值，而不是复制当前值——这是同一种更换，以同样的方式登出（在同一个 spec 中锁定，"a ordem errada"）。
  • 来源： ADR 0031， AT-196

RN-613 — AUTH_TOKEN_PEPPER 是必需的且独立的；迁移者用当前的 AUTH_JWT_SECRET 定义它​

不透明 token（refresh、账户链接、PAT、锁定桶）的 HMAC pepper 不再回落到 AUTH_JWT_SECRET。静默回退（AUTH_TOKEN_PEPPER ?? passphraseAtual()）让 JWT 的每一次"零停机"轮换都成为 pepper 的更换，而那是常见路径：生产和安装的 compose 甚至没有传递这个变量。在生产环境中，没有它 api 拒绝启动，拒绝信息会说明修正方法——"defina com o valor ATUAL de AUTH_JWT_SECRET para não deslogar ninguém"——，因为显而易见的修正（生成一个随机值）正是会让所有人登出的那个。pepper 等于旧 JWT 时，哈希与之前逐字节相同，refresh token 和 PAT 继续有效，此后 JWT 可以独自轮换。等于 JWT 的 pepper 不会被拒绝：它是每个迁移过的安装的正当状态。JWT 的尺子（RN-114）同样适用：空白、仓库的两个示例字面量以及少于 16 个字符都会让启动失败。在生产环境之外，使用独立的开发默认值（dev-auth-token-pepper-change-me），绝不是 JWT 的那个。

install.sh 负责迁移：全新安装生成随机 pepper；如果文件夹中有之前的 .env，它会在被覆盖之前被读取（绝不执行），并保留其中的 pepper——或者，没有 pepper 时，以其中的 AUTH_JWT_SECRET 生成。终端会说明值来自哪里，绝不说出值本身。

  • 位置： apps/api/src/infrastructure/security/auth-key-material.ts:168 （pepperAtual），:212（pepper）；apps/api/src/main.ts:46（启动检查）；install.sh:702（valor_no_env_anterior），:734（gerar_segredos）， :831（dizer_a_origem_do_pepper）；三个 compose 中的变量 （docker/docker-compose.yml、docker-compose.prod.yml、 docker-compose.install.yml），docker/smoke.sh 中以及 .env.example 中
  • 测试： test/infrastructure/security/auth-key-material.spec.ts （describe "pepperAtual (RN-613)"：即使有 JWT 也拒绝没有 pepper、消息、示例值、下限、接受等于 JWT 的值、开发默认值）； test/application/use-cases/auth/rotacao-dos-segredos.spec.ts（describe "a migração do RN-613"：用旧公式写入的 refresh 在 pepper 等于旧 JWT 时仍然有效，并能挺过 JWT 的更换；AUTH_JWT_SECRET 的 describe：生产之外没有 pepper 时，更换 JWT 不会登出）； scripts/dev/install-env.spec.ts（describe "o AUTH_TOKEN_PEPPER do instalador (RN-613)"，针对 docker compose config，完整的值）
  • 边界情况： 安装程序只能看到它运行所在文件夹的 .env。.env 位于别处的安装、自有 compose 以及使用 ExternalSecret 的 Kubernetes 需要按 runbook 手工迁移——在 Kubernetes 中，AUTH_TOKEN_PEPPER 属性已经存在于 ExternalSecret 和 bootstrap.sh 中，没有它的提供方本来就会让同步失败。而安装程序的迁移会删除卷（ADR 0150）：refresh 只对恢复 Postgres dump 的人存活，而这正是重要的情形。
  • 来源： AT-210（AT-196 的发现），维护者的决定：用当前值迁移

RN-595 — 服务读取的每个 _PREVIOUS 都通过三个 compose 到达它，默认为空​

三种零停机轮换（AUTH_JWT_SECRET、BRABO_SERVICE_TOKEN、 CREDENTIALS_MASTER_KEY）依赖于进程在窗口期间通过 _PREVIOUS 变量看到旧值。Compose 不传递主机的环境，而三者都不在任何 compose 的 environment: 中：在 .env 中定义 _PREVIOUS 没有效果，按 runbook 操作的人不知不觉地做了一次轮换本来要避免的硬切换。现在 api 接收这三个，engine 和 broker 接收 BRABO_SERVICE_TOKEN_PREVIOUS，在开发、生产和安装的 compose 中都是，默认值总是空——定义了就是轮换进行中，而填充了的默认值会让安装永远处于轮换中途。在三个读取方中，空与缺失等同。

  • 位置： docker/docker-compose.yml、docker/docker-compose.prod.yml 和 docker/docker-compose.install.yml（api、engine 和 broker 服务）； 读取方是 apps/api/src/infrastructure/security/auth-key-material.ts:136 （passphraseAnterior），apps/api/src/infrastructure/security/service-token.ts:92 （tokenDeServicoAnterior），apps/api/src/infrastructure/security/envelope-encryption.service.ts:93, apps/engine/config/runtime.exs:70 和 apps/broker/src/config.ts:85
  • 测试： scripts/ci/previous-nos-composes.spec.ts——从三个服务的代码中推导所读取的 _PREVIOUS 列表，在三个 compose 中任何一个缺失或带非空默认值时失败；"ExternalSecret do k8s" 块拒绝没有 dataFrom.extract 的 ExternalSecret、data: 中的 _PREVIOUS，以及没有 envFrom: brabo-secrets 的 api/engine Deployment
  • Kubernetes（AT-220，维护者的决定）： Pod 读取 envFrom: brabo-secrets，而 ExternalSecret （deploy/k8s/base/common/externalsecrets.yaml）通过 dataFrom.extract 从 store 拉取整个 brabo 对象——_PREVIOUS 存在时进入，被移除时在下一次同步中退出。它不能列在 data: 中：ESO 没有可选键，缺失的属性（正常状态）会让整个 Secret 的同步失败。声明的代价：对象的每个键都会成为 api、engine、迁移和备份的变量，而缺失的必需键不再让同步失败——指出问题的是消费者。通过真实 ESO 的同步在一次性的 k3d 中手工演练过，不在 CI 中
  • 来源： AT-201（AT-196 的发现），与 RN-540 同类；Kubernetes 一半在 AT-220

RN-598 — 之前的服务 token 经过与当前 token 相同的尺子​

在轮换期间，BRABO_SERVICE_TOKEN_PREVIOUS 和当前 token 一样能打开 /internal/*。它经过一把尺子，与当前 token 的相同（exigirTokenDeProducao），没有任何副本。周围的空格被丢弃，只由空格组成的值视为缺失。在生产环境中，公开的开发字面量（dev-service-token-change-me）以及 trim 后少于 16 个字符的值会让 api 启动失败，消息中点名 BRABO_SERVICE_TOKEN_PREVIOUS。在此之前，变量被原样比较：使用示例值的之前 token 会向任何读过这个仓库的人打开内部大门，而且不报任何错误。必需性是当前规则中唯一不被复制的部分，因为在轮换之外，之前值缺失是正常状态。等于当前值（trim 后）的之前值仍然不算轮换。

  • 位置： apps/api/src/infrastructure/security/service-token.ts:63 （exigirTokenDeProducao），:92（tokenDeServicoAnterior）； apps/api/src/main.ts:50（tokenDeServicoAnterior），它在启动时与当前值并列运行
  • 测试： test/infrastructure/security/service-token.spec.ts（describe "tokenDeServicoAnterior (RN-598)"）
  • 边界情况： 这条 RN 是 api 一侧。engine 和 broker 自 RN-601 起应用同一把尺子。
  • 来源： AT-205（AT-196 的发现）

RN-601 — engine 和 broker 对两个服务 token 应用 api 的尺子​

比较服务 token 的三个进程都使用 RN-598 的同一把尺子，各用自己的语言。周围的空格被丢弃，只由空格组成的值视为缺失。在生产环境中，BRABO_SERVICE_TOKEN 缺失、公开的开发字面量（dev-service-token-change-me）或 trim 后少于 16 个字符的值会让启动失败，消息中点名该变量。后两种拒绝在 BRABO_SERVICE_TOKEN_PREVIOUS 被定义时也适用于它。等于当前值的之前值不算轮换。在生产环境之外只应用 trim，空的当前值落到开发默认值。

以前，engine 在 config/runtime.exs 中原样读取两者：没有 trim，没有下限，在生产环境中变量缺失时以公开默认值启动（compose 传空值时则以空字符串启动）。只有 api 拒绝启动才保护了安装。broker 已经对当前值应用这把尺子，但对之前值只做 trim。

形式上的两处分歧，已声明。在 engine 中，"生产"是 config_env() == :prod（release），而不是它不读取的 NODE_ENV；生产镜像总是 :prod release。并且尺子内联在 runtime.exs 中，而不在 lib/ 的某个模块中，因为在 release 中这个文件在应用代码加载之前就在 config provider 中运行。

后果：在 :prod release 中评估这个 runtime.exs 的每个进程都需要 token，包括迁移（bin/engine eval Engine.Release.migrate()）。因此，生产和安装 compose 中的 migrate-engine 服务开始接收 BRABO_SERVICE_TOKEN 和 BRABO_SERVICE_TOKEN_PREVIOUS，没有默认值。CI 的 smoke 显示了这一点：没有它们，迁移会在迁移之前就死掉。Kubernetes 的迁移 Job 本来就通过 brabo-secrets 的 envFrom 接收它们。

  • 位置： apps/engine/config/runtime.exs:85 （exigir_token_de_servico_de_producao），:105（service_token），:121 （service_token_previous）；apps/broker/src/config.ts:89（anterior）， :125（exigirTokenDeProducao）
  • 测试： apps/engine/test/engine/runtime_service_token_test.exs（通过 Config.Reader.read!/2 真正评估 runtime.exs，带 env: :prod 和 :dev）；apps/broker/src/config.spec.ts（describe "lerConfiguracao — produção, o token ANTERIOR (RN-601)"）
  • 边界情况： 尺子在三个进程中是复制的，而不是共享的：它们是三种语言或运行时，没有测试核对三份副本是否保持一致。下限计算字符数（Elixir 中是 String.length，TS 中是 .length），这只对非 ASCII 的 token 有区别。
  • 来源： AT-216（AT-205 的发现）

RN-128 — sessionId/projectId/agent/agentId 在成为发往 engine 的内部请求 URL 段之前被校验​

HttpApiToEngineClient 在模板字符串中插入这些值来构造 /internal/* 的 URL——中间没有 DTO/class-validator，与 RN-127 一样：它们来自 @Param/会话查找，在链条中某处没有校验管道，插入之前没有任何东西保证它们的形式。恶意值可能注入额外的路径段或破坏所构造 URL 的字符——EngineServiceGuard 认证的是调用方（RN-035），而不核对调用方在 URL 中发送了什么。

RN-106 — git push、PR 和部署不能通过终端发出——即使在项目范围之内​

RN-107 — 代码标签页有第四种状态：因待定决定而被阻塞​

RN-115 — Anamnese 可以被全局暂停；暂停属于产品，从不删除数据​

AnamneseSchedulerWorker.kickoff/0（在启动时调用一次）在停用时不安排周期性 job，而不是安排后让 perform/1 在每个 tick 空转——更便宜（Oban 队列不会每隔 ANAMNESE_INTERVAL_SECONDS 收到一个只为什么都不做的 job），对检查队列的人也更清楚。2026-08-10 的更正（执行中的真实发现，而非假设）：这条规则的原始版本刻意让 perform/1 无条件执行，使轮次之间的链条不携带开启/关闭的决定——但这意味着在 flag 存在之前（或在有人停用它之前）已经安排好的链条会永远自我重新安排，在 flag 为 false 的情况下真正运行 Anamnese。这正是在一个比原始 PR 更老的开发 Postgres 中发生的事，通过手动取消已安排的 job 得到补救。perform/1 现在在每个 tick 都检查 enabled?/0，与 kickoff/0 一样：停用时，既不执行 enqueue_projects/0 也不重新安排，链条就此终止——这也能自愈仍会触发一次的旧 job 的情形，无需人工干预。

RN-108 — 会话 socket 要求一次性的不透明 ticket，而不是复用 JWT​

EngineWeb.SessionSocket.connect/3 原来只要求 session_id（UUID）存在于 Registry 中就允许连接——发现了 UUID 的人就能进入 session:<id> 通道，接收该会话的所有实时广播。关闭这一点是自 Fase 3 起就记录在模块本身中的刻意限制。

POST /projects/:projectId/sessions/:sessionId/socket-ticket（scope: "heartbeat"|"terminal"）签发一个不透明 ticket（32 字节 CSPRNG， TokenFactory），TTL 30 秒，一次性。scope: "heartbeat" 要求角色 viewer；scope: "terminal" 要求 developer——与 domain/actions/decide.ts 中 MIN_ROLE_FOR_ACTION_TYPE.terminal 相同的最低角色（目前没有任何路径真正请求 terminal；这个值为 FASE 25 的交互式终端正确地诞生）。api 只持久化哈希（纯 SHA-256，而不是 hashDeToken/HMAC——engine 没有 api 的 pepper，而一个 256 位的 CSPRNG token 不需要 pepper 来防御字典攻击，与 hashDeToken 自己记录的推理相同），从不持久化原始 token。

消耗属于 ENGINE，它直接读取 session_socket_tickets（与 Engine.Outbox.Event 对 outbox_events 的模式相同——绝不是 changeset/insert，只有一次性所需的窄写入），分两步： SocketTicket.validar/1（窥视，不标记任何东西——由 connect/3 调用，它还不知道将请求哪个 session_id）和 SocketTicket.consumir/2（条件 UPDATE，要求主题的 session_id 与该行一致——由 SessionChannel.join/3 调用，它还会对照会话的 project_id 检查 ticket 的 project_id，纵深防御，防止一个项目的 ticket 打开另一个项目的通道）。没有 ticket，或 ticket 无效：整个连接被拒绝（{:error, %{reason: "unauthorized"}}），而不只是通道的 join。

web（session-channel.ts）在每次 socket.connect() 之前都获取一个新 ticket——包括自动重连，它确实存在。Phoenix.Socket 的原生重连会复用构造时的同一个 params（旧 ticket，已经过期或被消耗），因此它被中和（reconnectAfterMs 几乎永不触发），重连完全变为手动，每次尝试都获取新的 ticket。

这种中和适用于 socket 的每个客户端，而不只是 web 的——包括 /runner socket，它的 ticket（POST .../runner-ticket）是同一口径。它在仓库四个 Socket 构造器中的两个里失败了，代价在真实执行中被测量：apps/runner/src/ channel.ts 构造 socket 时没有这个选项——而模块的 docblock 却声称重连"因此被中和"——自动重连每 ~5.13s（phoenix.js 内部退避的上限）重复同一个已被消耗的 ticket，几个小时内产生 61 次 REFUSED CONNECTION TO EngineWeb.RunnerSocket。再加上 runner 自己的策略（index.ts，这个是正确的），结果是一分钟 530 个请求，而 RATE_LIMIT_USER 的上限是 300——由于限制是按用户的，429 出现在账户所有者的浏览器中。两个后果，第二个比 429 更糟：处于这个循环中时 runner 没有连接，因此 RunnerReadiness（RN-507）会拒绝，项目看起来"没有本地 agent"。apps/web/src/lib/fs-browser-channel.ts 有同样的缺陷行（同样的一次性 ticket，且没有自己的重连策略——它的 onClose 说"关闭再重新打开"），一并修正。

阻止第三个实例的是机制，而不是注释：在 runner 中，Socket 的选项变成了一个 reconnectAfterMs 必填的类型（channel.ts 中的 OpcoesDoSocket），两侧都增加了断言传给构造函数的选项的测试——一个只检查"能连上"的测试在缺陷存在时也会通过，而且确实通过了。同时，conectarERodar（index.ts）开始显式丢弃掉线的连接（conexao.desconectar()）：没有这一点，上一轮的 Socket 会在下一轮创建后继续存活，每次掉线都会多留下一个用失效 ticket 尝试的存活对象。

RN-129 — ToolLoop 从不写入空的 agent.response；传输失败成为持久的 agent.error​

RN-141 — read_file 读取的内容同样有字节上限​

RN-150 — search_workspace 有命中数量上限和字节上限，各自带有标记​

在一次 PR 审查中发现：search_workspace（dev agent 以及两个 QA/gate agent，qa_tools.ex 和 qa_performance_seguranca_agent.ex——后者只有 read_file/search_workspace，刻意没有 Terminal）返回全部搜索结果，没有任何上限——与发现 S（Engine.Actions.TerminalExecutor.truncate/2）以及 read_file 的修正（Engine.Harness.Tools.ReadFile.truncate/2）同类：结果留在循环的历史中并在之后的每个回合中传输，一棵大目录树就足以触发提供方的 {413, "request entity too large"}。

两个独立的上限，因为搜索会以两种不同方式溢出：

  1. 命中数量——一棵有数千个文件匹配搜索词的树会产生数千行 - caminho，即使没有任何单个文件很大。只在最后按字节截断，仍然要付出扫描并读取每个文件内容然后再组装字符串的代价。因此数量上限（SEARCH_WORKSPACE_MAX_HITS，默认 500）位于 WorkspaceFiles.search/3 中，它一旦找到足够的命中就停止消费搜索——流水线运行在 Stream 上，Enum.take(stream, max_hits + 1) 只从源头读取产生前 max_hits + 1 个结果所需的东西。"+1"使得可以说明还有更多，而不必继续扫描其余部分来计算准确总数——计算总数会再次付出上限要避免的 I/O，因此标记说"显示前 N 个"，从不编造总数。
  2. 最终文本的字节数——即使命中受限，非常长的路径也可能产生大字符串。字节上限（SEARCH_WORKSPACE_MAX_BYTES，默认 32,768），与 terminal_output_max_bytes/read_file_max_bytes 同一模式——独立的变量，不复用另外两个：同一类溢出，改动其中一个不应该需要触碰其他的。

截断标记是写给模型的，而不是给人的：它说明截断了什么（命中和/或字节），并指示细化搜索词——与 TerminalExecutor/ReadFile 标记的精神相同。

  • 测试： apps/engine/test/engine/harness/workspace_files_test.exs （带 max_hits 的 search/3 截断数量，只有在多于上限时才标记截断）， apps/engine/test/engine/harness/search_workspace_test.exs（结果少的搜索不被改变；命中多于上限的搜索被截断并给出清楚的提示；大于字节上限的最终文本也被截断）

RN-154 — 即使"自动模式"打开，三个绝对上限仍然阻止​

RN-603 — 自动模式放开路径范围，且只放开它​

产品所有者在 2026-09-26 的决定（AT-226， ADR 0167）：在某个 agent 上打开"自动模式"——RN-153 的通配符 "*" 解析为 auto_approve——时，agent 无需请求批准就能运行任何终端命令，包括在项目文件夹之外。ADR 0055 的路径范围上限对该 agent 不再有效。在 exp001（mounted 模式，容器运行中）中测得：模式打开时有 51 条命令请求批准，其中 47 条仅仅因为引用了 /work 或 /tmp——dev agent 在容器中运行，而范围是与主机的根比较的。

decide() 开始接收自主权的来源（ctx.autonomyOrigin： 'especifica' 或 'curinga'），由已经解析优先级的同一仓储解析——findMode 成为 resolve 的一种读取，而不是第二把尺子。只有处于 auto_approve 的通配符才是自动模式（modoAutomaticoDoAgente）；缺少来源视为具体规则。在自动模式下，有两种请求不再存在：范围上限，以及当某段在 permissions.json 中没有任何规则时复合命令合成的 require_approval（文件没有意见，它从不降级之前的阶段）——没有第二点，cd /work && npm test 仍会请求批准。

RN-163 — Criativo 兑现重试的承诺​

Criativo 的每个回合都运行一个有界的工具使用循环，上限为 12 次模型调用——与 PO 和 Arquiteto 已有的设计相同。以前每个回合只调用模型一次：工具结果被附加到内存中的历史，再也没有人读它，因此*"vou corrigir e tentar de novo"*这句话——代码中的字面量——只有在用户再发一条消息时才会兑现。对使用者来说，Criativo 在说它要修正之后就干脆不再回应了。

四个后果，每一个都是规则：

  1. 工具错误是输入，而不是终点。 原因作为 tool 消息回到模型，循环再次调用模型，模型在同一回合之内发出修正后的结果。
  2. 不宣布代码不会执行的东西。 重试的句子在派发工具之后、在知道还剩多少圈的情况下决定：有剩余的圈数时，agent 说它会修正；没有时，它不作承诺。
  3. 工具失败变成了带来源的持久 agent.error（RN-059）——原来是 agent.response，在事件日志中与正常回答无法区分。api 拒绝 append_event 时为 origem: infra；对于模型写出的 payload（错误的键、不是列表的 origin、重复的规则、系统发出的类型）为 origem: modelo。payload 携带 tool 和 retentativa。
  4. 上限耗尽不会以沉默结束。 它变成带 reason: "limite_de_iteracoes" 和 origem: modelo 的 agent.error，与 ToolLoop 的 toolloop.limit_reached 相同的解读。事件名不被复用：这个 agent 不在 ToolLoop 内运行，那个事件会就谁产生了它撒谎。

循环的两个边界，都是刻意的：成功的 ask_structured_questions 结束回合（球在用户那边，回答会在未来的回合中返回——RN-162）；某一圈失败过的回合在消息流中以汇总的结果收尾，使最后一句话不是一圈之后已经被修正的错误。

RN-169 — 项目选择代码存放的位置：本地或容器​

由 RN-421 修订（ADR 0104）：workspace_mode/local 变成了有三个值的 execution_mode（container/mounted/runner，迁移 0048）——本条目的其余部分是历史，忠实于修订之前的有效内容。

项目诞生时带有一个workspace 模式（projects.workspace_mode，迁移 0043），由它决定范围根从哪里推导：

  • container（默认，也是一直存在的行为）：由产品托管的文件夹，join(PROJECT_WORKSPACES_ROOT, workspace_dir_name) （RN-109）；

这一对由数据库中的 CHECK 约束绑定 （(workspace_mode = 'local') = (workspace_path IS NOT NULL)），而不仅仅由用例绑定：该列由两个进程（api 和 engine）读取，并由不经过用例的 seed/回填脚本写入。没有路径的 local 会让终端范围指向无处；带路径的 container 会成为等待与第一个分歧的第二个事实来源。

  1. Arquiteto 的镜像闸门（RN-105）不适用。 由 RN-494 撤销（ADR 0135）：豁免结束了——三种模式都开始要求在打开代码标签页之前作出镜像决定。本项的其余部分是历史。本地项目不启动容器，因此代码标签页会放行，而不等待一个永远不会发生的决定。豁免与 api 中的闸门位于同一漏斗中，界面也一致：当项目是本地时，ProjectCodeTab 甚至不去询问容器的状态（RN-107）——如果只有 api 豁免，标签页会因为一个不存在的决定而在界面上保持阻塞。
  2. permissions.json 位于用户的文件夹中，与代码在一起——因为策略必须从终端范围所授权的同一根读取。

workspace_mode 不要与 GitProviderName 'local' 混淆：一个说的是代码在磁盘上的位置，另一个说的是 git 仓库的位置，两种选择是正交的。

RN-170 — 本地路径在创建时校验，拒绝会给出指引​

由 RN-422 修订（ADR 0104）：创建时的校验开始按模式分歧——mounted（改名后的 local）仍按此处描述触碰磁盘，runner 只校验词法，不做 I/O——本条目的其余部分是历史，忠实于修订之前的有效内容。

以 local 模式和一个 api 够不着的路径创建项目，会产生一个之后才卡住的项目——在第一个 agent 的第一个工具上，远离作出决定的那个界面。因此创建以 400 拒绝，消息说明还缺什么。

路径必须：

  1. 是绝对路径，任何段中都没有 .. 或 .（写入的路径就是读取的路径；/srv/app/../../etc 就是 /etc，看起来却不像）；
  2. 在 api 容器内存在且是文件夹；
  3. 进程可写（access(W_OK|X_OK)）——镜像以非 root 运行（ADR 0024），所有者不同的主机文件夹实际上会以只读方式挂载进来；
  4. 位于根目录和系统文件夹之外（/、/etc、/usr、/var、/data……及其下的一切）：项目的根是授权 agent 终端的范围（ADR 0055），根在 /etc 的项目会把"agent 在它的项目里写东西"变成"agent 重写容器"；
  5. 在两个方向上都不与 Brabo 的 checkout 重叠——包含单体仓库的文件夹和位于其内部的文件夹。第二种情形就是 ADR 0055 报告的真实发生过的问题。

写入的路径是规范化后的，而不是原始字符串：校验一个字符串却写入另一个，就是校验在第二天失效的方式。与 workspace_mode: container 一起发送的 workspacePath 会被拒绝，而不是被忽略——被静默丢弃的字段会变成"可我配置过了"。

词法部分（第 1、4 和 5 项）在读取时也会运行，在每次推导 projectScopeRoot 时：绕过创建的唯一途径是直接写数据库，而由此得到的是 / 上的终端范围。磁盘部分（第 2 和 3 项）只在创建时运行，那时用户还可以修正。

文件夹缺失的拒绝会附带挂载说明——文件、两个服务以及那一行（- <caminho>:<caminho>），并指向 runbook。只在 api 中挂载会产生一个 api 接受而 engine 看不到的项目：api 校验的是它看到的东西，无从得知另一个容器中挂载了什么。

RN-172 — handoff 和审批是回合的结果​

在会话的消息流中，提供的 handoff 和审批卡片出现在它们诞生的那个回合的最后一句话之后——绝不在中间。

这不修正排序：RN-155 完整有效，时间线仍按事件日志的 seq 排序。日志记录的是事实：po_server.ex（run_turn/2）在同一次迭代中发出回合的 agent.response，然后是 offer_handoff 的 tool.call（写入 handoff.offered），然后才递归到收尾的 agent.response。handoff 的 seq 诚实地小于最后一句话的 seq。对于 proposed_action.created 也一样，它诞生于回合中间，而 agent 还有话要说。在对话中间显示"交出了接力棒"或"批准这个"，是对正确数据的错误解读——因此这条规则属于呈现，在一次单独且显式的处理（afundarDesfechos）中应用，在按 seq 的 sort 之后，而不是藏在一个有三项的比较器中。

不同的回合永远不会混合。一个结果向下沉到它正下方那一段的末尾，并停在第一个不满足以下三个条件中任何一个的条目处：

  1. 同一回合——回合是条目之前最后一个开启的 seq，而开启是执行者为 user 的事件（chat.message、agent.activated、故事的晋升/退回）。这保护了两个回合之间的边界没有任何可见条目的情形：agent.activated 开启回合，却不会成为消息流中的一项。
  2. 同一作者——在执行会话中，多个 agent 在用户一句话都不说的情况下写入，它们都在同一个回合中；一个 agent 的结果不能越过另一个 agent 的话。
  3. 不是结果——两个连续的结果保持彼此之间的顺序（在同一次确认中，Infra 的 handoff.offered 在 Dev Lead 的之前）。

执行者 system 不开启回合：它是消息流中间的基础设施噪音，而不是对话者的决定。

RN-171 — 列表问题默认有自由文本的出口​

ask_structured_questions（RN-162）的 type: "select" 问题接受列表之外的回答。字段是 allowOther，默认为 true：什么都不声明的人会提供这个出口。关闭列表需要显式的 allowOther: false，并且只在列表真正封闭时（"是"/"否"）才有意义。

开放的默认值不是风格偏好。因模型遗忘而关闭的列表会卡住整个对话，而用户无法从外部解开它——这正是真实使用中遇到的：模型提供了一个"自己填写"之类的选项，表单却没有地方可写，因为工具的 schema 不知道如何表达"除了这些，你想要什么都行"。被错误打开的列表，最坏情况下多提供一个字段。两种错误的代价不同。出于同样的原因，工具描述禁止在 options 中创建"其他"选项：表单会自己提供它，同一列表中的两个出口会造成困惑。

RN-174 — 触发 agent 回合的动作会武装消息流的指示器​

RN-184 — 对比度在两个主题中测量​

RN-185 — 八个语法角色，handoff 的值只有在测量之后才进入​

handoff 的最后两个键：brabo.project（活跃项目）和 brabo.tab（活跃标签页）——在用户点击侧边栏中的标签页链接（LinhaDeAba/项目名称链接）时写入。URL 中的 ?tab= 只作为初始深链接有效（project-tabs.ts，FASE 24）——在 ProjectPage.tsx 内切换标签页是本地状态，第一次加载之后不写入 URL，因此这些键是偏好在一次导航与另一次导航之间存活的唯一途径。这一半从未改变。

RN-228 — 药丸过滤器按轨迹归并 2 个没有自己药丸的状态​

handoff 的药丸过滤器（全部/活跃/已关闭/已中止）只覆盖 5 个状态中的 4 个。created（等待中）进入"活跃"药丸——它还没有到达任何地方，是"仍在进行中的会话"。closing 进入"已关闭"药丸——它已经在没有错误地走向关闭。每行的徽章（RN-227）从不被过滤器重写；药丸只做归并。

  • 位置： apps/web/src/routes/ProjectSessionsTab.tsx （correspondeAoFiltro）
  • 测试： apps/web/src/routes/ProjectSessionsTab.test.tsx——describe "filtro pill agrupa os 2 estados sem pill própria (RN-228)"

RN-229 — Criativo 标签页的"本月成本"KPI 是执行者的消耗，而不是项目的总额​

复用 getMySpend(projectId, 30)——与 ProjectSpendTab.tsx#MeuConsumo 用于成员视图的同一个 queryKey（RN-101，ADR 0063），没有新的聚合。绝不显示把所有人加起来的项目总额（getWorkspaceSpendReport 中的 porProjeto），因为那个数据只属于 owner，而 Criativo 标签页对项目的任何成员可见——显示总额会把别人的花费泄露给 RN-060/101 不授权查看的人。

  • 位置： apps/web/src/routes/ProjectSessionsTab.tsx（CriativoKpis）
  • 测试： apps/web/src/routes/ProjectSessionsTab.test.tsx——describe "KPIs da aba Criativo"，用例 "caminho feliz" 和 "CASO DE FALHA"

RN-230 — "构思 → 提交率"KPI 被声明为缺失，绝不计算​

在产品的任何地方都不存在创意会话与其产生的提交之间的关联。Criativo 标签页显示"—"以及句子"não medido: sessão não é vinculada a commit hoje"，而不是编造一个计算——与 ADR 0042 已经对模型分数拒绝的错误同类。

  • 位置： apps/web/src/routes/ProjectSessionsTab.tsx（CriativoKpis）
  • 测试： apps/web/src/routes/ProjectSessionsTab.test.tsx——"'Taxa ideação → commit' é DECLARADA ausente — nunca um número calculado"
