    Contratos

    Git

    RN-028 — Capability decides, not the provider's name

    An unsupported operation (branch protection on the local provider) is declared in capabilities and rejected with GitNotSupportedError — never a silent failure.

    There are four capabilities: protectBranch and pullRequests since Phase 2, and listTree and pullRequestDiff since PHASE 26 (Code tab, read-only). The rule didn't change with them — its reach did. And the criterion for declaring is still proof: a capability is only true when the suite exercises it on that provider; without proof, it's declared false and degrades (same criterion as ADRs 0041/0042).

    • Where: packages/shared/src/index.ts (GitProviderCapabilities); the ceilings of the two read operations in apps/api/src/domain/git/git-read-limits.ts, outside shared because it's 100% types
    • Test: single contract suite, test/contract/git-provider.contract.ts, run against the three providers
    • Origin: ADR 0001

    RN-087 — O Dev Lead é o único endereço externo da execução

    Existe um agente dev-lead, conversacional, que recebe o handoff do Arquiteto (desde a RN-672, da Infra, com o container do projeto running) e propõe o plano de execução: quantos agentes por módulo e por quê. Ele não escreve código — distribui trabalho e responde por ele.

    Antes dele, a frase "quem decide é o lead" da RN-083 não tinha dono. O Arquiteto terminava e a execução subia por um botão, sem ninguém no meio para avaliar quanto trabalho havia.

    Os dev-<modulo> deixaram de ser endereçáveis por handoff. Isso não é exceção nova: é a regra do ADR 0038 — handoff externo endereça só lead de área ou agente sem área — passando a valer para o dev como já valia para QA e Infra. Enquanto não havia Dev Lead, eles eram agentes SEM área e por isso alvos válidos; virando membros, deixam de ser.

    A área de dev é a primeira DINÂMICA, e é o que forçou o predicado: os membros são um por módulo do module_map, decididos pelo Arquiteto e diferentes em cada projeto, então não há lista a enumerar. dev-lead casa com o mesmo prefixo dev- dos membros, e quem o exclui é a regra genérica o lead nunca é membro da própria área — que vale para qualquer área e vive num lugar só. A primeira versão repetia essa exclusão em três pontos, e a verificação por mutação mostrou que nenhuma das cópias era alcançável por teste: cada uma sobrevivia à mutação da outra.

    O plano é proposed_action (revisado pelo ADR 0086, RN-284). Até essa mudança o plano virava EVENTO simples, sem aprovação: o argumento era que propor não tem efeito externo — o gasto acontece quando os agentes sobem, e é lá que o teto cobra autorização; transformar a proposta em ação a decidir faria você decidir duas vezes a mesma coisa. Uma auditoria de docs/fluxo.yml × código encontrou que o fluxo já declarava esta saída como via: proposed_action desde o ADR 0085, e o código nunca foi ajustado para bater — o dono do produto decidiu que o código errava: o plano é a PRIMEIRA decisão real de quanto a sessão vai gastar com paralelismo, e o usuário passou a decidir ativar a execução tendo VISTO uma aprovação de verdade, não só lido uma linha no fio. A lição antiga não desapareceu — é o motivo pelo qual propose_execution_plan NÃO entrou no bloco de tetos absolutos de decide.ts (ver RN-284).

    O plano BEM-SUCEDIDO encerra o turno — no caminho SEM suspensão.     RN-605 — The image pull is a NAMED step of start, under the control ceiling, and the overflow says a big image does not come up

    The Docker port's start did not pull: docker run did, internally, under TIMEOUT_DE_CONTROLE_MS (30 s). Reproduced in AT-234 with a double of the daemon (image absent, 45 s pull, without sleeping and without network): the overflow came out as ComandoDeDockerFalhouError — "docker run … ended with code -1: (no error output)" —, became a 502 with origem: null in the broker and reached the api without a name. And killing the CLI CANCELS the pull (measured on Docker 29.8.0, containerd): the image stayed absent for the following 60 s, so the sentence "the pull may continue in the daemon" did not hold.

    Of the four ways out measured (its own ceiling of ~300 s, asynchronous start, pull in advance at the image decision, only giving a name), the maintainer decided on D — only giving a name (2026-09-27). The rule:

    1. The pull is explicit. Before the run, image inspect; a present image is not downloaded again (the same --pull missing as the run). Absent, docker pull under the SAME 30 s control ceiling — no bigger ceiling.
    2. The overflow has a name. PullExcedeuTetoError, origin infra, with the image, the ceiling and the whole consequence: the pull was cancelled, the image stays absent, a big image does not come up through this path, and the fix is downloading it beforehand on the host. Before asserting that, the adapter checks the daemon (docker version): a daemon down remains DockerIndisponivelError. A pull that fails for another reason follows the usual path (ComandoDeDockerFalhouError, without an origin, ADR 0128).
    3. The name crosses over. The broker answers 504 with origem: 'infra', and the api passes it on in BrokerRecusouError — origem filled in, never null. In runner mode the same adapter runs on the user's machine and the message arrives in the container_start_result.
    4. The ceilings of whoever waits for the start count the whole worst case: the two ps of resolver, image inspect, pull, run and the diagnostic docker version — six control calls (CHAMADAS_DE_CONTROLE_NO_START). The api waits 10 + 6 × 30 + 5 = 195 s (TETO_DE_MUTACAO_MS); the engine, in RunnerRouter, 6 × 30 + 5 = 185 s on start and 4 × 30 + 5 = 125 s on stop/remove (it was 60 s, less than the resolver plus the operation).
    5. The engine's propose_action waits for the execution the api does inside it. Auto-approved container_start, container_start_via_runner and container_stop are EXECUTED in the same request (ProposeActionUseCase), and the call fell back to Req's 15 s default — a long start came back as a transport timeout even without a pull. Now it carries a receive_timeout of 225 s (the api's ceiling + 30 s), mirrored in the api as TETO_DO_PROPOSE_ACTION_DE_CONTAINER_NO_ENGINE_MS; the tests on both sides check broker < api < engine and runner < engine. container_remove stays out: it is never born auto-approved.

    No new dependency (ADR 0128), no field the caller writes (ADR 0130): the image keeps coming from the Arquiteto's decision, and pull is not a new broker operation — it is a step of start.

    Declared, not closed:

    • A big image does not come up on the first attempt, neither through the broker nor through the runner — the maintainer's decision D. The outcome is now named; the fix is downloading the image beforehand on the host.

    • In the worst failure case, the approval stays stuck for up to ~195 s: ExecuteContainerStartUseCase runs inside the approval POST, and neither the web nor the HTTP server has its own ceiling.

    • It was not measured whether the layers downloaded before the cancellation are reused on the next attempt.

    Deciding in the chat, where the owner is (RN-626)

    RN-627 — The project container runs as the folder's owner, measured by the api

    Under --cap-drop ALL the container's root lacks CAP_DAC_OVERRIDE and cannot write to the project folder, which belongs to the operator's uid: npm install gave EACCES for every dev agent (AT-247, ADR 0180).

    1. The api measures, the broker composes. container-spec returns usuarioDaPasta (stat of the folder for the container/mounted modes; null if the folder is not reached, if the owner is root or if the project is runner). The broker copies it into spec.usuario and the adapter emits --user uid:gid and --env HOME=/tmp.

    3. The broker revalidates. Integers in 1..2^31-1; 0 is refused naming usuario.uid/usuario.gid (root is the absent one, "as always").
    4. It does not loosen containment: --cap-drop ALL, one bind, a two-valued network and five operations remain. An already created container only changes when recreated.

    RN-738 — Stopping a project container is immediate, and the /containers row rereads on deciding

    • Rule: every project container starts with --init — a CONSTANT of the docker run composition in DockerViaCli, never a spec field (the containment is the type, ADR 0130); it applies to the broker and to the runner, which use the same port.     RN-807 — An exec that exceeds the ceiling comes back as an overflow, and the command dies inside the container

    • Rule: the overflow of the DockerPort's exec ceiling is decided by the CLOCK (elapsed ≥ ceiling) besides killed, because the docker exec client catches the SIGTERM of execFile's timeout and exits with code 0 — measured: sleep 30; echo FIM under a 3s ceiling came back erro: null, stdout: "", and the adapter returned exitCode: 0. An agent command that exceeded the 120s came back "exit 0", and QA approved a suite that hangs. The overflow now returns exitCode: -1, timedOut: true and the timeout mark. And killing the client does not kill the command: exec wraps the command (which stays as ONE argument, intact) in an sh that records its own PID — group and session leader, because the runtime does setsid on every docker exec — in the container's /tmp; on overflow the adapter kills the GROUP by that PID (SIGKILL), in an internal call, without a new operation on the port (ADR 0130). Measured and refused: busybox's timeout inside the sh -c — the watcher dies with the client and the sleep survives. If killing fails (/tmp not writable, for example), the mark says the process may have survived.

    RN-820 — The project container comes back on its own when the daemon restarts
