    ADR 0104 第 1 波——execution_mode 三个值，工作区由 runner 验证

    RN-423 — runner 确认路径；没有确认，命令被拒绝——永远不落入容器

    runner 是 runner 项目路径的事实来源，而不是向导中输入的内容。Phoenix 频道一连接上 （terminal:<projectId>，角色 :runner），apps/runner/src/index.ts 就推送带有它从命令行收到的 --dir 的 workspace_confirm。engine 把它转发（Engine.Sessions.EngineApiClient.confirm_workspace/4）到 POST /internal/projects/:projectId/workspace-verification （ConfirmProjectWorkspaceUseCase），后者：

    1. 如果项目不在 runner 模式，以 400 拒绝；
    2. 用与创建时相同的词法谓词重新校验路径 （RN-422）——即使来自 runner，系统根目录和与 Brabo 的重叠仍然被禁止；
    3. 用规范化后的路径覆盖 workspacePath，并写入 workspaceVerifiedAt = now()——不要求与创建时输入的内容相同：runner 说了算；
    4. 是幂等的——重新连接时报告相同路径不会重写任何东西 （changed: false）；不同的路径会重写，因为每次重连时 runner 仍然是事实来源；
    5. 项目中还没有会话时（ProjectSession.latest_id/1 返回 nil）：UPDATE 照样发生，只是事件 project.workspace_verified（以及 workspace-verificado gate 的证据）缺失——与 pty_open/pty_close 已经接受的降级相同（RN-108/RN-420）。被接受并声明的缺口，不是静默的。

    Engine.Actions.TerminalExecutor.decisao_de_execucao/1 有四个出口，而不是两个：runner 且 workspace_verified_at: nil 拒绝 （:recusar_nao_verificado）；runner 已验证但没有已连接的 runner 拒绝（:recusar_runner_desconectado）；runner 已验证且已连接则路由（:rotear_runner）；任何其他模式走一贯的路径 （:caminho_de_sempre）。两种拒绝永远不会落入 System.cmd——runner 项目没有 bind-mount，“落回一贯的路径”就是在一个 engine 进程看不到的文件夹里盲目执行。同样的拒绝也适用于竞态（run/3 开始时 Registry 说已连接，但 runner 在分派回应之前掉线了）。

    • 位置： apps/api/src/application/use-cases/iam/confirm-project-workspace.use-case.ts、 apps/api/src/interfaces/http/internal/internal-projects.controller.ts （POST :projectId/workspace-verification）、 apps/engine/lib/engine/actions/terminal_executor.ex （decisao_de_execucao/1）、apps/engine/lib/engine_web/channels/terminal_channel.ex （handle_in("workspace_confirm", ...)）、apps/engine/lib/engine/sessions/engine_api_client.ex （confirm_workspace/4）、apps/runner/src/channel.ts （enviarWorkspaceConfirm）、apps/runner/src/index.ts
    • 测试： apps/api/test/application/use-cases/iam/confirm-project-workspace.use-case.spec.ts、 apps/engine/test/engine/actions/terminal_executor_test.exs （describe "roteamento pro runner local"）、 apps/engine/test/engine_web/channels/terminal_channel_test.exs （describe "workspace_confirm"）、apps/runner/src/channel.spec.ts （join 之后的 enviarWorkspaceConfirm）

    • 架构决策： ADR 0104
    • 来源： ADR 0104 的调和，经与产品负责人确认的决定（runner 是事实来源；没有会话时 UPDATE 照样发生；没有验证/连接时命令被明确拒绝）

    RN-429 — 本地文件夹浏览是经由 Runner 的纯中继，从不是 api 枚举容器

    RN-434 — 在 Linux 上，本地 runner 的 --dir 只在用户的 $HOME 之内才被接受

    CLI brabo-runner（runner 模式，ADR 0103/0104）只校验 --dir 存在且是文件夹——对该文件夹可以位于文件系统中的何处没有任何限制。lerArgumentos() （apps/runner/src/index.ts）在存在性检查之后立即调用 validarDirDentroDoHomeNoLinux(dir, process.platform, homedir()) （apps/runner/src/guard.ts）：在 Linux 上（process.platform === 'linux'），--dir 只在 os.homedir() 之内才被接受——$HOME 本身或它的任何子文件夹；这棵树之外的路径（/etc、/root、/，甚至 /home 中的另一个账户）以 process.exit(2) 被拒绝，消息说明原因并显示期望的 home。在 Linux 之外（macOS、Windows）行为不变——限制只针对 Linux。

    该检查复用 dentroDoEscopo/semBarraFinal，即同一模块中 validarCwdDentroDaRaiz 已在使用的路径比较原语，但有意比它更简单：没有 realpath，也不防护 TOCTOU/符号链接，因为它不防御恶意服务器（那是 validarCwdDentroDaRaiz 的角色，在每次 exec 时执行）——它是本地 CLI 自身的启动检查，引导在启动 runner 时输错路径的用户。

    • 位置： apps/runner/src/guard.ts （DirForaDoHomeError/validarDirDentroDoHomeNoLinux）、 apps/runner/src/index.ts（lerArgumentos）
    • 测试： apps/runner/src/guard.spec.ts （describe('validarDirDentroDoHomeNoLinux', …)——在 Linux 上接受 home 本身及其子文件夹，在 Linux 上拒绝 home 之外的路径和 /home 内的另一个账户，并确认该限制在 Linux 之外不适用）
    • ADR： 0104 （附加扩展——runner 早已被声明为“路径的事实来源”；这条规则只是收窄了它在 Linux 上接受为 --dir 的东西）
    • 来源： 产品负责人在一次真实的项目创建测试中的明确请求（尝试把 --dir 指向 home 之外的路径 /home/dev/exp001，而该路径在机器上不存在——由此决定在 Linux 上锁定 $HOME 之外的路径）

    RN-435 — 本地 runner 不存在的 --dir 会被创建，而不是被拒绝

    CLI brabo-runner（runner 模式，ADR 0103/0104）过去会以 process.exit(2) 拒绝任何尚不存在于磁盘上的 --dir——必须在启动 CLI 之前手动创建项目文件夹。garantirDiretorio()（apps/runner/src/guard.ts）改为在文件夹不存在时自动创建它（mkdirSync(dir, { recursive: true })），lerArgumentos()（apps/runner/src/index.ts）在 validarDirDentroDoHomeNoLinux（RN-434）之后立即调用这个函数——顺序就是规则：$HOME 检查对尚不存在的路径也有效（只有 resolve()，不触碰磁盘），因此它先运行，并在任何创建尝试之前继续拒绝 Linux 上 home 之外的 --dir，即使它尚不存在——先创建会重新打开 RN-434 刚刚关闭的漏洞。指向一个已存在文件的 --dir 仍然是真正的错误（DirNaoEUmaPastaError、process.exit(2)，不尝试创建任何东西）——这个 CLI 从不悄悄覆盖文件。创建本身失败（权限被拒、磁盘已满等）也会拒绝（NaoConsegiuCriarDiretorioError），并嵌入原始错误的消息。

    • 位置： apps/runner/src/guard.ts （garantirDiretorio/DirNaoEUmaPastaError/NaoConsegiuCriarDiretorioError）、 apps/runner/src/index.ts（lerArgumentos）
    • 测试： apps/runner/src/guard.spec.ts （describe('garantirDiretorio', …)——文件夹已存在时什么都不做，不存在时递归创建，路径已存在且是文件时不创建而拒绝，并把 mkdir 的失败包装为 NaoConsegiuCriarDiretorioError；以及在 describe('validarDirDentroDoHomeNoLinux', …) 中多加一个用例，证明 home 之外且尚不存在的 --dir 仍被拒绝，确认两项检查的顺序不会打开漏洞）
    • ADR： 0104 （附加扩展——不改变 runner 作为路径事实来源的设计，只降低启动新项目的摩擦）
    • 来源： 产品负责人的请求，他注意到 runner 模式下一个新项目的文件夹在机器上不存在，需要在运行 CLI 之前手动创建——与促成 RN-434 的场景相同（不存在的 /home/dev/exp001），现在通过创建文件夹而不只是拒绝来解决

    RN-452 — node-pty 通过注入解析，而不是静态导入——由此在 npm 冒烟测试中打开的缺口在同一个 commit 中关闭

    pty.ts 不再在模块顶部静态地 import * as nodePty from 'node-pty'——改为在 GerenciadorDePty 的构造函数中通过注入接收已解析的模块，在 main()（src/index.ts）中经由 native-pty-loader.ts#carregarNodePty() 解析一次。这一变化是为独立二进制（ADR 0112）而存在的：编译后的路径需要在解析 node-pty 之前把嵌入的文件解压到一个真实目录，这需要一次异步调用——与被提升的静态 import 不兼容。在编译后的二进制之外，行为与之前完全相同（await import('node-pty')，从安装该包的人的 node_modules 解析）。

    这一变化打开的缺口，在同一个** commit 中关闭**：ADR 0106 早已记录，node-pty 的静态 import 因为在任何参数解析之前被提升，使得 smoke-dist.mjs 仅通过导入 dist/index.cjs 就证明了原生绑定能加载——即使在 uso() 路径（零参数）上，它从未到达 main()。把解析移进 main() 悄悄破坏了这种保证，因为 smoke-dist.mjs 只走 uso() 路径。smoke-dist.mjs 增加了第三项检查——用有效参数运行 CLI（但另一端没有真实的 api/engine），在杀掉进程之前等待 stdout 中出现 node-pty carregado com sucesso 这一行——关闭了这一变化本身打开的缺口，而不是让它成为静默的覆盖率损失。

    • 位置： apps/runner/src/pty.ts（GerenciadorDePty，注入 NodePtyModule）；apps/runner/src/native-pty-loader.ts （carregarNodePty）；apps/runner/src/index.ts（main，解析一次）； apps/runner/scripts/smoke-dist.mjs（第三项检查， verificarNodePtyCarrega）
    • 测试： apps/runner/scripts/smoke-dist.mjs（npm/tsup 路径）和 apps/runner/scripts/smoke-bin.mjs（二进制路径，RN-451）——仅有的两个真正运行打包制品的地方，没有单元测试可以替代
    • ADR： 0112
    • 来源： 独立二进制的技术需要；npm 冒烟测试中的缺口是通过对这次变更的自我审计发现的，而不是通过报告失败的真实运行

    对话型智能体的决策制品（RN-505）

    RN-507 — Docker 成为 runner 模式的真正前提：三种执行模式要求相同的谓词

    在此之前，Engine.Actions.TerminalExecutor.decisao_de_execucao/1 为把终端路由到 execution_mode: runner 项目只检查两个前提——工作区已确认和 runner 此刻已连接——两者一满足就无条件路由，不检查是否有记录为 running 的容器（Engine.Containers.ProjectContainerLifecycle.running?/1），而 container/mounted 自 RN-502（ADR 0143）起就已要求这个谓词。另一边的 runner 自行决定命令是在它启动的容器内运行（ADR 0137）还是落到纯宿主机——而当用户机器上没有运行 Docker 时，它总是悄悄落到宿主机：ADR 0134 试图为 container 建立的隔离从未对 runner 生效。

    修正把三种模式统一在同一个问题之下。 runner 获得第三个前提，与另外两个按同样的顺序：已验证 → 已连接 → 容器 running。三种具名拒绝（工作区未验证、runner 未连接、没有容器）如今位于 Engine.Runners.RunnerReadiness——之所以提取出来，是因为在同一个 PR 中诞生了第二个消费者（Engine.Actions.Workspace.RunnerGit，见下文）：“这不是两个推导，而是这个函数有两个消费者”，与 ProjectContainerLifecycle 的 moduledoc 相同的推理。

    镜像把工作复制到用户的文件夹（RN-516）

    RN-516 — 镜像目标随 join 的「授予」传递，镜像只按单一方向复制 git 的列表且绝不删除，触发点是一个具名时刻——绝不是 watcher

    FASE 28 第 6 次会话的 B 半部：espelho 能力（RN-514，ADR 0147）开始「存在」。RN-515 决定了目标放在哪里，没有复制任何文件；本规则决定它如何到达本地代理、复制什么以及何时复制。

    目标随 join 的授予传递，绝不在 runner 的配置中。 对 :runner 角色而言，频道 terminal:<projectId> 的 join 回应不再为空：当项目声明了目标（projects.mirror_path）并且授予了 espelho 能力时，它携带 %{espelho: %{destino: "<caminho>"}}。runner 将其保存在 estado.destinoDoEspelho 中，随连接一同消亡，并且对那条连接中未授予它的目标拒绝 mirror_sync（ADR 0147，第 4 点）。绝不是环境变量，绝不是本地文件：全局目标会让项目 B 的产物落进项目 A 的文件夹，而用户会通过内容、而非通过错误发现这一点。

    已声明的后果，也是代价：在 runner 已连接时更换目标需要重新连接它。 授予属于 join，从另一扇门到来的新目标恰恰就是规则所拒绝的全局配置。

    非空的 mirror_path 开始「要求」该能力。 它不进入按 execution_mode 的映射——要求它的是项目的一项「数据」，而不是模式（mounted 和 runner 可以有目标，而 container 不能）。这是 RN-514 留下的、已实现但从未触发的拒绝机制的第一个真实案例：早于此版本的 brabo-runner 连接到有目标的项目时将无法再连接，并收到点名的拒绝（JoinRecusadoError，致命且不重试）。这是 opt-in——只在有人配置了目标的地方发生——其代价已在 ADR 0147 中声明。

    守卫的「三种」拒绝，realpath 那一遍并不多余。 apps/runner/src/espelho-guard.ts 是 guard.ts 的兄弟，而不是它的扩展：复用 semBarraFinal/dentroDoEscopo/realpathMaisProximo 以及 validarCwdDentroDaRaiz 的「先词法再 realpath」双遍检查，并以书面形式继承同样的 TOCTOU 保留意见——它是尽力而为，不是安全边界。它拒绝 (1) 逃出目标的 symlink，(2) 包含 workspace 的目标，以及 (3) 位于 workspace 之内的目标；(2) 和 (3) 是方向相反的同一个环，而在 ADR 0141 的按身份绑定下，把镜像写进源头会让镜像复制镜像自身。api 已经拒绝了词法的一半（RN-515），并在代码中说明那只是词法——它没有可以解析用户计算机上 symlink 的磁盘。destino/atalho -> /caminho/do/projeto 在那边会被放过，而这里会解析它。

    实现时发现的一处机制差异：realpathMaisProximo 会落到第一个存在的祖先，而镜像目标几乎从不存在（是本轮的 mkdir -p 创建它）。把两边都折叠到祖先会让 /base-outra 和 /base 都变成 /，守卫就会拒绝所有兄弟文件夹。因此第二遍解析祖先并重新接上后缀——symlink 只能存在于存在的段中，所以剩下的部分绝不会藏着任何链接。拒绝 (1) 还有第二半，按文件进行（caminhoNoDestino）：一个指向 /etc 的 destino/sub 链接会让 sub/passwd 的复制写到外面，而目标本身却完全合法。

    单一方向，且「绝不」删除。 Workspace → 目标。绝不 --delete，绝不 unlink，绝不 rm。在 workspace 中删除的文件会留在目标中，这是决定，不是疏忽：用户的文件夹不是副本，而是累积——因为另一边的一次 git clean 而去删除某人个人文件夹中文件的代理，正是产品存在就是为了不制造的意外。覆盖已改变的文件是预期的；删除从来不是。ADR 中声明的代价：目标只增不减，没有任何自动机制清理它。

    复制的是「git 的列表」，别无其他。 已跟踪的文件（git ls-files）加上未被忽略的未跟踪文件（git ls-files --others --exclude-standard），带 -z（没有它，git 会给含空格或重音的路径加引号并转义）。这恰好就是「工作」：跳过 node_modules、dist、构建产物以及 .git 本身，无需维护任何排除列表——那种列表会随每个新技术栈而过时——项目的 .gitignore 已经是这份列表，由维护项目的人维护。workspace 从构造上就是 git 仓库（产品在其中配置 Gitflow，并用 git init/fetch/checkout 将其实体化），所以这一前置条件属于「产品」，不是对机器的假设。git 失败或文件夹不是仓库时，以点名的原因失败——绝不以 cp -r 全部内容作为 B 计划，那样整个 node_modules 就会落进某人的个人文件夹。

    两个已验证且已声明、不加隐藏的属性：嵌套的 git 仓库作为「一个」目录条目返回，不会深入——每个 dev agent 的 worktree（<workspace>/.worktrees/<agent_id>）就是这样一个，所以镜像显示的是主检出，绝不是仍隔离在 worktree 中的工作；而源头中的 symlink 被跳过，因为跟随链接会把项目之外的内容带进个人文件夹。被排除的东西会被「计数」（pulados/recusados），绝不被吞掉。也没有「变了吗？」的启发式：总是复制会花掉相同字节的代价，而按大小+mtime 跳过则会让镜像静默地不复制一个已经改变的文件。

    「自己的」谓词，镜像不要求 Docker。 Engine.Runners.RunnerReadiness 逐字节保持原样（ADR 0147，第 3 点）——Engine.Runners.Espelho 不调用它、不扩展它，也不从它接收任何东西。镜像有「两个」前置条件：workspace 已确认、runner 已连接，没有 RN-507 加上的第三个（已「登记」为 running 的容器）。带有「跳过容器」标志的 RunnerReadiness，恰恰就是第三个前置条件在未来某次重构中意外地对 exec 失效的机制，而 ADR 0145 的存在就是为了不让它失效。而镜像确实不需要它：第三个前置条件之所以存在，是因为原本有两种可能的执行，而错误的那种看不见；在用户机器上复制文件，没有可以掉落的容器。它也不询问 execution_mode——做出这一决定的已经是 api，在写入目标时（RN-515 拒绝 container），重复这一决定就是同一规则的第二个来源。

    由「具名时刻」触发，绝不是 watcher。 engine 从代码中一个有名字的点推送 mirror_sync——目前是成功的提交（EngineWeb.ActionCommandController，git_commit）。绝不用 fs.watch：watcher 是由任何事情触发的无限工作——一次依赖安装、一次构建，更糟的是镜像自身的写入，那就是环——并会在用户机器上持续运行而无人要求，这与「本地代理」应有的含义相反。该推送是 fire-and-forget：没有 from、没有 pending_execs、也没有 mirror_sync_result，因为触发者正在做别的事，而同步的遥测是 ADR 的第 7 点，属于另一次会话。镜像失败会变成本地日志，绝不是让 runner 崩溃的异常，也绝不是沉默。

    它「不是」proposed_action，也不应变成。 镜像的写入是用户声明的配置，不是代理请求行动——ADR 0147 对此明确，而通过终端命令同步会落入 ADR 0055 的范围，变成例行审批的队列，侵蚀那道赋予点击意义的上限。

    本地代理成为「用户」服务，status 不坍缩状态（RN-518）

    RN-518 — brabo-runner service install|uninstall|status 以「用户」级别安装，绝不用 root；uninstall 清理「unit」所登记的文件夹；status 回答四种状态且不坍缩任何一种；Windows 是点名的拒绝

    FASE 28 的第 7 次会话，以及 ADR 0147 的第 5 点。在此之前，本地代理只能在前台运行：一个由 SIGINT/SIGTERM 结束的进程，随终端一同死去，也不会随用户会话回来。没有任何先例——apps/runner/ 中没有任何地方提到 systemd、launchd 或 LaunchAgent。

    用户级别，「始终」如此——root 是「拒绝」，不是警告。 Linux 上是 systemd --user，macOS 上是 LaunchAgent。这不是打包偏好：apps/runner/src/guard.ts:9-31 的 docblock 声明 "o runner roda NA máquina do usuário, com os privilégios DELE"，这是产品三道真实边界（认证、审批流水线、同意）所依托的前提——而 cwd 守卫明文写着是尽力而为，正因为撑住任何东西的都不是它。以 root 运行的系统服务会打破这一不变量，让尽力而为的守卫成为已批准命令与机器磁盘之间唯一的东西。因此 uid 为 0 时的 install 会拒绝并点明原因，不写任何文件，也不运行任何命令：安装后再警告会让错误的安装留在原地，而警告只会被读一次。

    Windows「不在范围内」，拒绝是点名的。 构建矩阵已经产出 Windows 二进制（ADR 0112），但那里的用户服务是第三种机制（以用户账户运行的操作系统服务，或登录时的任务计划程序）——不是前两种的变体。三个子命令的回答都会点名平台，说明这是已声明的决定，并指出仍然可行的途径（在前台运行）。绝不是沉默的失败，绝不是什么都没装的「已安装」。任何其他平台也落入同样的拒绝。

    每个项目一个 unit，以 projectId 命名——brabo-runner-<id>.service / dev.brabo.runner.<id>——因为服务器已经强制每个项目一个 runner：同一个 terminal:<projectId> 上的第二次 join 会被 Engine.Runners.Registry 拒绝。按「文件夹」命名会允许安装两个永远不可能同时运行的 unit，而第二个会表现为连接失败，而不是安装错误。从另一个文件夹再次安装会覆盖。uninstall 和 status 能准确找到同一个 unit，因为它们从「同一个」projectId 推导名称，按与一直以来的 CLI 相同的顺序、由「同样」的两个来源解析（--project，否则 brabo-runner.config.json），而文件夹取自 guard.ts 的 resolverDir——绝不是第二把尺子。在 Linux 上，文件放到 systemd 会去找的地方，按它的优先级：变量设置时为 $XDG_CONFIG_HOME/systemd/user，未设置时为 ~/.config/systemd/user——只选后者会让 unit 诞生在管理器从不查看的地方，而失败会以 enable 时的 "unit file does not exist" 出现，看得见，但原因是错的。

    projectId 会变成「文件名」，所以在这里校验它。 它来自两个不是服务器的来源（一个输入的标志和文件夹中的一个文件），而 --project ../../etc/systemd 会写到 unit 目录之外。只允许字母、数字、.、- 和 _，最多 64 个字符——UUID，即产品中每个项目的真实格式，可以完整通过。runner 的路径和含双引号或换行的文件夹同样是点名的拒绝：unit 文件中的换行是指令注入，不是边界情况。

    服务以「设备密钥」认证，绝不用令牌。 install 要求文件夹中有有效的 brabo-runner-device-key.jwk.json，没有就拒绝，并有意忽略 --token/BRABO_ACCOUNT_TOKEN：把账户令牌写进 unit 文件会让它留在磁盘上，可被用户的任何进程读取，并在导出它的 shell 结束后继续存在——而这个 CLI 从未把凭据写到磁盘（auth.ts 的 docblock 有一个专门防止这种情况的测试锁）。RN-434 照样运行，通过「同一个」函数：在 Linux 上指向 $HOME 之外的服务会被拒绝，因为用 unit 做 CLI 拒绝用标志做的事，就是从后门绕过规则。

    RN-529 — brabo-runner 诞生时带有本地「基目录」，每个项目是它的一个子文件夹，而基目录「绝不」使 --dir 失效

    本地代理原本没有基目录的概念。唯一的根是 --dir，由 resolverDir 相对于 INIT_CWD ?? process.cwd() 解析；没有该标志时，根就是 cwd 本身。estado.dir 是一个路径，单数——那条连接所属项目的路径——，没有任何常量、变量或字段说明项目在那台机器上住在哪里。「基目录」这个词只出现在注释中。

    守卫复用尺子；不会诞生第四份拷贝。 base-guard.ts 是 guard.ts 的「第三个」兄弟，与 espelho-guard.ts 并列：导入 semBarraFinal、dentroDoEscopo 和 realpathMaisProximo——这三个辅助函数正是为此不再私有（RN-516）——，重复 validarCwdDentroDaRaiz 的「先词法再 realpath」双遍检查，并「整个」复用 validarDirDentroDoHomeNoLinux 来要求 Linux 上基目录位于 $HOME 之内（基目录在 $HOME 之内意味着每个子文件夹都在其中，所以两项检查仍然一致）。从 espelho-guard.ts 的环拒绝中复用的是尺子——dentroDoEscopo，按「段」比较，绝不是原始的 startsWith，这样 /base-outra 不会算作在 /base 之内——而不是 recusarLaco 函数，它抛出 DestinoDeEspelhoInvalidoError，会把格式错误的基目录报告为镜像问题。与 RN-515 相同的教训：复用的是尺子，不是消息。

    这里的环是「不对称」的，这就是发现。 在镜像中两个方向都是缺陷。这里项目文件夹位于基目录「之内」是「正常」的安排——这正是「每个项目是它的一个子文件夹」字面上的意思。反方向才是环：基目录位于本项目的根之内（或等于它），会让每个新项目都诞生在这个项目之内，本项目的 git 和镜像开始扫描其他项目。只拒绝这一个方向。

    本地代理打开 N 条连接，每个项目一条（RN-544，FASE 30）

    RN-544 — 本地代理打开 N 条连接，路由发现的每个项目一条——重试上限和 join 拒绝不再属于「进程」

    RN-543 开放了 GET runner/projects，却没有调用方。brabo-runner 仍然要求 --project：index.ts 中有 if (!projectId) uso()，不存在没有项目的执行。本 RN 就是消费者——也是 ADR 0154 证明其发现的那一半："um único processo que abra N conexões — uma por projeto que ele atende — satisfaz os itens 1, 2 e 3 byte a byte"。engine 中没有任何变化：主题 terminal:<projectId>、socket id 和票据描述的是一条「连接」，N 条连接仍然是 N 条连接。对同一项目中第二个 runner 的拒绝保持不变，这是真实的保证，不是偶然。

    两种模式，旧的逐字节不变。 使用项目凭据的 --project/--dir——包括浏览器流程（ADR 0118，RN-464）——是一直以来的路径：「一条」连接，它的结果仍然是进程的结果。新模式要求「两样」东西，原因各不相同：「机器」凭据，因为路由接受的是它；以及已同意的基目录（RN-529），因为没有它就无从推导每个项目的文件夹，而捏造一个就是往用户磁盘上写一个他没有同意的路径。没有基目录时，不带 --project 运行仍然落入 uso()，说明缺的是两者中的哪一个。

    runner 不知道自己密钥的种类，这是决定。 在磁盘上，机器密钥和项目密钥是「同一种」文件：一个带 kid 的私有 JWK（RN-475）。知道的是「服务器」，它通过这个 kid 找到公钥。所以 CLI 去询问，PatAuthGuard 点名的 403 变成 CredencialNaoEDeMaquinaError，带有 api 的原话和修复办法（--project）——绝不是笼统的「连接失败」。本地猜测会成为关于同一件事的第二个真相来源，而本地的那个会是错的。这次调用的 JWT 不带 projectId 声明，因为守卫比较 payload.projectId !== request.params.projectId，而在没有项目的路由上两者都必须是 undefined。

    N 条连接需要 N 个状态。 EstadoDoRunner 的四个字段是按项目的——dir、canalAtual、containerAtivo、destinoDoEspelho——再加上由 dir 产生的 gerenciadorPty。共享状态会让一个项目的 docker exec 在「另一个」项目的容器中运行，让一个项目的 PTY 在另一个项目的文件夹中打开。docker 和 base 属于「机器」，作为「同一个」值进入所有状态，绝不是可能分歧的拷贝。类型没有变，处理器（tratarExec、tratarMirrorSync、tratarWorkspaceCreate…）一行都没变：镜像（RN-516）和 workspace_create（RN-532）本来就是按项目的，并且本来就随那条连接的 join 授予传递，这正是让它们在 N 条连接下也正确的东西。

    上限和拒绝变成「项目」的。 它们原本属于进程：join 被拒绝会导致 process.exit(1)，TETO_DE_TENTATIVAS_SEGUIDAS 耗尽也是。有 N 条连接时，因为一条而杀掉全部，会让代理在所有正常工作的项目中都倒下。所以每个项目有自己的循环和计数器；被拒绝或耗尽的项目单独结束，并「点名」，其余继续——只有当一个都不剩时，进程才以 1 退出，并附上说明每个项目结果的摘要。循环的每条日志都以项目名为前缀：在 N 个交错的循环中，没有归属的「连接失败」就是有 N 个东西时沉默所呈现的样子。在 projeto 模式中旧的处置完全相同，出于相反的同一推理：只有「一条」连接时，就没有剩下要服务的东西。

    列表在启动时只查询「一次」。 定期重新查询被考虑过并拒绝：为一个罕见事件付出周期性调用的代价，而真正的代价不是流量——而是一个变「短」的列表是有歧义的（项目被删除、模式被转换、角色被吊销，或一个伪装成这三者的瞬时 500），因为这种歧义断开「活动」连接，会把一个确定的状态换成一个猜测。进程在启动时说明这一点，而获取新项目的动作是重新连接代理——一条命令，借助 RN-518 的用户服务。

    「空」列表是正常状态，以 0 退出。 这是每台刚安装的机器的状态：安装程序在任何项目存在之前就启动代理（ADR 0155）。这不是错误，所以不是错误码——而 Restart=on-abnormal（RN-518）不会重新拉起它，这是对的：没有要拉起的东西。以零条连接保持运行，就是一个什么都不做的「活动」服务，unit 的 status 就会开始撒谎。

    每个项目的文件夹是 <base>/<workspaceDirName>，经过已有的守卫。 resolverPastaDoProjetoNaBase（workspace_create 使用的「同一个」，原因也相同：名称来自网络），再加上 validarDirDentroDoHomeNoLinux（RN-434）和 garantirDiretorio（RN-435）——不会诞生第四份尺子拷贝。创建文件夹是把 RN-435 应用到一个「推导」的而不是输入的路径；这里「不」发生的是 git init/克隆，那仍然属于 workspace_create（RN-532）。文件夹被拒绝的项目被点名移出计划，不会拖垮其他项目。在机器模式下 OpcoesDaBase.raizDoProjeto 接受 null：没有 --project 就没有 --dir，环拒绝失去了主体（每个根都由基目录推导，所以「基目录在某个项目的根之内」无从构造），而在那里传入基目录本身会更糟——dentroDoEscopo(base, base) 为真，每个基目录都会被拒绝。

    「机器」unit，与按项目的 unit 共存（RN-545）

    RN-545 — service install --machine 为机器安装「一个」unit，两个种类不会重叠

    RN-544 让机器代理作为「进程」存在——N 条连接，路由发现的每个项目一条——并以书面形式声明了缺少的东西："a unit continua sendo POR PROJETO; este PR muda o PROCESSO, não o serviço"。本 RN 是另一半，也是 ADR 0154 测量的五个耦合中的第五个也是最后一个（apps/runner/src/servico.ts:264,391）。其他四个已经关闭或被声明为不可触碰：第 1、2、3 项描述的是一条「连接」，N 条连接逐字节满足它们，第 4 项在 RN-543 中关闭。

    机器 unit 的名称不能与任何 projectId 冲突，而它按构造就不冲突。 brabo-runner.service / dev.brabo.runner，没有后缀，对比 brabo-runner-<projectId>.service / dev.brabo.runner.<projectId>。PROJECT_ID_VALIDO 要求至少一个字符，所以项目名在机器名结束的地方总有一个 -（或者在 launchd 中一个分隔用的 .）——两者永远不会产生同一个字符串。这由测试锁定，而不是靠阅读正则。

    平台层改为按「种类」而不是按 projectId 为键。 PlataformaDeServico 的八个成员中有六个接收 projectId: string；它们改为接收 AlvoDaUnidade，一个可辨识的类型（{especie:'projeto', projectId} | {especie:'maquina'}）——绝不用 projectId: string | null，因为有了 null，每个成员都会自行决定如何处理它，而编译器不会要求任何一个。PlanoDeInstalacao 出于同样的原因变成联合：项目计划的三个字段在机器上失去意义，那里没有项目、没有 --dir（每个根都来自基目录），api 也不能来自一个按项目的文件。caminhoDaUnidade 从成员「下沉」为函数，因为两个平台回答的是同一件事——文件夹加名称——，维持两份相同的实现，就是在第二个种类到来时让它们分歧的机会。

    区分依据是 --machine 标志，「绝不」是缺少 --project。 ADR 0154 第 5 点写道 "service install sem --project instala a unit de máquina"，这在本次会话中经测量后无法按字面实现：resolverProjeto 有「两个」来源，而今天的正常路径是在浏览器配置好的文件夹中不带任何标志运行 install——由 brabo-runner.config.json 来回答。把「没有 --project」当作「机器」，会静默转换已在使用产品的人的安装，而这恰恰是同一 ADR 第 5 点承诺不做的。所以新种类是显式 opt-in，两个项目来源逐字节保持不变，--machine 与 --project 同时出现是点名的拒绝，而不是捏造的优先级。

    install --machine 比项目那一半拒绝得更多，两种自己的拒绝都经过测量。 第一种：文件夹中不能有 brabo-runner.config.json。lerArgumentos 在缺少 --project 时通过这个文件解析 projectId，而机器模式恰恰是「没有 projectId」——一个 WorkingDirectory 中有这个文件的机器 unit 会静默地以「项目」模式启动进程，服务「一个」项目却自称机器代理。第二种：没有已同意的基目录（RN-529），机器代理在第一次启动时就会落入 uso()（RN-544），写入一个永远起不来的服务，就是本模块处处拒绝的「错误的安装留在原地」——基目录以「注入」方式进入（DependenciasDeInstalacao.resolverBase），与其他四个依赖一样，这样 servico.ts 仍然不会自行读取磁盘或环境。

    unit 冻结 XDG_CONFIG_HOME，绝不冻结基目录的「值」。 这与 RN-518 中 PATH 的决定相同，后果更大：正是这个变量决定基目录文件住在「哪里」（base.ts），而 systemd --user 不传递安装者 shell 的环境——没有它，一个把该变量指向 ~/.config 之外的用户，服务会读到错误的基目录，或者读不到。基目录的值有意不放进去：更换它仍然是编辑文件并重启，绝不是重新安装，这正是 base.ts 的 docblock 在拒绝「只用 --base 标志」时已经主张的。

    机器 unit 的 apiUrl 读取 BRABO_API_URL，项目 unit 不读。 「项目」计划的优先级逐字节不变（--api-url › 那个文件夹的配置 › 默认值），因为那里有一个文件在回答。在机器计划中，这个文件是按项目的，用不上，所以没有这个变量的话，--api-url 唯一的替代就是默认的 localhost——在设置了 BRABO_API_URL 的 shell 中安装会静默生成一个指向错误地方的 unit。它进入 ContextoDoServico（apiUrlDoAmbiente），绝不直接从 process.env 读取。

    当另一个种类已安装时，install 会「拒绝」，且什么都不删除。 机器代理服务其密钥所有者在 runner 模式下的「每个」项目；在它之上再加一个按项目的 unit（或反过来），会让两个进程争夺同一个 terminal:<projectId>，服务器会拒绝其中一个——很可能是人刚刚安装的那个，这是发现问题最糟糕的顺序。这一拒绝与该文件中已有的 root 拒绝采用「同一」标准："instalar e avisar deixaria a instalação errada de pé, e a mensagem seria lida uma vez só"。已存在的 unit 保持完好，消息点名每个的 uninstall，并且没有 --force——一个能推倒症状沉默的守卫的标志，会把沉默的症状带回来。这「不」违背 ADR 第 5 点：它保证的是已安装的按项目 unit 继续工作，而它确实逐字节继续工作；被拒绝的是「现在」制造重叠。

    status 回答所询问的种类，四种状态不会变成八种。 退出码仍然是「被询问」unit 的（RN-088）——把两者相加会抹掉是哪一个在请求关注，就像把五个决策队列相加会抹掉哪个队列是哪个一样。共存以「文字」显示，并且是来自磁盘的回答：另一个种类的 unit 按名称列出，不向管理器询问各自的状态，输出会「说明」它没有询问。这就是 ADR 0154 第 5 点的兑现——"deixar seis processos disputando três projetos em silêncio" 正是这一块存在就是为了防止的缺陷。没有 --machine 且没有可解析的项目时，主体是机器 unit（唯一一个名称不需要参数的），输出为想要另一个的人点名 --project；在本 RN 之前，同样的输入回答的是「需要知道是哪个项目」，对于拥有安装程序恰好产生的那种安装的人来说，这是一个问题而不是答案。

    uninstall 「不」继承这个默认值，这种不对称是有意的。 读错种类的代价是一行错误；删错种类的代价是一个服务和一把设备密钥。没有 --machine 且没有可解析的项目时它会「拒绝」，列出磁盘上存在的东西以及各自的确切命令——绝不两者都删，那会删得比所要求的更多。

    机器代理等待第一个项目，密钥在终端中诞生（RN-550/551，FASE 30）

    RN-550 — 连接数为零时本地代理「不」退出：它等待并重新查询列表；有活动连接时查询仍然只在启动时进行

    FASE 30 的第 8 次会话。RN-544 让空列表成为「正常」状态，进程以 0 退出，并说 "crie um projeto em modo Runner e suba o agente de novo — a lista é consultada só no start"。这与 ADR 0155 第 5 点白纸黑字地矛盾——"ele espera… quando a pessoa criar o primeiro projeto na web, o agente já está lá"——并恰恰破坏了本阶段所追求的情况：新安装，即项目数为零的安装。安装程序启动代理，代理发现什么都没有就离开了，而几分钟后创建第一个项目的人会回到终端，却从未被告知这一点。

    规则是「不对称」的，不对称就是设计：

    conexões > 0  →  a lista é consultada SÓ no start   (a RN-544 fica byte a byte)
conexões = 0  →  reconsulta, com cadência declarada

    它「不」推翻 RN-544 的决定。 那次会话的论点完整保留：一个变「短」的列表是有歧义的——项目被删除、模式被转换、角色被吊销，或一个伪装成这三者的瞬时 500——，因为这种歧义断开「活动」连接，会把一个确定的状态换成一个猜测。连接数为零时没有可断开的东西，也没有任何歧义：出现的任何项目都是纯收益，不会对消失的东西做出任何决定。重新查询在第一个非空列表到达的那一刻停止，此后的行为逐字节与今天相同——只要进程活着，等待模块就不会再被调用。

    exit 0 的论点不成立，因为它的前提不成立了。 RN-544 写道 "ficar de pé com zero conexões seria um serviço 'ativo' que não faz nada, e o status da unit passaria a mentir"——而这依赖于进程什么都不做。本 RN 移除的正是这个前提：它以声明的节奏重新查询，并「说明」自己在这样做。active (running) 变为真实，撒谎的是以 0 退出，它恰恰在人要创建第一个项目的那一分钟让新安装没有代理。

    节奏逐级递增并「稳定」：15 秒、30 秒、60 秒，最后一个永远重复。 两个短档存在，是因为要照顾的情况是有人「现在」正在创建第一个项目；以分钟计的上限会让代理在人放弃观看之后才出现。60 秒的平台是常态下的代价——一次安装每分钟「一个」请求，针对一个返回凭据所有者自己列表的路由。再增长就是节省没人在付费的流量，而让等待唯一交付的东西变差。

    有上限，而它是「失败」的上限，绝不是等待的上限。 等待没有限制——等待是新安装的正常状态，可能持续数天。有上限的是查询的连续失败：十次，之后进程以 1 退出并「点名」这个数字，就像连接循环对 TETO_DE_TENTATIVAS_SEGUIDAS 已经做的那样，原因也相同（问题不是暂时的时候，不永远捶打 api）。一次「有回应」的查询会把计数器清零——包括回应为「空」时，这是成功，因为空列表就是正确答案。这个常量有意「分开」，值相同：一个计数「连接」的失败，另一个计数「列出」的失败，把它们绑在一起会让连接节奏的改动在没人要求的情况下改变新安装放弃前等待的时间。CredencialNaoEDeMaquinaError（按密钥种类的 403，RN-544）不计入上限：它当场就是致命的，因为项目密钥不会因为多等一分钟就变成机器密钥。

    静默地保持运行比退出更糟。 对读 journalctl 的人来说，「等待中」和「卡住了」是同一幅画面，所以进程在进入等待时说明节奏，在第一个项目出现时说明，并每 30 次查询（在平台期是半小时）打一次「心跳」，告知已经查询了多少次。也有意不让每次查询都变成一行：每分钟一条日志、永远持续，正是会埋没重要行的噪音。

    Restart=on-abnormal 逐字节保持，在「两个」unit 种类中都是（RN-545），它们中没有任何改变。 已测量：on-abnormal 因「信号」、watchdog 或超时而重新拉起——绝不因退出码，无论 0 还是 1。以 0 退出从来不是阻止服务被重新拉起的原因；阻止它的是 on-abnormal 不看任何退出码。这一变化的真实效果与所担心的相反：运行这种模式的「机器」unit 开始真正保持 active (running)，而不是在启动几秒后以 inactive (dead) 结束——在新安装中，service status --machine 开始回答 rodando (0)，而之前回答 parado (3)。按「项目」的 unit 一行都不受影响：它运行 projeto 模式，永远到不了这里。

    一个已声明的例外：所有项目都被拒绝的「非空」列表仍然以 1 退出。 这也是零条连接，但仍然不等待——因为那里每个拒绝都点名了一个具体的本地缺陷（逃出基目录的段、是文件的文件夹），有自己的修复办法，而重新查询会无限重复同样的拒绝，把说明该修什么的那一行埋进日志。等待是为了 "ainda não existe projeto"，绝不是为了 "existe e eu não consigo atendê-lo"。

    RN-551 — brabo-runner device-key create/finish：Ed25519 密钥对在「机器上」诞生，私钥从不传输，runner 读取的文件绝不会在没有 kid 的情况下存在

    FASE 30 的第 8 次会话，另一半。在此之前，只有浏览器生成设备密钥对（apps/web/src/lib/runner-bootstrap.ts，ADR 0118，RN-464）；CLI 只会读取别人放在文件夹里的东西（device-key.ts）。ADR 0155 第 4 点要求另一边："o par é gerado na máquina; a privada nunca viaja… mantém verdadeira a frase que a RN-519 usa para recusar a visão de maintainer: 'a privada de uma chave de dispositivo nunca sai do navegador' — passa a ser 'nunca sai da máquina'"。没有它，RN-543、RN-544 和 RN-545 都带着同一个已声明的缺口：没有人创建机器密钥。

    这是「两」步，原因在于 kid。 写在私有 JWK 之内的 kid 「就是」服务器上登记的 id（RN-475）——整条链只是「转交」它（runner 读取 jwk.kid，JWT 把它放在头部，PatAuthGuard 凭它找到公钥），没有人从别的东西推导它。它只在公钥登记之后才存在，在那之前写入的私钥生来就无用，这正是 RN-475 花了一番追查才找到的那个缺陷。浏览器的解决方式是在登记与写入之间把密钥对保存在「内存」中；CLI 的解决方式是一个**不完整（PARCIAL）**文件：

    PUB=$(brabo-runner device-key create)          # gera aqui, imprime a PÚBLICA
ID=$(… registra PUB na api …  | jq -r .id)     # quem registra é o instalador
brabo-runner device-key finish --id "$ID"      # carimba o kid e grava

    任何时刻都不存在没有 kid 的 brabo-runner-device-key.jwk.json。 create 写入 …jwk.json.parcial，这是 lerChaveDeDispositivo 不会查找的名字；finish 盖上 kid 并写入真正的名字。runner「读取」的文件要么完整，要么不存在，两步之间的中断会留下一个 runner 「忽略」、下一次 create 会「点名」的 .parcial——说明那次尝试的登记可能已成为「孤儿」，它是惰性的，并出现在 RN-519 的列表中。

    CLI 「不」和 api 对话，原因在于「密钥」，而非技术。 登记机器密钥的是安装程序，由它刚刚生成的 BRABO_SERVICE_TOKEN 认证（ADR 0155 第 1 点）。让 brabo-runner 调用该路由，就需要把这个令牌交到它手上——一个「安装」级的密钥，能打开内部路由，交给一个今天只看到设备凭据、并且永远在用户机器上运行的进程。切分正好相反：每一边恰好保管一个密钥，谁也看不到对方的。穿过两者之间边界的是「公钥」JWK 和 id——没有任何需要保护的东西。

    默认目标是机器的配置文件夹，优先级是「复用」的。 $XDG_CONFIG_HOME/brabo/（否则为 ~/.config/brabo/），紧挨着 RN-529 的 runner.json，原因相同——这是「机器」的配置，而机器密钥没有可以住的项目文件夹。pastaDeConfiguracaoDoBrabo 在获得第二个消费者时从 caminhoDoArquivoDeBase 中「抽取」出来，绝不是复制。这不会重新打开 ADR 0104 第 2 波所关闭的那扇门（全局且「隐式」路径中的凭据）：device-key.ts 仍然只从调用方传入的 cwd 读取，而指向这个文件夹的是机器 unit 的 --dir（RN-545），显式地写在服务中。--dir 存在并服务于 项目文件夹——在磁盘上两个种类是同一种文件，知道区别的是「服务器」（RN-544）：这个命令不断言任何种类。

    私钥以模式 600 写入，显式设置，绝不交给 umask。 当文件夹由「本」命令创建时，它以 700 诞生；已经存在的文件夹属于用户（可能是浏览器配置的那个），不会被重新收紧。--dir 经过 RN-434 的「同一个」validarDirDentroDoHomeNoLinux，完整复用：写入的是用户的密钥，而位于其 $HOME 之外的文件夹不是他的 systemd --user 会去找的地方。

    stdout 携带「一个」值，占一行，其余全部是 stderr。 这是 install.sh 所依赖的契约（PUB=$(…)）：把两者混在一起会迫使脚本过滤给人看的输出，而契约就是这样在无人察觉中被打破的。在 create 中 stdout 是公钥 JWK；在 finish 中是文件的「路径」——下一步（service install --machine --dir <pasta>）需要的值。

    覆盖完整的密钥会被「拒绝」，没有 --force。 替换一台已配对机器的密钥，会静默地替换一个「现在」可能正在运行的代理的身份：公钥仍然登记着，而进程会开始用一把没人知道的密钥签名。拒绝点名动作（吊销、删除、重建），而一个能推倒症状沉默的守卫的标志，会把沉默的症状带回来。

    修复是「点名」的结果，而不是交付凭据。 docker exec 仍然没有 env 字段——改动它就是改变约束端口，属于 ADR 的决定，而不是取舍（见下面声明的缺口）。改变的是：(env 存在、容器活动) 这一组合不再被执行，而是被拒绝，带有标记、消息和来源。

    拒绝的是「RUNNER」，也只有它能。 它是唯一同时知道两半的进程：命令携带凭据，以及它将进入容器内部。engine 不知道后一半，这一点已被「测量」：estado.containerAtivo 在 runner 每次执行时都初始为 null（index.ts:1449），只由 tratarContainerStart 设置，所以一个容器 在数据库中被「登记」为 running，并不意味着容器在那个进程中是活动的——一个在容器运行时重启的 runner 会路由到「宿主机」，凭据在那里正常到达。把检查上移到 RunnerReadiness 或 RunnerGit 会拒绝一条可行的路径。而 RunnerReadiness 「逐字节」保持原样：它不获得标志，也不获得第四个前置条件——这与 RN-516 已经阐明的「不给它挂一个『跳过容器』标志」是同一条规则。

    来源是 politica，这一选择指向「行动」。 ADR 0020 的四种来源不分配责任，它们说明该做什么。这不是没人写的子句（codigo），也不是断掉的网络（infra）：这是 ADR 0130 的约束按设计运作，面对一个它没有预见的情况。读到 politica 的人知道没有 bug 要追——有一个待定的产品决定。Engine.Runners.CredencialDeGit.desfecho/1 增加「一个」情况，不重新分类任何其他情况：任何其他 worktree 失败在「两个」dev agent（真实的那个，以及 Noop——它的存在是为了演练「这条」路径而不是它的拷贝）中都逐字节保持 {"falha ao preparar o worktree", "codigo"}。

    重新启用的 Anamnese：合格的对象与档案事实（RN-680）

    RN-688 — runner 的二进制在 Bun 下用自己的读取器读取 PTY，自检证明「第二次」读取

    在 Bun 下（bun build --compile 的二进制，ADR 0112），tty.ReadStream（node-pty 用它读取 PTY 主端）是一个 fs.ReadStream，非阻塞 fd 上第一次没有数据的读取会以 EAGAIN 「抛出」：流自我销毁，关闭 fd，此后不再有任何 onData（oven-sh/bun#25822）。二进制的交互式终端在「三个」Unix 平台上都在第一段输出后停止；Linux 能通过测试只是因为第一次读取已经同时带回了回显和回答。

    规则： 在 Bun 下且不在 Windows 上，spawn（属于 node-pty）运行时会把 tty.ReadStream 换成一个自己的读取器，它用 fs.read 读取「同一个」fd，遇到 EAGAIN 时「等待」并重试（从 4 ms 开始，翻倍直到 32 ms，每次有数据就回到最小值）；EIO 或零字节表示结束。替换只在 spawn「期间」有效，即使它抛出也会恢复；在 Node 下模块保持「原样」。fd 和子进程仍是真实的——不模拟任何输出。并且 --self-test-pty 做「两」轮，第二轮在一段无可读内容的停顿之后：正是这段停顿迫使读取经过一次 EAGAIN，也正因此旧读取器在 Linux 上同样不通过。不通过时，自检会说明原因（数据段、子进程的输出、在第二个 PTY 上的探测以及流的事件）——裁决不变。

    正是探测测得了 Windows 的情况：在那里读取端是 ConPTY 的命名管道，由 node-pty 作为 net.Socket 打开，没有读取器可以接管的 fd，而管道在第一段之后就结束了——因此 win32-x64 被移出了矩阵（ADR 0187），而不是加一个变通方案。
