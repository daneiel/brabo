    Измерение маршрутизатора инструментов Jev

    AT-237 (EP-029, HS-063). Измерение вне продукта: ничто в apps/ не импортирует этот код, ничего не пишется в базу, и никакой выгоды продукта здесь не утверждается — это задача AT-239, которая сравнивает ходы с маршрутизатором и без него. Измеряемый маршрутизатор — тот, что специфицирует AT-235; решения, от которых он зависит, — из AT-236.

    Измерено 2026-09-29 против локального экземпляра dev (проект compose brabo-dev), репозиторий на d48f99f8ec. Второй раунд — варианты state, классы эквивалентности, разделение настройка/проверка, top-2 и расстояние по причинам — ниже.

    Что существует

    Всё живёт в scripts/jev/ и запускается Node репозитория (type stripping, без шага сборки, без новых зависимостей).

    Шаг, а не вызов инструмента

    Маршрутизатор опрашивается один раз на вызов чат-модели, перед provider.chat (AT-235). Шаг может нести несколько вызовов инструментов — десять emit_artifact в ответе Criativo, terminal + read_file в ответе dev, — поэтому опрос Jev по разу на tool.call задавал бы вопросы, которых продукт никогда не задаёт, с state, уже содержащим соседние вызовы того же шага.

    У event log нет маркера шага (AT-235, пробел 1), поэтому граница берётся из token_usage: api записывает строку на вызов LLM до того, как engine запишет tool.call этого ответа. Каждый tool.call той же сессии и того же актора между двумя последовательными строками — один и тот же шаг. Отсюда три метки:

    • шаг с одним инструментом (один или несколько его вызовов): метка = этот инструмент;
    • разнородный шаг (два разных инструмента): попадание = выбор Jev — один из них, — но ограничение меню одним инструментом отрезало бы остальное;
    • шаг без tool.call после своей строки: модель ответила текстом (или упала). Это единственная метка, которую responder_sem_ferramenta может получить этим методом, — бриф не ожидал ни одной; граница шага даёт семь.

    Моменты сравниваются как текст UTC фиксированной ширины с микросекундами: строка расхода и первый tool.call шага иногда попадают в одну и ту же миллисекунду.

    Отправляемый state

    Формат AT-235, вырезанный из того, что существовало до шага: agente; pedido — для разговорных агентов последнее chat.message, написанное пользователем; для dev agents и gates задач — заголовок задачи из dev.working; contexto — идентичность агента плюс строка agent_instructions проекта, когда она есть (два слоя системного промпта, а не весь собранный промпт); passos_recentes — последние 6 вызовов этого актора в этой сессии, с аргументами и результатом, обрезанными до 500 символов. Вопрос — choice, чьи criteria — это {name: description} каталога плюс зарезервированный responder_sem_ferramenta.

    Запрос идёт в POST https://openrouter.ai/api/alpha/decisions с моделью typesafe/jev-1.13. Исправление к AT-235, измеренное: questions — объект, индексированный по id вопроса, а не список — списочная форма получает 400 expected record, received array. Ответ — answers.<id>.{choice, probabilities, confidence}, usage.{input_tokens, output_tokens, cost}, id (gen-dec-…) и датированный снимок в model (typesafe/jev-1.13-20260917 в каждом ответе этого исполнения).

    Политика превращает ответ Jev в ограниченное меню. Решения владельца действуют везде: Jev только ограничивает меню, а когда он отвечает responder_sem_ferramenta, остаётся весь каталог (AT-236); потолок 2 000 мс (во втором раунде его не превысил ни один из 328 запросов).     политика меню
    P0 весь каталог (якорь: 100% покрытия, ничего не ограничивает)
    P1 два самых вероятных инструмента Jev
    P2 {выбор Jev, предыдущий инструмент того же исполнения}
    P3 P2, но если Jev говорит responder_sem_ferramenta (или предыдущего инструмента нет), меню — весь каталог

    Правила, общие для всех: упавший ответ (таймаут, ошибка, выбор вне вариантов) оставляет весь каталог; предыдущий инструмент, которого нет в каталоге агента, игнорируется; меню, которое вышло бы пустым, — весь каталог.

Доля ограничения = доля шагов, на которых меню меньше каталога агента: политика, которая почти никогда не ограничивает, тривиально «100%» и бесполезна, поэтому покрытие даётся также среди ограниченных шагов.     Потолок: чего не говорит покрытие

    Покрытие — это потолок сквозной точности, а не точность. Меню содержит правильный инструмент; модели агента ещё нужно выбрать его среди вариантов. Метка («инструмент, который вызвала чат-модель») — выбор, сделанный агентом из всего каталога, поэтому полное меню — 100% по построению, а ограниченное может только терять. Что можно сказать без продукта, для P3 на проверке, разделив 160 шагов:

    • 99 (62%, 54–69%): каждый инструмент меню верен, поэтому любой выбор агента верен — пол.
    • 46 «спорных»: ровно один из вариантов верен, и агент решает сам — 28 только предыдущий инструмент, 18 только выбор Jev. Агент, всегда берущий предыдущий инструмент, заканчивает на 127/160 = 79%; всегда берущий выбор Jev — на 117/160 = 73% (снова базовые линии второго раунда); бросающий монетку — на 76%. Агент, выбирающий лучше обоих, а на этом и строится вся ставка, попадает между 79% и потолком 91%.
    • Остальные 15 вне меню: потеряны, что бы ни делал агент.

    Итак, сквозной диапазон — от 62% до 91%, и где он окажется, зависит от того, насколько хорошо модель агента читает ситуацию, которую повтор не видит. Ответить на это может только живой тест (AT-239).

    Каталог содержал описание каждого инструмента (catalogo.json), а теперь ещё и definicoes: размер в байтах полного spec/0 каждого инструмента (имя, описание и схема параметров), сериализованного engine (catalogo.exs, запущен заново; остальная часть файла не изменилась). Токены — это байты, делённые на 4, приближение, которое использует весь повтор. На проверке P3 уходит с 746 до 138 токенов определений на вызов — 608 токенов, на 81% меньше: восемь инструментов dev agent весят 3 068 байт, а меню из двух — около 500. P1 экономит 596, P2 — 644 (средние по шагам половины; половина настройки экономит меньше, потому что Anamnese сохраняет весь каталог).

Кеш — подвох: провайдеры кешируют префикс запроса, определения инструментов идут первыми, а меню, меняющееся от шага к шагу, меняет префикс — экономия может быть возвращена промахами кеша. Это живое измерение, и причина, по которой тест ниже записывает долю кешированных токенов.

    Что запускает инструмент и что является переносом

    pnpm --filter @brabo/scripts jev:vivo (файлы в scripts/jev/vivo/) запускает цикл dev agent на пяти маленьких задачах, один раз с включённым маршрутизатором и один раз с выключенным, и вызывает OpenRouter напрямую — api, engine и база не участвуют, как в платной проверке языка AT-167.

    файл роль продукт или перенос
    roteador.ts recortarEstado, montarPedidoAoJev, lerRespostaDoJev, menuP3, потолок state код продукта, реэкспортированный из apps/api/src/domain/llm/tool-router.ts
    laco.ts цикл: потолок итераций, восстановление вызовов инструментов, написанных текстом, остановка на принятом report_done/report_blocked, единственная повторная попытка с полным каталогом, когда ограниченное меню получило ответ без инструмента перенос ToolLoop, EngineApiClient.llm_turn/5 и DecidirFerramentaDoPassoUseCase
    recuperacao.ts какие шаги прошли через tool_call_recovery.ex перенос; его spec прогоняет случаи tool_call_recovery_test.exs и фиксирует строки-якоря .ex
    rede.ts вызов чата (сообщения на проводе, как их пишет api) и вызов Jev (потолок 2 000 мс, те же именованные падения) перенос toWireMessage/toWireTool и JevToolRouter; строки-якоря зафиксированы
    ferramentas-dev.exs → ferramentas-dev.json полный spec/0 девяти инструментов Engine.Dev.Tools.registry/0 (имя, описание, схема параметров) прочитан из исходников engine чистым elixir, без скомпилированного engine; spec падает, когда реестр или описание дрейфует
    tarefas.ts пять задач над проектом Node без зависимостей, у каждой проверка, запускаемая после цикла (исходные тесты восстановлены, скрытые тесты добавлены): «задача вышла» собственный инструмента
    executor.ts инструменты в временной песочнице, возвращающие тексты engine там, где они зашиты в код собственный инструмента
    resumo.ts, vivo.ts таблица, правило решения, оценка стоимости, CLI собственный инструмента

    Вне инструмента, одинаково в обеих ветвях и заявлено: конвейер одобрения (terminal и write_file выполняются напрямую, как в автоматическом режиме), сжатие контекста, языковая ориентация и профиль автора, добавляемые в конце каждого вызова, RAG (пустой индекс), контракты модулей (ни одного не объявлено) и остальная часть настоящего системного промпта (файлы инструкций, бизнес-правила, состояние задачи). Системный промпт — это идентичность dev из engine плюс две строки контекста проекта; первое пользовательское сообщение — собственный kickoff engine (scripts/jev/kickoff.ts). Стоимость каждого вызова — usage.cost ответа, число, которое RN-665 (ADR 0188) кладёт в metering; token_usage продукта не участвует.

    • Модели: deepseek/deepseek-v4.1-flash (медленнее, рассуждающая) и anthropic/claude-haiku-4.5 (быстрее), две, до которых проверка AT-167 уже дотягивалась с определениями инструментов на этом ключе.

Оставить включённым по умолчанию, если все три выполняются на каждой модели; выключить, если качество проваливается на каждой модели или ни одна модель не проходит все три; ограничить моделями, которые проходят, — в противном случае. Меньше 10 исполнений на ветвь — это amostra_insuficiente, но никогда не вердикт.

    Рекомендация (измерено — решает владелец)

    Ограничить, по правилу, записанному до исполнения: оставлять маршрутизатор включённым там, где у чат-модели нет действующего кеша промпта и она достаточно медленна, чтобы дополнительный последовательный вызов был мал (класс Haiku, US$ 1,00/5,00 за миллион), и выключенным там, где провайдер отдаёт большую часть входа из кеша, а чат быстр (класс DeepSeek). Числа, которые это оправдывают, — строки правила выше: Haiku ×0,62 по стоимости и ×0,95 по задержке без потери качества; DeepSeek ×2,21 по стоимости и ×1,45 по задержке без выигрыша в качестве.

    Чего это не покрывает и чего потребовало бы ограничение:

    • Измерены только dev agents (ToolLoop). Прежнее прочтение — никаких свидетельств для семи разговорных агентов — остаётся в силе; ничто здесь на них не распространяется.
    • Разделение — по модели, а переключатель продукта — по workspace (PUT workspaces/:workspaceId/tool-router). Ограничения по модели (или по «действующему кешу») не существует; его создание — новое решение и новое изменение, здесь не сделанное. До тех пор измеренный выбор по workspace таков: включено, если его агенты работают на модели класса Haiku без кеша, выключено, если на модели класса DeepSeek с кешем.
    • Выборка и задачи малы (10 исполнений на ветвь, пять задач от 4 до 16 шагов). Отношения стоимости и задержки достаточно широки, чтобы их читать; разница качества в одно исполнение — нет.
    • Эффект кеша зависит от кеша провайдера, а не только от скорости: workspace на Haiku с включённым кешем промпта, вероятно, сдвинулся бы к линии DeepSeek. Не измерено.

    Предварительная рекомендация, которая была здесь до исполнения (ограничить: включено для dev agents, выключено для разговорных агентов), заменена вердиктом правила выше, как и говорил тот абзац.
