    Architectural decisions

    An ADR records why something was decided, at the moment it was decided. They are immutable: no ADR is edited after being accepted. When a decision changes, a new ADR is born that supersedes the previous one — that's what happened with 0018, which records the replacement of the NoopDevAgent decided in 0011.

    Practical consequence: an ADR can describe a state that is no longer current. For the current state, use Business rules, Architecture and the Runbook. For the reasoning, come here.

    Of the 61, all are accepted except those still waiting for implementation — today 0053, 0054 and 0056, marked proposed in the file itself. 0055 was accepted once it was implemented in Phase F. 0154 and 0155 took the same path: accepted on 2026-09-27, after Phase 30 exercised them, with an "acceptance notes" section naming where the text and the code diverge. No check verifies this sentence: it aged saying 48 when there were already 54, and again 58 when there were already 59, and it's the argument of ADR 0029 (gerar > verificar > lembrar) confirming itself against itself.

    The decisions are grouped by theme — the product front they decide about — and each ADR appears once, under its main theme. The theme lives in docs/adr/temas.yml, next to this page, and not in the ADR, because an accepted ADR is never edited (ADR 0202); pnpm docs:check fails an ADR without a theme or a row under the wrong section. The phase-by-phase story is in the phase history.

    Git, repository and branch policy

    The git provider contract, the repository's birth and adoption, protection and the branch policy.

    # decision
    0001 Format of the GitProvider's normalized contract: nine operations and declared capabilities, validated by a single contract suite
    0002 Error normalization: six specific classes, with no common base class — the abstraction was considered and rejected for not paying for itself yet
    0003 Automatic retry only on reads, never on mutations, with Full Jitter and 4 attempts
    0004 Registration of git credentials: dedicated enum in the database, united with LLM providers only in type
    0005 Gitflow bootstrap in six idempotent, resumable steps; skip is success
    0028 Branch protection diverges between GitHub and GitLab — and that's why it's not the gate; the gate is the domain
    0030 Mechanized branch policy: rule → mechanism, logic in a testable script, backmerge gate, and the cost of reintroducing each cut
    0044 Adoption of an existing repository with origin (created|adopted) in both tables, and the PLAN as the gate: the dry-run is the check() from ADR 0005 without run(), the plan lives in the cursor (a snapshot, not a log), and nothing is changed while the decision is null — the Phase 2 runner goes out verbatim to a collaborator and is never filtered, just not called; "divergent protection" stays at the boolean level because that's all the contract exposes (ADR 0028)
    0056 The engine works on a remote repository. get_local_repo_path/1 returns unsupported_provider for anything that isn't local, and four consumers stop along with it — the dev agent's worktree, the terminal executor, the diff that QA and SecOps judge, and the project context. The root cause is the asymmetry: the api speaks GitHub over HTTP (created the repo, committed, created the branches) and the engine works on the filesystem, only knowing a local bare repo; a remote project does the conversational half and stops at the construction half. That's what blocks Phase 13b from existing as writes. The git plumbing is already generic — init + remote add + fetch + checkout doesn't care whether the origin is a path or a URL —, so what's missing is a CREDENTIAL. The engine doesn't receive the master key: it asks the api for the working remote over the /internal/* channel that already exists, at the moment it needs it. And the token NEVER enters .git/config, a decision that's a direct consequence of 0055: writing https://x-access-token:TOKEN@… into origin puts the secret in plain text INSIDE the folder where RN-075 just granted the dev agent auto-approved read access — a cat .git/config would return the token, which would travel to the LLM provider on the next turn. Scope protects against reading outward, not against a secret the product placed inside. origin keeps the clean URL and authentication is injected per invocation.     The convention

    • One file per decision, at docs/adr/NNNN-short-title.md, with sequential 4-digit numbering, and the title # ADR NNNN — <title> (0218). No number reuse, not even when an ADR is superseded — the next one is 0220.
    • One theme per decision, chosen by whoever writes the ADR, in the same PR: a line in docs/adr/temas.yml and the index row under that theme's section, in numeric order. The reviewer confirms it. A new theme is a change to the list in temas.yml, justified in the PR that adds it; going past 15 takes an ADR that revises 0202.
    • Three sections, only those: Context (the problem or force that motivated it), Decision (what was decided), Consequences (the accepted trade-offs and what's left for later).
    • No third-party template — no Nygard, MADR or variants. The three sections are enough.
    • In Portuguese, like the rest of the project.
    • An accepted ADR is not edited. One superseded by a later decision stays as it is; the new ADR references the old one and explains what changed.

    What gives these ADRs their value is recording what did not work: 0020 documents nine failed executions in a row, and 0027 records a justification that was revised within the same session that produced it. An omitted bad consequence is the part that's missed six months later.
