Измерение маршрутизатора инструментов Jev

AT-237 (EP-029, HS-063). Измерение вне продукта: ничто в apps/ не импортирует этот код, ничего не пишется в базу, и никакой выгоды продукта здесь не утверждается — это задача AT-239, которая сравнивает ходы с маршрутизатором и без него. Измеряемый маршрутизатор — тот, что специфицирует AT-235; решения, от которых он зависит, — из AT-236.

Измерено 2026-09-29 против локального экземпляра dev (проект compose brabo-dev), репозиторий на d48f99f8ec. Второй раунд — варианты state, классы эквивалентности, разделение настройка/проверка, top-2 и расстояние по причинам — ниже.

Всё живёт в scripts/jev/ и запускается Node репозитория (type stripping, без шага сборки, без новых зависимостей).

Шаг, а не вызов инструмента​

Маршрутизатор опрашивается один раз на вызов чат-модели, перед provider.chat (AT-235). Шаг может нести несколько вызовов инструментов — десять emit_artifact в ответе Criativo, terminal + read_file в ответе dev, — поэтому опрос Jev по разу на tool.call задавал бы вопросы, которых продукт никогда не задаёт, с state, уже содержащим соседние вызовы того же шага.

У event log нет маркера шага (AT-235, пробел 1), поэтому граница берётся из token_usage: api записывает строку на вызов LLM до того, как engine запишет tool.call этого ответа. Каждый tool.call той же сессии и того же актора между двумя последовательными строками — один и тот же шаг. Отсюда три метки:

  • шаг с одним инструментом (один или несколько его вызовов): метка = этот инструмент;
  • разнородный шаг (два разных инструмента): попадание = выбор Jev — один из них, — но ограничение меню одним инструментом отрезало бы остальное;
  • шаг без tool.call после своей строки: модель ответила текстом (или упала). Это единственная метка, которую responder_sem_ferramenta может получить этим методом, — бриф не ожидал ни одной; граница шага даёт семь.

Моменты сравниваются как текст UTC фиксированной ширины с микросекундами: строка расхода и первый tool.call шага иногда попадают в одну и ту же миллисекунду.

Отправляемый state​

Формат AT-235, вырезанный из того, что существовало до шага: agente; pedido — для разговорных агентов последнее chat.message, написанное пользователем; для dev agents и gates задач — заголовок задачи из dev.working; contexto — идентичность агента плюс строка agent_instructions проекта, когда она есть (два слоя системного промпта, а не весь собранный промпт); passos_recentes — последние 6 вызовов этого актора в этой сессии, с аргументами и результатом, обрезанными до 500 символов. Вопрос — choice, чьи criteria — это {name: description} каталога плюс зарезервированный responder_sem_ferramenta.

Запрос идёт в POST https://openrouter.ai/api/alpha/decisions с моделью typesafe/jev-1.13. Исправление к AT-235, измеренное: questions — объект, индексированный по id вопроса, а не список — списочная форма получает 400 expected record, received array. Ответ — answers.<id>.{choice, probabilities, confidence}, usage.{input_tokens, output_tokens, cost}, id (gen-dec-…) и датированный снимок в model (typesafe/jev-1.13-20260917 в каждом ответе этого исполнения).

Чего повтор не видит​

  • Первое сообщение цикла. Агент ToolLoop (dev agents, gates, Anamnese, Infra-Workflows) начинает с пользовательского сообщения, собранного в коде, — задача, история, карта модулей, — которое никогда не доходит до event log. У повтора есть лишь заголовок задачи для dev agents и gates задач и ничего для qa-estrategia, appsec, anamnese и infra-workflows. state продукта нёс бы это сообщение. 0/16 у qa-estrategia (Jev каждый раз отвечал responder_sem_ferramenta) измеряет слепоту повтора так же, как и Jev; эти строки — нижняя граница и ничего не должны решать.
  • Остальной системный промпт. contexto — это идентичность и строка инструкции проекта, а не собранный промпт (бизнес-правила, состояние задачи, файлы).
  • Верна ли метка. Модель, выбравшая инструмент, — не эталон; 157 шагов помечены как подозрительные и сообщаются отдельно («без подозрения»). Согласие ниже на чистых шагах (31%), чем в целом (47%): подозрительные шаги — в основном падающие вызовы terminal от dev agents, которые Jev тоже склонен выбирать, — поэтому плохо размеченные шаги не объясняют несогласия.
  • Эффект. Ограниченное меню меняет то, что модель делает дальше; повтор лишь сравнивает выбор с записанным. Становятся ли ходы короче, быстрее или дешевле — это AT-239.

Две находки вне чисел​

  • Разнородные шаги часты: 36 из 295 (12%). Ограничение меню одним инструментом превращает каждый из них как минимум в два шага — пробел 1 AT-235, теперь подсчитанный.
  • Риск синхронизации каталога из AT-235 (пробел 3) реален, под другим именем: GET /api/v1/models не перечисляет typesafe/jev-1.13, но перечисляет typesafe/jev-router — чат-маршрутизатор с ценой -1. Синхронизация моделей импортировала бы его как чат-модель (неактивную). Записано здесь, не изменено.

Протокол (записан до любого исполнения)​

  • Только то, что продукт может произвести во время выполнения, до шага. Ничто от целевого шага не попадает в state: ни инструмент, который он вызвал, ни аргументы, ни результат, ни текст, который модель написала на том же шаге (Passo.texto читается только из предыдущих шагов; variantes.spec.ts утверждает для каждого варианта, что вызов, аргумент, результат и текст целевого шага отсутствуют). Каждое новое поле имеет источник в engine, процитированный в заголовке scripts/jev/variantes.ts.
  • Классы эквивалентности зафиксированы в scripts/jev/equivalencia.ts до запуска, исходя из семантики инструментов, и сообщаются рядом со строгим правилом (правилом первого раунда, чтобы 47% оставались сопоставимыми). Три накопительных слоя: E1 terminal, чья команда лишь читает/перечисляет/ищет (ls, find, cat, pwd, grep, head, git status/log/diff… — составная команда считается по самому сильному сегменту, исполнение > запись > чтение) ≡ read_file/search_workspace; E2 read_file ≡ search_workspace; E3 terminal, пишущий файл (перенаправление, heredoc, tee, sed -i, cp, mv, touch) ≡ write_file. Асимметричны намеренно: выбор Jev terminal подходит только к вызову terminal, а команда, которая исполняет (npm, node, rm, mkdir, git commit…), не эквивалентна ничему, кроме terminal. Заголовок — полное правило (E1+E2+E3), строгое правило рядом. Ничего не переклассифицировалось после просмотра результата; 3 ошибки, которые классы всё ещё допускают, посчитаны как таковые ниже.
  • Настройка × проверка по исполнению, а не по шагу. Группа — это исполнение ToolLoop (задача dev agent, раунд gate) или, для разговорных агентов, вся сессия агента. Группы упорядочиваются по хешу имени, и каждая идёт в ту половину, где к этому моменту меньше шагов, — детерминированно и слепо к любому результату. 328 пригодных шагов: 167 настройки, 161 проверки (n ниже считает шаги с инструментом: 161 и 160). Варианты итерировались только на настройке; проверка опрашивалась потом, по разу на вариант. Один инцидент, заявленный: после первых исполнений настройки я обнаружил, что skip_proficiency / emit_proficiency Anamnese тоже завершают цикл, и добавил их в список границ исполнения, используемый для сборки state. Использование исправленного списка для разделения также переместило бы 154 из 167 шагов настройки в проверку, поэтому разделение сохраняет список, который был до первого запроса (FERRAMENTAS_DE_FIM_DA_DIVISAO), и только state использует исправленный. Четыре варианта state, зависящие от границы, были опрошены на настройке заново (US$ 0,075, сохранены как .descartado в журнале расходов).

Политики (записаны до запуска, в scripts/jev/menu.ts)​

Политика превращает ответ Jev в ограниченное меню. Решения владельца действуют везде: Jev только ограничивает меню, а когда он отвечает responder_sem_ferramenta, остаётся весь каталог (AT-236); потолок 2 000 мс (во втором раунде его не превысил ни один из 328 запросов). Ничего не переклассифицировалось после просмотра результата; menu.spec.ts фиксирует, что возвращает каждая политика.

политикаменю
P0весь каталог (якорь: 100% покрытия, ничего не ограничивает)
P1два самых вероятных инструмента Jev
P2{выбор Jev, предыдущий инструмент того же исполнения}
P3P2, но если Jev говорит responder_sem_ferramenta (или предыдущего инструмента нет), меню — весь каталог

Правила, общие для всех: упавший ответ (таймаут, ошибка, выбор вне вариантов) оставляет весь каталог; предыдущий инструмент, которого нет в каталоге агента, игнорируется; меню, которое вышло бы пустым, — весь каталог.

Покрытие = доля шагов с инструментом, на которых инструмент, который агент действительно вызвал, находится внутри меню, — строго (то же имя) и по эквивалентности (классы E1–E3 второго раунда, так что меню с read_file покрывает terminal, который лишь читает). Доля ограничения = доля шагов, на которых меню меньше каталога агента: политика, которая почти никогда не ограничивает, тривиально «100%» и бесполезна, поэтому покрытие даётся также среди ограниченных шагов. Потолок: чего не говорит покрытие​

Покрытие — это потолок сквозной точности, а не точность. Меню содержит правильный инструмент; модели агента ещё нужно выбрать его среди вариантов. Метка («инструмент, который вызвала чат-модель») — выбор, сделанный агентом из всего каталога, поэтому полное меню — 100% по построению, а ограниченное может только терять. Что можно сказать без продукта, для P3 на проверке, разделив 160 шагов:

  • 99 (62%, 54–69%): каждый инструмент меню верен, поэтому любой выбор агента верен — пол.
  • 46 «спорных»: ровно один из вариантов верен, и агент решает сам — 28 только предыдущий инструмент, 18 только выбор Jev. Агент, всегда берущий предыдущий инструмент, заканчивает на 127/160 = 79%; всегда берущий выбор Jev — на 117/160 = 73% (снова базовые линии второго раунда); бросающий монетку — на 76%. Агент, выбирающий лучше обоих, а на этом и строится вся ставка, попадает между 79% и потолком 91%.
  • Остальные 15 вне меню: потеряны, что бы ни делал агент.

Итак, сквозной диапазон — от 62% до 91%, и где он окажется, зависит от того, насколько хорошо модель агента читает ситуацию, которую повтор не видит. Ответить на это может только живой тест (AT-239).

Экономия на определениях инструментов​

Каталог содержал описание каждого инструмента (catalogo.json), а теперь ещё и definicoes: размер в байтах полного spec/0 каждого инструмента (имя, описание и схема параметров), сериализованного engine (catalogo.exs, запущен заново; остальная часть файла не изменилась). Токены — это байты, делённые на 4, приближение, которое использует весь повтор. На проверке P3 уходит с 746 до 138 токенов определений на вызов — 608 токенов, на 81% меньше: восемь инструментов dev agent весят 3 068 байт, а меню из двух — около 500. P1 экономит 596, P2 — 644 (средние по шагам половины; половина настройки экономит меньше, потому что Anamnese сохраняет весь каталог).

Сколько это стоит — другой вопрос. Сам вызов Jev читает ~1 870 токенов (US$ 0,0000769) на модели гораздо дешевле модели агента; экономия на определениях — 608 токенов модели агента на вызов. Точка безубыточности — входная цена US$ 0,126 за миллион токенов (0,0000769 / 608): выше неё экономия окупает вызов Jev, без учёта кеша. Кеш — подвох: провайдеры кешируют префикс запроса, определения инструментов идут первыми, а меню, меняющееся от шага к шагу, меняет префикс — экономия может быть возвращена промахами кеша. Это живое измерение, и причина, по которой тест ниже записывает долю кешированных токенов.

  • Выборка: 2 раунда → 10 исполнений на ветвь на модель, всего 40. Порядок ветвей чередуется по задаче и раунду, чтобы ни одна ветвь не получала всегда самую медленную минуту провайдера. Потолок итераций 30 (потолок dev в продукте — 60; здесь он ограничивает расход).
  • На исполнение: шаги; шаги, чьи вызовы пришли текстом и прошли через восстановление; шаги, на которых маршрутизатор был опрошен, применил меньшее меню, оставил весь каталог без падения (нет предыдущего инструмента, или Jev сказал responder_sem_ferramenta) или упал (с причиной и источником RN-059); повторные попытки с полным каталогом; вызовы вне меню шага; настенная задержка всего исполнения (Jev + чат + инструменты) и части LLM; стоимость чата и Jev; как закончилось; вышла ли задача.
  • Правило решения (comparar в resumo.ts), по модели, включено против выключено: качество — доля «задача вышла» у включённого не более чем на 10 пунктов ниже выключенного; стоимость — средняя стоимость на вышедшую задачу (чат + Jev) у включённого не выше выключенного; задержка — медианное исполнение включённого не выше 1,2× выключенного. Оставить включённым по умолчанию, если все три выполняются на каждой модели; выключить, если качество проваливается на каждой модели или ни одна модель не проходит все три; ограничить моделями, которые проходят, — в противном случае. Меньше 10 исполнений на ветвь — это amostra_insuficiente, но никогда не вердикт.

Рекомендация (измерено — решает владелец)​

Ограничить, по правилу, записанному до исполнения: оставлять маршрутизатор включённым там, где у чат-модели нет действующего кеша промпта и она достаточно медленна, чтобы дополнительный последовательный вызов был мал (класс Haiku, US$ 1,00/5,00 за миллион), и выключенным там, где провайдер отдаёт большую часть входа из кеша, а чат быстр (класс DeepSeek). Числа, которые это оправдывают, — строки правила выше: Haiku ×0,62 по стоимости и ×0,95 по задержке без потери качества; DeepSeek ×2,21 по стоимости и ×1,45 по задержке без выигрыша в качестве.

Чего это не покрывает и чего потребовало бы ограничение:

  • Измерены только dev agents (ToolLoop). Прежнее прочтение — никаких свидетельств для семи разговорных агентов — остаётся в силе; ничто здесь на них не распространяется.
  • Разделение — по модели, а переключатель продукта — по workspace (PUT workspaces/:workspaceId/tool-router). Ограничения по модели (или по «действующему кешу») не существует; его создание — новое решение и новое изменение, здесь не сделанное. До тех пор измеренный выбор по workspace таков: включено, если его агенты работают на модели класса Haiku без кеша, выключено, если на модели класса DeepSeek с кешем.
  • Выборка и задачи малы (10 исполнений на ветвь, пять задач от 4 до 16 шагов). Отношения стоимости и задержки достаточно широки, чтобы их читать; разница качества в одно исполнение — нет.
  • Эффект кеша зависит от кеша провайдера, а не только от скорости: workspace на Haiku с включённым кешем промпта, вероятно, сдвинулся бы к линии DeepSeek. Не измерено.

Предварительная рекомендация, которая была здесь до исполнения (ограничить: включено для dev agents, выключено для разговорных агентов), заменена вердиктом правила выше, как и говорил тот абзац.
