RN-040 — agent 的 binding 要求原生 tool calling​

只有当模型具备 supports_tool_calling 时，才允许把模型绑定到agent（scope = 'agent'）。agent 只存在于 ToolLoop 之内，而 ToolLoop 只有在模型懂得请求工具时才能工作；否则失败会在后面表现为"agent 没做完就停了"，这正是 ADR 0020 所禁止的排除法诊断。拒绝是 422，消息指向**"适用于 agent"**过滤器——没有这个指引，规则就成了死胡同。

engine 的 ToolCallRecovery 会挽回模型以散文写出的调用，但它是救援，而不是许可：它依赖模型碰巧写对格式。

只有 agent 做校验。workspace 和 project 是人工聊天的回退，session 是对话——它们都不运行 ToolLoop，锁住它们会禁止产品中只能聊天的模型。context-manager agent 在构造上已被覆盖：它是 agent 范围之内的一个 slug，而不是一个独立的范围。

附加说明——过滤器改为默认勾选，而打开它的是范围。 上面一段说拒绝指向"适用于 agent"过滤器，"否则规则就成了死胡同"——而很长一段时间里它确实是：让选择器在打开时勾选过滤器的 prop 从 Fase 9c 起就存在，却没有任何生产界面传递它。agent 的选择器打开时提供只能聊天的模型，点击它们只是为了被拒绝。写入经校验范围的两个界面改为打开时即过滤——ModelsSection（agent）和 AreaModelsSection（区域）——，而决定谁打开它的尺子不是界面，而是 assertModelFitsBindingScope：api 拒绝的地方，过滤器默认勾选；api 不拒绝的地方，由人来选择。因此会话选择器仍然没有过滤——在那里勾选会隐藏 api 接受的模型。这并不消除 422：过滤器只覆盖三个原因之一，另外两个（RN-043——在 workspace 中被停用、从提供方消失）仍然可能出现，不可用的模型仍会被列出并标记；RN-470 的拒绝结果仍然是说明发生了什么的东西。而且它是复选框的初始状态，不是锁：取消勾选就会重新列出全部。

后果：被过滤器隐藏的现行模型会被说出来。 workspace 和 project 从未要求 tool calling，而解析 agent 或区域 binding 的路由调用 ResolveModelBindingUseCase 时不带 exigeToolCalling——因此这些层级上只能聊天的默认值会被正常解析，成为该行的现行模型。在过滤器勾选时，触发器显示的名称不在打开的列表中，也没有任何选项被选中。选择器现在会点名该模型和原因；它可以点名原因，因为那里只有一个过滤器。当整个列表都为空时，说话的仍然是空列表文本，它已经让人取消勾选——关于同一个复选框的两条提示只是噪音。

事实更正，而不是对上文的更正："Only agent validates" 描述的是 Fase 9a。自 ADR 0064 起， area 进入同一校验——它不是通用回退，区域模型唯一的消费者是该区域的 agent（RN-102）——，这就是打开过滤器的界面有两个的原因。

RN-041 — 提供方未给出的 token 计数被标记为估算​

当提供方的响应不含 usage 时，OpenAI 兼容基类用 tokenizer 在本地计数，并以 estimated: true 发出 chunk。这个数字仍可用于计费，但这个标记保留了**"提供方说是零"与"提供方什么也没说"**之间的区别——正是它让 UI 能够限定成本，而不是显示一个来历不明的值。

另外两个提供方有分歧，而分歧被规范化，而不是被隐藏：Ollama 在没有 done 行时干脆不发出 usage；Anthropic 不能省略计数，因为在其协议中 usage 在 message_start 里是必需的。三种响应见 docs/reference/llm-providers.md。

  • 位置： apps/api/src/infrastructure/llm/openai-compatible-provider.ts:167
  • 测试： test/contract/llm-provider.contract.ts（场景 sem_usage，针对三个提供方运行）
  • 来源： ADR 0041

RN-042 — 计量记录实际服务调用的是谁，而不只是调用从哪里进入​

当调用经过一个会告知真实提供方的 hub 时，token_usage 除了入口提供方外，还在 upstream_provider 中记录该提供方。没有 hub——或 hub 没有告知——时，该字段是**null**，绝不是空字符串：按提供方统计成本的查询需要区分"没有经过 hub"和"经过了 hub 但 hub 没说"。

在指标中，没有 hub 时 upstream_provider 标签重复提供方本身，因此 sum by (upstream_provider) 仍然汇总全部成本。

  • 测试： test/application/use-cases/llm/record-llm-usage.use-case.spec.ts

RN-681 — 与现有相似的故事和规则通过 embedding 产生警告，绝不拒绝；检查的花费是计量中的独立一行​

在写入一个故事（create_story）或一条业务规则（business_rule 的 emit_artifact）之后，api 将其标题与项目中同类现有条目的标题比较，使用 RAG embedding 模型向量之间的余弦，当最接近的达到阈值时发出警告。

  1. 警告，绝不拒绝。 检查运行时条目已经存在。警告在工具结果中返回给 agent——句子点名相似条目、id 和数值——并以 backlog.semantic_duplicate_warned 留在日志中。精确重复仍会在此之前被 RN-080 和 RN-081 拒绝，因此规范化后相同的标题不参与比较。
  2. 阈值是 0.80，是起点，未经校准（ADR 0198，与 ADR 0080 的权重一样）：在规则诞生的环境中，无法记录发现 R 那一对以及非重复对的真实向量。一旦 vetores.json 被记录，证明会自行运行；在那之前它被跳过并给出警告。
  3. 没有 embedding 提供方时，检查被跳过并说明——能力缺失、daemon 不在、超时：backlog.semantic_duplicate_check_skipped，原因写入日志和给 agent 的句子。绝不会让发出失败。
  4. 花费作为独立一行进入计量：执行者 system/duplicata-semantica，RAG 的提供方和模型，输出为零，模型在目录中时使用目录价格。这是对 ADR 0075 划分的唯一例外——RAG 的索引和搜索仍在其外——，之所以成立，是因为发出发生在会话之内。
  5. 上限： 最近的 100 个现有条目（截断时结果会说明是多少中的多少）以及整个检查 10 s 的挂钟时间。

RN-666 — 计量记录输入中有多少来自缓存、输出中有多少是推理​

token_usage 的每一行记录提供方在 OpenAI 方言的 usage 中给出的两个部分：cached_input_tokens （prompt_tokens_details.cached_tokens——input_tokens 中有多少由缓存提供，以价格的一小部分计费）和 reasoning_tokens （completion_tokens_details.reasoning_tokens——output_tokens 中有多少是推理）。

  1. 是部分，绝不是相加。 input_tokens/output_tokens 仍然是提供方给出的总数，已经包含这些部分；不往它们上面加任何东西，也不据此重新计算任何成本——成本的数字是 RN-665 的那个。
  2. "没说"不是零。 null = 提供方未告知；0 = 告知没有。不是非负整数的值视为"没说"。
  3. 测量会说明缓存占多少。 medir-execucao.ts 开始按 agent 显示读取的缓存和推理及其占总数的百分比，只针对告知了的调用（不是全部时说明有多少次），没有任何调用告知时显示"未测量"——另外还显示有多少次调用的成本是真实成本。
  4. 对方言的所有提供方都读取，因为这两个字段是 OpenAI 自己的；不发送它们的提供方保持 null。Anthropic 在其协议中告知缓存（cache_read_input_tokens），这里不读取——保持 null，已声明；Ollama 不告知。

RN-665 — 提供方返回的真实成本就是计量的数字；目录价格用在没有真实成本的地方​

所有者的决定（9月30日）：真实成本成为数字。当 LLM 调用的响应说明了提供方收取多少——在 OpenRouter 中是流最后一帧中的 usage.cost——，这个值就是该行的 token_usage.cost_micros、回合返回给 engine 的值（循环将其累加到本地预算）、增加项目/会话/区域预算的值，以及支出报告汇总的值。没有它时，由目录的冻结价格产生数字，与 ADR 0042 中一样。

  1. 一条规则，三条路径。 RunLlmTurnUseCase、StreamLlmTurnUseCase 和 SendChatMessageUseCase 都经过同一个 custoDaChamada；没有第二把尺子。
  2. 隐含价格，带标记。 有真实成本时，两个价格列都记录 custo ÷ tokens（同一个值：提供方返回一个成本）以及 price_implicit = true——这保持了 tokens × preço = custo （RN-044），而不假装是价目表价格。没有真实成本时， price_implicit = false，各列是目录的值。
  3. 目录价格放在旁边。 catalog_cost_micros 记录按目录价格本应收取的金额，只在数字为真实成本的行中（其他行为 null）——这是逐行的估算与账单之间的差距。
  4. estimated 仍然只说 TOKEN（RN-041）。带真实成本的行 estimated = false，因为成本只会随提供方的 usage 一起到达；把成本标记为真实的是 price_implicit。
  5. 响应关于自身说了什么，就记录什么。 resolved_model_name（帧中的 model——解析后的别名）和 generation_id（id，在 OpenRouter 中是 gen-…），对方言的所有提供方都适用。model_name 仍然是目录的那个，即报告的维度。
  6. 只有经过证明的才读取成本。 extrairCustoReal 钩子只存在于 OpenRouter；没有它的提供方会忽略存在的 usage.cost。不是有限非负数的成本视为"没说"（真正的零是真实成本），而在 is_byok: true 时不读取成本：那是 hub 的费用，推理在别处计费——该行回落到目录价格。

RN-679 — 策展拒绝 OpenRouter 的自由路由别名​

所有者的决定（10月1日）：~ 别名不进入策展——只接受上游固定的模型。OpenRouter 的自由路由别名（以 ~ 开头的 id，如 ~deepseek/deepseek-flash-latest）"总是重定向到该家族最新的那个"：目录发布的是橱窗价格（在 9月29日的真实使用中，是该家族最便宜端点的价格），端点列表为空，收费的是实际服务的上游。没有一个上游能让 ADR 0042 的冻结价格有任何意义。替代方案——按上游定价——被否决。

  1. 尺子属于提供方。 ehAliasDeRoteamentoLivre 是 provider = 'openrouter' 且名称以 ~ 开头；其他提供方中相同的前缀不是别名，不会拒绝。
  2. 激活会拒绝，带代码。 POST .../models/activate 带 isActive: true 且批次中有任何别名时，返回 422，带 code: "alias_de_roteamento_livre"、被拒绝的 modelIds 以及点名它们的句子。整个批次被拒绝，与不存在 id 的 404 一样 （RN-043）：同一批次中上游固定的模型也不会被打开。目录界面在一个有专门标题的 toast 中显示 api 的句子，并按 code 匹配，绝不按文本。
  3. 同步不过滤别名。 它继续留在目录中——从那里消失会让同步把已策展的东西标记为 unavailable，级联会悄无声息地跳过它的 binding。策展的读取会标记它： freeRoutingAlias，在读取时由提供方和名称推导，从不写入。该行在有人尝试激活之前，以文字显示徽章和原因。
  4. 已策展的继续工作。 这是可测量的（OpenRouter 行中带 ~ 的名称），选择的出路是最不令人意外的：规则之前已激活的别名保持激活——它的 binding 继续解析，选择器继续显示——，在目录中带标记出现，并且可以被关闭。关闭后不会回来。什么都不删除，也不重写任何 binding。对仍处于激活状态的别名新建 binding 在这里不会被拒绝：规则属于策展，binding 遵循 RN-043。

RN-583 — hub 的路由标准属于 binding，随之传输，并在计量中冻结​

模型 binding 可以保存一个路由标准—— routing_preference：price、throughput 或 latency——告诉 HUB 如何选择服务该模型的上游。可为空：null 是一贯的行为，不向线路发送任何东西，由 hub 自行决定。

  1. 随胜出的 binding 传输，从不独自级联。 级联仍然是 binding 的级联：胜出的层级带来模型和它的标准。级联跳过的层级（模型不可用、没有 tool calling）会把标准一起带走——只让标准存活会产生没有人选择过的组合。

  3. 冻结发送到线路上的东西。 token_usage.routing_preference 按调用记录，与 RN-042 的 upstream_provider 并列：发送的标准，当 binding 没有标准或提供方不声明该能力时为 null（没有发送的东西不是任何东西的来源）。与冻结价格（ADR 0042）同一把尺子。

RN-043 — 新发现的模型以停用状态进入；消失的模型被标记，从不删除​

目录同步有三种结果，没有一种是破坏性的：

  1. 新模型进入时在任何 workspace 中都没有策展行，而没有行就是停用状态。一个提供方的目录有数百行——把它们全部作为激活状态倒进来会让选择变得不可能，并在没有任何人决定的情况下打开一个昂贵的模型。激活是 owner 的策展，只在他的 workspace 中有效（RN-052）。
  2. 从远程目录中消失的模型获得 availability = 'unavailable'，并留在表中： model_bindings 和 token_usage 指向这一行，删除它会把成本历史一起带走。
  3. 回来的模型恢复为 available，策展保持不变——owner 的选择能挺过提供方的暂时缺席。

  • 失败的提供方不会让任何东西变得不可用：401 是"我不知道那里有什么"，而不是"那里什么都没有"。该提供方被跳过，报告中带有失败的来源（infra | modelo）——绝不是排除法诊断。

RN-189 — embedding 为每个输入返回一个向量，或者一个错误​

RN-045 — 被采纳的仓库只能由已批准的计划修改​

采纳现有仓库只诊断不行动。采纳校验访问（getRepo），写入项目的行，并产生一个计划：bootstrap 将要做的事情的序列化列表，通过调用每个步骤的 check() 获得——与自 RN-029 起提供幂等性的是同一个——而从不执行相应的变更。

RN-047 — dev agent 的熔断器：连续 N 次阻塞让它停下，而不在循环中烧掉预算​

模式改变触发器，而不是标准。 两条路径都经过 assertPromotable——就绪性（RF/DoD/DoR/规则）以及对照现行 module_map 解析的模块——这正是 story-promotion.spec.ts 中的对称性测试所锁定的：对于每个 story，isPromotable 都与 assertPromotable 抛出的结果一致。在这个阶段之前，校验是重复且不对称的（创建调用 canBecomeReady，转换调用 assertReady + assertModulesResolved）：通往同一状态的两扇门，锁不一样。让触发器可配置，首先需要把它们统一起来，否则"通过 UI 晋升"和"在创建时晋升"会是同名的不同规则。

不完整的 story 永远不会被提议。只有当 story 已经能通过校验时，proposed_ready 才会打开——提议领域会拒绝的东西，就是把 PO 的工作伪装成决定推给用户。

拒绝会把 story 退还给 PO：写入 returned_reason/returned_at，关闭 proposed_ready，发出 backlog.story_promotion_returned，并把原因作为置顶消息注入 PO 的会话，措辞与退还给 dev 的 gate 的优先级措辞相同（ADR 0020 的教训）。拒绝在与 engine 通信之前被记录，engine 失败也不会撤销它——这与 RN-047 中重新武装的顺序相反，理由是：那里事件断言的是关于 engine 的事情，这里断言的是关于用户的事情，无论是否有值班的 PO 在听，它都是真的。

批量晋升不是全有或全无：每个 story 是它自己的事务，在提议和决定之间失去就绪性的 story 会带着原因以 failed 返回，而不会拖垮用户刚刚审阅过的其他 story。

backlog.story_transitioned 事件记录真实的执行者——手动晋升时是 user，自动晋升时是 agent/po。事件日志是不可变的，也是审计所读取的：在用户的决定中记录 PO，恰恰会抹去规则要交还的那个人工环节。

迁移 0033 做的是有针对性的回填，而不是盲目的：列以 manual 诞生，所有已存在的项目都被移到 auto。新的默认值适用于之后来的项目；进行中的项目不能因为一次部署而停止产出。

RN-050 — 没有打开的 PR，就不打开任何 gate​

dev agent 提议 commit、push 和 PR，并读取每一项的结果。只有三项都执行了，它才打开 gate。如果有一项停在 pending——agent 的自主权处于 require_approval——它进入 awaiting_approval，持有 worktree，不打开任何 gate。

没有这一点，gate 无论如何都会打开，而损害是无声的：QA 扫描的是worktree，而不是 PR；找到文件，批准；SecOps 批准；任务以完成告终——一行都没有提交，也没有任何 PR。直到之后批准 commit 时，用户才会看到动作失败（诊断为空，因为在已删除的目录中 System.cmd 返回 {"", 2}）。

这条规则也顺带消除了 D5（待批准时 worktree 被回收）：worktree 只在 gate_resolved 时释放，gate 只在 PR 之后打开，PR 只在 commit 和 push 之后打开。

RN-051 — 手工输入的价格胜过提供方的目录​

manual_pricing = true 的 models 行有一个数字，是有人在阅读提供方文档之后输入的。目录同步不会碰它——即使远程目录带有自己的价格也一样。schema 一直是这么说的（"同步价格的一方不能在没有显式决定的情况下覆盖此处标记的行"），而代码没有这样做：只要远程带有价格，它总是胜出，下一次同步会撤销那个修正了错误数字的人所做的更正。

RN-052 — 模型策展只在作出决定的 workspace 中有效​

在选择器中打开或关闭一个模型，是那个 workspace 的决定，不会波及邻居。目录本身仍然是全局的——名称、价格、窗口和能力是提供方的事实，对所有人都一样，按 workspace 复制它们会对同一个模型产生 N 个真相，还会把 token_usage.model_id 劈成两半。

在此之前，models.is_active 是整个安装的一列：点击"激活"的人替所有 workspace 作了决定，界面对此没有任何提示。实际效果是一个 workspace 在另一个 workspace 的选择器中打开了昂贵的模型——花费出现在什么都没决定的人的预算中。

  1. 没有行就是停用状态。 没有单独的"从未决定"状态；同步发现的模型没有行，不出现在选择器中（RN-043）。

RN-068 — dev agent 无需请求许可即可读取 worktree​

RN-143 — 只读的 git 子命令只有在被使读取无歧义的标志锚定时才被允许，绝不凭单独的动词​

查询一次真实执行的数据库时发现，dev agent 在探索性子命令上烧掉了几十次人工审批——git branch -a、git remote -v、git worktree list、git show origin/dev --stat、git log --all --oneline --graph、git for-each-ref、git ls-tree -r origin/dev --name-only、git config user.name——没有一个被 RN-068 覆盖，后者只允许 git status/diff/log（不带额外标志）。由于按 token 前缀匹配要求复合命令的每个段都在 allow 中，只要其中出现一个这样的子命令，一长串探索命令就整体落入 require_approval。

DEV_TERMINAL_ALLOW_PATTERNS 新增了 git branch -a/-r/-v/--list/--show-current、git remote -v/git remote show、git worktree list、git show、git for-each-ref、git ls-tree、git rev-parse 和 git config --get。git log 不需要新模式：匹配本来就是按 token 前缀（允许额外的尾随 token），所以 Terminal(git log) 已经覆盖了 git log --all --graph --oneline --decorate。

这里的谨慎与 RN-068 对 ls/lsof 所展示的相同，只是应用于那些有一个接受同样截断形式的变更型兄弟的动词。 Terminal(git branch) 会匹配 git branch -D nome（删除），也会匹配 git branch nome-nova（创建）或单独的 git branch——模式看不到它所核对的前缀之后是什么。这就是为什么四个具有变更形式的动词（branch、remote、worktree、config）没有一个是凭单独的动词被接纳的；每一个都由使读取无歧义的标志锚定，无论后面跟什么：

  • git branch——锚定在 -a/-r/-v/--list/--show-current，绝不在单独的动词上；-D/-d/-m/-M（删除/重命名）和单独的分支名（创建）被排除在外。

  • git remote——锚定在 -v 和 show（其后只接受远程名，总是读取）；add/remove/set-url 被排除在外。

  • git worktree——锚定在 list；add/remove/prune 被排除在外。

  • git config——只接纳了 --get，因为它是 git 本身保证无论后面跟什么都是读取的唯一标志（一个键，或一个键 + 值模式）。不带 --get 的 git config user.name/git config user.email 被刻意排除：键之后的第二个 token（git config user.name "novo valor"）是写入，而前缀匹配在不发明新的参数计数解析器的情况下，无法区分"没有多余 token"和"多一个 token"——这与已经阻止单独 git branch 的限制相同。--global/--system 从未被锚定。

RN-070 — 每个声明的 gate 都指向证明它的证据​

RN-072 — 没有显式选择时，模型是 Criativo agent 的模型​

Criativo agent 始终是项目的入口：第一次对话就是与它进行的，它的 binding 代表"这个项目用来思考的模型"。

继承只填补空缺，从不覆盖：会话、agent 或项目的 binding 是某个人的显式选择，继续胜出。这就是为什么它是级联之后的一步，而不是级联之内的新范围——它不争夺优先级。继承的模型经过同样的过滤：从目录中消失或没有 tool calling 意味着不被继承，理由与级联跳过它们相同（RN-043）。

RN-073 — 待定的审批暂停循环，而不是烧掉它​

当流水线工具返回 pending 时，ToolLoop 停止，dev agent 进入 :awaiting_approval，持有任务、worktree 和循环的历史。用户的决定发出 task.action_settled，唤醒它：真实结果占据原本会是 "pending" 一词的位置，循环从中断处继续。

测试锁定的两个性质：

  • 等待期间什么都不记录。 工具消息的位置保持为空。在那里写 "pending" 会告诉模型这就是命令的回答——而这正是缺陷所在。
  • 拒绝也是一个回答。 原因占据结果的位置，agent 得知那条路已经关闭，而不是永远等待没有人会批准的东西。这与 opened: false 的 pr_settled（RN-047）是同一原则，低一个层级。
  • wake 必须到达。 task.action_settled 诞生于 task 聚合，而不是表名所暗示的 proposed_action：engine 的 drain 读取一个封闭的聚合列表（session 和 task）。在这个列表之外发出时，事件被成功写入，processed_at 保持为空，甚至不会被读取——没有 job，没有错误，没有日志，agent 永远等待。契约跨越两种语言，这就是它在两侧都被锁定的原因。

如果 engine 在等待期间重启，这条规则对该任务不再适用：暂停的循环只存在于内存中，因此任务以来源 infra 被阻塞地回到队列，之后作出的决定无处可用。带诊断地阻塞是刻意的——另一种选择是永恒而无声的等待，而这正是这条规则要终结的。

这修复的是：pending 过去作为工具的结果返回，循环继续前进。模型把它读作命令的回答，什么也没学到，尝试别的东西——每次尝试都烧掉一次迭代，直到 toolloop.limit_reached {iteration: 8, max_iterations: 8}，任务因"达到迭代上限"而被阻塞，一行都没写。授予的批准在循环耗尽之后才到达，毫无用处。

终端允许列表（RN-068）仍然有效，但不再是唯一的防线：它是预期命令的列表，而模型会发明命令。

  • 测试： apps/engine/test/engine/dev/dev_agent_awaiting_approval_test.exs （pending action STOPS the agent；approved: resumes the loop with the REAL output；restart during the wait BLOCKS the task）和 apps/engine/test/engine/dev/wake_do_outbox_ao_agente_test.exs，它走完整条链——outbox、drain、队列和进程——因为逐环节的测试在投递损坏时全都是绿的；聚合在 api 一侧锁定于 apps/api/test/application/use-cases/actions/approve-deny-action.use-case.spec.ts

RN-074 — 终端输出有字节上限​

命令的输出在成为工具结果之前被截断到 TERMINAL_OUTPUT_MAX_BYTES（默认 32 KiB），截断会留下一个标记，说明两个大小以及该怎么做：

[saída truncada: 32768 de 1048576 bytes. Refine o comando (head, grep,
-maxdepth) para ver o que falta.]

测试锁定的三个性质：

  • 上限是 >，不是 >=。 恰好等于限制的输出原样通过——标记它会让模型去细化一个已经给出全部内容的命令。
  • 截断不会切开多字节字符。 binary_part/3 按字节截断；落在一个 é 中间会产生无效二进制，在结果到达模型之前就破坏 JSON 序列化。
  • raw_bytes 仍然是产生的真实大小，而不是截断后的。这是测量，在这里撒谎恰恰会隐藏促成这个上限的行为。想检测截断的人比较 byte_size(stdout) 与 raw_bytes。

这修复的是：每个命令的输出都留在循环的历史中，并在之后的每一个回合中传输。没有上限时，一个在大目录树上的 find 就足够了——hello-limpo 的执行在第 18 回合以 {413, "request entity too large"} 死掉，一行都没写。溢出的是请求的字节，而不是上下文窗口：最大的成功调用有 28,993 个输入 token。

标记是写给模型的，而不是给人的——不说该怎么做，它往往会重复同一个命令。

  • 测试： apps/engine/test/engine/actions/terminal_executor_test.exs （describe teto de bytes da saída）

RN-075 — 终端命令按其触及之处评估，而不只是按动词​

项目文件夹（<PROJECT_WORKSPACES_ROOT>/<workspace_dir_name>——在 RN-109 之前的项目中是纯 UUID，在新项目中是 <slug>-<id 的 8 个字符>）是范围。 触及其外任何路径的 terminal 命令永远不会被自动批准，无论动词是否在 allow 中。在其内部，cd 不再需要许可——它是范围的声明，而不是动词。

测试锁定的四个性质：

  • **收紧：**放开的 Terminal(cat) 不再自动执行 cat /workspace/apps/engine/.../git_executor.ex。这是发现 U：匹配按动词进行，因此 agent 读取执行它的平台的代码，并触及其他项目的 worktree。
  • 放松：cd <内部> && cat README.md 变为 auto_approve。这是阶梯中代价最高的缺陷——dev agent 总是发出 cd <路径> && <动词>，cd 不在任何 allow 中，而复合命令要求所有段都匹配。
  • **允许但不豁免：**在范围之内，allow 之外的动词仍然需要请求。身处项目文件夹并不会让 curl … | sh 变得安全。
  • **范围之外是 require_approval，绝不是 deny：**agent 可能有查看外部的正当理由，决定仍属于用户。

deny 仍然最先胜出，两个上限（RN-006、 RN-007）保持不动。没有向 decide() 提供根目录时，裁决与这条规则之前相同——没有任何调用者因省略而改变行为。

规范化是词法的，而不是 realpath：<raiz>/../.. 会被解析并拒绝，但内部指向外部的符号链接不会被检测到。decide() 按契约是纯函数，解析符号链接需要在领域中做 IO。范围是策略；隔离是另一个问题，在 ADR 中声明为未解决。

刻意不对输入使用正则。 去掉根目录末尾的斜杠原来是 .replace(/\/+$/, '')，CodeQL 指出了多项式 ReDoS （js/polynomial-redos，HIGH）：该模式迫使引擎尝试每个起始位置并扫描到末尾，退化为 O(n²)。现在是 O(n) 扫描，包括在退化情形下也等价——根目录 / 在两者中都变为空字符串，正是这一点让 startsWith('/') 对所有绝对路径成立。谁要是把它"简化"回正则，就会重新打开这条警报。

  • 位置： apps/api/src/domain/actions/path-scope.ts, domain/actions/decide.ts（范围上限和范围内的 cd）， 根目录推导于 infrastructure/filesystem/project-workspaces-root.ts
  • 测试： apps/api/test/domain/actions/path-scope.spec.ts 和 apps/api/test/domain/actions/decide.spec.ts （describe decide — escopo de caminho）
  • 来源： ADR 0055， 发现 U，backlog 的 Fase F

RN-092 — projectId 是路径段，范围永远不离开根目录​

projectScopeRoot() 拒绝不是简单路径段（^[A-Za-z0-9_-]{1,64}$）的 projectId，抛出异常而不是拼出路径。

原因是 id 来自没有校验管道的 @Param('projectId')，而 Express 在交付之前就解码了段的百分号编码：..%2F..%2Fetc 到达时是 ../../etc，join 会毫无怨言地解析到根目录之外。这个函数的两个消费者都会受害，而第二个是严重的：

  • permissions.json 会在任意路径上被读取和写入；
  • RN-075 的范围授权在该文件夹下执行 terminal 命令。逃出根目录的范围，就是审批策略指向了错误的地方——这是安全失败，而不是找不到文件。

检查刻意比 UUID 更宽（接受字母、数字、连字符和下划线），以免绑定 id 的格式，同时又窄到结果永远无法逃出。它位于根目录被推导的地方，而不是每个调用者中，理由与这个函数存在的理由相同：两种推导必须一致，重复的检查就是有一天会分歧的检查。

正常路径不变——每个真实 id 都是来自数据库的 UUID。

  • 测试： apps/api/test/infrastructure/filesystem/project-workspaces-root.spec.ts

RN-095 — 仓库读取被限制在项目内并有上限​

代码读取接口面（GET /projects/:projectId/code/{tree,file,search} 以及 PR 的 diff）有两项保证，而两项属于同一类型：产品拒绝做客户端请求的事。

约束。 来自客户端的每个文件路径都经过 caminhoDeRepositorioContido()，它把请求锚定在项目文件夹上，拒绝离开它的东西——../、绝对路径或 NUL 字节。它是唯一的一个函数，与 RN-092 的 projectScopeRoot 在同一文件中，复用终端范围的原语（normalizarCaminho/dentroDoEscopo）。没有任何路由自行校验路径，而这正是规则所断言的：同一约束的四个实现就是四次分歧的机会，CLAUDE.md 已经记录了保持中央检查、并在 CodeQL 面板上付出代价的决定（它看不到位于另一个函数中的屏障）。

它返回规范化后的路径，调用者使用返回的东西。返回原始路径会允许检查 b 却把 a/../b 发给提供方——这是约束存在却不生效的最常见形式。

向量不是"读错文件"。在 github/gitlab 中，路径会成为提供方 API 的 URL 段，因此一个 ../ 会换掉端点，而手里拿着 workspace owner 的凭据（RN-058/RN-082）。在 local 中，它成为 git show <ref>:<path> 的右侧。ref 在同一位置、出于同一理由被检查，其中的 .. 被拒绝，因为对 git 而言 dev..main 是提交区间，而不是修订。

上限。 目录树和 diff 已经由契约截断 （GIT_TREE_ENTRY_LIMIT、GIT_DIFF_FILE_LIMIT，FASE 26a）。搜索不是：它不是契约的操作——它组合在 listTree 和 getFileContent 之上，是唯一一个成本随仓库大小而不是请求大小增长的读取。三个预算让它停下（遍历的目录、打开的文件、返回的匹配），一个短 TTL 缓存避免重复相同的调用，truncated 说明发生了截断。没有它们，viewer 可以随意消耗 owner 的凭据和速率限制——与仪表板每分钟 3,824 次请求（RN-090）同一族的缺陷。

截断总是可见的：每个可能被截断的响应都在一个字段中说明这一点。搜索中还会带上 filesScanned，因为没人看得见的成本就是没人修正的成本。

读取不会变成 proposed_action。 读取不是外部效果，把它变成审批动作会让队列充满噪音，直到再也没有人去读真正的那些。阶段的冻结是这件事的另一面：标签页只读，而写入——当它到来时——以 proposed_action 的形式诞生。

RN-127 — 代码标签页的 ref/path 拒绝以数组形式到达，而不只是拒绝范围之外的路径​

@Query('ref') ref?: string 和 @Query('path') path?: string （code.controller.ts）提取原始值，中间没有 DTO/class-validator，全局的 ValidationPipe（main.ts）也帮不上忙：按 Nest 的设计，它跳过原生基本类型（String），因此在 ref/path 作为方法参数到达之前，没有任何东西拦截它们。Express 把 ?ref=a&ref=b 作为数组而不是字符串交付——TypeScript 的 string 注解只存在于编译期。

RN-093 — 在生产环境中，api 不会以 OAuth state 的示例密钥启动​

当 NODE_ENV === 'production' 且 GIT_OAUTH_STATE_SECRET 缺失、等于仓库的示例字面量或少于 16 个字符时，resolveOauthStateSecret() 使启动失败。在生产环境之外，开发默认值继续有效。

这个密钥签署 git OAuth 的 state，而 state 是唯一阻止回调 GET /git/oauth/:provider/callback——出于必要而公开的路由——被伪造的东西。密钥一旦为人所知，任何人都能为任意的 {projectId, userId, provider} 签发 state，让回调把从提供方获得的 git token 写入该 payload 所指的项目。

为什么拒绝字面量，而不只是空值。 默认值位于一个开源仓库的 .env.example 中——它是已发布的秘密，而不是弱秘密。而 docker-compose.prod.yml 把它作为回退值提供，因此在真实的出错路径上变量是已定义的：一个"非空"检查会对整个缺陷视而不见。

解析位于唯一的函数中，而不是每个调用者中，理由与 RN-092 相同——原来是同一字面量的两份副本，而副本会分歧。在这里分歧的话，回调会拒绝所有合法的 state。

RN-114 — GIT_OAUTH_STATE_SECRET 的四个姊妹秘密在生产环境中同样不会以示例值启动​

ADR 0059 为 GIT_OAUTH_STATE_SECRET 关闭了这个模式，并明确保留了同一失败模式适用于四个姊妹秘密这一开放问题，它们在 docker-compose.prod.yml 中都有开发默认值：AUTH_JWT_SECRET、 BRABO_SERVICE_TOKEN、CREDENTIALS_MASTER_KEY 和 SECRET_KEY_BASE。这条 RN 关闭了这四个，完全复制同一条规则——这不是新的决定，而是把同一决定应用于姊妹们。

  • AUTH_JWT_SECRET——推导出签署 access token 的 Ed25519 密钥对。使用公开默认值时，任何人都能伪造有效的 access token。

RN-076 — git 凭据从不写入文件​

engine 在远程仓库上工作，方式是向 api 请求工作远程（GET /internal/projects/:projectId/git-remote），后者返回干净的来源，并单独返回 owner 的 token。token 通过子进程的环境进入 git 调用，别无他处：

  • 不在 origin 中——写入 .git/config 的是干净的 URL；
  • 不在 argv 中——ps 会显示任何进程的命令行；
  • 不在文件中——既没有持久化的 helper，也没有 ~/.git-credentials。

凭据 helper 通过 -c 传入，只对那个进程有效，并且位于一个空的 credential.helper= 之后：helper 是累加的，第一个响应的胜出，因此不先清零的话，主机上的 helper 会抢先响应。

为什么这是规则而不是偏好。 把 https://x-access-token:TOKEN@github.com/… 写进 origin——几乎每个教程都这么教——会以明文把凭据写进项目文件夹内部，正是 RN-075 给予 dev agent 自动批准读取权限的地方。一个 cat .git/config 就会在不经任何审批的情况下返回 token，而它会在循环的历史中传到 LLM 提供方。路径范围防止 agent 读取项目之外的东西；它无法防止产品自己放在内部的秘密。

凭据是 workspace owner 的，通过 RN-058 的同一个解析器——两条"凭据属于谁"的规则会分歧。local 提供方没有 token，也不询问 api：它直接从数据库解析，这是 pnpm dev 和整个测试套件所走的路径。

RN-077 — 失败的来源总是四者之一​

RN-078 — 保护分支的失败可以被确认，且只有它可以​

在 GitHub 免费计划的私有仓库中，protect_branches 会失败——向导在开始之前就提醒这一点。用户可以确认这个失败并继续；bootstrap 结束，项目变得可以访问。

这解锁的东西比看起来更大。 失败后唯一提供的按钮是"重试"，而它总是因为同样的原因失败。而 provision_failed 让仪表板把点击项目重定向回部署页面——项目永远无法访问，困在一个不可能成功的步骤中。

只有保护可以被确认。 它是最后一步，也是唯一一个失败后仍留下可用仓库的步骤：仓库存在，文件已提交，分支已创建。创建仓库或提交失败是另一回事——在那里"继续"会产生一个没有地方工作的项目，按钮会成为第一个谎言之上的第二个谎言。拒绝会说明这一点，而不只是否定。

RN-079 — Psicólogo 不分析没有可分析事件的会话​

在花费一个模型回合之前，分析会先问有没有可分析的东西。没有的话，它不运行，结果成为 psychologist.analysis_skipped。

"可分析"排除两样东西，原因不同：

  • 分析者自身的痕迹。 Psicólogo 把它的回合写进它所分析的会话日志（agent.response、tool.call、tool.result、假设）。把这些计算在内，会让一个空会话从第一次分析起就显得充实，每次重试都会让它更满——标准将再也不会失败。Anamnese 同理；
  • bootstrap.*，即独自运行的仓库部署：九个机器步骤对这个人什么也说明不了。

其他一切都算，包括 proposed_action.*——用户不写任何消息地批准和拒绝就是行为，这是 Anamnese 已经学到的教训（RN-063）。

这是两个计数，它们不能互相替代。 原始计数衡量工作量（要读多少日志，进而用哪个分诊层级，轻还是重）；可分析计数决定是否有工作。混淆它们就是缺陷：一个只有 bootstrap 的会话被当作"20 个事件"，实际上一个都没有，于是获得了分析，而模型——没有任何东西可以引用——会编造不存在的 seq，直到证据校验拒绝它、它放弃为止，而预算已经花掉了。

跳过同样适用于手动重新处理。 重新处理不会制造材料：点击的人会在日志中收到原因，而不是关于一份不存在的日志的编造假设。

跳过会成为事件，这与 Anamnese 的跳过不同，后者只是日志——那个每 15 分钟运行一次，会变成噪音；这个每次会话关闭运行一次，而一个没有任何叙述的缺席分析是无法诊断的。

RN-081 — 重复的故事：相同标题拒绝，相同理由警告​

对两个不同的问题给出两种不同的回应：

  • 项目中相同的标题是错误，而不是选择：故事被拒绝，什么都不创建；
  • 相同的理由——故事引用的所有业务规则都已被另一个故事覆盖——是可疑，而不是错误。故事会被创建，并发出 backlog.story_overlap_warned。同一规则的第二种切分可能是正当的，因此由用户来判断；产品只是拒绝让它不被注意地通过。

是包含，不是交集。 两个故事共享一条规则是正常的，对此发出警告会变成没人读的噪音。只有当新故事没有增加任何覆盖时，信号才存在。不引用任何规则的故事不产生警告：把空集当作一切的子集会指控所有故事。

界限与 RN-080 相同，而发现中的那一对恰好越过了它： "Endpoint público de saudação determinística" 和 "Endpoint público GET /hello que responde saudação imediata" 以不同的标题和理由覆盖同一个端点——没有任何机械的东西把它们联系起来，它们继续通过。有测试断言这一点，让界限可见而不是隐含。 自 RN-681 起，这一对会通过 embedding 被警告——仍然通过，断言这个机制界限的测试依然有效。

RN-082 — 动作的 git 凭据是 workspace OWNER 的​

RN-083 — lead 决定并行度；超过上限时由你授权​

启动多少个 agent 不再是代码中的一个数字：评估的是区域的 lead。但它的决定在花费上并不至高无上——在 agent_areas.max_parallel（默认 2）之内它直接启动并继续；超过时就成为 parallelize 类型的 proposed_action，经过与所有外部效果动作相同的流水线。

上限属于会话，而不是模块。 这是规则中唯一不显而易见的部分，也是粗心的重构会撤销的部分：按模块计数会允许 N 个模块 × 2 个 agent 而不需要任何授权——换了个名字的旧漏洞。有测试正好断言这一点。

零或负数的上限是无效配置，而不是"无限制"。 把它当作无限，会把一个输入错误变成无限制的花费，这与流水线存在的目的正相反。

提出请求的是 lead；作出决定的是你。 proposed_action 以 lead 为执行者诞生，决定以你的名字留在事件日志中——正是这一区分让历史之后可以重建（ADR 0048）。

原因在不可变的 payload 中传输，带三个数字（现有多少、请求多少、上限是多少）：六个月后阅读的人需要在不重建会话状态的情况下理解授权了什么。

AcceptParallelizationUseCase 不变：它仍然是执行者，无论是在直接路径上，还是在动作被批准时。从内部吸收它而不是重写它，正是让 Fase 4 的测试套件无需修改就保持绿色的原因——这证明了这一更换没有泄漏到外部契约。

上限可按区域配置，并且只能由你配置。 PATCH /projects/:projectId/agent-areas/:key/max-parallel 要求 maintainer——与激活执行相同的角色，理由也相同：改变上限就是决定产品可以不询问就花多少钱。没有自动提高它的途径。Anamnese 在注意到授权已成例行公事时可以提议，而提议在你接受之后仍要经过这条路由——一个自己提高自己花费上限的产品，正是审批流水线要阻止的东西。

改变上限对之后的请求有效。已经在等待决定的保持等待：动作在 payload 中带着它被创建时现行的上限，用新上限重新解读它，会改变你读完之后即将决定的东西。

RN-084 — 显示的流水线来自 gate 注册表​

RN-085 — 迭代上限按 agent 类型设置​

一个 agent 在工具循环中可以转多少圈，取决于它所做的工作：对话者为 8，dev agent 和 QA 子 agent 为 60。不再有单一的数字。

8 的上限诞生于对话型 agent，被做工作的 agent 继承了。 在 13b 的真实验证中，这表现为阻塞：dev agent 把八圈都花在探索一个新部署的仓库上，从未写过一个文件；改为 25 后，它写了三个并运行了测试。记录的结果是 limite de iterações atingido，来源 modelo——技术上正确，实际上毫无用处，因为模型从未来得及判断任何东西。

提高全局默认值是错误的修正，而这正是规则所保护的：Criativo 对话不需要 60 圈，上限也是防止无限循环的锁。

能提高的不是"工作多的"，而是下面有花费锁的。 迭代上限防止无限循环；保护钱包的是 token_budget_micros。dev agent 和 QA 子 agent 带着任务的 task_budget_micros 运行，因此放宽圈数不会放宽账单。infra-workflows 使用重型工具，却仍然保持 8：它在没有预算的情况下运行，对它来说上限是唯一存在的锁。

两个有专门测试的边界情况：

  • dev-lead 是对话型的，尽管有识别 dev agent 的 dev- 前缀（dev-<modulo>、dev-<modulo>-2）。lead 负责决定和委派，没有显式子句的话，它会因命名的偶然而以重型工作的上限诞生。

  • 未知 agent 落到最低上限。 向便宜的一侧犯错：需要更多圈数的会以 limite de iterações atingido 出现并被修正；错误地获得 60 的会悄无声息地花钱。

RN-086 — 为更多 agent 花钱永远不会自动批准​

触及产品可以独自花多少钱的两个动作—— parallelize（现在就超过上限）和 raise_max_parallel（改变上限） ——永远不可自动批准。agent_autonomy 不行， permissions.json 也不行。这与合并锁和指令补丁上限是同一类保证。

没有这一点，RN-083 的上限就只是装饰。 一个在 allow 中带 Parallelize() 的 permissions.json 会让每次超限都自行批准——要求用户决定的规则会变成免除用户决定。而 raise_max_parallel 是更严重的情形：那将是产品提高自己的花费上限，正是审批流水线要阻止的东西。

Anamnese 可以提议，它做的正是这件事。 当再授权一个 agent 成为例行公事时，上限就是错的，而最先察觉的是阅读历史的那一方。信号本来就会到达它：窗口内用户的决定来自 proposed_actions，带有 actionType 和 status。

阈值是三次批准且没有拒绝，两半都重要：

  • 两次不是例行——就是两次。 三次是区分"发生过"与"总在发生"的东西；
  • 一次拒绝就推翻整个信号，不管有多少次批准。如果用户曾经拒绝过，上限就在做它的工作，提议提高它就是把信号读反了。

提议一个等于或小于现行值的上限会被 api 拒绝：Anamnese 周期性运行，每轮都会重新提议同样的东西，让用户需要阅读的队列充满噪音。

批准应用的是 payload 中的值，而不是当时重新计算的值——那是你在作决定时读到的数字。

RN-087 — Dev Lead 是执行的唯一外部地址​

存在一个对话型 agent dev-lead，它接收 Arquiteto 的 handoff（自 RN-672 起，来自 Infra，项目容器处于 running），并提议执行计划：每个模块多少个 agent 以及为什么。它不写代码——它分配工作并为之负责。

在它之前，RN-083 中"由 lead 决定"这句话没有主人。 Arquiteto 完成后，执行由一个按钮启动，中间没有人评估有多少工作。

dev-<modulo> 不再能通过 handoff 寻址。 这不是新的例外：这是 ADR 0038 的规则——外部 handoff 只寻址区域的 lead 或没有区域的 agent——开始像对 QA 和 Infra 一样对 dev 生效。在没有 Dev Lead 时，它们是没有区域的 agent，因此是有效目标；成为成员后，就不再是了。

dev 区域是第一个动态区域，正是它迫使使用谓词：成员是 module_map 的每个模块一个，由 Arquiteto 决定，每个项目都不同，因此没有可枚举的列表。dev-lead 与成员匹配相同的 dev- 前缀，排除它的是通用规则lead 永远不是自己区域的成员——它适用于任何区域，只存在于一处。第一个版本在三处重复这个排除，变异检查表明没有一份副本是测试可达的：每一份都能在另一份被变异时存活。

计划是 proposed_action（由 ADR 0086、RN-284 修订）。 在这次变更之前，计划成为简单的事件，没有审批：理由是提议没有外部效果——花费发生在 agent 启动时，上限在那里要求授权；把提议变成待决定的动作会让你对同一件事决定两次。对 docs/fluxo.yml × 代码的审计发现，自 ADR 0085 起流程就已经把这个输出声明为 via: proposed_action，而代码从未被调整为一致——产品所有者判定是代码错了：计划是会话将在并行上花多少钱的第一个真实决定，用户开始在看到一次真正的审批之后才决定激活执行，而不只是读到消息流中的一行。旧的教训没有消失——它正是 propose_execution_plan 没有进入 decide.ts 绝对上限块的原因（见 RN-284）。

成功的计划结束回合——在没有暂停的路径上。 在第一次真实执行中，Dev Lead 在同一会话中登记了两次 execution.plan_proposed——文本不同，总数相同——因为循环回到了模型，它又提议了一次。事件日志是不可变的：留下了两份提议，没有任何东西说明哪个有效。工具 spec 中"只用一次"的指示是请求，不是保证；保证的是循环停止。自 ADR 0086 起，当提议处于 pending 时，结束回合的是暂停的停止（RN-284）——立即成功（auto_approved/executed/approved，见 RN-284）继续以一贯的方式关闭循环。

是成功，而不是"调用了工具"：被拒绝的计划（空的，或某个模块零个 agent）让循环继续，否则拒绝会变成回合结束，模型永远没机会修正。这道防护的第一个版本只看工具名称，就有这个缺陷——是由行为测试发现的，而不是靠阅读。

空计划，或某个模块零个 agent 的计划，在提议任何东西之前就被拒绝——提议一旦创建，就是用户的真实决定，而一个提议了一半的计划无从撤回。

  • 测试： apps/engine/test/engine/agents/dev_lead_tools_test.exs, dev_lead_server_test.exs（o plano ENCERRA o turno、o plano recusado NÃO encerra o turno）， apps/api/test/domain/agents/agent-areas.spec.ts（o dev de módulo DEIXOU de ser endereçável、`dev-lead` É endereçável, apesar do prefixo）和 test/application/use-cases/agents/offer-infra-handoff.use-case.spec.ts

RN-064 — 心跳不会结束有待定工作的会话​

由 RN-581（AT-072）扩展： 等待用户的对话型 agent 成为第五个信号，也是唯一有上限的（8h，原因 conversation_idle_timeout）；响应新增了 aguardandoUsuarioDesde。这条规则的其余部分照旧有效。

心跳超时衡量的是标签页的不活动，而不是工作的不活动。在结束之前，SessionServer 询问 api 是否还有剩余工作（GET /internal/sessions/:id/pending-work）；如果有，它重新安排超时并在日志中记录原因，而不是杀死会话。

默认值是 30 秒。离开会话切换到 Backlog 标签页就足以杀死它——在一次真实执行中，这把一个给 Arquiteto 的 offered handoff 困在了一个已关闭的会话中：史诗和四个故事都已就绪，而链条无法继续，因为没有地方可以接受已死会话的 handoff。

关闭会话关乎工作是否结束，而不是谁在看。

api 宕机不会阻止结束：{:error, _} 照样结束，在日志中给出警告。用永生的会话换掉孤儿会话，就是用一个缺陷换另一个。

"待定工作"是三个信号——第二个来自发现 V，第三个来自 Criativo→PO→Arquiteto 的真实 bug：

  1. offered 的 handoff——上面的原始情形；
  2. 状态为 pending 的 proposed_action——有人在等你的决定，某个 agent 可能已暂停等待结果（RN-073）；
  3. 已激活且仍在回合中的 agent——在会话中发过言的每个执行者的最后一个 agent.status 是 working，之后没有 idle。

第二个是第一个的同一缺陷低一个层级，而 hello-limpo 的执行显示了代价：会话诞生于 23:34:12，一个动作在 23:34:13 变为 pending，心跳在 23:34:42——恰好是超时的 30s——关闭了它。dev agent 在一个数据库认为已结束的会话中又工作了一个多小时，这毒害了每一项按会话的指标：时长、成本以及"多少个好好结束了"都开始读取一个不描述实际发生之事的状态。

第三个是同一个窗口，在前两个任何一个存在之前一步：AcceptHandoffUseCase 把旧 handoff 标记为 accepted 并立即激活下一个 agent，但 engine 中的激活是 GenServer.cast，发出即不管——在 agent 甚至开始之前就响应 201。由 Criativo 的 handoff 激活的 PO 运行一个最多 12 次 LLM 迭代的 kickoff，只使用 category: :direct 的工具（create_epic/create_story/create_task），它们从不产生 proposed_action，并且只在整个回合结束时才提供下一个 handoff（信号 1）。在激活与那个结束之间，信号 1 和信号 2 都不存在——只有每 10s 一次的 Phoenix 通道 ping 撑着会话，任何超过 30s 超时的延迟都会在 PO 仍在生成 backlog 时关闭会话，从根上打断 handoff 链：下一个 handoff 最终被提供在一个已经 closed、不再接受任何东西的会话中。

agent.status（working/idle）是每个对话型 agent（Criativo/PO/Arquiteto/Dev Lead/Infra）已经在回合边界叙述的东西，并且被持久化在事件日志中，而不只是在通道中广播 （Engine.Sessions.LiveBroadcast.agent_status/4，ADR 0021） ——团队面板已经读取同一个信号来推导名册（apps/web/src/lib/agent-status.ts 中的 conversationalStatus）。在这里复用它不需要任何新事件：第三个信号是在会话中发过言的每个执行者的最后一个 agent.status，并且按事件类型是通用的——它覆盖任何由 handoff 激活的 agent，而不只是 PO。

这条规则的上一个版本白纸黑字地写着，把 agent 的工作包括进来"而没有证明这种交互的测试，就是在猜"。执行产生了证明，测试现在存在了。

**仍然排除在外的：**没有待定动作、没有 handoff、也没有未完回合的 in_progress 任务。dev agent 有自己的状态机，自行持有 worktree；api 拥有且执行已证实的信号是待定动作。把任务包括进来需要 api 读取属于 engine 的 dev_agent_states——这是边界决定，不是顺手修复。dev agent 也不发出 agent.status（它们用自己的状态机运行，而不是对话型的回合循环）——第三个信号不覆盖它们，也不需要：待定动作已经覆盖了它们的路径。

RN-063 — 不产出而结束是结果，不是失败​

Anamnese 有一个工具用来说**"没有什么要发出，原因如下"**（skip_proficiency）。这一轮以 anamnese.run_skipped 结束，原因放在 payload 中——绝不以 anamnese.run_failed 结束。

之前它没有这个动词。唯一的工具是 emit_proficiency，它拒绝空列表（有道理：空档案不是档案）。在没有合格成员的窗口中，Anamnese 在第一次迭代就发现了这一点，用散文写下"没有合格成员"，以 profiles: [] 调用 emit_proficiency，被拒绝——然后重复直到迭代上限。每一圈都会重新发送历史，而历史每圈都在增长。

在一次真实执行中，这花费了 14.5 万输入 token，是 Criativo 和 PO 花费总和的 4 倍，什么都没产出。而且它会在调度器的每次 tick 时回来，每 15 分钟一次，永远如此。

迭代上限是有效的——这不是无限循环。浪费是每一轮的，无限重复，这更糟：循环会卡住，有人会注意到；这个是慢慢流血。

为一个做了正确事情的轮次叙述 run_failed 也是缺陷：读日志的人会学会忽略失败事件。

RN-060 — 密钥的花费属于 owner，只有他能看到​

按凭据的消耗报告（GET /workspaces/:id/credential-spend）要求在 workspace 中是 owner。不是 maintainer：自 RN-058 起，所有项目的 agent 都消耗所有者的凭据，而他的账单与只是操作某个项目的人无关。

报告按提供方分组，因为那是凭据的单位——每人每个提供方一个密钥。单一总数无法与任何账单对上。

并且它把 agent 与人分开：自 RN-058 起，两者都出自同一个密钥，而"我的 agent 贵吗？"与"我聊天用得多吗？"是不同的问题。这就是为什么这是产品中唯一没有 RN-038 的 actor_kind = 'agent' 过滤器的成本汇总——这里的问题是从密钥中流出了多少，而 owner 自己的聊天也从中流出。

没有任何秘密穿过：响应包含提供方、token 和成本——绝不包含密钥，即使是加密的也不包含（ADR 0050）。

RN-101 — 同一笔花费，两类受众：账单属于 owner，消耗属于花钱的人​

产品回答关于 token_usage 的两个不同问题，没有一个是另一个的切片。

owner 的问题是按凭据的。 GET /workspaces/:id/credential-spend 保持 RN-060 留下的样子——按提供方，要求 owner，回答"从我的密钥里流出了多少"。与它一起，GET /workspaces/:id/spend-report（同样是 owner）按模型、提供方、项目、执行者和日期拆分 workspace——提供方维度由 RN-186 引入。owner 能看到两者，因为他是唯一能看到两者的人。

成员的问题是按执行者的。 GET /projects/:id/spend/me（角色 viewer）以 token 和估算成本返回调用者在该项目中消耗了什么，按会话和日期。它不按提供方或凭据拆分——运行的密钥是 owner 的（RN-058），而他账单的一个切片不是成员所问的东西。

执行者不是参数：它来自已认证的用户，没有地方可以写入别人的 id。"成员看不到其他执行者的行"是用例签名的性质，而不是某个人可能忘记调用的检查。

agent 不计入成员的账。 token_usage 记录的是谁花了钱，而不是谁让花钱；把 agent 归给启动它的人，就是编造一个表中没有的数据。agent 的花费出现在 owner 的报告中，密钥是他的。

provider 维度存在，而成员够不着它。 在 ADR 0076 之前，它在聚合中根本不存在，正是这种缺失约束着成员的视图。如今 sumGroupedBy 有六个维度（model、provider、project、actor、 session、day），约束改变的是形式而不是力度：约束它的是类型——见 RN-186 和 RN-187。没有改变的是，提供同一模型名称的两个提供方，在 model 维度上仍然落在同一行。

RN-102 — 区域的模型是可继承的默认值；偏离是 agent 的决定，恢复继承会抹去该决定​

binding 级联增加了一层：sessão > agente > **área** > projeto > workspace。area 位于 agent 和项目之间——它是一个区域的 lead 和子 agent 共享的默认值（qa/qa-automacao/ qa-performance-seguranca、infra/infra-workflows、dev/dev-<módulo>），而 agent 自己的 binding 是覆盖它的偏离。如果区域位于 agent 之上，它总会胜出，"可继承的默认值"实际上就成了"强加的默认值"——没有任何 agent 能选择别的模型。

新的层级进入与 RN-041/RN-043 相同的能力重新校验：从提供方消失或不做 tool calling 的区域模型会被跳过并记录在 skipped 中，与 agent 原来一样。assertModelFitsBindingScope（RN-040）开始在 area 范围也要求 supports_tool_calling——它从不被人工聊天读取，只被 agent 读取，因此放它通过只会把同样的无声失败推迟一个层级。

"恢复继承"会删除 binding，从不把下层的模型复制到上层。 把区域决定的模型写入 agent，在界面上看起来一样，但并不一样：它会成为一份副本，区域的下一次变更会在无人察觉的情况下把这个 agent 甩在后面。继承是没有自己的决定，撤销偏离就是删除那一行——DELETE /projects/:id/agent-bindings/:slug 和 DELETE /projects/:id/area-bindings/:key，都是 204，当范围已经在继承时都是 404（如果是静默的 204，幂等性就会撒谎：删除不存在的东西和真正删除，对同一界面来说是不同的回答）。

更改区域的模型要求 maintainer，而不是像单个 agent 那样的 developer——理由与并行上限相同（RN-083）：区域的 binding 一次触及 lead 和所有子 agent，而选择模型就是决定产品不询问就花多少钱。

界面开始遵守两个最低要求，而且确实是两个。 在此之前， ModelsSection——按 agent 的模型表——不检查任何角色：现行模型列的 ModelPicker 和来源列的"恢复继承"对所有人都显示为可点击，包括 viewer，而 api 以 403 拒绝。出路不是复制姊妹部分的闸门（owner || maintainer）：那会把缺陷换成相反的缺陷，把一个 developer 锁在 PUT/DELETE .../agent-bindings/:slug 接受的操作之外——而相反的缺陷更糟，因为提供会被拒绝的东西至少会以一个 toast 告终，而失去能力对失去它的人是不可见的。最低要求属于端点，而不是部分，这两个部分在同一界面上相邻，最低要求却不同。比较从界面中移出，成为 roleAtLeast（apps/web/src/lib/roles.ts），基于已经存在的 ROLE_ORDER——与后端函数同名，因为这是线路两侧的同一条规则；手写层级（role === 'owner' || role === 'maintainer'）在最低要求高时碰巧正确，在低时悄无声息地出错。缺失的角色（查询进行中，或失败了）什么也够不着：向禁用的一侧犯错，重新加载就能修复。

RN-103 — agent 的 binding 是按项目的，不再是全局的​

在 FASE 23 之前，scope = 'agent' 保存一个全局 SLUG（scope_id = 'qa'），而 PUT /projects/:id/agent-bindings/:slug 在路由中接收 :projectId 却刻意丢弃它——在一个项目的界面上选择 Arquiteto 的模型，会改变它在所有项目中的模型。当区域成为可继承的默认值（RN-102）之后，这站不住了：区域是按项目的，而一个位于按项目默认值之上的全局 agent binding，会让同一个 agent 只在存在区域的地方解析出不同的模型——并且会让"恢复继承"抹去一个波及无人关注的项目的决定。

RN-470 — 模型来源区分自有 binding 与从 Criativo 继承，级联中的空值不与其他空值共用同一符号​

api 响应中的 origin: 'agent' 意味着两件不同的事，而 api 不区分它们是正确的：agent 在 model_bindings 中有一行 agent 范围的记录，或者级联落在 workspace 上而 herdarModeloDeStart 把值换成了 Criativo 的模型——读"来自哪里"的人需要看到它来自一个 AGENT，而不是来自一个数据库中不存在的范围。必须区分它们的是界面，而在此之前它没有区分：来源列打印原始枚举，在一个数据库中有 3 行 agent 的项目里，12 个 agent 都显示同一个词 agent。

来源是一条链，而不是一个词。 workspace › projeto › área › agente，每个节点四种状态，四种都存在是因为它们说的是不同的事：现行（使用中的模型从这里来——唯一以 Badge 显示的节点）、已定义（这一层有自己的值，但一个更具体的层胜出了）、空（这里没有值）和被跳过（有值，但级联因 unavailable/sem_tool_calling 丢弃了它，RN-043）。把"已定义"折叠成"空"会把原始枚举的问题带回低一层。

在继承中，agente 节点保持为空，一个额外节点点名 Criativo。 级联到达的层级（workspace）显示为"已定义"，而不是现行：workspace 的模型不是生效的那个，把它标为现行就是断言了错误的模型。Criativo 的节点是唯一一个不是数据库范围的节点，这是刻意的——它点名的是级联之后的那一步。同一条链也适用于区域部分，在那里 origin: 'agent' 只能是这一步：区域查询不会把 agent 范围放进级联。

推导属于客户端，它无法证明的东西仍然可以操作。 没有新端点：界面已经获取了四个层级。当工作区之上没有任何层级有可用的值（被跳过的不会阻止下降）并且模型与解析出的 Criativo 模型相同时，agent 就是继承。剩下一个无法区分的情形：agent 有自己的行，指向与 Criativo 相同的模型，且没有区域或项目默认值。这就是为什么"恢复继承"在每个 agent 来源上都继续显示——动作恰恰在链无法证明的情形中保持可用，而在那种情形下它仍然会改变未来（没有这一行，agent 开始跟随 Criativo）。

这个选择的另一半：404 有自己的结果。 在每个 agent 来源上保留按钮，意味着也在没有行可删的地方提供它——在那里 ClearModelBindingUseCase 正确地响应 404（"删除了不存在的东西"和"删除了"不是同一个回答；把它们折叠起来会隐藏一个错误的 agentSlug）。然而对点击的人来说，这个 404 不是失败：所请求的状态——agent 在继承——已经是事实，把它称为错误就是界面与它所知道的东西相矛盾。因此它不像其他拒绝那样经过 mensagemDaApi，有两个原因：api 的句子是硬编码在代码中的 pt-BR，而 web 的默认语言是 en；并且这个端点只有一个 404 原因（角色不足是 RolesGuard 中的 403，格式错误的 scope_id 不是 404）——客户端知道这个 404 意味着什么，可以用读者的语言说出来。任何其他状态仍然是真正的失败，带 api 的句子和 danger 色调。在两种结果中都会重新读取该行：如果 api 说本来就没有 binding，过时的是界面。

而自己的结果属于端点，而不是界面。 同一行的另一个动作——通过现行模型列的 ModelPicker 更换模型——有七条拒绝路径，没有任何一个状态能单独识别其中之一（SetModelBindingUseCase）：格式错误的 scope_id 或 DTO 拒绝的 modelId 是 400，低于 developer 的角色是 403，两个无法区分的原因是 404（"Modelo não encontrado" 和 "Projeto não encontrado"），三个原因是 422（RN-040 没有 tool calling；RN-043 在 workspace 中被停用或从提供方消失）。在那里客户端不能点名 404——选择两句中的一句，就是界面断言它不知道的东西——因此每次拒绝都遵循正常语法，带 api 的句子和 danger 色调。这两个函数相邻，刻意以相反的方式处理同一个状态：授权自己结果的是唯一的原因，而不是界面。

在拒绝时，现行模型列继续显示已确认的 binding。 ModelPicker 不在本地状态中保存选择（selected 来自 selectedModelId prop，它来自查询），因此拒绝不会在界面上留下 api 拒绝写入的模型——而该行只在成功时重新读取，因为拒绝时数据库中什么都没变。这是把这条 RN 的同一纪律应用于时间：界面不断言一个不存在的状态，不靠短横线，不靠枚举，也不靠乐观。

空值有自己的文本，不同的空值有不同的文本。 界面上的三个 — 用同一个符号说三件事，现在各说各的：sem modelo em nenhum nível（没有任何层级为该 agent 设置 binding）、sem gasto ainda（agent 没有记录消耗——不同于 US$ 0,00，那是免费运行过）以及 sem padrão em nenhum nível（区域及其上面的两层都为空）。与 RN-180 同一纪律：界面不用一条短横线断言它无法点名的东西。

RN-059 — 回合失败是带来源的持久事件，而且 agent 会说话​

当 LLM 回合失败时，agent 在事件日志中写入 agent.error，带三个字段：origem（ADR 0020 的词汇）、葡萄牙语的 mensagem 以及原始的 reason。并且消息出现在对话的消息流中，而不只是在日志中。

还有第二条路径，更糟：当 api 在它自己的最后一帧中叙述失败（预算、缺少凭据、缺少 binding）时，回合不会落入错误分支，根本不发出任何事件——绝对的沉默。

LLM 凭据属于一个人（user_credentials.user_id），而 agent 不是人。agent 的回合按 workspace owner（workspaces.created_by）解析密钥，而不是按打开会话的人，也不是按创建项目的人：付账的人为 agent 买单，当团队中的另一个人开始会话时，这一点不变。

用 created_by 而不是 workspace_members.role = 'owner'：可能有多个 owner，"其中任意一个"会让使用的密钥在无人决定的情况下变化。

在此之前，回合在用户列中传入的是 agent 的 slug（agentId ?? sessionId）。查询以 user_id = 'criativo' 到达数据库，Postgres 拒绝了无效的 UUID，错误在消息流中变成空响应——没有指标，没有失败事件，界面上什么都没有。只有一次真实执行才揭示的实际效果是：从来没有任何 agent 使用过带凭据的提供方。只有 ollama 能工作，因为对它会跳过查找——而 Fase 4、Fase 10 的 dogfooding 以及所有演示都是用本地模型运行的。

人工聊天从未有过这个缺陷：它使用 actor.id，那是真正的用户。

RN-056 — 能力的分面来自提供方；沉默保留原有的值​

supports_vision、supports_reasoning 和 generates_image 是提供方的事实，而不是意见：它们在同步时来自远程目录，回退与 supports_tool_calling 相同——远程，然后本地，然后 false。

在 OpenRouter（目前唯一公布这些的）中，三者来自： architecture.input_modalities 包含 image， supported_parameters 包含 reasoning，以及 architecture.output_modalities 包含 image。接受图像和生成图像是不同的维度：把它们合并会把用户送到错误的模型。

以前，同步从已写入的数据读取 supportsVision，从不查询远程——该列以 false 诞生，没有途径变为 true。第一次真实同步的 338 个模型全部为 false，包括提供方声明为多模态的 181 个。

没有声明不等于声明没有 （ADR 0041）：当提供方沉默时，解析器省略该字段，undefined 保留本地值。因此界面只把分面用作正向过滤器，从不写"不能读图"——这里的 false 意味着"提供方没有声明"。

RN-057 — "用途"是 workspace 的策展，标记用途不会打开模型​

没有任何提供方的目录公布"适合写代码"。这是操作者的意见，在使用中发现——因此它位于 workspace_models.uses，与 workspace 的另一个决定（RN-052）并列，而不是在 models 中。

封闭的词汇——codigo、documentacao、analise、imagem、 conversa——，两侧都有编译期的穷尽性证明。自由文本会在一周内让 code、coding 和 código 出现在同一个过滤器中。

保持维度分离的两条规则：

  1. 标记用途不会打开模型。 workspace_models.is_active 的 DEFAULT 是 true，因此由用途标记创建的行以显式的 is_active = false 插入。没有这一点，对模型发表意见就会授权它花钱，违反 RN-043。
  2. 更换用途不会关闭已经打开的。 is_active 不在 ON CONFLICT 的 SET 之中。

用途列表替换之前的，而不是相加：空列表就是全部取消标记的方式，并且是一个正当的状态——"没有人发表意见"不等于"没用"。

RN-038 — workspace 摘要中计数的 agent = 本月花费了 token​

项目仪表板的摘要（"N 个活跃项目 · M 个 agent · 本月花费"）把在当月 token_usage 中至少有一行 actor_kind = 'agent' 的执行者计为"agent"，汇总 workspace 的所有项目。没有 actor_kind 过滤器，发送聊天的 user 或记录使用的 system 会让计数膨胀——token_usage 为任何类型的执行者记录，而不只是 agent。按月截断使用 created_at >= date_trunc('month', now())；只在上个月工作过的 agent 不计入，即使它仍出现在某个会话的名册中。计数自然包括 Fase 8 的区域子专业（qa-automacao、qa-performance-seguranca、infra-workflows）：每个在花费 token 时都有自己的 actor_id。

RN-703 — 没有模型的子 agent 继承区域 lead 解析出的模型​

"应用到所有 agent"（RN-476）为设置目录中的每个 agent 写入一个 binding——17 行——，而 engine 在这个列表之外运行的子 agent 在任何层级都没有模型：appsec 以来源 infra 的 agent.error（"Nenhum modelo vinculado para esta sessão"）告终，对除 dev-backend/dev-frontend 之外的每个 dev-<modulo> 以及 qa-estrategia 也是如此。当子 agent 的级联找不到值（或者只找到没有人为项目选择的 workspace 全局默认值）时，它使用其区域 lead 的已解析 binding：目录（agent-areas.ts）中区域的 lead，或者——对于 appsec → secops 和 qa-estrategia → qa，它们由 engine 在 lead 内部运行但不接收 handoff——旁边的一张表，只服务于这种继承。响应带有指明 lead 的 herdadoDoLead，origin 仍然是 lead 的 binding 的来源（RN-470：界面不断言自有配置）。tool calling 过滤器（RN-040）在 lead 的解析中与子 agent 的解析中同样适用。如果仍然没有模型，失败消息会说明在哪里配置。

RN-774 — 每个模块的第一个任务拥有两倍的单任务上限​

模块的第一个任务搭建整个骨架（清单、应用、数据库、测试），比后续任务花费更多：在 10月8日的 TP-01 中，它使用 Haiku 4.5 花费了 US$ 0.53，被 US$ 0.50 的固定上限（taskBudgetMicros: 500000）阻塞。根据所有者的决定（10月9日），它获得2 倍的单任务上限（默认为 US$ 1.00）；其余任务沿用配置的上限。倍数是 engine 中的命名常量，而不是配置。

"第一个"由日志衡量，绝不由任务状态衡量：它是其 backlog.task_claimed 在项目中针对该模块最早的任务。阻塞会清空 assigned_to，重启 engine 会丢失进程的记忆；日志不变，因此同一任务在被释放后再次被领取时仍然是第一个，gate 要求的修正也会获得 2 倍。api 在 dev 的上下文中返回 task.primeiraDoModulo（没有 module 时为 false，该模块没有任何领取时也为 false——正常上限是保守的），有效上限在 engine 的单一位置解析。因预算而阻塞时会说明对该任务生效的上限（"teto da primeira tarefa do módulo: 1000000 micro-USD, US$ 1.00"）。QA 的 gate 仍使用基础的 task_budget_micros——不在卡片的范围之内。

RN-802 — Dev Lead 计划的估算把每个模块第一个任务算作两倍​

propose_execution_plan 的审批卡片（RN-709）原来说"最多 N × 上限"，忽略了每个模块的第一个任务有两倍上限（RN-774）。现在 api 在 payload 中、在 orcamentoPorTarefaMicros 旁边带上 multiplicadorDaPrimeiraDoModulo，句子汇总有效上限：（任务数 − 有任务的模块数）× 上限 + 有任务的模块数 × 倍数 × 上限，并说明"每个模块的第一个算两倍"。一个模块 8 个任务、上限 US$ 0.50 时：最多 US$ 4.50。这是上限：已经有任务被领取过的模块的第一个不会获得两倍，句子仍然说"最多"。payload 中没有倍数（旧提议）时，用旧的算法。

倍数只在 engine 中应用（Engine.Dev.TetoDaTarefa）；api 有一个声明的镜像，因为界面不应该复制这个常量，而提议时不会询问 engine。改一个就要改另一个。

RN-892 — 调用的稳定前缀带标记发往 prompt 缓存，能力只在 OpenRouter 中打开，并经过证明​

在 TP-01（10月15日）中测得：经由 OpenRouter 的 anthropic/claude-haiku-5.5 收到 840 万输入 token，其中缓存为 0，输入占 US$ 1.02 中的 US$ 0.84。Anthropic 模型只从缓存读取在文本内容块中以 cache_control: { type: "ephemeral" } 标记的前缀（最多四个点，TTL 5 分钟——https://openrouter.ai/docs/features/prompt-caching）。

  1. 提供方能力，必需。 LLMProviderCapabilities.promptCaching 只在 OpenRouter 中为 true，在其他八个中为 false。声明它而没有 marcarCacheDePrompt 钩子会在构造时失败。关闭时，请求体与之前逐字节相同。
  2. 配置中的模型层。 在 OpenRouter 中只有 anthropic/* 获得缓存点；其他模型自行缓存，原样返回。
  3. 两个点，放在不变的东西上。 前缀的最后一个 system（指令，以及其前的工具）和末尾 system 尾部之前的最后一个 user/tool。尾部——语言（RN-622）、环境（RN-706）、流程（RN-711）、档案（RN-680）——位于最后一个点之后，消息的顺序从不改变。
  4. 证明（ADR 0041/0042）。 2026-10-15，smoke 使用真实凭据运行（OPENROUTER_TEST_KEY=… pnpm --filter api exec vitest run test/infrastructure/llm/openrouter-provider.cache.smoke.spec.ts），对 anthropic/claude-haiku-5.5 的第二次调用返回 cached_input_tokens=8011；只有在那之后，OpenRouter 的能力才变为 true。打开其他提供方需要等效的 smoke。收益通过 RN-666 出现在计量中。
