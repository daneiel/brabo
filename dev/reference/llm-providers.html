Providers de LLM

Todo agente e todo chat do Brabo fala com um modelo atrás de um contrato único. Quem chama não sabe se do outro lado está um Ollama em disco, a API da OpenAI ou a API da Anthropic — e não deveria saber.

Decidido no ADR 0041, com o teto de inatividade herdado do ADR 0020.

O contrato​

LLMProvider (apps/api/src/application/ports/llm-provider.port.ts) tem uma operação OBRIGATÓRIA, e ela é sempre streaming:

abstract class LLMProvider {
  abstract readonly name: LLMProviderName;
  abstract readonly capabilities: LLMProviderCapabilities;
  abstract chat(
    messages: ChatMessage[],
    options: ChatOptions,
  ): AsyncGenerator<ChatStreamChunk>;

  /** Only when `capabilities.listModels` (Phase 9c). */
  listModels?(apiKey?: string): Promise<ModeloDoCatalogo[]>;
  /** Only when `capabilities.embeddings` (ADR 0075). */
  embed?(
    inputs: readonly string[],
    options: EmbeddingOptions,
  ): Promise<EmbeddingResult>;
}

As duas opcionais seguem o mesmo contrato de dois lados: quem declara a capability implementa o método, e quem não a declara não o expõe. O consumidor degrada checando a capability, nunca descobrindo-a na falha.

Não há método separado para tool calling nem para contagem de tokens: as ferramentas vão em options.tools e tudo volta pelo mesmo stream, como um dos quatro tipos de ChatStreamChunk.

chunkquando
text_deltaum pedaço de texto gerado
tool_callso modelo pediu ferramentas (chunk único, não incremental)
usagecontagem de tokens, com a marca estimated; e, quando a resposta diz, o custo real (costMicros), o modelo que serviu (resolvedModel), o id da resposta (generationId) e as PARTES em cache/raciocínio das contagens de tokens (cachedInputTokens, reasoningTokens, RN-666) — ADR 0188
errorfalha classificada por code — nunca uma exceção

A falha vira chunk, e não exceção, porque o turno já gastou tokens: o metering precisa acontecer mesmo quando a resposta não veio.

Capabilities: duas camadas​

A do provider é o teto do que aquele backend sabe fazer. A do modelo é o que aquela linha da tabela models sabe fazer. Um modelo pode ser mais pobre que o provider, nunca mais rico.

As três facetas de modalidade​

supports_vision, supports_reasoning e generates_image são fato do provider: saem do catálogo remoto na sincronização, com o mesmo fallback do tool calling — remoto, depois local, depois false. Hoje só o OpenRouter as publica:

facetade onde vem no OpenRouterno catálogo de 2026-08-04
supports_visionarchitecture.input_modalities contém image181 de 338
generates_imagearchitecture.output_modalities contém image11 de 338
supports_reasoningsupported_parameters contém reasoning213 de 338

Aceitar imagem e produzir imagem são eixos distintos: ler um diagrama e desenhar um resolvem problemas diferentes.

O parser omite o campo quando o provider não declara a modalidade, e undefined preserva o valor local na sincronização — ausência de declaração não é declaração de ausência. Por isso a tela usa as facetas só como filtro positivo: false quer dizer "o provider não declarou", nunca "o modelo não sabe" (ADR 0051).

:::caution Isto NÃO cobre "melhor para código" Nenhum catálogo de provider publica para que um modelo é bom. Isso é curadoria de quem opera, e mora em workspace_models.uses, por workspace (RN-057) — não é capability, e derivá-la do nome do modelo seria um palpite vestido de dado. :::

Provider sem list_models é PULADO pela sincronização do catálogo, com o motivo no relatório — nunca tratado como "o catálogo voltou vazio". "Origem dos modelos": sync descobre sozinho, seed só entra por apps/api/src/db/seed.ts, sync + seed tem os dois (o seed é só o bootstrap antes da primeira sincronização). "Quirks resumidos" são os RÓTULOS em negrito da seção de prosa do provider abaixo — o porquê de cada um mora lá, não aqui. "embeddings" é a capability do ADR 0075, e só é sim com PROVA de execução: ler a documentação não conta, e o motivo de cada não está no comentário do literal, no arquivo da última coluna. "preferência de roteamento" é a capability do ADR 0166 (um hub escolhendo o upstream por price, throughput ou latency), sob a mesma régua: sim só depois de um smoke contra a API real devolver o upstream escolhido.

O default de supports_tool_calling é false. É de propósito: um modelo descoberto pela sincronização automática (Fase 9c) entra sem uma promessa que ninguém verificou. Os modelos do seed declaram a capability explicitamente, e a migration 0026 faz o mesmo backfill em bancos que já existiam — mirando as sete linhas do seed, nunca um UPDATE cego na tabela.

:::caution Modelo inserido à mão models não tem endpoint HTTP de edição: quem acrescenta um modelo o faz pelo seed.ts ou por SQL direto. Nos dois casos, declare supports_tool_calling se pretende vincular esse modelo a um agente — o default false faz o binding ser recusado, inclusive quando o modelo é apontado por DEMO_QA_MODEL nos scripts de demonstração de gate. :::

Onde a pessoa vê e edita os providers​

Os providers têm página própria, /providers, no rodapé do menu ao lado de Containers (AT-577). Desde a RN-911 (AT-597) ela é o ÚNICO lugar de credencial, catálogo e gasto por chave: as Configurações do projeto só escolhem modelo. Ela compõe, com os mesmos endpoints e queryKeys: chaves, a tabela do que cada provider sabe fazer (lida de GET /llm/provider-capabilities, uma coluna por chave da resposta), o catálogo de modelos e, só para owner, o gasto por chave. O critério de roteamento do OpenRouter continua sendo do modelo do agente ou da área, escolhido nas Configurações do projeto.

A api já expõe quais providers têm chave do TITULAR do workspace (a pessoa cuja chave os agentes gastam, RN-058): GET workspaces/:workspaceId/llm-providers/credentialed, viewer, resposta { providers: [...] } só com nomes e sem ollama (RN-926, AT-607). Desde a RN-931 a tela a consome: a tabela do que cada provider sabe fazer lista só os providers ATIVOS (local ou com chave do titular), cada um com o nome e a cor do card de credencial, e uma linha diz quantos ficaram de fora e quais. O catálogo de modelos é um painel com uma aba por provider ativo; o provider sem chave que ainda tem modelo ativo aparece como aba marcada "sem chave do titular", para dar para desativá-lo. Se a rota não responde, as telas mostram todos os providers.

Catálogo de modelos: descoberta e ciclo de vida​

Quem declara listModels sabe listar o próprio catálogo. A base compatível implementa o GET /models do dialeto que ela já fala, com o parsing trocável por configuração (parseCatalogo) — um hub devolve preço e janela na mesma linha, e isso não pode virar um if dentro do parsing padrão.

Ollama e Anthropic agora declaram true — o backlog que o ADR 0042 deixou aberto. Eles declaravam false não por falta de endpoint, mas porque o formato não tinha sido conferido contra a doc oficial, e a regra é não programar contra contrato adivinhado. Os dois formatos foram conferidos antes de escrever uma linha de código:

  • Anthropic — GET /v1/models devolve { data: [{ id, display_name, max_input_tokens, ... }], has_more, last_id }, paginado por cursor (não por offset): last_id vira o after_id da próxima página, com limit de 1 a 1000. Quem percorre as páginas é o client.models.list do SDK oficial, que já pagina sozinho — refazer o laço do cursor à mão seria reescrever código mantido pelo fornecedor. Preço não vem na resposta, então o modelo entra sem preço em vez de com um inventado.
  • Ollama — GET /api/tags devolve { models: [{ name, model, size, ... }] } no host local (OLLAMA_HOST, default http://localhost:11434). Sem preço, como cabe a um runtime local.

Os dois LANÇAM no erro, como o contrato exige: devolver lista vazia seria lido pela reconciliação como "sumiu tudo" e deixaria o catálogo inteiro indisponível (RN-043).

Os dois eixos independentes de disponibilidade​

Um modelo tem dois estados INDEPENDENTES, e confundi-los era o buraco que a Fase 9c fechou:

ondequem escreveo que quer dizer
workspace_models.is_activeo owner daquele workspace, pela tela de curadoriaaparece no seletor e pode receber binding novo
models.availabilitya sincronização, sozinhaunavailable = sumiu do catálogo do provider

Um modelo pode estar ativo E indisponível ao mesmo tempo — é essa sobreposição que gera o aviso na tela. Quando o provider o traz de volta, a escolha do owner continua valendo: a sincronização nunca religa o que alguém desligou de propósito.

Os dois eixos deixaram de morar na mesma tabela no ADR 0049. A curadoria é por workspace — models.is_active era uma coluna da instalação inteira, e o owner do workspace A ligando um modelo o ligava também para o B (RN-052). O que ficou em models é fato do provider: nome, preço, capabilities e disponibilidade, iguais para todos.

Ausência de linha em workspace_models É "desligado". Não há um estado separado de "nunca decidido", e é assim que a RN-043 continua valendo sem coluna nenhuma que a sincronização pudesse atropelar.

O terceiro eixo: para que o workspace usa o modelo​

workspace_models.uses guarda a curadoria POR USO — codigo, documentacao, analise, imagem, conversa — um vocabulário fechado em apps/api/src/domain/llm/model-uses.ts. É o que nenhum catálogo publica: o provider declara a capability, mas qual modelo rende bem em código para este time só se descobre usando.

Ele não se mistura com is_active:

  • marcar um uso não liga o modelo — a linha nova nasce com is_active = false explícito, contra o DEFAULT true da coluna;
  • trocar o uso não desliga o que estava ligado;
  • a lista substitui a anterior (lista vazia desmarca tudo).

Rota: POST /workspaces/:workspaceId/models/uses, owner (RN-057).

As três regras de reconciliação​

  1. Modelo novo entra INATIVO — sem linha de curadoria em workspace nenhum. Um catálogo tem centenas de linhas; despejá-las todas ativas tornaria a escolha impossível e ligaria um modelo caro sem ninguém decidir.
  2. Modelo que sumiu vira unavailable, nunca é apagado. model_bindings e token_usage apontam para a linha; apagá-la levaria o histórico de custo junto.
  3. Falha do provider não torna nada indisponível. Um 401 quer dizer "não sei o que tem lá", não "não tem nada lá" — marcar tudo como sumido por causa de uma chave revogada derrubaria de uma vez todo binding daquele provider. O provider é PULADO, com a origem da falha (infra | modelo) no relatório.

E as duas regras de reconciliação de preço​

  1. manual_pricing vence o catálogo remoto. Uma linha marcada assim tem um número que alguém digitou a partir da doc do provider, e a sincronização não mexe nele — nem quando o catálogo traz preço próprio (RN-051).
  2. Toda mudança de preço feita pela sincronização deixa uma linha em model_price_changes, com origem sync e changed_by nulo (RN-044).

Um modelo NOVO descoberto pela sincronização nasce manual_pricing = false quando o catálogo informou preço — a origem é a sincronização, e é ela que mantém a linha em dia. Descoberto SEM preço, nasce true: a linha está esperando alguém digitar um, e marcá-la já protege esse número do primeiro catálogo que por acaso informe preço.

A cascata revalida a capability ao descer de nível​

resolveBinding pula o candidato indisponível e segue a precedência. Quando o turno leva ferramentas, ele também pula quem não faz tool calling em todo nível — sem isso, o fallback de um agente pousaria num modelo só de chat e violaria em silêncio a RN-040: a falha só apareceria depois, no ToolLoop, como "o agente parou sozinho". O que foi pulado volta em skipped, e a interface o mostra.

A precedência é session > agent > area > project > workspace (RN-020). area entrou na FASE 23: é o PADRÃO que um lead e os subagentes da área dele compartilham, e o binding próprio do agente é a divergência que o sobrepõe — ele entra na mesma revalidação de capability acima, inclusive a exigência de tool calling (RN-102). Os escopos agent e area passaram a ser POR PROJETO (scope_id composto, <projectId>:<slug|chave>) — antes, agent era um slug global e o mesmo binding valia para todo projeto (RN-103, ADR 0064).

Um subagente sem valor em nível nenhum (ou só com o default global do workspace) herda o binding RESOLVIDO do lead da área dele, e a resposta leva herdadoDoLead nomeando o lead; appsec herda de secops e qa-estrategia de qa (RN-703).

Quem agenda e quem executa​

O engine agenda (um worker do Oban que se reagenda, MODEL_SYNC_INTERVAL_SECONDS, 6h por padrão) e a api executa, porque é ela que guarda as credenciais e o registro de providers. O botão "Atualizar catálogo" da tela de curadoria chama o mesmo caso de uso — não há duas reconciliações que possam divergir.

Preço: vale daqui para frente, nunca retroativo​

token_usage guarda o preço que produziu cada cost_micros (input_price_per_million_micros e output_price_per_million_micros). O custo histórico já era imutável antes da Fase 9c; o que faltava era ser reproduzível — sem o preço gravado, tokens × preço = custo deixaria de fechar no momento em que alguém corrigisse a tabela.

Desde o ADR 0188 (RN-665) o preço do catálogo só é o número quando a resposta não traz o custo real. Quando traz (o usage.cost do OpenRouter), ele é o cost_micros, as duas colunas de preço guardam o preço IMPLÍCITO (custo ÷ tokens, marcado por price_implicit), e o que o catálogo teria cobrado vai ao lado em catalog_cost_micros — então tokens × preço = custo continua valendo em toda linha, real ou estimada.

Toda mudança de preço grava uma linha em model_price_changes, append-only, com o par antes/depois e a origem (manual | sync). O par é gravado junto de propósito: reconstruir o "antes" a partir da linha anterior dependeria de nenhuma escrita ter escapado do caminho auditado, que é exatamente o que a auditoria existe para provar.

:::caution Duas escritas escapavam A origem sync existia no domínio desde a Fase 9c e nenhuma escrita a produzia: a sincronização trocava o preço por upsert, fora do caminho auditado. O seed.ts fazia o mesmo — e ele roda contra banco já semeado (BRABO_FORCE_SEED=1 no bootstrap.sh do k8s), então corrigir um preço no seed trocava o número em silêncio. Os dois passaram a auditar; o seed reusa o UpdateModelPricingUseCase em vez de repetir a lógica, e o chama antes do upsert — depois dele, os dois valores já seriam iguais e a auditoria trataria como nada a fazer. :::

:::note Não é evento da outbox model_price_changes é tabela própria, não uma linha em outbox_events. O Engine.Outbox.Drain.run_once/0 filtra por aggregate_type == "session" — uma linha de preço ali ficaria com processed_at nulo para sempre e poluiria a métrica de atraso da outbox. É um log de domínio imutável, como session_events. :::

Embeddings​

A segunda operação do contrato (ADR 0075), e a única além de chat que gasta tokens. Só existe onde capabilities.embeddings é true.

const { vectors, dimensions, model, inputTokens, estimated } =
  await provider.embed(['primeiro trecho', 'segundo trecho'], {
    model: 'nomic-embed-text',
  });

É em lote, e a ordem é contrato. Um índice recebe N trechos de uma vez, e a posição é o único vínculo entre entrada e vetor. Daí a garantia que mais importa: um vetor por entrada, ou erro — nunca uma lista mais curta. Uma resposta parcialmente recusada é indetectável depois; o defeito só apareceria na busca, longe da causa. Pelo mesmo motivo o contrato recusa vetor vazio, dimensões diferentes dentro da mesma resposta e lista de entradas vazia.

O erro lança, não vira chunk. No chat o erro vira chunk porque o turno já gastou tokens e o metering precisa acontecer; aqui não há nada a preservar — ou o provider devolveu os vetores e cobrou, ou não devolveu e não cobrou. A taxonomia de code é exatamente a mesma da tabela abaixo.

dialetoendpointcorpo da resposta
base OpenAI-compatívelPOST /embeddings{ data: [{ index, embedding }], model, usage.prompt_tokens }
OllamaPOST /api/embed{ model, embeddings: number[][], prompt_eval_count }

O index da OpenAI é o vínculo com a entrada, e a doc não promete ordem — por isso a base ordena por ele antes de devolver. O campo dimensions de EmbeddingOptions (reduzir o vetor) só existe na OpenAI; o Ollama o ignora, em vez de falhar, porque ali a dimensão é do modelo — e o resultado sempre declara a dimensão REAL do que voltou.

O Ollama também é o único que publica a camada do MODELO: /api/tags traz capabilities: ["embedding"] e details.embedding_length por linha, e é daí que vêm supportsEmbeddings e embeddingDimensions no catálogo. :::note O gasto ainda não é medido embed devolve inputTokens/estimated para alimentar o metering, e calculateCostMicros(input, 0, …) já funciona (embedding não tem saída em tokens). O que falta é estrutural: token_usage.session_id é NOT NULL, e indexar um repositório não acontece dentro de sessão. Corte declarado no ADR 0075 — pertence à onda que implementa o consumidor. :::

Ninguém decide nada casando substring da mensagem do fornecedor: a decisão é tomada pelo code do chunk. As classes moram em apps/api/src/domain/llm/llm-provider-errors.ts.

Teto de inatividade​

O teto não é sobre duração total, é sobre silêncio. Um turno legítimo pode demorar (um modelo processa milhares de tokens de prompt antes do primeiro token), mas nunca fica calado. É a lição do ADR 0020, em que o fetch desistia nos 300s fixos do undici com um "fetch failed" opaco e o agente gravava "o modelo parou" para uma requisição que nunca foi respondida.

O Ollama tem env própria porque um modelo local tem outra ordem de grandeza de latência até o primeiro token.

A base OpenAI-compatível​

OpenAICompatibleProvider implementa o dialeto /chat/completions uma única vez. Nove providers nascem dela: OpenAI (a primeira instância), OpenRouter (Fase 11a, o hub) e os cinco da Fase 11b — NVIDIA NIM, Together, DeepInfra, Bitdeer, Vultr. Todos mudam baseUrl, o cabeçalho de autenticação e flags — nunca o parsing (a única exceção que se provou necessária foi o parseCatalogo próprio de cada um, quando a capability é true — ver as seções por provider abaixo).

interface OpenAICompatibleFlags {
  streamOptionsIncludeUsage: boolean;
  maxTokensField: 'max_tokens' | 'max_completion_tokens';
}

O campo de teto de saída vai em TODA chamada (RN-734): options.maxTokens quando quem chama o define, senão MAX_TOKENS_PADRAO (4096, o mesmo default do provider Anthropic). Sem o campo, o OpenRouter reserva crédito para a saída MÁXIMA do modelo por chamada em voo e responde 402 mesmo quando a chamada real caberia no saldo. Uma resposta cortada por esse teto ainda não é narrada: este dialeto não lê finish_reason: "length".

Quando o modelo raciocina (models.supports_reasoning) e a configuração do provider tem campoDeRaciocinioDesligado (hoje só o OpenRouter), o teto de saída vira saída visível + ORCAMENTO_DE_RACIOCINIO (4096), porque o raciocínio conta dentro de max_tokens (RN-741). Nenhum campo de raciocínio é enviado só porque o modelo aceita o parâmetro (RN-782): a medição paga de 2026-10-10 (AT-467) mostrou reasoning: { max_tokens } LIGANDO o raciocínio no anthropic/claude-haiku-4.5 (74% das chamadas, 2,8x o custo) e sendo IGNORADO pelo anthropic/claude-haiku-5.5 (1024 pedidos, 8192 gastos). Os dev agents de execução (dev-<modulo>, não o dev-lead) recebem reasoning: { enabled: false } (RN-783, decisão do dono): 0 de 8 respostas cortadas, -42% de custo no Haiku 5.5. A ajuda da faceta "pensamento" do catálogo de modelos diz isso. O provider Anthropic direto não envia thinking, então ali o modelo não raciocina.

Exceção por modelo (RN-914, ADR 0223): com models.reasoning_budget preenchido (curado à mão; hoje só qwen/qwen3.7-flash, 2048, provado em 22/10) o corpo leva reasoning: { max_tokens: N } e o teto vira saída visível + N. O deepseek/deepseek-v4.1-flash ignorou max_tokens e effort na medição: o limite dele (2048, migração 0075) é imposto ABORTANDO o stream quando o delta.reasoning passa de caracteres/4 > N, com custo estimado e reconciliado depois (RN-915, ADR 0224). effort nunca é enviado, e o limite não garante a tool call.

Cada flag existe porque um provider real diverge. Não acrescente flag sem um provider que precise dela.

Uma mensagem system no fim da conversa (AT-161)​

A linha do system tardio existe porque a orientação de idioma da AT-081 prevê enviar uma mensagem efêmera role: "system" no FIM da lista, em toda chamada de um turno — depois de user na primeira chamada, depois de tool nas seguintes. A suite de contrato responde, para cada um dos onze providers, onde essa mensagem pousa no corpo serializado: cada harness declara posicaoDoSistemaTardio e o contrato a confere nas duas posições, além de o texto aparecer exatamente uma vez e o resto da conversa manter a ordem (apps/api/test/contract/llm-provider.contract.ts).

provideradaptadoronde o system tardio pousa
OpenAI, OpenRouter, NVIDIA NIM, Together, DeepInfra, Bitdeer, Vultr, 9Router, OpenCode Zenbase compatível (toWireMessage)fim de messages, role: "system"
Ollamapróprio (messages enviado como está)fim de messages, role: "system"

Nenhum adaptador a descarta nem a duplica. O que o servidor falso não sabe dizer é se o provider REAL aceita esse corpo — ele aceita qualquer coisa. Isso é um smoke manual à parte, apps/api/test/infrastructure/llm/sistema-tardio.smoke.spec.ts, um describe por provider, cada um condicionado à mesma chave que os smokes de aceite usam (mais ANTHROPIC_TEST_KEY; o Ollama por OLLAMA_SISTEMA_TARDIO_SMOKE=1). Quais já rodaram está registrado no aceite de providers. Sem essa rodada, um provider não está provado quanto a aceitar system tardio — a regra dos ADRs 0041/0042.

Observação, não medida (lacuna 2 da AT-081): na Anthropic o içamento faz a orientação mudar o bloco system do topo, que vem ANTES da conversa — então toda mudança no texto dela muda o prefixo da requisição, e com ele qualquer prompt caching que o prefixo teria. Cache não é observável no produto hoje (AT-082), então isto fica registrado, não quantificado.

OpenRouter — o primeiro hub (Fase 11a)​

OpenRouterProvider é OpenAICompatibleProvider com openrouterConfig() (apps/api/src/infrastructure/llm/openrouter-provider.ts). Ele declara listModels: true — a única peça de código que muda quando uma capability liga é a configuração; o SyncModelCatalogUseCase já cuida do resto.

Peculiaridades encontradas e testadas (test/infrastructure/llm/openrouter-provider.contract.spec.ts):

  • Cabeçalhos próprios: HTTP-Referer (de API_PUBLIC_URL) e X-Title: "Brabo" — opcionais pela doc oficial (atribuição/ranking no site do OpenRouter), sempre enviados porque não custam nada;
  • Id de modelo prefixado pelo upstream (openai/gpt-4o-mini, anthropic/claude-3-5-sonnet): o prefixo é o fornecedor PEDIDO, não o que respondeu — ver extrairUpstreamProvider abaixo;
  • Catálogo com preço na própria linha: GET /v1/models devolve pricing.prompt/pricing.completion como STRING decimal em USD por token, ao contrário do padrão simples só com id { data: [{ id }] } da OpenAI. parseCatalogoOpenRouter converte para micro-USD por milhão (* 1e12, arredondado — a coluna é bigint);
  • Erro NO MEIO do stream: o OpenRouter aceita a conexão e começa a mandar texto antes de saber se o provider real por trás vai falhar — um modo de falha que a OpenAI não tem, porque não roteia para infraestrutura de terceiros. O frame vem como {"error":{"code":"...","message":"..."},"choices":[...]}; um campo error verdadeiro é o sinal. Código numérico usa o mesmo normalizeHttpStatus da base; código em string é mapeado por substring (mapearCodigoDeFrame) com upstream como default seguro — nunca silêncio, nem para código fora do mapa;
  • Custo real em usage.cost (ADR 0188, RN-665): o último frame do stream traz o que o hub cobrou, em USD; extrairCustoRealOpenRouter o converte em micro-USD e o metering o grava como o número. Com is_byok: true o campo é a taxa do hub, não a inferência, então NÃO é lido e a linha cai no catálogo. model (a versão datada para a qual um alias como ~deepseek/deepseek-flash-latest resolveu) e id (gen-…) são lidos pela base para todo provider do dialeto;
  • Alias de roteamento livre (~…) é sincronizado mas não pode ser curado (AT-271, RN-679): um id como ~deepseek/deepseek-flash-latest sempre redireciona para o modelo mais novo da família, o preço dele no catálogo é preço de vitrine, e a conta vem de qualquer upstream que tenha servido a chamada. A sincronização o mantém no catálogo (tirá-lo marcaria unavailable um já curado); ativá-lo é 422 alias_de_roteamento_livre, e a leitura da curadoria o marca com freeRoutingAlias. Um ativado antes da regra continua ativo e pode ser desligado — desligado, não volta;
  • Teste de conexão: GET /key (doc oficial) valida a chave sem gastar tokens numa chamada de chat de verdade. É o primeiro LLMCredentialConnectionTester do lado de LLM. Desde o ADR 0050 ele não roda no cadastro: a credencial é cifrada e guardada sem julgamento, e a verificação é a ação explícita POST /users/me/credentials/{provider}/test, sobre a chave já guardada. Um provider sem teste declarado (hoje: ollama/anthropic/openai) devolve nao_suportado — nunca um ok falso (RN-055).

O teste de aceite com credencial real que a Fase 11a exige — cadastro, sincronização povoando o catálogo, ativação curada e uma sessão de chat ponta a ponta com custo congelado em token_usage — é test/infrastructure/llm/openrouter-provider.smoke.spec.ts. Ele nunca roda em CI: sem OPENROUTER_TEST_KEY no ambiente, o describe inteiro é pulado com um aviso. Mesmo molde dos smokes de git contra API real (github-provider.smoke.spec.ts, gitlab-provider.smoke.spec.ts).

Hubs e custo real​

Num hub (OpenRouter), quem aparece na chamada é o hub, mas quem custa é o provider que de fato serviu. O metering grava os dois:

  • ChatUsageChunk.upstreamProvider — o provider o preenche quando o hub o informa;
  • token_usage.upstream_provider — texto livre e anulável. Não é enum: o conjunto é do hub, muda sem aviso e não cabe a nós versioná-lo. null quer dizer "não veio de hub, ou o hub não informou";
  • as métricas brabo_llm_tokens_total e brabo_llm_cost_micros_total ganharam o rótulo upstream_provider, e o dashboard executivo tem um painel de custo por provider subjacente. Sem hub, o rótulo repete o próprio provider — com rótulo vazio, sum by (upstream_provider) mostraria só o que passou por hub e faria parecer que o resto não custou nada.

Ler o campo do frame é um hook de configuração na base (extrairUpstreamProvider), não um if dentro do parsing: cada hub põe a informação num lugar diferente, e a regra da fase é que particularidade de provider vira configuração.

models.manual_pricing marca um preço digitado a partir da doc do provider em vez de sincronizado. A sincronização do catálogo não sobrescreve o preço de uma linha marcada sem decisão explícita — e quando o catálogo remoto não informa preço, o valor guardado é preservado em vez de zerado: campo ausente quer dizer "o provider não disse", nunca "é de graça".

Exemplo: o mesmo modelo, hub × direto​

A promessa da Fase 11a ("custo comparável entre 'mesmo modelo via hub' e 'direto' é consultável") só vira uso real quando o MESMO modelo aparece dos dois lados — hoje é o caso de qualquer modelo que OpenAI/Anthropic publiquem e que também esteja no catálogo do OpenRouter (por exemplo, GPT-4o):

# Razão de custo: servido via OpenRouter vs. servido direto pela OpenAI,
# no mesmo período. > 1 quer dizer que o hub saiu mais caro que o direto.
sum(rate(brabo_llm_cost_micros_total{provider="openrouter", upstream_provider="openai"}[1h]))
  /
sum(rate(brabo_llm_cost_micros_total{provider="openai"}[1h]))

Este é o gancho que upstream_provider habilita — hoje sem consumidor automático. A leitura pretendida (registrada como semente, não implementada) é o Psicólogo um dia sugerir "este modelo sai mais barato direto que via hub" a partir dessa mesma métrica.

A suite de contrato​

apps/api/test/contract/llm-provider.contract.ts roda a mesma bateria contra qualquer implementação, como a suite de git faz desde a Fase 2. A divisão é o ponto: o contrato é dono das asserções, o harness é dono do dialeto.

Um provider novo só precisa escrever o harness — traduzindo cada cenário para o próprio formato de fio — e herda os testes de stream com frame partido, usage presente e ausente, tool calling, os quatro erros e o servidor calado. O servidor falso é um node:http de verdade numa porta efêmera, não um mock de fetch: o que está sob teste é justamente o comportamento do socket.

Tool calling e o resgate do engine​

O ToolCallRecovery do engine (ADR 0020) recupera chamadas que um modelo pequeno escreveu em prosa em vez de usar o campo tools. É resgate, não licença: depende de o modelo acertar o formato por acaso e falha calado quando não acerta. Por isso vincular a um agente um modelo sem tool calling nativo é recusado no domínio, e não apenas desencorajado.
