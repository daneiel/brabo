RN-040 — Binding агента требует нативного tool calling​

Привязка модели к агенту (scope = 'agent') разрешена, только если у модели есть supports_tool_calling. Агент существует только внутри ToolLoop, а ToolLoop работает, только если модель умеет запрашивать инструменты; без этого сбой проявился бы позже как «агент остановился, не закончив», — ровно та диагностика методом исключения, которую ADR 0020 запретил. Отказ — это 422, и сообщение указывает на фильтр "aptos para agentes" — без этого указания правило превращается в тупик.

ToolCallRecovery в engine восстанавливает вызовы, которые модель написала прозой, но это спасение, а не лицензия: оно зависит от того, угадает ли модель формат случайно.

Проверяет только agent. workspace и project — это fallback человеческого чата, а session — разговор; ни один из них не запускает ToolLoop, и их блокировка запретила бы в продукте модели только для чата. Агент context-manager покрыт по построению: это slug внутри области agent, а не собственная область.

Дополнительная заметка — фильтр стал приходить ОТМЕЧЕННЫМ, и включает его ОБЛАСТЬ. Абзац выше говорит, что отказ указывает на фильтр "aptos para agentes", «иначе правило становится тупиком» — и долгое время оно им было: prop, открывающий селектор с отмеченным фильтром, существовал с Фазы 9c, и ни один экран production его не передавал. Селектор агента открывался, предлагая модель только для чата, клик по которой существовал лишь для того, чтобы быть отклонённым. Оба экрана, записывающие в проверяемую область, начинают открываться отфильтрованными — ModelsSection (агент) и AreaModelsSection (область), — и правило того, кто включает, — не экран, а assertModelFitsBindingScope: там, где api ОТКЛОНЯЕТ, фильтр приходит отмеченным; там, где не отклоняет, выбирает человек. Поэтому селектор СЕССИИ остаётся без фильтра — отметка там скрыла бы модель, которую api принимает. Это не устраняет 422: фильтр покрывает одну из трёх причин, а две другие (RN-043 — отключена в workspace, исчезла у провайдера) остаются достижимыми, при этом недоступная всё ещё ПЕРЕЧИСЛЕНА и помечена; исход отказа из RN-470 по-прежнему то, что сообщает, что произошло. И это НАЧАЛЬНОЕ состояние checkbox, а не замок: снятие отметки снова перечисляет всё.

Следствие: действующее значение, которое скрывает фильтр, ПРОГОВАРИВАЕТСЯ. workspace и project никогда не требовали tool calling, а маршруты, разрешающие binding агента или области, вызывают ResolveModelBindingUseCase без exigeToolCalling — так что чат-модель по умолчанию на этих уровнях разрешается нормально и становится действующей для строки. С отмеченным фильтром триггер показывал имя, которого открытый список не содержал, без какой-либо отмеченной опции. Picker теперь называет модель и причину; он МОЖЕТ назвать причину, потому что фильтр там только один. Когда весь список становится пустым, говорит по-прежнему текст пустого списка, который уже велит снять отметку, — два предупреждения об одном checkbox были бы шумом.

Исправление факта, а не текста выше: "Only agent validates" описывает Фазу 9a. Начиная с ADR 0064 area входит в ТУ ЖЕ проверку — это не общий fallback, единственный потребитель модели области — её агент (RN-102), — и именно поэтому экранов, включающих фильтр, ДВА.

RN-041 — Количество токенов, не сообщённое провайдером, помечается как оценочное​

Когда ответ провайдера не несёт usage, OpenAI-совместимая база считает локально токенизатором и выпускает chunk с estimated: true. Число всё ещё годится для выставления счёта, но метка сохраняет разницу между «провайдер сказал ноль» и «провайдер ничего не сказал» — и это позволяет UI квалифицировать стоимость, а не показывать значение без происхождения.

Два других провайдера расходятся, и расхождение нормализуется, а не прячется: Ollama просто не выпускает usage без строки done; Anthropic не может опустить подсчёт, потому что usage обязателен в message_start его протокола. Все три ответа — в docs/reference/llm-providers.md.

  • Где: apps/api/src/infrastructure/llm/openai-compatible-provider.ts:167
  • Тест: test/contract/llm-provider.contract.ts (сценарий sem_usage, выполняемый против трёх провайдеров)
  • Источник: ADR 0041

RN-042 — Metering регистрирует, кто ОБСЛУЖИЛ вызов, а не только через что он вошёл​

Когда вызов проходит через hub, который сообщает реального провайдера, token_usage регистрирует этого провайдера в upstream_provider, помимо провайдера входа. Без hub — или с hub, который не сообщил, — поле равно null, никогда пустой строке: запрос стоимости по провайдеру должен различать «не проходил через hub» и «проходил через hub, и hub не сказал».

В метриках метка upstream_provider повторяет самого провайдера, когда hub нет, так что sum by (upstream_provider) продолжает суммировать всю стоимость.

  • Тест: test/application/use-cases/llm/record-llm-usage.use-case.spec.ts

RN-681 — История и правило, похожие на существующие, порождают ПРЕДУПРЕЖДЕНИЕ через embedding, никогда отказ; расход проверки — собственная строка metering​

После записи истории (create_story) или бизнес-правила (emit_artifact с business_rule) api сравнивает её ЗАГОЛОВОК с заголовками существующих того же типа в ПРОЕКТЕ, по косинусу между векторами модели embedding из RAG, и ПРЕДУПРЕЖДАЕТ, когда ближайший находится на пороге или выше.

  1. Предупреждение, никогда отказ. Элемент уже существует, когда выполняется проверка. Предупреждение возвращается агенту в результате инструмента — фраза называет похожий элемент, id и число — и остаётся в логе как backlog.semantic_duplicate_warned. ТОЧНЫЙ дубликат по-прежнему отклоняется раньше, согласно RN-080 и RN-081, и поэтому одинаковый нормализованный заголовок исключается из сравнения.
  2. Порог — 0,80, и это ОТПРАВНАЯ ТОЧКА, не откалиброванная (ADR 0198, как и веса ADR 0080): реальные векторы пары из находки R и пар, не являющихся дубликатами, не удалось записать в окружении, где родилось правило. Доказательство запускается само, когда будет записан vetores.json; до тех пор оно ПРОПУСКАЕТСЯ с предупреждением.
  3. Без провайдера embedding проверка ПРОПУСКАЕТСЯ, и об этом ГОВОРИТСЯ — отсутствие capability, демон недоступен, timeout: backlog.semantic_duplicate_check_skipped с причиной в логе и во фразе агенту. Никогда не роняет эмиссию.
  4. Расход входит в metering собственной строкой: актор system/duplicata-semantica, провайдер и модель RAG, нулевой вывод, цена каталога, когда модель в нём есть. Это ЕДИНСТВЕННОЕ исключение из среза ADR 0075 — индексация и поиск RAG остаются вне, — и оно уместно, потому что эмиссия происходит внутри сессии.
  5. Потолки: 100 самых свежих существующих (результат говорит, сколько из скольких, когда обрезает) и 10 s по часам на всю проверку.

RN-666 — Metering записывает, сколько входа пришло из кэша и сколько вывода было рассуждением​

Каждая строка token_usage записывает две ЧАСТИ, которые провайдер сообщает в usage диалекта OpenAI: cached_input_tokens (prompt_tokens_details.cached_tokens — сколько из input_tokens было отдано из кэша, по доле цены) и reasoning_tokens (completion_tokens_details.reasoning_tokens — сколько из output_tokens было рассуждением).

  1. Часть, никогда не сумма. input_tokens/output_tokens остаются итогами, которые сказал провайдер, и уже включают части; к ним ничего не прибавляется, и никакая стоимость по ним не пересчитывается — число стоимости берётся из RN-665.
  2. «Не сказал» — это не ноль. null = провайдер не сообщил; 0 = сообщил, что не было. Значение, не являющееся неотрицательным целым, — «не сказал».
  3. Измерение говорит, сколько было кэша. medir-execucao.ts начинает показывать по агенту прочитанный кэш и рассуждение с процентом от итога, ТОЛЬКО по вызовам, которые сообщили (и в скольких, когда не во всех), и «не измерено», когда не сообщил ни один, — а также в скольких вызовах стоимость реальная.
  4. Читается для каждого провайдера диалекта, потому что оба поля — от самой OpenAI; кто их не присылает, остаётся с null. Anthropic сообщает кэш в своём протоколе (cache_read_input_tokens), и это здесь НЕ читается — остаётся null, объявлено; Ollama не сообщает.

RN-665 — Реальная стоимость, которую возвращает провайдер, — это число metering; каталог остаётся там, где её нет​

Решение владельца (30.09): реальная стоимость становится числом. Когда ответ вызова LLM говорит, сколько провайдер взял, — в OpenRouter это usage.cost в финальном кадре stream, — это значение является token_usage.cost_micros строки, тем, что ход возвращает engine (и цикл прибавляет к локальному бюджету), тем, что увеличивает бюджеты проекта, сессии и области, и тем, что суммируют отчёты о расходах. Без него число даёт замороженная цена каталога, как в ADR 0042.

  1. Одно правило, три пути. RunLlmTurnUseCase, StreamLlmTurnUseCase и SendChatMessageUseCase проходят через одну и ту же custoDaChamada; второго правила нет.
  2. Неявная цена, помеченная. При реальной стоимости обе колонки цены записывают стоимость ÷ токены (одно и то же значение: провайдер возвращает ОДНУ стоимость) и price_implicit = true — что сохраняет токены × цена = стоимость (RN-044), не изображая табличную цену. Без реальной стоимости price_implicit = false, и колонки — из каталога.
  3. Каталог рядом. catalog_cost_micros записывает, что взяла бы цена каталога, только в строках, чьё число реальное (null в остальных), — это расстояние между оценкой и счётом, построчно.
  4. estimated по-прежнему говорит о ТОКЕНАХ (RN-041). Строка с реальной стоимостью имеет estimated = false, потому что стоимость приходит только с usage провайдера; СТОИМОСТЬ как реальную помечает price_implicit.
  5. То, что ответ сказал о себе, записывается. resolved_model_name (model кадра — разрешённый alias) и generation_id (id, gen-… в OpenRouter), для каждого провайдера диалекта. model_name остаётся значением каталога, измерением отчётов.
  6. Стоимость читает только тот, кто доказал. Hook extrairCustoReal существует только в OpenRouter; провайдер без него игнорирует присутствующий usage.cost. Стоимость, не являющаяся конечным неотрицательным числом, — «не сказал» (настоящий ноль — реальная стоимость), а при is_byok: true стоимость НЕ читается: это комиссия hub, а инференс оплачивается отдельно, — строка падает на каталог.

RN-679 — Курирование отклоняет alias свободной маршрутизации OpenRouter​

Решение владельца (01.10): alias ~ не входит в курирование — только модель с фиксированным upstream. Alias свободной маршрутизации OpenRouter (id, начинающийся с ~, например ~deepseek/deepseek-flash-latest), «всегда перенаправляет на последнюю модель семейства»: каталог публикует ВИТРИННУЮ цену (при реальном использовании 29.09 — цену самого дешёвого endpoint семейства), список endpoints приходит пустым, а берёт деньги upstream, который обслужил. Нет upstream, относительно которого замороженная цена ADR 0042 что-либо означала бы. Альтернатива — цена по upstream — была отклонена.

RN-043 — Обнаруженная модель входит отключённой; исчезнувшая модель помечается, никогда не удаляется​

У синхронизации каталога три исхода, и ни один не разрушителен:

  1. Новая модель входит без строки курирования в каком-либо workspace, и отсутствие строки И ЕСТЬ отключённое состояние. Каталог провайдера содержит сотни строк — выгрузить их как активные сделало бы выбор невозможным и включило бы дорогую модель без чьего-либо решения. Активация — курирование owner, и действует только в его workspace (RN-052).
  2. Модель, исчезнувшая из удалённого каталога, получает availability = 'unavailable' и остаётся в таблице: model_bindings и token_usage указывают на строку, и её удаление унесло бы вместе историю стоимости.
  3. Вернувшаяся модель возвращается в available с нетронутым курированием — выбор owner переживает временное отсутствие у провайдера.

Две оси намеренно независимы: курирование — решение человека, availability — наблюдение провайдера. Ни одна не пишет в другую — и начиная с ADR 0049 они даже не живут в одной таблице, так что у синхронизации нет поля курирования, которое она могла бы растоптать, даже если бы захотела.

Три следствия в остальной системе:

  • НОВЫЙ binding для неактивной или недоступной модели отклоняется в домене (ModelNotBindableError, 422). Уже существующие bindings остаются;

  • каскад resolveBinding пропускает недоступного кандидата, записывает пропущенное в skipped и — когда ход несёт инструменты — повторно проверяет supports_tool_calling на ВСЕХ уровнях. Без этого fallback посадил бы агента на модель только для чата и молча нарушил бы RN-040;

  • упавший провайдер ничего не делает недоступным: 401 — это «не знаю, что там есть», а не «там ничего нет». Провайдер пропускается, с ИСТОЧНИКОМ сбоя (infra | modelo) в отчёте — никогда диагностика методом исключения.

RN-047 — Circuit breaker dev agent: N последовательных блокировок его останавливают, не сжигая бюджет в цикле​

Каждый dev agent ведёт счётчик (dev_agent_states.consecutive_blocked) того, сколько задач подряд ЗАВЕРШИЛИСЬ blocked — локально (в ToolLoop) или удалённо (исчерпан потолок исправлений gate). При достижении потолка проекта (max_consecutive_blocked, по умолчанию 3) агент останавливается в idle_tripped, не пытаясь взять следующую задачу. Одобренный терминальный исход обнуляет счётчик; отдельная заблокированная задача идёт обычным путём (возвращается с диагнозом, доступна человеку для разблокировки) — breaker имеет дело с ПОСЛЕДОВАТЕЛЬНОСТЬЮ, а не с задачей.

Единственный выход из idle_tripped — явное перевзведение (POST .../agents/:agentId/rearm, роль developer): оно обнуляет счётчик, и агент снова пытается брать задачи. Автоматической разблокировки нет — тот же принцип, что у MarkTaskBlockedUseCase/unblock, применённый к последовательности, а не к задаче. Перевзведение агента, который не заблокирован, — 409, а не молчаливый успех: событие dev.rearmed неизменяемо, и его регистрация для несостоявшегося перевзведения была бы ложью в event log.

Блокировка, приходящая ИЗВНЕ агента (например, внутренний сбой QaLeadServer), тоже должна его будить — поэтому выпуск task.gate_resolved живёт в MarkTaskBlockedUseCase, воронке, через которую проходит каждая блокировка, а не в RecordGateVerdictUseCase, который видит лишь их часть. Без этого агент навсегда остался бы в awaiting_gate, с мёртвой задачей и никогда не растущим счётчиком breaker.

Перезапуск engine с агентом в working не засчитывается в счётчик: удерживаемая задача блокируется с диагнозом перезапуска, но эта блокировка — не агент, «сжигающий потолок», а падение инфраструктуры. Счётчик растёт, только когда сам цикл dev↔gate производит настоящий blocked.

RN-048 — Продвижение story по умолчанию принадлежит пользователю; режим меняет того, кто запускает, никогда то, что проверяется​

projects.story_promotion выбирает, КТО продвигает story из draft в ready:

  • manual: PO доводит story до полноты, и она остаётся draft с stories.proposed_ready = true. Ни одна из её задач не может быть взята — claimNext требует story.status = 'ready', — и продвигает её пользователь, по отдельности или пакетом, из Backlog.
  • auto (значение по умолчанию для нового проекта начиная с RN-659): PO продвигает сам, завершив полную story. Таким было поведение до Фазы 12c; manual был значением по умолчанию 12c до RN-659 (миграция 0065), которая изменила только значение колонки по умолчанию — проекты, созданные в промежутке, остаются manual.

Режим меняет триггер, а не критерий. Оба пути проходят через assertPromotable — готовность (RF/DoD/DoR/правило) и модули, разрешённые относительно действующего module_map, — и именно это фиксирует тест симметрии в story-promotion.spec.ts: для каждой story isPromotable согласуется с тем, что выбрасывает assertPromotable. До этой фазы проверка была дублированной и асимметричной (создание вызывало canBecomeReady, переход вызывал assertReady + assertModulesResolved): две двери в одно состояние, с разными замками. Чтобы сделать триггер настраиваемым, сначала пришлось их объединить, иначе «продвинуть через UI» и «продвинуть при создании» были бы разными правилами с одним именем.

Неполная story никогда не предлагается. proposed_ready включается, только когда story уже прошла бы проверку, — предложение того, что домен отклонил бы, переложило бы работу PO на пользователя под видом решения.

Отказ возвращает story PO: записывает returned_reason/returned_at, выключает proposed_ready, выпускает backlog.story_promotion_returned и внедряет причину как ЗАКРЕПЛЁННОЕ сообщение в сессии PO, с той же формулировкой приоритета, что и у gate, возвращённого dev (урок ADR 0020). Отказ записывается до обращения к engine, и сбой engine его не отменяет — это противоположно порядку перевзведения в RN-047, и по причине: там событие утверждает что-то О engine, здесь — что-то о пользователе, что верно независимо от того, дежурит ли PO, чтобы это услышать.

Пакетное продвижение не «всё или ничего»: каждая story — своя транзакция, и та, что потеряла готовность между предложением и решением, возвращается failed с причиной, не роняя остальные, которые пользователь только что просмотрел.

Событие backlog.story_transitioned регистрирует реального актора — user при ручном продвижении, agent/po при автоматическом. Event log неизменяем, и его читает аудит: запись PO в решении пользователя стёрла бы ровно тот человеческий этап, который правило существует, чтобы вернуть.

Миграция 0033 делает направленный, а не слепой backfill: колонка рождается manual, и каждый уже существовавший проект переводится в auto. Новое значение по умолчанию действует для тех, кто придёт позже; идущий проект не может перестать производить из-за deploy.

RN-050 — Без открытого PR ни один gate не открывается​

Dev agent предлагает commit, push и PR и читает исход каждого. Он открывает gate, только если все три выполнены. Если один остался pending — автономия агента в require_approval, — он переходит в awaiting_approval, удерживая worktree, и не открывает никакого gate.

Без этого gate открывался в любом случае, и ущерб был молчаливым: QA прочёсывает worktree, а не PR; нашёл файлы — одобрил; SecOps одобрил; задача закрылась как завершённая — без единой закоммиченной строки и без какого-либо PR. Только потом, одобряя commit, пользователь увидел бы, как действие падает (с пустым диагнозом, потому что System.cmd в удалённом каталоге возвращает {"", 2}).

Агента освобождает task.pr_settled, выпускаемый api, когда pr_open приходит к терминальному исходу: opened: true открывает gate; opened: false (отклонено или сбой) возвращает задачу с диагнозом, вместо того чтобы оставить агента вечно ждать gate, который никто не откроет.

Отклонённый PR не засчитывается в circuit breaker из RN-047: решение было за пользователем, а не за агентом, сжигающим потолок, — тот же принцип, что у восстановления после перезапуска.

Это правило также устраняет D5 (worktree, переработанный при ожидающем одобрении) как следствие: worktree освобождается только в gate_resolved, gate открывается только после PR, а PR открывается только после commit и push.

RN-051 — Цена, набранная вручную, побеждает каталог провайдера​

Строка models с manual_pricing = true содержит число, которое кто-то набрал, прочитав документацию провайдера. Синхронизация каталога его не трогает — даже когда удалённый каталог приносит собственную цену. Это всегда говорила схема («тот, кто синхронизирует цену, НЕ МОЖЕТ перезаписать строку, помеченную здесь, без явного решения»), и этого не делал код: удалённое всегда побеждало, когда приносило цену, и следующая синхронизация отменяла исправление того, кто поправил неверное число.

Позволить удалённому каталогу его перезаписать значило бы заменить одно известное приближение другим, без чьего-либо решения.

НОВАЯ модель рождается с флагом из каталога, а не с фиксированным значением по умолчанию: обнаруженная с ценой — manual_pricing = false (источник — синхронизация, и именно она поддерживает строку актуальной); обнаруженная без цены — true: строка ждёт, что кто-то наберёт цену, и пометка уже защищает это число от первого каталога, который решит сообщить цену.

RN-052 — Курирование моделей действует только в workspace, который его решил​

Включение или выключение модели в селекторе — решение этого workspace, и оно не доходит до соседа. Сам каталог остаётся глобальным — имя, цена, окно и capabilities — факты провайдера, одинаковые для всех, и их дублирование по workspace создало бы N истин об одной модели, а также разрезало бы token_usage.model_id пополам.

До этого models.is_active был колонкой на всю установку: кто кликал «активировать», решал за все workspaces, и экран никак этого не показывал. Практическим эффектом был workspace, включающий дорогую модель в селекторе другого, — и расход, появляющийся в бюджете того, кто ничего не решал.

Три производных правила:

  1. Отсутствие строки — отключённое состояние. Нет отдельного состояния «никогда не решалось»; модель, которую обнаружила синхронизация, не имеет строки и не появляется в селекторе (RN-043).
  2. Отключение — это UPDATE, а не DELETE. Удаление строки удалило бы также, кто решил и когда. Чтения трактуют оба случая как неактивные; запись существует для того, кто проводит аудит.
  3. Области agent и session не проверяют курирование. Ни у одной нет привязки к workspace — binding агента идёт по глобальному slug. Проверка получает null и проверяет только доступность, оставляя пробел явным, вместо того чтобы угадывать workspace.
  • Где: apps/api/src/db/schema/llm.ts (workspace_models), apps/api/src/application/use-cases/llm/set-models-active.use-case.ts, apps/api/src/application/use-cases/llm/set-model-binding.use-case.ts (workspaceDoEscopo)
  • Тест: test/application/use-cases/llm/set-models-active.use-case.spec.ts (activating in one workspace does NOT turn on the model in its neighbor)
  • Источник: ADR 0049

RN-067 — Каждая сессия рождается, выпуская session.created​

RN-068 — Dev agent читает worktree, не спрашивая разрешения​

Активация исполнения засеивает два семейства команд в allow проекта: чтение собственного worktree (ls, pwd, find, cat, head, tail, grep, wc, echo, git status, git diff, git log) и build и тест.

Второе уже существовало: ReportDone позволяет открыть PR только после terminal с exit 0. Первое было добавлено, потому что агент смотрит перед тем, как строить, а без этого не мог даже начать.

Причина конкретна. Ожидающий инструмент :pipeline возвращает proposed_action <id> status pending как РЕЗУЛЬТАТ — а не вывод команды, — и ToolLoop идёт дальше. В только что провизионированном репозитории каждый ls -la агента попадал на одобрение, ничему его не учил и сжигал итерацию. При реальном исполнении исходом был toolloop.limit_reached {iteration: 8, max_iterations: 8}, задача, заблокированная с "limite de iterações atingido", без единой написанной строки — а одобрения, данные пользователем, пришли после исчерпания цикла.

Освобождение чтений не ослабляет конвейер, и именно это утверждает тест: deny побеждает allow, BUILTIN_DENY_PATTERNS остаются активными, сопоставление идёт по префиксу ТОКЕНА (разрешённый ls не разрешает lsof), а составная команда требует совпадения КАЖДОГО сегмента — ls && rm -rf / не проходит благодаря ls.

Allowlist — смягчение, а не решение: это список предусмотренных команд, а модель выдумывает команды. Структурное исправление — чтобы агент ЖДАЛ решения, а не сжигал итерации, — находится в ADR 0052.

  • Тест: test/domain/actions/dev-terminal-patterns.spec.ts (allows ls -la; a composite command doesn't hitch a ride on the allowed segment)

RN-143 — Подкоманда git только для чтения разрешена, лишь будучи закреплённой флагом, делающим чтение однозначным, никогда по одному глаголу​

RN-070 — Каждый объявленный gate указывает на доказательство, которое его подтверждает​

Ни одна запись docs/gates.yml не существует без evidencia, и реестр не может утверждать больше, чем проверяет: gate block требует verificacao: script, а gate planned не несёт доказательства того, что ещё не произошло.

Доказательство — это локатор, а не проза: event_log несёт типы событий и фильтр payload, отличающий их от соседей; teste и ci несут путь, и исчезнувшая цель ПРОВАЛИВАЕТ. Это тот же режим отказа, который docmap называет мёртвым glob, — правило, которое никогда не срабатывает и изображает покрытие.

Три типа, потому что не каждый gate живёт в event log: merge-protegida — это потолок в чистом правиле, не выпускающем собственного события (гарантирует его тест), а backmerge — это CI с состоянием в .release/gate.json. RN-072 — Без явного выбора модель — модель агента Criativo​

Когда каскад bindings приземляется на значение по умолчанию workspace — то есть никто ничего не решил для этого проекта, — наследуемая модель — это модель агента Criativo, а не глобальное значение по умолчанию.

Агент Criativo — всегда входная дверь проекта: с ним происходит первый разговор, и его binding представляет «модель, которой этот проект думает».

Наследование заполняет пробел, никогда не перезаписывает: bindings сессии, агента или проекта — чей-то явный выбор, и они продолжают побеждать. Именно поэтому это шаг ПОСЛЕ каскада, а не новая область внутри него — он не соревнуется за приоритет. И наследуемая модель проходит те же фильтры: исчезнувшая из каталога или без tool calling означает, что она не наследуется, по той же причине, по которой каскад их пропускает (RN-043).

Что это исправляет: значение по умолчанию workspace глобально и обычно является маленькой локальной моделью. Новая сессия и dev agent — у которых нет собственного binding — рождались на ней, а ADR 0020 запрещает маленькую локальную модель на семантическом шаге. При реальном исполнении пришлось вручную менять модель в каждой открытой сессии, и три dev agents поднялись на llama3.2:1b, хотя никто об этом не просил.

  • Тест: apps/api/test/domain/llm/binding-resolver.spec.ts (fills the gap; does NOT override %s's explicit choice)
  • Источник: находки B и O реального исполнения (ФАЗА 13c, фаза A)

RN-073 — Ожидающее одобрение ПРИОСТАНАВЛИВАЕТ цикл, а не сжигает его​

Когда инструмент конвейера возвращает pending, ToolLoop останавливается, а dev agent переходит в :awaiting_approval, удерживая задачу, worktree и историю цикла. Решение пользователя выпускает task.action_settled, которое его будит: реальный результат занимает место, где было бы слово «pending», и цикл возобновляется с того места, где остановился.

Свойства, которые фиксирует тест:

  • Во время ожидания ничего не записывается. Место сообщения инструмента остаётся пустым. Записать туда «pending» означало бы сказать модели, что это ответила команда, — ровно в этом и был дефект.
  • Отказ — это ответ. Причина занимает место результата, и агент узнаёт, что этот путь закрыт, вместо того чтобы вечно ждать того, что никто не одобрит. Это тот же принцип, что у pr_settled с opened: false (RN-047), уровнем ниже.
  • Wake должен ДОЙТИ. task.action_settled рождается в агрегате task, а не в proposed_action, которую подсказывает имя таблицы: drain engine читает закрытый список агрегатов (session и task). RN-074 — У вывода терминала есть потолок в байтах​

Вывод команды обрезается до TERMINAL_OUTPUT_MAX_BYTES (по умолчанию 32 KiB), прежде чем стать результатом инструмента, и обрезка оставляет метку, называющую оба размера и что делать:

[saída truncada: 32768 de 1048576 bytes. Refine o comando (head, grep,
-maxdepth) para ver o que falta.]

Три свойства, которые фиксирует тест:

  • Потолок — >, а не >=. Вывод, ровно умещающийся в предел, проходит нетронутым — его пометка заставила бы модель уточнять команду, которая уже выдала всё.
  • Обрезка не разрывает многобайтовый символ. binary_part/3 режет по байту; попадание в середину é даёт недопустимый бинарь, который ломает сериализацию JSON до того, как результат дойдёт до модели.
  • raw_bytes остаётся РЕАЛЬНЫМ произведённым размером, а не усечённым. Это измерение, и ложь в нём скрыла бы именно то поведение, которое мотивировало потолок. Кто хочет обнаружить усечение, сравнивает byte_size(stdout) с raw_bytes.

Что это исправляет: вывод каждой команды остаётся в истории цикла и путешествует в каждом последующем ходе. Без потолка хватает find по большому дереву — исполнение hello-limpo умерло с {413, "request entity too large"} на ходе 18, без единой написанной строки. Переполнение — это байты запроса, а не окно контекста: самый крупный успешный вызов имел 28.993 входных токена.

Метка адресована модели, а не человеку — без указания, что делать, она склонна повторять ту же команду.

RN-075 — Команда терминала оценивается по тому, чего она касается, а не только по глаголу​

Папка проекта (<PROJECT_WORKSPACES_ROOT>/<workspace_dir_name> — голый UUID в проекте до RN-109, <slug>-<8 символов id> в новом проекте) является областью видимости. Команда terminal, касающаяся любого пути вне её, никогда не автоодобряется, как бы ни был глагол в allow. Внутри неё cd перестаёт требовать разрешения — это объявление области видимости, а не глагол.

Четыре свойства, которые фиксируют тесты:

  • Ужесточает: разрешённый Terminal(cat) перестаёт автоматически выполнять cat /workspace/apps/engine/.../git_executor.ex. Это была находка U: сопоставление идёт по ГЛАГОЛУ, поэтому агент читал код платформы, которая его исполняла, и дотягивался до worktree других проектов.
  • Ослабляет: cd <dentro> && cat README.md становится auto_approve. Это был самый дорогой дефект лестницы — dev agent всегда выдаёт cd <caminho> && <verbo>, cd не было ни в одном allow, а составная команда требует совпадения ВСЕХ сегментов.
  • Разрешает, не освобождая: внутри области видимости глагол вне allow по-прежнему спрашивает. Нахождение в папке проекта не делает curl … | sh безопасным.
  • Вне области видимости — require_approval, никогда deny: у агента может быть законная причина посмотреть снаружи, и решение остаётся за пользователем.

deny по-прежнему побеждает первым, а два потолка (RN-006, RN-007) остаются нетронутыми. Без корня, переданного в decide(), вердикт такой же, как до этого правила, — ни у одного вызывающего поведение не меняется по умолчанию.

Нормализация лексическая, а не realpath: <raiz>/../.. разрешается и отклоняется, но символическая ссылка изнутри, указывающая наружу, не обнаруживается. decide() по контракту чиста, а разрешение symlink потребовало бы IO в домене. Область видимости — политика; изоляция — другая проблема, объявленная открытой в ADR.

Без regex над входом, намеренно. Удаление завершающих косых черт корня было .replace(/\/+$/, ''), и CodeQL указал полиномиальный ReDoS (js/polynomial-redos, HIGH): шаблон заставляет движок пробовать каждую начальную позицию и сканировать до конца, деградируя до O(n²). Сейчас это проход за O(n), эквивалентный даже в вырожденном случае — корень / становится пустой строкой в обоих, и именно это делает startsWith('/') истинным для любого абсолютного пути. Тот, кто «упростит» обратно до regex, снова откроет предупреждение.

RN-092 — projectId — это сегмент пути, и область видимости никогда не выходит за корень​

projectScopeRoot() отклоняет projectId, не являющийся простым сегментом пути (^[A-Za-z0-9_-]{1,64}$), выбрасывая исключение вместо сборки пути.

Причина в том, что id приходит из @Param('projectId') без pipe проверки, а Express декодирует percent-encoding сегмента перед его передачей: ..%2F..%2Fetc приходит как ../../etc, и join разрешил бы его за пределы корня без жалоб. Страдают оба потребителя функции, и второй — серьёзно:

  • permissions.json читался бы и записывался по произвольному пути;
  • область видимости RN-075 авторизует команду terminal под этой папкой. Область видимости, сбежавшая из корня, — это политика одобрения, указывающая не туда, — сбой БЕЗОПАСНОСТИ, а не «файл не найден».

Проверка намеренно шире UUID (принимает буквы, цифры, дефис и подчёркивание), чтобы не привязывать формат id, и достаточно узкая, чтобы результат никогда не сбежал. И она находится там, где выводится корень, а не у каждого вызывающего, по той же причине, по которой функция появилась: два вывода должны совпадать, а продублированная проверка — это проверка, которая однажды разойдётся.

Счастливый путь не меняется — каждый реальный id является UUID из базы.

RN-093 — В production api не стартует с примерным ключом state OAuth​

resolveOauthStateSecret() роняет загрузку, когда NODE_ENV === 'production' и GIT_OAUTH_STATE_SECRET отсутствует, равен примерному литералу репозитория или короче 16 символов. Вне production значение по умолчанию для разработки продолжает действовать.

Этот ключ подписывает state OAuth для git, а state — единственное, что не даёт подделать callback GET /git/oauth/:provider/callback — публичный маршрут, по необходимости. С известным ключом любой подписывает state для выбранных {projectId, userId, provider} и заставляет callback записать в указанный этим payload проект git-токен, полученный от провайдера.

RN-076 — Учётные данные git никогда не записываются в файл​

RN-079 — Psicólogo не анализирует сессию без анализируемых событий​

Прежде чем тратить ход модели, анализ спрашивает, есть ли что анализировать. Если нет, он не запускается, и исходом становится psychologist.analysis_skipped.

Анализируемое исключает две вещи, по разным причинам:

  • след самих аналитиков. Psicólogo записывает свой ход в лог анализируемой сессии (agent.response, tool.call, tool.result, гипотеза). Его подсчёт заставил бы пустую сессию выглядеть заполненной с первого анализа, и каждая повторная попытка наполняла бы её больше — критерий больше никогда не проваливал бы.   • bootstrap.*, то есть провизионирование репозитория, работающее самостоятельно: девять машинных шагов ничего не говорят о человеке.

Всё остальное считается, включая proposed_action.* — пользователь, одобряющий и отклоняющий, не написав ни одного сообщения, является поведением, урок, который Anamnese уже усвоила (RN-063).

Пропуск действует и для ручной повторной обработки. Повторная обработка не фабрикует материал: тот, кто кликнул, получает причину в логе, а не гипотезу, выдуманную о несуществующем логе.

Пропуск становится событием, в отличие от пропуска Anamnese, который лишь лог: та запускается каждые 15 мин и стала бы шумом, этот запускается раз на закрытие сессии, и отсутствующий анализ, о котором ничего не рассказано, невозможно диагностировать.

Сколько агентов поднимается, перестаёт быть числом в коде: оценивает lead области. Потолок — на СЕССИЮ, а не на модуль. Это единственная неочевидная часть правила и та, которую невнимательный рефакторинг отменяет: подсчёт по модулю позволил бы N модулей × 2 агента без какого-либо разрешения — прежняя дыра под другим именем. Есть тест, утверждающий ровно это.

Нулевой или отрицательный потолок — недопустимая конфигурация, а не «без ограничения». Трактовка его как неограниченного превратила бы опечатку в неограниченный расход — противоположность тому, для чего существует конвейер.

ПРОСИТ lead; РЕШАЕТЕ вы. proposed_action рождается с lead как актором, а решение остаётся в event log с вашим именем — именно это различие делает историю восстановимой потом (ADR 0048).

Причина путешествует в НЕИЗМЕНЯЕМОМ payload, с тремя числами (сколько есть, сколько просит, каков потолок): тот, кто прочтёт через полгода, должен понять, что было разрешено, не восстанавливая состояние сессии.

AcceptParallelizationUseCase не меняется: он по-прежнему ИСПОЛНЯЕТ — как на прямом пути, так и когда действие одобрено. Поглощение его изнутри, а не переписывание, — то, что сохраняет набор тестов Фазы 4 зелёным без изменений, — это доказательство того, что замена не просочилась во внешний контракт.

Потолок настраивается по области, и только вами. PATCH /projects/:projectId/agent-areas/:key/max-parallel требует maintainer — ту же роль, что для активации исполнения, и по той же причине: изменение потолка — это решение о том, сколько продукт может тратить без спроса. Автоматического пути его поднять не существует. Anamnese может ПРЕДЛОЖИТЬ, когда заметит, что разрешение стало рутиной, и предложение по-прежнему проходит через этот маршрут после того, как вы его примете, — продукт, поднимающий собственный потолок расходов, — ровно то, чему конвейер одобрения существует, чтобы помешать.

Изменение потолка действует для СЛЕДУЮЩИХ запросов. То, что уже ждёт решения, продолжает ждать: действие несёт в payload потолок, действовавший при его создании, а его переинтерпретация под новым потолком изменила бы то, что вы собираетесь решить, уже прочитав.

RN-085 — Потолок итераций зависит от ТИПА агента​

Сколько кругов агент может сделать в цикле инструментов, зависит от работы, которую он выполняет: 8 для того, кто разговаривает, 60 для dev agent и подагентов QA. Единого числа больше нет.

Потолок 8 родился у разговорного агента и был унаследован теми, кто работает. При реальной проверке 13b это проявилось как блокировка: dev agent потратил восемь кругов, исследуя только что провизионированный репозиторий, и так и не написал ни одного файла; с 25 он написал три и запустил тесты. Зарегистрированным исходом было limite de iterações atingido с источником modelo — технически правда и практически бесполезно, потому что модель так и не дошла до того, чтобы что-либо оценить.

Поднять глобальное значение по умолчанию было бы неверным исправлением, и именно от этого защищает правило: Criativo не нужно 60 кругов, чтобы разговаривать, а потолок — также замок против бесконечного цикла.

Поднимать может не «тот, кто много работает», а тот, у кого внизу есть замок расходов. Потолок итераций защищает от бесконечного цикла; КОШЕЛЁК защищает token_budget_micros. Dev agents и подагенты QA работают с task_budget_micros задачи, так что ослабление кругов не ослабляет счёт. infra-workflows использует тяжёлый инструмент и всё равно остаётся на 8: он работает без бюджета, и для него потолок — единственный существующий замок.

Два граничных случая с собственным тестом:

  • dev-lead — разговорный, несмотря на префикс dev-, обозначающий dev agents (dev-<modulo>, dev-<modulo>-2). Lead решает и делегирует, и без явного условия он рождался бы с потолком тяжёлой работы по случайности именования.

  • Неизвестный агент попадает на самый низкий потолок. Ошибаться в дешёвую сторону: тот, кому нужно больше кругов, проявляется как limite de iterações atingido и исправляется; тот, кто получает 60 по ошибке, тратит молча.

RN-086 — Расход на дополнительных агентов никогда не автоодобряется​

Два действия, затрагивающие то, сколько продукт может тратить сам, — parallelize (превысить потолок сейчас) и raise_max_parallel (изменить потолок), — никогда не автоодобряются. Ни через agent_autonomy, ни через permissions.json. Это тот же класс гарантии, что блокировка merge и потолок патча инструкции.

Без этого потолок RN-083 был бы декоративным. permissions.json с Parallelize() в allow заставил бы каждое превышение одобрять себя само — правило, существующее, чтобы ТРЕБОВАТЬ решения пользователя, начало бы от него освобождать. А raise_max_parallel — самый тяжёлый случай: это был бы продукт, поднимающий собственный лимит расходов, ровно то, чему конвейер одобрения существует, чтобы помешать.

Anamnese может ПРЕДЛОЖИТЬ, и именно это она делает. Когда разрешение ещё одного агента становится рутиной, потолок неверен, и первым это замечает тот, кто читает историю. Сигнал уже доходил до неё: решения пользователя в окне приходят из proposed_actions, с actionType и status.

Порог — три одобрения и ни одного отказа, и обе половины важны:

  • два — это не рутина, это два. Три — то, что отделяет «случилось» от «случается всегда»;
  • один отказ обрушивает весь сигнал, сколько бы ни было одобрений. Если пользователь хоть раз отказал, потолок делает свою работу, и предложение его поднять было бы прочтением сигнала наоборот.

Предложение потолка, равного или меньшего действующего, отклоняется api: Anamnese работает периодически и предлагала бы одно и то же каждый раунд, наполняя шумом очередь, которую пользователю нужно читать.

Одобрение применяет значение из payload, а не пересчитанное в моменте, — это число, которое вы прочитали, принимая решение.

RN-087 — Dev Lead — единственный внешний адрес исполнения​

Существует агент dev-lead, разговорный, который получает handoff от Arquiteto (начиная с RN-672 — от Infra, с контейнером проекта в running) и предлагает план исполнения: сколько агентов на модуль и почему. Он не пишет код — он распределяет работу и отвечает за неё.

До него фраза «решает lead» из RN-083 не имела владельца. Arquiteto заканчивал, и исполнение поднималось кнопкой, без кого-либо посередине, кто оценил бы, сколько работы есть.

dev-<modulo> перестали быть адресуемыми через handoff. Это не новое исключение: это правило ADR 0038 — внешний handoff адресует только lead области или агента без области, — начавшее действовать для dev так же, как уже действовало для QA и Infra. Пока Dev Lead не было, они были агентами БЕЗ области и потому допустимыми целями; став участниками, они перестают ими быть.

Область dev — первая ДИНАМИЧЕСКАЯ, и именно это вынудило предикат: участники — по одному на модуль module_map, решаемые Arquiteto и разные в каждом проекте, так что перечислять нечего. dev-lead совпадает с тем же префиксом dev-, что и участники, а исключает его общее правило lead никогда не является участником собственной области — которое действует для любой области и живёт в одном месте. Первая версия повторяла это исключение в трёх точках, и проверка мутациями показала, что ни одна из копий не была достижима тестом: каждая переживала мутацию другой.

План — это proposed_action (пересмотрено ADR 0086, RN-284). До этого изменения план становился простым СОБЫТИЕМ, без одобрения: аргумент был в том, что у предложения нет внешнего эффекта — расход происходит, когда агенты поднимаются, и именно там потолок требует разрешения; превращение предложения в решаемое действие заставило бы вас решать одно и то же дважды. Аудит docs/fluxo.yml × код обнаружил, что поток уже объявлял этот выход как via: proposed_action с ADR 0085, а код так и не был подогнан под это, — владелец продукта решил, что ошибался код: план — ПЕРВОЕ реальное решение о том, сколько сессия потратит на параллелизм, и пользователь стал решать активировать исполнение, УВИДЕВ настоящее одобрение, а не просто прочитав строку в ленте. Старый урок не исчез — это причина, по которой propose_execution_plan НЕ вошёл в блок абсолютных потолков decide.ts (см. RN-284).

УСПЕШНЫЙ план завершает ход — на пути БЕЗ приостановки. При первом реальном исполнении Dev Lead зарегистрировал два execution.plan_proposed в одной сессии — разные тексты, одинаковый итог, — потому что цикл возвращался к модели, и она предлагала снова. Event log неизменяем: остались два предложения и ничего, говорящего, какое действует. Инструкция «используй один раз» в spec инструмента — просьба, а не гарантия; гарантирует остановка цикла. Начиная с ADR 0086, когда предложение остаётся pending, ход завершает ОСТАНОВКА по приостановке (RN-284) — немедленный успех (auto_approved/executed/approved, см. RN-284) по-прежнему закрывает цикл так же, как всегда.

Успешный, а не «вызвал инструмент»: отклонённый план (пустой или с нулём агентов в модуле) позволяет циклу продолжаться, иначе отказ становится концом хода, и модель так и не доходит до исправления. Первая версия этой защиты смотрела только на имя инструмента и имела этот дефект — найденный поведенческим тестом, а не чтением.

Пустой план или план с нулём агентов в модуле отклоняется до предложения чего-либо — предложение, однажды созданное, является реальным решением пользователя, а наполовину предложенный план нельзя было бы отозвать.

RN-064 — Heartbeat не закрывает сессию с незавершённой работой​

Расширено RN-581 (AT-072): разговорный агент, ждущий пользователя, стал ПЯТЫМ сигналом, и единственным с потолком (8h, причина conversation_idle_timeout); ответ получил aguardandoUsuarioDesde. Остальная часть правила действует как есть.

Timeout heartbeat измеряет бездействие вкладки, а не работы. Прежде чем закрыть, SessionServer спрашивает api, осталась ли работа (GET /internal/sessions/:id/pending-work); если да, он перепланирует timeout и записывает причину в лог, вместо того чтобы убить сессию.

По умолчанию — 30 секунд. Уйти из сессии на вкладку Backlog уже было достаточно, чтобы её убить, — и при реальном исполнении это заперло handoff offered для Arquiteto внутри закрытой сессии: эпик и четыре истории готовы, а цепочке некуда идти, потому что нет места, где принять handoff мёртвой сессии.

Закрытие сессии — о том, что работа закончилась, а не о том, кто смотрит.

Недоступная api НЕ мешает закрытию: {:error, _} всё равно закрывает, с предупреждением в логе. Обменять осиротевшую сессию на бессмертную значило бы обменять один дефект на другой.

«Незавершённая работа» — это три сигнала: второй вошёл по находке V, третий — по реальному багу Criativo→PO→Arquiteto:

  1. handoff offered — исходный случай выше;
  2. proposed_action со статусом pending — кто-то ждёт ВАШЕГО решения, и агент может быть приостановлен в ожидании исхода (RN-073);
  3. АКТИВИРОВАННЫЙ агент всё ещё в ходе — последний agent.status каждого актора, уже говорившего в сессии, — working без последующего idle.

Второй — тот же дефект, что первый, уровнем ниже, и исполнение hello-limpo показало цену: сессия родилась в 23:34:12, действие стало pending в 23:34:13, а heartbeat закрыл её в 23:34:42 — ровно через 30s timeout. Dev agent продолжал работать больше часа в сессии, которую база считала закрытой, и это отравляет каждую метрику по сессии: длительность, стоимость и «сколько закончились хорошо» начинают читать состояние, не описывающее того, что произошло.

Третий — то же окно, на шаг раньше, чем появляется любой из первых двух: AcceptHandoffUseCase помечает старый handoff как accepted и сразу активирует следующего агента, но активация в engine — это GenServer.cast fire-and-forget — отвечает 201 до того, как агент вообще начнёт. PO, активированный handoff от Criativo, выполняет kickoff до 12 итераций LLM, используя только инструменты category: :direct (create_epic/create_story/create_task), которые никогда не порождают proposed_action, и предлагает следующий handoff (сигнал 1) только в КОНЦЕ всего хода. Между активацией и этим концом не существовало ни сигнала 1, ни сигнала 2 — сессию удерживал только ping канала Phoenix каждые 10s, и любая задержка больше 30s timeout закрывала сессию, пока PO ещё генерировал backlog, ломая цепочку handoff под корень: следующий handoff в итоге предлагался в уже closed сессии, которая больше ничего не принимает.

agent.status (working/idle) — то, что каждый разговорный агент (Criativo/PO/Arquiteto/Dev Lead/Infra) уже описывает на границах хода, и он СОХРАНЯЕТСЯ в event log, а не только транслируется в канал (Engine.Sessions.LiveBroadcast.agent_status/4, ADR 0021) — тот же сигнал, который панель команды уже читает, чтобы вывести roster (conversationalStatus в apps/web/src/lib/agent-status.ts). Его переиспользование здесь не потребовало никакого нового события: третий сигнал — последний agent.status КАЖДОГО актора, уже говорившего в сессии, и он общий по типу события — покрывает любого агента, активированного через handoff, а не только PO.

Предыдущая версия этого правила письменно говорила, что включение работы агента «без теста, доказывающего взаимодействие, было бы гаданием». Исполнение дало доказательство, и тест теперь существует.

Что остаётся вне: задача in_progress без ожидающего действия, handoff или открытого хода. У dev agent собственная машина состояний, и он удерживает worktree сам; сигнал, которым владеет api и который подтвердило исполнение, — ожидающее действие. Включение задачи потребовало бы, чтобы api читала dev_agent_states, принадлежащую engine, — решение о границе, а не исправление мимоходом. Dev agents также не выпускают agent.status (работают с собственной машиной состояний, а не с разговорным циклом хода) — третий сигнал их не покрывает, и не нужно: их путь уже покрывает ожидающее действие.

RN-063 — Завершение без производства — исход, а не сбой​

У Anamnese есть инструмент, чтобы сказать «выпускать нечего, и вот причина» (skip_proficiency). Раунд завершается anamnese.run_skipped с причиной в payload — никогда anamnese.run_failed.

Раньше у неё не было этого глагола. Единственным инструментом был emit_proficiency, который отклоняет пустой список (и справедливо: пустой профиль — не профиль). В окне без подходящего участника Anamnese обнаруживала это на ПЕРВОЙ итерации, писала прозой «нет подходящих участников», вызывала emit_proficiency с profiles: [], получала отказ — и повторяла до потолка итераций. RN-060 — Расход по ключам принадлежит owner, и видит его только он​

Отчёт о потреблении по учётным данным (GET /workspaces/:id/credential-spend) требует owner в workspace. Не maintainer: начиная с RN-058 агенты всех проектов тратят учётные данные владельца, и его счёт — не дело того, кто лишь управляет проектом.

RN-101 — Один расход, две аудитории: счёт принадлежит owner, потребление — тому, кто потратил​

Продукт отвечает на два разных вопроса о token_usage, и ни один не является срезом другого.

Вопрос owner — по УЧЁТНЫМ ДАННЫМ. GET /workspaces/:id/credential-spend остаётся таким, каким его оставила RN-060, — по провайдеру, требуя owner, отвечая на «сколько ушло с моего ключа». Рядом с ним GET /workspaces/:id/spend-report (тоже owner) разбивает workspace по модели, провайдеру, проекту, актору и дню — ось провайдера вошла по RN-186. Owner видит оба, потому что он единственный, кто может видеть оба.

Вопрос участника — по АКТОРУ. GET /projects/:id/spend/me (роль viewer) возвращает, в токенах и оценочной стоимости, то, что вызвавший потребил в этом проекте, по сессии и по дню. Он не разбивает ни по провайдеру, ни по учётным данным — работал ключ owner (RN-058), и доля его счёта — не то, о чём спрашивает участник.

Актор не является параметром: он берётся из аутентифицированного пользователя, и нет места, куда вписать id другого человека. «Участник не видит строку другого актора» — свойство сигнатуры сценария использования, а не проверка, которую кто-то может забыть вызвать.

Агент не входит в счёт участника. token_usage регистрирует, кто ПОТРАТИЛ, а не кто велел потратить; приписывать агента тому, кто его запустил, значило бы выдумывать данные, которых в таблице нет. Расход агента появляется в отчёте owner, которому принадлежит ключ.

Сегодня у sumGroupedBy шесть измерений (model, provider, project, actor, session, day), и ограничение сменило форму, а не силу: ограничивает ТИП — см. RN-186 и RN-187. Не изменилось то, что два провайдера, обслуживающие одно имя модели, по-прежнему попадают в одну строку измерения model.

RN-102 — Модель области — наследуемое значение по умолчанию; расхождение — решение агента, а возврат к наследованию стирает решение​

Каскад binding получил уровень: сессия > агент > **область** > проект > workspace. area находится МЕЖДУ агентом и проектом — это ЗНАЧЕНИЕ ПО УМОЛЧАНИЮ, которое делят lead и подагенты области (qa/qa-automacao/qa-performance-seguranca, infra/infra-workflows, dev/dev-<módulo>), а binding самого агента — это РАСХОЖДЕНИЕ, которое его перекрывает. Если бы область стояла ВЫШЕ агента, она побеждала бы всегда, и «наследуемое значение по умолчанию» на практике было бы «навязанным» — ни один агент не смог бы выбрать другую модель.

Новый уровень входит в ТУ ЖЕ повторную проверку capability, что и RN-041/RN-043: модель области, исчезнувшая у провайдера или не делающая tool calling, ПРОПУСКАЕТСЯ и записывается в skipped, ровно как это уже было с agent. assertModelFitsBindingScope (RN-040) стала требовать supports_tool_calling также в области area — её никогда не читает человеческий чат, только агент, так что её пропуск отложил бы тот же молчаливый сбой на один уровень.

«Вернуться к наследованию» удаляет binding, никогда не копирует модель нижнего уровня наверх. Запись в агента модели, которую решила область, выглядела бы на экране так же, но это не так: это стало бы КОПИЕЙ, и следующее изменение области оставило бы этого агента позади, и никто бы не заметил. Наследование — это ОТСУТСТВИЕ собственного решения, а отмена расхождения — удаление строки: DELETE /projects/:id/agent-bindings/:slug и DELETE /projects/:id/area-bindings/:key, оба 204, оба 404, когда область уже наследует (идемпотентность, которая СОЛГАЛА бы, будь она молчаливым 204: удалить несуществующее и удалить по-настоящему — разные ответы для одного экрана).

RN-103 — Binding агента — ПО ПРОЕКТУ, а не глобальный​

Это перестало держаться, когда область стала наследуемым значением по умолчанию (RN-102): область — по проекту, и глобальный binding агента НАД значением по умолчанию по проекту заставил бы одного и того же агента разрешать разные модели только там, где существует область, — и заставил бы «вернуться к наследованию» стирать решение, дотягивавшееся до проектов, на которые никто не смотрит.

Выходом стало сделать agent тоже по проекту, а не опускать область ниже агента: scope_id у agent и area стал СОСТАВНЫМ — <projectId>:<slug агента|ключ области> — вместо выдумывания новой таблицы только ради хранения проекта для каждого binding. UUID проекта и slug агента никогда не содержат :, что делает первое : однозначным разделителем; чтение режет по нему, а не по всем, чтобы slug с : (сегодня таких нет, но ничто не мешает) не превратился в три куска.

scope_id без проекта (старый формат) ОТКЛОНЯЕТСЯ при записи, а не принимается и игнорируется: его запись создала бы binding, который каскад больше никогда не нашёл бы, — невидимый, а не ошибку. Миграция 0040 разносит каждый существующий глобальный binding агента по строке на проект (сохраняя то, что каждый проект разрешал до изменения) и удаляет старый формат; это РАЗНЕСЕНИЕ, а не удаление, потому что глобальная строка никогда не хранила информации о том, кому она «принадлежала», — выдумывать проект-владельца значило бы выдумывать несуществовавшие данные.

RN-470 — Источник модели отличает собственный binding от наследования от Criativo, и ни одна пустота каскада не использует тот же символ, что другая​

origin: 'agent' в ответе api означает две разные вещи, и api права, не разделяя их: у агента есть строка области agent в model_bindings, или каскад приземлился на workspace, и herdarModeloDeStart заменил значение на модель Criativo — тот, кто читает «откуда пришло», должен видеть, что пришло от АГЕНТА, а не из области, которой нет в базе. Разделять их должен экран, и до сих пор он их не разделял: колонка Origem печатала сырой enum, и в проекте с 3 строками agent в базе все 12 агентов показывали одно и то же слово agent.

Источник — это ЦЕПОЧКА, а не слово. workspace › проект › область › агент с четырьмя состояниями узла, и все четыре существуют, потому что говорят разное: действующий (отсюда берётся используемая модель — единственный узел в Badge), заданный (у этого уровня есть собственное значение, но победил более конкретный), пустой (здесь нет значения) и пропущенный (значение было, и каскад его отбросил по unavailable/sem_tool_calling, RN-043). Слияние заданного с пустым вернуло бы проблему сырого enum на уровень ниже.

При наследовании узел агент остаётся ПУСТЫМ, а дополнительный узел называет Criativo. Уровень, которого достиг каскад (workspace), показывается как заданный, а не как действующий: модель workspace — не та, что действует, и пометка её действующей утверждала бы неверную модель. Узел Criativo — единственный, не являющийся областью базы, намеренно — он называет послекаскадный шаг. Та же цепочка действует для раздела ОБЛАСТИ, где origin: 'agent' может быть только этим шагом: запрос области не кладёт область агента в каскад.

Вывод делает КЛИЕНТ, и то, что он не может доказать, остаётся действенным. Ни одного нового endpoint: экран уже запрашивает четыре уровня. agent — это наследование, когда ни у одного уровня выше workspace не было ПРИГОДНОГО значения (пропущенное не удерживает спуск), и модель совпадает с разрешённой моделью Criativo. Остаётся один неразличимый случай: агент с собственной строкой, указывающей на ту же модель, что и Criativo, без значения по умолчанию области или проекта. Поэтому «вернуться к наследованию» продолжает появляться при любом источнике agent — действие остаётся доступным именно в том случае, который цепочка не доказывает, и в нём оно всё ещё меняет будущее (без строки агент начинает следовать за Criativo).

Другая половина этого выбора: у 404 собственный исход. Сохранение кнопки при любом источнике agent означает предлагать её ТАКЖЕ там, где нет строки для удаления, — и там ClearModelBindingUseCase отвечает 404, правильно («удалил несуществующее» и «удалил» — не один и тот же ответ; их слияние скрыло бы неверный agentSlug). Для того, кто кликнул, однако, этот 404 — не сбой: запрошенное состояние — агент наследует — уже истинно, и назвать это ошибкой значило бы экрану противоречить тому, что он знает. Поэтому он не проходит через mensagemDaApi, как остальные отказы, по двум причинам: фраза api — pt-BR, зашитая в коде, а язык web по умолчанию — en, и у этого endpoint одна причина 404 (недостаточная роль — 403 в RolesGuard, некорректный scope_id — не 404) — клиент ЗНАЕТ, что значит этот 404, и может сказать это на языке читающего. Любой другой статус по-прежнему настоящий сбой, с фразой api и тоном danger. В обоих исходах строка перечитывается: если api говорит, что binding не было, устарел экран.

И собственный исход принадлежит ENDPOINT, а не экрану. Другое действие той же строки — смена модели через ModelPicker колонки МОДЕЛЬ ДЕЙСТВУЮЩАЯ — отклоняет семью путями, и ни один статус не идентифицирует один из них в одиночку (SetModelBindingUseCase): 400 для некорректного scope_id или modelId, отвергнутого DTO, 403 для роли ниже developer, 404 для двух неразличимых причин ("Modelo não encontrado" и "Projeto não encontrado") и 422 для трёх (RN-040 без tool calling; RN-043 отключена в workspace или исчезла у провайдера). Там клиент НЕ может назвать 404 — выбрать одну из двух фраз значило бы экрану утверждать то, чего он не знает, — так что каждый отказ следует обычной грамматике, с фразой api и тоном danger. Две функции — соседи и обрабатывают один статус противоположно намеренно: собственный исход разрешает ЕДИНСТВЕННАЯ причина, а не экран.

При отказе колонка МОДЕЛЬ ДЕЙСТВУЮЩАЯ продолжает показывать подтверждённый binding. Это та же дисциплина этой RN, применённая ко времени: экран не утверждает несуществующее состояние — ни прочерком, ни enum, ни оптимизмом.

RN-057 — «Для чего подходит» — курирование workspace, и пометка использования не включает модель​
