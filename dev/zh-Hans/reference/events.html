    事件

    Brabo 中并存着三族名称，而且很容易混淆，因为它们都使用 主题.动词 的形式：

    族 所在位置 持久性
    领域事件 session_events 中的一行 永久且不可变
    Broadcast Phoenix 通道 → 浏览器 短暂，不持久化
    Span OpenTelemetry 的 trace Tempo 的保留期（本地为 24 小时）

    只有第一种是契约。另外两种是传输和观测。

    领域事件

    session_events 中的一行，只追加，每个会话有一个连续的 seq（RN-002）。列：

    列 含义
    id uuid
    session_id 所属会话
    seq 会话内的顺序，从 1 开始，没有空洞
    type 下面的标识符
    actor 由谁引起：{kind, id}——用户、agent 或系统
    payload jsonb，每种类型有自己的格式
    created_at —

    type 在代码中是自由的 string——没有 TypeScript 的 union，也没有数据库 enum 列出合法的类型。下面的列表是从发出事件的位置提取的，因此可能过时而不会弄坏任何东西。参见本页末尾的说明。

    会话

    类型 时机
    session.created 会话以 created 状态诞生
    session.activated 转为 active
    session.draining 承载它的节点正在排空
    session.closed 正常结束
    session.closed_abnormally 带原因的结束——node_shutdown 是最常见的
    session.reopened 一个 closed/closed_abnormally 的会话回到了 active（ADR 0183）

    终止状态的会话不再接收对话（RN-581）。 当会话处于 closed 或 closed_abnormally 时，写入对话事件会被以 409 和 reason: "sessao_encerrada" 拒绝。对话是指只作为对话存在的类型（chat.message、chat.message_cancelled、chat.structured_question、chat.structured_question_answered、agent.status、agent.activated、handoff.offered、handoff.accepted、readiness.confirmed、necessity.validated、architecture.readiness_confirmed），或者任何 actor 是对话 agent 的事件——所以创意 agent 的 tool.call/agent.response 会被拒绝，而来自心理学家的同类事件——它运行在已关闭的会话之上——仍然可以写入。对待处理动作的人工决策（action.approved/action.denied）也仍然可以写入：动作队列比会话活得久。因对话停滞超过上限而关闭的会话带有 termination_reason: "conversation_idle_timeout"，并以 closed 结束，与 heartbeat_timeout 相同。

    已关闭的会话可以重新打开（RN-649，ADR 0183）。 POST /projects/:projectId/sessions/:sessionId/reopen（developer，ADR 0184）把一个 closed/closed_abnormally 会话带回 active，并写入 session.reopened，内容为 {from, to, closedAt, terminationReason}——这是它处于关闭状态那段时间的唯一记录，因为该行的 closed_at 和 termination_reason 会被清空。不会编辑任何之前的事件，会话的 kind 也不变。已有 execution.activated 的会话会被以 409 sessao_com_execucao 拒绝。

    聊天与 agent

    类型 时机
    chat.message 会话对话流中的消息，来自用户或 agent
    chat.message_queued 消息在 agent 回合进行中到达，进入了它的队列而不是被拒绝（RN-673，ADR 0191）。Actor：该 agent。Payload：mensagemId（chat.message 的 id）、texto、idioma 和 posicao。文本放在这里是因为 engine 重启后队列要重新读取它。入队的消息保持待处理，直到某个 chat.message_delivered 或 chat.message_cancelled 指名它；每个 agent 每个会话最多 10 条
    chat.message_delivered 读取队列的回合开始了：待处理的消息被一起、按顺序在一个回合中读取。Actor：该 agent。Payload：mensagemIds
    chat.message_cancelled 发送待处理消息的人取消了它——没有 agent 读过它。Actor：该用户。Payload：mensagemId、agente。由 engine 写入；在已关闭的会话中被拒绝（RN-581）
    chat.structured_question 创意 agent 通过表单一次请求多个回答——工具 ask_structured_questions（RN-162）。每个问题带有 id、label、type、options 和 allowOther——后者是 select 的自由文本出口，模型未声明时为 true（RN-171）
    chat.structured_question_answered 用户回答了表单；回答也会作为 chat.message 返回给 agent 阅读
    agent.activated 某个 agent 在会话中接手了工作
    agent.response agent 完整、合并后的回应。modelName 说明是哪个模型生成的，三个生产方都会写（五个对话 agent、每个执行/gate agent 的 ToolLoop，以及没有活动 agent 时 api 的聊天）——回合在解析 binding 之前就失败时为 null，在该规则存在之前写入的事件中不存在（RN-175）。来自对话 agent 时，content 只是回合的收尾文本，passos（没有时不存在）按顺序列出之前各轮的文本，对话流把它们折叠在"回合步骤"之下（RN-698，AT-395）
    agent.error agent 的失败，带有 origem（infra/modelo/codigo/politica）以及它在对话流中说出的 mensagem（RN-059）。当 engine 在回合中途重启、孤立的 working 状态在启动时或 agent 启动时被关闭时，也会以 reason: turno_interrompido_por_reinicio（origem infra）发出，随后是 agent.status: idle（RN-586）。它覆盖整个回合，也覆盖循环中途某一个工具的失败，payload 中带有 tool 和 retentativa（RN-163）
    tool_router.decided Jev 选择工具的那一步（RN-625，ADR 0179）：menuAntes/menuDepois、escolha、confianca、segunda、anterior、aplicado（菜单比目录小）、Jev 失败时的 motivoDaQueda + origemDaQueda（infra/modelo/codigo）、latenciaMs、custoMicros（真实的 usage.cost）和 foraDoCardapio（模型调用了但未被提供的工具）。由 engine 的门面为每个 agent 写入；没有咨询路由器时不存在（provider 不是 OpenRouter、工具少于两个、workspace 开关关闭）。收益的度量（AT-239）从这个事件和 token_usage 中读取，从不手工记录
    tool.result 工具执行的结果，由 hook Engine.Harness.Hooks.EventLog 写入，对七个对话 agent（Infra Lead 自 RN-617 起）则由它们的服务器写入，带 tool、ok 和 resultado（或 erro），截断为 2.000 个字符，截断时带 resultadoTotal（RN-589）。Infra Lead 为它内联分派的每个工具产生同样的 payload，Dev Lead 在挂起的调用被解决时也会产生——但在它等待审批期间绝不会（RN-593）
    handoff.offered 一个 agent 把工作提供给另一个
    handoff.accepted 接收方接受了。通常由人接受（actor user）。当接受隐含在"我准备好了"点击中时（RN-658），actor 仍是这个人，payload——以及随后的 agent.activated 的 payload——还带有 implicito: { via: "readiness.confirmed", readinessEventId }。自 RN-660（ADR 0186）起，PO 向架构师的提议可以由 system actor handoff-auto-accept 接受，此时 payload 还带有 automatico: true、emNomeDe（打开会话的人——仓库以此人的名义创建）和 criterio（regras、cobertas、repositorio）
    handoff.auto_accept_failed 系统决定接受 PO 向架构师的提议（RN-660），但接受失败了。Payload：handoffId、toAgent、origem（infra）和 error。Actor system handoff-auto-accept。提议未被标记为 accepted 时保留按钮
    handoff.superseded 一个 offered 状态的 handoff 不再是现行的，也不能再被接受（RN-635，ADR 0182）。Payload：handoffId、toAgent、motivo（agente_ativado——目标通过任何途径被激活；nova_oferta——项目中对同一目标的更新提议取代了它）和 substitutaId（取代它的提议，agente_ativado 时为 null）。由 system actor handoff-lifecycle 写入旧提议所在的会话，该会话可能已关闭——这是记录而不是对话，所以 RN-581 允许它写入。该行的 status 变为 superseded；事件即历史
    context.compacted 上下文管理器把某个 agent 历史中较早的回合做了摘要，以适应窗口。自 RN-580 起，payload 除了 tokensBefore/tokensAfter 之外，还带有替代这些回合的 summary、拥有该历史的 agent 以及 messagesSummarized。在此之前写入的事件只带两个计数——摘要已经丢失，重新水合时会说明这一点，而不是编造一个

    对话 agent 重新读取什么（RN-580）。 当七个对话 agent 之一在已有对话的会话上启动时，Engine.Agents.Reidratacao 从这个日志的尾部（最近 200 个事件）重建它的历史：chat.message、agent.response、chat.structured_question（作为 agent 自己的回合，带标签和选项）以及它自己的 tool.call/tool.result（作为文本注记——事件不带调用 id，所以绝不会被重放为 role: tool）。chat.structured_question_answered 被故意跳过：api 随后会把同样的回答写成 chat.message，agent 实时读到的就是那个。在队列中被取消的 chat.message，或对该 agent 仍待处理的 chat.message，也会被跳过（RN-673）：前者从未被说出，后者会通过读取队列的回合到达。自 RN-589 起，七者都会把工具返回的文本写入 tool.result（resultado，截断为 2.000 个字符，截断时 resultadoTotal 给出真实长度）；在此之前写入的会话调用没有 tool.result，注记会说明日志中没有结果。当对话长于尾部时，历史以一条系统消息开头，说明有多少更早的事件被省略，然后是最后写入的压缩摘要和开场消息。

    提议的动作

    类型 时机
    proposed_action.created 动作诞生——在任何执行之前。payload.status 说明它如何诞生（pending、auto_approved 或 denied），这正是区分人工决策与策略的依据（RN-049）。payload.reason 说明是策略的哪条规则做了决定——即 decide() 返回的字符串，三种结果都有；在该规则存在之前写入的事件中不存在，这意味着"未记录"，绝不意味着"没有原因"。同名的 outbox 行不带它（RN-567）。在 terminal 动作中——唯一一种决策会参考路径范围的类型——payload.scopeRoot 说明范围是与哪个根比较的，形式为 { executionMode, ancora, segmento }：container → ancora: raiz_gerenciada 和 workspace_dir_name；mounted → ancora: base_de_projetos 和 BRABO_PROJECTS_BASE 之下的路径段（文件夹在基础目录之外或没有基础目录时为 ancora: indisponivel、segmento: null）；runner → ancora: nome_da_pasta 和 workspace_dir_name。绝不是绝对路径，那会把用户的 $HOME 暴露给每个成员。在旧事件和其他动作类型中不存在；也不在 outbox 中（RN-609）
    proposed_action.approved 由用户决定——actor 是点击的人。自动批准不经过这里：它出现在 created 中，带 status: auto_approved 和 agent actor
    proposed_action.denied 被拒绝——终止状态。actor 是拒绝的人，payload.reason 是原因
    proposed_action.executed 执行成功
    action.failed 已执行但失败
    permission.granted 授权已写入策略

    Backlog

    类型 时机
    backlog.epic_created —
    backlog.story_created —
    backlog.story_transitioned 故事的状态变更。actor 说明是谁推进的：auto 模式下是 agent/po，manual 模式下是 user（RN-048）
    backlog.story_completed PO 用 complete_story 补全了一个已有的 draft 故事——关联规则，填写 RF/DoD/DoR——而不是重新创建它（RN-720）
    backlog.story_promotion_proposed PO 在 manual 模式的项目中完成了一个完整的故事：它保持 draft，等待用户决定，在此之前它的任何任务都不可领取（RN-048）

    backlog.story_archived 一个没有执行中任务的 draft 故事被归档，由用户或 PO（archive_story）完成：它及其任务离开 backlog、覆盖率、计划和领取；该行保留。带有 reason 和 taskIds（RN-727，ADR 0212）
    backlog.story_demoted 某个模块从 module_map 中消失；故事回到 draft（RN-012）
    backlog.story_overlap_warned 故事已创建，但它引用的所有规则都已被另一个故事覆盖——是警告，不是阻止：由用户判断是否重叠（RN-081）
    backlog.semantic_duplicate_warned 写入了一个故事或业务规则，其标题通过 embedding 与项目中同类型的已有项相比达到或超过阈值——是警告，绝不拒绝；payload 指出相似项和余弦值。Actor system/duplicata-semantica（RN-681）
    backlog.semantic_duplicate_check_skipped 语义重复检查未能运行——没有 embedding provider、daemon 宕机、10 秒上限——reason 说明是哪一种；该项照样被写入（RN-681）
    backlog.story_modules_assigned 故事 ↔ 模块的关联
    backlog.task_created —
    backlog.task_claimed 某个 dev agent 领取了任务
    backlog.task_status_changed —
    backlog.task_merge_conflict 任务 PR 已批准的合并因合并冲突被拒：taskId、pullRequestId、conflictingFiles、actionId。自 RN-715 起，任务回到 in_progress，所属 dev agent 被 outbox 中的 task.merge_conflict 行唤醒（RN-705）
    backlog.task_blocked 修正尝试次数耗尽，或登记了一个阻碍
    backlog.task_unblocked —
    backlog.epic_without_story PO 结束了一个回合，创建了一个史诗却没有为它创建任何故事。史诗不产生任务——故事才产生——所以这是一个在没有可见错误的情况下卡住执行的状态。按 RN-059 模式的显式结果：带 origem、epicIds/epicTitles 和消息的持久事件，外加 broadcast agent.error。每次发生只报告一次，绝不循环（RN-165）
    backlog.handoff_not_offered PO 结束了一个回合，所有业务规则都已覆盖，但未能向架构师提供 handoff：某个故事没有任务（origem: modelo，带 storyIds/storyTitles），或者读取 backlog 或创建提议失败（origem: infra）。当每个故事都有任务时，PO 的服务器自己会提供 handoff（RN-700）

    执行与 gate

    类型 时机
    execution.plan_proposed 自 ADR 0086 起已弃用（RN-284）——旧会话的日志中仍可能有这个类型；新会话使用 propose_execution_plan 类型的 proposed_action（参见 docs/reference/permissions.md），因为 Dev Lead 的计划变成了真正的决策，在"审批"中被批准或拒绝，而不再是一个简单事件
    execution.activated 执行阶段开始了。只能写入 criativa 会话——在 consultiva 会话中写入会返回 409（RN-097）。说明一个会话是否正在执行的，仍然是这个事件，而不是 sessions.kind 列
    execution.parallelization_suggested 系统提议并行化——只有当项目有一个登记为 running 的容器时才在激活时发出（否则 dev agent 会被阻塞，dev.blocked_by_container，更多 agent 只会让被阻塞的数量翻倍；AT-104）
    execution.plan_applied 人批准了 Dev Lead 的 propose_execution_plan（或它被自动批准），而这次批准激活了执行：计划中的每个任务获得了自己的模块，ActivateExecutionUseCase 运行了（RN-677，RN-678）。Payload：actionId、sessaoDeExecucao、modulos、tarefasAtribuidas，以及——当计划带有 tarefas 时——tarefasPorModulo 和 modulosSemTarefa（没有 agent 的模块，RN-709）。写入 Dev Lead 的会话，actor system/action-executor
    execution.plan_failed 已批准的计划没有激活执行——计划与现行的 module_map 不再吻合，或激活被拒绝（例如没有仓库时的 409）。Payload：相同的字段外加 motivo，即 api 自己的说法。人工决策被记录下来；当计划本身被拒时，任务上什么都没有写入

    Broadcast

    从 Phoenix 通道发往浏览器的消息。它们不被持久化：重新加载页面的人收不到它们——收到的是 event log。

    broadcast 含义
    agent.delta 模型流式输出的文本片段
    agent.status agent 可见的状态变化
    agent.done 回合结束了
    agent.error 回合失败了
    event.appended 有新事件进入日志——面板刷新的触发器；只带 type 和 actorId

    一个领域事件几乎总会产生一个 event.appended；反过来则不成立。自 RN-579 起，engine 会为 api 通过 EngineApiClient 门面确认的每一次写入（记录、提议的动作、handoff、PO 的 backlog）发出它，而对被拒绝的写入从不发出。api 自己完成的写入——人对动作做决定、会话状态转换——自 AT-157 起也会到达同一个 broadcast：api 在写入提交之后向 engine 请求它（POST /internal/sessions/:id/event-appended），而对来自 engine 的写入不请求，因为 engine 已经宣布过了。浏览器只把它当作触发器：使 type 影响的东西失效（事件和预算总是；动作、handoff 或 backlog 按前缀），每个目标有一个最小窗口，通道活着时，会话页面的轮询降到 15 秒（预算为 30 秒）。

    谁可以收听（RN-108）

    进入 session:<id> 通道——从而接收这些 broadcast 中的任何一个——需要一个由 POST /projects/:projectId/sessions/:sessionId/socket-ticket 签发的一次性不透明 ticket（TTL 30 秒）。在 RN-108 之前，Phoenix socket 的 connect/3 除了 session_id 存在之外什么都不检查：发现了 UUID 的人就可以进入并收听一切。ticket 既不持久化也不在 event log 中读取——它存放在 session_socket_tickets 中，由 engine 自己验证和消费——因此不会出现在下面的领域事件清单中。参见 RN-108。
