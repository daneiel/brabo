    外部视角

    Brabo 接收一个产品意图（"我想要一个做 X 的系统"），交回一个带有代码、测试和 决策历史的 git 仓库，由一个 AI 智能体团队产出。在输入和输出之间，每一个对外界有 影响的动作——运行命令、提交、开 PR、花费 token——都要经过一个由人决定的审批请求。

    从外部看，它是一个 Web 应用。它的不同之处在于，工作由与语言模型对话的长时间运行的 进程完成，而系统的构建方式使得没有任何事情会在没有痕迹、没有许可的情况下发生。

    这张图中有两件事并不显而易见，却能解释很多：

    engine 从不直接与 LLM 或 git 对话。 它请求 api。正是这一点保证了 metering、 预算和审批管道没有旁路——没有任何路径能绕过它们。

    api→engine 的通信是双重的。 一个通过 Postgres 中的 transactional outbox 的 异步事件（由 Oban 消费），以及用于同步命令的内部 HTTP。outbox 之所以存在，是因为 写入状态和发布事件必须是同一个事务；HTTP 之所以存在，是因为某些操作需要立即响应。

    outbox 排空三种 aggregate_type：session（自 Fase 5 起）、task（Fase 12b—— task.gate_resolved/task.became_claimable，在 gate 解决或新任务变得可领取后对 dev agent 的重新调度）以及 container（ADR 0143 /RN-502——container.running，在记录项目容器到达 running 的同一事务中附加，使因其缺失而停在 :idle 的 dev agents 自行醒来；用一个 独立的聚合而不是借用 task，因为这个事件与任何任务都无关）。 它之所以是 outbox，而不是像其他一样的同步 HTTP 调用：在 gate 裁决和智能体反应之间 engine 的一次重启不能丢失信号——这一行能比要读取它的进程活得更久，而 HTTP 无法在 等待响应者死亡后幸存。 一个崩溃的 dev agent（任何不是 :normal/:shutdown 的退出）不被当作已结束： Engine.Dev.Monitor 记录一个持久的 agent.error（来源 infra），并从它在 dev_agent_states 中自己的那一行重启它，最多三次；被中断的任务由已有的重启恢复 机制带着诊断阻塞（RN-742）。 dev_agent_states 增加了 consecutive_blocked/max_consecutive_blocked （断路器，RN-047）；完整决定在 ADR 0045 中。 因网络/provider 的暂时故障（DNS、连接重置、5xx/429）而阻塞的任务，会在 1、3 和 10 分钟后由一个 Oban job 再次解除阻塞（最多三次，通过人工解除阻塞的同一用例）， dev agent 暂停一分钟而不是去领取下一个任务（RN-864）。

    gate 智能体（QaLeadServer/SecOpsAgentServer）在中间转换时不经过 outbox （correct/run_secops 仍是内存中的直接调用——机制上的证明在 record-gate-verdict.use-case.ts 的注释中：只有终止结果 done/blocked 经由 outbox 传递），因此它们获得了与 dev agents 已有的相同的安全网：gate_states， 外加一个 GateRescuer，扫描停滞的周期并自行恢复它们——outbox 路径不需要新表，因为 问题不在于缺少 outbox，而在于同一进程中两次调用之间发生的事缺少持久状态。见 RN-140、ADR 0067。

    QA 的 gate 在 approved/changes_requested 之外还有第三种裁决： needs_user_decision，用于用户从未确认过的需求（或与现行决策相矛盾的需求）。它不 消耗一次修正；QA Lead 把它合并在 approved 之上，周期由 ADR 0207 的机制停放，直到用户回答 问题，这会恢复它。同一规则在会话侧的对应是工具 declare_open_question（Criativo、 PO、Arquiteto、Dev Lead），它写入 artifact.open_question；用户的回答作为 dev-context 中的"用户的决定"回到 dev 和 QA（RN-862、 ADR 0214）。

    请求 gate 的从来不是 gate 自己：Engine.Gates.Dispatcher 是一个有五个回调的 behaviour（PR 的 QA 和 SecOps、两个确定性的 infra gates 以及设计阶段的 AppSec——QA 策略的那个随 ADR 0192 移除，当时测试 计划变成了 PR 的 QA 自身的第一步），它唯一的工作是在需要时启动每个项目的 GenServer 并对其 cast。这层间接是为调用方的测试而存在的：Engine.Agents.DevLeadTools 由一个不带 Ecto sandbox 的轻量测试覆盖，而仅仅为了证明 gate 被请求过就在那里 启动一个真实的 GenServer，会把 Dev Lead 的测试绑到数据库上。五个中最新的 run_appsec_design/2 关闭了最后一个没有生产调用方也能触发的 gate： assess_implementability 现在并行请求用户故事的设计威胁模型——裁决从不等待它， 并且每个用户故事只请求一次（RN-539、 ADR 0090）。

    apps/web — React 19，src/ 中 487 个文件（2026-09-25 测量）

    src/lib/api-types.ts 和 src/lib/activity.ts 是值得先读的两个文件：前者是与 api 的契约，后者把日志的 40 种事件类型分类为可显示的东西——它是关于每个事件含义的最佳 事实来源。

    同一个 event log 的三种派生，回答不同的问题：

    文件 回答
    lib/activity.ts "发生了什么"——按时间顺序的信息流
    lib/agent-status.ts "谁存在，处于什么状态"——团队卡片
    lib/timeline-tree.ts "每个智能体做了什么，现在在做什么"——树

    lib/aprovacoes.ts 回答第四个问题，而它不来自 event log："如果我批准会发生什么"。 每种 proposed_action 的动词和句子都在那里，三个决策界面使用它们——审批队列、聊天中 的卡片和 Insights 标签页（RN-096）。

    联合类型 ActionType 曾经是一份副本，而副本过时了——两次，在生产中（Gitflow bootstrap 的三种类型；然后是 parallelize/raise_max_parallel），两次编译器都没有 察觉，因为 apps/api 不是 apps/web 的依赖。ADR 0116 关闭了这一类问题：ActionType 现在由 openapi-typescript 从 docs/reference/openapi.json 生成 （lib/api-types.generated.ts，由 lib/api-types.ts 重新导出），而不是手写，编译器 现在要求 lib/aprovacoes.ts 中的 Record<ActionType, ...> 映射在每次编辑时都穷尽。 api-types.ts 的其余部分——约 1600 行——仍然是手写的；只有这个被证明有重复成本的类型 迁移了。lib/aprovacoes.test.ts 也保留，但做更窄的工作：它不再需要抓出缺失的条目 （编译器会抓），只抓坏的——句子太短、没有句号、原始的 snake_case 泄漏到葡萄牙语 文本中。拿不准时，UI 仍然降级而不是让 React 树崩溃。

    树把信息流的轴反过来（先智能体，后时间），因为在一个有 Criativo、PO、Arquiteto 和 N 个 dev 的会话中，按时间排列的列无法回答谁在做什么。三者都没有自己的状态或路由—— 全部从同样的事件派生，不在日志中的事件不会出现在其中任何一个里。

    读取范围：项目界面按会话询问，列表界面按 workspace 询问。 在一个项目内部，查询 按会话和按项目进行，这是打开内容的自然切分。但仪表板和侧边栏显示所有项目，在 那里按项目切分会变成 N+1——每张卡片七个带轮询的查询，23 个项目时 3.824 req/min， 而限额是 300，界面会因 429 自己把自己拖垮。两者都读取 GET /workspaces/:id/projects-summary——一个跨聚合（git、预算、会话、backlog、架构） 的读模型，其与数据库的往返次数不随项目数量增长（RN-090）。

    铃铛抽屉遵循同样的切分，有一个值得记录的差异：它需要每个项目的已读截止点，而这个点 是保存在查看者浏览器中的一个 seq（lib/read-state.ts）——服务器没有、也不会有 "标记为已读"。因此客户端在 POST /workspaces/:id/unread-events 的请求体中发送 project → afterSeq 映射，尽管动词如此，它是一次读取并返回 200 （RN-091）。动词来自请求体，而不是一次变更：有几十对， 这么长的查询字符串会在代理处断掉，还会把项目 id 放进访问日志。

    这个端点返回 event log 的事实，从不返回组装好的组件：lib/agents.ts（谁是 lead、 图标、颜色）和 rosterFromFacts（lib/agent-status.ts）仍然是 web 的工作，在场规则 与团队面板使用的相同。这与上面三种派生是同一条边界——api 说发生了什么，web 决定据此 画什么。

    有两项 UI 检查是自动的：对比度（lib/contraste.ts，一个针对 design/tokens.css 的 测试）和布局（scripts/dev/validacao-visual.js，在浏览器中运行）。说明在 design/README.md 中。

    安装决定项目向导提供什么。 getProjectsBase（lib/api-client.ts）读取 GET /workspaces/:workspaceId/projects-base——本安装挂载项目的唯一基目录（ADR 0141）——新建项目向导是它唯一的调用方 （RN-513）。projectsBase: null 是正常状态，不是故障： 安装没有 BRABO_PROJECTS_BASE，于是挂载文件夹的卡片就不提供，container 仍是默认。 响应在途中以及查询失败时同样如此——未知永远不会变成提供，与 RN-088/RN-468 是同一条规则。 有基目录时，卡片预选，路径字段以 <base>/<slug> 打开，由 caminhoSugeridoNaBase （lib/wizard.ts）组成——一个纯函数，旁边是 caminhoDentroDaBase，它按路径段回答 "这个路径在基目录之下吗？"，并镜像 api 的 dentroDoEscopo。预选和建议都不会覆盖人的 选择。

    文件夹选择器是 web 中唯一有两种传输方式的读取，使其成为一体的接口位于 lib/fs-browser.ts（RN-504）。FsBrowser—— listarDiretorio / diretorioInicial / fechar——有两种实现，而它们不与同一台机器 对话：criarFsBrowserViaApi(workspaceId) 调用 api 中的 GET /workspaces/:workspaceId/project-folders，严格限定于 BRABO_PROJECTS_BASE （ADR 0141），而 connectFsBrowserChannel(projectId)（lib/fs-browser-channel.ts）使用 Phoenix 通道 terminal:<projectId>，通过 runner 读取用户的磁盘。

    接口之所以从通道模块中抽出来，正是因为它不再只有一种实现。FolderBrowserModal 用一个 可辨识联合在两者之间选择——origem: { tipo: 'api'; workspaceId } | { tipo: 'runner'; projectId }，而不是两个可选 prop，使"都没有"和"两者都有"不成为组件需要在 运行时处理的可表示状态——它的主体从不知道收到的是哪一个。只有三件事按 origem 分支： 运行哪个工厂、存在哪些快捷方式（api 传输不提供 /；它按构造就在基目录之外，按钮只能 以 400 结束），以及 RunnerOnboardingPanel 是否有意义。

    ListagemResultado 增加了三个可选字段——arquivos、simbolicos、truncado—— 它们是可选的，因为只有 api 传输会统计它排除了什么。runner 的协议（apps/runner/src/channel.ts 中的 FsEntrada）返回混在一起的文件夹和文件，什么也不统计；在那里填零会断言"没有 遗漏任何东西"，这与不知道是两回事。

    RN-504 把两种模式都指向 api 并声明了代价：对 runner 来说，列表不再是用户的机器， 而变成了基目录。之所以接受，是因为 runner 模式本要从创建向导中移除——它没有被移除， 而 RN-533（ADR 0151 第 7 点）撤销了它。现在是模式选择传输，因为它们回答不同的问题：mounted 询问 api （它的文件夹位于服务器上的基目录之下），runner 询问本地智能体（它的文件夹位于 服务器看不到的机器上）。runner 分支锚定在向导已提前创建的项目上 （RN-437）；当这次创建失败时，不会打开任何模态框，因为 回落到 api 会在"你的机器"的标签下显示服务器的基目录。

    失败带有一个可辨识的原因（MotivoDeFalhaDoAgente）：sem-agente 是服务器断言 没有 runner，sem-resposta 是超时、断开的 socket 或被拒绝的 ticket——无知，就作为无知 说出（RN-088/RN-468）。组件过去 用 includes('Nenhum runner conectado') 判断，匹配一句位于 engine 的 .ex 中的 pt-BR 句子；子串匹配现在只在一个地方，即拥有通道协议的模块中，engine 改写过的消息会降级为 sem-resposta，而绝不会变成"有一个智能体"。两个原因都会挂载 EsperaDoRunner——RN-474 的等待，被复用：同样的三种状态、同样的上限、同样的信号——它在时间戳变化时自行重做 失败的列表。每个界面一个等待：RunnerOnboardingPanel 接收 mostrarEspera，只在其宿主 已经显示一个的地方为假。而选择器在两种来源下都说明它正在列出的是谁的磁盘——此前 唯一的线索是一个快捷方式的标签，它命名的是一个位置，而不是一台机器。

    面板还会识别一台已配对的机器（RN-548、 ADR 0154）。lib/api-client.ts 中的 listRunnerDeviceKeys 读取 GET /projects/:projectId/runner-device-keys，自 RN-543 起它标记每把密钥的种类——而整个派生都在组件之外， 在 lib/agente-de-maquina.ts 中，因为规则关乎数据，组件关乎绘制。七种状态，没有 一种塌缩成另一种，失败由 isError 而不是某个状态派生，因此网络错误说"不知道"，而不是 永远转着"正在检查……"。已注册的密钥不是正在运行的智能体——与 workspaceVerifiedAt 已经施加的纪律相同——而列表属于账户而不是这个浏览器，因此能用的最强的说法是"你的 账户有一台已配对的机器"。这两个限制都在界面上说明。 ADR 0118 的浏览器流程 （生成密钥、下载二进制、写入文件夹）已在 ADR 0203 （RN-687）中退役：面板现在显示 install.sh 的命令，当识别到 服务于该项目的密钥时它就消失，而带 PAT 的手动命令放在一个以其回答的情况（另一台机器） 命名的 <details> 中。读取的最低要求来自针对端点的 developer 的 roleAtLeast， 真实的 403 落入同一状态——workspace 角色是代理，api 才是权威。

    代码标签页（FASE 26）是同样的读取模式，应用于代码而不是事件： lib/api-client.ts 中的 getContainerState/getCodeTree/getCodeFile/ searchCode/getCodeDiff 镜像 api 的读取路由（container 加上 code.controller.ts 中的七个，FASE 26b），类型在 lib/api-types.ts 中（EstadoDoContainer、CodeTree、 CodeFile、CodeSearchResult、CodeDiff），从 DTO 复制——与文件其余部分相同的约定， 不导入 apps/api。routes/code/ highlight.ts 是一个自有的基于正则的语法高亮分词器，零新依赖。ProjectCodeTab.tsx 的闸门（RN-107）在尝试读取代码之前询问容器的状态，使它作为独立的消息出现，而不是 作为一个 409 的脚注。

    FASE 26b 把 getCodeBlame/getCodePullRequests/getCodeBranches 加入同一模式， CodeBlame/CodePullRequestList/CodeBranchDetailList 在 lib/api-types.ts 中—— 代码标签页三个已声明待办项（RN-110/111/112）的基础。三者现在都有消费者： CodeEditor.tsx（blame 开关）、code/PrListAndDiff.tsx（PR 列表 + diff，被 CodeDiffPanel.tsx 和独立的 prs 标签页共同使用）和 CodeBranchPicker.tsx（丰富的 分支下拉框）。

    容器镜像闸门（RN-105）是一个单一漏斗（ReadProjectCodeUseCase.alvo），由七个路由 共享，因此在 Arquiteto 决定镜像之前它们中的任何一个都可能返回 409——不只是树。 ProjectCodeTab.tsx 用一次预检避免这个 409（RN-107，见上）；prs 标签页没有可以 预检的树/文件读取，所以 code/PrListAndDiff.tsx 对它自己的 getCodePullRequests/getCodeDiff 调用的 409 作出反应。两条路径渲染同样的呈现 ContainerImageGateNotice（components/ContainerImageGate.tsx），由 isContainerImageGateError（lib/api-client.ts，匹配 ApiError.status === 409）检测 ——这是使用中发现的 bug：在此之前，prs 标签页把这个 409 显示为通用的暂时错误，带一个 "重试"按钮，而对于只有 Arquiteto 采取行动才能解决的状态来说，这是错误的 affordance。

    全局容器页面（/containers，ADR 0136/RN-495）是 workspace 的读取，不是项目的—— lib/api-client.ts 中的 getContainersOverview 调用 GET workspaces/:workspaceId/containers，lib/api-types.ts 中的 ContainerOverviewItem 镜像 ContainerOverviewItemResponseDto。api 一侧是一个专门的读模型 ContainersOverviewRepository/DrizzleContainersOverviewRepository，与 ProjectsSummaryRepository 有同样的"项目之间无 N+1"纪律——三个恒定的查询（projects LEFT JOIN 容器行、批量的 artifact.project_image 事件、批量的待处理容器 proposed_actions），从不按项目查询。无法批量完成的——向 broker 询问观察到的状态—— 改为获得每次加载的显式预算（ObterVisaoGeralDeContainersUseCase.TETO_DE_VERIFICACOES_POR_CARGA， 只询问 provisioning/running 行，上限 20）：预算之外的行显示 naoVerificado，绝不 悄悄复用另一行的回答，也不继承已记录的状态。动作（停止/移除/启动）与其他地方一样是 proposed_action——页面从不直接调用 broker——每行的待处理动作（如果有）随同一次批量读取 一起到来，渲染为内联的 ApprovalCard，与 ProjectPrsTab.tsx 用于合并提议的模式相同。

    自 RN-521 起 join 是 LEFT，页面列出 workspace 的每个 项目，因为它成了人工启动第一个容器的路径：在登记之前就失败的启动不会留下行，而旧的 INNER JOIN 恰好隐藏了需要这个页面的项目。因此 ContainerOverviewItem.registrado 可为 空——类型中命名的第三种状态，不同于 stopped 和"无法观察"——没有容器的行永远没有资格 占用 broker 的预算，所以它们不能挤掉真实的容器。container_start（broker）与 container_start_via_runner（本地智能体）之间的分支是客户端的一个纯函数 routes/containers-subida.ts：它还决定何时不提供按钮（没有已决定的镜像、没有任何 智能体确认过其文件夹的 runner、按 roleAtLeast 低于 maintainer 的角色），每种拒绝 都有自己的文本——界面从不提议一个它已知会失败的动作，也从不隐藏原因。

    另一个提议者——Infra Lead 智能体——自 RN-566 起以同样 方式分支。它的两个工具都经过 infra_lead_server.ex 中唯一的 recusa_local_de_subida/2，它只读取项目一次（Project.get/1，同一个 BEAM 进程， 从不 HTTP：智能体循环内的网络调用正是这次修正付不起的代价），返回 nil 或一个命名的 原因，每个工具一个子句——container/mounted 提议 container_start，runner 被拒绝 并指向 container_start_via_runner，而 container_start 的子句是与 broker 一样的 允许列表，因此枚举中的新模式生来就被拒绝。拒绝是模型读取的工具结果文本（循环的 输入，RN-163），绝不是 agent.error，并且 tool.call 仍会发出，使本地拒绝永远不会从时间线上消失。智能体不检查而界面检查的， 是已决定的镜像和已确认的文件夹。

    边界与不变量

    这是最重要的部分。下面每一项都是可验证的，其中好几项有一个在违反时会失败的测试。

    1. 领域是纯的。 apps/api/src/domain/ 不导入 infrastructure、application、 @nestjs 或任何数据库驱动——已验证：三者都是零出现。方向始终是 interfaces → application → domain，application 中有 89 个文件导入 domain。如果你 需要在 domain/ 中做 IO，设计就错了：在 application/ports/ 中创建一个端口。

    2. 领域事件是不可变的。 事件表上永远没有 UPDATE。session_events 有 unique(session_id, seq)，且 seq 在每个会话内是连续的——恢复测试会验证没有空洞。 需要变化的状态（假设的生命周期、handoff 的状态）放在它自己的可变表中，与事件并列。 不再是现行的 handoff 提议在该表中变为 superseded，并获得它自己的 handoff.superseded 事件——绝不是对宣布它的 handoff.offered 的编辑（ADR 0182）。

    3. Harness 之外没有 LLM 调用。 这不是约定：engine 没有 LLM 客户端。它请求 api， 由 api 做 metering。

    4. 每个有外部效果的动作都变成 proposed_action。 在 permissions.json 中 deny 总是胜过 allow，而两个上限最后施加，覆盖已计算出的裁决：受保护分支上的合并和 指令补丁永远不能自动批准。见 RN-006 e RN-007。

    5. 受保护分支上的合并是手动的。 没有将其自动化的选项。这是领域中的一个上限 （decide.ts），由一个测试保证。

    6. 一个会话，一个所有者。 SessionServer 注册在 :global 下，而不是本地的 Registry——否则 N 个副本会托管同一会话的 N 份拷贝，而没有心跳的拷贝会杀死活着的 会话（ADR 0026）。

    7. 智能体故障记录来源（infra | model | code | policy），绝不是排除法诊断。来自 ADR 0020 的昂贵教训：一次 provider 宕机被记录为 "模型停止了而没有发出信号"，系统把一个基础设施问题归咎于模型。

    8. 项目的容器是被决定的，绝不是隐含的。 代码标签页只有在 Arquiteto 发出 artifact.project_image 之后才解锁——在状态为 sem_decisao 时，读取代码返回 409 （RN-105）。而 git push、开 PR 和部署不经过 终端，即使在项目范围之内：decide() 通过命令前缀识别它们，并在任何宽松步骤之前 返回 deny——不是 require_approval，因为"总是允许"会把模式写入 allow 并重新打开 这扇门（RN-106、 ADR 0065）。 容器的生命周期（配置、回收、清理）尚不存在——FASE 25 的一个已声明的削减，记录在 CLAUDE.md 中——因此这个不变量目前与 ADR 0055 的路径范围策略共存。

    而自 ADR 0143 /RN-502 起，已决定的镜像不再是唯一的前提条件：在项目的 容器被登记为 running 之前，dev agent 不领取任何任务。守卫位于 Engine.Dev.AgentIo.try_claim/2——唯一的领取点——而不仅在 api 的 activate-execution 中，因为重新水合会在不经过任何路由的情况下到达 try_claim/2 （DevAgentServer.init/1 -> finish_restart_recovery/1）。没有容器时智能体落到 :idle（唤醒仍能挽救的唯一状态），并用 dev.blocked_by_container 说明这一点。同一 规则的另一半是，Engine.Actions.TerminalExecutor 在没有容器时不再回落到 engine 进程 内的 System.cmd：它拒绝，并命名原因，就像 runner 模式已经做的那样。

    9. 会写的智能体必须能读，也必须能问。 这两半是同一个教训，来自一个只有写入工具 的智能体：PO 在 kickoff 时组装一次上下文，此后基于一张旧快照行事——面对缺口，它在 编造和停止之间选择（RN-164、 RN-165）。读取不变成 proposed_action （不变量 4 关乎外部效果，而读取不是），但它在 ADR 0060 的意义上受到约束：范围由路由 路径封闭、每次调用成本恒定、交给模型的文本有行数上限。而智能体的循环不会悄无声息地 结束——迭代上限发出 toolloop.limit_reached，未履行的义务发出带来源的持久结果 （RN-166）。

    横切关注点

    跨源。 web 从自己的源提供服务，并与另外两个源对话，因此 CORS 是一条架构边界， 而不是配置细节（ADR 0037）。四条 路径，只有三条经过 CORS：

    路径 机制
    web → api，HTTP Nest 的 CORS，WEB_ORIGIN 的精确源 + credentials
    web → engine，HTTP（/health） EngineWeb.Plugs.Cors，仅 health 路由
    web → engine，WebSocket Phoenix endpoint 的 check_origin——WebSocket 不经过 CORS
    api ↔ engine，HTTP CORS 不适用：服务器客户端，不是浏览器

    单一变量——WEB_ORIGIN——在两个服务中为前三条供值。独立地读取两次，正是 engine 的 CORS 最终没有任何源、而 check_origin 已有正确列表的原因；在 engine 中它现在只在 runtime.exs 中解析一次。

    而端口是源的一部分：在浏览器看来，:5174 上的 web 是另一个系统。这就是 vite.config.ts 使用 strictPort 的原因。

    认证。 first-party，在 api 的领域中——没有外部 IdP。密码用 argon2id，15 分钟的 EdDSA access token，以及强制轮换的不透明 refresh token；web 的会话保存在 httpOnly cookie 中，用 double-submit 做 CSRF。JwtAuthGuard 是全局的，通过 token 的 sub （即 users.id）读取用户；开放路由需要显式的 @Public()。

    没有任何 RBAC 决策读取 token 的 claim：角色来自 request.user.id 和数据库中的行。这就是 权限矩阵在更换签发者后无需改变而幸存的原因。决定见 ADR 0031 和 ADR 0032。

    engine 的调用不经过 JWT：/internal/* 路由是 @ServiceRoute()，EngineServiceGuard 以恒定时间比较一个共享密钥（BRABO_SERVICE_TOKEN）。整个表面在 security-surface.md 中分类，一个表格测试会拒绝未分类的新路由。

    授权。 领域中的 RBAC，有效角色从项目解析（回落到 workspace）。路由上使用 @RequireRole。

    错误。 领域错误是有类型的类（InvalidSessionTransitionError、 StoryNotReadyError），由 main.ts 中的全局过滤器转换为 HTTP。git provider 的错误由 单一契约规范化（ADR 0002）——调用方不知道它是在 与 GitHub 还是 GitLab 对话。

    日志。 在生产中三个应用每个事件都是单行 JSON，带有相关联的 trace_id；在开发 中对人可读。api 使用 pino，强制脱敏 apiKey、access_token、clientSecret 以及 api↔engine 的服务 token。每一行都说明它来自哪个类和方法，每个请求一行显示经过各层的 路径及每一步的耗时——见可观测性。

    事务。 模式是 unit of work：通过 outbox 在同一事务中写入状态和发布事件。在 事务之外发布会为一个从未持久化的状态创建事件。

    追踪。 端到端的 OpenTelemetry，trace_id 诞生于 web：浏览器生成 traceparent，api 把它作为父级采用，engine 采用 api 的。一个会话是一条根 trace—— traceparent 持久化在 sessions.trace_parent 中并在 outbox 的信封中传递，因此由事件 触发的异步工作留在产生它的那个 trace 中。

    插桩和导出是相互独立的（ADR 0035）： span 总是被创建，trace_id 总是进入日志，即使没有收集器；OTEL_EXPORTER_OTLP_ENDPOINT 只决定它是否离开进程。这就是 pnpm dev 中能获得关联的原因。

    密钥。 信封加密：每条记录一个随机 DEK，由主密钥包裹。通过 CREDENTIALS_MASTER_KEY_PREVIOUS 实现无停机轮换——见 runbook。
