架构决策

ADR 记录的是某件事在被决定的那一刻为什么这样决定。 它们是不可变的：任何 ADR 在被接受之后都不再编辑。当一项 决策改变时，会产生一份新的 ADR 来取代旧的——这正是 0018 的情况，它记录了对 0011 中所决定的 NoopDevAgent 的取代。

实际后果：一份 ADR 可能描述的是一个已不再是当前的状态。 要了解当前状态，请看业务规则、 架构和运维手册。要了解 推理过程，请来这里。

在这 61 份中，除了仍在等待实现的之外都已接受——目前是 0053、0054 和 0056，它们在各自文件中标为提议。0055 在 Fase F 实现时被接受。0154 和 0155 走了同样的路：在 Fase 30 实际运行过它们之后，于 2026-09-27 被接受，并附有一节"接受说明"，指出文本与代码在哪些地方不一致。没有任何检查会核对这句话：它在已经是 54 份时还说着 48，在已经是 59 份时又说着 58，这正是 ADR 0029（gerar > verificar > lembrar）的论点在反驳自身时得到印证。

决策按主题分组——即它所决定的产品前线——每份 ADR 只出现一次，位于其主要主题之下。主题存放在 docs/adr/temas.yml 中，与本页并列，而不放在 ADR 里，因为已接受的 ADR 永远不会被编辑（ADR 0202）；pnpm docs:check 会拒绝没有主题的 ADR 或放错章节的行。逐阶段的历史见阶段历史。

Git、仓库与分支策略​

git provider 的契约、仓库的创建与采纳、分支的保护与策略。

#决策
0001GitProvider 规范化契约的形态：九个操作和声明的 capabilities，由唯一的契约测试套件验证
0002错误规范化：六个具体类，没有公共基类——这种抽象曾被考虑并被拒绝，因为它目前还抵不上自身的成本
0003自动重试只用于读取，从不用于变更，采用 Full Jitter 和 4 次尝试
0004git 凭据的登记：数据库中专用的 enum，与 LLM 的 providers 只在类型上合并
0005Gitflow 的 bootstrap 分为六个幂等且可恢复的步骤；skip 即成功
0028分支保护在 GitHub 和 GitLab 之间存在差异——因此它不是闸门；闸门是领域
0030机械化的分支策略：规则 → 机制，逻辑放在可测试的脚本中，回传 gate，以及重新引入每一项裁剪的代价
0044采纳已有仓库，两张表中都有 origin（created|adopted），并以计划作为闸门：dry-run 就是 ADR 0005 的 check() 而不执行 run()，计划存放在游标中（快照，不是日志），在决策为空期间什么都不改变——Fase 2 的 runner 原样交给一个协作者，从不被过滤，只是不被调用；"分歧的保护"停留在布尔层面，因为契约只暴露了这么多（ADR 0028）
0056engine 在远程仓库上工作。get_local_repo_path/1 对所有不是 local 的情况返回 unsupported_provider，四个使用方会一起停下——dev 的 worktree、终端执行器、QA 和 SecOps 评判的 diff，以及项目上下文。不对称是根源：api 通过 HTTP 与 GitHub 对话（创建了仓库、提交、创建了分支），而 engine 在文件系统上工作，只认识本地 bare repo；远程项目完成了对话那一半，停在构建那一半。这正是阻止 FASE 13b 以写入的形式存在的原因。git 的管道已经是通用的——init + remote add + fetch + checkout 不在乎来源是路径还是 URL——所以缺的是凭据。engine 不接收主密钥：它在需要的时刻，通过已经存在的 /internal/* 通道向 api 请求工作用的远程地址。而且 token 永远不进入 .git/config，这一决定是 0055 的直接后果：把 https://x-access-token:TOKEN@… 写进 origin，就会把秘密以明文放进 RN-075 刚刚给 dev agent 开放了自动批准读取的文件夹里——一个 cat .git/config 就会返回 token，它会在下一个回合被送到 LLM 的 provider。范围防的是向外读取，而不是产品自己放进来的秘密。origin 保留干净的 URL，认证在每次调用时注入。凭据是 OWNER 的（RN-058），local 保持不变，凭据失败以来源 infra 拒绝
0139晋升是 --no-ff，而这条规则被打破了三次（#367、#394、#464）——第三次正是修复前两次的那个 PR。调查发现的恰恰不是检测上的漏洞：这个检查自 2026-07-27 起就存在，并且在两次 squash 晋升中都正确触发了；2026-08-25 的日志一字不差地写着 o merge em qa não é merge commit (1 pai)。缺的是一个接收者——由 push 触发、在永久分支上失败的 workflow 没有可以变红的 PR（merge 已经发生了），所以它只在 Actions 标签页留下一次没有任何东西指向的执行，而仓库在整个历史中 issue 数为零。因此 tag-release 增加了一个 avisar job 来开一个 issue（如果同一分支已有 issue，就在其中评论而不是再开第二个，因为一大堆相同的 issue 是教会人忽略它们的最快方式），认证使用 github.token 而从不用 PAT——一个无效的 BRABO_BOT_TOKEN 本身就是告警需要报告的故障之一，依赖于可能已损坏之物的告警恰恰会在需要时沉默。这条规则也延伸到 dev，但方式是狭窄的：dev 有意通过 squash 接收工作，因此"一个父提交就是缺陷"会在每个 PR 上触发；那里的缺陷只是带入了一条新边的 PR（它的 head 是一个 merge，其第二个父提交尚不在基线中）——即 #464，它的全部交付就是这条边。良性的孪生情况，即一个把 dev 拉进自身的工作 PR，head 同样是 merge，但它的第二个父提交已经在基线中。识别产生该提交的 PR 时按 merge_commit_sha 过滤，而不是按 .[0]：commits/{sha}/pulls 返回所有关联的 PR，而由于 dev 是整个周期都保持打开的晋升 PR 的 head，.[0].head.ref 会在每次工作 PR 的 squash 时读到 dev，从而让整个仓库不通过——这个错误曾被犯下，并在进入之前针对真实数据被发现。在整个仓库关闭 squash 经过测量后被拒绝：dev 上最近的六次 merge 都是单父提交的 squash，而 changelog.mjs 运行 git log --no-merges，所以这种修正会向每个工作 PR 收取代价，并改变 changelog 的生成。预防仍然悬而未决，属于产品决策：由 promote.yml 自己执行 --no-ff merge 可以在机械化方法的同时保留权限，但需要决定一次人工触发是否算作"手动 merge"
0165项目的仓库在发给Arquiteto的 handoff 被接受时创建，没有仓库时执行拒绝开始。v6.1.0 的一次真实安装（AT-092）显示，在任何仓库存在之前，Arquiteto 三次提议 open_adr_pr，发给 Dev Lead 的 handoff 停留在 offered，而 POST .../execution/activate 在一个三张 git 表永远为空的项目上回应 201。RN-522 把触发点放在发给 Dev Lead 的 handoff 上——在两个会往仓库写入的智能体（Arquiteto 和它激活的 Infra Lead）之后——而且这个触发点可以被跳过，因为激活执行从来不要求它。Arquiteto 只能被发给它的已接受 handoff 激活（来自 PO 或手动），所以触发点移到同一个 AcceptHandoffUseCase 中，在 activateAgent 之前，使用同样的机制（local，失败作为事件）。Dev Lead 的接受保留为第二道门，幂等——这是在旧规则下经过 Arquiteto 的项目的出路，也是一次失败的创建的自然重试——幂等性通过两道门针对 Postgres 和真实的本地 provider 得到证明。没有仓库就激活会变成一个在任何效果之前抛出的 409，其消息根据项目的 handoffs 选择（HandoffRepository.findByProject）；概览让按钮失效并以文字说明一次原因，发给 Dev Lead 的 handoff 卡片失去激活的捷径。已声明：在 Arquiteto 的整个阶段，git-bootstrap 会话会成为项目最近的会话
0217当 QA 处于测试阶段（QA_FASE_DE_TESTE=true）时，每次合并到 dev 都会在所有检查都通过后，自动开启并合并 dev → qa 的晋升；审批阶梯只豁免这一对由 bot 开启的晋升，qa → main 仍然是手动的

智能体的 harness、回合与会话​

一个智能体如何运行——上下文、工具循环、对话回合、会话及其状态。

#决策
0006确定性的上下文组装：有序的层次，每层有预算，可预测的截断
0007ToolLoop、工具目录和 ContextManager——与真实 LLM 交互的循环
0061会话的类型是创建时的数据，而执行仍然是事件。过去每个会话诞生时都一样，要找到 Criativo 必须先打开会话，然后再在顶栏里发现一个按钮——用户正是这样报告问题的。风险不在于新字段：而在于产品已经能够通过推导区分一个执行中的会话，findActiveExecutionSession 查找带有 execution.activated 的 active 会话（正是它让重新激活落在 dev agents 已经所在的会话上，第一次 dogfooding 的发现 #11）。记录一个类型会产生第二个来源，而两个来源会出现分歧——在这里，分歧关乎 dev agents 往哪里写。全部从日志推导行不通，原因在于时间：意图在任何事件之前就存在，在打开会话的那次点击里，而一个没人激活的创意会话根本没有可推导的事件。决策是让两者共存，回答不同的问题——kind 是创建时的意图且不可变，事件是执行的状态，findActiveExecutionSession 不开始查看 kind——并受一条防止它们冲突的规则约束：在 consultiva 会话中出现 execution.activated 是 409，永远不是静默转换。这道锁位于漏斗（AppendSessionEventUseCase）中，因为用户的路由和 engine 的 /internal/* 都经过它，在用例里加锁会留下另一个口子；并且它在 incrementSeq 之前运行，使被拒绝的尝试不消耗 seq。该字段在每个创建点都是必填的，包括四个内部创建点：可选会让调用方默默继承默认值。列的 DEFAULT 是 consultiva（能力最少的类型），而 BACKFILL 是 criativa，方向相反，依据是 0046 的论点——每一条现有记录都早于这种区分，其中一些正是 dev agents 现在工作所在的会话。随之而来的还有友好名称，它叠加在 hashtag 上而从不替代它（hashtag 是用来粘贴到 URL 里的；人名不唯一），以及会话页面的退出入口，此前它一个都没有。接受的代价：问题"这个会话执行吗？"今后有两个地方可查
0098PR 上的 413 request entity too large 根源在 Brabo 自己的 api，从来不在 LLM 的 provider（把责任归给 provider 的注释是错的）。两端一起修复（RN-412）：apps/api/src/main.ts 从未配置 Express 的 body 限制（沿用 100 KB 的默认值，而 Phoenix 在最重的 engine→api 方向 POST .../llm-turn 上接受 8 MB）——它新增了 API_JSON_BODY_LIMIT（默认 10 MB）；Engine.Harness.ContextManager.Default 的压缩在溢出之前结构上不可达——estimate/1 不计算 toolCalls（它们几乎不消耗 token），窗口只用了 context_window（128k，压缩前约 350 KB）。有效窗口变为 min(context_window, teto_de_transporte)，截断总是落在 ToolLoop 的迭代边界上，绝不把带 toolCalls 的 assistant 与回应它的 tool 分开
0163启动智能体回合的点击在接受时就响应，而不是在回合结束时，拒绝也不再是沉默的。在 v6.1.0 的一次真实安装中测得（AT-089）：回答 Criativo 的问题表单用了 97.3 s，确认就绪 97.3 s，确认架构 51.8 s——每次点击都被整个回合卡住，因为对话智能体的 handle_call 只有在回合的 Task 结束时才回应 engine 控制器的同步 GenServer.call，而超过 120/180 s 上限的回合会在一个本已成功的命令上变成 500。同一次安装显示了另一半：在 Arquiteto 的 kickoff 期间输入的一句 "Continue" 收到了 {:error, :turno_em_andamento}，控制器在回应 202 之前把它丢掉了——被接受、从未被读取、不留痕迹。决策：TurnoAssincrono.iniciar/3 一旦 Task 启动就回应 :ok（在持久化 agent.status: working 之后，永远不在之前），把 0086 只为挂起的 Dev Lead 所做的事推广开来——六个对话智能体一个机制，没有第二条路径。智能体在开始之前拒绝的内容仍然是同步的，并获得自己的状态码（409 turno_em_andamento/aguardando_aprovacao，422 sem_regra_de_negocio），由 api 带着 engine 的原话转发。api 的成功契约不改变（201 { ok: true } 一直意味着"已接受"）。界面不再把"调用已返回"理解为"回合已结束"，而是通过通道加上日志尾部来跟踪结束。发给 Dev Lead 的 handoff 在 Arquiteto 的收尾回合运行期间被扣住，以便继续在 Infra 的之后到达。已声明：在 engine 拒绝之前记录的 chat.message 保留在日志中（现在有了解释），而回合中途 engine 重启会让进度条一直显示，直到"Parar"。
0175Infra Lead 通过 composer 对话，成为第七个对话智能体（AT-141，维护者的决定）。RN-584 曾把这个问题留作开放并为"是"定了价：Infra Lead 的整个回合在 handle_call/handle_cast 内部运行——接受时没有响应，没有"Parar"，没有孤儿回合的关闭，调用上限 180 s 低于容器 propose_action 的 225 s（RN-605），而在 kickoff 期间发送的消息要在进程队列里等待整个回合。所以回合先改变：kickoff、gate 修正和消息都通过 Engine.Agents.TurnoAssincrono 开始，与其他六个是同一个模块——在其之前持久化 working 的接受、409 turno_em_andamento、用于"Parar"的 via_for("infra")、TurnoOrfao 以及自身上限 14 的 toolloop.limit_reached。Workflows 的汇总在 Task 内运行；回合进行中到达的 gate 修正会进入一个队列，并在回合结束时开始，因为没有 from 的 TurnoAssincrono 会丢弃它。之后 message/2 才获得了 infra 自己的子句（具名拒绝被移除），web 把 infra 放进 AGENTES_DE_CHAT，使它在是最近被激活的智能体时成为接收者；它的 handoff 保留自己的卡片（RN-499），并按卡片名称从对话流中排除。没有新的外部效果：同样的四个工具，一切有效果的东西仍然是 proposed_action。SOLO_CONVERSATIONAL_AGENTS 不变——Infra Lead 是领域的 lead
0177智能体回应所用的语言存放在三个地方——账户、会话和项目——作为 BCP-47 代码的开放列表，永远不放在 users.locale 中（AT-162，维护者在 AT-168/AT-169 中的决定）。没有 enum：每个位置都保存由 normalizarIdiomaBcp47 校验的规范 text（形式由 Intl.getCanonicalLocales 决定，语言子标签须为 api 的 ICU 所知，永远不是 und 或私有用途，最多 35 个字符），因为开放回应语言不需要资源文件，而 enum 每种语言都需要一次 migration。账户：users.response_language（NULL 表示自动，所有账户都从这里开始），以及由 CHECK 绑定的一对 detected_language/detected_language_confirmed_at——检测只有在确认后才算数（由 AT-163 写入）。会话：session_language_overrides，以 {session, user} 对为键，是配置而不是事件。项目：projects.language（AT-243，RN-619）。对有人类作者的回合，按个人的优先级：会话覆盖 > 账户的选择 > 已确认的检测 > users.locale，因此链条总是以一种语言结束；ResolverIdiomaDaRespostaUseCase 返回胜出者、来源和链条。已声明：目前还没有任何回合改变——传达给模型是 AT-164 的工作

0141创建一个 mounted 项目曾需要在 docker-compose.yml 中为 api 和 engine 手工编辑一行 bind-mount 并重启它们——这会杀死整个安装中所有进行中的智能体回合、终端 socket 和 LLM 调用，只为接纳一个项目。在 mounted 还是逃生通道时可以容忍；如今它成为带建议路径的一等选择，就不可接受了。于是：一个基目录 BRABO_PROJECTS_BASE，由运维者配置一次，以同一性（$X:$X）挂载到 api 和 engine，每个挂载的项目都住在它下面，永远不按项目编辑任何东西。是同一性而不是固定挂载点，因为 projects.workspace_path 是用户输入、界面回显的字符串：如果主机 ≠ 容器，产品就得选择保存两者中的哪一个，而任何选择都会让界面对某人撒谎——而同一性恰恰让 projectScopeRoot（api）和 Engine.Actions.Workspace.workspace_dir/2（engine）在零新代码的情况下继续正确，仍由开头的斜杠来决定。一个新变量，永远不是 PROJECT_WORKSPACES_HOST_DIR，有三个理由，第一个会对数据造成后果：被管理的 workspace 由 workspace_dir_name（UNIQUE）命名，而挂载的项目由用户命名，所以 <base>/loja 和一个文件夹名为 loja 的 container 项目会落在同一个物理文件夹中，init_from_bare! 会在另一个人的项目里执行 git init——schema 中没有任何东西阻止这一点，因为唯一性是在 workspace_dir_name 的值之间，从不针对 workspace_path 的最终名称。缺失是正常状态：baseDeProjetos() 返回 null 且从不抛出，GET /workspaces/:workspaceId/projects-base（maintainer，与 POST .../projects 相同的最低要求，因为决定这条路由提供什么是该值唯一的用处）把 null 带到客户端，向导就干脆不提供 Montado 模式——永远不要提供安装无法兑现的模式。而 /workspace 的盲点终于在可以设守卫的地方得到一个：scripts/dev/preflight.mjs 在基目录与 Brabo 的 checkout 在任一方向上重叠时拒绝启动整套服务，因为它在主机上运行——api 比较的是 process.cwd()，即它自己容器内的 /workspace，所以把 Brabo 克隆到 $HOME/brabo 并把基目录指向那里的人能通过现有的所有校验，并让 dev agents 在产品自己的目录树中执行，这是 ADR 0055 的失败从一扇它没看守的门进来。声明的两项代价：基目录下的 symlink 在两侧解析结果不同（文件夹浏览器拒绝进入 symlink 并统计它们；物化时的磁盘检查才是捕获分歧的地方，作为具名失败），基目录之外的代码需要移动文件夹——v1 支持一个基目录，拒绝消息如实说明这一点，而不是暗示有隐藏的配置
0142ADR 0141 决定了 mounted 项目住在哪里，并明确把另一半留给下一个 PR：这个文件夹何时开始存在。产品所有者的要求是字面的——"se for Pasta montada, o bind-mount deve ser criado DEPOIS da decisão do arquiteto"（如果是挂载文件夹，bind-mount 应在 Arquiteto 做出决定之后创建）——而今天的代码让它不可能：validarCaminhoDeWorkspaceLocal 在项目创建时运行，提出三个磁盘问题（存在吗？是目录吗？本进程可写吗？），任何一个失败就以 400 拒绝。创建是流程的第一个界面；Arquiteto 的决定在许多个会话之后才发生，所以在创建时要求文件夹就绪，就是要求它在任何决定存在之前就存在——这正是阻止 mounted 成为一等选择的原因，因为向导建议的路径按构造就是一个尚不存在的路径。于是 mounted 采用 runner 已有的纪律（RN-423）：创建时只做词法谓词，再加上一条自己的新规则——路径必须位于 BRABO_PROJECTS_BASE 之内，这是 api 和 engine 容器唯一能看到的机器文件夹，没有配置基目录时，该模式在此安装中不可用，拒绝会如实说明。推迟的验证在 materializarWorkspaceMontado 中回归（mkdir -p 加上同样的三个磁盘问题，在 mkdir 之前拒绝基目录之外的路径，以免产品之外写下的路径让 api 在它能触及的任何地方创建文件夹），从两个地方调用：ExecuteContainerStartUseCase，常规路径，Infra 启动容器时创建文件夹并盖上 workspace_verified_at——那里的失败是具名的 failed，从不 throw，生命周期不标记为 provisioning，因为先标记再发现不能写入会让这一行断言一个从未存在的状态；以及 ConvertProjectExecutionModeUseCase，声明的例外，它没有可以挂靠这项工作的容器步骤，并紧接着把 permissions.json 移进这个文件夹。有意不改变的是 caminhoDeWorkspaceLocalValido：基目录规则不放进它，因为这个谓词通过 projectScopeRoot 在每次读取时运行，一个基目录之外的遗留 mounted 项目会仅仅因为被读取就开始崩溃。没有 migration，CHECK (execution_mode <> 'container') = (workspace_path IS NOT NULL) 保持不动——推迟验证从不触及配对不变量
0146Montado 模式已经就绪却无法到达：ADR 0141 构建了单一基目录，ADR 0142 使建议一个尚不存在的路径成为可能，但产品中没有任何地方真正请运维者配置 BRABO_PROJECTS_BASE——所以 GET /workspaces/:workspaceId/projects-base 在 web 中没有调用方，该模式干脆从未被提供。因此 pnpm bootstrap 增加一个同意步骤：它提议 $HOME/projetos-brabo（在 $HOME 下，因为这是 Docker Desktop 默认共享的——一个需要先打开 Docker 设置的默认值是一个伪装的问题），而不是 $HOME/brabo-projetos，因为 .env.example 已经把这个确切名称用作 PROJECT_WORKSPACES_HOST_DIR 的注释示例，即产品管理的根目录——这正是 ADR 0141 拒绝的混淆，因为 <base>/loja 会与一个 workspace_dir_name 也是 loja 的 container 项目冲突，bootstrap 会在另一个人的项目里执行 git init。名称只是绕开；保护是机制：脚本拒绝任何等于该根目录、包含它或被它包含的基目录，复用已经支撑 baseSobrepoeOCheckout 的 dentroDe。由 scripts/dev/consentir-base.mjs 用 Node 编写而从不用 bash，出于两个测量过的原因：bootstrap.sh 没有写变量的 helper（garantir_env 只复制示例，唯一的就地写入者是 preflight.mjs 中的 escreverEnv），以及——决定性的——菜单项无法提问，因为每个菜单命令都在后台运行、stdin 为 /dev/null，以免有东西抢走用户的方向键；写在那里的同意步骤按构造就是一个无法征得同意的步骤。Docker Desktop 的文件共享通过挂载来证明（docker run --rm -v <base>:/sonda ... ls /sonda），从不读取 settings.json：该文件没有文档，在 macOS 和 Windows 之间不同，随版本变化，描述的是用户配置了什么而不是守护进程将会做什么——与产品对 LLM providers 已经应用的规则相同，只有经执行证明的 capability 才被声明（ADR 0041/0042）。这成为产品的第二个平台守卫，与 validarDirDentroDoHomeNoLinux 并列，两者在原则上对称：每个只在限制有意义的地方施加限制。broker 只在本地 compose 中离开 profiles: ["container-broker"]——ADR 0130 选择那个 profile 是因为*"nada o chama para escrever ainda... em troca de nada"*（还没有东西调用它来写入……换来的什么也没有），而这个前提已经死了：ADR 0133/0136 给了它四个真实调用方，ADR 0144 让 mounted 通过 broker 启动容器，所以当 mounted 成为本地默认值时，broker 就是区分默认模式与 BrokerIndisponivelError 的那个东西。不对称性是支撑这一点的：运行 pnpm dev 的人已经拥有 Docker socket——他在运行 docker compose——所以 broker 获得它并没有授予运维者所缺的任何东西，而在生产中 socket 是真正的特权边界，运维者也不是开发者。五层隔离保持不动：这改变的是 broker 何时运行，从不改变它接受什么

项目容器与 broker​

项目容器的生命周期、镜像的决定、Docker 端口，以及与守护进程对话的 broker。

#决策
0065每个项目一个容器：边界不再是策略。修订 0055，它曾自己声明了这项待办：路径范围是策略，不是隔离——只要 Brabo 的 monorepo 挂载在执行命令的同一个容器中，边界就依赖于策略判断正确，而从内部指向外部的 symlink 不会被发现。发现 Z 和 AD（动词白名单不收敛——动词、形式和调用是不同的空间）强化了 FASE 13 的同一结论：通往自主的道路不经过放松策略，而经过更换边界。用户的决定，原文如下：每个项目获得自己的容器，智能体在其中是自由的（读、写、安装、构建、测试、运行），而 Code 只有在 ARQUITETO 决定启动哪个镜像之后才开放——他是知道技术栈需要哪种运行时的人。镜像作为工件诞生（事件日志中的 artifact.project_image，版本化，无表——修订就是重新发出），带有显式的 OCI tag（拒绝 latest）和必填的 rationale；闸门（RN-105）让 Code 标签页在 sem_decisao 期间回应 409，位于已经包含路径的同一个函数中（RN-092），从不在四条路由中重复。剩下的边界在外面：git push、PR 和 deploy 不通过终端出去——即使在项目范围之内——规则是 deny，而不是 require_approval，因为"sempre permitir"会把模式写入 allow，一次点击就会永远重新打开这扇门；消息把人引导到有类型的动作（git_push/git_merge/pr_open），那本来就是 dev agent 的真实路径。网络在工件中一次性决定（默认 network: none，egress 由用户授权），而不是逐条命令——为出站重复白名单就是重复 Z 和 AD 证明不收敛的错误；开销（cpus/内存/pids）有上限，超出时拒绝而不是静默降级。诚实且已声明的裁剪：容器的生命周期（创建、回收、清理、重启后留存什么）留给有 migration 名额的阶段——容器状态是可变的，需要表，而一个启动后不回收的容器比没有更糟。后果：终端策略中"内部自由"的那一半尚未改变；在墙真正立起来之前，0055 原样有效
0081容器的生命周期：状态表，没有编排器。关闭了 0065 自己声明的裁剪（"O que este ADR NÃO faz"）——project_containers（migration 0046）记录可变的状态（status、指向 Arquiteto 决定而不复制它的 image_version、container_id、声明的资源上限、failure_reason），每个项目一行，就像 engine 中的 dev_agent_states（0045），带有纯状态机（provisioning → running ⇄ stopped，三者都可到达 failed，removed 只能通过重新创建离开），格式与 session-state-machine.ts 相同。事先调查确认产品中没有服务挂载 /var/run/docker.sock 或以 privileged 运行——因此两个用例（Registrar/ObterCicloDeVidaDoContainer）只写和读，没有对 Docker 的真实调用：为了"真正能用"而挂载 socket 就等于做出一个没人在这一切片中要求的安全决定（升级到 root 的向量）。第一次转换（provisioning）要求镜像已经决定（RN-105，与 Code 标签页同一个闸门），并在这一行中冻结版本/资源；处于 workspace_mode: 'local'（0072）的项目被拒绝，因为它不启动自己的容器。没有新的 HTTP 路由——还没有真正的使用方，暴露一个就是猜测契约
0083Terminal 标签页获得生命周期的真实使用方，而不是终端。修订 0081 中把 HTTP 路由推迟到出现真实使用方的那部分——这条前线（PROGRAMA 28，Onda 5/F2）就是那个使用方。原计划是完整的交互式终端，但 FASE 25b 仍被裁剪：没有服务挂载 /var/run/docker.sock，生产中也没有任何东西转换 project_containers（ADR 0081 创建的是表，不是编排器）。实现一个假的终端——或者在 Brabo monorepo 的同一个容器中运行，即 0055 已经描述为策略的那笔债——就是编造能力，与 ADR 0041/0042 对 provider 和模型所拒绝的错误相同。真正的交付：GET /projects/:projectId/container/lifecycle（RN-267），忠实映射 ObterCicloDeVidaDoContainerUseCase，以及 CodeBottomPanel.tsx 在已有的说明文字之下——从不取代它——显示这个状态（翻译后的徽章、失败原因），只在 Terminal 标签页打开期间获取（RN-268）。null（从未创建）是今天诚实且最常见的结果
0128runner 中对 Docker 的访问被放到一个恰好有五个操作（start/stop/remove/inspect/exec）的端口之后，实现是由一次失败的证明选定的。dockerode 被安装、导入、实例化，并通过针对真实工件运行的 --self-test-docker 标志进行了实际调用（ping()）——从不是打包器可能通过 tree-shaking 消除的 import。tsup 通过了（它把 dependencies 保留为外部 require，所以 dockerode 从未进入 bundle）；bun build --compile（ADR 0112，独立二进制）失败了，错误按原文记录：Could not resolve: "../build/Release/cpufeatures.node"。这条链是必然的，不是偶然的——docker-modem/lib/modem.js 在模块顶部 require ./ssh，ssh2 require cpu-features，而这个可选的原生 binding 被包在一个打包器所没有的运行时 try/catch 中。与 ADR 0112 为 node-pty 记录的同一类问题，差别在于决定性的一点：那里 binding 是必需的，这里它加速的是这个 runner 从不使用的 SSH 传输（它与本地 unix socket 对话）。已测量且未采用，免得有人重做调查：--external cpu-features 可以编译（280 个模块对 79 个，每个二进制 +1.7 MB × 5 个平台），dockerode 在二进制内能工作——这恰恰是产品所有者事先排除的那种巧妙绕法。于是 runner 使用 execFile('docker', …)，dockerode 离开 lockfile，而 BROKER（PR 1.2）不继承这个决定：它以我们构建的镜像交付，从不变成独立二进制。隔离靠的是类型，而不是调用方的自律：没有 privileged/cap_add 的字段，RedeDoContainer 是 `'none'
0130容器 BROKER 诞生——一个新的 Node/TS 服务（apps/broker），是产品中唯一在服务器上与 Docker 守护进程对话的进程，api 永远拿不到 socket。三个不可分割的决定。第一，端口移动位置：docker-port.ts 和 docker-cli.ts（以及两个 spec）离开 apps/runner/src/，进入一个新的 workspace 包 packages/docker-port，由 runner 和 broker 使用——正是 ADR 0128 写下的会做的事，从不复制，因为"一个带着同样五个操作外加第六个'仅 broker'操作的第二份文件，就是隔离终结的开始"。packages/shared 因其声明、并由 packages-shared-so-tipos.spec.ts 保持诚实的不变量被拒绝（100% 类型，如果有运行时值在 tsc 之后留存，api 的生产镜像会以 ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING 死掉）；新包没有构建步骤，由两个使用方打包（tsup、bun build --compile），这就是为什么 api 不能使用它，以及为什么 validarDecisaoDeImagem 不移动位置。独立二进制在这次移动中存活，已测量：build、build:bin、smoke 和 smoke:bin 全绿，Bun 的 bundle 从 79 → 83 个模块，npm pack --dry-run 不变。第二，也是该服务的目的：broker 不接受容器 spec。它接收一个 projectId 加上五个操作之一，在 api 本身读取 Arquiteto 的决定（GET /internal/projects/:projectId/container-spec，RN-485），并组合镜像、网络、资源和唯一的挂载——没有可以写 privileged、cap_add、network: host 或自由 -v 的字段，因为根本没有字段。它重新校验 api 返回的内容，因为依赖调用方正确的隔离不是隔离，而两次校验回答不同的问题（api 的那次是关于工件是否可修订；这次是把不可信的 JSON 解析为封闭类型）。有一项检查只存在于此且是新的：以 - 开头的镜像引用会被 CLI 读作 FLAG——没有 shell 的 execFile 解决的是命令注入，不是参数注入。第三，api 不发送任何路径：-v 由守护进程针对主机的文件系统解析，所以 api 容器内部的路径会静默地挂载一个空文件夹；broker 把 workspaceDirName（RN-109）与自己的 PROJECT_WORKSPACES_HOST_ROOT 拼接，缺少它时拒绝 start 而不是去猜。pidsLimit 进入端口，理由值得一提——工件一直带着三个数字，丢掉一个就会让它承诺一个容器得不到的上限。由五个独立层隔离：没有发布的端口，一个只有 api 进入的 internal: true 网络，以常数时间比较的共享 service token，五个操作，以及计算出来的 spec。它在两个 compose 中都以 profiles: ["container-broker"] 交付，因此默认关闭，其镜像不发布到 GHCR——docker-bake.hcl 和 ALVOS 保持 ADR 0119 的四个镜像。api 获得一个端口和一个 HTTP 客户端，其唯一的调用方是 inspect：容器生命周期路由开始在登记的状态旁边返回观察到的状态，从不合并，当没有办法查看时用 naoObservado 说明原因（RN-486）——所以表现在可能说谎，而读取会说出这一点。没有任何东西启动容器：没有循环、没有队列、没有 container_start 的 proposed_action，RegistrarTransicaoDeContainerUseCase 逐字节保持不变，包括按模式的守卫

用户机器上的 CLI——通道、凭据、设备密钥、分发、基目录和服务。

#决策

0156自我降级的上限延伸到另一扇门：移除自己在 project_members 中的那一行。ADR 0127 只在写入路径上设了上限，并书面把这个动作排除在外，把它固定在一个名字就记录了这个漏洞的测试中——"a remoção AINDA consegue rebaixar quem a chamou"——并预见了关闭它的代价（RemoveProjectMemberUseCase.execute 的签名）。这就是那个下一个人。移除不会抹去一个角色，而是替换有效角色：projectRole ?? workspaceRole（RN-471）改为由第二项解析，所以一个权限来自项目行、在 workspace 中是 viewer 的 maintainer 会不可挽回地降为 viewer——恢复需要 POST :projectId/members，而它要求刚刚放弃的 maintainer 本身；如果没有任何 workspace 角色，下降就是降到没有访问权限。规则是上限 2，不是新上限：ehAutoRebaixamento 比较今天的有效角色与之后的有效角色，从来不需要知道第二个是经由哪条路由到达的，所以 remocaoEhAutoRebaixamento 把 workspace 角色作为请求的角色委托给它，而不重新实现任何比较。它作为独立函数存在，只为另一个函数的签名无法表述的唯一情况——没有 workspace 角色的执行者，那里的"之后"是无，而这不是一个 Role。上限 1 有意不获得配对：owner 是 ROLE_ORDER 的顶端，所以移除 workspace 所有者的项目行只可能提升其有效角色——这实际上是撤销上限 1 所禁止创建的限制的唯一方式，在那里设上限只会拒绝良性的动作，并使 ADR 0127 生来要消除的状态永久化。表述没有阈值，与上限 2 一样，声明的代价也随之而来：从项目的 owner 自我移除为 workspace 的 maintainer 是可逆的，也会被拒绝——这是唯一一个原本通过、现在被拒绝的良性动作。消息是自有的，因为点击"移除"的人没有要求改变角色，应该得到机制的说明，而不是 add 的那句话。拒绝的方案：移除上的所有者上限、第二条比较规则、触碰 forProject、扩展到 workspace 范围（其 POST 仍然没有上限，其成员 @Delete 不存在）、阻止移除其他会下降的人，以及客户端闸门——MembersSection.handleRemove 已经在 toast 中显示 mensagemDaApi，只计算界面能算的那一半就是 ADR 0127 拒绝的半个闸门。关闭 BRB-001
0157自我变动的上限延伸到 WORKSPACE 的 upsert，而 ADR 0127 书面保留的自我晋升被视为漏洞并关闭。AddWorkspaceMemberUseCase 是一个十二行的转发，从不接收执行者，位于一条要求 owner 的路由上：与 project_members 同类的缺陷，高一个范围且更糟，因为这里没有更高的层级来接住下降，而且根本不存在成员的 @Delete（经测量；ADR 0156 曾用同一事实来推迟这件事）。一个把自己写成 viewer 的 owner 会失去整个 workspace——每个项目、按 RN-060 属于他的 LLM 开销，以及邀请能恢复他的人的能力本身——而撤销就是这同一条路由，要求刚刚放弃的 owner。上限不计算 owner 数量，依据 ADR 0127 的字面标准（"enunciado como cláusula, não tem número para envelhecer"）：计数会增加一次可能与写入不同步的读取，需要判断一个已经离开公司的第二个 owner 是否还算数，并让同样请求体的同一请求今天通过、明天被拒绝。最有力的论点是，这条子句已经产生了计数本应保证的不变量——workspace 永远不会剩下零个 owner，因为移除最后一个需要那个 owner 自己去做，而那正是被拒绝的动作。上限 1 在这里不获得配对，这经过了考虑而没有镜像：与移除（ADR 0156）不同，这个动作存在——一个 owner 可以降级另一个 owner。它被拒绝是因为上限 1 是关于层级倒置的规则，而 @RequireRole('owner') 已经让这个范围内的倒置不可能：能调用的人永远不会低于他所触及的人。加上它，再加上缺失的移除路由，会让 owner 成为一个无法通过 HTTP 离开的吸收态——离职、所有权轮换和错误邀请的修正都需要直接写数据库，这正是 ADR 0127 生来要消除的那类状态，只是符号相反地被重建。所以降级另一个 owner 保留，任何剩下的 owner 都可以通过同一条路由撤销。自我晋升在两条成员关系路由上都关闭。ADR 0127 曾把它记录为保留的能力（"os tetos são sobre descer"）；在这里重新打开后，答案是两半是同一个动作——一个人独自决定自己拥有什么权限——而上面那一半是唯一会提升特权的，恰恰是那份 ADR 能断言它的上限从不会做的事。重写相同的角色仍然通过：幂等的 upsert 不是变动，拒绝它会破坏 seed.ts。比较不被复制：它变成一个分类器 autoMovimentoDoProprioPapel，返回方向而不是布尔值，因为调用方需要它来选择消息。ehAutoRebaixamento 作为这个分类器的一种读取方式保留下来——是有意的，而不是为了兼容：remocaoEhAutoRebaixamento 委托给它，扩大它会让移除也拒绝自我晋升，破坏 ADR 0156 点名保护的良性动作。四条消息，每个方向和每个范围各一条——尝试晋升自己的人不会读到降级的那句话，在 workspace 被拦下的人也不会被叫去找 maintainer。拒绝的方案：计算 owner 数量、这个范围内的所有者上限、创建 workspace 成员的 @Delete（一扇新门需要同样的上限外加对最后一个 owner 的判断）、扩大移除之门、连续第三份 ADR 触碰 forProject，以及客户端闸门——没有什么可构建的，因为 apps/web 中没有这条路由的调用方。声明的代价：一个合法需要 owner 的 maintainer 现在要依赖另一个人。关闭 BRB-002
0158信封开始说明是哪把主密钥封装了它，而这个标签从不决定它能否打开。运维手册的那一页自己就陈述了这个漏洞（"O wrapped_dek guardado no banco não identifica qual chave o embrulhou"），由此产生两个缺陷：轮换的中间一步没有进度——中断它的人不知道停在哪里，"旧密钥上还有东西吗？"在 SQL 中没有答案，只能按打印出的计数器再跑一遍脚本——而且错误的密钥和损坏的 blob 落入同一个 catch，两个行动相反的诊断穿着一件通用失败的外衣。于是两张信封表都获得一个可空的 key_id，总是一起，因为它们共享信封和脚本，只改其中一张会留下一个查询只能回答一半的存量。值是密钥的指纹，HMAC-SHA256(derived key, label) 截断——它通过测量而非假定回答了活动留下的开放问题（"não um hash da chave, isso dá a quem lê o banco um oráculo de verificação offline"）：信封是 AES-256-GCM，它会认证，所以针对 wrapped_dek 测试候选口令本来就是一个完美的预言机，代价是一次 scrypt；针对指纹测试它代价相同。没有制造任何预言机，也没有增加任何变量——运维者不需要在任何地方输入指纹，它是已发布密钥的纯函数，这正是让"又一个要保持同步的元数据"这一旧异议对任意 id 成立、而对指纹不成立的原因。标签是可观测性，从不是权威，这正是此决定偏离显而易见方案的地方：decrypt 逐字节保持不变，rewrap 仍然通过尝试来判断"已经在当前密钥上"。用标签来跳过尝试曾被考虑，并因其特有的失败模式被拒绝——一行标为"当前"、而信封实际在旧密钥上的记录会被静默跳过，不计入重新封装的数量，第 3 步会让它永远不可读，把元数据的不一致变成秘密的丢失。所以标签在密码学决策之外服务于三件事：进度查询（IS DISTINCT FROM，从不是 <>，以便 NULL 计为待处理）、没有任何密钥能打开时的诊断，以及 rewrap 在新信封旁写下的戳记。没有回填：key_id 在下一次写入时产生，已有的行保持 NULL，表示*"在这一列之前写入"，从不表示"在当前密钥上"*——声明的代价是，在已有安装上，这个查询只有在第一次轮换之后才开始有意义。api 在启动时打印当前的指纹，因为一个没人能与任何东西比较的列是无用的。拒绝的方案：KMS/HSM/按租户的密钥（ADR 0027 仍然有效）、key_id 上的索引，以及把诊断带进热读取路径
0173workspace 成员的移除诞生，由同一条子句设上限。DELETE /workspaces/:workspaceId/members/:userId（owner，204）终结了通过写数据库来办理离职，那是 ADR 0157 拒绝顺手打开的。上限 2 被继承而没有新规则——remocaoEhAutoRebaixamento，以 workspace 角色作为今天的有效角色，以无作为之后的角色，因为上面没有东西接住下降——所以移除自己总是 403，而同一条子句不计数地保护最后一个 owner：只有 owner 调用这条路由，而没人能移除自己，所以每次移除至少留下调用者。移除另一个 owner 是允许的；上限 1 仍然没有配对。移除在一个事务中级联（目标在该 workspace 中的 project_members 行、项目设备密钥及其在那里的 PAT），然后通过 RN-520 的路径按项目断开他的活跃 runner。声明为开放：workspaces.created_by 不变，所以移除创建者会让智能体继续花费创建者的 LLM 密钥（RN-058）。

0202ADR 索引按主题分组，主题在 ADR 之外（AT-137，所有者 10月1日的决定，发现 BRB-026）：docs/adr/temas.yml 保存 15 个主题的封闭列表以及每个 ADR 一个主要主题，使任何已接受的 ADR 都不被编辑，即使是为了获得 frontmatter。索引是核对的，而不是生成的——一行描述仍然是人工精选的——docs:check（scripts/docs/temas-de-adr.mjs，每条规则由变异证明）让没有主题的 ADR、不在列表中的主题、没有 ADR 的主题，以及放错章节、不在任何章节或不按数字顺序的索引行失败。分类法来自产品的前线，而不是阶段或代码文件夹，是 lane 提交给所有者审阅的提议；新 ADR 的作者在同一个 PR 中选择它的主题，超过 15 个主题需要一份 ADR
0206API 参考变成在服务器端渲染的一个 Redoc 页面（redocusaurus），位于 /reference/api/，修订了 0033 中发布的那一半：OpenAPI 的插件和主题拖入了 postman-collection → @faker-js/faker@5.5.3（High 告警 #43），没有修正的途径。按操作的页面、按 tag 的侧边栏、按操作的 URL、playground 和 cURL 片段按所有者的决定移除；api-render-check.mjs 现在断言标题以及每个操作一个 SSR 章节
0216文档和界面使用四种语言——pt-BR 成为来源和默认，英语、俄语和简体中文作为分阶段的翻译，测量一致性，并对未翻译或过时的页面逐页给出提示（AT-545，所有者 10月15日的决定）
0218每个 ADR 都命名为“ADR NNNN — 标题”：H1 加上 ADR 前缀、4 位编号和破折号；文件名（即 URL）不变，规范标题标签不算编辑决策（AT-559，所有者 10月15日的决定）
0219参考文档纳入翻译：docs/reference/** 成为 pt-BR 源，被翻译并计入平价统计（包括生成块），平价报告本身和 openapi.json 除外；Redoc 页面留给 AT-565（AT-564，所有者 10/15 的决定）
0220API 页面按目录翻译：源仍是 api 装饰器文本（pt-BR 源的例外），每个语言环境一个以文本哈希为键的目录，spec 在构建时派生且不进 git，孤立键失败、缺失只警告，Redoc 固定标签保持英文（AT-565，所有者 10/16 的决定）

约定​

  • 每个决策一个文件，位于 docs/adr/NNNN-short-title.md，使用 4 位顺序编号，标题为 # ADR NNNN — <标题>（0218）。编号不复用，即使一份 ADR 被取代——下一个是 0220。
  • 每个决策一个主题，由编写 ADR 的人在同一个 PR 中选择：docs/adr/temas.yml 中的一行，以及该主题章节下的索引行， 按数字顺序。审阅者确认。新主题是 对 temas.yml 中列表的修改，在添加它的 PR 中说明理由；超过 15 个需要一份修订 0202 的 ADR。
  • 三个章节，仅此三个： 背景（促成它的问题或力量）， 决策（决定了什么），后果（接受的权衡以及 留待以后的事）。
  • 不使用第三方模板——不用 Nygard、MADR 或其变体。三个 章节就够了。
  • 用葡萄牙语，与项目的其余部分一样。
  • **已接受的 ADR 不被编辑。**被后续决策取代的 ADR 保持 原样；新的 ADR 引用旧的并解释改变了什么。

让这些 ADR 有价值的，是它们记录了没有奏效的东西：0020 记录了连续九次失败的执行，0027 记录了一个 在产生它的同一次会话中就被修订的理由。被省略的坏后果 正是六个月后会缺失的那一部分。
